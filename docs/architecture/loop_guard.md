# Loop guard

**Source:** `alan/loop_guard.py`

Bounded-revisits + stall detection between the router and the dispatcher. Runs after `select_next_team` returns an `enqueue` decision; if the cap is exceeded or the team is looping, the decision is converted to `escalate`.

## Spiral detection

Spiral detection runs **before** the revisit cap and Jaccard stall checks. When a `verification ↔ implementation_fix` round-trip has already completed at least once on the same `handover_chain_id`, the next iteration is classified and short-circuited at iteration 2 rather than waiting for the generic cap (3–4) to exhaust. This yields a typed escalation reason so users can distinguish "verifier overstrict" from "real defect impl_fix can't fix".

**Precedence:** spiral → revisit cap → Jaccard stall

### Detection conditions (all must hold)

1. The inbound `from_team`/`next_team` pair is `(implementation_fix, verification)` or `(verification, implementation_fix)`.
2. `revisit_counts[f"{next_team}|{handover_chain_id}"]` ≥ 1 (at least one prior round-trip on this chain).
3. A prior same-chain handover from the *other* team (the one not emitting the current handover) can be found on disk. The current in-memory handover serves as the anchor for its own team.
4. The current verification handover does **not** carry an actionable gate block (`_has_actionable_gate_block` — see below). An actionable block short-circuits the whole detector: there is concrete, machine-identified work to hand to `implementation_fix`, so no spiral kind applies.
5. `_is_impl_fix_stuck(impl_fix_h)` is true **or** `_verifier_reports_persistent_clean_block(workspace, verif_h)` is true (see below).

If any condition fails, the call falls through to the revisit cap check.

#### Condition 4–5 helpers

**`_has_actionable_gate_block(verif_h)`** — `GATE_ACTIONABLE: yes` appears inside the handover's `## External Gate Status` section (see below). Checked before either condition-5 trigger, so it overrides both.

**`_is_impl_fix_stuck(impl_fix_h)`** — the `implementation_fix` handover either contains `produced no commits — escalating` in `full_synthesis` or raises a blocking `non_actionable_feedback_*` question with `resolver_role == "human"`.

**`_is_clean_external_block(verif_h)`** — the verification handover's `full_synthesis` contains `## External Gate Status` or `SCENARIOS_MISSING` **and** `effective_critical_count(...) == 0`, i.e. `DIFF_FINDINGS_CRITICAL_IN_SCOPE` when the judge emitted it and `DIFF_FINDINGS_CRITICAL` otherwise. A marker with any effective CRITICAL findings is not a clean block (genuine defects still recycle normally).

**Actionable vs non-actionable gate blocks.** The verifier classifies the block before writing it, via `_verification_gates._resolve_actionable_gate_checks` — survivor-evidenced promotion (`evidenced_actionable_failing_checks`) with a diff-join fallback (`diff_attributable_e2e_checks`: failing spec file in the PR diff, or a failure-message locator token removed by it — see `merge_recovery.md`'s "Diff-join attribution"). The marker semantics for consumers are unchanged. It emits either

```
GATE_ACTIONABLE: no
```

or

```
GATE_ACTIONABLE: yes
GATE_ACTIONABLE_CHECKS: <name> | <name>
```

The signal travels as **text in the handover**, not as a call: the import contract layers `merge_recovery` above `loop_guard`, so `loop_guard` cannot ask it anything. `loop_guard` matches the marker string, which `alan/teams/verification.py` exports as `GATE_ACTIONABLE_YES` so a rename trips ruff/pyright rather than silently reverting to escalate-on-everything.

The banner keys on the same classification but not on the marker. `_verification_gates._downgrade_output` prepends `_GATE_PARK_HEADER_ACTIONABLE` — which keeps the `> PARKED ON EXTERNAL GATES` prefix, drops "not a code-quality rejection", and says the named checks are red on this diff and in scope for the fix round — when the actionable tuple is non-empty, and `_GATE_PARK_HEADER` otherwise. The selection reads the tuple, never `GATE_ACTIONABLE: yes`, because `_gate_actionability_lines` also emits that marker for a `DIRTY` merge state with an empty tuple: a conflicted branch with no named checks keeps today's wording, as does a `GATE_ACTIONABLE: no` block.

An actionable block means the red checks *are* this diff's own defects and code changes can clear them, so the spiral short-circuit must not fire — routing proceeds to `implementation_fix`, bounded by the ordinary `REVISIT_CAP` (three attempts, then escalate). PR #855 is the motivating case: a broken new Playwright spec plus 6.0% duplication on new code, both fixable, both escalated as "external" before this distinction existed. Handovers written before the marker existed carry neither string and are treated as non-actionable, preserving the old behaviour with no migration.

The check sits at condition 4 — above *both* condition-5 triggers — because `_is_impl_fix_stuck` otherwise vetoes it. The motivating shape: a verifier emits `GATE_ACTIONABLE: yes` naming specific failing checks, but the preceding `implementation_fix` round ran before that scope existed, found nothing in the judge review, and parked a blocking `non_actionable_feedback_*` question. `_classify_non_actionable` runs first in `_classify_spiral`, so without condition 4 sitting above it the run would escalate with concrete fixable work still in hand. When the verifier names specific failing checks and `implementation_fix` says "nothing to fix", the verifier's evidence wins and impl_fix gets the round with the scope it was missing; if it really cannot fix them, the revisit cap still ends the loop.

Known residual, corrected: rerun evidence (`pr_<n>_gate_survived.json`) is written only by the pre-approval verifier lane (`_verification_gates._maybe_rerun_flaky_gates` → `record_flake_survival`) — the post-approval `pr_merge` lane (`merge_recovery._recover_transient_flake`) triggers a rerun but never settles-and-compares, so it never writes survivor evidence (see the "Merge-lane gap" note in `docs/architecture/merge_recovery.md`). A prior version of this note claimed the opposite; it was backwards. A PR whose *only* red check is a genuinely-broken `Frontend E2E` still reads as `GATE_ACTIONABLE: no` (non-actionable) here whenever no survivor evidence yet exists, because that check sits on `SHARED_FLAKY_ALLOWLIST`. Since 2026-08-04 (incident PRs #944/#947) a survivor record at the *current head* flips this to `GATE_ACTIONABLE: yes` immediately — the rerun budget is no longer a precondition, so the marker reflects the verifier's own settle-and-compare outcome on the very pass that produced it. Since the verifier's own downgrade path computes this same flaky-only-with-no-survivor-evidence condition directly (`_verification_gates.resolve_external_gates` / `_pr_flake_ledger.flaky_only_failing`, see `docs/architecture/merge_recovery.md`'s "Verifier-lane parity" section) and routes such cases to `pr_merge` instead of `implementation_fix`, the `verification ↔ implementation_fix` round-trip this spiral detector exists to catch no longer occurs for this case — the second leg never dispatches to `implementation_fix` in the first place. (Until 2026-08-20 that held only while no verifier REQUEST_CHANGES from a prior head was still standing: the bot's own stale review made `flaky_only_failing` return False at snapshot time, so the second leg *did* dispatch `implementation_fix` and dead-ended — PR #1159, issue #1163; closed by the verifier-lane review-decision derivation and dismiss-before-snapshot in `pr_iteration_pipeline.md` D12a.) The `pr_merge` lane's own `REVISIT_CAP`-bounded remediation retry supersedes this spiral path here instead. `resolve_external_gates`'s `rescue_only` gate-path mode (a `REQUEST_CHANGES` verdict with zero effective criticals — see `docs/architecture/pr_iteration_pipeline.md`'s D14 "Gate-path modes" note) returns the judge output byte-identical, so this spiral detector — and every other `full_synthesis` predicate above — sees nothing new from that mode either. A `rescue_only` or `skip` pass's fix round instead reads the red required checks itself, live, at fix-dispatch time (`alan/teams/_fix_gate_checks.py::live_failing_checks`, see `docs/architecture/pr_iteration_pipeline.md`'s D11) — that read renders straight into the fix worker's prompt and writes nothing back onto any handover, so it is invisible to every predicate on this page: `_has_actionable_gate_block`, `_is_clean_external_block`, and `_classify_external_gate_blocked` all still see exactly the same `full_synthesis` they saw before #1430.

The red-checks block that read renders (`_fix_gate_checks.gate_failures_block`) extends its "in scope exactly like a review finding" framing in two sentences, both placed ahead of the untrusted-output notice: the files a named check's repair requires are in scope too, and a worker that finishes the round with a named check still red declares it under `## Open questions` in a `[BLOCKING]` bullet with the reason — the same mark and section that `_fix_prompt.INSTRUCTION_DECLINE_GUIDANCE` names, cross-referenced rather than restated. The scope sentence is inclusion, never exemption: the file-scope restriction is stated in the system prompt (`SCOPE_DEFERENCE_NOTICE`), which this block cannot edit, so it says the finding's files are in scope and asserts nothing about the restriction not applying. A repair whose file is a tightening-only baseline stays closed by `## Absolute prohibitions`, and the worker declares it.

**`_verifier_reports_persistent_clean_block(workspace, verif_h)`** — both the current verification handover and the most-recent prior verification handover on the same `handover_chain_id` (found via `_find_latest_prior_for_team`) are clean external blocks. Exactly two consecutive verifier passes must both show the block; a single clean-block pass does not trigger early exit, giving `implementation_fix` one cycle to attempt resolution before short-circuiting.

When condition 4 passes via the persistent-clean-block path (i.e. impl_fix kept committing but the external gate remained), `_classify_external_gate_blocked` and `_classify_scenarios_missing` are reached and produce a **typed** escalation reason — the loop does not burn all `REVISIT_CAP` revisits on a block that code changes cannot resolve. "Cannot resolve" is now a decided fact rather than an assumption: only a `GATE_ACTIONABLE: no` block reaches this path.

**Disk-persistence note:** the dispatcher's `save_handover` call precedes `detect_spiral`; the current verifier handover is already on disk when the check runs. `_find_latest_prior_for_team`'s `handover_id` exclusion prevents it from returning the current handover as its own prior.

### Unchanged actionable gate checks across three passes

An actionable gate block (condition 4, above) exists precisely so a diff with concrete, machine-identified fixable work gets routed to `implementation_fix` instead of parked — bounded by the ordinary `REVISIT_CAP` of three attempts. That bound was originally meant to be tight: `loop_guard.md`'s original note on the actionable path (above) intended an actionable red to cost at most the ordinary three-attempt cycle before something changed. The revisit-count *decay* mechanism (`has_forward_progress`/`_artifacts_changed`, see **Revisit caps** below) quietly removed that guarantee — a fix worker that changes its artifact set every round, without ever clearing the named checks, keeps decaying the counter back down and never trips `REVISIT_CAP`, so the same actionable failure set can recur indefinitely with no escalation. This section restores the three-attempt bound for that one shape, without touching the decay mechanism itself.

**The rule.** When the current verification handover (`from_team == "verification"`) reports a clean actionable gate block (`GATE_ACTIONABLE: yes`, `effective_critical_count(...) == 0`) and its named `GATE_ACTIONABLE_CHECKS` set has at least one member in common with the same computation on *each* of the two preceding verification passes on the same `handover_chain_id` — three consecutive verification passes in all — `detect_spiral` fires with `kind="external_gate_blocked"` and evidence naming the intersection — at the third pass, not the sixth (fix-cycle ceiling) or the `REVISIT_CAP`-bounded ordinary path.

**Three-way intersection, not pairwise.** The computation (`_unchanged_actionable_checks`) takes the current pass's clean-actionable-check set and intersects it, in turn, with each of the two immediately preceding verification passes' own clean-actionable-check sets (walked backwards via `_prior_verification_passes`, bounded to `_UNCHANGED_WALK_LIMIT - 1 = 2` priors). Only a check present in all three passes survives. A **shrinking** set fires deliberately: `{A,B}` → `{A,B}` → `{A}` still intersects on `A` — a check that outlives two full fix cycles is evidence the wall hasn't moved, even if a sibling check came and went. This mirrors the clause-stall detector's own choice of intersection over exact-equality (see below) for the same reason: the cost of a false positive here (an unactionable park, since this path raises no human question) is asymmetric with the cost of a missed one (bounded anyway by the ordinary revisit cap), so the detector leans toward firing rather than waiting for a bit-exact repeat.

**Why a genuinely fixable first-occurrence red never fires.** The backward walk requires two full prior verification passes on the chain before it will even compute an intersection; `_unchanged_actionable_checks` returns the empty tuple outright when fewer than two priors are found. A brand-new actionable block — the common case, since most PRs clear their gate checks in one or two fix cycles — has zero or one prior verification pass on the chain and cannot reach this rule at all. It falls straight through to the pre-existing condition-4 short-circuit and routes to `implementation_fix` exactly as it always has. The same emptiness falls out of the intersection itself for a wall that changed character mid-chain: a `GATE_ACTIONABLE: no` pass contributes the empty set (`parse_actionable_gate_checks` never matches `no`), so `no → yes → yes` never fires even though the last two passes share a check — the `&=` against the `no` pass's empty set collapses the whole intersection before the walk finishes.

**The bypass is exactly two preconditions, not three.** Reaching this rule requires bypassing:
1. The revisit-count gate (`detect_spiral`'s `revisit_counts.get(key, 0) < 1` check) — this shape's whole premise is that a human question should not wait for a prior round-trip to have been *counted* by the ordinary bookkeeping, since the decay mechanism can keep that counter at zero indefinitely.
2. The actionable-gate-block short-circuit (`_spiral_anchors_to_classify`'s condition 4) — this is the specific short-circuit this rule exists to override for the unchanged-set case.

The **third** precondition on the classify path — `_verifier_reports_persistent_clean_block`, requiring the current and immediately-prior verification pass to both be clean external blocks — needs no bypass at all: `_is_clean_external_block` only checks for the gate marker plus a zero effective-critical count, not for actionability, so it is already `True` on both passes for this shape without any code change. Giving it a bypass as well would be a redundant third one.

**Findings attributable to the diff are excluded, not merely deprioritised.** `_actionable_checks_if_clean` returns the empty set for any pass with `effective_critical_count(...) > 0`, regardless of what its `GATE_ACTIONABLE_CHECKS` line says — a pass carrying its own CRITICAL findings is not admitted into the intersection at all, so it cannot contribute to nor break a three-pass overlap; the three-way `&=` collapses to `frozenset()` the moment any one of the three passes fails this test, and that pass's own routing is untouched, falling through to the ordinary classifiers.

**Human intervention is transparent, not a reset — with one ordering hazard.** The backward walk (`_prior_verification_passes`) skips an answer-recording `revisit_amend` (`_is_transparent_amend`, a local duplicate of `alan/teams/_clause_stall.py`'s helper of the same name, kept in sync by grep only since that module is private and adjacent to parked clause-withdrawal work) via `continue` — it neither counts as one of the three passes nor breaks the walk. A **non**-answer-recording `revisit_amend` (an operator amendment that records no answer) does break the walk, clearing whatever passes had been collected so far. The transparent-amend test **must** run before the `from_team == "verification"` test: `record_answer` copies `from_team` from the blocking handover, so a human's answer recorded on a verification handover is itself `from_team == "verification"`. Testing `from_team` first would read the human's own answer as a fourth repeating verification pass and the guard could never release once it started firing — this is the same ordering hazard the clause-stall detector already had to solve (see below), solved the same way, independently, because that module's version of the helper is private and this code does not import it.

### `SpiralKind` classification rules

| Kind | Detection rule |
|---|---|
| `external_gate_blocked` (unchanged-set path) | `_classify_unchanged_gate_checks` — the three-pass unchanged-actionable-checks rule above fired; `unchanged_checks` is non-empty. Runs first in `_classify_spiral`, ahead of `_classify_non_actionable`, so a stale `non_actionable_feedback_*` question from an earlier, narrower-scoped `implementation_fix` round cannot mis-type this park (see PR-citation note above). No new `SpiralKind` member: this reuses `external_gate_blocked`, since every shape that reached `_classify_spiral` before this rule existed had already passed `not _has_actionable_gate_block`, making the new classifier provably unreachable for any pre-existing shape. |
| `non_actionable_finding` | The latest `implementation_fix` handover has a blocking `open_question` whose `id` starts with `non_actionable_feedback_` and `resolver_role == "human"`. |
| `scenarios_missing` | The latest verification handover's `full_synthesis` contains `SCENARIOS_MISSING` **and** `effective_critical_count(...) == 0`. |
| `external_gate_blocked` | The latest verification handover's `full_synthesis` contains `## External Gate Status` **and** `effective_critical_count(...) == 0`. Reachable only for a `GATE_ACTIONABLE: no` block — an actionable one short-circuits at condition 4, before any classifier runs (unless the unchanged-set bypass above admits it). Note: when all failing checks are quarantined (pre-existing or known-flake), `check_pr_verifier_blockers` removes them from `failed_reasons`, so the verifier never adds the gate block marker — this spiral kind is not triggered for all-quarantined blocks. |
| `verifier_repeating_unresolved` | The latest verification handover's `effective_critical_count(...)` is non-zero, **and** its `(path, line)` CRITICAL-anchor set — parsed via `alan.teams.verification.parse_inline_findings` from the handover's `## INLINE_FINDINGS_YAML` block — is non-empty **and** exactly equal to the prior verification handover's anchor set on the same chain. Counts and prose play no part in either direction. See below. |
| `genuine_defect` | `DIFF_FINDINGS_CRITICAL: N` with N > 0 in the latest verification handover. |
| `unclassified` | Fallback when none of the above match. |

Classifiers run in the order shown; the first match wins. The unchanged-set row above is listed first because it *is* checked first in `_classify_spiral`: reaching it with a non-empty `unchanged_checks` is only possible via the bypass described above, and placing it ahead of `non_actionable_finding` stops a stale `non_actionable_feedback_*` question — raised by an earlier, narrower-scoped `implementation_fix` round — from mis-typing this park as `non_actionable_finding` instead. Among the remaining rows, `non_actionable_finding` runs first because it signals impl_fix's own diagnosis, independent of the verifier's output.

#### `verifier_repeating_unresolved`

Added 2026-08-21 as the backstop for when the verifier does not declare a capability boundary. A verifier can mark a `REQUEST_CHANGES` finding as unresolvable by any fleet role with `NO_FLEET_ROLE_CAN_FIX:` (`alan/teams/_verification_capability.py`, `declared_capability_boundary`); when that marker is present, `alan/teams/_verification_review_post.py`'s `_emit_capability_boundary_escalation` builds a blocking `verification_escalation` human question directly on the verification handover, so `select_next_team` returns `await_human` and `_enforce_loop_guard` never calls `detect_spiral` at all — the declaration short-circuits ahead of this classifier, and `verifier_repeating_unresolved` cannot fire when it is present.

When the declaration is **absent** — which the system already concedes happens often enough to warrant this backstop, since incidental commits (a review-thread reply, a low-severity tidy) are almost always available to `implementation_fix` and keep `_is_impl_fix_stuck` from tripping even when the verifier's real finding goes unaddressed — `_verifier_repeats_unresolved(workspace, verif)` classifies the repeat instead of leaving it to fall through to `genuine_defect`. Reaching it requires widening `_spiral_anchors_to_classify`'s condition 5: `_verifier_repeats_unresolved(workspace, verif_h) is not None` is a third way to admit a pair for classification, alongside `_is_impl_fix_stuck` and `_verifier_reports_persistent_clean_block`. Without that widening, a normally-committing `implementation_fix` handover never satisfies condition 5 and this classifier — despite being present and unit-tested — would never actually run in the real routing path.

**Identity rule.** Since #1405, this classifier no longer compares critical counts or prose similarity at all — in either direction. It compares finding *identity*: the set of `(path, line)` anchors the verifier attached to its CRITICAL findings. The anchors come from the same `## INLINE_FINDINGS_YAML` block that `alan/teams/_verification_review_post.py` already emits one entry per CRITICAL finding into, read via `alan/teams/_inline_findings.py::parse_inline_findings` (re-exported from `alan/teams/verification.py`); the judge copies each finding's path/line verbatim, and sibling-owned locations on a decomposed workspace are included in the compared set exactly as they appear — only the in-scope gate (`effective_critical_count(...) > 0`) that decides whether the *current* pass reaches this classifier at all is scoped, not the anchor set itself. Matching is exact equality of the full `frozenset[tuple[str, int]]`: no path normalisation, no line-number tolerance, and a partial overlap, subset, or superset never fires. If either pass's block is missing, empty, or fails to parse (malformed YAML, or every entry missing a valid `path`/`line`/`body`), `parse_inline_findings` returns no anchors for that pass and the classifier does not fire — there is no fallback to counts or text similarity. Per-entry parsing is lenient: a block with some invalid entries alongside valid ones still contributes the valid entries' anchors.

This replaces the `_UNRESOLVED_STALL_THRESHOLD = 0.45` count-and-`_is_stalled` rule added 2026-08-21, retired here because all three of its recorded live firings were false positives that identity catches cleanly: two anchored their two passes in different files entirely, and the third anchored the same file 14 lines apart. None of the three has identical `(path, line)` anchors across passes, so none fires under the identity rule. The motivating case (#1143, `pyproject.toml:289` on three consecutive passes) is still caught — each consecutive pair shares one identical anchor, so the classifier fires at the second pass exactly as before.

**Accepted residual risk.** Exact-line matching can miss a genuine repeat that the verifier re-anchors to a different line across two passes. Such a case simply returns to how this loop behaved before this classifier existed (2026-08-21): the ordinary revisit-cap and Jaccard-stall paths still bound it, so it is no worse than before, not a new failure mode.

**Scope.** This backstop stops the workspace at the *second* consecutive verification pass instead of dispatching a third `implementation_fix` run — it converts what would have been a third verify-fix cycle into a one-cycle-earlier escalation. It does not generalise to a chain where `implementation_fix` already revisited twice before the verifier started repeating: the ordinary revisit-cap and Jaccard-stall paths still own that longer chain, because by then the per-team bookkeeping this classifier reads (the single before/after verification pair) no longer characterises the whole history.

Since 2026-08-20 (#1164) a `GATE_ACTIONABLE: no` downgrade no longer produces the `verification → implementation_fix → non_actionable_feedback` pair at all on the first round: `suggestions_for_verdict`'s `gate_non_actionable` flag routes it to `pr_merge` (see `pr_iteration_pipeline.md`'s routing table), so both `external_gate_blocked` and `non_actionable_finding` now fire only for legacy handovers and for the genuine-finding shape (`tests/fixtures/transitions/non_actionable_dead_end/`). The classifier order is unchanged; `tests/fixtures/transitions/non_actionable_gate_reroute/` pins that the rerouted handover trips neither the spiral pair nor the revisit cap.

The verification markers (`SCENARIOS_MISSING`, `## External Gate Status`, `DIFF_FINDINGS_CRITICAL:`, `GATE_ACTIONABLE:` and its `yes`/`no`/`GATE_ACTIONABLE_CHECKS:` forms) are exported as public constants from `alan/teams/verification.py` so a rename trips ruff/pyright instead of silently falling back to `unclassified`.

## Clause-stall short-circuit

**Source:** `alan/teams/_clause_stall.py`, `alan/teams/_verification_review_post.py`, wired into `VerificationTeam._build_verdict_handover` (`alan/teams/verification.py`).

The two mechanisms above key off a critical-finding count, a gate marker, or trigram similarity between two `full_synthesis` strings — none of which sees a clause the judge and the clause auditor agree is failing for a reason no fleet role can act on (the judge cannot demote its own clause auditor's evidenced FAIL, and a fix worker's only compliant moves are to refuse on rules grounds and escalate, or ship code that cannot satisfy the clause). That unresolvability is *why the detector exists*, not something the host observes on any given firing: the host observes exactly one thing — the same clause ids in the actionable set of two consecutive verification runs — and the stall question tells the operator only that. A judge writing a deeper justification each round defeats the Jaccard-stall check by construction, and the clause override carries neither a critical count nor a gate marker, so it is invisible to both existing detectors. `alan.teams._clause_stall.detect` closes this gap directly: it recognises when **any clause id is actionable in both** of **two consecutive verification runs on the same `handover_chain_id`**, regardless of what ran in between. That non-empty intersection — `_repeated_actionable_ids`, compared as sets so auditor row order is irrelevant — is the trigger. The overlap may hold more than one clause: a correlated group, the normal shape since one scoping conversation typically mints several measurement obligations together, trips the detector exactly as a single repeating clause does.

**Why the intersection and not exact set equality.** Until 2026-09-17 the rule was bit-exact set equality between the two runs, and an asymmetric or shrinking set was read as evidence of progress. That is wrong when the set moves for a reason other than progress. The clause auditor is an LLM, and on a workspace that delivers one roadmap item as a manual sequence of PRs every item-level clause is audited against every PR (`_clause_audit._select_requirements` takes the `len(meta.tasks) <= 1` branch), so a large fixed clause set produces a *different* actionable subset on each run at an unchanged HEAD. X2.2 / PR #1537 did exactly that — `{A,B}`, then `{A,B,C}`, then `{A,D,B}` — never matched, never stalled, and the workspace dead-ended in `escalated` with no open question after a fix worker correctly refused to commit (alan#1538). Exact equality made the *only* human escape hatch conditional on an LLM emitting a bit-identical set twice; the intersection does not. A premature stall costs one human answer, and one of its two options is "you were wrong, re-dispatch verification"; a missed stall costs an unbounded fix/verify loop with no operator exit. The asymmetry is the whole argument.

**Identity and scope are deliberately different sets.** `ClauseStall.clause_ids` is the *current* run's full actionable set — it drives the question text, and the escalation separately carries the whole `ClauseOutcome`, so answering withdraws every currently-actionable id. `ClauseStall.repeated_ids` is the intersection, and it alone derives the question **id**. Keying the text on the overlap would withdraw ids the human was never shown, and `Requirement.withdrawn_by_question_id` is write-once. Keying the id on the full set would reproduce the defect one level up: a flapping auditor would mint a *new* `clause-stall-<digest>` on every pass instead of re-raising one question. The overlap is the only thing a flapping auditor holds stable. For a single repeating clause the two sets coincide, so no previously persisted question id changes meaning.

`_build_verdict_handover` short-circuits in a fixed precedence order, each check reachable only if every check ahead of it did not fire:

1. **Capability-boundary declaration** (`_capability_boundary_handover`) — the judge's own `NO_FLEET_ROLE_CAN_FIX:` marker (see above). This is the front door: the judge is instructed to emit it on first occurrence, including when it disagrees with the clause auditor on **vacuity grounds** — a clause asserting a precondition the delivered design cannot satisfy, whose only compliant implementation would be unreachable code (`alan/teams/_verification_prompts.py`'s `_JUDGE_PROMPT`). When the judge declares it, the clause-stall detector below never runs — the specific, first-occurrence channel always wins over the generic, two-run backstop.
2. **Clause-PR-state escalation** (`outcome.escalate_unactionable`) — an existing check, unchanged; a clause whose only evidence is unactionable PR state.
3. **Clause stall** (`_clause_stall.detect`) — the backstop for exactly the case above when the judge did *not* declare a capability boundary on the first occurrence. It is a two-run detector, not a one-shot: a single actionable FAIL never trips it, only a clause id that is actionable on two consecutive verification passes on the same chain. Two runs whose actionable sets are wholly **disjoint** are the remaining progress signal and still route to `implementation_fix`.
4. Normal routing (`suggestions_for_verdict`) — unchanged.

**Detection conditions (`alan.teams._clause_stall.detect`).** Given the incoming handover to this verification pass and the just-computed `ClauseOutcome` for the current pass:

- The current pass's `ClauseOutcome.actionable_ids` must be **non-empty** — an empty set means nothing actionable failed and the detector never fires. A shrinking or asymmetric set (e.g. `{X, Y}` then `{X}`, or `{X, Y}` then `{X, Z}`) *does* now fire, on `X`: the surviving clause outlasted a full fix cycle, and the ids that moved are as likely to be auditor nondeterminism as progress. Only a wholly disjoint pair (`{X}` then `{Y}`) is read as progress.
- `alan.teams._clause_stall._latest_verification_since_intervention` scans `alan.handover.list_handovers(ws)` backwards (never a subtask-scoped file glob, since handovers are filed under the *workspace's* `task_id`, not the audited subtask's — see `docs/architecture/acceptance_gate.md`), matching the incoming handover's `handover_chain_id`. An answer-recording `revisit_amend` (`_is_transparent_amend`) is **transparent**: it is skipped via `continue`, neither counted as a pass nor treated as a reset. It returns `None` — resetting the count — the moment it meets a **non**-answer-recording `revisit_amend` handover on that chain; only if the next chain-matching, non-transparent handover is itself `from_team == "verification"` does it return that as the prior pass. An `implementation_fix` (or any other non-`revisit_amend`, non-`verification`) handover in between is skipped, not treated as a reset — a fix worker's intervening commit is not, by itself, evidence the count should reset.
- The prior pass's `ClauseOutcome` must exist, its `task_id` must match the current pass's, and `set(prior.actionable_ids) & set(current.actionable_ids)` must be non-empty — a set intersection, so the auditor listing clauses in a different row order across the two passes is irrelevant, and so is any id that appears in only one of them.

**Human intervention is transparent, not a reset.** `record_answer` (`alan/handover.py`) always writes `handover_type="revisit_amend"`, copying the blocking handover's `from_team` — so a human answering the clause-stall escalation and re-dispatching verification produces a `revisit_amend` handover on the chain that also records an answer (`is_answer_recording`). The scan above treats that specific shape as **transparent**, not a reset: it is skipped and the walk continues past it. This is why the transparent-amend check must run *before* the `from_team == "verification"` check when scanning backwards: `record_answer` copies `from_team` from the blocking handover, so a human's own answer recorded on a verification handover is itself `from_team == "verification"`. Without the transparent check running first, that answer would misread as "another verification run repeating the same clause" and the guard could never release. Only a **non**-answer-recording `revisit_amend` — an operator amendment that changes something on the chain without recording an answer — is treated as a reset.

**Never stand down.** Every path that can observe the vacuity case — the judge's own declaration, or the two-run detector — routes to a blocking, `resolver_role="human"` `OpenQuestion`; neither can resolve to normal routing on its own. `ClauseStall` (`alan/teams/_clause_stall.py`) carries `clause_ids: tuple[str, ...]` — the current pass's full actionable set, which is also the withdrawal scope — plus `repeated_ids: tuple[str, ...]`, the intersection that triggered the stall and the sole input to the question id, and a `clauses: tuple[StalledClause, ...]` — one `StalledClause(req_id, text, evidence)` per id in `clause_ids`, each string still bounded to 2000 characters, the `ScenarioOutcome.diagnostic` precedent — and the shared `judge_rationale` (also 2000-bounded). The clause-stall question (`alan/teams/_verification_review_post.py`'s `_emit_clause_stall_escalation`) renders one `Clause <id>: <text>` / `Evidence: <evidence>` block per `StalledClause`, so a repeated group of any size is named in full. The question asserts only what the host observed — the repeating ids, that they failed as actionable on two consecutive verification runs on this handover chain, and the currently actionable set an answer acts on — and no longer borrows the `NO_FLEET_ROLE_PHRASE` constant (`alan/teams/_verification_capability.py`) or claims the clause is unresolvable, unfixable or a matter for a human scoping decision. That phrase stays exclusive to the capability-boundary question, where the judge actually declared it; the two channels are deliberately not worded as the same class of problem, because only one of them observed a declaration. Its two options — "rewrite or drop this clause, then re-dispatch verification" (`pending_external`) and "waive this clause and proceed to merge" (`closes`) — add no new member to the clause-actionability demotion vocabulary (`alan.teams._clause_actionability.ClauseActionability`); they are the same `OpenQuestion.option_effects` shape the capability-boundary escalation already uses, not a new gate downgrade. The question id is derived from `repeated_ids`, not `clause_ids`: `clause-stall-{id}` for a single repeating clause (unchanged, preserving dedupe against a previously-answered singleton question) and a bounded `clause-stall-{16-hex}` — a `sha256` of the sorted, comma-joined repeated ids — for a group of more than one, since `alan/routes/answer.py` caps `question_id` at 200 characters and a raw joined-id form could exceed that on a large group. Because the question text names every clause in `clause_ids` while the id names only the overlap, the question states explicitly that an answer acts on the whole listed set.

**Why the question's accuracy and lead wording matter.** The question text does not stay on the operator's card. The park's blocker record keeps only its first 500 characters (`alan/router.py`, `question.question[:500]`), and the issue comment the autonomous unblocker files slices that again to its first 300 (`alan/unblock_sweep.py`). `alan/routes/answer.py` injects the same text into a dispatched resolver team's instructions, and `alan/compression.py` folds it into compacted worker context — so an unobserved assertion in it is read as fact by a fleet role, not only by a human. The one full-text render (`alan/web/src/features/workspace/components/OpenQuestionItem.tsx`) collapses blank lines, so the wording must not depend on paragraph breaks for legibility. The template therefore leads with the two-run statement naming the repeating ids, then the actionable-set sentence, then the clause blocks and the judge's reasoning. With two repeating ids the lead paragraph is 172 characters. Measured against the current template, the 300-character slice keeps the two-run statement whole up to 12 repeating ids and keeps each id whole up to 15; at 16 repeating ids the slice cuts an id mid-token. The 500-character slice keeps the actionable set whole up to 13 ids when two repeat, and cuts the 14th mid-token. These limits are documented, deliberately not coded: every observed stall fits with room to spare, and a bounding branch would cost complexity and branch-coverage budget for a scale nobody has observed.

**An answered overlap id is never reused for a wider scope.** `_stall_question_id_for` (`alan/teams/_verification_review_post.py`) falls back to the `clause_ids`-derived id when `alan.handover.find_recorded_answer` already finds an answer for the overlap id on this chain. This exists because the stability that makes the overlap a good identity also makes it collide across stalls with *different* withdrawal scopes: `find_recorded_answer` keys only on `(chain_id, question_id)`, and `answer.py`'s replay branch (`_claim_already_answered`, kept for rulings recorded before the withdrawal mechanism existed) resolves the ids to withdraw from the **latest** escalation's `ClauseOutcome`. Without the fallback, a stall that repeats on `{A}` but now carries `{A, B}` would inherit the earlier `clause-stall-A` ruling and withdraw `B` — a clause the human never saw — irreversibly, since `withdrawn_by_question_id` is write-once. When the scope is unchanged the fallback returns the same id, so ordinary dedupe against a previously-answered question is preserved.

**Deferral records are outputs, not inputs.** `detect` appends a `clause_stall_detected` row to `verification_audit.jsonl` (`task_id`, `audited_task_id`, `req_id` — the first clause id in sorted order, kept for existing readers — plus a `req_ids` list naming every currently-actionable clause, `repeated_req_ids` naming the intersection that fired the detector and from which the question id can be recomputed offline, `prior_req_ids` naming the prior pass's set, without which an exact repeat cannot be told from a partial overlap when diagnosing a suspected premature stall, and `prior_handover_id`) purely as a record of what the host decided — nothing about the detector's decision is read back from that file, and nothing a judged role writes can populate or influence a `ClauseOutcome`: it is built exclusively by `alan.teams._clause_audit._clause_outcome_from_rows` from the clause auditor's parsed `CLAUSE` rows and the host's own `ClauseAuditContext`, restricted to the batch's actionable rows.

### Escalation format

When a spiral is detected, `_enforce_loop_guard` returns:
```
RouterDecision(kind="escalate", reason="spiral:{kind}: {evidence}")
```

`evidence` is ≤ 300 characters referencing the specific verifier output or impl_fix summary that triggered the classification.

### `spiral_audit.jsonl` schema

Each spiral detection appends one JSON line to `~/.alan/logs/spiral_audit.jsonl` (override via `ALAN_LOGS_ROOT`):

```json
{
  "timestamp_utc": "2026-05-20T14:30:00.000000+00:00",
  "task_id": "my-workspace-slug",
  "kind": "scenarios_missing",
  "evidence": "verifier output contains SCENARIOS_MISSING with 0 critical findings",
  "handover_chain_id": "handover_my-workspace-slug_abc123",
  "revisit_counts_snapshot": {"verification|handover_my-workspace-slug_abc123": 1}
}
```

Cap-exhausted escalations (revisit cap exceeded or Jaccard stall) that were **not** preceded by a spiral detection also emit a `cap_exhausted_no_spiral` record into the same file with `kind="cap_exhausted_no_spiral"`. This gives the upcoming `replace-completed-fraction-with-flow-metrics` workspace a single audit source covering all loop-guard escalations.

`chain_decay` records are emitted when the dispatcher detects forward progress and decays the revisit count instead of incrementing it (see **Revisit caps** below). `chain_reset` records are emitted by `dispatch_team_core` (`alan/dispatch.py`) whenever a dispatch with a prior handover resets the entire chain — manual dispatch (`dispatch_task_team`), propose-mode approval, and auto-continue all route through it.

`LoopGuardAuditKind` is the full set of possible `kind` values in `spiral_audit.jsonl`: the six `SpiralKind` values plus `cap_exhausted_no_spiral`, `chain_decay`, and `chain_reset`. `SpiralFinding.kind` is typed as `SpiralKind` only (the 6-value subset) so `SpiralFinding(kind="cap_exhausted_no_spiral", ...)` is a type error.

The finisher-rate funnel (`alan/finisher_rate.py::_build_spiral_index`) excludes the two bookkeeping kinds `chain_decay`/`chain_reset` from its spiral index — they mark healthy control flow (forward-progress decay, chain reset on re-dispatch), not convergence failures — while the six `SpiralKind` values and `cap_exhausted_no_spiral` still classify an unmerged task as `not_converged`. Because `finisher_rate` layers below `loop_guard` in the import contract, the exclusion set is a local frozenset (`_BOOKKEEPING_AUDIT_KINDS`); `tests/test_finisher_rate.py::test_bookkeeping_kinds_partition_loop_guard_audit_kinds` asserts the partition over `LoopGuardAuditKind` is exhaustive, so adding a new kind fails CI until the filter decision is made explicitly. `scripts/intervention_report.py` deliberately still consumes `chain_reset` rows from this same file.

## Revisit caps

Per-team rerun cap per task, flat across all teams:

`REVISIT_CAP = 3` — every team gets 3 revisits before the loop guard escalates.

### Increment vs decay

After every team finishes, the dispatcher calls `has_forward_progress(workspace, handover, next_team)` to choose between two paths:

- **No progress** → `increment_revisit_count(ws, from_team, chain_id)` as before.
- **Forward progress** → `decay_revisit_count(ws, from_team, chain_id)` (decrements by 1, floor 0) + emits `chain_decay` audit row.

`has_forward_progress` returns `True` when any of these signals are present:
1. `next_team == "pr_merge"` (approval path).
2. `parse_verdict(prior.full_synthesis) != parse_verdict(handover.full_synthesis)` — both non-`None` and changed.
3. `parse_critical_count(handover.full_synthesis) < parse_critical_count(prior.full_synthesis)` — findings decreased.
4. `{a.path for a in handover.artifacts_produced} != {a.path for a in prior.artifacts_produced}` — artifact set changed.

### Chain reset on human intervention

`dispatch_team_core` calls `reset_revisit_chain(ws, handover_chain_id)` before enqueuing when a prior handover exists — covering manual dispatch (`dispatch_task_team`), propose-mode approval, and auto-continue. This clears all keys whose `chain_id` segment matches, giving the new run a clean slate. A `chain_reset` audit row is emitted to `spiral_audit.jsonl` in every case.

`workspace.decay_revisit_count` and `workspace.reset_revisit_chain` are public workspace functions mirroring the `increment_revisit_count` signature.

## Stall detection

Jaccard trigram similarity of `full_synthesis` between consecutive same-team handovers, with `_STALL_THRESHOLD = 0.85`. Before computing similarity, `_strip_boilerplate` removes template sections that are structurally identical across all verification outputs:

- Lines containing `VERDICT:`, `DIFF_FINDINGS_CRITICAL:`, or `SCENARIOS_MISSING`.
- The `## External Gate Status` section (from that header to the next `##` or end of string).

A stall fires when:

- `has_forward_progress` returns `False` (no progress signals), AND
- stripped-similarity > 0.85, AND
- blocking-question ID sets are unchanged between the two handovers.

The ID-set comparison replaces the former bare-count comparison, preventing false stalls when two handovers each have zero blocking questions (e.g., all verification handovers share `count == 0`).

`_find_latest_prior_for_team` also filters by `handover_chain_id`, so a stall is only detected when two consecutive handovers from the same team share the same chain.

A stall → `escalate`.

## Outcomes

`check_loop_guard(workspace, handover, next_team)` returns `RouterDecision(kind="escalate", reason=...)` when a cap is exceeded or a stall is detected, otherwise `None` (pass). The dispatcher consumes the result and either enqueues the next job or transitions the workspace to ESCALATED.

## Fix-cycle ceiling

**Source:** `alan/teams/_pr_state_paths.py` (the counter), `alan/loop_guard.py` (`fix_cycle_ceiling_reached`, `fix_cycle_park_reason`), `alan/_dispatcher_selfheal.py` (`SelfHealMixin._enforce_fix_ceiling`), `alan/dispatch.py` (the operator-path 409 and increment).

`REVISIT_CAP` and `detect_spiral` above bound a single handover chain — a chain reset (human re-dispatch) or forward progress (a changed artifact set, a changed verdict) both legitimately zero their counters, by design. Neither can bind on a PR that keeps earning fresh chains or incidental forward-progress signal while never actually converging: one observed case cycled fix work 15 times over 15 hours and 33 invocations against the same PR, roughly a fifth of the spend landing after the blocker was already provably permanent, with no question ever asked of a human. The fix-cycle ceiling is a second counter, scoped to `(pr_number, engine)` rather than to a handover chain, with no reset path at all.

**Shape.** `_pr_state_paths.FixCycleState(count, allowance, granted_question_ids)`, persisted at `pr_<n>_fix_cycles.json` in the same per-engine state directory every other PR-scoped counter in that module already uses. It deliberately carries no `head_sha` field and no reset-aware accessor — the neighbouring `GateRerunState` shape offers both a lifetime figure and a head-aware one that zeroes on every new commit, and reading the head-aware one here would reintroduce exactly the decay this counter exists to prevent. Omitting the field from the schema makes that mistake structurally impossible rather than a rule to remember. `FIX_CYCLE_CEILING = 6`; `fix_cycle_budget(pr_number, forge)` is `FIX_CYCLE_CEILING + allowance`; `fix_cycle_ceiling_reached(pr_number, forge)` is `count >= budget`.

**Increment sites.** Exactly two, both unconditional — no origin is exempt, so "an operator re-dispatch does not change the count" means it does not *reset* it, not that it is skipped:
- `SelfHealMixin._enforce_fix_ceiling`, called from `Dispatcher._apply_router_decision` immediately before `_enforce_loop_guard`, for every autonomous route (verification's forward suggestion, the merge-gate remediation rewrite) that resolves to `enqueue implementation_fix`.
- `dispatch_team_core` (`alan/dispatch.py`), for every manual dispatch, propose-mode approval, and auto-continue that targets `implementation_fix` against a prior handover with a resolvable PR number.

A different PR number always starts at zero; the counter never reads anything but this one file.

**The park.** At the ceiling, `_enforce_fix_ceiling` returns `RouterDecision(kind="await_human", team=None, block_class=None, ...)` — never `kind="escalate"`: `park.park_reason_for_decision` maps a block-class-less `escalate` to `ParkReason.ESCALATED` (no question), but a block-class-less `await_human` to `ParkReason.QUESTION` (the frontend renders one). The paired handover (`alan/teams/_spiral_handover.py::fix_cycle_ceiling_handover`) is the first consumer of `escalation_skeleton` in this codebase to populate `open_questions` on the result — the `spiral_escalation_handover` and `no_commits_handover` precedents both leave it empty, which is exactly what would have made this park unanswerable. The question names the cycle count and the last verifier finding, and its two options map directly via `option_resolvers` to `implementation_fix` (grant three more cycles) or `verification` (hand-resolved, re-verify).

**The ordering hazard.** The override option must itself pass through `alan/dispatch.py::assert_team_dispatchable` (via `answer.py`'s `_validate_resolver`) to dispatch `implementation_fix` — the same gate that refuses dispatch past the ceiling with a `409`, checked after the archived-workspace check so that one still wins. `alan/routes/answer.py::_maybe_grant_fix_cycle_override` therefore runs *before* `_resolve_answer_resolver` in `_claim`'s fresh-answer branch: the grant (`_pr_state_paths.grant_fix_cycle_override`, idempotent on the question id) lands on disk first, so the downstream ceiling check reads the widened budget rather than refusing the very answer meant to lift it.

**Severity.** `should_escalate_fix_cycle_severity(count, job_running)` lives beside the counter in `_pr_state_paths.py`, not in this module or in `health.py` — `triage_pregate.py` (which computes the `build_task` observation `health.py` later reads) sits below this module in the import-layer order and cannot import it, so the threshold constant and its one predicate function live together in the lowest layer both callers can reach. See [health.md](health.md) for the severity mapping this feeds.
