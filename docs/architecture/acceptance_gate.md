# Acceptance Gate

A workspace reaches `completed` only when every agreed `Requirement` (acceptance clause) is *proven* — by one of two paths, not one: a passing test bound via `test_ref`, or coverage by a subtask's definition-of-done clause that has been stamped with delivery evidence. This prevents partial delivery from silently finishing a workspace.

**Corrected premise (2026-09-05).** `all_clauses_satisfied` (below) is the real gate, and it is coverage-aware: it does not merely fall back to test-bound clauses whenever a workspace has *any* task-declared coverage. A measurement of the live fleet that counted only `test_ref` bindings and concluded the gate "never evaluates a single clause" was false — it missed the coverage path entirely. The corrected count, taken 2026-09-05 across 409 workspaces carrying requirements (4597 clause rows): 8 bound via `test_ref`, 1461 covered by a subtask DoD clause, and 3128 (68.0%) with **no proof of either kind** — see [Visibility: unbound acceptance and unevaluated self-heal scenarios](#visibility-unbound-acceptance-and-unevaluated-self-heal-scenarios) below for the per-clause measure that makes that last number a first-class, queryable quantity instead of an unrendered boolean.

**Implementer blindness (the "dark factory" invariant).** The team that writes the implementation never sees the acceptance scenarios that will judge it — enforced by the system in `alan/teams/_plan_projection.py`, applied inside `alan/teams/implementation.py`'s prompt-composition path, on every planning shape a workspace can take. See [implementation_pipeline.md](implementation_pipeline.md#implementer-blindness-to-acceptance-scenarios) for the mechanism. This is scoped strictly to *what reaches the implementer's prompt* — it changes nothing on this page: scenarios still reach `verification`'s `scenario_runner` exactly as before via `Handover.test_scenarios`, and every classification below (`DOCUMENTED`/`SKIPPED`/`ADVISORY`/`BUDGET_EXHAUSTED` non-blocking; `FAIL`/`TIMEOUT` blocking) is untouched. Closing the leak is expected to raise how often an acceptance reference resolves to nothing the implementer could have coincidentally matched — that is real drift becoming visible, not a new failure mode, and per the non-goals of that build it is deliberately **not** mitigated by reclassifying an unresolvable reference as blocking here.

`Requirement` is the durable **acceptance clause** — the agreed-scope checklist. It is the single concept (not a parallel one): an acceptance clause is a `Requirement` that may be *unbound* (no `test_ref` / proof yet). Phase 1a evolved it to carry a stable `id` and an optional `test_ref` so clauses can exist before any test or proof is bound; Phase 1a does **not** tighten completion (an unbound clause never blocks). The strict clause-satisfaction tightening lands in the acceptance-gate phase.

## Vocabulary

- **`Requirement`** (`alan/workspace.py`): stable content-hash `id` (`req-` + `sha256(text.strip())[:12]`, auto-minted by a `mode="before"` validator that also heals legacy `meta.json` lacking an `id`), `text`, **optional** `test_ref` (`str | None`; when set, must equal a `TestScenario.id`), derived `status` (`PASS`/`FAIL`/`PENDING`), optional `merged_pr_url`. `_sanitize_requirements` always re-derives `id` from `text` (client-supplied `id` is ignored) and resets `status`→`PENDING` / `merged_pr_url`→`None`.
- **`TaskDoDClause`** (`alan/workspace.py`): a per-task definition-of-done clause — stable `id` (`dod-` + hash), `text`, `covers: list[str]` (the acceptance-clause `id`s it covers, many-to-many), optional `evidence` (a reference to the merged piece). Persisted on `Task.dod_clauses` alongside `Task.description`, `Task.planning_state` (`outline`/`detailed`, default `detailed`), `Task.split_rationale`, `Task.parent_task_id`, `Task.child_task_ids`. These are populated by the decomposer (1b) and read by the gate (2) and UX; 1a ships them additive + defaulted.
- **`reconcile_clauses(existing, new_texts)`** (`alan/acceptance.py`): append-only amendment — preserves every existing clause (id + status), appends only clauses whose content-`id` is new, dedups within the batch, skips blank text. Idempotent on identical text. Persist the result via `workspace.update_requirements`.
- **`TASK_COUNT_BUDGET`** (`alan/acceptance.py`): 10 — recommended task split ceiling. Exceeding it sets `WorkspaceProposal.over_budget=True` and surfaces a UI warning; not a hard refusal.

## `alan/acceptance.py` (pure module)

Only imports `alan.workspace`. Provides:

- `scoped_dod(meta: Meta, task_id: str) -> tuple[list[str], list[str]] | None`: returns `(in_scope_texts, out_of_scope_texts)` when `task_id` refers to a subtask with non-empty `dod_clauses`; returns `None` for undecomposed tasks (no `dod_clauses`). `in_scope_texts` = `Requirement.text` values whose `id` is covered by the current task's DoD clauses. `out_of_scope_texts` = texts owned by a sibling task (same `parent_task_id`, different `task_id`). **A requirement claimed by two or more siblings resolves to exactly one owner** (`alan.acceptance.resolve_owners`): the last sibling by position among tasks sharing that `parent_task_id` — a total, deterministic order, safe because `workspace.inject_tasks` appends in decomposer emission order and no writer reorders `meta.tasks`, and dependency-consistent because `_derive_dependencies`/`_union_deps` (`alan/teams/decomposer.py`) emit only backward edges. Every non-owner sees the requirement in `out_of_scope_texts` only — never `in_scope`. **This reverses a previously documented property**: a requirement owned by both the current task and a sibling used to appear in `in_scope` for both, unconditionally; `TestScopedDod::test_shared_req_stays_in_scope_not_out` and `::test_partial_sibling_overlap` (`tests/test_acceptance.py`) were rewritten, deliberately, to pin the new one-owner outcome instead of the old shared-ownership one — this is an intended reversal of a recorded design decision, not a coverage downgrade. A subtask that loses every requirement it claimed to sibling ownership through non-withdrawal causes (lost the ownership tie-break, or its `covers` never resolved to a real requirement) falls through to the clause-text fallback below rather than receiving an empty fence. A subtask whose live definition-of-done view empties **because every clause it covered was withdrawn** is different: it receives an explicit empty `([], out_of_scope)` fence instead of the clause-text fallback — see "Withdrawn acceptance clauses" below for why. Bogus `covers` entries (pointing to non-existent `Requirement.id`) are silently filtered. **Fallback (2026-08-20):** when none of the current task's `covers` resolve to a `Requirement` — no requirements were ever extracted for the workspace (every explore-chat / `ui_review`-originated brief today has `requirements: []` and `covers: []`), or the ids are bogus — the fence is built from the clause texts themselves: `in_scope_texts` = the task's own `dod_clauses[].text`, `out_of_scope_texts` = sibling tasks' clause texts minus any text the task also carries. Before this, such a subtask got no scope block at all and the judge reviewed it against the whole workspace brief (PR #1159: verification #1 demanded the sibling subtasks' geometry work from subtask A and asked whether "the remaining scope" was a follow-up). Used by `VerificationTeam` to input-shape the judge's user text with `## IN-SCOPE ACCEPTANCE OUTCOMES` / `## OUT-OF-SCOPE ACCEPTANCE OUTCOMES` blocks so the verifier judges only the subtask's own deliverable.
- `all_requirements_satisfied(meta: Meta) -> bool` — **not the gate.** Since PR #1263 (merged 2026-08-31) it has exactly one caller, `all_clauses_satisfied` below, invoked only in that function's no-coverage branch. Documenting this function as though it were the completion criterion (as an earlier revision of this page did) is precisely what produced the false "the gate never evaluates a clause" premise above — it is a legacy fallback, not an answer to "is this workspace done."
  - `meta.requirements is None` → `True` (legacy; falls back to old rule)
  - `meta.requirements == []` → `False` (explicit empty set is never satisfied)
  - otherwise considers only **test-bound** clauses (`test_ref` truthy); when no clause is bound → `True` (unbound-only clauses degrade to the legacy terminal rule and never block — Phase 1a behaviour-preservation invariant); else all bound `status == "PASS"` → `True`. For an all-test-bound workspace this is identical to the original rule.
- `evaluate_requirements(scenario_results, requirements) -> list[Requirement]`: maps `(scenario_id, status)` pairs to updated statuses via `_resolved_status`, which treats a raw `"ADVISORY"` scenario result the same as `"PASS"` (both are evidence the bound command ran clean) and everything else that isn't `"PASS"`/`"ADVISORY"`/`"PENDING"`/absent as `"FAIL"`. Unmatched `test_ref` stays `PENDING`.
- `all_clauses_satisfied(meta: Meta) -> bool` — **this is the gate** (Phase 2), coverage-aware, and it evaluates a clause via either of two independent proof paths:
  - `meta.requirements is None` → `True`; `[] → False` (same legacy degradation as above).
  - It reads `(covered, evidenced)` from the tasks' `dod_clauses` (`covered` = clause ids any DoD covers; `evidenced` = clause ids covered by a DoD that has `evidence`). When **no** task declares any coverage it degrades to `all_requirements_satisfied` (an undecomposed/legacy workspace is governed by its test-bound clauses only) — this is the **only** place `all_requirements_satisfied` still runs.
  - When coverage exists, every clause must be satisfied: `status == "PASS"` (test-bound + passing), OR it is **uncovered** (no task claims it → non-blocking), OR it is **covered AND evidenced**. A clause that a task covers but for which no evidence has been stamped **blocks** completion — this is what makes a partial split delivery unable to silently finish.
- `unproven_clause_ids(requirements: list[Requirement] | None, tasks: list[Task]) -> set[str]` — a pure per-clause measure, added alongside the gate rather than inside it: a clause id is unproven when it carries neither a `test_ref` nor coverage by any subtask DoD clause (evidence is irrelevant to this measure — a covered-but-unevidenced clause is not unproven, it is proven-but-incomplete, which `all_clauses_satisfied` already blocks on separately). It is **never consulted on a decision path** — no call site in `all_clauses_satisfied`, `workspace_terminal_status`, or `is_build_success` — it is derived at read time purely for visibility. `requirements_unbound(meta) -> bool` (the pre-existing workspace-level vacuity predicate consumed only by `workspace_dag._maybe_audit_vacuity`, non-blocking) is now implemented on top of it: `bool(reqs) and len(unproven_clause_ids(meta.requirements, meta.tasks)) == len(reqs)` — algebraically identical to its prior direct implementation, and it fixes that predicate's blind spot for free, since a partially-covered workspace (fewer unproven clauses than total) now falls out of the same computation rather than needing a second code path. `WorkspaceDetail` (`alan/routes/_workspace_detail.py`) exposes `unproven_clause_ids`/`unproven_clause_count` as computed fields over the same requirements/tasks the response already carries, and `alan/health_repo_metrics.py::unproven_clause_count` aggregates it over the same terminal build-pipeline population `build_success_rate` scores — see `docs/architecture/health.md`'s `quality_metrics` section.

## Withdrawn acceptance clauses

A verification run can stall on an acceptance clause: the same clause id appears in the actionable set of two consecutive verification runs on one handover chain, and the workspace parks on a human — see "Clause-stall detector" below. Answering that escalation needs a durable way to shrink the acceptance set, since "rewrite or drop this clause" was previously an instruction the system gave a human with no mechanism to carry out. `Requirement.withdrawn_by_question_id: str | None` (`alan/workspace.py`) is that mechanism: a single nullable field, defaulting to `None` so every already-persisted workspace keeps loading unchanged.

**Not a `RequirementStatus`.** `alan._dispatcher_reconcile._maybe_evaluate_requirements` → `acceptance.evaluate_requirements` → `_resolved_status` overwrites `status` for any clause whose `test_ref` resolves, on the same path that then decides the workspace's terminal outcome — a withdrawal recorded as a status value would be silently erased there the next time a bound scenario runs. A separate field survives that `model_copy` untouched, and it can name the withdrawing question, which a status literal cannot.

**Sole write authority.** `alan.clause_withdrawal.withdraw` has exactly one caller: `alan/routes/answer.py::_claim` — including its `_claim_already_answered` replay branch (see "Replaying a recorded ruling" below), which reuses `alan/routes/answer.py::_apply_human_ruling` rather than calling `withdraw` a second, independent way — itself reachable only when the answered question is a clause-stall question (`alan.clause_withdrawal.is_clause_stall_question`) — i.e. only through a **human** answer to a clause-stall escalation. `alan/unblock_sweep.py::_record_plan_answer` is the one autonomous caller of `handover.record_answer` in the codebase; it answers only with an option one of its recipes (`alan/unblock_recipes.py`) named, and no tier-1 recipe answers a clause-stall question, so it cannot reach a clause stall today, but withdrawal authority is keyed to the human answer route and the clause-stall question class specifically — never to "an answer was recorded" — so that remains true even if a future autonomous path grows the ability to answer more question classes.

**Which ids get withdrawn.** Exactly `ClauseOutcome.actionable_ids` — the post-demotion set `_clause_audit._clause_outcome_from_rows` produces and `_clause_stall._repeated_actionable_ids` intersects — never ids parsed out of the question's own identifier. That identifier names only the *repeating* ids and, for a group, is an irreversible truncated hash; the withdrawal is deliberately wider than the question id, which is why the question text names every clause in the current actionable set and says so. `alan.clause_withdrawal.clause_ids_for_withdrawal` reads the set straight off the escalation handover's own `clause_outcome` field when present. Older, already-parked escalations predate `_emit_clause_stall_escalation` carrying that field, so `clause_ids_for_withdrawal` falls back to `alan.clause_withdrawal.latest_verification_with_clause_outcome`, which walks the chain backward for the most recent `from_team == "verification"` handover that still carries a `clause_outcome` — by construction the same outcome the stall detector matched *against* when it escalated, since that handover is the detector's own prior pass.

**Asymmetric failure handling.** When no clause ids are recoverable, the withdraw option raises HTTP 422 and writes neither the answer nor a withdrawal — silently succeeding while withdrawing nothing would reproduce the infinite re-park this mechanism exists to end. The waive option proceeds regardless and withdraws nothing on the same failure, because that is exactly today's (pre-withdrawal) behaviour, which is unchanged by this feature.

**Replaying a recorded ruling.** A `revisit_amend` handover can carry a human's clause-stall ruling from before this mechanism — or before a later verification run re-raised the identical stall — with no withdrawal ever having taken effect: `alan.handover.find_recorded_answer` returns the *earliest* matching record on the chain, so a stale ruling permanently shadows every later `POST` for the same question, and the pre-existing already-answered short-circuit in `alan/routes/answer.py::_claim` returned `dispatch=None` unconditionally, discarding what the recorded ruling had already decided. `_claim_already_answered` now acts on that decision instead of swallowing it: when all three conditions hold together — the question is a clause stall (`clause_withdrawal.is_clause_stall_question`), the recorded answer is `OPTION_WITHDRAW_WORDING_LEGACY` or `OPTION_WITHDRAW_WORDING_CURRENT` (never the waive wording, and never any other answer — those keep today's dispatch-nothing behaviour unchanged), and the clause ids are not already fully withdrawn on committed state — the next `POST` for that question withdraws the clause and dispatches the follow-on team, exactly as a fresh answer would. The guard re-reads the workspace from disk (`workspace_mod.read`, inside `_claim`'s `_lock`) rather than trusting the route handler's pre-lock snapshot, because that same read is both the idempotence check and the dispatch gate: `update_requirements` (`alan/workspace.py`) already re-reads for the *write*, and this closes the matching gap on the *decision* of whether to write. The already-withdrawn check (`_clause_stall_fully_withdrawn`) is deliberately question-agnostic — it looks at `withdrawn_by_question_id is not None`, not at whether it equals the current question's id — because `_withdraw_one` already refuses to re-stamp a clause another question marked first; a clause fully withdrawn by a *different* question therefore makes the replay a deliberate no-op rather than a repeat dispatch. Resolving the follow-on target happens before the withdrawal, matching the fresh-answer ordering, so a legitimately absent target (another unanswered blocking question on the same handover) still withdraws with no dispatch — the same outcome the fresh-answer path already produces for that shape. The recorded ruling itself is never re-recorded or rewritten; idempotence comes from the withdrawal marker alone, exactly as it does for a fresh answer. Because the replay reuses `alan/routes/answer.py::_apply_human_ruling` unchanged, its HTTP 422 on unrecoverable clause ids is inherited: an already-answered `POST` that previously always returned `200` can now return `422` when the ids that ruling named no longer resolve. When `handover_id` is omitted from the `POST` body, `_find_blocking_handover`'s fallback search can resolve `blocking` to the recorded ruling itself rather than the original escalation — and a ruling recorded before `clause_outcome` was carried onto every `revisit_amend` (via `record_answer`'s full-field copy) has none. `clause_ids_for_withdrawal`'s own fallback can't recover from that: it re-scans the whole chain from the latest handover and stops at the very ruling it's being asked to see past. `_resolve_escalation_for_withdrawal` (`alan/routes/answer.py`) walks the same chain first, skipping past `blocking` itself and any other answer-recording `revisit_amend`, to hand `clause_ids_for_withdrawal` a handover that actually carries (or, failing that, still correctly fails to find) the outcome — a genuine content revisit in between still stops the walk, exactly as it stops `latest_verification_with_clause_outcome` today.

**Host-derived effect and resolver, confined to the clause-stall namespace.** Nothing rewrites a persisted `OpenQuestion`, so a workspace already parked on the legacy wording ("Rewrite or drop this clause, then re-dispatch verification.") would answer into a dead end forever if the host only consulted the stored `option_effects`/`option_resolvers` maps. `alan.routes.answer` derives the effect and resolver at answer time for a clause-stall question via `clause_withdrawal.resolve_human_ruling`, which recognises both `OPTION_WITHDRAW_WORDING_LEGACY` and the current `OPTION_WITHDRAW_WORDING_CURRENT` as the withdraw option (resolver `verification`, effect `closes` — no longer `pending_external`) and `OPTION_WAIVE_WORDING` as the waive option (resolver `pr_merge`, effect `closes`). It returns `None` for every other question, so every non-clause-stall question keeps taking its behaviour from what was stored on the handover.

**One decision serves every door (2026-09-18).** `resolve_human_ruling(question, answer) -> Ruling | None` widens the door beyond the clause-stall namespace to every way a human can waive or withdraw a clause. `Ruling` is a frozen `NamedTuple(resolver, effect, scope)` where `scope` is `"clause"` (the ruling withdraws a named acceptance clause) or `"pr"` (the ruling is recorded against the pull request itself, because the underlying finding is not a clause). Four branches, tried in this fixed priority order, the first match wins:

1. **Operator-only escalation** (`is_operator_only_escalation`) — any of the operator-only wordings → `Ruling("pr_merge", "closes", "clause")`.
2. **PR-state escalation answered with the override wording** (`is_pr_state_escalation(question) and answer == OPTION_CLAUSE_OVERRIDE_WORDING`) — `Ruling("pr_merge", "closes", "clause")`. This is the new door: previously `resolve_clause_stall_option` returned `None` for this question id, so the override wording answered into whatever the persisted (usually empty) `option_resolvers`/`option_effects` maps said, and the clauses named on that escalation were never marked ruled-on.
3. **Clause-stall question** (`is_clause_stall_question`) — the two shapes already documented above.
4. **Generic verification-escalation waiver** — `question.question_class == "verification_escalation"` and `question.option_resolvers.get(answer) == "pr_merge"` → `Ruling("pr_merge", question.option_effects.get(answer, "closes"), "pr")`. This is the fourth door: the capability-boundary waive (`_CAPABILITY_BOUNDARY_OPTION_WAIVE`, "Waive this finding and proceed to merge.") matches here, `scope="pr"` because the capability-boundary finding is not a `Requirement` — there is nothing to withdraw, only a pull-request-scoped record to write (see below). This branch also absorbs what `alan.routes._answer_waiver.is_waiver` used to compute as a standalone fallback (`option_resolvers.get(answer) == "pr_merge"` on any `verification_escalation`) — `is_waiver` is now a one-line projection: `ruling is not None and ruling.resolver == "pr_merge"`.

The same decision that used to serve only "is this answer a waiver" (dismissing the verifier's blocking review) now also serves "does this answer mark a clause" — a single `resolve_human_ruling` call answers both questions for every door, so a waive answered from any recognised card both records the ruling and dismisses the review; no door can do one without the other.

**Bucket selection, per question kind.** `ClauseOutcome` carries three id buckets: `actionable_ids` (the clause-stall door reads this), `operator_only_ids` (the operator-only door), and `unactionable_ids` (new, schema `1.23`→ additive, default `()` — the PR-state door reads this). `_enforce_outcome` sets `escalate_unactionable = not parts.actionable`, so on the PR-state door `actionable_ids` is provably empty — without a third bucket, `clause_ids_for_withdrawal` would return an empty list for that door and the override wording would silently withdraw nothing. `clause_ids_for_withdrawal(ws, escalation, question=...)` selects the bucket by question kind (operator-only → `operator_only_ids`, PR-state → `unactionable_ids`, everything else including clause-stall → `actionable_ids`) rather than branching per call site.

**The capability-boundary ruling is recorded per pull request, not against a clause.** `alan.teams._pr_state_paths.record_capability_boundary_waiver(pr_number, question_id, forge)` / `capability_boundary_waiver_recorded(...)` store the answered question's id in `pr_{n}_capability_waivers.json` under the same `_engine_state_dir(forge)` the fix-cycle state lives in — a new file, deliberately not a new field on `FixCycleState`: `FixCycleState.granted_question_ids` (#1573) is a monotone no-reset set whose membership drives the fix-cycle *allowance* bump, and a second, unrelated writer sharing that set would corrupt any future ceiling-metrics read over it. `alan.teams._verification_capability.capability_boundary_waived(workspace, prior)` resolves the forge via `_pr_forge.forge_target_for_ws(workspace)`, returns `False` when `prior is None` or `prior.pr_number is None`, and otherwise checks every capability-boundary-shaped (`is_capability_boundary_question`, a **prefix** match on `verif-capability-boundary-` — the id also embeds `inv_id[:8]` and is different on every pass) answered question on `prior.open_questions` against the recorded set. `alan.teams.verification._capability_boundary_handover` folds this into its existing guard: `if capability_boundary_reason is None or capability_boundary_waived(workspace, prior): return None` — a waived finding with no PR behind it (`prior.pr_number is None`) still escalates exactly as before, since the predicate degrades to `False` and the escalation still fires.

**Answering a card costs no extra cycle.** `_clause_stall._latest_verification_since_intervention` used to treat *every* `revisit_amend` handover as a reset (`return None` immediately), including one that only recorded a human's answer to an unrelated question — so a clause that failed again on the very next verification pass after an answer was recorded would not re-trip the stall detector until the pass *after* that, one cycle later than it should. It now calls `alan.handover.is_answer_recording(handover)` (hoisted out of `alan.routes.answer` so both the stall walk and the answer route agree on what "just recording an answer" means) and `continue`s past an answer-recording `revisit_amend` instead of stopping at it — the walk stops at a `revisit_amend` only when it carries genuine content, exactly as `alan.routes.answer._skip_for_escalation_resolution` has always treated it. `alan#1562`'s "disarmed forever" claim about this class of defect is false at current head: the measured cost was one extra verification cycle per answered card, not permanent disarmament.

**A stall re-raised one pass earlier can no longer replay a stale answer.** `_verification_review_post._stall_question_id_for` already fell back from the overlap-keyed id to the full-clause-set id once the overlap id had a recorded answer. Firing the stall a cycle earlier means the same repeating clause set can now exhaust *both* ids inside the run that used to take two cycles, so a third, always-fresh fallback was added: when the clause-id form also already has a recorded answer, the id becomes `clause-stall-<16-hex digest of clause_id + from_invocation_id>-<from_invocation_id[:8]>` — the same `-{inv_id[:8]}` idiom `_emit_capability_boundary_escalation` already uses to keep every capability-boundary question id unique per pass. This guarantees a stall escalation raised on this pass is never silently treated as the identical already-answered escalation from a prior pass.

**Total read-site coverage.** `acceptance.is_withdrawn`/`acceptance.live_clauses` are applied inside `acceptance.py` itself — `all_clauses_satisfied`, `all_requirements_satisfied`, and `unproven_clause_ids` all filter to live clauses before doing anything else, so the completion gate and both unproven-acceptance measures (the workspace-detail computed fields and `health_repo_metrics.unproven_clause_count`) close for free. Four call sites needed an explicit external filter: `_clause_audit._select_requirements` (the auditor's clause set — see below), `_dispatcher_selfheal._pending_test_refs` (the self-heal probe's pending-proof accounting), `alan/teams/decomposer.py` (the clause context shown to a re-decomposition, and the `covers` ids a new subtask is allowed to reference), and `alan/teams/brief_refine.py` (the prior-clause context shown to the refiner, annotated `[WITHDRAWN]` rather than dropped, so the model is not asked to keep proposing a clause it is required to carry forward).

**The auditor never sees a withdrawn clause.** `_select_requirements` filters to `live_clauses` on both its undecomposed and decomposed branches, so a withdrawn clause can never produce a `CLAUSE ... FAIL` row, force the enforce-mode `REQUEST_CHANGES` downgrade, land in `_clause_outcome_from_rows`'s `actionable_ids` (and therefore can never re-trigger the stall detector on itself), or reach a fix worker. When filtering empties the audited set entirely, `_select_requirements` appends a `clause_audit_skipped_all_withdrawn` audit row before `begin` returns `None` — deliberately distinct from `clause_audit_skipped_unscoped`/`clause_audit_skipped_no_owned_requirements`, so "every clause was withdrawn" and "the audit mechanism itself did not run" are never indistinguishable in `verification_audit.jsonl`.

**The judge's scope fence, filtered at the DoD-clause level, not the id level.** `acceptance.scoped_dod` builds a live view of every task's `dod_clauses` first (`_live_dod_clauses`/`_with_live_dod`/`_live_scope_meta`): a `TaskDoDClause` is dropped from that view only when its `covers` resolve to at least one requirement and every one of those resolved requirements is withdrawn; a clause covering a mix of withdrawn and live requirements keeps its text and all of its covered ids, unchanged; a clause whose `covers` is empty, or resolves to nothing, is untouched. `_owned_clause_ids`, `_resolve_ownership`, `_clause_text_scope`, and `resolve_owners` are unmodified — they are simply fed this filtered view instead of the raw one. This ordering matters: filtering ids directly, without first dropping the covering DoD clause, empties a task's owned set exactly the way losing an ownership tie-break does, and `scoped_dod`'s own anti-empty-fence fallback (`_clause_text_scope`) would then render that task's own DoD clause text — the prose restatement of the very obligation just withdrawn — as an in-scope finding for the judge to demand. When the live-filtered view of the current task's own `dod_clauses` is empty (every original clause covered only withdrawn ids), `scoped_dod` returns `([], out_of_scope)` directly, built from the other tasks' own live-filtered clause texts — never `None`, and never through `_clause_text_scope`.

**An empty in-scope fence silences the judge's own retry, and that is intended.** `VerificationTeam._scope_block_present` treats `scoped_dod` returning `([], ...)` identically to returning `None`: no `## IN-SCOPE ACCEPTANCE OUTCOMES` block is appended to the judge's prompt, and `_judge_retry_reason`'s `missing_in_scope_count` branch — which otherwise forces a retry when a scope block was shown but the judge's output carries no in-scope critical count — never fires either. This is a real, deliberate reduction in how tightly this run's judge is grounded to the subtask's own deliverable: the alternative, asserting a withdrawn obligation as still in-scope, is strictly worse, since it manufactures exactly the false in-scope finding this mechanism exists to prevent.

**Carry-forward marker travel.** `brief_refine._carry_forward` is the one production path that rewrites a clause's text; because `Requirement.id` is content-derived from `text`, a rewrite always mints a new id. `_carry_forward` copies `withdrawn_by_question_id` onto the rewritten `Requirement` alongside `test_ref`/`status`/`merged_pr_url`, so the marker rides the object through the identity change instead of being matched by an id that no longer exists. `acceptance.reconcile_clauses` has no caller inside `alan/` (tests and docs only) and passes existing objects through untouched, so it is not a path this marker needs to survive.

**Sanitisation at creation time.** `workspace._sanitize_requirements` already rebuilds every `Requirement` passed to `workspace.create` from only `text` and `test_ref`, dropping every other client-supplied field as a side effect — including a client-injected `withdrawn_by_question_id`. This is pinned by a dedicated test rather than relied on as an accident of the existing rebuild.

**Never deleted, never invisible.** A withdrawn clause stays in `meta.requirements`, renders in `RequirementsChecklist` with a distinct neutral-status marker and the withdrawing question's id, and is excluded from the "never mechanically checked" summary count above the list — the marker is never carried by strikethrough alone. The web UI derives one `ClauseDisplay` union (`WITHDRAWN` > `UNPROVEN` > the raw `RequirementStatus`) and keys its label/class/icon maps on that union, so a missed case is a compile-time error, not a silent fallthrough.

## Evidence pipeline (Phase 2)

Nothing wrote delivery evidence before Phase 2. Now, when a task completes with a merged PR, the dispatcher stamps it: `_advance_workspace_dag` calls `_stamp_evidence(ws, task_id, handover)`, which — when `handover.pr_number` is set and the completed task has `dod_clauses` — calls `workspace.record_task_evidence(ws, task_id, "PR #<n>")`. That sets `evidence` on the task's still-unstamped DoD clauses (existing evidence preserved). As covering subtasks merge, their covered clauses become evidenced; once all covered clauses are evidenced (or pass a test), `all_clauses_satisfied` lets the workspace complete. The gate itself stays a **pure predicate over persisted `Meta`** (no `gh`/network in the dispatch loop, and `acceptance` cannot import `delivery` per the layering) — the evidence is written upstream.

## Dispatcher integration (`alan/dispatcher.py`)

`_workspace_terminal_status` uses `all_clauses_satisfied` at both code paths (it is one function, called from `_advance_workspace_dag` and `_propagate_and_cancel`):
- All tasks `COMPLETED` + `all_clauses_satisfied` → `Status.COMPLETED`
- All tasks `COMPLETED` + NOT satisfied → `Status.FAILED`
- Any task `FAILED` (and all terminal), >=1 sibling merged a PR (DoD evidence stamped) → `Status.PARTIAL` (see [partial_workspace_status.md](partial_workspace_status.md))
- Any task `FAILED` (and all terminal), no sibling merged a PR → `Status.FAILED`

`_maybe_evaluate_requirements` runs scenarios before the terminal check when all tasks are complete and requirements are non-None. Uses a **repo-root fallback**: `_run_scenarios` runs `uv run --no-active pytest -k <test_ref>` and logs a warning; returns `PENDING` on exception.

## Minting requirements at agreement time

`CreateWorkspaceBody.requirements: list[Requirement] | None = None` — `None` = legacy (no gate). `[]` = requirements declared but never satisfied; workspace can never complete. Server-side, `workspace.create()` sanitizes: `status` resets to `PENDING`, `merged_pr_url` to `None`.

**Dispatch-time per-PR clause ownership.** `TaskCreateEntry.dod_clauses: list[TaskDoDClause] = []` lets a caller of `POST /api/workspaces` declare, per unit of work, which acceptance clauses that unit's own pull request owns — the same `covers`-keyed ownership shape the decomposer writes for a split, now reachable at dispatch time for a human-planned sequence of pull requests. `to_task()` threads it straight onto `Task.dod_clauses`, so a dispatch-seeded task is scoped by `_select_requirements` exactly like a decomposer-seeded one (see "Clause selection" below). `TaskCreateEntry`, `CreateWorkspaceBody`, and `CreateWorkspaceResponse` live in `alan/app/workspace_create_models.py` — moved out of `alan/routes/workspaces.py`, which is pinned shrink-only against `tests/size_baseline.py`'s `SOURCE_MODULE_CAP`; the move shrinks that file by the moved size rather than growing it in place. The module is a public (non-underscore) name specifically so `check_forced_split`'s private-module shrink accounting (`tests/test_size_ratchets.py`) never applies to it — a `_`-prefixed name would have had to earn its keep by shrinking an unrelated pinned sibling by the same amount, for a module `workspaces.py` itself needed to shrink to begin with. `alan/routes/workspaces.py` re-imports the three names plain (not aliased), which is both what keeps `tests/test_dispatch_gate_invariant.py`'s `workspaces_routes.CreateWorkspaceBody` reference working and what keeps the import off `tests/test_reexport_facade.py`'s radar (that gate flags an unused `as`-aliased re-export, not a plain one). It later moved again, from `alan/routes/` to `alan/app/`, when workspace creation was extracted into `alan/app/workspace_creation.py` (see [application_layer.md](application_layer.md)); the exhaustive "Layered architecture" contract lists only top-level `alan.<name>` packages, so that move is covered by the `app` entry directly beneath `routes` rather than by `alan.routes`.

**The full-coverage rejection.** `reject_uncovered_clauses(body, tasks)` runs inside `create_workspace` immediately after `tasks_to_create = [t.to_task() for t in body.tasks]` and before every other side effect (the predispatch scope scan, workspace creation, the lane-limit check, the route audit row). It fires only when `len(tasks) >= 2` **and** `body.requirements` is non-empty — a single- or zero-task dispatch is never rejected, matching the fenced 0/1-task behaviour below — and reuses `acceptance.unproven_clause_ids(body.requirements, tasks)` as its sole coverage check: no second coverage primitive was written for this. A non-empty result raises `HTTPException(400, detail={"error": UNCOVERED_CLAUSES_DETAIL, "uncovered_clause_ids": sorted(...)})` — a hard rejection, not a warning or a log line, that names every uncovered id, whether the gap is partial (one clause of many unclaimed) or total (no task declares any `dod_clauses` at all — the two-or-more-units-with-no-ownership shape). Because the check runs before `workspace_mod.create` is ever called, a rejected dispatch creates nothing. **This check is independent of `ALAN_CLAUSE_AUDIT`** — it fires even when that mode is `off`, since it is a dispatch-payload validation, not a verification-time audit; a client cannot dispatch an uncovered multi-task item by dialing the audit mode down. Overlapping (non-disjoint) ownership is legal here exactly as it is in `scoped_clause_requirements` — two tasks both declaring `covers` on the same clause id passes this check, since coverage, not disjointness, is what full-coverage means. `decomposer._validate_clause_coverage` (`alan/teams/decomposer.py`) is deliberately left checking only that `covers` references *known* clause ids, never full coverage — a decomposer split can still produce an uncovered clause, and that asymmetry between the two paths is accepted knowingly: the full-coverage rule binds ownership declared through dispatch only, not the decomposer's own splitting decision.

## Prose DoD / scenario execution contract (explicit decision)

**Decision (2026-06-14): prose Given/When/Then is documentation; the `when` field's exact executable command is the single executable gate.**

The verifier cannot run arbitrary prose descriptions such as "The user clicks…" or "POST /api/…". Rather than manufacturing ambiguous SKIPPED results, the system now uses a distinct `DOCUMENTED` status so the contract is unambiguous.

### `DOCUMENTED` vs `SKIPPED` vs `ADVISORY` vs `TIMEOUT` vs `BUDGET_EXHAUSTED` contract

`ScenarioStatus` (`alan/teams/_scenario_runner.py`) is `Literal["PASS", "FAIL", "SKIPPED", "DOCUMENTED", "ADVISORY", "TIMEOUT", "BUDGET_EXHAUSTED"]`. `NON_BLOCKING_STATUSES` is the frozenset `{"SKIPPED", "DOCUMENTED", "ADVISORY", "BUDGET_EXHAUSTED"}` — the single source every role prompt that reasons over scenario outcomes is checked against (`tests/test_scenario_then_advisory.py`).

| Status       | Meaning                                                                                       | Blocks APPROVE (mechanically enforced)? |
|:-------------|:----------------------------------------------------------------------------------------------|:----------------|
| `PASS`       | Command ran; exit 0 and (if non-empty) `then` string found in output.                        | No              |
| `FAIL`       | Command ran but exit non-0, or pytest collected no tests (rc=5).                              | **Yes**         |
| `DOCUMENTED` | `when` field is prose: parseable, no forbidden operators, but command prefix not in allowlist.| No              |
| `SKIPPED`    | Runner-level failure: forbidden shell operator, unbalanced quotes, path traversal, empty `when` field, a pytest collection error (rc=2), or a missing/renamed `test_ref` (rc=4). | No |
| `ADVISORY`   | Command ran and exited 0, but the (non-empty) `then` string was not found in the combined output. The mismatch is still reported as diagnostic text — it is evidence, not silence — but it alone can never block. | No |
| `TIMEOUT`    | The `when` command was still running when its per-scenario limit — `min(resolved per-scenario timeout, remaining resolved aggregate budget)`, which shrinks as earlier scenarios in the run consume the budget — expired, and was killed. | **Yes** |
| `BUDGET_EXHAUSTED` | The scenario was never attempted at all because the run's resolved aggregate budget was already spent by earlier scenarios in the same run. | No |

**The "Blocks?" column is host-enforced, not a prompt instruction the judge is trusted to honor.** `alan/teams/_scenario_gate.py::apply`, wired into `VerificationTeam._build_verdict_handover` immediately after the clause-audit rewrite, loads the scenario outcomes persisted for this invocation and computes `status != "PASS" and status not in NON_BLOCKING_STATUSES` per outcome (`NON_BLOCKING_STATUSES` — this frozenset, unchanged and not widened by the gate) — any status that is neither `PASS` nor a member of that frozenset rewrites the judge's verdict to `REQUEST_CHANGES` and prepends a named banner, regardless of what the judge's own `VERDICT:` line said. An unrecognized future `ScenarioStatus` value therefore fails closed (treated as blocking) rather than silently passing through. `SCENARIOS_WAIVED` (below) remains an upstream flag that empties the scenario-results list before the gate ever sees it, not a status the gate special-cases — waiver still suppresses the gate entirely, exactly as it suppresses the judge's own `## TEST SCENARIOS` prompt block. `apply` additionally appends the persisted outcomes verbatim (one line per scenario id, status, and diagnostic) to the judge's output — on both the clean path (no blocking status; nothing is rewritten) and the banner path (after the verdict rewrite) — so the reviewing judge role is no longer asked to restate this run's per-scenario outcomes in its own prose; the ground truth is appended by the host instead of narrated by the model.

Outcomes are persisted (`alan/teams/_scenario_gate.py::save_outcomes`) at scenario-derivation time in `VerificationTeam.run()`, before the pipeline's LLM roles execute, and only when the scenario-runner node has not already succeeded for this invocation — so the gate is live across a service-restart resume of an in-flight invocation (the persisted file survives untouched; the resume path reads it and never rewrites it), and inert only for invocations that were already past that point when this mechanism was deployed. An inert invocation is not silent: `apply` appends a `scenario_gate_no_outcomes` audit row whenever no persisted outcomes are found.

`DOCUMENTED` is returned by `run_scenario` when the `when` field passes security checks (no forbidden shell operators, tokenises cleanly) but its command prefix is not in the allowlist resolved for the governing engine (below). It signals that the scenario is intentional documentation of behaviour, not a runnable assertion. The helper `_is_prose_rejection(when, cfg)` exposes this predicate.

### Resolving the per-scenario timeout, the aggregate budget, and the command allowlist

`alan/teams/_scenario_runner.py` resolves all three of these per run, from the `EngineConfig` governing the workspace (`cfg`, threaded in from `verification.py`'s `_pr_forge.governing_config_for_ws(workspace)`) — never hardcoded to the alan engine's own values. `EngineConfig.scenario` (`alan/engine_config.py`) is a nested `ScenarioConfig` carrying `command_prefixes: list[list[str]]`, `timeout_s: float | None`, and `aggregate_budget_s: float | None`, all defaulting empty/`None` so an engine that never sets the field reproduces today's behaviour exactly. A `model_validator` on `ScenarioConfig` rejects, at config-load time, an `aggregate_budget_s` that resolves below `timeout_s` (comparing the *resolved* values — i.e. a set `timeout_s` with an unset `aggregate_budget_s` is checked against `AGGREGATE_BUDGET_DEFAULT`, not left to pass and die at 120s later) and rejects a non-positive or non-finite value for either field — a reviewed, tracked configuration fails loudly rather than degrading quietly.

- **Per-scenario timeout** (`scenario_timeout(cfg)`): precedence is env `ALAN_SCENARIO_TIMEOUT_S` → `cfg.scenario.timeout_s` → `SCENARIO_TIMEOUT_DEFAULT` (120s). The env tier is deliberately outermost and deliberately quiet on bad input (blank, unparseable, non-positive, or non-finite all fall back to the hardcoded default, never to `cfg`) — an operator's environment override is allowed to keep degrading silently in a way a tracked config is not, and it is checked first specifically so an operator reaching for it during an incident can always outrank a tracked config, including a second engine's.
- **Aggregate budget** (`resolve_aggregate_budget(cfg)`): precedence is `cfg.scenario.aggregate_budget_s` → `AGGREGATE_BUDGET_DEFAULT` (600s). There is no environment tier for this one — nothing reads an aggregate-budget env var today, and adding one would need its own `tests/env_var_classification.py` registration for no stated requirement.
- **Command allowlist** (`_allowed_prefixes_for(cfg)`): the static `_ALLOWED_COMMAND_PREFIXES` tuple (below), plus prefixes derived from `cfg.gate_commands` (each command's first two tokens), plus `cfg.scenario.command_prefixes` verbatim — additive, deduplicated, and defaulting empty. `SCENARIO_TIMEOUT_DEFAULT` and `AGGREGATE_BUDGET_DEFAULT` live in `alan/engine_config.py` (import-linter forces this: `engine_config` sits below `teams` in the layers, so the model's own cross-field validator can reference them without an upward import) and are re-exported from `_scenario_runner.py` for its existing importers (`alan/teams/implementation_plan.py`'s synthesizer prompt among them).

**The iOS-preset engine.** That engine's own tracked `config/engines.d/<repo>.yaml` sets `scenario.command_prefixes` to `xcodebuild`/`tuist`/`swift`/`xcrun`/`python3` (single-token, matching `_check_command_prefix`'s positionally-exact matching — a two-token tuple would reject a scenario that writes its test selector before the subcommand) and both `scenario.timeout_s` and `scenario.aggregate_budget_s` to `900.0`. `python3` was added alongside the other four so a scenario (or a fix-worker rebind) can name one of that repository's own `scripts/gate.sh`'s own stdlib check scripts directly: the gate script invokes every one of its twelve stdlib checks as `python3` and lists `python3` in its required-tools array, while `python` appears nowhere in it. `alan/engine_presets.py`'s `ios_preset()` carries the identical entry, for the same reason and for consistency with the tracked config. Both fields are set, not just the aggregate: the effective ceiling is `min(timeout, remaining budget)`, so an aggregate of 900 alongside a timeout still at its 120s default would keep dying at 120. 900s clears, with margin, the measured runtime of a full iOS gate run (UI tests, an unsigned archive and the gate's self-test dominate it). `alan/engine_presets.py`'s `ios_preset()` carries the identical `ScenarioConfig` so the next iOS engine is born correct, but the preset itself reaches no live engine — nothing re-hydrates a live engine's config from its `preset` label at load time — so it is forward-looking and unverified, not the mechanism that fixes that engine; only its own tracked `config/engines.d/<repo>.yaml` does that.

**The alan engine.** No `scenario:` block is set on `config/engines.d/alan.yaml` or the in-code `default_engine_config()`, so resolution for the default engine reproduces today's values and behaviour exactly: `120.0`/`600.0`, and an allowlist identical to `_ALLOWED_COMMAND_PREFIXES` plus its own gate-command-derived prefixes (already a strict subset of the static tuple).

**A known, deliberately unfixed gap.** `alan/_dispatcher_selfheal.py`'s self-heal probe and `alan/_dispatcher_reconcile.py`'s out-of-band reconcile probe both call `run_scenarios` with no `cfg` at all — but only on the default forge, the only case in which either probe still reaches that call. `_probe_checkout_for` (`alan/_dispatcher_selfheal.py`) resolves to a `ProbeCheckout(path, skip_reason)`: the dispatcher's own checkout for the default forge, or `path=None` with a named `skip_reason` for any other forge, and both probes decline to execute anything — `run_scenarios` included — once `path` is `None`. So on the default forge those two probes still resolve the alan-shaped defaults (120s timeout, 600s budget, the static allowlist only) rather than the governing engine's own settings; there is no checkout registry for a second engine's repository, so for any other forge both probes decline to execute anything rather than run another repository's gate commands against alan's own tree and resolve requirements on false evidence. Making these two call sites engine-aware is unsafe until a future per-engine checkout registry lets `_probe_checkout_for` resolve a real path for a non-default forge.

### Authoring-time scenario validation (planning stage)

`alan/teams/implementation_plan.py`'s synthesizer scenario block is validated the moment the plan is authored, not first at verification time. `_parse_test_scenarios` applies `alan/teams/scenario_authoring.py::collect_rejections` to every parsed `test_scenarios` entry, resolved against the workspace's governing `EngineConfig` (`_pr_forge.governing_config_for_ws(workspace)`). Two independent checks feed one collected diagnostic:

- **Shape rejection** (`scenario_authoring.shape_rejection`): reuses `_scenario_runner.py`'s own `_check_forbidden_ops` / `_check_no_path_traversal`, plus a `shlex.split`-with-`.split()`-fallback tokenizer for the prefix gate only, to catch a forbidden shell operator, unbalanced quotes, or a path-traversal segment — the exact same runner-level diagnostics `_check_allowlist` would raise at verification time, worded identically. This fires **only** when the command's leading tokens are a *full* match against `_allowed_prefixes_for(cfg)` (the same allowlist the runner itself resolves) — never merely a leading-token match. A prefix that is outside the allowlist entirely is never rejected here; it stays `DOCUMENTED` at verification time exactly as it does today. This is deliberate and structural, not an oversight: rejecting on a partial prefix match would catch a case like `git push origin ../../etc/passwd` at planning while the runner itself would classify that same command `DOCUMENTED` — a direct contradiction of "never reject a scenario because its command prefix is outside the engine's allowlist."
- **Whole-gate rejection** (`scenario_authoring.whole_gate_when`): an engine-generic companion to the pre-existing unscoped-whole-suite check (`alan/teams/_scenario_block.py::unscoped_suite_when`, which only recognizes the default engine's `uv`/`npm` toolchains). A `when` whose shell tokens are exactly one of the governing engine's configured `gate_commands` with no further arguments is a whole-gate invocation and is rejected with the same wording the unscoped check already uses. The reason is not the timeout — a whole-gate scenario mostly passes — it is that running it consumes nearly the run's entire aggregate scenario budget, so every sibling scenario in the same run ends `BUDGET_EXHAUSTED`, a non-blocking status that silently drops them from the gate.

Both checks are collected across the whole block rather than raised on the first offending entry: `collect_rejections` returns one `ImplementationPlanError` naming every offending index with its own reason, never a single-entry error. This matters because `alan/block_correction.py`'s retry loop abandons after two consecutive identical error strings (`FLEET_MAX_ATTEMPTS` in `alan/teams/_block_correction_fleet.py`); a partial repair that fixed one of several offending entries would otherwise still surface the exact same error text and trip that abandonment on real progress. A shrinking index list is guaranteed to produce a different string as entries are fixed, so the planner's existing retry-and-repair loop can converge inside the same invocation instead of failing the whole plan.

The scenario section of the synthesizer's own guidance is rendered per workspace to match: `scenario_authoring.scenario_section(cfg)` / `synthesizer_prompt(cfg)` state the governing engine's own admissible command shapes (derived from its `gate_commands` and `scenario.command_prefixes`), its resolved per-scenario timeout and aggregate budget, and a worked example built from the engine's own gate command — never the default engine's `uv`/`npm` pair when the governing engine is something else. The generic rules (the exit-code taxonomy, the advisory-only `then` note, the whole-suite/whole-gate ban, the YAML quoting rule) are unchanged and rendered identically regardless of engine. This is applied through a new `StaticPipelineTeam._role_system_prompt(role, workspace)` seam (`alan/teams/_static_pipeline.py`) — default returns `role.system_prompt` unchanged; `ImplementationPlanTeam` overrides it for the `synthesizer` role only — at **both** the role's normal turn and its correction turn, since the correction turn is exactly where the authoring-time diagnostic above lands; applying it at only one site would show the planner guidance that contradicts the very rejection it is being asked to repair. See [implementation_pipeline.md](implementation_pipeline.md#per-engine-worker-instructions) for where this seam sits relative to the other per-engine rendering already documented there.

`SKIPPED` is reserved strictly for runner-level failures where the scenario could not even be attempted safely:
- Forbidden shell operator (`&&`, `||`, `;`, `|`, `>`, `<`, `` ` ``) — security rejection.
- Unbalanced quotes — parse failure.
- Path traversal (`..` segment) — security rejection.
- Empty `when` field — no command to run.
- pytest collection error (rc=2, combined stdout+stderr contains `errors during collection`, `error during collection`, or `ERROR collecting`) — the referenced test module exists but failed to import; a non-blockable environment artifact, not a defect in the code under test.
- pytest scenario not found (rc=4, combined stdout+stderr contains `file or directory not found` or `ERROR: not found:`) — the `test_ref` no longer resolves to any file or test node (renamed or deleted since the plan was written); a checkout artifact, not a defect in the code under test.

Aggregate budget exhaustion is its own status, `BUDGET_EXHAUSTED`, not `SKIPPED` — see the table above. A scenario that never got a chance to run because an earlier scenario in the same run consumed the whole resolved aggregate budget is a resource-scheduling fact about the run, not a runner-level failure of that scenario's own command.

### Collection error (rc=2) vs scenario not found (rc=4) vs missing tests (rc=5)

pytest's exit code distinguishes three different failure shapes, and the runner must not conflate them:

- **rc=2 — collection error**: the test module failed to *import* (syntax error, missing dependency, broken fixture chain at collection time) before any test could run. `_execute_scenario` (`alan/teams/_scenario_runner.py`) pre-checks the combined stdout+stderr via `_collection_diagnostic` for the substrings `errors during collection`, `error during collection` (pytest's singular phrasing for a single collection error), or `ERROR collecting`; when found, the scenario is reclassified from `FAIL` to `SKIPPED` with diagnostic `pytest collection error (rc=2): <signature>`. An rc=2 that matches neither signature (e.g. an interrupted run) is not recognized and falls through to the normal rc!=0 path, staying `FAIL` — failing closed rather than silently passing on an unrecognized rc=2.
- **rc=4 — scenario not found**: the runner invokes pytest positionally (`_resolve_command` synthesises `uv run --no-active pytest <test_ref>` when `when` is empty), so a `test_ref` that has been renamed or deleted since the plan was written resolves to pytest's USAGE_ERROR exit code, not a test failure. `_notfound_diagnostic` mirrors `_collection_diagnostic`'s signature-gating: it checks the combined stdout+stderr for `file or directory not found` (the module/file itself is missing) or `ERROR: not found:` (the module exists but the named test node does not), and reclassifies to `SKIPPED` with diagnostic `pytest scenario not found (rc=4): <signature>` when matched. Like rc=2, an rc=4 that matches neither signature falls through to the normal rc!=0 path and stays `FAIL` — failing closed on an unrecognized rc=4.
- **rc=5 — no tests collected**: pytest collection succeeded but matched zero test items. This can arise several ways — an author-written filter expression in the scenario's `when` field (e.g. a `-k` selector) matching nothing, a `test_ref` resolving to an existing file or module that contains no tests, or a test function that was removed since the plan was written. Since `_resolve_command` invokes pytest positionally with the raw `test_ref` rather than a filter expression, an existing-but-empty target is at least as likely a cause as an author-written filter. Regardless of cause, the DoD proof the scenario is supposed to provide is simply absent, so it stays `FAIL` unconditionally — reclassifying it would let a missing test silently pass verification.

### Executable gate: the `when` command

Any scenario meant to gate the verdict must place the exact executable command directly in the scenario's `when` field — that is what the runner executes. Two forms are supported: a backend pytest run (`uv run --no-active pytest tests/test_foo.py::test_bar`) or a frontend package-script run (`npm --prefix alan/web run <script>`) — plus, for an engine whose `EngineConfig.scenario.command_prefixes` carries it, whatever native build/test invocation that engine allows (the iOS-preset engine's `xcodebuild`/`tuist`/`swift`/`xcrun`, above). The runner always works from the repository root (cwd = repo root). A prose `when` (command prefix not in the resolved allowlist) is documentation-only and can never gate — see the `DOCUMENTED` row above.

`TestScenario.test_ref` is a fallback, not a requirement: when `when` is empty and `test_ref` is set, `_resolve_command` synthesises `uv run --no-active pytest <test_ref>` and the runner executes that instead. This `test_ref` is distinct from `Requirement.test_ref` (see Vocabulary above), which binds an acceptance clause to a `TestScenario.id` for the acceptance gate — same field name, different mechanism.

### Reconciling PR #336 (SCENARIOS_WAIVED)

PR #336 introduced the `SCENARIOS_WAIVED` escape hatch so the verifier would not block on un-executable prose scenarios. With `DOCUMENTED` now being the natural non-blocking status for all prose `when` fields, `SCENARIOS_WAIVED` is retained as a **narrowed audited escape hatch** for exceptional legacy cases (e.g. tasks created before this change whose scenarios were explicitly waived by a human). It is not a general bypass of the gate.

**Migration caveat**: tasks that were waived under the old regime (all scenarios returned `SKIPPED`, waiver applied) will continue to route through the `SCENARIOS_WAIVED` path without disruption. New tasks whose scenarios are prose-only will naturally produce all-`DOCUMENTED` results and route through without needing a waiver. The `SCENARIOS_WAIVED_MARKER` remains in `verification.py` for backward compatibility; the judge prompt now describes it as a narrowed escape hatch rather than a general bypass.

**Dependency-bot auto-waiver**: `_scenarios_waived(task, prior)` also returns `True` when the inbound handover carries `prior.dependency_bot_authorized` (autonomous `dependency_sweep` PRs — see [dep_sweep.md](dep_sweep.md)). A lockfile-only Dependabot bump has no meaningful test scenarios and is already gated by the full CI suite, so it routes through the `SCENARIOS_WAIVED` path rather than stalling `verification` on `SCENARIOS_MISSING`. `effective_verdict` still forces `REQUEST_CHANGES` on any `DIFF_FINDINGS_CRITICAL > 0`, so correctness gating is unaffected.

### Operator repair: task-level override and workspace-level scenario bindings

`_effective_scenarios` (`alan/teams/verification.py`) resolves through a three-tier precedence chain. Tiers 1/2 are the original logic; tier 3 is `alan/scenario_binding.py`'s overlay, added so a stale or unsatisfiable binding can be corrected on **any** workspace shape, including one with no subtasks. `verification.py` and `alan/_dispatcher_reconcile.py` (the OOB/requirements DoD probe, relocated from `dispatcher.py` by H5.2) both delegate to the same `alan.scenario_binding` primitives, so the live verification pipeline and the out-of-band completion path never diverge on what counts as "runnable":

1. **Task-level scenarios** (`Task.scenarios`) when the current task carries any — written by the decomposer at planning time.
2. **Prior handover's `test_scenarios`** when the task carries none — the path taken by an atomic, undecomposed workspace, where `Meta.tasks` is empty and there is no task-level slot to write into at all.
3. **`Meta.scenario_bindings[scenario_id]`** (`alan/workspace.py`) — a workspace-level overlay keyed by `TestScenario.id`, applied on top of whichever of tiers 1/2 supplied the base scenario. A binding may repoint `when`/`test_ref` and/or mark the scenario `waived`; it can never change the scenario's `id`, its `then` predicate, or the scenario *set* itself — only the binding, not the assertion, is editable through this path.

`when` and `test_ref` precedence when both a binding and the base scenario carry a `when`: `_apply_binding` (`alan/scenario_binding.py`) blanks the overlaid scenario's `when` whenever the binding supplies `test_ref` without also supplying `when` — this is deliberate, not an oversight. `_resolve_command` (`alan/teams/_scenario_runner.py`) only falls back to synthesising a command from `test_ref` when `when` is blank, and `TestScenario.when` is a required field that every real scenario populates, so a `test_ref`-only overlay that left `when` untouched would be silently ineffective: the runner would keep executing the stale `when` command while `GET .../scenarios` showed the "corrected" `test_ref`. Supplying `when` in the same PUT always wins outright.

```python
task = _find_current_task(workspace)
if task is not None and task.scenarios:
    return task.scenarios          # tier 1
if prior is not None:
    return prior.test_scenarios    # tier 2
return []
# alan.scenario_binding.bound(meta, scenarios) then overlays any tier-3 binding, by id
```

**Tiers 1/2 precedence is deliberate and stays; the task-immutability invariant survives.** Task scenarios are written by the decomposer at planning time and are immutable to *workers* — a worker that could overwrite them could weaken its own acceptance criteria, which is precisely what the gate exists to prevent. The binding tier does not reopen that hole: every binding write (`PUT`/`DELETE .../scenarios/{scenario_id}/binding`, `alan/routes/scenario_binding.py`) sits behind the same `require_control_token` dependency as the task-level route below, and the control token is never handed to a worker's prompt — only a human operator (or their automation, hitting the API directly) can reach it.

The gap the binding tier closes is the *operator's*. A decomposer-authored scenario can be unsatisfiable by construction — a `when` whose command cannot possibly emit what its `then` asserts — or, the failure mode that actually cost a delivery, its `test_ref`/`when` can go **stale**: a PR's own test reorganization moves the file or function a scenario points at, the behaviour still has a passing test at the new path, but the stored scenario still names the old one. Either way, no `implementation_fix` commit can ever clear it, because the code was never the problem — the loop runs until the spiral counter escalates. On a workspace with subtasks, `PUT .../tasks/{task_id}/scenarios` (below) already repairs this by rewriting `Task.scenarios` wholesale. On a workspace with **no subtasks** — the dominant shape, since the decomposer correctly keeps an atomic item whole — that route 409s (`_reject_no_subtasks_or_archived`, `alan/routes/workspaces.py`), and there is no `Meta.tasks[]` entry to relax the guard into: repairing tier 2 in place isn't possible either, since handovers are immutable, append-only history. `Meta.scenario_bindings`, keyed by scenario id rather than by task, reaches this shape — and every other shape — with one lookup and no task-key plumbing.

Motivating cases: workspace `unblock-main-and-close-block-cla` (PR #918) — scenario `timer_lint_rules_enforced_and_ratcheted` had `when: npm --prefix alan/web run lint` but a `then` asserting vitest meta-test output that `lint` never emits; six `implementation_fix` iterations hit the identical diagnostic on a diff that was correct from the first commit — and roadmap item H8.1b (PR #1015) — a 0-subtask workspace whose verification run returned `DIFF_FINDINGS_CRITICAL: 0` and confirmed every scope item, yet still escalated and could not self-recover, because 4 of 8 stored scenarios named test functions at paths the PR's own test reorganization had moved (all four had passing tests at the new paths — nothing was unverified, the *pointers* were wrong), and the designed repair route 409'd on the empty subtask list.

#### `PUT /api/workspaces/{workspace_id}/tasks/{task_id}/scenarios` (task-level, `alan/routes/workspaces.py`)

- Body carries `scenarios` (full replacement) and/or `waived`; at least one is required, and supplying only one leaves the other field untouched.
- `404` for an unknown workspace or subtask, `409` when the workspace has no subtasks or is archived.
- Every call appends a row to `scenario_override_audit.jsonl` **before** the mutation — an acceptance gate overridden by hand must leave a trail, exactly as out-of-band completion does.

#### `GET/PUT/DELETE /api/workspaces/{workspace_id}/scenarios[/{scenario_id}/binding]` (workspace-level, `alan/routes/scenario_binding.py`)

- `GET .../scenarios` is the operator's discovery view — the current effective (bound) scenario list, which ids are waived, and the resolved `ScenarioMode` — without which an operator would have to read `handovers/` by hand to find a stale reference. Resolution is scoped to the workspace's own task id (`ws.task_id`), mirroring tiers 1/2 above; for a decomposed workspace, the task-level route remains the precise per-subtask mechanism.
- `PUT .../scenarios/{scenario_id}/binding` (control-token gated) writes or replaces the binding for one scenario id. Body: `{when?, test_ref?, waived?, reason}` — `reason` mandatory and non-empty; at least one of `when`/`test_ref`/`waived` is required. Four guards, checked in order:
  1. `404` — unknown workspace.
  2. `409` — workspace is archived.
  3. `404` — `scenario_id` is not in the workspace's scenario set, so a binding can never attach to an id that doesn't exist.
  4. `422` — a supplied `when` fails `alan.teams._scenario_runner._is_prose_rejection`. This is the **executability guard**: a `when` outside the scenario runner's command allowlist resolves to `DOCUMENTED` (non-blocking) rather than being executed, so an unguarded repoint would be a silent universal waiver dressed up as a repair — the guard forces every correction to stay an executable, runnable command.
  5. `409` — `waived=true` on a scenario id referenced by a live `Requirement.test_ref`. `acceptance.all_requirements_satisfied` leaves an unmatched `test_ref` `PENDING` forever, so waiving such a scenario would trade a loud escalation for a silent completion deadlock.

  A repeated `PUT` **replaces** the binding wholesale, not a merge — a second call that supplies only `when` resets `waived` back to `false` unless it is supplied again in that same call.
- `DELETE .../scenarios/{scenario_id}/binding` (control-token gated) removes the binding, reverting to whatever tier 1/2 would otherwise supply — the same unknown-workspace/archived/unknown-scenario-id guards as `PUT`, minus the two guards that only apply to a value being set. The unknown-scenario-id guard is relaxed for DELETE only: an id that has fallen out of the workspace's current scenario set (e.g. a later handover's `test_scenarios` no longer lists it) but still has a live entry in `Meta.scenario_bindings` is treated as known, so an orphaned binding can always be cleaned up. `PUT` keeps the guard strict — a binding can still never be *created or repointed* against an id that doesn't currently exist.
- Both mutating verbs append to the **same** `scenario_override_audit.jsonl` the task-level route uses, with a `"kind": "binding"` discriminator (plus `"action": "put"|"delete"`) — so "how often is the gate overridden by hand" stays a one-file read regardless of which route did it — and both record a `SCENARIO_OVERRIDE` `Intervention`, same as the task-level route.

**Per-id waiver is narrower than `SCENARIOS_WAIVED`.** `SCENARIOS_WAIVED` (above) is all-or-nothing: when it applies, `scenario_mode` returns `WAIVED` and *no* scenario for that task runs at all. A per-scenario-id binding waiver only removes that one id from the runnable set (`alan.scenario_binding.runnable`); every other, unwaived scenario keeps executing and blocking exactly as before, and waiving an id is refused outright (409, guard 5 above) when a live `Requirement.test_ref` still points at it. `scenario_mode` only escalates to workspace-level `WAIVED` when *every* scenario id currently in play has been individually waived. The distinction between "this binding is stale" and "this behaviour is broken" survives because the two repair verbs mean different things: a `when`/`test_ref` repoint keeps the scenario executing — and failing, if the behaviour really is broken; `waived` is the deliberate, audited, reason-carrying admission that it should not run at all.

A binding persists until explicitly `DELETE`d — it is not tied to any particular handover or task, so it survives decomposition of the workspace (an atomic workspace that later gets split into subtasks keeps its bindings, because they are keyed by scenario id on `Meta`, not by task id).

Prefer repairing the scenario over waiving it, at either tier. A repaired `when`/`test_ref` keeps the DoD proof; `waived` discards it.

### 2026-08-10 update: the class recurred, and the `then` mismatch is now `ADVISORY`, never blocking

The class documented above recurred exactly this way in PR #1015 (roadmap H8.1b): six of eight scenarios FAILed on a fully green pytest run, and a human had to dismiss a verifier review to unblock a diff that was correct from the first commit. The remedy above — the operator repair endpoint — could not fire for it: `PUT .../tasks/{task_id}/scenarios` returns `409` when the workspace has no subtasks, and PR #1015's workspace was the atomic (single-task) shape. A count across `~/.alan/workspaces/` found 630 occurrences of the `then`-mismatch diagnostic across 160 handover files in ~65 distinct workspaces — every one by construction a command that exited 0 — and no instance where the mismatch caught a real defect.

The fix: a `then` mismatch on a `when` command that exited 0 no longer produces `FAIL`. It produces `ADVISORY` — see the taxonomy table above. Only the `when` command's own exit status can block a scenario now; `then` is still checked and a mismatch is still surfaced as diagnostic text, but the mismatch alone can never flip a verdict to REQUEST_CHANGES. This makes the predicate advisory-only *by construction* — it does not depend on authors writing `then` text that happens to appear verbatim in test-runner output, nor on an operator repairing it after the fact. The operator-repair endpoint above is no longer load-bearing for this specific class; it remains the right tool for other repairs (e.g. waiving a scenario outright), and its `409` gap for 0-subtask workspaces is a real problem tracked and fixed separately, out of scope for this change.

### Operator repair: withdrawing an acceptance clause directly

Every recognised door above records a human ruling as the byproduct of answering a card the fleet raised. `PUT /api/workspaces/{workspace_id}/clauses/{clause_id}/withdrawal` (`alan/routes/answer.py`'s `operator_clause_router`, wired in `alan/server.py` beside `answer_router`) is a fifth, trusted-operator door with no card in front of it: an operator can withdraw a live acceptance clause directly, distinct from a ruling that came from answering a question.

- Gated by `require_control_token` (`alan.control_plane`) — the control token is never handed to a worker's prompt, so this route is unreachable by any fleet worker, exactly like the scenario-binding and task-scenario operator routes above.
- Guards, checked in order: `404` unknown workspace; `409` workspace archived; `404` `clause_id` does not resolve against a live `Requirement.id`; `409` the clause is already withdrawn.
- The withdrawal marker's `withdrawn_by_question_id` is stamped with the sentinel value `alan.clause_withdrawal.OPERATOR_WITHDRAWAL_SENTINEL` (`"operator:withdrawal"`) rather than a real question id — the acceptance-clause data model gains no new field; the operator ruling reuses the existing marker with a synthetic provenance value that every downstream reader (`acceptance.is_withdrawn`, `RequirementsChecklist`) can distinguish from a question-answered withdrawal by value alone.
- Every call appends a row to the **same** `scenario_override_audit.jsonl` the task-level and workspace-level scenario-binding routes already write to, via the same `alan.teams._audit.append_jsonl_audit` helper. Counting only **kinded** rows — the file also carries task-level scenario-override rows written by `alan/routes/workspaces.py:380` with **no `kind` field at all**, outside this accounting — there are now three distinct `kind` values: `"binding"`, written by two call sites (`alan/routes/scenario_binding.py:104` and `alan/_dispatcher_scenario_rebind.py:66`), `"clause_withdrawal"` from the operator `PUT` below, and `"clause_reinstatement"` from the operator `DELETE` below.
- The route does **not** call `alan.workspace.record_intervention` — there is no `InterventionAction` member for an operator clause withdrawal or its reversal. The resulting gap in `finisher_rate`'s intervention accounting is a known, accepted cost, filed as a follow-up rather than risking a mislabelled reused `InterventionAction`.
- **Reversal (the real rule).** `DELETE` on the same path — `reinstate_clause_as_operator`, same `operator_clause_router` — reverses an operator withdrawal: `require_control_token` gated, same guard set as the `PUT` plus two more, checked in order: `404` unknown workspace; `409` workspace archived; `404` `clause_id` does not resolve; `409` the clause is not withdrawn (checked first, so a live clause and an already-reinstated clause both get this specific answer — a second `DELETE` is never a silent `200`); `409` the withdrawal came from a human answering a question, with its own detail string distinct from the wrong-token `403`. A stated `reason` is required exactly as the `PUT` requires one, and a `clause_reinstatement` audit row is appended only after the mutation succeeds — `append_jsonl_audit` swallows its own write failures and never raises, so ordering is the only mechanism that keeps a failed write from ever leaving a trail claiming a reversal that did not happen. **Question-provenance withdrawals stay one-way, permanently, through every path** — this reversal touches only a clause whose `withdrawn_by_question_id` equals `OPERATOR_WITHDRAWAL_SENTINEL`.
- **Why the clearing had to be taught to `alan/workspace.py`, not bypassed.** `_merge_withdrawal_markers` re-applies on-disk withdrawal markers on every write, so a clearing verb living anywhere outside `alan/workspace.py` would be silently re-undone by the very merge it was trying to bypass. `alan.clause_withdrawal` sits above `alan.workspace` in the `[tool.importlinter]` layers and already imports it, so the sentinel cannot travel downward — `update_requirements` gained one optional keyword-only argument, `clear_withdrawn: tuple[frozenset[str], str] | None`, and stays value-agnostic: it is *told* the ids and the expected on-disk value by the caller, and drops a marker only when they match. The clear is opt-in per clause id and conditioned on that value — a caller naming the wrong provenance clears nothing — so `clause_withdrawal.reinstate` passes `OPERATOR_WITHDRAWAL_SENTINEL` as the expected value and can therefore never clear a question-answered marker, even one that happens to sit in the same id set. Every existing writer of the clause list (the question-withdrawal, reconciliation, and brief-refinement paths) omits the new argument and carries an existing marker forward exactly as it does today — none of their three call sites changed.
- **The bound.** Durable against every writer that takes a fresh read. A writer holding a snapshot taken *before* the reversal re-withdraws the clause from its own carried state on its next write — the three requirements writers that carry a marker on their own incoming objects, and roughly ten whole-meta `update_*` writers that write `requirements` verbatim from an in-memory snapshot. The operator's remedy is to repeat the `DELETE`. **This whole-state overwrite hazard predates this change and affects withdrawals equally today**; it is a pre-existing condition, not something this reversal introduces, and it is filed separately rather than fixed here.
- **Frozen history.** `Handover.clause_outcome` is immutable, so a verification run already in flight was prompted from the pre-reversal live set and will not audit the reinstated clause — the reversal is a state repair, and the operator re-dispatches verification to get a fresh audit. `_clause_stall.detect`'s baseline is the last verification handover carrying a `clause_outcome`, reset only by a `revisit_amend`, so the next verification run will likely re-mint the identical stall: the reversal restores the pre-withdrawal situation, stall included, by design.
- **The replay conversion, stated and tested, not guarded.** `_clause_stall_fully_withdrawn` (`alan/routes/answer.py`) counts *any* withdrawal marker regardless of provenance, so a reversal re-arms the replay of an already-recorded stall answer: the next answer `POST` on that clause-stall question re-withdraws the clause, this time with a **question id** — which is one-way. Since every measured operator withdrawal to date was made under a live clause stall, this is the normal, expected next step for a reinstated clause, not a defect to close.
- The requirements view renders an operator withdrawal with its own label — `RequirementsChecklist`'s `ClauseDisplay` union gains `"WITHDRAWN_BY_OPERATOR"` alongside `"WITHDRAWN"`, checked before the generic non-null branch so the sentinel value is recognised first; both the visible label ("withdrawn by operator") and the `aria-label` ("status: withdrawn by operator") are distinct from a question-withdrawn clause's ("withdrawn"/"status: withdrawn"), reusing the existing status vocabulary (`STATUS_LABELS`/`STATUS_CLASSES`/`STATUS_ICONS`) with no new UI primitive. A reinstated clause renders as whatever status it genuinely has, with no visual trace that it was ever withdrawn-and-reinstated — correct for this API-only scope, and the seam a future operator-facing reversal affordance will have to design against.

## Clause audit in verification (H8.1b)

Code review answers "is this diff good?"; nothing previously asked "is it what was asked for?" Four merged PRs (#990/#992/#994/#996) violated their own explicit acceptance clauses with zero `diff_reviewer` findings. `alan/teams/_clause_audit.py` adds a `clause_auditor` role to verification stage 1 that reads the workspace's stored clauses and reports a per-clause verdict, host-enforced.

**Clause selection (Scope (a)).** `_select_requirements` picks the audited set from `workspace.meta`:
- Undecomposed workspace (`len(meta.tasks) <= 1`) → all of `meta.requirements`.
- Decomposed workspace (`len(meta.tasks) > 1`) → `alan.acceptance.scoped_clause_requirements(meta, task_id)`'s owned `Requirement` objects. **Corrected:** before this change, `scoped_clause_requirements` applied no sibling subtraction at all — the "never a sibling-owned clause, the same disjointness guarantee `scoped_dod` provides" claim this line used to make was false; a requirement double-claimed by two siblings audited identically against both subtasks' diffs. Both `scoped_dod` and `scoped_clause_requirements` now resolve ownership through the single `alan.acceptance.resolve_owners` (see above) — a double-claimed requirement has exactly one owner, and only the owner's subtask sees it in its audited set.
- A subtask that loses every requirement it claimed to sibling ownership records a new `clause_audit_skipped_no_owned_requirements` audit row (distinct from `clause_audit_skipped_unscoped` below, which fires when the subtask has no `dod_clauses` at all) and runs no auditor — the skip is recorded, never silent.
- A subtask in a multi-task workspace with **no `dod_clauses`** runs **no auditor at all** — `scoped_clause_requirements` returns `None`, which is recorded as a `clause_audit_skipped_unscoped` audit row rather than silently auditing every workspace clause against one subtask's diff.
- `requirements` `None`/empty, or `ALAN_CLAUSE_AUDIT=off` → the role does not run: zero prompt text, zero cost.

**The fenced `len(meta.tasks) <= 1` comparison is deliberately not `< 1`.** A workspace with zero tasks is the normal shape of every kept, undecomposed single-PR item in the fleet, and `<= 1` routes it into `_select_undecomposed_requirements`, which audits the full live `meta.requirements` — exactly as it always has. Tightening the comparison to `< 1` would route a zero-task workspace into `_select_decomposed_requirements` instead, where `_find_task` returns `None` for a task id that names no task, `scoped_clause_requirements` returns `None` in response, and `_select_requirements` returns `[]` with a `clause_audit_skipped_unscoped` row — silently disabling the clause gate for every zero-task workspace in the fleet, in a gate that defaults to `enforce`. `test_zero_task_workspace_audits_full_dod_not_skipped` (`tests/test_clause_audit_selection.py`) pins the `<= 1` behaviour directly against a zero-task `meta.tasks`, so a future edit that narrows this comparison fails loudly instead of merely dropping test coverage for an untested branch.

**The `clause_audit_scope` audit row.** `_select_decomposed_requirements` appends one `clause_audit_scope` row (`verification_audit.jsonl`) whenever it selects a non-empty clause set for the audited task — guarded so the existing `clause_audit_skipped_*` rows above are never doubled up with this one on the same call. `selected` maps each clause id in the audited set to its owning task id; `not_selected` maps every other **live** clause id to the task id that owns it, restricted to ids `alan.acceptance.clause_owner_map` can actually resolve an owner for. `clause_owner_map(meta)` unions a `parent_task_id is None` pass over `resolve_owners` with the existing `_all_group_owners` (group owners winning on overlap, matching `_resolve_ownership`'s own precedence) — `_all_group_owners` alone returns `{}` for a flat dispatch DAG, since `_sibling_parent_ids` only collects non-`None` parent ids, and a flat multi-task dispatch (the shape this work adds) is exactly a DAG with no parent ids at all. The row is what lets a later reader of a *passing* audit tell that a clause absent from `selected` was accounted for — owned by a named sibling task — rather than silently forgotten; it is a strict extension of the existing ownership mechanism `scoped_dod`'s `sibling_owned` already computes, not a second one. **This is a different row, with a different trigger, from `append_route_audit_row`'s `clause_audit_route_unaudited`**: the latter fires once at workspace-creation time, only for a roadmap-item-gated workspace dispatched with no `requirements` at all, and says nothing about ownership; `clause_audit_scope` fires at verification time, once per audited PR attempt (a verification retry appends its own row, exactly as `clause_audit_skipped_*` already does), and only when a decomposed or dispatch-owned selection actually chose a non-empty clause subset.

**The gate hole this closes, and the live-fleet behaviour change.** Before this change, `alan.acceptance._coverage_and_evidence` counted `evidenced` as a plain union over every task's `dod_clauses` with `evidence` set, with no regard to which sibling actually owned a requirement — so a double-claimed requirement could be marked satisfied by whichever subtask happened to merge first (and stamp evidence), whether or not it could actually deliver the requirement. `evidenced` is now restricted to the resolved owner's own clause; `covered` stays an unfiltered union across every task (unaffected by the change — the owner is always among the claimants, so `covered`'s membership is identical either way). This is a live-fleet behaviour change, not just a new-code guard: a workspace whose persisted `meta.json` already carries an unresolved double-claim will see `all_clauses_satisfied` tighten the next time it is evaluated.

**Persisted-data asymmetry.** A split produced after this change never persists a double-claimed `covers` — `alan/teams/decomposer.py` repairs it deterministically at parse time (see [decomposer.md](decomposer.md)). A split persisted before this change, or a task injected by a path other than the decomposer, may still carry overlapping `covers` on disk; those rely on the read-side `resolve_owners` call inside `scoped_dod`/`scoped_clause_requirements`/`_coverage_and_evidence` for the same one-owner resolution, applied at read time rather than baked into the stored data.

**Host evidence pre-pass (Scope (b)).** Before the role runs, `_clause_audit.begin` fetches the PR's diff file list (`_pr_branch.fetch_diff_files`) and `isDraft`/`headRefName`/`baseRefName` via `gh pr view --json` — host-side, because a worker's own `gh` calls are denied headless. Both fetches degrade to `None`/unavailable on any failure (non-zero exit, malformed JSON, timeout) rather than raising; the auditor is told plainly when ground truth is unavailable. The same block also lists the pull request's required-check **names** (`_clause_actionability.check_name_lines`, read from the `PrReadiness` `begin` already holds — the union of its passing, pending and failing sets, sorted) so a `check="<name>"` citation copies an exact spelling instead of guessing one. Names only, never conclusions: a conclusion read this early is usually not the one that matters (see the decision-time read below), and a rendered "passed" would invite a `PASS` verdict grounded on a check rather than on the diff. The block is omitted when the head has no check runs yet — routine, since verification starts seconds after the push — and the auditor prompt then sends it to the `name:` of the workflow job in its own checkout.

**The CLAUSE line contract (Scope (c)/(d)).** The `clause_auditor` role emits one line per clause: `CLAUSE <req-id>: PASS|FAIL|UNVERIFIABLE — <evidence>`, plus a trailing `CLAUSE_FAILURES: <n>` line. A `FAIL` with no cited evidence downgrades to `UNVERIFIABLE`; `UNVERIFIABLE` never blocks. Parsing itself lives in `alan/teams/_clause_line_parse.py` — a leaf module `_clause_audit.py` imports from, never the reverse, so the split introduces no import cycle. `_clause_audit.absorb` parses the output; on a parse failure it retries once (`_run_clause_auditor_retry`, the `_JUDGE_RETRY_NODE_ID` precedent), then degrades to all-`UNVERIFIABLE` plus a `clause_audit_parse_failed` audit row — recorded, never a silent block. Gating always reads the **parsed `CLAUSE` rows**, never the `CLAUSE_FAILURES` count line; a mismatch between the two is recorded on the result as an audit field rather than trusted, so a model writing `CLAUSE_FAILURES: 0` above three FAIL rows cannot silently disable enforcement — this cross-check fires identically whether the rows underneath it came from the canonical pattern or a decorated one.

**Three accepted presentation families, and the ordering rule.** `parse_clause_audit(output, audited_ids)` tries three explicitly anchored regexes per line, in this fixed priority order — never a single relaxed pattern:

1. **Canonical** (`_CLAUSE_LINE_CANONICAL_RE`) — copied verbatim from the pre-tolerance pattern, unchanged. Evidence may be empty; a `FAIL` with empty evidence still demotes to `UNVERIFIABLE` exactly as before. This is the **only** pattern that fail-open can reach.
2. **Decorated** (`_CLAUSE_LINE_DECORATED_RE`) — tolerates a leading blockquote/list marker (`>`, `-`, `*`, `+`, `N.`), markdown emphasis or backticks around `CLAUSE`, the req-id, or the verdict word, and an absent `CLAUSE` keyword. Evidence is **required non-empty** (`\S.*`) — a decorated `FAIL` with no evidence text simply does not match this pattern (or any other), so it is dropped rather than silently demoted.
3. **Inverted** (`_CLAUSE_LINE_INVERTED_RE`) — the one fleet shape that swaps the position of the separator and the verdict token, `<id> — VERDICT: <evidence>` instead of the canonical `<id>: VERDICT — <evidence>`. Matched as its own fully-anchored alternative, never by relaxing the canonical pattern's own ordering — a matcher that hunts for the nearest verdict word to an id would treat evidence prose containing those words as a verdict, turning a failure into a pass.

A line is tried against canonical first; if canonical matches but the captured req-id itself carries stray markdown characters (a bold or backticked id swallowed whole by canonical's permissive `[^\s:]+` class), that match is discarded and the line falls through to decorated instead — this is what lets `CLAUSE **req-1**: PASS — evidence` resolve to the clean id `req-1` rather than being rejected as a foreign id spelled `**req-1**`.

**The de-quotation rule.** A parsed line counts only if its req-id is a member of `audited_ids` — the live requirement ids this specific verification pass is actually auditing, already in hand on `ClauseAuditContext.requirements`. A line naming an id not under audit (quoted from a prior workspace's example, or a code-fenced sample the auditor pasted for illustration) is dropped silently, per line — the surrounding valid rows are unaffected. Two rows for the **same** audited id carrying **different** verdicts reject the **whole output** as unparseable (triggers the existing retry-then-degrade path); identical repeats (same id, same verdict) collapse to the first occurrence by document position. This is what lets a clause line quoted inside prose, or fenced in a code block as an example, be ignored instead of counted as a real verdict — without a special-cased pattern for either shape.

**Why tolerance never reopens the fail-open.** The known fail-open is structural: a `FAIL` row whose evidence group captures empty is silently rewritten to `UNVERIFIABLE` (see "The known risk" note below), and it exists only inside the canonical pattern's match arm. Both new patterns require non-empty evidence as a **precondition of matching at all** — a decorated or inverted line with no evidence text does not produce a row, it produces nothing, and an audited id with no row for it is not silently marked passing anywhere downstream. Tolerating three presentation shapes therefore cannot widen the one place a blocking verdict can go quiet.

**The retry runs grounded, not in the service's own checkout.** The retry runs with verification's role override (`VerificationTeam._role_overrides`): the same grounded slot directory and engine-rendered tool grant as the first auditor — on a secondary repository, that repository's own grant, never the default repository's. Verification hands the override in as a required keyword-only `overrides` on `absorb`, `_parse_with_retry`, and `_run_clause_auditor_retry`, because `_clause_audit` is imported by verification and cannot import it back to derive the override itself. The retry therefore passes `_require_grounded_cwd` like its sibling nodes; a caller that omits the override fails the type check and the call itself, instead of silently running the retry in the service's own checkout on `main`. `_role_overrides` currently ignores its role name, so a future role-specific grant would have to name the retry explicitly. **The retry runs under its own system prompt, not the first auditor's.** `clause_auditor_retry_prompt(cfg)` keeps the auditor's head and tail but swaps the TEST OWNERSHIP block for a `TEST OWNERSHIP (RETRY)` block: the first attempt in this checkout already owned and ran this pass's suite/gate commands (named per engine — the default engine's two runs, a secondary engine's gate list, or "declares no local quality gates") exactly once, so the retry must not run any suite or gate; the first attempt's full output rides along as the `### clause_auditor` section of the retry's user text and the log files it captured are still in the same checkout, to be re-read and cited. The user-level RETRY NUDGE repeats the same instruction, so system and user text agree — under the original ownership block's "run each exactly once" the system text would have outranked the nudge. The first run's TEST OWNERSHIP block, for its part, tells the auditor to capture each suite the one time it runs it with the run's own exit status preserved (`… > pytest_full.log 2>&1; rc=$?; tail -60 pytest_full.log; (exit $rc)`, likewise `vitest_full.log`) and cite from the file with `grep -n`, so re-formatting output is never a reason to run a suite again and a second run of either suite is a defect in the audit, not extra evidence.

**`ALAN_CLAUSE_AUDIT` modes (Scope (e)).** `off` runs nothing. `report` is advisory-by-absence: `absorb` strips the `clause_auditor` pair out of the judge's input entirely in this mode, so the judge's own computation is byte-identical to a build with no clause audit — the consequence lives in host code, never a prompt caveat (the `_review_context.py` ratchet-loosening-audit precedent, `_audit_ratchet_loosening`). `enforce` is the **default** (owner ruling, 2026-08-09) and feeds the judge normally; `_clause_audit.apply` force-downgrades an APPROVE to REQUEST_CHANGES (the `_maybe_flag_count_flip` shape — a named banner, not a silent rewrite) whenever an evidenced `FAIL` survives partitioning as `ACTIONABLE`, or a non-actionable batch still contains a `PR_STATE` demotion. A batch whose every demotion is corroborated by a passing cited check is neither downgraded nor escalated — see "Per-clause partitioning" below for the full three-way split.

**PR-state-only escalation.** When **every** `FAIL` row's evidence is prefixed `PR_STATE:` — tested inside `_clause_actionability.partition` by its `PR_STATE:`-prefix branch in `_classify_and_corroborate` — the auditor's signal that the only evidence behind each of those FAILs is the host-provided `isDraft`/head/base block rather than diff content — the result escalates directly to a blocking `verification_escalation` `OpenQuestion` (`_emit_clause_pr_state_escalation`) instead of routing to `implementation_fix`: a fix worker cannot mutate PR state, so burning a fix cycle toward the spiral cap buys nothing. A mix of one `PR_STATE:` FAIL and one ordinary FAIL does not escalate — routing to `implementation_fix` can still address the ordinary FAIL.

**Operator-only post-merge measurements** are a third corroboration-free demotion, alongside `PR_STATE:` and the two check-corroborated classes below. `_uncorroborated_class` (the first statement of `_classify_and_corroborate`) recognizes an `OPERATOR_ONLY:`-prefixed evidence string the same way it recognizes `PR_STATE:`: classified before any check-citation logic runs, `check_name`/`check_outcome` both `None`. It exists for a clause that can only be satisfied after merge, by an operator with live access — a live-traffic measurement, a multi-day batch observation, anything no pre-merge artifact could contain — so there is nothing a fix worker could try. `ClauseActionability.OPERATOR_ONLY` is deliberately excluded from `_STAND_DOWN_ELIGIBLE` (`stands_down` requires both membership in that frozenset and a corroborated `PASS`, not a corroborated `PASS` alone), so a batch whose only failures are operator-only can never fall through to a silent pass — visibility is preserved in every case. It always escalates to a human via `_emit_clause_pr_state_escalation`, under a distinct `clause-audit-operator-only` question id (instead of `clause-audit-pr-state`) whenever any row in the batch is `OPERATOR_ONLY` — this is deliberate: a workspace that hits both classes across passes must not have the second escalation dedupe silently against an already-answered first one. The escalation names every implicated clause (`cause_text`) and its remediation option directs the human to file or reference a tracking issue for the measurements, then re-dispatch verification — no fleet worker is ever asked to close that tracking issue. A mix of one `OPERATOR_ONLY:` FAIL and one ordinary FAIL does not escalate on this path either — the ordinary FAIL still routes to `implementation_fix` unchanged, with the operator-only id named only in the demoted note.

**The operator-only escalation now stops re-firing.** Before this fix, answering an operator-only escalation dispatched straight back to `verification`, which re-derived the identical `OPERATOR_ONLY` finding and escalated again — the answer never stuck. Two things close the loop. First, `ClauseOutcome.operator_only_ids: tuple[str, ...]` (schema 1.23, additive, default `()` — no version bump) carries exactly the ids classified `OPERATOR_ONLY` in the batch; `_clause_outcome_from_rows` now returns a populated outcome whenever *either* `actionable` or `unactionable` is non-empty (previously: only on a non-empty actionable set), so an all-unactionable batch — the operator-only-only shape — gets an outcome for the first time, and `_emit_clause_pr_state_escalation` attaches it to the escalation handover exactly as `_emit_clause_stall_escalation` already attaches `ClauseOutcome.actionable_ids`. Second, `alan.clause_withdrawal.resolve_human_ruling` — already the mechanism that host-derives a resolver/effect pair for a clause-stall question regardless of what was persisted on disk — now also recognises the operator-only question id (`CLAUSE_AUDIT_OPERATOR_ONLY_QUESTION_ID = "clause-audit-operator-only"`) and maps **both** of its options to `Ruling("pr_merge", "closes", "clause")`: the remediation option (`OPTION_OPERATOR_ONLY_WORDING_CURRENT`, ending "…then proceed to merge." — `OPTION_OPERATOR_ONLY_WORDING_LEGACY`, ending "…then re-dispatch verification.", is kept as a recognised legacy wording so an escalation persisted before this change still resolves) and the override option (`OPTION_CLAUSE_OVERRIDE_WORDING`, "Override the clause manually and proceed."). Routing to `pr_merge` rather than `verification` is the actual fix; the wording change alone would have been cosmetic. `alan.routes.answer._apply_human_ruling` passes the answered `question` into `clause_withdrawal.clause_ids_for_withdrawal(ws, escalation, question=question)`, which reads `ClauseOutcome.operator_only_ids` instead of `actionable_ids` whenever `is_operator_only_escalation(question)` is true, then withdraws exactly those ids — so the underlying `Requirement`s get `withdrawn_by_question_id` set and `_select_requirements`'s `live_clauses` filter (see "The auditor never sees a withdrawn clause" below) hides them from every later audit pass, the same mechanism that already closes the loop for a clause-stall withdrawal. `alan.routes._answer_waiver.is_waiver` reads the same ruling — `ruling is not None and ruling.resolver == "pr_merge"` over `resolve_human_ruling(question, answer)` — so a legacy-persisted operator-only escalation whose `option_resolvers` was never populated (every escalation raised before this fix) still gets its standing `CHANGES_REQUESTED` review dismissed as a waiver on answer, not left blocking merge.

**Verification never starts on an already-merged PR.** A second, independent defect: answering *any* escalation on a workspace whose PR had already merged still re-dispatched a full verification pass, and — because a squash-merge deletes the head branch — that pass's own `gh pr view --json headRefName` would come back empty, parking the workspace with "PR missing," the exact wrong human-facing report for a PR that is in fact done. `alan/teams/_verification_merged_guard.py` (new, no import-layer manifest entry needed — see below) closes this: `pr_state_name(pr_number, forge_target) -> str | None` makes one `gh pr view --json state` call and returns the raw state string, or `None` on any failure (missing binary, timeout, non-zero exit, empty stdout) — a tri-state, never conflating "not merged" with "couldn't tell." `terminal_if_merged(...)` is a no-op unless `pr_number` is present and `pr_state_name` returns exactly `"MERGED"`; only then does it append a `verification_merged_short_circuit` audit row and return a `build_terminal_handover` (never a park, never the missing-PR escalation path) carrying the merged PR's number. `VerificationTeam.run` calls this **between** resolving `(pr_number, branch)` and the `pr_number is None or branch is None` precondition check — deliberately after branch resolution runs (so a squash-deleted branch is still looked up, at no extra cost, exactly as before) but before the precondition decides what a `None` branch means, so a merged PR's now-gone branch is read as "already done," never as "PR missing." A transient `gh` failure (`pr_state_name` returning `None`) always falls through to the unchanged precondition/grounded-checkout path — a forge blip can never silently terminate a live verification pass.

**The table (Scope (f)).** `render_clause_table` renders the parsed rows as a markdown table; `apply` appends it to the judge output in **both** `report` and `enforce` modes, so it reaches both the posted review body (`_maybe_post_review`) and the `_write_review_artifact` output regardless of mode — fix workers see which clause failed and why even when the mode dial is dialed back to advisory.

**A required check's conclusion may now be consulted — narrowly (stop-routing-unactionable-remediations, 2026-08-18).** Blocking still rides the existing REQUEST_CHANGES → `implementation_fix` → spiral-escalation channel, exactly like every other verdict-path signal in this file. What changed: the clause auditor may cite a required check by name (`check="<exact name>"`) inside a FAIL's evidence, as corroboration that the failure is (or is not) attributable to the diff. The host resolves that citation via `alan.teams._pr_ready.resolve_named_check_outcome` against a `PrReadiness` read **at decision time** — `_clause_audit._decision_readiness`, called from `_enforce_outcome` after the judge has run — not against the one `begin` fetched when the pass started (see "Why the conclusion is read at decision time" below). The resulting `CheckOutcome` can only ever **demote** — never create a block, never produce a `PASS` verdict for the clause, never re-arm:

- It can demote a FAIL from fix-routing (`implementation_fix`) two ways: to a blocking human escalation (a `PR_STATE` demotion present in an otherwise non-actionable batch — the same `OpenQuestion`/`verification_escalation` route), or, when every demotion in the batch is corroborated by a passing cited check, to a stand-down that rewrites nothing and lets the batch fall through to normal routing instead — never the reverse, and never from a `PASS`/`UNVERIFIABLE` starting point.
- It never produces a `PASS` for the clause itself — the clause's own verdict in the rendered table stays `FAIL` either way. Only *who gets asked to fix it* changes: a fix worker, or a human told the real cause.
- It never re-arms: the check's conclusion is read once, synchronously, inside the same verification pass that produced the FAIL, at the moment that pass decides. There is no polling, no deferred re-evaluation, no mechanism by which a later CI event flips an already-decided outcome — a check-conclusion-based re-armer can never reach a verdict-path signal, because three separate consumers in this repo's merge pipeline (branch protection, the dispatcher merge gate, verification's own external-gate downgrade) key on a check's *conclusion*, not on any opt-in advisory flag, so anything that lets a later event flip an already-decided verdict re-arms all three at once; this carve-out is deliberately narrower than that hazard.

Three guards keep this fail-closed:

1. **Same head SHA.** The `PrReadiness` `begin()` fetches alongside the PR-state fetch is the **anchor**: it pins the head the auditor's checkout was grounded at. The decision-time read is accepted only when its `head_sha` equals the anchor's (`_clause_actionability.same_head`); a missing anchor, an anchor with no `head_sha` (its forge read failed), or a head that moved while the pass ran all resolve to no readiness at all, which guard 3 turns into `ACTIONABLE`. The decision read goes through `_pr_ready.readiness_or_unavailable`, so a forge rate limit or transient error at that moment comes back as an unavailable readiness with no head — the same `ACTIONABLE` outcome — instead of raising out of a verification pass whose every stage has already run and been paid for. Neither value is ever forwarded from an earlier stage of the pipeline or a prior invocation.
2. **Positively-passed set only.** `resolve_named_check_outcome` only returns `PASS` when the cited name appears in `PrReadiness.passing_checks`, built from `statusCheckRollup` conclusions that are unambiguously `SUCCESS` — `NEUTRAL`/`SKIPPED`/`CANCELLED`/absent all fall through to `ABSENT`, never `PASS`. See [merge_recovery.md](merge_recovery.md)'s `CheckOutcome` section for the full resolution table.
3. **Fail-closed on everything else.** `ABSENT` and `FAIL_OR_PENDING` both resolve to `ACTIONABLE` in `alan.teams._clause_actionability.classify_failure`'s decision order — a check that can't be positively proven to have passed corroborates nothing, so an uncorroborated `ENV:` or `check="..."` nomination never demotes anything on its own. This guard is orthogonal to the `OPERATOR_ONLY:` prefix (above), which is uncorroborated by construction — it never attempts a check citation and never depends on `PrReadiness` at all.

**Why the conclusion is read at decision time (alan#1640, 2026-09-20).** The carve-out originally resolved citations against the `PrReadiness` fetched in `begin()`. Verification is dispatched the moment the implementer or fix worker pushes, so that read lands seconds after the push: on alan#1640 the pass began at 07:34:31Z, the head's CI run was *created* at 07:34:35Z, it was green by 07:38:57Z, and the verdict was decided at 07:47Z — against a snapshot in which the run did not yet exist. Every citation therefore resolved `ABSENT`, guard 3 made the FAIL `ACTIONABLE`, and a clause a green blocking check had already proven was routed to a fix worker who could do nothing about it; two fix cycles later the workspace parked `non_actionable_feedback`. The read now happens in `_enforce_outcome`, after every stage and the judge have finished. This is still one synchronous read inside the pass that produced the FAIL — only its moment moved, so "never re-arms" holds unchanged — and it is skipped entirely (no forge call) when no FAIL row carries a corroborable citation: `_clause_actionability.cites_check` ignores a citation sitting under a `PR_STATE:`/`OPERATOR_ONLY:` prefix, since those classes never consult a check. The auditor prompt was widened to match: a citation is owed not only for a local command that failed but for a command the pass **did not or may not run** (an end-to-end or rendered-UI audit run) when a required check runs exactly that command, and it is owed even when the auditor cannot tell whether the check has finished. A check still pending at decision time stays `ACTIONABLE`; that residue is the unblocker's (`docs/architecture/unblocker.md`), not a reason to poll here.

**Per-clause partitioning (`alan.teams._clause_actionability.partition`).** A batch of FAILs is no longer judged all-or-nothing. Each FAIL row's evidence is classified independently, in this fail-closed order: a `PR_STATE:` or `OPERATOR_ONLY:` prefix always wins first (via `_uncorroborated_class`, before any check-citation logic runs); then a missing/stale `PrReadiness` or unparseable `check="..."` citation is `ACTIONABLE`; then a cited check whose `CheckOutcome` isn't `PASS` is `ACTIONABLE`; only a corroborated `PASS` can yield `HOST_ENV` (an `ENV:`-prefixed nomination) or `CHECK_CONTRADICTED` (any other corroborated FAIL). `apply()` routes the partitioned batch three ways, discriminated by the corroboration property: any actionable FAIL still downgrades an APPROVE to REQUEST_CHANGES and routes to `implementation_fix`, exactly as before — a genuine failure alongside an unactionable one still blocks. With no actionable FAIL but a `PR_STATE` or `OPERATOR_ONLY` demotion present, the batch still escalates to the blocking human route, exactly as before, preempting routing. With no actionable FAIL and no `PR_STATE`/`OPERATOR_ONLY` demotion — `alan.teams._clause_actionability.stands_down(parts)` is true, which holds exactly when every demoted clause's classification is in the structural `_STAND_DOWN_ELIGIBLE` set (`HOST_ENV`/`CHECK_CONTRADICTED` only — `OPERATOR_ONLY` can never be a member) **and** its `check_outcome` is a corroborated `PASS` — the batch **stands down**: no verdict rewrite, no escalation, the clause table still renders with each clause's own `FAIL` verdict intact, and the batch falls through to the existing effective-verdict and routing logic, so a genuine fix route (judge-found criticals) or a gate-owned merge route can still fire. Each demoted clause is recorded additively as a `clause_demoted_unactionable` row in `verification_audit.jsonl` (`req_id`, `demotion_class`, `corroborating_check`, `check_outcome`) on all three paths, so the frequency of each path is measurable after ship rather than reconstructed from transcripts.

**Description clauses resolve against the live PR body, never the dispatch brief.** `_fetch_pr_state` fetches `body` via the same `gh pr view --json` call that already backs the `isDraft`/head/base evidence, and `evidence_prefix()` renders it under an explicit instruction that a clause about the change description must be judged against that live text — never against the immutable dispatch brief in the user prompt, which no actor can edit and which diverges the moment anyone updates the PR. The PR body is human-editable and becomes the squash-merge commit body, so evaluating it live is a deliberate choice, not an oversight — the guard against it becoming a silent bypass path is that a description clause still needs the auditor to find corroborating evidence in the diff/checkout content per the clause's own text; a trivially-satisfying body edit with no corresponding diff change does not by itself manufacture that evidence.

## Clause kind: record clauses advise, behaviour clauses block

Every acceptance clause used to block with equal force whatever evidence it could possibly have. `Requirement.kind: ClauseKind | None` (`alan/workspace.py`, `ClauseKind = Literal["behaviour", "record"]`) gives a clause a kind. A **behaviour** clause has behavioural evidence and keeps its full blocking power. A **record** clause can only ever be evidenced by a record — prose in a document or in a change description — so when it fails in a verification pass the verdict stands, nothing escalates, and the failure is recorded rather than enforced.

**Persisted literals.** `"behaviour"` and `"record"` are written into `meta.json` forever; renaming either is a data migration, not a refactor. The field is nullable and defaults to `None` on purpose: a defaulted non-nullable field generates as a required TypeScript property and would force every existing fixture and generated-type consumer to change, whereas a nullable one renders optional exactly like `withdrawn_by_question_id`. A clause persisted before this change, or created without a kind, loads as `None` and nothing back-fills a value. Every backend reader tests only `req.kind == "record"`, so `None` and `"behaviour"` both block — the fail-closed direction. The kind does not participate in the clause's identity: `_clause_id` still hashes the text alone, so adding the field changed no existing clause's id.

**Chosen once, at creation.** A kind supplied on a workspace-creation request survives creation (`workspace._sanitize_requirements` is the only rebuild on the create path; single-task and multi-task creation share it). `alan/app/workspace_create_models.py::_canonical_requirements` also rebuilds clauses, but its output is discarded after the coverage check, so it is not a persistence site and is deliberately untouched. `brief_refine._carry_forward` carries a clause's kind forward unchanged, including across a text rewrite; house rules minted or appended by refinement take the default (`None`, blocking). No later stage chooses a kind.

**Who produces a record clause.** The build chat's proposal path is the producer. The `EXTRACT_DISPATCH_YAML` contract (`_BUILD_DISPATCH_CONTRACT` in `alan/claude_cli.py`) asks for a `recorded_clauses` list beside `acceptance_clauses` — outcomes whose only possible evidence is prose, a docs passage or the change description — plus one advisory budget sentence (keep the blocking list to about a dozen clauses; prefer splitting an item over compound clauses). `DispatchProposal.recorded_clauses` (a `FreeTextList`, under the same title requirement as `acceptance_clauses`) carries it, and the web UI's `deriveRequirementsFromAcceptanceClauses` is the single site that mints kinds on that path: blocking clauses are sent with **no** `kind` (absent, never an explicit `"behaviour"`), recorded clauses with `kind: "record"`. A direct workspace-creation request remains a second producer, not the only one. The explore chat's contract never asks for the key; the shared model accepts it there but it stays empty in practice. There is no host-side budget: nothing counts clauses, refuses a proposal or bounces an over-budget one — the budget is prompt guidance plus the count the proposal view shows.

**Duplicate text collapses at creation.** `workspace._sanitize_requirements` folds clauses of identical stripped text — the same text that keys the clause id — into one, on every creation path. The survivor blocks if any copy blocked: a record copy never displaces a blocking one, so a text listed in both groups arrives once and blocks. The first blocking copy is the survivor: its `test_ref` and its kind literal — absent or an explicit `"behaviour"` — survive, and any later blocking copy is dropped, including one that carries a different `test_ref` or the other literal. A record copy held first is replaced by the first blocking copy that follows, so that copy's `test_ref` and literal survive instead. Survivors keep first-occurrence order. This is a creation-time rule only: `update_requirements` (used by `clause_withdrawal`, `_dispatcher_reconcile` and `brief_refine`) does not pass through the sanitizer, so later refinement of an existing workspace's clauses is outside its reach and a duplicate introduced there is accepted. The uncovered-clause refusal (`reject_uncovered_clauses` in `alan/app/workspace_create_models.py`) still runs on the pre-collapse body; that direction is fail-closed, since a duplicate can only make it stricter.

**Accepted risk.** A model can file a genuinely behavioural outcome as recorded, and no deterministic host-side guard catches it; only the all-recorded degenerate case is covered, by the anti-gaming floor below. The control is the person confirming the dispatch, who sees the proposal in two groups headed `Blocking (n)` and `Recorded (n)` — the blocking count is always in the heading text. On the auto-dispatch path, and on any creation path that bypasses the proposal door, nobody looks.

**Why a record clause cannot name a `test_ref`.** A `model_validator(mode="after")` rejects `kind == "record"` together with a `test_ref`. `alan/acceptance.py` reads a clause's `status` only when the clause names a test reference (`_resolved_status`, `all_requirements_satisfied` and `_clause_ok`), so making the combination unrepresentable keeps a record clause's pass/fail state inert in every downstream consumer without editing any of them. The rejection is what makes the rest of the design safe and must not be relaxed as fussy.

**The split happens before enforcement.** `_clause_audit.apply` separates the failing rows by kind *before* `_enforce_outcome` runs. Only the blocking rows reach `_enforce_outcome`, so only behavioural failures can rewrite an approving verdict, escalate, or produce a `ClauseOutcome`. Filtering afterwards would not work: a record `FAIL` can never carry a corroborating passing check, so it would classify as unactionable, leave `escalate_unactionable` true and park the workspace. When only record clauses failed, `apply` returns the judge output plus the table with `escalate_unactionable=False`, no `clause_outcome`, and no actionable ids. When both kinds failed, only the behavioural ids are actionable and the record rows carry an `(advisory — record clause)` mark in the table's Evidence column. `UNVERIFIABLE` rows are never marked. Table marks render in every mode; the audit rows below are written in `enforce` mode only.

**Advisory means the fix worker never sees it.** A record failure never enters `ClauseOutcome`, the structure that carries failing clauses to the fix worker (`_fix_forward.render_failing_clause_block` reads `prior.clause_outcome`), to the clause-stall detector, or to clause withdrawal. Even when a sibling behavioural failure sends the workspace to `implementation_fix`, that worker is told about the behavioural clause only. This is the stated boundary, not an omission: the record failure is carried by the posted review's clause table alone.

**The anti-gaming floor.** If a workspace authored no behavioural clause of its own, every clause blocks regardless of kind, and the table appends `_No behaviour clause was authored; every clause is enforced._`. Without it, a workspace consisting only of record clauses could never fail. "Of its own" is load-bearing: `brief_refine` appends `HOUSE_RULES` — behavioural clauses — to every workspace, so a floor that counted them would be switched off automatically nearly everywhere and would protect nothing. `_clause_audit.begin` therefore evaluates the floor once (`ClauseAuditContext.floor_active`) over **all** of `meta.requirements` — the workspace's authored set, withdrawn clauses included, never the per-task selection `_select_requirements` returns — minus the house-rule ids, which are derived (the clause-id hash of each rule's text) rather than persisted. Two consequences follow. The floor is constant for the workspace's whole life, so withdrawing every behavioural clause mid-flight cannot flip the remaining record clauses into blockers and re-park the human who withdrew them. And a decomposed subtask whose own clauses are all record still takes its failures as advisory when the workspace authored a behavioural clause elsewhere — the case this feature exists for. An author's own clause whose text exactly equals a house rule's text has the house rule's id and is excluded from the floor; only text-equal duplicates are affected.

**The durable record.** Each advisory record failure appends one `clause_record_advisory` row to `verification_audit.jsonl` carrying `task_id`, `pr_number`, `req_id` and `judging_verdict` (`_verdict.parse_verdict` of the judge output, `null` when the judge emitted no parseable verdict). It is the machine-readable evidence of how often the mechanism fires.

**Two adjacent paths are deliberately unchanged and stay fail-closed.** They apply to clauses of any kind and read as contradicting "record clauses never block" if not named. First, the coverage-and-evidence path that can drive a workspace's terminal status: a record clause a subtask covers *without evidence* still blocks terminal completion. Second, `reject_uncovered_clauses`: a decomposed create carrying a record clause that no task covers is still refused. The clause-stall detector, the withdrawal buckets, the live-clause filter and the unproven-clause health metric are also untouched — unchanged is fail-closed here.

## Clause-stall detector: ending the fix loop on a clause no role can satisfy

The clause audit above stops a change that violates its own acceptance clauses from merging silently. It does not, by itself, stop the fleet from repeatedly dispatching a fix worker against a clause that asserts a precondition the delivered design cannot satisfy — every move available to that worker either violates a standing rule (refuse and escalate) or ships code that cannot satisfy the clause (fails the build). `alan/teams/_clause_stall.py`'s `detect` recognises this class directly and routes it to a human the first time it recurs, rather than after the generic loop-guard backstop finally exhausts (see `docs/architecture/loop_guard.md`'s "Clause-stall short-circuit" section for the full precedence and wiring).

That framing is the detector's motivation — *why the detector exists* — not something the host observes on a given firing. The host observes exactly one thing: the same clause ids in the actionable set of two consecutive verification runs. The stall question therefore tells the operator only that observation (the repeating ids, the two-run statement, the currently actionable set an answer acts on, and each clause's text, evidence and the judge's reasoning), and does not claim the clause is unresolvable, unfixable, or a matter for a human scoping decision.

**What it requires.** A **non-empty intersection** of `ClauseOutcome.actionable_ids` across **two consecutive verification runs on the same `handover_chain_id`**, scoped to the same audited `task_id` — compared as sets, so auditor row order is irrelevant. A correlated group of more than one repeating clause trips it exactly like a single clause does. An asymmetric or shrinking actionable set (`{X, Y}` then `{X}`, or `{X, Y}` then `{X, Z}`) **does** trip it, on the survivor: until 2026-09-17 the rule was exact-set equality and such a set was read as progress, which alan#1538 falsified — an LLM auditor re-audits a fixed clause set and returns a different actionable subset each run at an unchanged HEAD, so exact equality made the only human escape hatch conditional on that set repeating bit-for-bit, and the workspace dead-ended instead. Only a wholly **disjoint** pair (`{X}` then `{Y}`) is still read as progress. See `docs/architecture/loop_guard.md`'s "Clause-stall short-circuit" section for the full detection rule, the `clause_ids`/`repeated_ids` split, the plural `ClauseStall`/`StalledClause` shape, and the question-id derivation (a single repeating clause keeps `clause-stall-<id>`; a repeating group hashes to a bounded `clause-stall-<16-hex>` id).

**Why the scan reads `alan.handover.list_handovers(ws)`, never a subtask-scoped file glob.** Handovers are filed as `handover_{ws.task_id}_{seq}.yaml` — keyed on the *workspace's* task id, not the audited subtask's — because `alan.handover.save_handover` raises unless `handover.task_id == ws.task_id`. A glob scoped to the audited subtask id (`handover_paths_under(ws.path, effective_task_id)`) would therefore return an empty list on every decomposed workspace and silently disable the detector there. `_clause_stall._latest_verification_since_intervention` scans the full chain-scoped handover list instead, and `detect` scopes to the correct subtask by comparing the embedded `ClauseOutcome.task_id` field on each candidate — the same pattern the clause audit's own `_select_requirements` and `scoped_clause_requirements` already use to resolve ownership on a decomposed workspace.

**Reset on human intervention, not on any intervening handover.** The count is of consecutive verification runs since the last recorded human intervention. `record_answer` always writes a `revisit_amend` handover (copying the blocking handover's `from_team`), so `_latest_verification_since_intervention` treats meeting one on the chain — before it ever meets a `from_team == "verification"` candidate — as a reset: it returns `None` immediately, without looking further back. An `implementation_fix` handover in between two verification passes is *not* a reset by this rule: a fix worker attempting (and failing) to move the clause is exactly the evidence the detector exists to catch, so intervening commits must not suppress it.

**The audit row is an output, never an input.** Every hit appends one line to `verification_audit.jsonl` (`action: "clause_stall_detected"`, `task_id`, `audited_task_id`, `req_id`, `req_ids`, `repeated_req_ids`, `prior_req_ids`, `prior_handover_id`) — a record of the host's own decision, never re-read to make it. `prior_req_ids` and `repeated_req_ids` exist so a suspected premature stall can be diagnosed from the log alone: without them an exact repeat is indistinguishable from a partial overlap. `ClauseOutcome` itself carries the same guarantee one level up: it is populated exclusively by `alan.teams._clause_audit._clause_outcome_from_rows` from the clause auditor's parsed `CLAUSE` rows and the host's `ClauseAuditContext`, restricted to the batch's actionable rows — no judged role's own prose can shape or forge one.

## `SCENARIOS_MISSING` self-heal: `implementation_fix` re-emit → forward

When a subtask has no `test_scenarios` and no `dod_clauses`, the scenario runner returns `SCENARIOS_MISSING` and the verifier is forced to `REQUEST_CHANGES` — even on a 0-CRITICAL, fully-covered diff. The pipeline heals this by routing the leaf to `implementation_fix`, which re-emits the Definition-of-Done as scenarios that the *next* verification run reads via `_effective_scenarios` (`prior.test_scenarios`, subtask-scoped by `_verification_task_id_var`).

The re-emit is a **write-side contract** in `alan/teams/implementation_fix.py`:

- **Canonical fence.** The worker is instructed (both `_SYSTEM_PROMPT` and the generic-engine tail) to append a yaml code block whose opening fence carries the `test_scenarios.yaml` info-string (```` ```yaml test_scenarios.yaml ````), with one 5-field entry (`id`, `description`, `given`, `when`, `then`) per DoD behavior. The guidance text is a single constant, `alan/teams/_scenario_block.py::SCENARIOS_BLOCK_GUIDANCE`, interpolated into both `_SYSTEM_PROMPT` and `_GENERIC_FIX_STATIC_TAIL` rather than duplicated — it also tells the worker to quote any free-text value containing a colon-space (`: `), to quote any value opening with a `'`, `"`, or backtick, and to re-read the finished block and confirm it parses as YAML before ending the turn.
- **Tolerant parser.** `_parse_fix_scenarios` accepts, in precedence order: the exact `test_scenarios.yaml`-info-string fence, a `## TEST SCENARIOS` heading followed by a yaml block, or a bare `yaml`/`yml` code block. A bare block is only accepted when it is a mapping with a `test_scenarios:` key **or** a list in which *every* item validates as a full `TestScenario` — so `INLINE_FINDINGS_YAML` (`path`/`line`/`body`) and the `non_actionable_feedback.yaml` info-string block are never mis-read as scenarios. Clean-fence scanning (only whitespace after the language tag) structurally excludes info-string'd fences.
- **Per-entry syntax recovery, scoped to positively-identified blocks.** The exact-fence and `## TEST SCENARIOS`-heading paths (never the bare-block path, whose strict all-or-nothing behaviour is a deliberate guard against reading an unrelated fenced block as scenarios) already tolerate an individual entry that parses but fails `TestScenario` validation (`strict=False`). `alan/teams/_scenario_block.py::recover_entries` extends that leniency to a *hard YAML syntax error* on the whole block: when `yaml.safe_load` raises on the full block text (most commonly an unquoted colon-space inside a free-text field value, occasionally a value opening with a quote or backtick), `_parse_scoped_block` splits the block on top-level list entries (lines opening at column zero with `-`), parses and validates each chunk independently, and keeps every entry that succeeds — so one malformed entry costs that entry, not the whole block. Accepted limit: a uniformly indented block has no column-zero entries, so it does not split and recovers nothing — identical to pre-recovery behaviour, except the outcome is now audited (below).
- **Forward, don't escalate.** In `_finalize_fix`, when the fix produced **no commits** but parsed scenarios, the handover is `forward` → `verification` (carrying the scenarios) instead of a no-commit `escalation`. The forward audit (`impl_audit.jsonl`, `action: scenarios_only_forward`) records `inbound_scenarios_missing` so operators can confirm the self-heal fired for a genuine `SCENARIOS_MISSING`. No commits **and** no parseable scenarios still escalates — the gate is never silently passed; the no-commits sentinel (`alan/loop_guard.py::_NO_COMMITS_SENTINEL`) and its routing are unaffected by any of this.
- **`scenario_block_unparsed` audit row.** When a positively-identified block (exact fence or heading — never a bare block) yields **zero** scenarios after recovery, `alan/teams/_scenario_block.py::unparsed_audit_row` returns a row appended to the same `impl_audit.jsonl` `_finalize_fix` already writes to (no new audit file, no `alan/retention_registry.py` entry): `task_id`, `action: "scenario_block_unparsed"`, `team`, plus two **optional** fields, `parse_error` and `source_line`, filled in by `_parse_diagnostics` re-parsing the matched block. Three designed shapes, keyed on the outcome rather than the exception: (1) a **marked** syntax error (PyYAML's `MarkedYAMLError`, which exposes `problem_mark`) — both `parse_error` and `source_line` (the offending line, read from `problem_mark.line`) are present; (2) an **unmarked** syntax error (a bare `YAMLError` with no mark, e.g. `ReaderError` on an illegal control character) — `parse_error` only; (3) **no exception at all** — every entry parsed as valid YAML but failed `TestScenario` validation, the case recovery cannot repair — neither field is present. This row fires whether the zero-scenarios outcome came from the new per-entry recovery or from the pre-existing item-validation leniency; it does not itself change routing — a zero-scenario, no-commits run still takes the existing `no_commits_handover` escalation path. The action string `scenario_block_unparsed` was checked against `alan/teams/triage_pregate.py::_FAILURE_KEYWORDS` (`fail`, `error`, `timeout`, `exception`, `401`, `403`, `5xx`) and contains none of them — a future rename needs the same check, since `_is_failure_line` substring-matches the action field alone and this row fires on roughly a fifth of results carrying the fence.

## Fix-role scenario rebind

The operator-repair endpoints above (`PUT .../tasks/{task_id}/scenarios`, `PUT/DELETE .../scenarios/{scenario_id}/binding`) require a human to hold the control token. When a verification run reports that a scenario's `when`/`test_ref` no longer resolves — the checkout artifact class documented above, not a defect in the diff — the fix role that reads that finding sees it accurately and repeatedly, but previously had nowhere to put the correction: the wholesale `test_scenarios.yaml` re-emit (`SCENARIOS_MISSING` self-heal, above) restates the *whole* scenario list and is gated on `Task.scenarios` being empty, so it silently discards any workspace whose task already carries scenarios; and nothing wrote the workspace-level binding tier at all from inside a worker. `alan/teams/_scenario_rebind_block.py` + `alan/_dispatcher_scenario_rebind.py` close that gap with a narrower, host-validated channel.

**The block shape — one shape only.** `implementation_fix` may append a fenced `scenario_rebind.yaml` block to its final synthesis: a YAML mapping of scenario id → the exact command that now proves it, one entry per corrected id.

```yaml scenario_rebind.yaml
<scenario_id>: <the exact command that now proves this scenario>
```

`alan.teams._scenario_rebind_block.parse_rebinds` accepts only a top-level mapping whose values are non-empty plain strings; any key that is not a string, or any value that is not a plain string (a nested mapping — the shape a worker would reach for to smuggle `waived`/`given`/`then`/`test_ref` alongside a command — a list, a bool, a number) is **dropped wholesale**, never partially honored. This is what makes the channel unable to waive a scenario even by accident: there is no field this parser will ever read as a waiver. `unparsed_rebind_audit_row` mirrors `unparsed_audit_row` above — a positively-identified fence that recovers zero entries after parsing appends a `scenario_rebind_unparsed` row (with `parse_error`/`source_line` when available) to `impl_audit.jsonl`, exactly like the `test_scenarios.yaml` re-emit's own diagnostic.

**Why the target is the binding overlay, not `Task.scenarios`.** `alan.scenario_binding.effective_scenarios` applies `bound()` — the `Meta.scenario_bindings` overlay — *after* resolving the base scenario set, whichever tier supplied it (`Task.scenarios` on a decomposed workspace, `prior.test_scenarios` on an atomic one). Writing into the overlay therefore reaches both shapes through one mechanism with no precedence change anywhere: a `implementation_fix`-emitted rebind is immune to the conditional shadowing that a `Task.scenarios` rewrite would have hit (silently dropped on a decomposed workspace, landing on an atomic one — the worst outcome, an intermittent fix).

**The worker sees its own current commands.** `implementation_fix`'s `_mid_blocks` renders a `## Current scenarios and their proving commands` section — one line per scenario id and its resolved command (`alan.teams._scenario_runner.resolved_command`, the former private `_resolve_command`, now public since both the rebind prompt and the acceptance-time `_check_allowlist` call it from outside the module) — computed from `scenario_binding.effective_scenarios(workspace, prior, task_id=task_id)`, i.e. **post**-overlay: a worker iterating on an already-rebound scenario sees the corrected command, not the stale one. This block (and the `REBIND_BLOCK_GUIDANCE` prompt text explaining the channel) is rendered unconditionally, regardless of the workspace's forge target — a worker instructed to emit corrections must see its own current commands and its own recent refusals whether or not it targets the default forge, since acceptance is now judged against the workspace's own engine (below), not against which repository it targets. A rejection is visible to the same role that emitted it: `_current_scenarios_block` also appends `alan.teams._scenario_rebind_block.rejected_rebinds_block(workspace_id)` — a bounded (20-row), workspace-filtered tail-read of the same audit file the acceptance path writes to, further filtered to rows carrying a rule still in force (`LIVE_REBIND_REJECTION_RULES`, below) — so a host-side refusal stops being recorded only as the worker's own unreliability, and the role can do something other than repeat itself verbatim.

**Host-side validation, in order.** `alan._dispatcher_scenario_rebind.apply_rebinds(ws, handover, task_id)` runs inside `Dispatcher._route_after_handover`'s per-workspace lock, as the first statement after the fresh `workspace_mod.read` — ahead of the revisit-count block and the `has_forward_progress` check, so an accepted rebind still decays the chain's revisit counter rather than incrementing it — and only when `handover.from_team == "implementation_fix"`. The candidate command is **never executed**: every check below is structural, which is what let the acceptance-time subprocess probe be deleted outright rather than merely relocated. Per rebound id:

1. **Unknown id** — the id is not in `scenario_binding.base_scenarios(ws, handover, task_id=task_id)` — rejected with `scenario_binding.UNKNOWN_SCENARIO_DETAIL`, the same string the operator route's `404` uses (`alan/scenario_binding.py`, importable from both a `routes` module and a `dispatcher`-layer module since the route sits above `dispatcher` in the layers list and the reverse direction is illegal). Stamped with rule `unknown_scenario`.
2. **Invalid command** — `alan.teams._scenario_runner._check_allowlist(cmd, governing_config_for_ws(ws))` returns non-`None` — rejected with `scenario_binding.PROSE_WHEN_DETAIL` (rule `prose_when`) when the command is prose-shaped, or the per-command allowlist diagnostic itself (rule `allowlist`) otherwise. This is the **full** command-validity check (forbidden shell operator, unbalanced quotes, path traversal, or a prefix outside the scenario-runner allowlist), evaluated against the workspace's own governing engine config — a fix worker targeting a second engine is judged against that engine's own `gate_commands`/`scenario.command_prefixes`, not against the default engine's — and deliberately stricter than the operator route's `_is_prose_rejection` (which only flags an unrecognized prefix and would let a compound command through) — acceptance-time validity has no human in the loop to catch what the looser check misses.
3. **Per-handover cap** — the 11th and later id that reaches this stage (i.e. has already cleared checks 1–2) is rejected without further validation; `_MAX_REBINDS_PER_HANDOVER = 10`. Rule `rebind_cap`.
4. **Conflict with an existing binding.** A candidate that clears 1–3 is checked against whatever `ScenarioBinding` currently exists for that id: `waived=True` rejects (rule `waived_conflict` — accepting would route to verification while the scenario is still excluded from the runnable set — a silent no-op that re-manufactures the exitless loop this channel exists to close), and a set `test_ref` rejects (rule `test_ref_conflict` — a fix worker correcting `when` must never silently override an operator's deliberate reference repoint). Neither is merged; both are refused with their own reason.

There is no forge-identity check in this list: admissibility is judged solely by the workspace's own engine config (`governing_config_for_ws`), never by which repository the workspace targets, so a rebind against a second engine or any other non-default forge is accepted on exactly the same terms as one against the default engine.

**Accepted iff every check above passes** — there is no execution-based rejection left. The accepted candidate is persisted via `workspace.update_scenario_binding`, `model_copy`-merged onto any existing binding (or constructed fresh) with `when` set to the candidate command and `written_by` forced to `"fix_rebind"` — `alan.workspace.ScenarioBinding.written_by: Literal["operator", "fix_rebind"] = "operator"`, a discriminator the operator's `PUT` route structurally cannot write (`ScenarioBindingBody` carries no such field), total with an `"operator"` default so every `meta.json` written before this field existed keeps validating on read. `waived`/`test_ref` on any pre-existing binding survive the `model_copy` untouched — a rebind is a repointing, never a waiver and never a reference override. A rebind naming only some of a workspace's scenario ids leaves every unnamed id's binding — including one with `waived=True` — byte-identical. Every accept and every rejection appends a row to `scenario_override_audit.jsonl` — the same file and the same `"kind": "binding"` shape the operator `PUT`/`DELETE` route writes, with `action="fix_rebind"` or `"fix_rebind_rejected"` — so "how often is a binding overridden by hand vs. by a fix worker, and how often is a fix worker's attempt rejected and why" stays one file to read regardless of actor. Every `"fix_rebind_rejected"` row additionally carries a `"rule"` field (one of the six rule constants above), stamped at write time by the predicate that rejected it (`alan.teams._scenario_rebind_block.LIVE_REBIND_REJECTION_RULES` holds the set of rules still in force); `rejected_rebinds_block` (above) renders only rows whose `rule` is in that set, so a row written under a since-removed rule — the deleted non-default-forge refusal among them — silently ages out of the worker-facing rejection history rather than confusing the worker with a refusal reason that no longer applies. Rows written before the `rule` field existed carry none and are likewise dropped from the rendered history; that loses at most one prompt render's worth of a 20-row tail and self-heals on the next rejection.

**Fail-closed, not skip-closed: strict re-evaluation at verification.** Deleting the acceptance-time probe would be an outright weakening if a wrong correction could still resolve to a non-blocking outcome later — the same silent-drop failure mode the probe existed to prevent. `alan.scenario_binding.fix_bound_ids(meta, scenarios)` returns the ids, among a given scenario set, whose binding carries `written_by == "fix_rebind"`. `VerificationTeam._compute_scenario_results` is the **only** call site that threads this into `run_scenarios(..., strict_ids=...)` — self-heal (`_dispatcher_selfheal._run_self_heal_scenarios`) and the reconcile/out-of-band path (`_dispatcher_reconcile._run_bound_scenarios`) both resolve their checkout through `_dispatcher_selfheal._probe_checkout_for(ws)`, which now declines to run anything at all for a non-default forge rather than falling back to the dispatcher's own working directory — see "A known, deliberately unfixed gap" above — so strictness there would still have nothing to run against; the same wrong-checkout hazard this channel routes around is now a hard skip rather than a silent false-positive. `alan.teams._scenario_runner.run_scenario` takes a `strict: bool` (default `False`); when strict and the underlying result is `SKIPPED` or `DOCUMENTED` (never `ADVISORY`, `BUDGET_EXHAUSTED`, `PASS`, `FAIL`, or `TIMEOUT` — the two statuses that mean "the command never ran" for a command the fix role itself just asserted resolves), it rewrites the result to `FAIL` with the original diagnostic preserved (`dataclasses.replace`). A fix-bound scenario whose corrected command turns out not to resolve therefore blocks the gate on the very next verification pass instead of quietly dropping out of it.

**Closing the two raw-read bypasses.** Before this change, two paths ignored the binding overlay entirely: `_dispatcher_selfheal._run_self_heal_scenarios` ran `list(task.scenarios)` verbatim (now `scenario_binding.runnable(ws.meta, task.scenarios)`), and `_dispatcher_reconcile._maybe_evaluate_requirements`'s handover-carrying branch called a separate, cruder fallback (`_selfheal._run_scenarios`, deleted in this change along with its `_run_one_scenario` helper — both `# pyright: ignore[reportUnusedFunction]`-marked dead weight once nothing called them, which `vulture` now confirms) that ran `pytest -k <scenario_id>` directly, bypassing `when`/`test_ref` resolution and therefore the binding overlay entirely. Both branches of `_maybe_evaluate_requirements` (the handover-carried path and the out-of-band `_run_oob_requirement_scenarios` path) now share one helper, `_run_bound_scenarios`, that always calls the real `alan.teams._scenario_runner.run_scenarios` and filters to `keep = ("PASS", "FAIL", "ADVISORY", "TIMEOUT")` — `TIMEOUT` is included alongside `FAIL` because `acceptance._resolved_status` already treats any non-`PASS`/`ADVISORY`/`PENDING` status as `FAIL`, so a timed-out scenario resolves the requirement rather than leaving it dangling. A `SKIPPED` or `BUDGET_EXHAUSTED` scenario result (renamed test, collection error, or the run's aggregate budget spent before this scenario got a turn) leaves the requirement `PENDING` rather than the old fallback's binary PASS/FAIL/PENDING conflating a genuinely-unresolvable probe with a failing one. A rebind's effect is therefore visible on every path that can decide a workspace's outcome from scenarios — verification, self-heal, and the reconcile/out-of-band path — not just the one it happened to be tested against.

## Visibility: unbound acceptance and unevaluated self-heal scenarios

Two findings this program surfaces without changing any verdict:

**`alan.acceptance.requirements_unbound(meta) -> bool`, now built on the per-clause measure.** `all_clauses_satisfied` and `all_requirements_satisfied` degrade to "not blocking" whenever a workspace's requirements are entirely uncovered and untest-bound — by design, per the Phase 1a behaviour-preservation invariant above. That degradation used to be silent: nothing distinguished "this workspace's acceptance clauses are genuinely satisfied" from "this workspace's acceptance mechanism was never wired to anything," and the boolean predicate that did exist could only see the all-or-nothing case — a workspace with some but not all clauses proven produced no signal at all. `requirements_unbound` is unchanged in what it decides — `workspace_dag.workspace_terminal_status` still calls it only to decide whether to append a row to `acceptance_vacuity_audit.jsonl` (`task_id`, `workspace_id`) on a `Status.COMPLETED` outcome, and the returned status is unchanged either way — but it is now `bool(reqs) and len(unproven_clause_ids(...)) == len(reqs)`, riding the same per-clause `unproven_clause_ids` the API and UI now surface (above). That measure closes the partial-coverage blind spot as a byproduct: a workspace-level count of 409 workspaces carrying requirements (4597 clause rows, measured 2026-09-05) breaks down as 283 with every clause unproven, 4 partially proven, and 122 fully proven — the "4 partial" bucket is exactly what the old boolean could never distinguish from "fully proven," since it only fired on total vacuity. A clause with a `test_ref` (even an unresolved one) or any covered clause is never counted as unproven — a devil's-advocate false positive `unproven_clause_ids` deliberately does not raise, since a workspace on the road to being wired up (a `test_ref` bound but not yet resolved) is not the same finding as one where nothing was ever wired.

**Self-heal withholds confirmation on an unevaluated scenario, and now says why.** `_dispatcher_selfheal._scenarios_confirm_done` previously confirmed self-heal whenever at least one scenario resolved `PASS`/`ADVISORY` and none `FAIL` — a workspace with some scenarios `SKIPPED` or `DOCUMENTED` (an unresolvable `test_ref`, a prose `when`) could still self-heal on the strength of the ones that did run. It now additionally returns `False` whenever any result is `SKIPPED`, `DOCUMENTED`, `TIMEOUT`, or `BUDGET_EXHAUSTED`, so a self-heal proof is never partial — every named scenario must have actually been evaluated (`PASS`/`FAIL`/`ADVISORY`) for the DAG to conclude done this way; `TIMEOUT` and `BUDGET_EXHAUSTED` join the `_UNEVALUATED_STATUSES` set for the same reason `SKIPPED`/`DOCUMENTED` are there — neither one is proof the behaviour works, so neither may silently license a self-heal. This makes the previously-quiet decline loud without making it blocking: `_record_self_heal_audit` now writes a `self_heal_audit.jsonl` row (with the new `unevaluated_scenario_ids` field) on *every* self-heal attempt that actually produced scenario results, confirmed or not — not only the confirmed path as before — so an operator can grep for "self-heal declined because a scenario was unevaluated" as a findable signal. `SKIPPED`/`DOCUMENTED` remain members of `NON_BLOCKING_STATUSES` everywhere else in the pipeline (as does `BUDGET_EXHAUSTED`, added when `TIMEOUT` and `BUDGET_EXHAUSTED` were introduced as first-class statuses — see the status table above); this withholding is scoped to the self-heal DAG-completion decision alone and does not itself mint a new blocking status.
