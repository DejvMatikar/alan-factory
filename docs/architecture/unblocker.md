# Autonomous build-workspace unblocker

**Tier 1 (shipped):** `alan/unblock_sweep.py`, `alan/unblock_recipes.py`, `alan/unblock_ledger.py`, `alan/teams/unblock_issue.py`.
**Tier 2 (planned):** an Opus planner and a bounded executor on top of the same ledger — see "Tier 2" below.
**Reused, unmodified:** `alan/dispatch.py`, `alan/handover.py`, `alan/merge_gate.py`, `alan/teams/_pr_ready.py`, `alan/teams/_pr_post.py`, `alan/teams/_pr_feedback.py`, `alan/teams/_pr_state_paths.py`, `alan/repo_status.py`, `alan/proposal_items.py`. `alan/incident.py` carries `STUCK_WS_STATUSES`, `incident_fingerprint` and (added for the read model below) `stuck_workspace_keys` — the sweep's own behaviour is untouched.

## Why this exists

A parked workspace is the fleet saying "a human decides now". Measured on the 30 days before 2026-09-19 (2,653 handovers, 217 workspaces): 169 blocking questions on 63 workspaces, every one of them `awaiting_input` + `park_reason: question`. Three quarters had a deterministic answer — a verifier review that outlived the commit it judged, a "declared blocker" that no longer held on main, a fix pass that correctly produced no commits, a check that went green after the park — and each answer was written down in a driver skill or a memory file and applied by hand. Nothing autonomous covered that population: `alan/incident.py::_is_exempt` drops every question park, so `derive_incidents` yields no incident and neither the investigator nor auto-continue ever fires on it; `alan/auto_continue.py` refuses any blocking question by design. The one exception, the merge-park green sweep, re-probed exactly one shape (`pr-merge-failed`, check green at the same head). This document generalises that sweep into a recipe table, records every attempt in a ledger with ceilings, and leaves one GitHub issue per park shape behind so the fleet defect producing the shape stays visible until fixed. Owner ruling, 2026-09-19: all stuck shapes on every engine; the recipe tier first, the planner tier after; the host owns every stall (the interactive driver loops never answer or re-dispatch a park); deterministic proof only for anything that lowers the bar; immediately at park with a backoff re-probe; one issue per shape per engine.

## Tier 1: the recipe sweep

### Trigger and exemptions

`LoopMixin._maybe_sweep_unblocks` (`alan/_dispatcher_loop.py`) calls `unblock_sweep.sweep(...)` every `SWEEP_INTERVAL_S` (60 s) from `_loop`, gated by the same `_deploy_gate_sweep_lock` compare-and-set the deploy-gate sweep uses, against `DispatcherState._unblock_sweep_next_at` (class default `0.0`, so the first tick after a restart sweeps). There is deliberately **no callee at the terminal-transition seam** (`_schedule_manager_summary`): that seam runs inside the dispatcher's non-reentrant workspace lock where forge work is forbidden, and a second writer of the watch blob would be a read-modify-write race. A workspace with no watch entry is due immediately, so "act at park time" is met within one tick by a single writer.

Enumeration is `WorkspaceIndex.rows()` (stat-validated, cheap) filtered to `STUCK_WS_STATUSES` (`awaiting_input`, `escalated`, `failed`, `partial`), then one `workspace.read` per stuck row. `candidate_for` exempts, with no attempt and no issue: internal teams (`triage`, `dependency_sweep`); a design-family workspace awaiting harvest (team or latest `from_team` ∈ `DESIGN_FAMILY_TEAMS` with no `to_team_suggestions` — that park is its terminal shape); a delivered workspace (latest handover from `deploy_verify` with no blocking question); a workspace the operator just restored from archive (`awaiting_input` with `park_reason: unarchived`, `lifecycle.held_by_unarchive`, reason `restored from archive` — it is parked because the operator chose to bring it back, not because it is stuck, so it gets no probe, no `needs_human` report and no issue; the exemption ends on its own when the operator dispatches a team or answers a question, since that moves the workspace to `active` and clears the park reason, after which any later park is treated normally); a hidden engine (`live_hidden`); an engine whose `EngineConfig.unblock_enabled` is `False`. The whole sweep returns early when `ALAN_UNBLOCK_DISABLE` is truthy or the queue is paused, and a workspace with a RUNNING job is never touched.

### Watch, backoff, act, observe

`queue_meta["unblock_watch_v1"]` holds `{task_id: {next_at, attempts, identity, acted, retried, terminal, park_head}}` in the wall-clock `Epoch` domain. The blob's one definition and one parser live in `alan/unblock_ledger.py` — `UNBLOCK_WATCH_META_KEY`, `REPROBE_CAP`, `WatchEntry` (with its `exhausted` predicate), `_parse_entry` and the public loader `load_watch` — because the record the API serves (see "Read model, rescue metrics and the log trail") carries the watch and `unblock_sweep` sits above `unblock_ledger` in the import layers, so the ledger can never import the sweep. The sweep imports those names and owns the only writer, `_save_watch`; nothing else parses or writes the blob. `identity` is `f"{latest handover id}@{meta.updated_at}"`: any state write moves it, so an entry whose identity no longer matches is dropped and the park is treated as new. Per tick at most `MAX_FORGE_CANDIDATES_PER_TICK` (3) candidates spend forge reads, and every head read counts — including a read that led to no action (an exhausted park whose head did not move, a noop-twice or ceiling report on a PR-backed row); a candidate that is not due or is running performs no read and spends none (a terminal entry is re-probed on the slow cadence described under "After a report").

For a due candidate the sweep reads readiness once (`_pr_ready.readiness_or_unavailable`, only when a PR exists) in `_read_and_settle`, before anything else, so the head is in hand for the park key, the watch record and the exhausted-park re-arm decision; it then builds a `RecipeContext` from that same read and walks `match_recipes(ctx)` in table order. Each recipe's `probe` returns `ready`, `not_yet` or `declined` with a reason: `ready` acts; any `not_yet` re-arms the entry on a 5→20 min backoff (`BASE_INTERVAL_S * 2**attempts`, capped at `MAX_INTERVAL_S`) and records one `wait` ledger row on first sight; all `declined` (or no match) files a terminal report. A forge rate-limit or transient error inside a probe is a `not_yet`. Readiness reaches the recipes as `ReadinessResult | None`: absent, `ReadinessUnavailable` and a real `PrReadiness` are the three cases every readiness-reading recipe tells apart, and the first two are a `not_yet`.

**Act** (`_act`): every plan is validated before anything is written — an `answer` plan's option must be one of the parked question's `proposed_answer_space`, must not carry `option_effects == pending_external`, and must resolve (`dispatch.resolver_team_for_answer`) to the plan's team; every plan's team must pass `dispatch.team_is_dispatchable` at the workspace's pinned posture and roster (a refusal is reported with `authority_holder = fleet_grant_missing`). Then the recipe's forge write (a review dismissal) and the probes run **outside** the workspace lock; the entry is persisted `acted=True` (write-ahead, so a crash cannot double-act) and only then `lock_for(task_id)` is taken for the re-read, the answer record and the dispatch. Inside the lock the workspace is re-read; a moved identity or a running job skips (`skipped_moved` / `skipped_running`). An `answer` plan records the option through `handover.record_answer(..., effect_override=question.option_effects.get(option))` — the same record a human answer leaves, minus `record_intervention` (human-only; it would zero the fully-autonomous metric), the gold label and the decision log. Every plan then calls `dispatch.dispatch_team_core(..., merge_gate=MergeGateDecision.skipped(UNBLOCK_SKIP_REASON), instructions_origin="generated")`; the merge gate still runs on the dispatched `pr_merge` invocation itself (`dispatcher._enforce_pr_merge_gate`). A raise inside the dispatch restores the park exactly as it was, and a raise anywhere in the act still lands an `attempt` row (`outcome = failed: <exception>`) plus its issue intent before propagating, so the ceilings count every attempt. The dispatch target is `dispatch.owning_task_id(ws, ws.task_id, blocking=...)`; a decomposed workspace without a unique owning subtask is reported, never guessed.

**Observe:** the acted entry is due again after `OBSERVE_DELAY_S` (120 s). If the workspace moved, its identity changed and the entry was dropped. If it is still parked on the same identity the action was a no-op: one retry (`retried=True`), then a terminal report with `authority_holder = nobody`.

**After a report** the entry is `terminal` but not dead: the forge can change under a park without the workspace moving (a check reruns green, a human dismisses a review), so a terminal entry is re-probed every `REPROBE_INTERVAL_S` (20 min) for up to `REPROBE_CAP` (72) probes — a day — and acts the moment a recipe reads `ready`. A re-probe that still declines only extends the entry; the report row and its issue comment are written once per identity.

**A park keeps its identity and head across re-invocation (alan#1630, alan#1645).** `identity` changes on every re-park, so it cannot say "the same stall again". The `needs_human` report fingerprint is therefore keyed on a *park key*, `incident_fingerprint("unblock:needs_human", task_id, f"{park class}@{head}")` (`unblock_ledger.park_key`). The park class (`unblock_ledger.park_class`, a pure function over strings) is the blocking question's id with the parking invocation's own token removed — the first 8 characters of the parking handover's `from_invocation_id` plus one trailing `_` or `-`; an id that does not end in that token is kept whole; a blocker-only park uses the blocker's name; neither is `""`. No question-minting site changed, and a question prefix minted later with either separator yields a stable class with no code change. The one carve-out is `_clause_stall_question_id`, which suffixes the *prior* invocation's id, so that class stays per-invocation. The head is the tick's live pull-request head — absent when the workspace has no PR or the forge read failed, which is correct, not a gap — so a park at a moved head, or of another class, reads as a first park.

The head is recorded at first sight of a park. `WatchEntry.park_head` (optional, default `None`, read with a tolerant `.get`: a record written without it loads, and a record written with it loads under the prior rules — no deploy drops live watch records) is filled from the tick's head the first time an entry is written for an identity and is never overwritten while the entry lives; because the entry is dropped on identity change, it is the head at the latest re-park. All five watch-entry constructions go through `_next_entry`, so none can forget it. The same tick head is written to `head_sha` on every report, wait, attempt and issue-intent row; that column is **forensic** — nothing reads it back. `RecipeContext.park_head` hands the park-time head to the recipes (`hand_resolved_declared_blocker`, below).

A repeat park reads as a repeat. When `report_history` (one `COUNT`/`MIN(ts)` over `report` rows for the workspace and park-key fingerprint, served by the existing `unblock_ledger_fp` index) finds earlier rows, `_report` rewrites the reason before it reaches the ledger row, the log line and `_file_intent`, so one string carries to the ledger, the activity summary and the per-shape issue comment's `probed:` line through the existing path: `<reason> · report #N of this park class at head <8 chars>, first reported <stamp>` (the head clause is omitted when none was read). The reported outcome stays `needs_human`; naming the option already chosen was dropped as a stretch item, and no repeat-park ceiling was added — that number is the owner's call. The ordinal counts report rows, not parks.

**A moved head re-arms the re-probe budget.** A terminal entry that has spent `REPROBE_CAP` probes is no longer frozen. It comes due on the same `REPROBE_INTERVAL_S` cadence and reads the head once. A head that differs from `park_head` replaces the entry with a fresh one (`attempts` 0; `terminal`, `acted` and `retried` cleared; `park_head` the new head) and the recipes run against it. An unchanged head, a failed forge read, or a park with **no** recorded head does not re-arm; the entry only advances `next_at` by `REPROBE_INTERVAL_S`, so the cadence advances whether or not it re-arms. A park with no recorded head records the live head from that first read and re-arms only on a later difference, so nothing re-arms on the day this ships.

Table order is precedence: a `pr-merge-timeout` park with a stale review is `stale_review`'s before `green_not_merging` sees it. Not yet in this tier and therefore reported as `needs_human`: verification escalations (waive / withdraw / operator-only) and walled (`pending_external`) options — the next slices add them under the deterministic-proof rule.

**Why `crash_park` reads `meta.pending_first_hop` as a fourth source (alan#1742).** A workspace created through the build front door is stamped with the team it was actually asked for, `meta.pending_first_hop`, consumed once by `_dispatcher_brief_refine.apply` the moment automatic brief refinement hands off; outside the crash-park recovery read described here, the field is never read again in production. A crash between the end of brief refinement and the first real dispatch therefore leaves a crash park whose only handover is `brief_refine`'s own terminal record — a park the first three sources cannot resolve: `brief_refine` mints no `next_hop` or `to_team_suggestions`, and it sits in `INTERNAL_ONLY_TEAMS`, so it can never satisfy `from_team in MANUALLY_DISPATCHABLE_TEAMS` either directly or through `propose_team`. `crash_team` now falls back, in third position (after the proposed next hop and the handover author, before the workspace's own `meta.team`), to `meta.pending_first_hop` when the latest handover's `from_team` is `brief_refine` and the recorded team is itself in `MANUALLY_DISPATCHABLE_TEAMS` — an operator-only team such as `dependency_sweep` still declines. A crash with no handover at all, including a crash *during* refinement itself, still declines on the same expression (`_from_team` returns `None`), because dispatching there would silently skip refinement rather than resume it. `brief_refine` stays deliberately absent from `unblock_sweep._INTERNAL_TEAMS`; adding it there would exempt every such park from the sweep entirely and make this source inert. The cost is real, not hidden: this shape spent zero lifetime unblocker attempts before this change; it now spends up to two, roughly one `SWEEP_INTERVAL_S` (60 s) apart, against the same shared `ATTEMPT_CEILING_PER_WORKSPACE` of 5 every other recipe on the workspace draws from. The change targets the service-restart case, which resolves on the first retry; a sustained upstream outage still consumes both retries and ends on the human report, exactly as before. The dispatch always carries the unblocker's own crash-park instructions text; it does not read or forward the pending first hop's operator-supplied sticky instructions — that boundary is deliberately out of scope here, left for separate work.

**Why `external_gate_spiral` dispatches the merge team, not the parking team (alan#1704).** The spiral detector (`loop_guard.detect_spiral`) parks a workspace as `escalated` with a synthetic blocker `Blocker(kind="reason", name="reason", detail="spiral:<kind>: <evidence>")` and no open question, so nothing in the table above read it: the sweep reported "no recipe recognises this park" and re-probed on the slow cadence with nothing to run, even after the named gate went green and the pull request became mergeable. The recipe recognises exactly one of the four spiral kinds, `external_gate_blocked`, by the full kind-qualified prefix `spiral:external_gate_blocked: ` — the trailing `: ` keeps a longer kind name and the other kinds out, and the evidence tail is never parsed: the kind has two producers (`_classify_unchanged_gate_checks`, whose evidence names the checks and is cut at 300 characters, and `_classify_external_gate_blocked`, whose evidence names none). The probe is the `green_not_merging` function object itself, so there is one readiness predicate. The plan is `pr_merge` because the detector fires only on the `implementation_fix` ↔ `verification` pair — re-dispatching either would re-enter the route that tripped it and risk a park-unblock-park cycle — while `pr_merge` cannot trip the detector and re-derives readiness on its own invocation, so a wrong `ready` costs one wasted invocation and a re-park, never a bad merge. A non-ready probe records no attempt, so a gate that stays red costs nothing against the ceilings. No `deploy_verify` exclusion is needed (unlike `green_not_merging`): the detector never parks a handover from that team. The kind is pinned by `EXTERNAL_GATE_SPIRAL_KIND: SpiralKind`, so renaming it in `alan/loop_guard.py` fails the type checkers, and `tests/test_unblock_recipe_external_gate_spiral.py` builds the park reason through the real dispatcher for both producers and asserts it starts with the recipe's prefix. Two accepted residuals: the type pin catches a kind rename but not a change to the `f"spiral:{kind}: "` format at `alan/dispatcher.py`'s `_enforce_loop_guard` (the dispatcher-driven tests catch that one); and `_classify_unchanged_gate_checks` does not assert zero critical findings, though the merge team's own readiness check is the backstop. The three other spiral kinds share the structural gap and are not recognised by any recipe yet.

**Why `non_actionable_green_head` bounds itself per head, not per fingerprint (alan#1640).** `implementation_fix` parks `non_actionable_feedback_<inv>` when the review it was handed names nothing its checkout can change. The shape that motivated the recipe: verification decided while the head's CI run did not exist yet, the clause audit failed a clause only a pipeline run can evidence, and the fix worker correctly refused — so the park is cured by looking again once the head is green, which is what the question's own by-hand option dispatches (`verification`), and what `acceptance_gate.md`'s decision-time check read makes succeed. The proof is the forge's, not the question text's: every required check green at the head, no human objection anywhere on the pull request. It does not prove the refused findings *were* about pipeline evidence, so the cost of a wrong guess has to be capped, and the usual cap does not hold here — the fingerprint's third component is the question id, which embeds the fix invocation's id, so every re-park is a new fingerprint and `ATTEMPT_CEILING_PER_FINGERPRINT` never counts past one. The recipe therefore reads its bound off the forge as well: each verification pass leaves one verifier review at the head it judged, so two live verifier rejections at the current head mean the retry already happened and was rejected again, and the probe declines into a `needs_human` report. One automated retry per head; a new head (someone pushed) earns one more; `ATTEMPT_CEILING_PER_WORKSPACE` still caps the workspace as a whole. Two properties of that bound are deliberate. A readiness read that is otherwise green but carries no `head_sha` is `not_yet`, never `ready`: with no head every review fails the `commit_id` comparison, the count reads zero, and the bound would silently stop binding. And the count is of reviews, not of verification passes — a review POST retried after a network error can leave two reviews from one pass — which errs only towards declining: the worst case is a retry the recipe could have made and did not, reported as `needs_human`, never a retry beyond the bound.

**Why `green_named_check_blocker` evaluates a mechanical predicate, not "the blocker is false" (alan#1730).** A fix worker can park `declared_blocker_<inv>` on a one-line claim about named checks (`backend must be green before this can merge`) that the forge already contradicts. `declared_blocker` only recognises claims about the default branch, and `hand_resolved_declared_blocker` only fires when the head moved *past* the park — the observed shape is the opposite: the worker pushed and then declared a blocker about the head it had just replaced, so the head sits at the park and no marker moved it. The recipe answers with the existing "blocker does not hold" option, which routes to `verification` and never to a merge. It does **not** claim the stated reason is false. The predicate is: the blocker's single line contains the name of at least one check this pull request has; no check on the pull request is red or pending; the merge state is `CLEAN`/`HAS_HOOKS`; and the per-head rejection bound is not exhausted. The host never interprets prose — the only text operation is whether a check name the pull request actually has occurs in the blocker's text, tested as an exact, case-sensitive substring against the union of `failing_checks`, `pending_checks` and `passing_checks`. A conditional human ask inside that same line ("once backend is green, someone must rotate the key") is invisible to the rule; the containment is the route (verification, never merge) plus the bound, not text interpretation.

The probe order is forced, and it is why neither `_usable_readiness` nor `_named_checks_green` is reused: a global "nothing failing, nothing pending" guard in front of the per-name classification would make the "a named check is red" branch unreachable, and `resolve_named_check_outcome` collapses red and pending into one outcome. The order is: readiness unusable → wait; no check results at the head → wait; more than one non-empty line → decline; no readiness check name in the line → decline; a named check red → decline, a named check pending → wait; *another* check red → decline with a distinct reason, another pending → wait; merge state not green → decline; and last, no head commit → wait, then the review stream, then the rejection count. The three decline reasons — "names no check on this pull request", "a check this blocker names is red", "another check on the pull request is red" — are distinct on purpose so a report says which. On the unblocker's read path a quarantined check stays inside `failing_checks`, so a quarantined name is in the universe and declines as named-red. `UNSTABLE` is deliberately outside the green set. `PrReadiness.review_decision` is not consulted and `_human_feedback_probe` is deliberately omitted: the review stream (`_reviews_or_probe`) is the only human guard, so a non-verifier author's `CHANGES_REQUESTED` declines, and an unresolved thread does not.

The retry bound reuses the per-head verifier-rejection ceiling exactly as `non_actionable_green_head` does, for the same reason: the question id embeds the parking invocation's id, so `ATTEMPT_CEILING_PER_FINGERPRINT` never counts past one for this shape. A read that carries no `head_sha` is `not_yet`, never `ready` — with no head every review fails the `commit_id` comparison, the count reads zero and the bound would silently stop binding. `ATTEMPT_CEILING_PER_WORKSPACE` is lifetime and shared across recipes, so spending an attempt here disarms `stale_review`, `crash_park` and `green_not_merging` on the same workspace. The recipe adds no ledger, reporting or issue-filing behaviour: a `not_yet` from it makes the sweep record one `wait` row under the first matched recipe's name (`declared_blocker`), and — like every recipe's waits — suppresses the decline report for the whole park until the wait resolves; a decline joins the shared `needs_human` report, which uses the fixed `needs_human` shape and title, so no new issue title is minted for a wait or a report.

Two accepted residuals. **Substring risk:** a short authoritative check name on another engine (an iOS-preset engine's, say) can occur inside prose that is not a claim about that check, and the recipe is live from day one because `unblock_enabled` defaults true. No minimum-name-length heuristic was added — it would be arbitrary — and the containment is the verification-never-merge route plus the per-head bound. **Truncation:** a marked bullet is cut at 300 characters (`_BULLET_MAX_CHARS` in `_declared_blocker.py`) and cannot contain a newline, so a blocker that named a check late in a long line can lose the name, and "names no check on this pull request" can mean "named one and the truncation ate it" — the outcome is a decline, never a wrong answer.

**The unknown-head marker (alan#1630).** Every fleet path that moves a pull-request branch and then fails to learn the resulting head — `merge_recovery._mark_system_head` (`BEHIND_PLUS_TRANSIENT`, `STALE_MEASURED_BASELINE`, `DIRTY`), `proactive_rebase._record_system_head` and `_pr_merge_post_update.record_merge_time_system_head_if_updated` — now writes `pr_<n>_system_head.json` with `head_sha` **absent** (`None`, stored as JSON `null`, never an empty string or a sentinel, so every existing comparison against a marker's head stays false without relying on a guard elsewhere) and a `written_at` epoch. It is written only where the branch update is already known to have succeeded; a conflict, a failed update or a raised one leaves the marker as it found it, and there is no clear or supersede primitive. `hand_resolved_declared_blocker` reads it: an unknown-head marker written at or after the park means the fleet moved the head, so the recipe declines. **Accepted residual:** a process dying between the push and the head read still leaves an unmarked head. The marker's contract lives in `merge_recovery.md`.

### Ledger and ceilings (`alan/unblock_ledger.py`)

`alan/unblock_ledger.py` is the ledger's whole surface and the read half of the watch blob: it defines `WatchEntry`, `REPROBE_CAP`, `UNBLOCK_WATCH_META_KEY` and `load_watch` (the blob itself lives in `queue_meta`, not in the table, and is written only by the sweep). The ledger itself is one INSERT-only table `unblock_ledger` in `queue.db`, created by `ensure_schema` through the new `Queue.run(sql, params)` accessor — the queue's own connection and lock, never a second connection (`Queue._conn` sets no `busy_timeout`). Columns: `ts`, `engine_key`, `workspace_key` (always `ws.task_id`, which survives the `ws:`→`pr:` scope flip), `scope_ref`, `shape`, `fingerprint`, `kind` (`attempt` | `wait` | `report` | `issue_intent` | `issue_delivered` | `issue_attempt`), `action`, `outcome`, `head_sha`, `handover_id` (the identity), `bar_lowering`, `cost_usd` (0 for every tier-1 row), `detail` (JSON), `ref_id`. Fingerprint: `incident_fingerprint(f"unblock:{recipe}", scope_ref, question id or blocker name)` for recipe attempts; the `needs_human` report uses the park key described under "Watch, backoff, act, observe" instead. `head_sha` is written on report, wait, attempt and issue-intent rows from the tick's readiness read (forensic; nothing reads it back).

Ceilings count `attempt` rows and increment on attempt, not success: `ATTEMPT_CEILING_PER_FINGERPRINT` 2, `ATTEMPT_CEILING_PER_WORKSPACE` 5, `BAR_LOWERING_CEILING` 2 (reserved for the waive/withdraw recipes; no tier-1 recipe sets `bar_lowering`). A ceiling hit is a terminal report. `last_record` composes the one-line summary the workspace API serves as `WorkspaceDetail.unblock` (`attempt 2 of 5 · stale_review · dispatch:pr_merge · acted · 2026-09-19T12:41Z`, `waiting · …`, `needs human · …`) plus the issue URL from the latest `issue_delivered` row; `counters_24h` feeds the health counters slice.

### Read model, rescue metrics and the log trail

The UI and any outside agent read the sweep's work through a pure read model layered on the same ledger, added without touching sweep behaviour, ceilings, backoff or reporting policy.

- **`UnblockRecord.action` / `.reason` / `.authority_holder`** are pure reads off the already-fetched `LedgerRow` (`row.action`, `row.detail.get("reason")`, `row.detail.get("authority_holder")`) — never parsed back out of `summary`, which stays a display string.
- **`UnblockRecord.watch_attempts` / `.watch_cap` / `.watch_next_at` / `.watch_exhausted`** carry the host's own watch state for a parked workspace it is still working, so a driver or a human reading the API can tell a park the host is re-probing from one it has abandoned. Before them the record changed only when a ledger row was written, and a declining re-probe writes none: a park re-probed six times looked byte-identical to a dropped one (2026-09-19, alan#1626). All four are `X | None = None` — nullable **and** defaulted, so they are optional properties in the generated client types and no fixture changes — and are all absent when there is no watch for the park. Each means exactly one thing:
  - `watch_attempts` is the watch entry's whole `attempts` count, the very number the host compares against the cap — not "re-probes since the report". It is unrelated to the record's existing `attempts` / `ceiling` pair, which count `attempt` ledger rows against `ATTEMPT_CEILING_PER_WORKSPACE`.
  - `watch_cap` is `REPROBE_CAP` (72), the figure `watch_attempts` is measured against.
  - `watch_next_at` is the earliest moment (wall-clock epoch seconds) the host will look at this park again. A time in the **past** means the park is due and waiting for a sweep tick — a RUNNING job on the workspace, more than `MAX_FORGE_CANDIDATES_PER_TICK` candidates due at once, `ALAN_UNBLOCK_DISABLE`, or a paused queue each hold the sweep off — and never means abandoned. The host never freezes this time: even an exhausted entry is re-armed by `_read_and_settle` on every due tick.
  - `watch_exhausted` mirrors the host's own predicate, `WatchEntry.exhausted` = `terminal AND attempts >= REPROBE_CAP` — the park has been reported and its re-probe budget is spent. A still-waiting park (not `terminal`) past 72 attempts is correctly **not** exhausted: the cap binds a reported park only, so `watch_cap` beside a waiting park's `watch_attempts` is not a binding budget. An exhausted park is still probed every `REPROBE_INTERVAL_S` and re-arms at `attempts = 0` when the head moves, so `true` means "budget spent", not "given up". `outcome` already separates a report row (`needs_human`) from a wait row (`not_yet`), which is why no fifth field exists.
  - **How to read it.** The record's `at` is the timestamp of the latest ledger row and stays at the report. An unchanged `at` beside an advancing `watch_attempts` means **still watching**: the host is re-probing and declining, writing no row. Because `watch_next_at` is never frozen, the **absence** of these fields is the only signal the host has stopped watching — the entry is pruned when the workspace leaves `STUCK_WS_STATUSES` or `candidate_for` exempts it, and the fields go with it.
  - **Same-park guard.** The watch is attached only when the row's `handover_id` equals the entry's `identity` (`handover_id@updated_at`, the composite every sweep-written row stores); otherwise the fields are absent and the record is exactly the pre-watch record. This keeps the two halves consistent with *each other*, not current: after a re-park the ledger row and the watch entry both describe the previous park until the next sweep tick rewrites them, as `at` always has. Because the identity embeds `updated_at`, a workspace whose `updated_at` churns can serve the fields absent while it is genuinely watched. The fields ride on an existing record, so a watched park with no ledger row at all serves no record.
  - **Accepted UI inconsistency.** The UI's ninety-minute silence rule (`alan/web/src/lib/unblockView.ts`, below) keys on `at` alone and is unchanged: a park at probe 7 of 72 still renders silent and human-owned. That is knowingly accepted, not overlooked; a later change can show "probe n of 72".
- **`records_for(queue, workspace_keys)`** batches the per-workspace record `last_record` computes one workspace at a time: it costs three SQL queries (latest row per key via `GROUP BY workspace_key` + `MAX(id)`, attempt counts per key, latest delivered-issue URL per key) plus one `queue_meta` read of the watch blob (`load_watch`, once above the per-row composition, so never once per workspace) regardless of how many keys are requested — a single `IN (...)` clause per query, not one query per key. The meta read goes through `Queue.get_meta`, not `Queue.run`, so it is pinned by its own counting test in `tests/test_unblock_ledger_watch.py`.
- **`alan.incident.stuck_workspace_keys(pairs)`** is the single authority for "the host may still be working this workspace" — a pure filter of `(workspace_key, Status)` pairs down to `STUCK_WS_STATUSES`. It gates every place the read model is attached: the workspace list (`WorkspaceSummary.unblock`, routes/workspaces.py), the workspace detail (`WorkspaceDetail.unblock`), and the population used by both rescue-metric routes below. No call site re-derives the stuck check by hand.
- **`rescue_window_start(now, window_days=RESCUE_WINDOW_DAYS)`** (`RESCUE_WINDOW_DAYS = 30`) is the one shared cutoff both rescue rates use — `now - window_days * DAY_S`, so with the default it is the 30-day cutoff every existing caller gets; the default is pinned by test against the 30-day window `outcome_rate_30d` already uses (`health_repo_metrics._WINDOW_DAYS`), so the two windows cannot silently drift apart.
- **`rescue_stats(queue, workspace_keys, stuck_keys, now, window_days=RESCUE_WINDOW_DAYS)`** returns `RescueStats(success_rate, success_sample, success_low_data, load_rate, load_sample, load_low_data)` over the given population:
  - a workspace the ledger touched (`attempt`/`wait`/`report` row) within the window that is **no longer stuck** counts as a clearance;
  - a workspace the ledger touched, still stuck, **and reported** (`KIND_REPORT` — the host gave up) counts in the denominator as a non-clearance;
  - a workspace the ledger touched, still stuck, and **not yet reported** (the host may still be working it) is excluded from both the numerator and the denominator — it is neither a success nor a failure yet;
  - `load_rate` is engaged-workspace count over the whole given population (whether or not the ledger ever touched them);
  - both rates report `low_data` (sample below `RESCUE_LOW_DATA_MIN_SAMPLE = 10`) **alongside** the computed value rather than suppressing it — a thin-sample rate is still returned, just flagged;
  - `window_days` windows **engagement only**, by the ledger row's own `ts` (`ts >= now - window_days * DAY_S`, a row exactly on the cutoff is in). Both row sets — the workspaces the ledger touched and the subset that carries a `report` row — are cut by that same cutoff, so a report older than the window does not turn a still-stuck workspace into a non-clearance for that window. Nothing else is windowed: the population (`workspace_keys`), the stuck set (`stuck_keys`, the workspaces' *current* status) and therefore `load_sample` are identical for every `window_days`. A 7-day and a 30-day call over one population thus differ only in which workspaces count as engaged; the default keeps every existing caller on the 30-day figure, and no caller other than the two routes above exists yet.
- **Routes**: `alan/routes/workspaces.py` attaches `WorkspaceSummary.unblock` for stuck rows only, fetched once per list via `records_for` (not per row); `alan/routes/health.py`'s `/api/health/repos` row exposes `rescue_success_rate` / `rescue_load_rate` in the existing nested `{value, sample, low_data}` shape, one `rescue_stats` call per repo slug (population = that repo's workspaces); `alan/routes/infra.py`'s fleet `quality_metrics` exposes the same two rates as six flat keys (`rescue_success_rate(_sample|_low_data)`, `rescue_load_rate(_sample|_low_data)`, mirroring the existing `format_error_rate`/`recovery_rate` flat shape), one `rescue_stats` call over the whole fleet. Neither route adds a new endpoint or a new read path over the attempt ledger.
- **Log trail** (`alan/unblock_sweep.py`, `logger = logging.getLogger("alan.unblock")`): a healthy sweep now writes one `logger.info` for each act (`_ledger_attempt`, one line per `attempt` ledger row — acted, forge-write-failed or raised), one for the first wait of a park (`_wait`, only when `entry is None`, matching the single `wait` ledger row already written on first sight), and one for each report (`_report`, only on the branch that writes a new `report` row — a terminal entry's re-probe extension logs nothing extra). A repeated wait tick or a terminal reprobe that still declines therefore leaves no new log line, matching the existing one-row-per-event ledger discipline. The log lines are the only behavioural addition to `unblock_sweep.py`, and the later move of the watch blob's read half out of it into the ledger changes nothing it does: no new recipe, no change to what it acts on, and no change to ceilings, backoff or reporting policy.
- **Display-layer silence threshold**: the frontend subtask treats a workspace as needing human attention if the host has held it without acting or reporting for longer than 90 minutes (4.5× `MAX_INTERVAL_S` = 4.5 × 1200s), even with no `report` row — an unbounded wait is currently a silent failure mode. That threshold lives in the UI, not here, and keys on the record's `at` alone (a live park at probe 7 of 72 can render as silent — see the `watch_*` bullet above); whether the sweep itself should eventually report after some number of consecutive waits is an open policy question, tracked as alan#1634 rather than fixed in this change.

### Activity view (`alan/unblock_activity.py`, `GET /api/health/unblocker-activity`)

The read model behind the Health page's "Unblocker activity" panel: what the sweep did in the last 30 days, readable after the fact. Nothing on this surface may trigger, retry, dispatch, suppress or otherwise change fleet state, and it changes nothing about the sweep's recipes, ceilings, backoff or reporting policy — it only observes the ledger the sweep already writes. The route is GET-only (a test pins that no other verb is registered on the path).

- **Window.** `unblock_ledger.rescue_window_start(now)` and `RESCUE_WINDOW_DAYS` are reused; `30` is never re-declared, so the view and the `rescue_success_rate`/`rescue_load_rate` tiles cannot tell contradictory stories. A row exactly at the cutoff is in the window. Older rows are not shown but are not deleted.
- **Two payloads, one discriminator.** `scope: "fleet"` carries aggregates only (per park `shape`: total, distinct workspaces, workspaces by clearance, workspaces retried, and **separate** attempt-outcome and report-outcome tallies that are never summed into one bar), plus `events_total`, `workspaces_touched`, `waited_workspaces`, `diagnosed_workspaces`/`diagnosable_workspaces`, `ever_recorded` and `unattributed_events`. `scope: "repo"` (`?engine=<slug>`) adds `events[]` — newest first, capped at `EVENT_LIMIT` = 50, `events_total` reporting the uncapped count so the UI can say "showing latest 50 of N" — and computes every figure over that repository's rows only. They are two Pydantic models, so repo-specific fields (`events`, `workspace_key`, `issue_url`) are structurally absent from the fleet payload rather than relying on the server to null them. The fleet view excludes hidden engines; the repo view serves any slug the caller names, and a slug that resolves to nothing is a well-formed empty payload, never a 404.
- **Two deduplicated summary counts, on both payloads.** `still_stuck_workspaces` (distinct workspaces whose current clearance is `still_stuck`) and `gave_up_workspaces` (distinct workspaces with a `report` row in the window — the host gave up) join `events_total` and `workspaces_touched` in the summary. Each counts a workspace once however many events or park kinds it spans, so they are not the sum of the per-`shape` `still_stuck_workspaces`, which counts a workspace once per kind it touched. Both are computed over the same uncapped, visibility-filtered events as `workspaces_touched`, so they can never exceed it, and they redefine no existing figure. They exist so a compact summary (the repository status strip) can read them from the same cached payload, with no summary-only query mode.
- **Per-workspace aggregate (`scope: "repo"` only).** `workspaces[]` holds one row per touched workspace — computed over the full 30-day window *before* the `EVENT_LIMIT` cap and never capped itself, so `len(workspaces) == workspaces_touched` by construction (both derive from one event tuple). Rows are newest-activity-first (`ts DESC, id DESC`, the ledger's own order); banding stuck/given-up rows above the rest is display-layer. Each row carries `workspace_key` (the link target), `last_at`, `shape` (the park kind of its latest event), `events_total`, `events_listed`, `attempts_total`, `attempts_ceiling`, `clearance`, `gave_up`, `issue_url` and `diagnosis`. `events_listed` is how many of that workspace's events survived the cap into `events[]`; where it is below `events_total` the child events are partial and the UI states "k of n events" rather than presenting the listed events as complete. `attempts_total` is the lifetime attempt count (the same figure `report` events carry), never clamped, served next to `attempts_ceiling` (`ATTEMPT_CEILING_PER_WORKSPACE`) so "6 of 5" reads as it is. `gave_up` is a `report` row anywhere in the window, not only as the latest event; `issue_url` is looked up for every row, not only for listed events, in batches of `ISSUE_URL_LOOKUP_CHUNK` (500) workspace keys unioned into one map so an uncapped window can never exceed SQLite's bound-variable limit; `diagnosis` is the workspace's latest RCA draft.
- **Fleet payload never carries `workspaces`.** The invariant is structural (two Pydantic models and two dataclasses: `FleetActivity`/`ActivitySummary` have no such field) and pinned by tests on the read model and the route: the fleet payload gains the two counts and nothing per-workspace. Both payloads are still served by the one `GET /api/health/unblocker-activity` through the one 30 s `_ACTIVITY_CACHE`, keyed `(queue, workspaces_root, slug)` — no new endpoint, no summary-only mode, no new cache key.
- **Lifetime attempt indices, displayed in-window.** `ATTEMPT_CEILING_PER_FINGERPRINT` and `ATTEMPT_CEILING_PER_WORKSPACE` are enforced by unwindowed SQL, so the "attempt N of M" shown per event is a lifetime `ROW_NUMBER()` over *all* `attempt` rows (ordered `ts, id`, partitioned by `(workspace_key, fingerprint)` and by `workspace_key`) and only the *display* is filtered to the window. Worked example: a workspace with two attempts 40 days ago and a third yesterday shows the third as "attempt 3 of 2" — a window-local index would print "1 of 2" for a park the host is about to abandon (and an over-ceiling "3 of 2" is shown as-is, not clamped). `report` rows get no attempt index; they carry `attempts_total`, the workspace's lifetime attempt count.
- **Clearance is three-valued and is current workspace state, not proof of a rescue.** Each event separately carries `cleared` (the workspace is present and not in `stuck_workspace_keys`), `still_stuck`, or `unknown` (the workspace is absent from `list_workspaces`, shown as "workspace gone"). "Cleared" means *this workspace is not currently stuck*, which a human merge, an archive or a manual answer also produces — an action taken is deliberately never presented as a problem solved, and a gone workspace is never counted as a success.
- **`wait` rows are not events.** They are excluded from events and aggregates and surfaced as one integer, `waited_workspaces`: distinct workspaces with a `wait` row in the window and no `attempt`/`report` row in it.
- **Repo attribution** uses the row's own stored `engine_key` (`unblock_sweep._record` writes it on every row), falling back to the live workspace's, else the row is `unattributed` (counted in the fleet payload's `unattributed_events`, never shown in any repo view). A `list_workspaces`-only join would silently drop exactly the cleared-and-cleaned-up successes this view exists to show.
- **Diagnosis** is attached per workspace from the investigator's RCA drafts (`RcaDraft.workspace_key`, see [investigator.md](investigator.md)); most workspaces have none and the UI then shows nothing. The coverage figure counts distinct workspaces in the listed population. The join is display-only: no recovery path reads it.
- **Ledger seams.** `unblock_ledger` gained public `activity_rows_since`, `issue_urls_for` (the former `_batch_issue_urls`) and `stamp` so this module never imports a `_`-prefixed name; the issue link on an event is the stored `issue_url` of the workspace's latest `issue_delivered` row, never constructed.

Import-linter placement: `unblock_activity` sits between `investigator` and `rca_store` — above `rca_store`, `unblock_ledger`, `incident`, `workspace` and `engine_config`, below `routes`. Tests: `tests/test_unblock_activity.py`, `tests/test_unblock_activity_workspaces.py`, `tests/test_routes_health_unblocker_activity.py`, `tests/test_routes_health_unblocker_workspaces.py`; the typed payload contract is `UnblockActivityResponse` in `alan/web/src/api.ts` (`api.unblockerActivity.test.ts`).

### Issue filing (`alan/teams/unblock_issue.py`)

One open issue per (engine slug, shape), label `unblocker`, title `Unblocker: <shape title> (<slug>)`; every case is a comment (workspace, PR, park, what was probed, what was done, outcome). Filing is durable intent: the sweep writes an `issue_intent` row (title, shape body, comment) in the same code path as the attempt or report row, and `drain_issue_intents` delivers up to `ISSUE_DRAIN_PER_TICK` (5) undelivered intents per tick, recording `issue_delivered` (with the URL) or `issue_attempt`; an intent is abandoned after `ISSUE_INTENT_MAX_ATTEMPTS` (20). Dedup is by exact title through the forge port's `open_issues_by_title` (`gh issue list --label unblocker --state open --search "in:title …"`), so a closed issue (the defect was fixed) reopens fresh on the next occurrence; a lookup that fails (non-zero exit, timeout, missing `gh`) is an `IssueLookup(ok=False)` that never falls through to `create`, so a forge outage cannot mint duplicates — the intent simply retries next tick. Each intent persists the workspace's resolved `ForgeTarget` (`owner`, `repo`, `credential_env_name`) so a later registry change cannot redirect the retry to another repository. The comment goes through REST (`gh api --method POST repos/<slug>/issues/<n>/comments --input`, the port's `comment_on_issue`), because `gh issue comment` fails under the GraphQL secondary limit while REST keeps working. Token: the engine's transport secret (`secrets_store.resolve_secret(slug, TRANSPORT_PURPOSE, env_fallback=credential_env_name)`), ambient `gh` when absent; the adapter resolves it, not this module. Every call goes through `active_forge()` (`open_issues_by_title`, `create_label`, `create_numbered_issue`, `comment_on_issue` — `forge_port.md`, "X2.7 PR13"), so the seam the tests fake is the port (the fake forge, or the adapter's process runner underneath it); `gh_guard` refuses the real writes.

### Guardrails and visibility

- `ALAN_UNBLOCK_DISABLE` (`1`/`true`/`yes`/`on`) disables the sweep fleet-wide; classified excepted-config in `tests/env_var_classification.py`. It is pinned to `1` in `tests/conftest.py` and in the e2e `serverEnv` (`alan/web/e2e/fixtures/server-env.ts`), exactly like `ALAN_DISABLE_DISPATCHER`: a test that boots the real dispatcher must never let the sweep reach the forge (`tests/gh_guard.py` refuses the write with a `BaseException` that would kill the loop thread), and an e2e server must never re-dispatch a spec's parked fixture; the sweep suites opt back in with `monkeypatch.delenv`.
- `EngineConfig.unblock_enabled: bool = True`, carried through `apply_stored_projection` like `dependency_sweep.enabled`; read through `_pr_forge.governing_config_for_ws` (snapshot-first, so a workspace stamped before the field existed sees the default).
- `WorkspaceDetail.unblock` (`alan/routes/_workspace_detail.py`, filled by `unblock_ledger.last_record` in `get_workspace`) is the per-workspace record the drivers and the owner read; the interactive driver loops treat any stuck row as the host's and only escalate to the owner (through the drivers' owner-escalation tag) when `unblock.outcome` is `needs_human`; a `needs_human` record that carries the `watch_*` fields is still being re-probed by the host, so an unchanged `at` on it is not evidence the host has stopped.

### Import-linter placement

`unblock_sweep` and `unblock_recipes` sit where `_dispatcher_merge_park_sweep` sat — after `_dispatcher_brief_refine`, before `project_auto_continue` — below `_dispatcher_loop` (which calls the sweep) and above `repo_status`, `dispatch`, `merge_gate`, `proposal_items`, `teams`, `handover`, `workspace`. `unblock_ledger` sits between `rca_store` and `incident` as a structural sibling store that imports only `queue`, so the routes layer can read it for the workspace detail. `alan/teams/unblock_issue.py` is a public module inside `teams`; it takes plain arguments and never imports the ledger.

## Tier 2: planner and bounded executor (planned)

The design below was written for PR #1601 against ten owner rulings (2026-09-19) and stands, with one correction: its trigger was the six investigator incident classes at the terminal-transition seam, which `_is_exempt` never reaches for a question park.
