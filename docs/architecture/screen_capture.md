# Rendered-screen capture (advisory, non-blocking)

**Source:** `alan/web/playwright.capture.config.ts`, `alan/web/src/capture-config.ts`, `alan/web/e2e/capture/capture.spec.ts`, `alan/web/src/capture-config.advisory.test.ts`, `alan/web/src/capture-config.identity.test.ts`.

`npm run capture:screens` (root `alan/web/package.json`) boots the built app via the shared `makeWebServer` factory (`alan/web/playwright.config.ts`) — the same real-backend-plus-stub-`claude` boot `playwright.mobile.config.ts` uses — and captures a full-page PNG of every named route (`/`, `/build`, `/explore/architecture`, `/health`, `/projects`, plus the parameterized project-detail screen) at a desktop viewport (1280×800) and a mobile viewport (`devices["Pixel 5"]`), via two Playwright projects (`desktop`, `mobile`) so each named screen's test in `e2e/capture/capture.spec.ts` runs once per project. PNGs write to `alan/web/screen-captures/pid-<pid>/<route>.<project>.png` (gitignored) — pid-namespaced per invocation; see "Shared-checkout concurrency" below. `precapture:screens` now runs only `npx playwright install chromium`, which is itself idempotent (skips an already-cached browser) — the build step that used to live here moved into `playwright.capture.config.ts`'s `webServer.command` (see below), since it now needs to target a per-run output directory rather than the fixed `alan/web/dist`. `precapture:screens` deliberately does NOT run `npm ci`: reinstalling `node_modules` on every best-effort capture invocation is a large, destructive side effect (and a source of network-fetch flakiness) that this advisory tool doesn't need — it relies on whatever `node_modules` the calling flow already installed.

## Shared-checkout concurrency

Alan's fleet workers run planning teams **in the shared production checkout**, not per-worker worktrees — several workers can invoke `capture:screens` from the very same checkout at the same time. That mode needs every per-run output isolated, not just the port and backend state root:

- **Port + backend state root** (pre-existing): `resolveCapturePort`/`resolveCaptureRoot`, now in `alan/web/src/capture-config.ts`, derive `ALAN_CAPTURE_PORT` (`4700 + pid % 1000`) and `ALAN_CAPTURE_ROOT` (`os.tmpdir()/alan-screen-capture/pid-<pid>`) from `process.pid`, caching the resolved value into `process.env` so the worker process(es) Playwright forks to run the `desktop`/`mobile` projects reuse the value the root process actually bound to (Playwright reloads `playwright.capture.config.ts` per project, and a worker's pid differs from the root runner's). The caching primitive itself (`resolveCached`/`resolveCachedPort`) now lives in `alan/web/src/lib/derived-run-config.ts`, shared with `alan/web/src/mobile-audit-config.ts` — see the mobile-audit note below.
- **Built UI artifact** (the first shared-collision point): `deriveBuildDir(pid)` (`capture-config.ts`) derives `os.tmpdir()/alan-screen-capture-build/pid-<pid>`, cached the same way into `ALAN_WEB_DIST_DIR` by `resolveBuildDir()`. `playwright.capture.config.ts`'s `webServer.command` chains `npx vite build --outDir <BUILD_DIR> --emptyOutDir` ahead of the backend boot with `&&` — not a Playwright `globalSetup`, so build-then-serve ordering is deterministic regardless of `globalSetup`/`webServer` timing — and sets `ALAN_WEB_DIST_DIR=<BUILD_DIR>` in that backend process's own environment. `alan/server.py`'s `_dist_dir()` helper reads `ALAN_WEB_DIST_DIR` (stripped; blank or unset falls back to the production default `alan/web/dist`) at the single import-time UI mount call, so the capture-booted backend serves its own isolated build. `alan/web/dist` — the artifact the live `ai.alan` launchd service mounts and serves — is never written by capture, at any concurrency level.
- **Screenshot output directory** (a second, independent shared-collision point discovered during implementation): `deriveScreensDir(pid)` (`capture-config.ts`) derives `alan/web/screen-captures/pid-<pid>`, cached into `ALAN_CAPTURE_SCREENS_DIR` by `resolveScreensDir()`. `capture.spec.ts` reads its `outputDir` from that variable, falling back to the flat `screen-captures/` directory only when it's unset (e.g. a direct `playwright test --config=playwright.capture.config.ts` invocation outside `npm run capture:screens`). Two concurrent runs therefore never share a directory, so neither can read or overwrite the other's PNGs, even mid-write.
- **Why the derive/resolve functions live in `src/capture-config.ts` rather than the config file itself:** `alan/web/src/capture-config.identity.test.ts` unit-tests them directly (per-pid distinctness, caching behavior, coverage-gated like the rest of `src/`). Importing `playwright.capture.config.ts` itself from a `src/` test would pull `@playwright/test` and `e2e/fixtures/server-env.ts` into `depcruise`'s `src`-rooted dependency graph and trip its "production code must not import test utilities" rule — `capture-config.ts` has zero Playwright/e2e dependencies (`node:os`/`node:path`/`node:url` only), so it stays outside that rule's reach while remaining the single source both the config and the test import.
- **The typecheck step is dropped from the capture build.** `precapture:screens` used to run `npm run build` (`tsc -b && vite build`), and `tsc -b` writes the single shared `alan/web/tsconfig.tsbuildinfo` incremental file — two concurrent `tsc -b` invocations would race that file. The capture build now runs `vite build` only: it needs the emitted bundle, not a type-check verdict, and standard CI (`npm run typecheck`) already gates types on every PR regardless. This removes the race outright rather than isolating the incremental file — there is no shared build state left for capture to race. A torn build from any other, still-unforeseen isolation gap just fails the capture Playwright run, which is the advisory-unavailable path below, not a gate.

`ALAN_WEB_DIST_DIR` is declared as an empty string in every other boot surface — `alan/web/e2e/fixtures/server-env.ts`'s `serverEnv()` (consumed by `playwright.config.ts`'s `makeWebServer`, so it covers the main e2e suite and `playwright.mobile.config.ts` too) and `deploy/ai.alan.plist` (production) — so an unset-or-blank override is indistinguishable from no override (`_dist_dir()` treats both the same) and only `playwright.capture.config.ts`'s `webServer.env` ever sets a real value. This mirrors the `ALAN_SLOT_UV_CACHE`/`ALAN_SLOT_NPM_CACHE` empty-string plist precedent (`CLAUDE.md`'s "a new `ALAN_*` env var must be threaded into every state-isolation surface" rule) rather than leaving the var undeclared in those other surfaces.

`alan/web/scripts/verify-capture-concurrency.mjs` (`npm run verify:capture-concurrency`) is the scripted proof: it hashes every file under `alan/web/dist`, runs two `npm run capture:screens` invocations concurrently with no manual env (so pid-derivation alone has to keep them apart), re-hashes `alan/web/dist` and asserts it is byte-for-byte unchanged, and asserts the two runs produced two distinct `screen-captures/pid-*/` directories each holding the full screenshot set. It lives under `scripts/`, not `e2e/capture/`, so it stays outside `capture-config.advisory.test.ts`'s scan (see below) — it's a concurrency test harness, not part of the capture flow itself, and it is not wired into any CI gate (it boots two real backends behind two real builds, on the order of minutes).

**Partially made concurrency-safe as of the mobile-audit port/root isolation change:** the blocking `mobile-audit` routine (`playwright.mobile.config.ts`) now derives its port (`5700 + pid % 1000`) and state root (`os.tmpdir()/alan-mobile-audit/pid-<pid>`) the same pid-cached way capture does (`resolveMobileAuditPort`/`resolveMobileAuditRoot`, `alan/web/src/mobile-audit-config.ts`, sharing the `resolveCached`/`resolveCachedPort` primitives with `capture-config.ts` via `alan/web/src/lib/derived-run-config.ts`), replacing the fixed port (`4174`) and homedir-rooted state root (`~/.alan-mobile-audit`) this section used to describe — two `audit:mobile` invocations from the same checkout no longer bind-conflict or `rm -rf` each other's live state root mid-run. This deliberately keeps capture's `pid % 1000` collision residual (two pids differing by an exact multiple of 1000 derive the same port) rather than fixing it here — the risk is unchanged from the pre-existing capture precedent, not newly introduced by this change, and a bind-and-report scheme was rejected as unnecessary complexity for a low-probability collision (see `docs/architecture/e2e_testing.md`'s equivalent note). This is a partial reversal of the deferral this section originally recorded, not a full one: `preaudit:mobile`'s `npm run build` step still writes the fixed `alan/web/dist` — the same shared-build-artifact hazard capture solved via `ALAN_WEB_DIST_DIR` — and stays out of scope, tracked as a follow-up alongside e2e's equivalent `pree2e` build step. `alan/web/mobile-audit-results/` also remains a fixed, unnamespaced path, so two concurrent runs can now boot without colliding but still overwrite each other's result files. This is exactly why `ui_review`'s prohibition on workers invoking the live `audit:mobile` runner (`alan/teams/ui_review.py`, `docs/architecture/ui_review.md`) is unchanged: relaxing it needs the build-artifact fix and `mobile-audit-results/` namespacing too, not just this port/root change. `makeWebServer` (`playwright.config.ts`), the shared boot helper both configs use, is unchanged by this.

This is a pure capture tool — no baseline comparison, no pixel-diff gating against a reference image. `capture.spec.ts` can still fail like any Playwright test (e.g. a navigation, screenshot, or build error), so `npm run capture:screens`'s exit code is not unconditionally zero — the property that makes this advisory is the absence of a baseline to compare against, not immunity from command failure. `capture-config.advisory.test.ts` is a drift guard (same `fs.readFileSync`-based mechanism as `src/design-system.drift.test.ts`) asserting `playwright.capture.config.ts` and `capture.spec.ts` never grow `compareToBaseline`, a `baseline.json` reference, or a `.toBe(true)` gate; it reads exactly those two files and does not scan `capture-config.ts`, `verify-capture-concurrency.mjs`, or `capture-config.identity.test.ts` — none of which carries baseline/gating logic itself. The blocking `mobile-audit` spec/baseline is a separate, deliberately untouched surface (see `docs/architecture/e2e_testing.md`).

## Wired into the worker + verifier loops (advisory, best-effort)

- `implementation` and `implementation_fix` (`alan/teams/implementation.py`, `alan/teams/implementation_fix.py`): the static `_SYSTEM_PROMPT` instructs the worker, when its diff touches `alan/web/`, to best-effort run `npm --prefix alan/web run capture:screens` and Read the resulting PNGs under `alan/web/screen-captures/` before finalizing — a rendered look at its own screens catches issues markup review misses. `implementation_fix` additionally points at `alan/web/test-results/**` (Playwright's own failure-screenshot output) when a local `npm --prefix alan/web run e2e` run failed — a cheap win with zero new tooling. The CI-artifact `gh run download` path for failure screenshots is explicitly deferred to the roadmap's P1.1 flake-lane work, not built here.
- `verification` (`alan/teams/verification.py`): the `diff_reviewer` role's prompt instructs the same best-effort capture + Read, run **inside the verifier's own grounded PR checkout** (the `_grounded_cwd_var` cwd it already uses for scenario execution — see `docs/architecture/implementation_pipeline.md`) — there is no worker→verifier PNG handoff and no PNG is ever committed into the PR or fetched from CI artifacts. The diff_reviewer reports what it saw under a fixed `## Rendered-screen observation` heading.
- `brainstorming`, `implementation_plan`, and `architecture` (`alan/teams/brainstorming.py`'s worker template, `alan/teams/implementation_plan.py`'s `_FRONTEND_ANALYST_PROMPT`, `alan/teams/architecture.py`'s `_JUDGE_PROMPT`): the shared `PLANNING_SCREEN_CAPTURE_INSTRUCTION` (`alan/teams/_base.py`) instructs each planner, when the task concerns `alan/web/`, to best-effort run `npm --prefix alan/web run capture:screens` and Read the PNGs under its own run's `alan/web/screen-captures/pid-<pid>/` directory — identified by diffing the `pid-*` directory listing before and after the capture command, since several planners can be capturing from the same shared checkout at once and a pre-existing pid directory may belong to, and still be written by, another run. This is planning-time, not diff-time — there is no diff yet, so the observation grounds the proposal in the app's current layout, density, and affordances rather than reviewing a change against it. The observation stays free prose, kept out of `decisions.yaml`, `files_to_edit`, and `test_scenarios`; a missing or failed capture never affects the plan's content.

## Advisory framing is load-bearing, not incidental

Capture is best-effort and time-boxed by design: the verifier's grounded checkout has source, not a build, so capture there requires `npm run build` + a backend boot + chromium inside the verifier's already-timeboxed run, and (absent the production slot pool) there is no warm `node_modules`. On failure or timeout the diff_reviewer writes exactly `capture unavailable — reviewed from markup` under the `## Rendered-screen observation` heading and continues reviewing from the diff alone — a missing or failed capture is never a reason to add a finding, raise severity, or otherwise affect `DIFF_FINDINGS_CRITICAL`/`VERDICT`. Capture stays out of the judge's machine-readable fields entirely (`_JUDGE_PROMPT` is unchanged) so a capture failure can never move the verdict. The acceptance test for the "attach an observation" clause is deliberately structural — it proves the capture script produces PNGs (`capture.spec.ts`) and that the prompt instructs best-effort capture plus the degrade path (`test_diff_reviewer_prompt_has_screen_capture_bullet` / `test_diff_reviewer_prompt_frames_capture_as_best_effort`) — never that a live verifier run always emits a screenshot, which would silently convert an advisory feature into a gate.

## No allowlist delta

`BASE_ALLOWED_TOOLS` (`alan/teams/_base.py`, sourced from `EngineConfig.base_tools`) already carries `Read`, `Bash(npm run:*)`, and `Bash(npx:*)` for every team, including `implementation`, `implementation_fix`, and `verification`. Running `npm --prefix alan/web run capture:screens` (or the underlying `npx playwright install chromium` / `npx vite build`) and `Read`-ing the resulting PNGs needs nothing beyond what every team already has — this document is the confirmation that closes the roadmap's "allowlist wiring in `teams/_base.py`" item without a code change.

## Capture is not web-only: the `ios` preset's native path

The framing above (and the allowlist paragraph just before this one) is true for the web-based path and incomplete: it describes the only capture mechanism that existed when it was written, not the only one that exists now. On the `ios` engine preset a second, **prompt-only** native path exists via `alan/teams/_native_capture.py` — no Python code runs a build or a capture on alan's side; the module only renders instruction text (`native_capture_block(cfg, team)`) that reaches `implementation`/`implementation_fix` workers through their system prompt, telling them to run `xcrun simctl` themselves inside their own grounded checkout. It needs `Bash(xcrun:*)`, already granted to every team via the iOS-preset engine's own `config/engines.d/<repo>.yaml`'s `base_tools` — no allowlist change, mirroring this document's own no-allowlist-delta finding above for the web path. The `ui_review` capability on this engine receives a structural-absence statement instead of a recipe, for the same "no working directory, no checkout" reason `verification`'s capture is scoped to its own grounded cwd above. The full recipe text, including its isolation and freshness-refusal steps, lives in `alan/teams/_native_capture.py`.

## Scope

`remediation`, `deploy_verify`, and `pr_merge` are deliberately **not** wired to capture — none of them iterate on a UI diff the way `implementation`/`implementation_fix`/`verification` do, so adding capture there would be speculative scope, not a concrete gap. `slot_pool.py` is unchanged: chromium provisioning relies on the shared, already-warm `~/.cache/ms-playwright` rather than adding a slot-pool-specific step. `alan/web/e2e/mobile-audit/**` (spec + `baseline.json`) is untouched; extending it to desktop viewports would smuggle a desktop merge-gate into what the roadmap scoped as advisory-only.
