# Handover artifacts

**Source:** `alan/handover.py`, `alan/compression.py`

Typed YAML artifacts that carry per-team output between dispatched jobs. Persisted under `~/.alan/workspaces/<task_id>/handovers/handover_<task>_<NNN>.yaml`.

## Save semantics

- Slot `<NNN>` is claimed via atomic `O_EXCL` (same pattern as `create_invocation_dir`).
- Write is atomic: `.tmp` file + `os.replace`.
- Append-only — handovers are never overwritten in place. Revisits get new slots.
- One triage-scoped exception: `prune_handover_files(ws)` deletes every handover file for the workspace's own task. It is called only from `prune_triage_invocations` (see `docs/architecture/triage.md` — the immortal sweep workspace exhausted `_MAX_SEQ = 999` on 2026-07-05; triage handovers are pure exhaust). Keep-zero is deliberate: `_claim_handover_slot` reuses the lowest free seq while `latest_handover` picks the lexicographically last filename, so retaining any old high-seq file would make `latest_handover` stale after the next low-seq save.

## Pydantic models

- `Handover` — top-level artifact.
- `Decision` — one entry; carries `reversibility` (informs router/loop_guard heuristics later).
- `OpenQuestion` — `id`, `blocking: bool`, `resolver_role`, `prior_attempts: list[str]`.
- `ArtifactRef` — typed pointer to off-handover output (commit SHA, file path, PR URL, …).

## Schema versions

`SCHEMA_VERSION` is the current version on save. The supported versions are declared once, as the `_SchemaVersion` `Literal` in `alan/handover.py`; load-side, `_SUPPORTED_SCHEMA_VERSIONS` is derived from it with `get_args`, so adding a version means adding one `Literal` member. The set stays closed — an unknown version is rejected, never accepted by a minimum-version comparison — and it accepts any listed version and defaults missing fields.

### Structured options on `OpenQuestion`

`OpenQuestion.proposed_answer_space: list[str]` existed since the model's introduction but sat unpopulated at every deterministic Python writer site until schema 1.17 (measured 2026-07-20: 527 handover files, 18 carried the key, 0 populated — `scripts/open_question_options_report.py` reproduces this measurement). Four sites now populate it, each constructing 2–4 options from state it already holds:

- `alan/teams/pr_merge.py:_merge_block_options` — blocking merge escalations (`no_pr`, `failed`, `timeout`, `unresolved`, `copilot_unresolved`). The `copilot_unresolved` cap-reached case reuses `_COPILOT_CAP_RECOVERY_RECIPE` verbatim as the recommended option (delete `.alan/copilot_escalation_count`, re-dispatch `pr_merge`) rather than a generic "resolve threads manually" narrative.
- `alan/teams/_verification_review_post.py:_JUDGE_PARSE_FAIL_OPTIONS` — the judge-parse-fail escalation (`id="verif-judge-parse"`).
- `alan/teams/_fix_escalation.py:non_actionable_question` — the non-actionable-feedback escalation (`id="non_actionable_feedback_*"`); its `GENERIC_OPTIONS` pair is the fallback, and when the prior verification handover carries a `GATE_ACTIONABLE: no` gate block the recommended option instead names the concrete external cause (failing checks, failing tests, flake-ratchet verdicts, merge state) and resolves to `pr_merge`.
- `alan/teams/_orchestrated.py:_completeness_options` — the low-completeness verifier gate (`id="low_completeness"`), built from `VerifierMetrics.gaps` (first two, `"Address gap: <gap>"`) plus two static fallback options (re-dispatch with expanded scope; accept at current completeness and forward anyway).

**`QuestionClass`** (`alan/handover.py`) is a closed four-value `Literal` — `merge_block_escalation`, `verification_escalation`, `fix_escalation`, `orchestrated_completeness` — one per writer site above, assigned at the writer and never inferred downstream. It is intentionally closed with no `"other"` escape hatch: a future fifth writer must extend the enum deliberately, since L0.4's UI labels and the future L3.1 graduation logic key off these exact string values.

**Recommendation encoding:** `OpenQuestion.recommended: str | None` is an explicit field carrying the verbatim recommended option string (not a positional `proposed_answer_space[0]` convention). Chosen because a positional convention renders indistinguishably to the sole reader (a human, or L0.4's UI) and a future reordering of `proposed_answer_space` would silently change which option is "recommended" — a field this fragile is worth spelling out explicitly. `OpenQuestion._validate_recommendation` (a `model_validator`) enforces only *consistency*, never presence: `recommended`, when set, must be a member of `proposed_answer_space`; `proposed_answer_space`, when non-empty, must have 2–4 entries. Neither field is required — this keeps every pre-1.17 handover (and every non-blocking or non-escalation `OpenQuestion`) loading unchanged.

The LLM-team question channel (an LLM emitting its own `proposed_answer_space` via a parsed block, analogous to `decisions.yaml`) is explicitly out of scope here — it lands separately as its own designed item.

### Structured answer persistence (L0.2)

`POST /api/workspaces/{workspace_id}/tasks/{task_id}/answer` (`alan/routes/answer.py`) resolves a blocking `OpenQuestion` by persisting the human's chosen option as structured data, never free text. Three functions in `alan/handover.py` carry the mechanics:

- `record_answer(ws, blocking_handover, question_id, answer, *, from_team) -> Handover` — appends a **new** `revisit_amend` handover whose `OpenQuestion` copy has `answer` set. `blocking_handover` itself is never rewritten in place: the append-only invariant (see "Save semantics" above) means every mutation is a new file, and an answer is no exception. This is why schema 1.14's `OpenQuestion.answer` field needed no schema bump to gain a writer — the field already existed on the model, the missing piece was purely a persistence *path*, not new shape. `revisit_of` on the new handover points at `blocking_handover.handover_id` (the immediate parent, same convention as every other `revisit_of` writer in the codebase), so multiple questions on the same blocking handover each get their own answer-carrying handover chained off whichever handover was current when it was answered — not necessarily off the original escalation directly.
- `find_recorded_answer(ws, handover_chain_id, question_id) -> str | None` — scans `list_handovers(ws)` for a `revisit_amend` handover whose `handover_chain_id` matches and whose `open_questions` carries a non-`None` answer for `question_id`. It keys on `handover_chain_id` (the root id of the whole revisit family, schema 1.5) rather than `revisit_of` (the immediate parent) deliberately: on a multi-question escalation, answering question 2 via the no-`handover_id` fallback (`alan.routes.answer._find_blocking_handover`) matches the newest handover carrying that question — which after question 1's answer is already an intermediate `revisit_amend`, not the root escalation. A `revisit_of`-keyed lookup anchored on the root's id would then miss that answer (it was recorded against the intermediate handover's id, not the root's), and a later call that references the root `handover_id` would find nothing recorded and re-dispatch. `handover_chain_id` propagates unchanged across every hop in a revisit family regardless of which specific node each answer was appended onto, so the lookup is stable no matter which handover in the chain a given `POST` happened to resolve against. This is the idempotency read-back: a second `POST` for an already-answered question finds the recorded answer here (or inline via `OpenQuestion.answer`, if the origin handover somehow already carried it) instead of re-recording or re-dispatching. First-recorded-answer wins; a repeat or conflicting second `POST` returns the original answer with `already_answered=true`. **One carve-out (see [acceptance_gate.md](acceptance_gate.md#withdrawn-acceptance-clauses)'s "Replaying a recorded ruling"):** when the recorded answer this lookup surfaces names a clause-stall withdrawal option and the clause it concerns is not yet marked withdrawn on committed state, `alan/routes/answer.py::_claim_already_answered` performs the withdrawal and the follow-on dispatch on that `POST` instead of a bare no-op. The lookup itself is unchanged — it still returns the earliest match — because idempotence for that carve-out comes from the `Requirement.withdrawn_by_question_id` marker, not from which record this function happens to surface.
- `unanswered_blocking_question_ids(blocking_handover, ws) -> list[str]` — the multi-question gate: a blocking handover with more than one blocking `OpenQuestion` only clears to dispatch once every one of them has an effective answer (`OpenQuestion.answer` or a recorded `revisit_amend`). Answering question 1 of 2 persists without dispatching; answering question 2 then finds zero remaining and dispatches.

Resolver derivation (`alan.dispatch.resolver_team_for_question`) maps the closed `question_class` enum to the team that must resume: `merge_block_escalation` → `pr_merge`, `verification_escalation` → `verification`, `fix_escalation` → `implementation_fix` (each single-emitter, per "Structured options" above), and `orchestrated_completeness` → the escalating handover's own `from_team` (never a constant, since that class is shared across ≥4 teams). The route fences the derived resolver against `MANUALLY_DISPATCHABLE_TEAMS` (`alan/teams/__init__.py`) before dispatching — a resolver outside that set 400s rather than silently no-op'ing.

When the POST answers the last remaining blocking question, `alan.routes.answer` derives and validates the resolver (`resolver_team_for_question` + the `MANUALLY_DISPATCHABLE_TEAMS` fence + `assert_team_dispatchable`'s task/archived/posture checks) **before** calling `record_answer` or appending the decision log. A 4xx from that validation therefore leaves neither a persisted answer nor a decision-log entry — a retry re-runs the same validation instead of hitting the idempotency read-back and getting permanently stuck at `already_answered=true, dispatch=null`. Only a question that isn't the last blocking one skips resolver validation entirely, since no dispatch is attempted for it.

L0.2's resumed-team context only covers single-task workspaces, where `dispatch_team_core`'s `prior_handover_for_task` falls back to `list_handovers(ws)[-1]` — the just-appended answer-carrying handover. Multi-task/DAG workspaces are out of scope: `prior_handover_for_task` resolves `prior` via `subtask.blocked_handover_id`, pinned to the original escalation handover, so a resumed resolver on a multi-task workspace would not see the recorded answer. A future multi-task extension needs to advance `blocked_handover_id` to the answer-carrying handover before dispatch.

### Honouring the human's chosen option (schema 1.20)

Before schema 1.20, the resolver team was derived purely from `OpenQuestion.question_class` (`alan.dispatch.resolver_team_for_question`) — the *category* of the question, never the specific option the human picked. When two offered options implied genuinely different next steps, picking either one produced the same dispatch. `OpenQuestion.option_resolvers: dict[str, str]` closes this gap: it maps a verbatim option string (a member of `proposed_answer_space`) to the team that must resume for that specific choice. `alan.dispatch.resolver_team_for_answer(question, from_team, answer)` checks `option_resolvers.get(answer)` first and only falls back to the untouched `resolver_team_for_question` when the chosen answer has no explicit mapping — so `resolver_team_for_question` itself stays byte-identical and every other caller (manual dispatch, proposal approval, auto-continuation) is unaffected.

**Where destinations are resolved.** Only `alan/routes/answer.py::_validate_resolver` calls `resolver_team_for_answer` — it is the sole human-answer path. The route still runs `assert_team_dispatchable` (task/archived/posture/roster checks) against the resolved destination before dispatching, exactly as it did for the category-derived resolver, and still validates before `record_answer`/the decision log, so a 4xx leaves no partial state. `dispatch_team_core` and its other four call sites (manual dispatch, proposal approval, auto-continuation) are untouched.

**Authoring is sparse and deterministic.** Only the non-actionable-feedback escalation (`alan/teams/_fix_escalation.py`) carries mappings: its "resolve by hand, then re-dispatch verification" option (`RESOLVE_BY_HAND`) → `"verification"`, and — when the verifier's gate block reads `GATE_ACTIONABLE: no` — the recommended "Re-dispatch pr_merge — the block is external gate state, not code (…)" option → `"pr_merge"`, because those are the only options in the codebase whose next step diverges from the class default (`fix_escalation` → `implementation_fix`). No destination is ever inferred from an option's free-text wording; every mapping is authored as a static dict literal at the same site that authors the option strings.

**Known limitations (by design, not oversight):** `_NO_PR_OPTIONS[1]` (`pr_merge.py`) and `_JUDGE_PARSE_FAIL_OPTIONS[1]` (`_verification_review_post.py`) describe a no-automated-next-step outcome and stay unmapped — a no-dispatch destination would be a new capability, not a routing fix. `_orchestrated.py`'s `_completeness_options` mixes up to two gap-derived options with two fixed constants (`_LOW_COMPLETENESS_RERUN_OPTION`, `_LOW_COMPLETENESS_ACCEPT_OPTION`, `alan/teams/_orchestrated.py:78-84`) — only the gap options are generated at runtime. The two fixed options stay unmapped because `orchestrated_completeness` is shared across every `OrchestratedTeam` subclass, including `ResearchTeam`, whose `to_team_suggestions` defaults to `()` (`alan/teams/research.py:111`) — there is no single known destination to key a static mapping to.

**Telling the resumed worker.** `alan.routes.answer` builds a `_decision_instructions` block — the question, the human's verbatim answer, and an explicit "do not re-ask or re-litigate it" directive — and forwards it through `_dispatch` into `dispatch_team_core`'s existing `instructions` parameter. This is the same `instructions` channel `dispatch_team_core` already threads into `enqueue_workflow`; only the answer route's local wrapper populates it for this call, so the other four `dispatch_team_core` callers are unaffected.

**`record_answer`'s synthesis.** The `revisit_amend` handover `record_answer` appends composes `full_synthesis` as the answer line, a blank line, then the *original* blocking handover's `full_synthesis` — not a replacement. Answer-first ordering means the decision survives `compression`'s `DEFAULT_MAX_CHARS` truncation even when the substantive context is long.

**Never presenting an answered question as open.** `alan.compression._format_questions` now takes the `workspace` param `_assemble` already threads through, and resolves every answered question in the handover's chain once via `alan.handover.recorded_answers_for_chain(ws, handover_chain_id)` (one `list_handovers` scan, not a per-question rescan). A blocking question whose `OpenQuestion.answer` or matching chain answer is set renders as `- <question> (resolver: <role>) [ANSWERED: <answer>]` instead of the bare open-question bullet — annotated, never dropped, so a resumed worker sees both the human's decision and the situation that prompted it. `summarize_handover_decisions_only` doesn't accept a `workspace` param and so still calls `_assemble` with `workspace=None`; `_format_questions` falls back to rendering every question as unanswered in that path, same as before this change — inline `OpenQuestion.answer` (already answered on the handover itself) still renders, only chain-scanned answers on other handovers require `workspace`.

### Suppressing dispatch on a pending-external answer (schema 1.22)

Before schema 1.22, every answer to a blocking `OpenQuestion` that resolved to a dispatchable team was treated identically: `alan.routes.answer._answer_and_maybe_dispatch` derived a resolver, dispatched to it, and composed a `_DECISION_DIRECTIVE` instruction ("The human has already decided this — do not re-ask or re-litigate it."). This was correct for an answer that genuinely settles the question, but wrong for one whose own wording promises future work — "complete the out-of-fleet step yourself, **then** re-dispatch" — because the route performed the re-dispatch immediately, at the exact instant the step is guaranteed not to have happened yet, and told the resumed worker the (unstarted) work was already done.

`OpenQuestion.option_effects` closes that gap by letting the code raising the question classify each option, at raise time, as `"closes"` (settles the question — dispatch and the decision directive apply as before) or `"pending_external"` (a human is undertaking to resolve this outside the fleet; nothing should start). `PENDING_EXTERNAL_NOTICE` (`alan/handover.py`) is the one constant that carries this meaning wherever a `pending_external` answer surfaces:

```python
PENDING_EXTERNAL_NOTICE = (
    "A human undertook to perform this step outside the fleet. It has not been "
    "observed to have landed. Check whether it has. If it has not, this remains "
    "blocked on that human — it is not accepted work, and the underlying finding "
    "is not to be re-derived as a fresh discovery."
)
```

It positively asserts the situation rather than merely omitting the old "recorded/answered" framing — omission alone would reopen the expensive re-declaration loop this notice exists to stop (the verifier re-raising the same capability-boundary finding forever). It replaces **both** places a recorded answer would otherwise render as settled:

- `alan.handover.record_answer`'s `full_synthesis` prefix — when the answered option's effect is `pending_external`, the prefix is `f"{PENDING_EXTERNAL_NOTICE}\n\n(question {question_id!r}, answer: {answer!r})"` instead of `f"Recorded answer for question {question_id!r}: {answer}"`. This is the text a human-re-dispatched worker reads via `alan.teams._base.build_prior_context_user_text`'s `prior_block`.
- `alan.compression._question_bullet` — when the effective answer's effect is `pending_external`, the bullet renders `f"{base} [{PENDING_EXTERNAL_NOTICE}]"` instead of `f"{base} [ANSWERED: {effective}]"`. This is the text a cross-team prior-outputs read (`load_cross_team_prior_outputs`) surfaces to any team whose handover named the escalating team in `to_team_suggestions`.

Both renderings matter because a recorded answer reaches a later role's context through both paths depending on how the workspace resumes; fixing one and leaving the other would look like it worked while a stale worker prompt still asserted the step was done.

**The suppression itself** lives entirely in `alan.routes.answer._answer_and_maybe_dispatch`: when `question.option_effects.get(answer) == "pending_external"`, `resolver` is set to `None` directly — `_is_last_blocking_question` and `_validate_resolver` are never called for that answer. Skipping `_validate_resolver` is load-bearing, not an optimization: it can raise on posture-admission grounds, and an option whose own wording promises to start no work must not be blockable by whether its named team happens to be dispatchable right now. `record_answer`, `record_gold_label`, the project decision-log append, and `record_intervention` all still run unchanged — the answer is genuinely recorded, only the dispatch is withheld. `AnswerResponse.pending_external: bool` (default `False`) and `InboxItem.pending_external: bool` (default `False`) surface this to the two frontends (`Workspace.tsx`'s `DecisionCard`, `Inbox.tsx`'s `ItemCard`) so neither presents a pending-external answer as either "still needs an answer" or "closed and dispatched."

**Two escalations classify their options today.** `alan/teams/_verification_review_post.py`'s `_CAPABILITY_BOUNDARY_OPTION_EFFECTS` maps the "resolve this outside the fix-worker loop" option (retitled from "complete the out-of-fleet step yourself" so the same wording also fits a vacuity finding, not only a permission/credential boundary) to `pending_external` and "waive this finding and proceed to merge" to `closes`. `_CLAUSE_STALL_OPTION_EFFECTS` mirrors the same shape for the clause-stall escalation (see `docs/architecture/loop_guard.md`): "rewrite or drop this clause, then re-dispatch verification" maps to `pending_external`, "waive this clause and proceed to merge" to `closes`. `_emit_judge_parse_failed` and `_emit_clause_pr_state_escalation` pass no `option_effects` (empty by default), and `_fix_escalation.non_actionable_question`'s `RESOLVE_BY_HAND` option (which *does* carry an `option_resolvers` entry, routing to `verification`) carries no `option_effects` entry either — a populated `option_resolvers` entry never implies `pending_external` by itself, since routing-to-a-team and promising-future-outside-fleet-work are independent facts about an option.

### Attaching a PR number to a stranded workspace

`POST /api/workspaces/{workspace_id}/tasks/{task_id}/attach-pr` (`alan/routes/pr_attach.py`, control-token gated) hands a pull-request number back to a workspace whose PR was pushed but never recorded — the branch and commits reached the remote, but `gh pr create` failed, so no consumer on the handover chain ever sees a `pr_number`. `alan.handover.record_pr_attachment(ws, prior, pr_number)` appends a `revisit_amend` handover carrying the number, the same `HandoverType` `record_answer` uses for a human-supplied fact — but the two are distinct channels for distinct kinds of fact. `record_answer` resolves a blocking `OpenQuestion`; the value it carries is read back via `OpenQuestion.answer` / `find_recorded_answer`, a question-answer-shaped lookup. `record_pr_attachment` supplies a forge fact with no associated question — it exists purely so `Handover.pr_number` is non-`None` on the handover a subsequent dispatch resolves as `prior`. Unlike `record_answer`, it never touches `open_questions`, and it is not looked up by chain scan — it only needs to be *reachable*, not *found by content*.

**Why appending to the chain is not enough.** `alan.dispatch.prior_handover_for_task(ws, task_id)` — the function every dispatch path (`dispatch_team_core`, `pr_merge`'s own re-dispatch, verification's resume) uses to find the handover it should act on — does not read the tail of the handover chain when the workspace has subtasks. It resolves the subtask's pinned `blocked_handover_id` if it has one; otherwise the most recent handover attributed to that subtask (`from_invocation_id` → `WorkflowDoc.source_task_id`); otherwise none — never a sibling's. The full rule, the all-or-nothing fallback for workspaces where nothing is attributable, and the in-memory pull-request recovery are in [queue_and_dispatcher.md](queue_and_dispatcher.md#resolving-a-subtasks-prior-handover).

An escalated workspace with subtasks has `Task.blocked_handover_id` pinned to the escalation handover by `alan.dispatcher._finalize_blocked_decision` (set on *every* blocked/escalated decision once `ws.meta.tasks` is non-empty). A handover appended after that pin is invisible to `prior_handover_for_task` — the pin still wins, so a post-pin amendment has to be repointed at. What changed is that a pinned PR-less escalation no longer strands the subtask: a missing `pr_number` on the selected handover is back-filled, in memory, from the nearest earlier handover among the subtask's own handovers that carries one (only that field; identity, lineage, summary, forbidden actions and instructions are untouched), while a subtask whose own history genuinely carries no PR still needs this endpoint. This is why `attach_pr`'s handler does two writes, not one: it calls `record_pr_attachment` to append the amendment, then — only when a subtask with that `task_id` exists — calls the shared `_point_subtask_at(ws, task_id, subtask, handover_id)` helper, which wraps `alan.workspace.update_task_status(ws, task_id, subtask.status, blocked_handover_id=handover_id)` to repoint the pin at it, passing the subtask's own unchanged `status` so the repoint is not also a status transition. On the zero-subtask workspace shape, there is no pin to repoint — `prior_handover_for_task` falls through to the tail-of-chain branch, and the freshly appended amendment already *is* the tail, so no second write is needed there. Any future operator mutation meant to influence a dispatch on a workspace-with-subtasks needs this same two-write shape; appending to the chain alone is a silent no-op for that population.

**The repeat path is a write too.** `_point_subtask_at` is called on *both* branches of the same-PR idempotency check — the fresh-attach path and the already-attached (`prior.pr_number == pr_number`) no-op path — pointed at whichever handover the pin should read as `prior` next: the newly-recorded amendment on the fresh-attach path, the unchanged `prior` itself on the repeat path. Before this, the repeat path returned immediately after the idempotency check, before ever touching the pin, so a first attach that pinned the subtask correctly could be followed by a second attach for the same PR number that left the subtask *unpinned* — a repeat that regressed the workspace's state relative to the first call. A repeat now always re-applies the same pin the first attach would have, so `meta.updated_at` advances on a repeat exactly as it does on a fresh attach, and the workspace never ends up less pinned after a second identical call than after the first.

**The two-id contract.** The route path is `/api/workspaces/{workspace_id}/tasks/{task_id}/attach-pr` — `workspace_id` and `task_id` name different things once a workspace has subtasks. `alan.handover.save_handover` enforces `handover.task_id == ws.task_id` (the *workspace* id); `record_pr_attachment` stamps the new handover with `ws.task_id` accordingly. `update_task_status(ws, task_id, ...)` takes the *subtask* id from the URL path and raises `WorkspaceError` unless exactly one task matches it. Passing the wrong id to either call raises at write time — the handler resolves the subtask via `next((t for t in ws.meta.tasks if t.id == task_id), None)` before ever calling `update_task_status`. Only the zero-subtask shape (`ws.meta.tasks` empty) is entitled to skip the repoint this way: `_task_id_known` refuses with `404` up front when `ws.meta.tasks` is non-empty and `task_id` matches none of them, so a typo'd subtask id on a workspace that *has* subtasks can no longer land the amendment on the chain tail with nothing pinned to it — a silent no-op invisible to every dispatch path until a human went looking.

**`iteration` is display-only.** `record_pr_attachment` derives `iteration=prior.iteration + 1` from the handover it is amending, not from `list_handovers(ws)[-1]` — deliberately, since the pinned `prior` on an escalated, multi-subtask workspace need not be the chain tail, and reading the tail unconditionally would `IndexError` on an empty chain in the (unreachable, but branch-coverage-visible) case a subtask has no chain at all yet. Because the amendment is derived from whichever handover the pin resolves to rather than from the tail, its `iteration` may legitimately duplicate a number already used by a sibling subtask's own chain — `iteration` orders a single subtask's revisions, it is not a workspace-wide sequence.

**Not required to be merged, and never terminal.** `attach_pr` deliberately does not call `verify_pr_merged` (nor its `triage_pregate` sibling) — driving an *open* PR to completion through `pr_merge` is the point; the sibling out-of-band `/complete` endpoint (`alan/routes/workspaces.py`) is the one that requires an already-merged PR, and stays exactly as strict as before. The amendment `record_pr_attachment` writes has `handover_type="revisit_amend"`, never `"terminal"`, so `reconciler`'s terminal-handover scan does not treat the attach itself as completing the workspace — the subsequent `pr_merge` dispatch is what decides the outcome, exactly as if `pr_merge` had received the number on its very first run.

**Locking scope.** `_reject_if_unattachable` (unknown-task / archived-workspace) still runs *outside* the lock, against the caller's possibly-stale `ws` — those two refusals don't depend on anything a concurrent request could change underneath them. `_attach` then holds the module-level `_lock` for the entire read-check-write sequence, which now *opens* with the in-flight liveness gate rather than the idempotency check: the fresh `workspace_mod.read` reload, `_reject_if_in_flight`'s liveness check (`reconciler._is_subtask_live`, see below), `prior_handover_for_task` resolution, the same-PR idempotency short-circuit, `resolve_existing_branch`'s forge call, and the `record_pr_attachment` + pin-repoint writes all sit inside this one critical section, guarded by a reload from disk rather than the caller's already-read `ws`. Checking `prior.pr_number == pr_number` before acquiring the lock against that stale `ws` (the original shape) let two concurrent requests for the same not-yet-attached PR both observe a PR-less prior and each append their own amendment — reloading only after acquiring the lock is what makes the liveness gate, the idempotency check, and the pin-repoint see any attach a concurrent request just committed. A plain `threading.Lock()` rather than the dispatcher's per-workspace lock is a deliberate choice: the population this endpoint targets is escalated with no worker running, so cross-workspace contention under this lock is not a concern this endpoint needs to optimize for. What "no worker running" meant before this change was merely an assumption about the population an operator would find escalated; the liveness gate below turns it into an enforced precondition — a call that finds a worker running for the subtask is refused rather than racing it.

**Refusal taxonomy.** Immediately after the reload, `_reject_if_in_flight` resolves the subtask matching the URL `task_id` (falling back to `ws.workspace_id` as the liveness key when no subtask matches — the population `_task_id_known` waves through unconditionally on a zero-subtask workspace) and checks it against `alan.reconciler._is_subtask_live(live_key, ws.workspace_id, queue)` — the same predicate `reconciler._try_complete_subtask` calls, reused here rather than forked, so attach-refusal cannot silently drift from that sweep's own eligibility test. `workspace_dag._ancestor_has_in_flight_job` is a *separate*, pre-existing implementation of the identical pending/running `list_jobs(...)` check (`alan/workspace_dag.py:258-262`) — it does not call `_is_subtask_live`, and this change does not unify the two. That is a second, independent fork of the same liveness notion, not reuse: a future change to either predicate's pending/running semantics must be mirrored in the other by hand, or the two will silently drift apart. A live subtask refuses `409` ("work already in flight …", naming up to five matching jobs by id/team/status) before the workspace is read a second time for anything else — no forge call, no write. This sits alongside the workspace's two pre-existing `409`s (`_WORKSPACE_ARCHIVED_DETAIL`, `_NO_PRIOR_HANDOVER_DETAIL`). The head ref is resolved via `alan.teams._pr_branch.resolve_existing_branch(pr_number, ws.task_id, forge_target=forge_target_for_ws(ws))` — the same helper `triage_pregate` uses for PR↔task matching, scoped through the workspace's own forge target rather than `triage_pregate`'s module-level default-engine constant (a latent multi-repo hazard in `verify_pr_merged`/`_fetch_pr_by_number` that `attach_pr` deliberately does not inherit). `resolve_existing_branch` collapses several failure shapes into `None` only for a genuinely absent PR (`domain_absent`); auth/rate-limit/transient/missing-binary/timeout failures raise `ForgeTransientError`/`ForgeRateLimited` instead. `attach_pr` keeps these separate: a caught raise becomes `503` ("could not confirm — forge unreachable"), a `None` return becomes `404` ("PR not found"), and a resolved ref that fails `teams/{ws.task_id}` / `teams/{ws.task_id}-*` prefix matching (`triage_pregate._pr_matches_task`) becomes `422` naming the expected prefix — conflating the first two would misreport a merely-unreachable forge as a definitive mismatch, the same defect class this incident's sibling fix addressed.

**Response shape.** `AttachPrResult.outcome` is a three-member `AttachOutcome` enum, not the boolean `repointed` it replaced: `attached` (a fresh amendment was recorded and pinned to a matched subtask), `already_attached` (the same-PR no-op path, re-pinned to the same handover), and `no_subtask_pin` (the workspace has no subtask matching `task_id` — the zero-subtask shape — so there is no pin to apply, regardless of whether the call was a fresh attach or a repeat). `no_subtask_pin` takes precedence over both `attached` and `already_attached` on that shape: pin-applicability is the fact a caller needs to act on, not whether this particular call happened to be a repeat.

### The `plan_synthesis` carrier

`plan_synthesis` (schema 1.15) is distinct from `full_synthesis` (schema 1.6): it holds the **full, untruncated plan synthesis** produced by `ImplementationPlanTeam`, carried specifically so a later `implementation`/`implementation_fix` worker can re-read the plan's own `## Implementation steps` section verbatim. The planning/decomposer side is the producer — `decomposer.py:372` (`_build_keep_handover`) copies `prior.full_synthesis` verbatim into the outgoing handover's `plan_synthesis` field on a split-vs-keep "keep" decision, including its trailing fenced `decisions.yaml` block (scenario ids, `when` commands, `then` outputs) — the **persisted** field is never sanitized; it is the record of exactly what the planner emitted. Downstream consumers apply both the prompt-budget truncation and the acceptance-scenario projection, not the producer: `implementation.py`'s `_prior_plan_block` calls `_plan_implementation_steps(_plan_projection.strip_scenario_fences(prior.plan_synthesis))` (fences stripped first, then sliced to the `## Implementation steps` section) when `plan_synthesis` is set, falling back to `_plan_projection.strip_scenario_fences(prior.full_synthesis)[:DEFAULT_MAX_CHARS]` only when it isn't — see [implementation_pipeline.md](implementation_pipeline.md#implementer-blindness-to-acceptance-scenarios) for why the acceptance-scenario fence never reaches the implementer's prompt on either branch, regardless of which planning shape the workspace took. Do not conflate the two fields: `full_synthesis` is the generic per-handover summary every team writes; `plan_synthesis` is the implementation-plan-specific carrier that survives the decomposer hop untruncated (and, at rest, unredacted).

### Spiral escalation carries forward decisions and artifacts

`Dispatcher._enforce_loop_guard` (`alan/dispatcher.py`) escalates a workspace the moment `detect_spiral` reports a spiral, replacing the router's `enqueue` decision with an `escalation` handover before anything downstream ever sees the spiral-triggering handover. Before this, that escalation handover was built inline as `escalation_skeleton(ctx, spiral_reason, handover.pr_number)` — a skeleton whose only content is the one-line `spiral:<kind>: <evidence>` reason string, with `decisions` and `artifacts_produced` both defaulting to empty. A fix worker re-dispatched onto that escalation therefore ran blind: `_load_judge_review` (`alan/teams/implementation_fix.py`) reads `artifacts_produced` for the full judge review and falls back to `full_synthesis` when it finds nothing, `parse_actionable_gate_checks` and the `_fix_forward.py`/`_fix_escalation.py` prose-matchers read `full_synthesis` for gate state that was never there to begin with — none of the four found what they needed, because the pass that spiraled had produced it and the skeleton never carried it forward.

`alan.teams._spiral_handover.spiral_escalation_handover(workspace, prior, spiral_reason)` is now the dispatcher's sole call for this path. It builds the `HandoverContext` the same way `_enforce_loop_guard` used to (team name from `prior.from_team`), calls the unmodified `escalation_skeleton` to get the skeleton, then layers `prior.decisions` and `prior.artifacts_produced` onto it with `model_copy(update={...})`. The update dict never names `open_questions` — the exclusion is structural, not a filter: a spiral escalation carries no open-questions content at all, so a stale question from the pass that spiraled can never resurface as if it were live on the escalation. `full_synthesis` is untouched by the `model_copy` and stays byte-identical to the one-line spiral reason `escalation_skeleton` already set — `parse_actionable_gate_checks`, `_fix_forward.py`, and `_fix_escalation.py` pattern-match that exact prose, so padding it with copied text from the prior pass would be misread as a fresh verification result.

`escalation_skeleton` itself is unmodified, so the other three callers sharing it — `no_pr_escalation_handover`, `no_commits_handover`, `push_failed_handover` — are unaffected by construction. No schema version bump: `decisions` and `artifacts_produced` already exist on `Handover` (see the 1.23 no-bump precedent above) — this only changes which fields a spiral escalation populates, never the schema itself.

Carrying `artifacts_produced` alone reconnects `_load_judge_review`, but three more readers still parsed `prior.full_synthesis` directly for state that only ever lived in the pass that spiraled: `_maybe_fetch_gate_failures`'s `parse_actionable_gate_checks` call (`alan/teams/implementation_fix.py`), `_fix_forward._inbound_scenarios_missing`, and `_fix_escalation.non_actionable_question`'s `parse_gate_cause` call. `alan.teams._fix_forward.resolve_review_text(prior)` is the shared, non-misleading channel all four now go through: it prefers the carried "full judge review" artifact's file content (the same one `_load_judge_review` already reads) and falls back to `prior.full_synthesis` only when no such artifact is present or it can't be read — the exact fallback `_load_judge_review` already used. `full_synthesis` on the escalation itself is still never touched; only the read side changed, so a spiral-escalated `prior` now yields actionable gate checks, the `SCENARIOS_MISSING` signal, and the gate-failure cause exactly as a direct (non-spiral) dispatch would, without ever risking a misread of the pinned one-line spiral marker.

### `SCENARIOS_MISSING` self-heal

When the judge review carries `SCENARIOS_MISSING`, `implementation_fix` regenerates a fenced `test_scenarios.yaml` block (prompt in `implementation_fix.py`). If that run makes **no code commits** (the only "fix" is the scenarios themselves), `_finalize_fix` does **not** fall through to `_pr_handover.build_handover`'s no-commits → escalation branch; instead it emits a `forward` handover with `to_team_suggestions=["verification"]` carrying the regenerated scenarios, so the verification pipeline re-runs them instead of dead-ending at human escalation.

## Save-time Layer 3 validator

`_validate_layer3_decisions` rejects any `forward` handover to `implementation` or `verification` with empty `decisions`. This forces upstream producers (notably the `implementation_plan` synthesizer) to emit non-empty Decision lists — see [teams_taxonomy.md](teams_taxonomy.md) for how the synthesizer's fenced `decisions.yaml` block satisfies this.

It also rejects any `forward` handover with `from_team == "architecture"` and empty `decisions`, independent of `to_team_suggestions` — architecture handovers never name an implementation/verification-family recipient, so the recipient-based check above never fires for them. This is a defensive net, not a fix for observed drift: today `architecture.py`'s `parse_decisions_block` call, which runs before `build_forward_handover`, already fails the run on an empty decisions block, so this branch is currently unreachable. It exists so that if that upstream parse is ever removed or refactored, an empty-decisions architecture handover still cannot reach persisted state. The match is a literal `from_team == "architecture"` string, not a shared team-name constant — a future rename of the architecture team must grep `alan/handover.py` for this literal.

## Operator-terminal sessions write no handover

A workspace-scoped operator terminal session (see [operator_terminal.md](operator_terminal.md)) leaves exactly two records on the workspace and neither is a handover: an `operator_terminal` entry in `Meta.interventions` when the session starts, and an `operator_transcript-<UTC>.txt` file when it ends. Nothing in the handover chain, `prior_handover_for_task` or the router reads either.
