# CI isolation model

**Status:** implemented  
**Scope:** `.github/workflows/tests.yml`, `boundary-smoke.yml`, `hotspots.yml`, `behavioral_eval.yml`, `ci-deploy.yml`, `e2e-stress.yml`, `auto-merge-label.yml`; `alan/roots.py` + `tests/test_roots_registry.py` (the drift gate)

## Context

A CI runner can share a physical machine with the production `ai.alan` launchd service. Wherever a runner and the live service do share a host, a job without explicit isolation could read, modify, or corrupt production runtime state — or, if `ALAN_SLOT_POOL_ROOT` leaks in, accidentally claim a production work slot.

Running CI work on separate machines from the production service narrows that premise but does not remove it: a job that still runs on the production machine is exactly the workload the isolation model binds hardest, so do not read a separate CI machine as "CI can no longer touch prod state". The machine-wide e2e port cleanup is a related case: the invariant below that a runner serving production never takes e2e jobs is carried by a range check, not by machine placement — the swept ranges are `20000+`/`36000+` while prod binds `8585`, so the predicate cannot match the live service.

## Production vs CI process spaces

The production service runs as a launchd daemon (`ai.alan`). launchd manages its own environment dictionary (see `deploy/ai.alan.plist`); the variables it defines are **not** exported to child processes outside the launchd session. GitHub Actions runner processes are spawned by the runner daemon, not by launchd, and do not inherit any launchd-managed env vars. The two process spaces are naturally disjoint.

The explicit env blocks below are a belt-and-suspenders guard for two scenarios:
1. A future operator accidentally sources a production env file in the runner shell.
2. `ALAN_SLOT_POOL_ROOT` — now set to a real path in the rendered plist (`~/.alan/slots`, rendered from the tracked template's `__ALAN_HOME__` token by `deploy/render_plist.sh`) — leaks into a runner that lacks the matching CI override.

## Runner routing labels

Every job carries a routing label; which machines carry which label is runner-fleet configuration, not part of this model.

## The `e2e-lane` job-level concurrency group

Three browser/CPU-heavy jobs share one runner lane, but sharing a lane alone does nothing to stop them from co-scheduling: `tests.yml`'s `e2e-frontend`, `test-frontend`, and `mobile-audit-gate` carry no `needs:` relationship between them, so a batch of in-flight PRs previously let all three race for the lane's runner processes simultaneously — this is the oversubscription the `test-frontend` step comment already named as *"the P-core contention that surfaces as Playwright expect timeouts"*. Serializing only `e2e-frontend` against itself would have removed roughly a third of that contention; the other two-thirds comes from `test-frontend`'s vitest burst and `mobile-audit-gate`'s own Playwright run co-scheduling on the same lane.

The fix is a single job-level `concurrency` block, identical across all three jobs:

```yaml
    concurrency:
      group: e2e-lane
      cancel-in-progress: false
      queue: max
```

`lint-frontend` deliberately stays out of the group even though it runs in the same lane: it runs no browser and no CPU-heavy test burst, so excluding it lets a runner process keep draining light lint work while the other three drain the shared lane. `e2e-stress.yml`'s nightly sweep also stays out — see the non-goal note on it above; a 60-minute job in a shared FIFO queue would head-of-line-block every PR run behind it. Excluding it from the group does not remove it from the lane: a nightly sweep that happens to overlap a PR batch still competes for the same runner processes as the grouped lane jobs, since exclusion from `e2e-lane` only stops it from *queueing behind* the group — it does not stop it from *running alongside* it. This residual risk is accepted and stated, not solved, for the reason above (head-of-line-blocking every PR behind a 60-minute job would be strictly worse).

**The queue-depth trap this group exists to avoid:** a GitHub Actions concurrency group holds exactly one *pending* run by default, and a new arrival **cancels** that pending run — `cancel-in-progress: false` only protects the run already *in progress*, not one waiting in the queue. Without `queue: max`, a batch of PRs sharing this group would still starve each other, just one level up: instead of Playwright timeouts, a PR's E2E check would silently vanish and never run at all, which is the one outcome this change is explicitly forbidden from producing. `queue: max` switches the group to a 100-deep FIFO queue instead of depth 1. The in-repo shape that looks like the right thing to copy and is not: `ci-deploy.yml`'s `{group: ci-deploy, cancel-in-progress: false}` carries no `queue:` key at all, so it is depth-1 by omission — safe there only because a superseded main push having its deploy signal delayed is an accepted, already-documented trade, not the failure mode this group must avoid.

The pre-existing workflow-level group at `tests.yml:8-10` (`${{ github.workflow }}-${{ github.ref }}`, `cancel-in-progress: true`) is unchanged and becomes *more* load-bearing once `e2e-lane` holds a deep queue: it is what keeps a superseded commit's stale jobs from occupying queue slots that a current commit's jobs would otherwise have to wait behind.

One direct consequence worth stating because it is easy to miss: a single PR with nothing else in flight now runs its own `e2e-frontend`/`test-frontend`/`mobile-audit-gate` triple **serially** rather than in parallel, since all three request the same group on every run. This is a real per-PR wall-clock cost, not just a batch-contention fix.

`tests/test_workflow_runner_labels.py` extends its structural pin set for this: `_E2E_LANE_GROUP`/`_E2E_LANE_JOBS` assert set-equality of group membership, that no lane job sets `cancel-in-progress: true`, that every lane job sets `queue: max`, that `lint-frontend` and `e2e-stress` carry no `e2e-lane` group, that `tests.yml`'s workflow-level group is untouched, that `ci-deploy.yml`'s group still carries no `queue` key, and that `_E2E_LANE_JOBS` is a subset of `_E2E_CARRIERS` — closing the gap where the two membership lists could silently drift apart.

**The verifier settle-wait ceiling is sized for this change, not left asserted-unchanged.** `alan/teams/_verification_gates.py`'s `_maybe_rerun_flaky_gates` triggers a rerun of a flaky-looking check and then waits up to a wall-clock budget of `_DEFAULT_SETTLE_MAX_POLLS` × `_DEFAULT_SETTLE_POLL_INTERVAL_S` seconds for it to resolve (spent in ≤ 15 backed-off wake-ups, each gated by a cheap REST check-runs probe — see `docs/architecture/pr_iteration_pipeline.md`'s settle-wait paragraph; the budget arithmetic below is unchanged). Once `e2e-lane` holds a real queue, that wait includes queue time it never had to absorb before — a rerun can be queued behind other PRs' lane jobs, or behind the triggering PR's own other two lane jobs. The observation side needs no repair: the readiness probe already models a queued-but-not-started job as *pending*, so the wait correctly keeps polling rather than mistaking "queued" for "finished" or "failed." Only the ceiling needed sizing. Lacking a live `gh`-measured job duration, the ceiling is sized against a worst-case bound computed from already-committed ceiling values: the three lane jobs' own `timeout-minutes` (15 + 8 + 16 = 39 minutes) as a worst-case single-PR lane-drain figure, plus one more `e2e-frontend` duration (15 minutes) as a rerun tail, at the *minimum possible* queue depth of 1 (this PR's own three lane jobs, zero contention from any other PR) — `ceil((2340 + 900) / 30) = 108` polls, i.e. `_DEFAULT_SETTLE_MAX_POLLS = 108` (54 minutes). **This bound is deliberately not a full solution and is stated as such:** it covers one PR's own lane drain, not a batch where other PRs' lane jobs sit ahead of the rerun in the up-to-100-deep `queue: max` FIFO — that residual case has no fixed ceiling that covers it by construction, since queue depth is unbounded by design. The correct fix for that residual case remains the same terminal-handover-and-re-park shape `alan/deploy_wait_gate.py` already uses for `deploy_verify`'s own wait — it needs no measurement, since it stops burning a fixed in-process budget on queue-wait at all — and stays a named follow-up rather than being implemented here, matching this document's e2e-stress exclusion above (state the residual risk, don't require solving it in the same change).

**A runner that serves production must never take e2e jobs**, because `tests.yml`'s `e2e-frontend` performs machine-wide port/process cleanup (killing stray `python -m alan` listeners across a fixed port range — see "Free e2e port range" in `tests.yml`), which frees a fixed port range. `mobile-audit-gate` runs on the same e2e-capable runners but its cleanup is narrower and has no equivalent workflow step: it frees or avoids only its own pid-derived port at Playwright config-load time (`reserveMobileAuditPort()` in `alan/web/src/mobile-audit-config.ts`, walking candidates via `alan/web/src/port-avoidance.ts`), reclaiming only listeners that match the same `python -m alan` predicate the E2E job uses — it never scans or kills across a fixed port range. A runner that never serves production can run either job's cleanup safely; one that does could kill the live service out from under itself.

## Per-job guaranteed-clean state

Every CI workflow that runs code uses `actions/checkout` with `clean: true` set **explicitly** (not relying on the default). The action runs `git clean -ffdx` before each job, removing:
- untracked source files from a prior run
- gitignored build outputs (`.venv/`, `node_modules/`, `coverage.xml`, `__pycache__/`)
- stale branch state from a different PR or branch

This means each job always starts from the exact tree that `git checkout` produces and nothing else.

## Dependency install speed (UV_CACHE_DIR)

`git clean -ffdx` removes `.venv/` and `node_modules/`, which would normally mean a full network reinstall on every run. To avoid this, all five non-deploy workflows that install Python dependencies (`tests.yml`, `boundary-smoke.yml`, `hotspots.yml`, `e2e-stress.yml`, `behavioral_eval.yml`) export an absolute cache path:

```yaml
env:
  UV_CACHE_DIR: <absolute path>/.alan-ci/uv-cache
```

**The path must be absolute.** GitHub Actions does **not** tilde-expand or shell-expand values in `env:` blocks, so an earlier `UV_CACHE_DIR: ~/.alan/cache/uv` was taken literally: uv created a `~` directory *inside the repo checkout* (`./~/.alan/cache/uv`), and pytest — which has no `testpaths` restriction — then recursively collected every vendored third-party test suite shipped in that cache (libcst, mypy, bandit, …), producing dozens of spurious failures. An absolute path keeps the cache outside the working tree so pytest never sees it.

**The path must not live under `/tmp`.** The cache once lived at `/tmp/alan-ci/uv-cache`, and macOS's periodic maintenance purges `/tmp` entries by access time around midnight, yanking cache files out from under running jobs — manifesting as corrupted installs and intermittent 401/ConnectionRefused noise on the runner. The configured path is a dedicated `.alan-ci/` directory in the runner user's home: persistent across reboots and maintenance sweeps, outside every repo checkout, and outside the production `~/.alan/` tree. It is intentionally NOT under the sandboxed `HOME` the backend pytest step uses — `UV_CACHE_DIR` is absolute, so that step keeps hitting the warm cache.

This claim was not actually true of every workflow until the runner-label-routing change that added this section: `behavioral_eval.yml` kept a per-run `/tmp/alan-ci/${{ github.run_id }}-${{ github.run_attempt }}/uv-cache` — the exact pattern this section warns against — from before this document was written until it was normalized to match its four siblings above. Stated plainly rather than papered over: this document's "the path must not live under `/tmp`" claim was aspirational for that one workflow, not universally enforced, until that normalization landed.

That cache path is **stable** (not under the per-run `${{ github.run_id }}-${{ github.run_attempt }}` subtree), so it survives `git clean` and stays warm across runs, while still being isolated from the production `~/.alan/` tree — consistent with this document's purpose.

`UV_CACHE_DIR` is uv's content-addressed **download** cache — it stores pre-built wheel files keyed by hash. It is:
- **persistent** across runs (survives `git clean` and macOS `/tmp` maintenance; lives outside the workspace, at a fixed absolute path under the runner user's home)
- **concurrent-safe**: uv's cache uses hard-link and copy-on-write semantics; multiple parallel jobs can read from the same cache simultaneously with no corruption
- **shares no mutable source-control state**: each job has its own `.venv/`, which is rebuilt from the shared cache but never shared itself

A warm `uv sync --locked --extra dev` call with an up-to-date `UV_CACHE_DIR` completes in under 10 seconds without any network traffic.

## ALAN runtime path isolation

All CI workflows set the following env vars to redirect Alan's runtime writes out of the production `~/.alan/` tree:

```yaml
env:
  ALAN_LOGS_ROOT: /tmp/alan-ci/${{ github.run_id }}-${{ github.run_attempt }}/logs
  ALAN_QUEUE_DB_PATH: /tmp/alan-ci/${{ github.run_id }}-${{ github.run_attempt }}/queue.db
  ALAN_WORKSPACES_ROOT: /tmp/alan-ci/${{ github.run_id }}-${{ github.run_attempt }}/workspaces
  ALAN_STATE_ROOT: /tmp/alan-ci/${{ github.run_id }}-${{ github.run_attempt }}/state
  ALAN_BUILD_CHAT_SESSIONS_ROOT: /tmp/alan-ci/${{ github.run_id }}-${{ github.run_attempt }}/build-chat-sessions
  ALAN_EXPLORE_CHAT_SESSIONS_ROOT: /tmp/alan-ci/${{ github.run_id }}-${{ github.run_attempt }}/explore-chat-sessions
  ALAN_PROJECTS_ROOT: /tmp/alan-ci/${{ github.run_id }}-${{ github.run_attempt }}/projects
  ALAN_SECRETS_STORE_ROOT: /tmp/alan-ci/${{ github.run_id }}-${{ github.run_attempt }}/secrets
  ALAN_PLANS_ROOT: /tmp/alan-ci/${{ github.run_id }}-${{ github.run_attempt }}/plans
  ALAN_DRIVER_LOOP_STATE_ROOT: /tmp/alan-ci/${{ github.run_id }}-${{ github.run_attempt }}/driver-loop-state
  ALAN_SLOT_POOL_ROOT: ""
```

`ALAN_DRIVER_LOOP_STATE_ROOT` joined the set with the supervised driver-loop runner (`docs/architecture/driver_loops.md`): its default (subdir `.`) is `~/.alan` itself, matching the pre-existing convention of driver skills writing their own journal state directly under `~/.alan/<name>/` — so this token exists purely to redirect that PAUSE-file/state-directory root away from production in every isolation surface, the same way `ALAN_STATE_ROOT` redirects the rest of the state tree. The runner thread itself is already off in every isolation surface via `ALAN_DETACHED_WORKERS: "off"` (the same dial that gates detached fleet workers); this token additionally protects a PAUSE-file write reached through a route call, independent of whether the runner thread is running.

The chat-session roots were added 2026-07-03 after a full-repo sweep run leaked empty build/explore/legacy chat sessions into the production `~/.alan`: the chat stores' default roots were, at the time, import-time `Path.home() / ".alan" / ...` constants, and until that fix nothing pinned them in CI. As of H3.2b, that plumbing no longer exists: each chat store's `ChatCoreConfig` (`alan/build_chat.py`, `alan/explore_chat.py`) supplies a `sessions_root: Callable[[], Path]` field bound directly to its `alan.roots` resolver (`roots.build_chat_sessions_root`, `roots.explore_chat_sessions_root`) — there is no `sessions_dir` constant and no `sessions_root_env` string anywhere in this stack. `alan/_chat_core.py::_base_dir` performs zero `os.environ` access itself: `return root if root is not None else cfg.sessions_root()` calls the injected resolver lazily, once per call, only when no explicit `root` was given. The env-var read still happens — it just lives inside `alan.roots`'s own `_state_root()` helper, one layer below — so the observable behavior (env override wins, call-time not import-time resolution) is unchanged; only the plumbing that used to be duplicated per chat store is gone. `ALAN_SECRETS_STORE_ROOT` joined the set on 2026-07-20 when the API-managed secrets store (`alan/secrets_store.py`, `POST/DELETE/GET /api/secrets`) shipped: its default root is `~/.alan/secrets` (a directory of one `0600` file per engine×purpose credential), so an unredirected worker or CI job would otherwise read or write real per-engine credentials there. `tests/conftest.py` also unconditionally assigns every `STATE_ROOT_SUBDIRS` token, `ALAN_LOGS_ROOT` included, to a shared per-session temp dir at import time (`setdefault` until 2026-09-18 — see "Closed gap: `setdefault` on the ten `STATE_ROOT_SUBDIRS` tokens deferred to a fleet worker's own sandbox" below), so local `uv run pytest` on the production Mac (and every `TestClient(server.app)` lifespan boot, which resolves these roots at startup) is sandboxed regardless of what the surrounding environment already carries. `ALAN_LOGS_ROOT` is then overridden a second time, per-test rather than per-session, to each test's own `tmp_path`, by the autouse `_redirect_alan_logs_root` monkeypatch fixture (which also redirects `ALAN_QUEUE_DB_PATH`, a queue-database path outside the roots registry).

## The roots registry (drift gate)

`alan/roots.py` is the canonical, stdlib-only registry of every `ALAN_*_ROOT` token in the isolation model above: `STATE_ISOLATION_ROOTS` (the ten state-redirect roots — workspaces, logs, state, the two chat-session roots, projects, the secrets store, the engines root, the plans root) and `CI_ISOLATION_ROOTS` (that set plus `ALAN_SLOT_POOL_ROOT`, the slot-pool disable switch, and `ALAN_WORKTREE_REPO_ROOT`, the bare-worktree repository redirect). `tests/test_roots_registry.py` is a structural pytest gate — no new CI job — that regex-scans each isolation surface's file content for every registered token and fails closed on any gap: the four CI workflows above (`CI_ISOLATION_ROOTS`), `tests/conftest.py` (`CI_ISOLATION_ROOTS`, widened from `STATE_ISOLATION_ROOTS` on 2026-08-30 — see "Closed gap" below), `alan/web/e2e/fixtures/server-env.ts` (`CI_ISOLATION_ROOTS` — upgraded from `STATE_ISOLATION_ROOTS` on 2026-07-16 after a locally-launched e2e server, inheriting the production plist's `ALAN_SLOT_POOL_ROOT`, built its own `SlotPool` over `~/.alan/slots` and hard-reset a slot a live production worker was using, destroying its in-flight implementation; `serverEnv()` now pins `ALAN_SLOT_POOL_ROOT: ""` so pools stay disabled in e2e regardless of ambient env). `alan/claude_cli.py`'s worker sandbox is no longer part of this regex-scanned list — see below for how its coverage is now checked structurally instead. The check is membership-only — it does not parse YAML/TS/Python or verify a token's *value*, only that the token string appears somewhere in the surface — so a new root added to production code and forgotten in one CI workflow, or removed from one surface but not another, fails this gate instead of silently leaking state into `~/.alan/` the next time that surface runs. `ci-deploy.yml` and `e2e-stress.yml` are deliberately excluded from the CI-workflow surfaces checked (see the dedicated sections below for why); the exclusion is enumerated explicitly in `tests/test_roots_registry.py::CI_WORKFLOWS` rather than inferred, so adding a fifth pytest-running workflow requires a conscious opt-in to (or documented opt-out of) the gate.

### Closed gap: `tests/conftest.py` never carried `ALAN_SLOT_POOL_ROOT` (2026-08-30)

`tests/conftest.py` was, until 2026-08-30, checked against `STATE_ISOLATION_ROOTS` rather than `CI_ISOLATION_ROOTS` — the one isolation surface held to the smaller group while every other surface (the four CI workflows, `server-env.ts`, `_worker_env()`) was held to the larger one. Because `STATE_ISOLATION_ROOTS` excludes `ALAN_SLOT_POOL_ROOT` and `ALAN_WORKTREE_REPO_ROOT` by construction, `tests/conftest.py` never set either token, and the gate checking it could never notice: it is membership-only, so a surface checked against a set that excludes a token passes cleanly no matter how badly that token leaks. This is the same incident shape as the 2026-07-16 `server-env.ts` fix above, replayed on the one surface that never received the equivalent upgrade.

The exposure was not confined to a handful of slot-pool tests. `alan.roots.slot_pool_root()` requires an explicit, non-empty environment value to return a path — nothing in the suite constructs a `SlotPool` directly — so the only route to production was the ambient environment flowing, unredirected, into every `TestClient`/application-lifespan boot in the suite, where pool construction and the reset-and-warm step both run before and outside the dispatcher-disabled gate. A test run launched with a real `ALAN_SLOT_POOL_ROOT` already exported in its shell (the shape a CI runner or an operator's own environment can produce) reached the live pool on every such boot, and the two cross-process protections that would ordinarily stop a foreign process — the boot-clean's job-queue check and the durable slot-hold/worker-record check — were both defeated *by* the test's own isolation: each reads a store the test had already redirected (`ALAN_QUEUE_DB_PATH`, `ALAN_STATE_ROOT`), so a foreign process saw an empty queue and zero reservations and was granted the clean.

Closed by widening the consumer, not the registry: `test_conftest_carries_every_state_isolation_root` became `test_conftest_carries_every_ci_isolation_root`, asserting `CI_ISOLATION_ROOTS` against `tests/conftest.py` instead of `STATE_ISOLATION_ROOTS`. `alan/roots.py` itself is untouched — neither token moved groups. `tests/conftest.py` now pins `ALAN_SLOT_POOL_ROOT` to `""` and `ALAN_WORKTREE_REPO_ROOT` to its synthetic per-session repo, both via unconditional assignment rather than the surrounding `setdefault` idiom — see "Assignment form: `setdefault` vs. unconditional" below for why that distinction is load-bearing here and invisible to the gate itself. (`test_conftest_carries_every_ci_isolation_root` itself was later retired, once the ten `STATE_ROOT_SUBDIRS` tokens stopped appearing as file-text literals — see the 2026-09-18 "Closed gap" section further below for its structural replacements.)

**Residual, accepted deliberately:** this closes the gap for every `pytest`-driven boot, but a second service instance started by hand — a restore drill, a staging environment, a scratch boot on another port, outside `pytest` and outside the four CI workflows — is not covered by any surface this gate checks, and inherits the ambient environment like any other unredirected process. That is protected by written convention only, with no gate behind it. A follow-up issue to give that path its own isolation is warranted; it is out of scope here because closing it would mean redirecting a hand-launched process's environment, not registering a token on an existing checked surface.

### Closed gap: `setdefault` on the ten `STATE_ROOT_SUBDIRS` tokens deferred to a fleet worker's own sandbox (2026-09-18)

The `setdefault` reasoning below — correct for `STATE_ISOLATION_ROOTS` because the production plist never exports any of those tokens — turned out to have a second live source, beside the plist, that the 2026-08-30 fix did not anticipate: a fleet worker's own gate subprocess. `alan/claude_cli.py::_worker_env()` populates every `STATE_ROOT_SUBDIRS` token with a per-worker sandbox path (`_worker_sandbox_root()`) before spawning that worker's `uv run pytest` gate (see "Worker subprocess parity" below) — so a backend suite run *as that gate* starts with all ten tokens already set in its ambient environment, to the worker's own sandbox rather than to nothing. `os.environ.setdefault(...)` is a no-op against an already-populated value, so the suite's `_SHARED_TEST_DIR` fallback never took effect there: the suite instead ran directly against the worker's own sandbox roots, shared across every test in that run and, since a worker's sandbox is keyed only by PID and can be reused across dispatches, potentially across runs too. Concurrent suites on different fleet workers could therefore read and write each other's leftovers, and a populated worker-sandbox `engines/` directory could carry a stale engine record into a boot that had no idea it was there — the exact shape `test_lifespan_starts_dispatcher_when_enabled` and its new sibling below guard against.

`tests/conftest.py` closes this the same way the 2026-08-30 fix closed the plist-sourced gap: by dropping `setdefault` in favor of unconditional assignment, generalized to a loop over `alan.roots.STATE_ROOT_SUBDIRS` (see "Assignment form" below) rather than nine hand-copied lines, so a future root added to the registry is defended automatically instead of requiring a matching hand-edit here. There is no CI-only carve-out and no new `ALAN_*` variable — the suite now provisions its own fresh per-session roots unconditionally on every host, including a developer's shell and a fleet worker's gate subprocess alike.

### Assignment form: `setdefault` vs. unconditional

Every `CI_ISOLATION_ROOTS` token in `tests/conftest.py` is now assigned unconditionally: the ten `STATE_ROOT_SUBDIRS` tokens via one loop keyed off `alan.roots.STATE_ROOT_SUBDIRS` (mapping the registry's `"."` subdirectory, used by `ALAN_DRIVER_LOOP_STATE_ROOT`, through a one-entry override so the on-disk layout stays `driver-loop-state` rather than colliding with `_SHARED_TEST_DIR` itself), plus `ALAN_SLOT_POOL_ROOT` and `ALAN_WORKTREE_REPO_ROOT` each on their own line as before. `os.environ.setdefault(...)` is no longer used anywhere in this block. This was previously *not* true for the ten `STATE_ROOT_SUBDIRS` tokens — they used `setdefault`, on the reasoning that `test_plist_excludes_state_isolation_roots` proves the production plist never exports any of those tokens, so there was no *plist-sourced* live value for `setdefault` to defer to. That reasoning missed the fleet-worker-sandbox source documented in the "Closed gap" section directly above, which is why all ten moved to unconditional assignment in the same change that closed it.

`ALAN_SLOT_POOL_ROOT` and `ALAN_WORKTREE_REPO_ROOT` were already unconditional before this change, for a related but distinct reason: production's rendered plist sets `ALAN_SLOT_POOL_ROOT` to a real path (`~/.alan/slots`), and an ambient `ALAN_WORKTREE_REPO_ROOT` leak resolves to whatever repository a foreign process happens to be running from — so for these two tokens, `setdefault` was a no-op in exactly the scenario it exists to guard against: an ambient value already present when the test process starts. Both are assigned unconditionally (`os.environ["ALAN_SLOT_POOL_ROOT"] = ""`, `os.environ["ALAN_WORKTREE_REPO_ROOT"] = str(_WORKTREE_REPO_DIR)`), overwriting whatever the ambient environment carried.

Because the ten `STATE_ROOT_SUBDIRS` tokens are now assigned through a loop over `alan.roots.STATE_ROOT_SUBDIRS` rather than as literal `os.environ[...]` string keys, their token strings no longer appear as text anywhere in `tests/conftest.py` — the same shift `alan/claude_cli.py`'s worker sandbox went through earlier (see below), and for the same reason: a membership-only regex scan cannot see a token reached only through an imported mapping. `test_conftest_carries_every_ci_isolation_root` (which asserted `CI_ISOLATION_ROOTS` against `tests/conftest.py`'s file text) is retired for exactly this reason and replaced by three checks in `tests/test_roots_registry.py`: `test_conftest_defends_every_state_root_subdir_token`, an in-process assertion that every `STATE_ROOT_SUBDIRS` token is currently set in `os.environ` to a value rooted under the suite's shared per-session temp dir; `test_state_root_env_is_defended_flags_a_synthetic_undefended_token`, a negative control proving that same check can actually fail, using a synthetic token that is never real; and `test_conftest_overrides_every_poisoned_ambient_state_root_subdir`, which spawns a child interpreter with all ten tokens pre-set to a poisoned ambient path (simulating the fleet-worker-sandbox scenario above), imports `tests.conftest`, and asserts every one of them was overwritten rather than deferred to. `ALAN_SLOT_POOL_ROOT` and `ALAN_WORKTREE_REPO_ROOT` keep their pre-existing coverage unchanged: they remain literal assignments (so `_assert_carries` still finds them textually), and `test_conftest_neutralizes_a_leaked_ambient_slot_pool_root` / `test_conftest_overrides_a_leaked_ambient_worktree_repo_root` still pin their unconditional-assignment form the same way they always have.

Both Python consumers of the registry now derive their lists rather than restating them: `engine_config._RESERVED_SANDBOX_ROOT_ENVS` is `alan.roots.STATE_ISOLATION_ROOTS` (an identity, not a copy), and `alan/claude_cli.py`'s `_WORKER_SANDBOX_ROOT_ENVS` is `alan.roots.STATE_ROOT_SUBDIRS`, with the module's own local `ALAN_SLOT_POOL_ROOT` constant folded into `alan.roots.SLOT_POOL_ROOT_ENV`. There is now exactly one authoritative list of these tokens. Because the literal token strings no longer appear anywhere in `claude_cli.py`, the regex scan above can no longer see them, so `claude_cli`'s surface check became structural instead of textual: `test_claude_cli_worker_env_carries_every_ci_isolation_root` (`tests/test_roots_registry.py`) deletes every `CI_ISOLATION_ROOTS` token from the process environment and asserts `_worker_env()` puts them all back, with `ALAN_SLOT_POOL_ROOT` additionally asserted via a literal the test owns so the check can never compare the registry to itself; two `is`-identity tests pin both derivations so a future re-typed literal fails immediately.

`alan/roots.py` also defines `INFRA_ROOTS` — currently just `ALAN_SLOT_REPO_ROOT`, the slot pool's git clone source (`docs/architecture/slot_pool.md`) — for real, documented `ALAN_*_ROOT` env vars that are deliberately *not* part of the CI-isolation surfaces above: CI already disables the slot pool entirely via `ALAN_SLOT_POOL_ROOT: ""`, so `alan.roots.slot_pool_root()` short-circuits before `ALAN_SLOT_REPO_ROOT` is ever read there, and threading it through the four CI workflows would add coverage for a var CI never consults. `ALL_KNOWN_ROOTS` (`CI_ISOLATION_ROOTS | INFRA_ROOTS`) backs two more gates that close the membership-only check's remaining blind spot — a root registered nowhere previously passed every surface test silently:
- `test_no_undocumented_root_env_in_source` regex-scans every `alan/**/*.py` file and fails if it finds an `ALAN_*_ROOT` token outside `ALL_KNOWN_ROOTS`, so a brand-new root a future change forgets to register in `alan/roots.py` fails immediately instead of shipping unregistered and unchecked by every other test in this file.
- `test_plist_excludes_state_isolation_roots` asserts `deploy/ai.alan.plist` carries none of `STATE_ISOLATION_ROOTS` — the production plist is deliberately unredirected (see "ci-deploy.yml" below), so an accidental `ALAN_STATE_ROOT`-shaped key leaking into the plist would silently sandbox the live service instead of failing CI.

This registry only covers the `_ROOT`-suffixed subset. For the full committed classification of every `ALAN_*` var read by `alan/` Python source (isolation vs. named excepted-config, with per-bucket counts), see `tests/env_var_classification.py`; `tests/test_env_var_classification.py` is the static gate enforcing that no new `ALAN_*` var reaches `main` without a classification.

The `run_id-run_attempt` suffix makes the path unique per workflow run and per re-run attempt, so concurrent runs of different workflows (e.g. `tests.yml` and `hotspots.yml` running simultaneously on the same machine) cannot share a `queue.db`, workspace root, or state directory.

`ALAN_SLOT_POOL_ROOT: ""` explicitly disables the slot pool in CI. `alan.roots.slot_pool_root()` treats an empty string as unset — it returns `None` and the pool is never created. A CI job therefore can never claim a slot from the production pool, even though the pool root is configured to a real path in the plist.

In practice the tests do not write to these paths either: the pytest conftest already redirects `ALAN_LOGS_ROOT` and `ALAN_QUEUE_DB_PATH` per-test via `monkeypatch`, and the Playwright e2e suite uses `~/.alan-playwright/` (see `docs/architecture/e2e_testing.md`). The CI env vars are a backstop that prevents any un-redirected access from reaching `~/.alan/`.

## Root resolver seam

`alan/roots.py` registers eleven `ALAN_*_ROOT` tokens (`ALL_KNOWN_ROOTS`) but, until H3.1, held only their names — every call site resolved its own token independently, via a copy-pasted `os.environ.get(TOKEN, "").strip()` prologue. H3.1 adds a call-time resolver function per token directly on the registry, so the token's environment-or-default logic lives in exactly one place. Resolvers take no arguments and read the environment **at call time, never at import time** — the same invariant the individual call sites already honored (the #466 bug shape: an import-time read freezes a default before a test or worker has a chance to redirect it). Call sites keep their own injected-root-wins prologue (e.g. an explicit `root: Path | None` constructor argument that overrides everything); the seam is only the environment-or-default tail.

The eleven tokens split into three tiers by return shape:

- **Tier A — the ten state roots** (`ALAN_WORKSPACES_ROOT`, `ALAN_LOGS_ROOT`, `ALAN_STATE_ROOT`, `ALAN_BUILD_CHAT_SESSIONS_ROOT`, `ALAN_EXPLORE_CHAT_SESSIONS_ROOT`, `ALAN_PROJECTS_ROOT`, `ALAN_SECRETS_STORE_ROOT`, `ALAN_ENGINES_ROOT`, `ALAN_PLANS_ROOT`) each resolve to `-> Path`, total, never absent: an empty string counts as unset, and the default is `Path.home() / ".alan" / <subdir>` — byte-identical to every scattered fallback it replaces. The token-to-subdirectory mapping is exported as data, `STATE_ROOT_SUBDIRS: Mapping[str, str]`, with `STATE_ISOLATION_ROOTS` now *derived* as `frozenset(STATE_ROOT_SUBDIRS)` rather than hand-duplicated — the derive-don't-enumerate payoff a later roadmap item (H3.3) harvests to build the duplicate CI/e2e root lists from the same source of truth. All ten are written as explicitly named two-line functions (`workspaces_root()`, `logs_root()`, …) delegating to one private `_state_root(token, subdir) -> Path` helper — not generated dynamically via a dict-of-callables or `__getattr__` — so every resolver stays greppable for the follow-on migration (H3.2), checkable under pyright strict, and holds at branch-count 2 instead of the ~18 a single dispatch function would need.
- **Tier B — `ALAN_SLOT_POOL_ROOT`** resolves to `slot_pool_root() -> Path | None`, with **no default**. Unset is semantically meaningful — it means slot pooling is disabled — and `alan/web/e2e/fixtures/server-env.ts` sets it to `""` deliberately for exactly that reason (see the 2026-07-16 slot-destruction incident above). A home-anchored default here would silently re-enable pooling in every isolated test/CI/worker environment; this is a hard behavioral constraint, not a style choice. This absorbs the old bespoke `alan/slot_pool.py::resolve_slot_pool_root()`, which is deleted; its sole consumer, `alan/routes/infra.py`, now imports `alan.roots.slot_pool_root` directly.
- **Tier C — `ALAN_SLOT_REPO_ROOT`** resolves to `slot_repo_root() -> str | None`, environment-read only, and — unlike every other resolver in the registry — is not `Path`-typed (see the caveat below for why). Its existing non-environment fallback — a `git rev-parse --show-toplevel` subprocess with a 30s timeout — deliberately stays with its current owner, `alan/slot_pool.py::resolve_repo_root()`, and is **not** moved into `alan/roots.py`: the registry is the bottom of the import-layer stack and must stay dependency-free (stdlib-only — `os`, `pathlib`, `collections.abc`), and a subprocess call is exactly what would make a bottom layer unimportable from itself and unsuitable as a dependency-free seam.

**A load-bearing caveat on Tier C, found while implementing this item's exemplar migration, not merely anticipated:** `ALAN_SLOT_REPO_ROOT` holds either a local filesystem path *or* a GitHub HTTPS URL (`deploy/ai.alan.plist` holds the `__ALAN_SLOT_REPO_URL__` placeholder, which `deploy/render_plist.sh` fills with the install's GitHub HTTPS URL). `pathlib.Path` cannot round-trip a URL: `Path("https://github.com/x/y.git")` collapses the scheme's `//` into a single `/` at construction time (`PurePath` parses on `/` and drops empty segments between consecutive separators), and no subsequent `str()`/`as_posix()` call recovers it — this is a permanent, version-independent property of `pathlib`, not a stripping or whitespace artifact. `alan.roots.slot_repo_root()` is therefore typed `-> str | None`, not `-> Path | None` like every other optional resolver: it returns the raw, stripped environment value and never routes it through `Path`, so calling it can never silently corrupt a URL, regardless of who calls it or when (`tests/test_roots_registry.py::test_slot_repo_root_returns_url_verbatim` pins this). `alan/slot_pool.py::resolve_repo_root()` — which must return the exact original string, hence its own pre-existing `-> str | None` signature and its own doc note "carried as a `str`, never a `Path`, because `pathlib.Path` collapses `https://` → `https:/`" (`docs/architecture/slot_pool.md`) — now delegates its env-read prologue to `alan.roots.slot_repo_root()` directly: both sides are `str | None`, so no adaptation was needed, and its own `git rev-parse --show-toplevel` fallback stays exactly where it was — the registry remains dependency-free. `tests/test_slot_pool.py::test_resolve_repo_root_returns_url_verbatim` pins the same URL-preserving behavior on `resolve_repo_root()` itself. `alan.roots.slot_repo_root()` still exists, still satisfies "a resolver exists for every registered token," and is directly unit-tested (`tests/test_roots_registry.py`) — and, with `alan/slot_pool.py::resolve_repo_root()` now delegating to it, it is no longer a type hazard on the seam itself, nor a resolver with zero production consumers. **H3.2 must budget for the same str-typed treatment on any other token whose value can be a URL** — never assume a bare `Path(str(...))` round-trip is safe; verify against the token's actual value shape first.

**The gate's four-way classification of environment access** (`tests/test_no_raw_root_resolution.py`, backed by `tests/raw_root_resolution.py`) prevents new raw resolutions of a *registered root* from reappearing once a call site has migrated, without demanding every `os.environ`/`os.getenv` touch in `alan/` route through the seam — that floor (~47 modules touch the environment at all) would make a later item's goal of an empty allowlist unreachable by construction. Each access is classified, fail-closed:

1. **Bulk or whole-environment access** (`dict(os.environ)`, `{**os.environ, ...}`, `x in os.environ`) — out of scope; no single token is being resolved, so there is nothing to classify.
2. **Writes** (`os.environ[k] = v`, `.setdefault`, `.update`, `.pop`, `del os.environ[k]`) — exempt; a write cannot leak a stale root value.
3. **Scalar read with a string-literal key** — in scope *only if* that literal is a member of `alan.roots.ALL_KNOWN_ROOTS`; a literal non-root read (a timeout, a TTL, a credential env var name) needs no allowlist entry at all. In-scope modules are grandfathered in `RAW_ROOT_RESOLUTIONS`.
4. **Scalar read with a non-literal key** (a `Name`, an f-string, an attribute lookup) — unprovable by static inspection, therefore **in scope by default**, requiring an explicit entry in `DYNAMIC_ENV_READS`. The gate does not attempt constant-folding an indirect token constant back to its literal value (e.g. resolving `os.environ.get(_STATE_ROOT_ENV)` by tracing `_STATE_ROOT_ENV = "ALAN_STATE_ROOT"`) — that would reach the same fail-closed verdict at a real complexity cost, for no gain: the point of case 4 is to fail closed onto *any* dynamism, not to see through the specific ones that happen to be provable.

Both allowlists are **tightening-only ratchets**, grandfathered at the module set measured by an AST walk at this item's branch point (`origin/main@5572e6a4`): `RAW_ROOT_RESOLUTIONS` drops from 22 to 21 (`alan/slot_pool.py`'s migrated Tier C read left it), `DYNAMIC_ENV_READS` drops from 33 to 31 (`alan/slot_pool.py`'s deleted Tier B read and `alan/engine_registry_store.py`'s migrated Tier A read both left it). A future PR may shrink either list as it migrates a module onto `alan.roots`, never grow one; raising either baseline is a `NEEDS-OWNER` decision and is not available to routine roadmap work. `alan/roots.py` itself is excluded from the walk — it is the seam these reads migrate *onto*, not a call site to migrate: all three environment reads in the module (`_state_root`, `_optional_root`, `_optional_root_str`) key off their `token` parameter, a `Name` node rather than a string literal, so all three are case 4 — there is no case-3 read anywhere in `roots.py` — and without the exclusion the registry would allowlist itself and a later item's empty-allowlist goal could never be reached.

**H3.2a (the `ALAN_LOGS_ROOT` tranche) migrated the twenty modules that resolved this token independently** — `alan/auto_continue.py`, `alan/auto_dispose.py`, `alan/dispatcher.py`, `alan/gold_label.py`, `alan/digest_sweep.py` (named `alan/inbox_sweep.py` at the time of this tranche; renamed by restore-propose-card-and-incident-disposition, 2026-09), `alan/incident_store.py`, `alan/loop_guard.py`, `alan/project_amendment.py`, `alan/project_auto_continue.py`, `alan/reconciler.py`, `alan/retention.py`, `alan/retention_registry.py`, `alan/routes/inbox.py`, `alan/routes/infra.py`, `alan/routes/workspaces.py`, `alan/teams/_base.py`, `alan/teams/_pr_branch.py`, `alan/teams/dependency_sweep.py`, `alan/teams/triage.py`, `alan/teams/verification.py` — onto `alan.roots.logs_root()`, deleting each module's private `_AUDIT_DIR_DEFAULT`/`_LOGS_DIR_DEFAULT` fallback constant (and, for `alan/teams/_pr_branch.py`, the public `AUDIT_DIR_DEFAULT`, a deliberate API removal — its sole consumer was a test). This ratchets `RAW_ROOT_RESOLUTIONS` 22 → 21 → **1**, leaving `alan/engine_config.py`'s `ALAN_STATE_ROOT` read as the sole remaining direct site; the follow-on tranche, H3.2b, closes it. **This substitution carries one genuine behaviour change, not a pure refactor:** the deleted constants froze `Path.home()` once, at module-import time, while `logs_root()` evaluates it fresh on every call — so a process that changes `HOME` after import (a test, a spawned worker) now follows the new value where the old constant would not. This is the seam's whole intent (the #466 call-time-resolution shape H3.1 established), and it is pinned by `tests/test_roots_registry.py::test_logs_root_resolves_at_call_time_not_import_time`, which monkeypatches `Path.home` after import and asserts both `roots.logs_root()` and `alan.teams._pr_audit_log.audit_dir()` follow. `DYNAMIC_ENV_READS` is untouched at 31 by this tranche — it closes via H3.2b's classifier narrowing, not by being emptied entry-by-entry — and `tests/conftest.py`'s per-test `_redirect_alan_logs_root` fixture contract is unchanged.

**The import-layer contract moves `roots` to the last position** in `pyproject.toml`'s `[tool.importlinter]` `layers` list (import-linter's layers contract allows an earlier-listed layer to import a later one, never the reverse). Three of the eleven token consumers — `secrets_store` (`ALAN_SECRETS_STORE_ROOT`), `engine_registry_store` (`ALAN_ENGINES_ROOT`), `engine_config` (`ALAN_STATE_ROOT`) — sat below `roots`'s old position and could not import it; without the move, three of the eleven resolvers would be born permanently unreachable from their own natural consumer. The move is safe and monotone: `roots` imports nothing (stdlib-only), so relocating it to the bottom only *widens* who is permitted to import it, and cannot introduce a new cycle.

**Known limitation, recorded rather than fixed here:** the registry is not yet authoritative over every environment variable this document treats as an isolation surface. `ALAN_QUEUE_DB_PATH` — set alongside every `STATE_ISOLATION_ROOTS` token in the CI workflow env blocks above and redirected per-test by the same `tests/conftest.py` machinery — is not a registered root token in `alan/roots.py`; it is a queue-database *file* path (not a directory root with a fixed subdirectory shape), resolved independently in `alan/routes/_deps.py`. Folding it into the registry, or deciding it structurally does not belong there, is out of scope for this item and left for a later one.

## Worker subprocess parity (production)

CI's `ALAN_SLOT_POOL_ROOT: ""` is also the value a production **worker** must run its gates under. The live `ai.alan` service sets `ALAN_SLOT_POOL_ROOT=~/.alan/slots` (rendered from `deploy/ai.alan.plist`'s `__ALAN_HOME__/.alan/slots` template token by `deploy/render_plist.sh`, see `docs/architecture/deploy.md`) so the host dispatcher can lease slots. A team's `claude` worker subprocess — which runs `uv run pytest` as a gate — is spawned via `subprocess.run` / `subprocess.Popen` in `alan/claude_cli.py` and would otherwise inherit that production value, making `_slot_pool_active()` return True *inside the test run* and failing the ~16 slot-pool-gated tests (the `tests/test_teams_verification_*.py` siblings, `test_teams_decomposer.py`, `test_dispatcher_usage_limit.py`) that CI — with the var empty — passes. The verifier then can't APPROVE and recycles `implementation_fix` against a failure its diff never caused.

To keep a worker's gate run identical to CI, both spawn points pass `env=_worker_env()`, where `_worker_env()` returns `{**os.environ, "ALAN_SLOT_POOL_ROOT": "", "ALAN_WORKTREE_REPO_ROOT": "", "CLAUDE_CODE_SUBPROCESS_ENV_SCRUB": "1"}`. Only the **child** env is overridden — the host process keeps the real `ALAN_SLOT_POOL_ROOT` (and any real `ALAN_WORKTREE_REPO_ROOT`), so slot leasing and the host-side `_slot_pool_active()` check (`alan/teams/verification.py`) are unaffected.

`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` is a directive read by the `claude` binary itself, not by `_worker_env()`'s own dict construction: per Claude Code's documented sandboxing behavior, it strips Anthropic and cloud-provider credentials (e.g. `ANTHROPIC_API_KEY`, AWS/GCP/Azure tokens) from the environment of every Bash-tool subprocess the worker's `claude` process spawns, fleet-wide, regardless of role. It deliberately does not cover `GH_TOKEN` or the `~/.claude` OAuth credential path — both stay in the worker's env because the worker's own model authentication (via `~/.claude`, reached through the preserved `HOME`) and its read-only `gh pr diff`/`gh pr view` lookups depend on them. This closes one leg of the rec#4 exfiltration chain identified by the auto-mode boundary audit — the credential-env leg — prophylactically: today's service environment carries no live Anthropic/cloud secret for a read-role worker to leak, so the near-term value is structural coverage against secrets added later, not sealing a currently hot one. The in-subprocess scrub itself happens inside the `claude` binary's own child-process spawning and cannot be observed or unit-tested from alan's own process; closure here rests on Claude Code's documented behavior (`https://code.claude.com/docs/en/sandboxing`) plus a test asserting the directive is set at the doc-verified value (`tests/test_claude_cli.py::test_worker_env_sets_subprocess_env_scrub`) and a companion test pinning that the load-bearing set — `PATH`, `HOME`, `GH_TOKEN`, and every sandboxed `ALAN_*_ROOT` — is not collaterally scrubbed (`test_worker_env_preserves_load_bearing_credentials_and_paths`). The larger permission-model/sandbox/deny-surface hardening (rec#4's egress leg, rec#5) remains owner-gated per PA7.1 and is untouched by this change.

`_worker_env()` additionally `pop`s every registered engine's env-fallback secret name from the child env, via `alan.engine_config.registered_secret_env_names()` (renamed from the forge-only `registered_forge_credential_env_names()`) — not just the default engine's `ALAN_VERIFIER_GH_TOKEN`. That resolver unions `ForgeConfig.credential_env_name` **and** `CodeQualityConfig.token_env_var` across every `EngineConfig` currently in `engine_config._registry` with the default engine's `_DEFAULT_FORGE.credential_env_name` and `_DEFAULT_CODE_QUALITY_TOKEN_ENV` (`SONAR_TOKEN`), so the default pair is always stripped even when nothing else is registered, and a second engine's distinct credentials (e.g. `ACME_WIDGET_GH_TOKEN`) are stripped too once that engine is registered. Generalizing past forge credentials closed a pre-existing leak: `SONAR_TOKEN` is read host-side only, by `alan/teams/_pr_sonar.py::sonar_ack_hotspots`, yet before this change it was never in the strip set, so it rode unstripped into every worker subprocess's `os.environ`. Credentials resolved from the new API-managed secrets store (`alan/secrets_store.py`, see `deploy.md`) need no strip entry here at all — `secrets_store.resolve_secret()` reads a store-only credential into a transient subprocess `env=` dict at the transport call site and never assigns it to `os.environ`, so it is structurally absent from a worker's inherited environment. This preserves per-engine secret isolation into the worker boundary: a leaked `gh` call from inside a worker subprocess can never authenticate as *any* engine's reviewer bot, not merely the default's, and a leaked SonarCloud API call can no longer authenticate at all. The production service holds the verifier bot PAT so the host-side review-posting path (`secrets_store.verifier_gh_env()`, in `alan/secrets_store.py` since X2.7 PR22, consumed by `alan/forge_gh.py` and `alan/teams/_pr_post.py` → `gh pr review` / `gh api POST .../reviews`) can post as `alan-verifier`; that path reads the secrets store and then `os.environ` in the service process and is unaffected by `_worker_env()`, which only touches the spawned worker's env. But the worker's `uv run pytest` gate must not carry any of these tokens: the verification test suite (`tests/_teams_verification_support.py::impl_handover`, called by the `tests/test_teams_verification_*.py` siblings) defaults its fixture to `pr_number=42` and exercises the live review-POST path with `ALAN_VERIFICATION_DRY_RUN` deleted, so any monkeypatch-escape that reaches a real `gh` call would post a junk review to the long-merged PR #42 as the verifier bot — each one firing the `auto-merge-label.yml` workflow. Stripping the token (parity with CI, which never carries it) makes such a leaked call fail to authenticate as the bot instead of posting. This is defense-in-depth; the loud-failure test-isolation guard is tracked separately.

Finally, `_worker_env()` redirects every root in `alan.roots.STATE_ISOLATION_ROOTS` — `ALAN_WORKSPACES_ROOT`, `ALAN_LOGS_ROOT`, `ALAN_STATE_ROOT`, plus the two chat-session roots `ALAN_BUILD_CHAT_SESSIONS_ROOT`, `ALAN_EXPLORE_CHAT_SESSIONS_ROOT`, `ALAN_PROJECTS_ROOT`, `ALAN_SECRETS_STORE_ROOT`, `ALAN_ENGINES_ROOT`, and `ALAN_PLANS_ROOT` — to a per-host-process sandbox at `<tmpdir>/alan-worker-<pid>/{workspaces,logs,state,build-chat-sessions,explore-chat-sessions,projects,secrets,engines,plans}` (`_worker_sandbox_root()`). This gives a worker's `uv run pytest` gate the same categorical inability to mutate the live `~/.alan/` tree that CI gets from its `/tmp/alan-ci/<run>/` overrides, and it closed a real production leak: gate runs whose tests were imperfectly isolated (e.g. `dependency_sweep` minting `dep/<N>` workspaces through `workspace.create(root=None)`) were writing fake `dep-*` workspaces and `dep_sweep_audit.jsonl` rows straight into `~/.alan/`, growing a `dep-N`/`dep-N-2`/`dep-N-3` suffix ladder on every restart. The redirect only bites once `alan/workspace.py::_root(None)` honors `ALAN_WORKSPACES_ROOT`. Historically `_root` returned a hardcoded `WORKSPACES_DIR` constant unconditionally, so even the pytest conftest's own `ALAN_WORKSPACES_ROOT` override (`tests/conftest.py`) was a silent no-op for workspace creation; that constant is gone as of H3.2b. `_root(root)` is now `return root if root is not None else roots.workspaces_root()` — there is no `WORKSPACES_DIR` fallback constant anywhere in `alan/workspace.py`, and the env-var-or-default logic lives solely inside `alan.roots.workspaces_root()`. Production is unaffected because the plist sets none of these roots, so the host resolves them to their real `~/.alan/` defaults. `ALAN_PROJECTS_ROOT` joined this sandbox dict (and the CI workflow env blocks, and `tests/conftest.py`) once `tests/test_roots_registry.py` caught it missing. `ALAN_PLANS_ROOT` joined the registry on 2026-08-19 after a maintenance health-check found 64 identical `ship-the-pipeline{,-N}.md` stub files in the production `~/.alan/plans`. `alan/teams/implementation_plan.py` held the last surviving import-time `PLANS_DIR = Path.home() / ".alan" / "plans"` constant — the one persistent store never migrated to a resolver — so every e2e and local run that exercised the implementation-plan team wrote a stub straight into production, and the collision-avoidance loop (`<slug>-<i>.md` for `i` in 1..100) turned that into unbounded growth rather than an overwrite. Nothing caught it because the module's own unit test bypassed the leak entirely: `monkeypatch.setattr(ipt, "PLANS_DIR", tmp_path)` redirected the constant instead of the env var, so the isolation surface it depended on was never exercised. `_write_plan` now calls `roots.plans_root()` at call time and the fixture sets `ALAN_PLANS_ROOT`, which is what makes `tests/test_roots_registry.py`'s membership checks load-bearing for this store. `ALAN_CHAT_SESSIONS_ROOT` — a stale key from the deleted standalone `alan/chat.py` store, with no reader anywhere in `alan/` — was retired from every surface in the same change; `alan.roots.STATE_ISOLATION_ROOTS` is now the single source of truth `tests/test_roots_registry.py` checks every surface against, so a future rename or removal fails the gate instead of drifting silently. The registry-membership tests above only check for *required* tokens, not forbidden ones, so they cannot catch an accidental re-add of the retired key; `tests/test_roots_registry.py::test_state_root_subdirs_excludes_retired_chat_sessions_root` is a direct negative assertion that `alan.roots.STATE_ROOT_SUBDIRS` excludes `ALAN_CHAT_SESSIONS_ROOT`, guarding the retirement itself.

**H3.2b: every root resolution in `alan/` now goes through `alan/roots.py`.** Before this change, seven modules (`alan/workspace.py`, `alan/project.py`, `alan/routes/_deps.py`, `alan/server.py`, `alan/teams/_pr_branch.py`, `alan/secrets_store.py`, `alan/_chat_core.py` and its three chat-store callers) each carried their own `_FOO_DIR = Path.home() / ".alan" / "foo"` constant plus a copy-pasted `os.environ.get(_FOO_ROOT_ENV, "").strip()` prologue. All seven are deleted; every one of those call sites now calls the matching `alan.roots` resolver (or, for `_pr_branch.py::state_dir()` and `secrets_store.py::store_root()`, delegates to `roots.state_root()` / `roots.secrets_store_root()` directly), and `tests/raw_root_resolution.py::RAW_ROOT_RESOLUTIONS` — the allowlist of modules still reading a registered root token as a direct string literal — is now empty. The companion classifier (`tests/test_no_raw_root_resolution.py`) was narrowed alongside this migration: it now folds a name assigned exactly once, at module level, to a string-literal constant, and classifies a read through that folded name exactly as it would classify a direct literal read of the same value. This is why a large share of `DYNAMIC_ENV_READS` entries disappeared in the same change even though those modules were not touched — most of them read the environment through an `_FOO_ENV = "ALAN_SOME_NON_ROOT_VAR"` module constant a few lines above the read, which the classifier can now see through and correctly bucket as "no entry needed" rather than "unprovable." A future `_FOO_ROOT_ENV = "ALAN_STATE_ROOT"` module constant feeding `os.environ.get(_FOO_ROOT_ENV)` therefore fails the gate as a RAW literal-root hit — case 3, not case 4 — instead of hiding in the dynamic bucket the way it would have before this narrowing.

## `ALAN_WORKTREE_REPO_ROOT`: isolating the repository a bare (non-pooled) worktree operates on

`alan/worktree.py::implementation_worktree` resolves which checkout a test-spawned or pooling-off backend runs its git operations against from `repo_root or worktree_repo_root() or _repo_root()`. Before this token existed, the `_repo_root()` fallback shelled out to `git rev-parse --show-toplevel` with no `cwd=` argument, resolving to whatever directory the process's ambient cwd happened to be — the developer's or fleet worker's own live checkout when the slot pool is disabled. `_bare_worktree()` then pruned and rewrote that checkout's worktree registry, force-created and force-moved local `teams/<task_id>-<inv_id>` branch refs there, and created/force-removed an untracked (gitignored) directory under its `.worktrees/` — all invisible to an ordinary `git status`. Production never takes this path while its slot pool is configured (`ALAN_SLOT_POOL_ROOT` is set to a real path in the rendered plist), so the exposure was confined to the two test suites and any other instance run with the slot pool disabled.

`ALAN_WORKTREE_REPO_ROOT` follows the **state-root convention** — `alan.roots.worktree_repo_root()` is built on `_optional_root`, the same unset-or-empty-falls-back-to-ambient shape as every `STATE_ROOT_SUBDIRS` resolver — not the pool convention (`slot_pool_root()`), where an empty string means "off" and is read as a deliberate disable switch. Here, empty or unset simply means "no explicit input; keep resolving the same way this code always has." This is why the token is registered in `CI_ISOLATION_ROOTS` (alongside `ALAN_SLOT_POOL_ROOT`) rather than in `STATE_ROOT_SUBDIRS`: `STATE_ROOT_SUBDIRS` resolvers all default to a `~/.alan/<subdir>` path, which has no meaning for "which repository," while `CI_ISOLATION_ROOTS` is exactly the bucket of tokens every isolation surface (CI workflow envs, `tests/conftest.py`, `server-env.ts`, `_worker_env()`) must carry, with `tests/test_roots_registry.py`'s structural membership checks enforcing that for free once the token is added to the registry.

Registered in the same change: `alan/roots.py` (`WORKTREE_REPO_ROOT_ENV`/`worktree_repo_root()`, folded into `CI_ISOLATION_ROOTS`); `tests/conftest.py` (a session-scoped synthetic repo at `_SHARED_TEST_DIR/worktree-repo`, `git init` + one empty commit, registered via unconditional assignment — **not** `os.environ.setdefault`, despite matching the surrounding idiom at the time this token was first added: `_optional_root` falls through to the ambient checkout on an empty *or* unset value, so `setdefault` would have been a no-op the instant an outer harness already exported the token, which is precisely the leak scenario closed on 2026-08-30 above); `.github/workflows/tests.yml`, `boundary-smoke.yml`, `hotspots.yml`, and `behavioral_eval.yml` (`ALAN_WORKTREE_REPO_ROOT: ""` in each top-level `env:` block — all four are checked by `tests/test_roots_registry.py::test_ci_workflow_carries_every_isolation_root` against the full `CI_ISOLATION_ROOTS` set, so all four needed the token even though only `tests.yml` also wires the proving gate below); `alan/web/e2e/fixtures/server-env.ts` (`ensureWorktreeRepo`, one edit that every Playwright config funnels through — see `e2e_testing.md`); and `alan/claude_cli.py`'s `_worker_env()` (`WORKTREE_REPO_ROOT_ENV: ""`, the drift-gated edit, symmetric with how `ALAN_SLOT_POOL_ROOT` is neutralized in a worker's own gate subprocess).

**CI behavioral delta from the 2026-08-30 fix:** `.github/workflows/tests.yml` (and its three siblings) already set `ALAN_WORKTREE_REPO_ROOT: ""` at the job level, so before this change a `pytest` process running under CI resolved `worktree_repo_root()` to `None` and fell through to `_repo_root()` — the ambient-cwd `git rev-parse --show-toplevel` behavior — exactly as it always had. `tests/conftest.py` previously never touched the token at all (it was outside the checked set), so the job-level empty string was the only assignment in effect. Now that `tests/conftest.py` assigns the token unconditionally to its synthetic per-session repo, it wins over the job-level `env:` block inside every `pytest` process, and CI resolution changes for the first time: any test exercising `implementation_worktree`/`_bare_worktree` now operates against the synthetic `_SHARED_TEST_DIR/worktree-repo` rather than the CI job's own checkout. `scripts/git_state_gate.py` (the proving gate wrapping `tests.yml`'s `uv run pytest` step) is unaffected in what it snapshots — the synthetic repo lives outside the checkout it watches — but this is the one place in this change where CI-observed behavior, not just local `pytest`, actually moves; a green `tests.yml` run is a required precondition for merging this fix, not an optional local corroboration.

**The proving gate (`scripts/git_state_gate.py`) asserts git *state*, not git *invocations*.** It snapshots the repo's git state before and after wrapping a command, and fails the wrapped command's own exit code closed (returns `1`) if anything in the snapshot moved — even when the wrapped command itself exited 0. It is deliberately **not** an assertion that `git worktree add`/`git branch` were never called (`alan/served_sha.py` reads `HEAD` from the package-derived checkout dir on every server boot by design, so an invocation-level gate would red-light immediately with no defect present). What it snapshots: the full `refs/heads` set matching `teams/e2e-impl-*`, `teams/e2e-wf-*`, and `e2e-stub-pr-branch*` (production's live branch-naming scheme is `teams/{task_id}-{inv_id}`, so scoping to these three e2e-only patterns — rather than the entire `refs/heads/teams/` namespace — is what stops a concurrent fleet worker's own legitimate branch from flaking the gate) plus `refs/remotes/origin/main`, and the `.worktrees/` registry (`git worktree list --porcelain`, filtered to paths under `<repo>/.worktrees/`) and the raw directory listing of `<repo>/.worktrees/` itself as a filesystem-level backstop. What it does **not** assert: anything about the working tree's tracked-file contents (an ordinary `git status`-visible change), and nothing about `origin/main` actually moving — the browser suites' generated `GIT_CONFIG_GLOBAL` rewrites the forge host to a local path that doesn't exist, so `git fetch origin main` fails there and `_resolve_base_ref` falls back to the local HEAD sha; the ref stays in the gate's scope anyway as a backstop, not as the load-bearing part of the proof. The gate wraps both test commands (`uv run pytest`, and the various `playwright test` invocations) rather than adding a new CI job, invoked as `uv run python scripts/git_state_gate.py -- <command...>`; it does not force the wrapped command's working directory to the repo root — the wrapped subprocess inherits the gate's own ambient cwd (so, for example, `playwright test` still runs from `alan/web` when wired into an `alan/web/package.json` script or an `alan/web`-scoped CI step), while the gate's own git snapshot commands always run against the resolved repo root explicitly.

## ci-deploy.yml: production deploy is not subject to isolation

A workflow that deploys the live service runs against the production checkout by design, redirects no ALAN state path, and is therefore excluded from the CI-workflow surfaces `tests/test_roots_registry.py` checks.

## e2e-stress.yml: isolated through server-env.ts, not a top-level env block

`e2e-stress.yml` (like `tests.yml`'s `e2e-frontend` job) never runs `uv run pytest` directly against `alan/` — it drives the built frontend against a real FastAPI server that Playwright's global setup spawns per worker, with each worker's full env built by `alan/web/e2e/fixtures/server-env.ts::serverEnv()` from a per-worker root under `ALAN_E2E_ROOT` (see `docs/architecture/e2e_testing.md`). That function — not a workflow-level `env:` block — is where `CI_ISOLATION_ROOTS` isolation for e2e is enforced and where `tests/test_roots_registry.py` checks it. `e2e-stress.yml` therefore has no top-level `ALAN_*_ROOT` block to check and is excluded from the CI-workflow surfaces in `tests/test_roots_registry.py::CI_WORKFLOWS` for the same reason `e2e-frontend` in `tests.yml` is never itself a checked surface — both isolate via `server-env.ts`, already covered.

## Stage-driven AI-assisted testing is additional, not a replacement

Any AI-assisted or shared-environment testing lane is **additional to, never a replacement for**, the per-worker isolated e2e suite described above: each Playwright worker still spins up and tears down its own FastAPI server against its own `ALAN_E2E_ROOT`, with `server-env.ts::serverEnv()` building that worker's isolated env exactly as documented above. One shared test environment reintroduces exactly the shared mutable state that per-worker isolation removed; it must never substitute for a worker's own isolated server, only run alongside it.

## Summary of isolation properties

| Concern | Mechanism |
|---|---|
| Stale files from prior job/PR | `clean: true` on `actions/checkout` (explicit) |
| Network download cost after clean | `UV_CACHE_DIR` set to an absolute path under the runner user's home (persistent, off `/tmp` so midnight maintenance can't corrupt it, concurrent-safe) |
| Production workspace/queue write | `ALAN_WORKSPACES_ROOT`, `ALAN_QUEUE_DB_PATH` → `/tmp/alan-ci/<run_id>-<attempt>/` |
| Production logs write | `ALAN_LOGS_ROOT` → `/tmp/alan-ci/<run_id>-<attempt>/logs` |
| Production state write | `ALAN_STATE_ROOT` → `/tmp/alan-ci/<run_id>-<attempt>/state` |
| Production chat-session write | `ALAN_BUILD_CHAT_SESSIONS_ROOT`, `ALAN_EXPLORE_CHAT_SESSIONS_ROOT` → `/tmp/alan-ci/<run_id>-<attempt>/...` + conftest setdefaults |
| Production project write | `ALAN_PROJECTS_ROOT` → `/tmp/alan-ci/<run_id>-<attempt>/projects` + conftest setdefault |
| Production secrets-store read/write | `ALAN_SECRETS_STORE_ROOT` → `/tmp/alan-ci/<run_id>-<attempt>/secrets` + conftest setdefault |
| Cross-run contamination | Per-run path (`run_id-run_attempt`) keeps concurrent workflow runs isolated |
| Production slot pool claim | `ALAN_SLOT_POOL_ROOT: ""` (pool explicitly disabled) |
| Drift between isolation surfaces | `alan/roots.py` registry + `tests/test_roots_registry.py` structural gate (see above) |
| launchd env leakage | Runner process is not a launchd child; env spaces are disjoint |
| Tests exec the real `claude` CLI | `tests/conftest.py` autouse guards (see below) |
| Tests spawn the real `gh` (any verb, read-only included) | `tests/gh_guard.py` stub + shrink-only baseline ratchet (see below) |
| A bypass reaches a real `gh` with the operator's credentials | `tests/bin/gh` first on `PATH`, empty `GH_CONFIG_DIR`, ambient `GH_TOKEN`/`GITHUB_TOKEN` popped at conftest import (see below) |

## Tests must never exec the real `claude` binary

Wherever the real `claude` CLI is installed (the
live service needs it), any test that reaches a `claude_cli` spawn primitive
without mocking would launch a real Claude Code process. The
`alan.manager_summary.trigger_manager_summary` daemon is fire-and-forget: it
starts a background thread that outlives a per-test `monkeypatch`, so per-test
mocks cannot catch it — every backend `pytest` run leaked ~one real `claude` per
dispatcher test that reached a terminal status, which OOM-froze the host.

Two autouse guards in `tests/conftest.py` make this structurally impossible:

- `_no_real_manager_summary_spawn` (function scope) no-ops
  `manager_summary.trigger_manager_summary` for the whole suite;
  `tests/test_manager_summary.py` restores the real function locally because
  exercising the daemon is that file's job.
- `_forbid_real_claude_spawn` (session scope) wraps `subprocess.run` /
  `subprocess.Popen` and raises `RuntimeError` when `argv[0]` is `claude`,
  delegating every other subprocess untouched by that half of the guard.
  Session scope survives per-test teardown, closing the daemon-thread race a
  function-scoped guard cannot. Tests that assert on the built argv override
  `subprocess.run` / `Popen` themselves and win during their own run.

The same fixture's other half guards `gh`. It used to permit any `gh`
invocation not matching an enumerated deny-list of mutating subcommands and
HTTP methods — a shape that stayed exposed to every verb nobody had enumerated
yet, and that misclassified a GraphQL mutation as a read whenever the call
carried no HTTP method flag (which every `gh api graphql` call does, since
GraphQL is method-less by nature). `tests/gh_guard.py` inverts this: `classify()`
positively recognises a subcommand as read-only (`READ_ONLY_GH_SUBCOMMANDS`),
recognises a non-GraphQL `api` call as an explicit-safe-method or
field/input-free read, or recognises a `gh api graphql` call's
`-f`/`--raw-field query=` document as a `query` (never a `mutation`, and never
the bare-brace anonymous-query shorthand); everything else is a refused write.
A refusal raises `GhGuardBlocked`, a direct `BaseException` subclass —
deliberately not an `Exception` subclass — so that a broad `except Exception`
in application code (of which this repository has several) cannot swallow the
refusal and let the test pass green while the mutation was still attempted.

**Since 2026-09-14 a recognised read is not spawned either.** Until then the
guard delegated permitted reads to the real `subprocess.run`, and on any host with an
authenticated `gh` login that meant ~186 tests (the route tests that reach `scan_predispatch` →
`_pr_branch.list_open_prs` and `collision._fetch_prs` through
`run_in_threadpool`, plus the implementation_fix tests that reach
the process runner — `_pr_branch.run_subprocess` then, `process_runner.run_subprocess`
since X2.7 PR22) made ~320 real `gh pr list`/`pr view`/`pr diff`/
`gh api` calls per full-suite run, ≈2,000 GraphQL points — enough, at fleet-scale
full-suite run rates, to exhaust the account's 5,000-point hourly budget. CI never saw it because its `HOME` is sandboxed (below).
Now `_guarded_run` returns a synthetic
`CompletedProcess(returncode=GH_STUB_RETURNCODE (86), stdout="", stderr=GH_STUB_STDERR)`
for every recognised read — the exact "gh unavailable" branch every production
wrapper already handles and that an unauthenticated CI `gh` has always
produced; the stderr text is chosen to match none of
`alan/teams/_forge_errors.py`'s rate-limit/auth/network markers, so the stub can
never be mistaken for a forge outage. Any `gh` reaching `subprocess.Popen` is
refused outright (`popen_refusal`): production spawns `gh` only through
`subprocess.run`, so a `Popen` gh is a new spawn site or a bypass. Because
CPython's `subprocess.run` calls the module-global `Popen`, a fall-through in
the run guard would still hit the fail-closed `Popen` guard.

Each stubbed read is recorded (`record_stubbed_read`) against the current
test's function-level key (`baseline_key(nodeid)`, parametrisation stripped).
The function-scoped autouse `_gh_read_ratchet` fails any test that stubbed a
read unless the key is listed in `tests/gh_read_baseline.py::GH_READ_STUBBED_TESTS`
or the test requested the `expect_gh_read_stub` fixture (for tests whose
purpose is the stub itself). The failure text names the seam to mock
(`alan.collision.check_collision`, `alan.predispatch_scan.list_open_prs`,
`alan.process_runner.run_subprocess`); the stub's own stderr carries the same
hint, verbatim: "gh stubbed by tests/gh_guard.py: alan's test suite never runs the
real gh. Mock the call (alan.collision.check_collision,
alan.predispatch_scan.list_open_prs, or alan.process_runner.run_subprocess)
instead of relying on this stub." The baseline is the legacy list
captured once; it only shrinks, is hand-edited, has no regeneration mechanism,
and `tests/test_gh_read_baseline.py` fails when an entry no longer names an
existing test function or the module stops being literal data. To find the
current offenders run the suite in write mode —
`GH_READ_BASELINE_WRITE=/tmp/gh-reads.txt uv run pytest --no-cov`, then
`sort -u /tmp/gh-reads.txt` — and delete every committed entry the fresh
output no longer contains. `_fail_on_background_thread_gh_guard_block`
(function scope) still drains refusals raised on anyio worker threads, which
cannot fail the test on their own. Resolving a refused write or an unlisted
read means mocking it in that test; widening the allow-list, appending to the
baseline, or requesting `expect_gh_read_stub` to silence a real leak defeats
the guard and is treated as a regression, not a fix.

## Belt and braces for fleet slots

The in-process guard covers every spawn that goes through `subprocess.run` /
`Popen` (all 65 production `gh` call sites do). Three import-time steps in
`tests/conftest.py` cover what it cannot: a test that installs its own real
`subprocess.run`, a child process that itself runs `gh`, or a future spawn
primitive. `tests/bin` (holding `tests/bin/gh`, a three-line `sh` script that
prints a refusal naming itself and exits 86 — the same code as the in-process
stub, so downstream handling is identical) is prepended to `PATH`;
`GH_CONFIG_DIR` points at an empty per-process directory under the shared test
tmp dir, so a real `gh` reached by any bypass finds no stored login and refuses
to run before touching the network (and the directory's emptiness doubles as a
canary: a real `gh` writes its config files there); and
`strip_ambient_gh_credentials` pops `GH_TOKEN`, `GITHUB_TOKEN` and their
enterprise variants, which `gh` would otherwise prefer over the config file.
No `alan/` code reads an ambient `GH_TOKEN` — every call that needs a token
injects `env={"GH_TOKEN": ...}` from the secrets store — so nothing under test
loses anything. The per-test `_strip_verifier_gh_token` fixture stays narrow
(only `ALAN_VERIFIER_GH_TOKEN`), and `tests/test_conftest_safeguards.py` keeps
pinning that a test may still `monkeypatch.setenv("GH_TOKEN", ...)` for its
own run. `tests/test_conftest_safeguards.py` and `tests/test_conftest_claude_guard.py`
pin all three steps.

## Sandboxed HOME (outermost ring)

Env-var isolation depends on every fallback path staying correct: a bug in a
`root is not None` fallback guard or an `os.environ.get("ALAN_*_ROOT")` read
could defeat both per-test `root=tmp_path` arguments and every env var above.
The fallbacks are `Path.home() / ".alan" / ...` constants (19 call sites
across `alan/`), and on a CI runner that shares a machine with production, `Path.home()` is the
production home. A full-suite sweep run once leaked empty chat
sessions, fixture audit rows, and fake workspaces into the live `~/.alan`
exactly this way.

Defence-in-depth against exactly that fallback-resolution class of bug sits
one level below any of that logic: the backend pytest step in `tests.yml`
runs with

```yaml
env:
  HOME: /tmp/alan-ci/${{ github.run_id }}-${{ github.run_attempt }}/home
```

(`mkdir -p "$HOME"` as the first script line). `Path.home()` resolves via
`$HOME`, and no absolute home-directory literal exists in `alan/`, so every
fallback lands inside the sandbox no matter what the fallback-resolution code
does. Side benefits: an escaped `gh` or `claude` invocation finds
no `~/.config/gh` or `~/.claude` credentials and fails fast instead of acting
as the production identity.

The isolation rings, outermost first:
1. **Sandboxed HOME** (step-level, backend pytest only) — defence-in-depth
   against a bug in the `root is not None` fallback paths themselves.
2. **Workflow env vars + conftest setdefaults** — correctness for the
   ordinary case.
3. **Call-time env reads in the fallbacks themselves** (`workspace._root`,
   `chat._root`, `_chat_core._base_dir`) — makes ring 2 effective at the
   fallback site (the #466 fix shape).

Scope: step-level only, never job-level — `actions/checkout`, `setup-uv`, and
`uv sync` keep the real HOME. A pre-pin step exports
`UV_PYTHON_INSTALL_DIR=${UV_PYTHON_INSTALL_DIR:-$HOME/.local/share/uv/python}`
into `$GITHUB_ENV` beforehand so `uv run`'s implicit sync never re-resolves
managed pythons under the fake home. Frontend and e2e jobs are exempt:
Playwright browsers live under `~/Library/Caches/ms-playwright` and npm's cache
under `~/.npm`. All backend git-committing tests set repo-local
`user.name`/`user.email`, so no test depends on `~/.gitconfig`.
