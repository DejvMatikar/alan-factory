# merge_recovery

`alan/merge_recovery.py` — typed PR-merge blocker classification and mechanical recovery ladder.

## Purpose

Improves autonomous PR merge success rate by attempting mechanical recovery before escalating to `implementation_fix` or human review. Sits between `_enforce_pr_merge_gate` in `dispatcher.py` and the remediation routing decision.

## CheckOutcome — fail-closed named-check resolution (relocated to `alan/teams/_pr_ready.py`)

`CheckOutcome`, `resolve_named_check_outcome`, and `resolve_check_outcome` live in `alan/teams/_pr_ready.py`, beside `PrReadiness` — not in this module. `merge_recovery.py` imports them. This keeps the enum next to the `PrReadiness.passing_checks` set it resolves against, and lets `alan.teams._clause_actionability` (the acceptance-clause audit's actionability classifier — see [acceptance_gate.md](acceptance_gate.md)'s "A required check's conclusion may now be consulted — narrowly" section) reuse the *named* resolution without pulling in this module's Sonar-specific authoritative-check gating.

`classify_block` and `needs_sonar_annotations` take a **required** positional `forge_target: ForgeTarget`; `reconcile_attempts_exhausted` and `attempt_mechanical_recovery` take it **required and keyword-only** (after `attempt_mechanical_recovery`'s still-defaulted `annotations`). There is no default: leaving the target out is a type error rather than a silent fall back to alan's own repository. This module stays pure: it accepts a `ForgeTarget` as a parameter and never reaches into the dispatcher or resolves a workspace's pinned engine itself; wiring a per-workspace `forge_target` through the call sites in `dispatcher.py` is the forge-targeting subtask's job, not this module's.

**The split.** `resolve_named_check_outcome(check_name, readiness) -> CheckOutcome` is authoritative-agnostic — it resolves a check name purely against `readiness`'s own three check-name sets (`failing_checks`, `pending_checks`, `passing_checks`), with no `ForgeTarget` involved at all:

| Value | Meaning |
|---|---|
| `pass` | `check_name` appears in `readiness.passing_checks` — built in `_pr_ready._bucketed_check_names_from_rollup` from `statusCheckRollup` entries whose conclusion is unambiguously `SUCCESS` (not merely "not failing/pending" — `NEUTRAL`/`SKIPPED`/`CANCELLED`/unknown conclusions all fall through to `absent`, never `pass`) |
| `fail_or_pending` | `check_name` appears in `failing_checks` or `pending_checks` |
| `absent` | `check_name` appears in none of the three sets — it can't be proven to have run at all |

`resolve_check_outcome(check_name, readiness, forge_target) -> CheckOutcome` is the authoritative-gated wrapper this module still uses everywhere it resolves a check outcome: it returns `absent` immediately unless `forge_target.authoritative_checks` declares `check_name`, then delegates to `resolve_named_check_outcome`. The former hardcoded `_SONAR_CHECK_NAME` literal is gone from both — resolution is against the caller-supplied `forge_target.authoritative_checks` set. Behaviour at every existing call site in this module is unchanged by the split: `_is_authoritative_check_only_failing` only ever resolves a check name it already knows is in `readiness.failing_checks`, so the `pass` branch — the only branch whose underlying logic actually moved, from "the whole PR is green" (`readiness.ok`) to "this specific check's own rollup conclusion" (`passing_checks` membership) — is unreachable from this module's own call site and therefore byte-identical in practice.

**Why `authoritative_checks` was deliberately not widened.** The stop-routing-unactionable-remediations build needed a way for the acceptance-clause auditor to corroborate a FAIL against *any* required check it cites by name — not just the Sonar-specific authoritative-check set this module gates mechanical recovery on. Widening `forge_target.authoritative_checks` to cover that would have blast-radiused this module's own Sonar-hotspot recovery ladder (`needs_sonar_annotations`, the `SONAR_HOTSPOT`/`SONAR_GENUINE`/`SONAR_NO_ANNOTATIONS` classification) for a need that has nothing to do with Sonar. `resolve_named_check_outcome` sidesteps this entirely by not gating on `authoritative_checks` at all — the clause auditor calls it directly, this module keeps calling the gated wrapper, and the two paths share one `passing_checks` definition without sharing an authorization list neither needs to share.

Fail-closed by construction either way: `absent` is the default outcome whenever the check can't be positively proven to have passed, and `absent` never contributes to a block being recovered as an approval (this module) or a clause FAIL being demoted from fix-routing (the clause auditor). `classify_block` only takes the sonar/authoritative-check recovery branch when the outcome is `fail_or_pending`; an empty or absent declared check set falls through to the ordinary pending/genuine classification instead.

## MergeBlockClass enum

| Value | Meaning |
|---|---|
| `behind_plus_transient` | Branch is behind main; no *genuine* (non-flaky, non-quarantined) failing check |
| `stale_review` | CHANGES_REQUESTED with no failing checks and either merge state in `{CLEAN, HAS_HOOKS, ""}`, or `BLOCKED` with no pending checks (the shape a PR takes when the outstanding review is itself the only blocker); `dismiss_stale_verifier_reviews` found no stale verifier-bot review (human-authored review, or a verifier review against the current head SHA that dismissal correctly skips) — routes to `await_human`. One exception: a waiver answer dismisses the verifier's own current-head review first, before this class is ever re-evaluated — see "Waiver exception to the current-head rule" below. |
| `stale_verifier_review` | Confirmed ≥1 verifier-bot CHANGES_REQUESTED predating current head SHA; successfully dismissed — recovered |
| `pre_existing_red` | All failing checks are quarantined (pre-existing on base or known-flake); no `CHANGES_REQUESTED` — routes to `await_human`, never recycles `implementation_fix` |
| `transient_flake` | Every failing check is on the shared flaky allowlist (`_pr_flake_ledger.SHARED_FLAKY_ALLOWLIST`); merge state != DIRTY, no `CHANGES_REQUESTED` — auto-reruns the check(s), routing back to `pr_merge` on success or `await_human` once the shared rerun budget for the *current head SHA* is exhausted (a new head SHA grants a fresh per-SHA budget; a non-resetting lifetime ceiling bounds total spend regardless of SHA churn — see "Shared flaky-gate substrate" below) |
| `sonar_hotspot` | Single failing check = SonarCloud; all annotations start with "make sure" |
| `sonar_no_annotations` | Single failing check = SonarCloud; check-run returned no annotations |
| `sonar_genuine` | Single failing check = SonarCloud; has at least one non-hotspot annotation |
| `dirty` | `mergeStateStatus=DIRTY` (real merge conflict) — routes through the mechanical reconciliation rung (`_recover_dirty` → `alan/teams/_pr_reconcile.reconcile_branch`) first; once that ladder has genuinely run out (`rec is None`, budget exhausted) or the reconcile verdict is itself terminal (`ReconcileOutcome.CONFLICT`), the block routes to `implementation_fix` instead of a human dead end — see "Mechanical reconciliation for DIRTY" below and "A human is no longer the terminal handler for a conflict" further down |
| `stale_measured_baseline` | `MEASURED_BASELINE_STALE_REASON` present in `failed_reasons` (injected by `Dispatcher._readiness_after_freshness_check` from the green short-circuit); recovered via `_pr_branch.update_pr_branch_outcome` — see "Measured-baseline freshness" below |
| `stale_measured_baseline_conflict` | `update_pr_branch_outcome` returned `CONFLICT` while recovering `stale_measured_baseline` — routes to `await_human`, never `implementation_fix`; see "Measured-baseline freshness" below |
| `no_check_results` | a real `PrReadiness` (never `ReadinessUnavailable`) for which `_pr_ready.results_absent(readiness)` holds — a `mergeStateStatus` the forge reports as clean/mergeable with a `statusCheckRollup` that came back with zero entries: checks for the measured commit have not been created yet, not "all checks passed". Classified in `_classify_block_head`, below `DIRTY`/`STALE_MEASURED_BASELINE`; a member of `dispatcher._BOUNDED_RETRY_REMEDIATION_CLASSES` but deliberately **not** of `CI_RESET_DELAY_CLASSES` (nothing was recovered, so `_delay_for_ci_reset` never fires for it) and not of `MERGE_LANE_POLL_CLASSES`; budget exhaustion terminates at `await_human` with a transient-wait recipe, never `implementation_fix` — see "`no_check_results` — absence is not readiness" below |
| `closing_links_missing` | The workspace brief's `Delivers-Issues:` trailer names issue(s) the forge's own `closingIssuesReferences` record does not (fully) list — a link broken by truncation or a code-span wrapper would otherwise merge with the issue left open. Classified in `_classify_block_head`, last, below `no_check_results` — every mechanically recoverable class still wins. No mechanical recovery rung exists for it (nothing to reconcile or rerun); it is **not** a member of `CI_RESET_DELAY_CLASSES` or `MERGE_LANE_POLL_CLASSES`, and — unlike `no_check_results` — it is also not a member of `dispatcher._BOUNDED_RETRY_REMEDIATION_CLASSES`, so it falls straight through `_pr_merge_remediation` to `implementation_fix` (append the missing `Fixes #N` line, re-dispatch `pr_merge`) rather than spending a bounded-retry cycle on a condition retrying won't clear by itself; see "Pre-merge closing-link read-back" below |
| `still_computing` | pending checks only (no failures) with merge state in `{CLEAN, HAS_HOOKS, ""}`; or `mergeStateStatus=UNSTABLE` with pending checks only, no failures and no CHANGES_REQUESTED. A readiness outage (`ReadinessUnavailable`) is not a `still_computing` case: it never reaches the classifier, because `merge_gate.attempt_recovery` returns `MergeGateNotAttempted` for it first |
| `blocked_pending` | `mergeStateStatus=BLOCKED`, no failing checks, no `CHANGES_REQUESTED`, has pending checks — routes back to `pr_merge` polling |
| `blocked_no_signal` | `mergeStateStatus=BLOCKED`, no failing checks, no pending checks, no `CHANGES_REQUESTED` — a genuinely blocked PR with no gate signal a fix worker could act on; routes back to `pr_merge` polling, never to `implementation_fix`; see "`blocked_no_signal` — routing away from code dispatch" below |
| `post_update_red` | Everything else fails to classify (the `genuine` fallthrough shape) **and** the current head SHA matches a `pr_<n>_system_head.json` marker the merge lane itself wrote — i.e. the PR was approved, the system updated its branch on its own initiative afterward, and this failure is the first read of the resulting commit's own CI state. Routes to `implementation_fix` exactly like `genuine` (not added to `dispatcher._BOUNDED_RETRY_REMEDIATION_CLASSES`); see "System-authored heads: `pr_<n>_system_head.json`" below |
| `genuine` | Any other combination, or the fallthrough shape with no matching system-head marker — routes to `implementation_fix` |

## Upstream forge-failure classification (pr_merge)

Before a merge failure ever reaches this module's taxonomy, `pr_merge` classifies the raw `gh` failure via `alan/teams/_forge_errors.raise_for_infra` (see [queue_and_dispatcher.md](queue_and_dispatcher.md) §"Forge (GitHub) failures ride the same two paths"): a rate-limited or network/5xx `gh pr merge` — and a rate-limited/network `gh pr checks` / `gh pr view state` poll with no usable JSON — raises `ForgeRateLimited`/`ForgeTransientError` for a dispatcher-level pause/retry instead of producing a `kind="error"` escalation or burning the poll budget on the `[PENDING]` fallback. Only auth (credential park), confirmed domain answers, and unclassified failures continue into the outcome taxonomy below, so an `error` escalation now implies the failure was not positively infra-shaped.

## Tolerating an advisory check in the live merge lane

`pr_merge`'s own poll loop (`alan/teams/pr_merge.py:_evaluate_checks`, distinct from the mechanical-recovery taxonomy below) used to treat *any* pending check on a PR's `gh pr checks` rollup as blocking, full stop — `alan/teams/_pr_merge_checks.classify_checks` returns `"pending"` the moment one check is still running, with no notion of which checks branch protection actually requires. One recorded workspace parked twice, twenty hours apart, purely because a non-required "Mutation probe (changed lines, advisory)" job (every step `continue-on-error: true`, so it can only report pending-then-success, never failure) was still `IN_PROGRESS` at the ten-minute poll-timeout mark while every required check was already green. Both times the human answer was "investigate why the checks are not settling" and both times nothing was wrong — the checks simply hadn't finished. `resolve_checks_kind` (`alan/teams/_pr_merge_checks.py`) closes this by giving the forge's own, more accurate merge-state judgement a chance to override a locally-pending classification, instead of letting the cheap local scan veto it before it is ever consulted.

**The precedence inversion.** Previously `_evaluate_checks` computed `classify_checks(...)` first and fed the result into `confirm_ready_kind`, which only ever probed live readiness when the local kind was already `"ready"` (`if kind != "ready": return kind, ""`) — so a `"pending"` verdict from the cheap scan was final, and the richer live signal was never consulted. `resolve_checks_kind` now calls `classify_checks` first as before (unchanged, still authoritative for `"ready"`/`"failed"`/`"unresolved"`/etc.), but when — and only when — it returns `"pending"`, tries a tolerant path before accepting that verdict. If the tolerant path can't confirm tolerance, behaviour is byte-identical to before: `"pending"`, keep polling. `classify_checks` and `confirm_ready_kind` themselves are untouched, so their existing test suites (`tests/test_teams_pr_merge_checks.py`, `tests/test_teams_pr_merge_conflict.py`) remain a non-regression harness for free.

**Local eligibility, checked before any extra `gh` call.** The tolerant path is attempted only when the *local* `gh pr checks` rollup itself is non-empty, is not the `PENDING_FALLBACK` sentinel (the conservative `[{"name": "?", "state": "PENDING"}]` rollup `_gh_pr_checks` returns when `gh` failed without usable JSON — "we don't know" must never be read as "the advisory check is pending"), contains no `_FAILURE_STATES` entry, and contains no blank/unclassified `state` entry either. That last guard exists because `_gh_pr_checks`'s own parser tolerates a malformed row (a missing or non-string `name`/`state`) by normalizing it to `state=""` rather than dropping it (Copilot review on PR #1488) — such a row is neither a known pending state nor a known failure state, so without an explicit check it would silently pass local eligibility and let the tolerant path merge without ever confirming that unclassified check actually settled. `classify_checks` tests pending before failure, so a mixed failing-and-pending rollup already reads `"pending"`; without the failure-state filter, a genuinely red required check sitting alongside a pending advisory one could reach the tolerant path. Only once this is satisfied does the tolerant path fetch live readiness at all — an already-`"failed"` or already-`"ready"` local verdict, or an empty/fallback/mixed-failure/unclassified rollup, costs zero extra `gh` calls over the pre-existing behaviour. A second local pre-check, `_advisory_floor_possible` (2026-09 quota incident), sits between that eligibility test and the readiness fetch: the fetch is skipped outright when `forge_target.authoritative_checks` is empty or when any authoritative check is itself in a pending state in the local rollup (`_pending_local_names`), because the authoritative floor below could not be met from that snapshot and the ~100-GraphQL-point `check_pr_merge_readiness` result would have been discarded on every pending poll — the previous behaviour for the whole duration of a long-running SonarCloud analysis.

**The tolerated merge state — one literal, nothing else.** GitHub's `mergeStateStatus` reports `UNSTABLE` for exactly this shape: mergeable, with a non-passing check that branch protection does not require. The tolerant path matches the literal string `"UNSTABLE"` and nothing else — it does not read or extend `alan/teams/_pr_merge_conflict.MERGEABLE_MERGE_STATES` (`{"CLEAN", "HAS_HOOKS", "UNSTABLE", "BEHIND"}`), which exists for a different purpose (`confirm_ready_kind`'s own second-source check on an already-`"ready"` local verdict). `BEHIND` in particular must never gain tolerance here: were a `"pending"` local verdict on a `BEHIND` PR treated as tolerable, `resolve_checks_kind` would report `"ready"`, `_execute_merge` would call `_handle_behind_recheck`, and `_behind_during_merge_outcome` would fire `gh pr update-branch` — a fresh reconcile push, starting a fresh CI run, which is the exact loop this work exists to end. `HAS_HOOKS` and `CLEAN` are excluded too: a `"pending"` local verdict under either of those states almost always means a required check simply hasn't reported yet, not that a non-required one is the sole holdout. `"UNKNOWN"` is never mergeable here, as an explicit design point rather than an accident of `frozenset` membership: the forge computes mergeability lazily and every push resets it, so `UNKNOWN` dominates immediately in the window right after a branch update, until the forge finishes recomputing. **This change therefore does nothing in that window** — a PR that just got pushed to, or just had `gh pr update-branch` run against it, keeps polling exactly as before until the forge produces a real verdict. That limit is accepted, not a bug to chase.

The shape checked against a fresh `PrReadiness` snapshot — merge state `UNSTABLE`, zero `failing_checks`, at least one `pending_checks` entry, and `review_decision` not `CHANGES_REQUESTED` — is deliberately identical to `merge_recovery._is_unstable_pending_only` (`:227-233`, feeding `MergeBlockClass.STILL_COMPUTING`). Handling of failing checks does not change anywhere in this feature: the advisory job's `continue-on-error: true` steps mean it can only ever be pending or successful, never failing, so a pending-only check is sufficient and a parallel failing-tolerant path was never needed.

**The authoritative floor — necessary, not sufficient.** Matching `UNSTABLE`-pending-only is not enough by itself: `forge_target.authoritative_checks` declares which checks *this engine* treats as load-bearing (`{"SonarCloud Code Analysis"}` for the default forge), and the tolerant path additionally requires every one of those declared checks to already be resolving `CheckOutcome.PASS` against the same readiness snapshot (via the existing `_pr_ready.resolve_check_outcome`, not a fresh `issubset` check, so a future glob-matching authoritative-check resolver can't silently diverge between the two use sites). An empty `authoritative_checks` set refuses the tolerant path outright rather than vacuously satisfying it — `all(...)` over an empty set is `True` in Python, so the refusal needs its own explicit `bool(forge_target.authoritative_checks)` guard, not an accident of the loop. This closes a fail-open: a repository whose branch protection has no required contexts configured (alan's own `repo_scaffold.py:253-287` and the `branch_protection_compat` PUT path can both leave protection in exactly this deferred state, and this code path is shared by every engine via `forge_target_for_ws`, not only alan's own repo) reports `UNSTABLE` for *any* pending check, including one that would otherwise have been required — `mergeStateStatus` alone cannot tell "the important suite is still running, and nothing here is actually required" apart from "only the advisory job is left." The floor forces confirmation that whatever this engine itself considers load-bearing is already green before ever tolerating anything else being incomplete.

**Named refusal — do not collapse this with its mirror image.** `forge_target.authoritative_checks` is used here purely as a *necessary* condition (every declared check must already be `PASS`), which can only make the tolerant path stricter. It must never be read the other way — as a *sufficient* condition, i.e. "if a failing check isn't in this set, it doesn't matter." That reading would make every check the default forge doesn't name (sixteen of seventeen, historically) optional and let a genuinely red *required* check merge; it is rejected on sight regardless of what a test suite says, because the two readings sound similar but point in opposite directions.

**Second source, same snapshot.** The tolerant path re-checks that the readiness is a real `PrReadiness` (not a `ReadinessUnavailable`), `not results_absent(readiness)`, and `bool(readiness.head_sha)` before ever consulting the merge state or the floor — the same two non-regressions the pre-existing `confirm_ready_kind` already defends for its own "ready" path (`alan/teams/_pr_merge_checks.py:_advisory_readiness`; see `results_absent` and `_pr_ready.py:75`). A malformed or absent `headRefOid`, or a rollup that came back with zero entries because checks for the measured commit haven't been created yet, must never read as "everything's fine, merge it" — both checks run against the *same single* `PrReadiness` fetch used for the merge-state and floor checks, so there is no cross-fetch skew between what was judged tolerable and what actually gets merged. When the tolerant path does confirm eligibility, it still runs the PR's feedback ladder (`_classify_feedback` — the ceiling check, then unresolved-human, then unresolved-Copilot, extracted verbatim from the tail of `classify_checks` so both the ordinary and the tolerant path share one ladder) before ever returning `"ready"`: merging over a tolerable advisory check must never also merge over an unresolved human review thread, a Copilot comment, or a blown unresolved-count ceiling.

**Audit, written only once a merge actually happens.** `resolve_checks_kind` does not audit anything itself — a tolerant-path `"ready"` verdict only hands its `PrReadiness` snapshot back as the third element of its return tuple, alongside the usual `(kind, head_sha)`. `pr_merge.py` threads that snapshot as `advisory_readiness` through `_merge_or_dry_run` into `_execute_merge`, and calls the public `_pr_merge_checks.audit_advisory_tolerated(workspace, pr_number, readiness, forge_target)` only at the point a merge is confirmed to have actually happened: right after `gh pr merge` returns rc=0, or (since a dry run can't fail) at dry-run's simulated-success point. Earlier, the row was written the moment `resolve_checks_kind` classified the PR as `"ready"`, before `_execute_merge` ran its own `_handle_behind_recheck` and `gh pr merge` calls — so a dry run, a BEHIND-during-merge abort, or a `gh pr merge` refusal (head-mismatch or policy hold) could each still produce an `advisory_check_tolerated` row claiming a merge that never happened (Copilot review on PR #1488). The row itself is unchanged: `task_id`, `pr_number`, the `merge_state_status` the decision relied on, `declined_checks` (the pending checks it chose not to wait for), and the `authoritative_checks` it confirmed were already green — so a future incident can still distinguish "merged over an advisory check, here's what it was" from the ordinary merge path's own `merge_ok` row, now with the added guarantee that the row only ever describes a merge that actually went through. The audit file literal (`_ADVISORY_AUDIT_FILE = "merge_gate_audit.jsonl"`) is declared locally in `_pr_merge_checks.py` rather than importing `pr_merge._MERGE_GATE_AUDIT_FILE` — `pr_merge.py` imports from `_pr_merge_checks`, so the reverse import would be circular; the same literal is simply declared twice, matching the precedent already set by `merge_gate.py`, `triage.py`, and `proactive_rebase.py`.

**Accepted asymmetry: this floor does not reach `merge_recovery`'s own `STILL_COMPUTING` rung.** `merge_recovery._is_unstable_pending_only` classifies the *identical* `UNSTABLE`-pending-only shape as `MergeBlockClass.STILL_COMPUTING`, which `routes_to_merge_lane` (`alan/_dispatcher_merge_brief.py`) sends straight back into `pr_merge`'s own poll loop with no authoritative-floor check at all — it only ever decides *where an already-blocked PR gets routed*, never whether to merge, so a floor there would gate nothing. Once routed back, the very same PR is re-evaluated by `resolve_checks_kind` on its next poll, where the floor above *does* apply before any merge is attempted. This is a deliberate asymmetry, not an oversight: the floor belongs at the one decision point that can actually produce a merge, and duplicating it at a routing-only rung would add a check with nothing to gate. Do not converge this with `alan/repo_status.py`'s unrelated `counted_over` field (`"main_ci_workflow"` vs. `"all_checks"`) — that field describes what set of checks a health dashboard's green/red counts are computed *over* for reporting purposes; it has no gating role and no connection to whether a merge is attempted. **The vocabulary collision that prompted this warning is gone**: `counted_over` used to have an `"authoritative_checks"` arm and `repo_status` used to scope its counts by `forge_target.authoritative_checks`, which made `red_count` structurally unable to go non-zero while `Tests` was failing (alan#1596). `repo_status` no longer reads `forge_target.authoritative_checks` at all — it scopes to the declared `ci.main_ci_workflow`'s check-suite (`repo_status.md`). The warning stands as the reason not to reintroduce the coupling.

## Advisory check failures never reach `classify_block`

`merge_gate._attempt_recovery_for_readiness` applies `_pr_ready.merge_lane_without_advisory` as its first statement, before `readiness_after_freshness_check` and `readiness_after_closing_links_check`, so `classify_block` and `attempt_mechanical_recovery` never see a red check that came from a non-Actions app and is not in `forge.authoritative_checks`. A PR whose only red checks are advisory reads as the same PR with those checks green (its `UNSTABLE` becomes `CLEAN`; `BLOCKED` and `DIRTY` are kept); a blocking red next to an advisory one leaves the readiness untouched. The `sonar_*` rungs below therefore apply only to an engine that lists a Sonar check as authoritative. The definition, the fail-closed cases and the audit rows are in [sonarcloud.md](sonarcloud.md).

## classify_block(readiness, annotations, forge_target, *, survived_at_head=frozenset(), system_head=False) → MergeBlockClass

Pure function — `system_head` is a keyword-only plain `bool` (default `False`), exactly like `survived_at_head`: no I/O, no forge target, no marker lookup inside the classifier itself. The caller (`attempt_mechanical_recovery`, below) owns the one place a `pr_<n>_system_head.json` marker is read and a head SHA is resolved via `gh`, and passes the already-computed boolean in — the same shape the module already used for `survived_at_head`, so `classify_block` stays a pure function of its arguments with no new I/O surface. Dispatch order matters (the recoverable-block ladder is factored into `_classify_recoverable_block` to keep `classify_block` under the repo's lizard CCN gate):
`classify_block` takes only a real `PrReadiness`; a readiness outage is a `ReadinessUnavailable`, which the merge gate short-circuits before classification, so there is no unavailable rung.
1. `DIRTY` → `dirty`
2. `_is_behind_plus_transient` → `behind_plus_transient`
3. `_is_stale_review_only` → `stale_review`
4. `_is_all_quarantined_failing` → `pre_existing_red`
5. `_is_transient_flake` → `transient_flake` — **inserted strictly after `pre_existing_red` and strictly before the authoritative/sonar rung.** This position is load-bearing: `SHARED_FLAKY_ALLOWLIST` and `forge_target.authoritative_checks` are disjoint sets (the only authoritative check today is `"SonarCloud Code Analysis"`, never on the flaky allowlist), so a lone Sonar failure always falls through unchanged to step 6, and a quarantined check is already claimed by step 4 before step 5 ever runs.
6. `_is_authoritative_check_only_failing` → `_classify_sonar_block(annotations)` (hotspot or genuine)
7. `_is_pending_only` → `still_computing`
8. `_is_unstable_pending_only` → `still_computing`
9. `_is_blocked_pending_only` → `blocked_pending`
10. `_pr_ready.is_blocked_without_signal` → `blocked_no_signal`
11. fallthrough → `post_update_red` if `system_head` else `genuine` — **`post_update_red` is placed last, deliberately, refining only the `genuine` fallthrough.** It must never pre-empt the recoverable ladder (steps 2–5), the sonar rung (step 6), or either pending rung (steps 7–10): a system-authored head that has gone `BEHIND` again must still rebase mechanically via step 2, a lone Sonar failure on a system-authored head must still reach its annotation-driven recovery via step 6, and a still-settling system-authored head must still poll via steps 7–10 rather than being misread as a genuine failure. Placing the check anywhere earlier would strand those cases — convergence depends on every earlier rung staying reachable regardless of `system_head`.

`_is_behind_plus_transient`: merge_state = BEHIND, no CHANGES_REQUESTED, and no *genuine* failing check (`_has_genuine_failing_check`, which delegates to `_pr_flake_ledger.rebase_blocking_failing_checks`: the failing checks that are neither in `REBASE_SAFE_FLAKY_CHECKS` — a strict subset of `SHARED_FLAKY_ALLOWLIST` containing only `"Frontend E2E (Playwright, blocking)"` — nor in `quarantined_checks`). This is deliberately **narrower** than the routing predicates (`actionable_failing_checks`/`evidenced_actionable_failing_checks`/`flaky_only_failing`) that `_verification_gates._format_gate_block` and the `_is_transient_flake` rung below use, which test the full three-member `SHARED_FLAKY_ALLOWLIST` — see "Write-path hold: `REBASE_SAFE_FLAKY_CHECKS`" below for why the two must diverge. `alan.teams` sits below both `merge_recovery` and `verification` in the import contract, so `_pr_flake_ledger` is the only place both callers can reach their respective predicates from. See `docs/architecture/loop_guard.md` for what the verifier does with its own judgement. The `failed_reasons` loop (`_behind_reasons_all_benign`) then only needs to confirm every reason is `"mergeStateStatus=BEHIND"`, a `"pending checks:"` reason, or a `"failing checks:"` reason — genuineness was already ruled out by the guard above. This means a PR that is BEHIND *and* whose only failing check is pre-existing-red or the E2E flaky gate still recovers via the existing `update_pr_branch_outcome` rung instead of falling to `genuine`; a PR that is BEHIND with any other failing check — including a red `"Backend tests + coverage"`/`"Frontend tests + coverage (100/100/100/100)"`, which `_has_genuine_failing_check` treats as genuine for *this* rung even though it is routing-eligible — instead falls through to `_is_transient_flake` (which still recognises it as flaky-allowlisted and reruns it) or, for a check off the allowlist entirely, all the way to `genuine`.

`_is_stale_review_only`: CHANGES_REQUESTED, no failing_checks, and either merge_state in `{"CLEAN", "HAS_HOOKS", ""}` or `_is_blocked_stale_review_only(readiness)` is true. `_is_blocked_stale_review_only`: merge_state = `"BLOCKED"`, no pending_checks — keyed on the literal `"BLOCKED"`; does not widen `_MERGE_STATE_ALLOWS_STALE`, whose other two call sites (`_is_authoritative_check_only_failing`, `_is_pending_only`) are unrelated decisions. The pending-checks requirement is deliberately asymmetric between the two arms: the shared-set arm above ignores pending checks entirely (`test_classify_block_pending_not_stale_when_has_requests` pins CHANGES_REQUESTED + CLEAN + pending checks still classifying as `stale_review`), while this `BLOCKED` arm requires none (`test_classify_block_genuine_blocked_with_changes_requested` pins CHANGES_REQUESTED + BLOCKED + pending checks staying `genuine`) — both are deliberate and must not be harmonised.

`_is_all_quarantined_failing`: `quarantined_checks` non-empty, all `failing_checks` are in `quarantined_checks`, no CHANGES_REQUESTED. Fires before the transient-flake and authoritative-check rungs so a quarantined SonarCloud failure is also caught here. **Scope note**: the rung fires on the merge states the forge actually produces for a failing check — `BLOCKED` when the quarantined check is required, `UNSTABLE` when it isn't. The conflict (`DIRTY`) and behind-plus-transient exclusions are structural, claimed by earlier rungs in `_classify_recoverable_block` rather than by a guard here, so this rung never has to re-check either. The class routes to bounded remediation retry and then a human park — never to `implementation_fix`.

`_is_transient_flake`: `failing_checks` non-empty, merge_state != `"DIRTY"`, no CHANGES_REQUESTED, and **every** failing check is in `_pr_flake_ledger.SHARED_FLAKY_ALLOWLIST`. Deliberately excludes only `DIRTY` — it does **not** require merge_state to be in `_MERGE_STATE_ALLOWS_STALE`/CLEAN, because a flaky *required* check reports `mergeStateStatus=BLOCKED`, and an ALLOWS_STALE-style guard would make this class never fire for the case it exists to handle.

`_is_authoritative_check_only_failing`: exactly one failing check, and `resolve_check_outcome(that check, readiness, forge_target)` is `CheckOutcome.FAIL_OR_PENDING` (i.e. the check is declared authoritative by `forge_target.authoritative_checks` *and* is the one actually failing), no CHANGES_REQUESTED, merge_state OK or empty. For the default engine `forge_target.authoritative_checks == {"SonarCloud Code Analysis"}`, so this reproduces the prior hardcoded `_is_sonar_only_failing` behaviour exactly. For an engine with an empty or non-matching `authoritative_checks` set, the single failing check resolves to `CheckOutcome.ABSENT` and this predicate returns `False` — the block falls through to `_classify_pending_state`/`genuine` rather than being routed into the Sonar-specific hotspot-ack recovery ladder. This is the fail-closed guarantee: an absent or empty authoritative-check declaration can never be mistaken for the one authoritative check that's failing, so it can never trigger a recovery path that treats the block as recoverable.

`_is_blocked_pending_only`: merge_state = `"BLOCKED"`, no failing_checks, no CHANGES_REQUESTED, has pending_checks. Keyed on the literal `"BLOCKED"` — does not widen `_MERGE_STATE_ALLOWS_STALE`.

`_is_unstable_pending_only`: merge_state = `"UNSTABLE"`, no failing_checks, no CHANGES_REQUESTED, has pending_checks — the sibling shape to `_is_blocked_pending_only` with the literal swapped, for the merge state the forge reports when checks are still settling and a non-required check is pending. Keyed on the literal `"UNSTABLE"` — does not widen `_MERGE_STATE_ALLOWS_STALE`, whose other two call sites (`_is_stale_review_only`, `_is_authoritative_check_only_failing`) gate unrelated decisions, one of which (`_is_authoritative_check_only_failing`) drives forge-write recovery paths (Sonar hotspot ack/rescan) that must not be armed on this shape. Placed after `_classify_recoverable_block` in `classify_block`'s dispatch order, so a quarantined or flake-allowlisted failing check under `UNSTABLE` still reaches `pre_existing_red`/`transient_flake` first — this predicate only ever fires when `failing_checks` is empty, so it never competes with those rungs for the same PR. Classifies as `still_computing`, not `blocked_pending`: the two are routing-identical (both are members of `MERGE_LANE_POLL_CLASSES`, so both route back to `pr_merge` polling), so the choice is purely about the audit bucket a row lands in — `blocked_pending` would assert a `mergeStateStatus=BLOCKED` that this shape does not carry, while `still_computing`'s documented meaning ("checks are still settling") is exactly this shape.

`_pr_ready.is_blocked_without_signal`: merge_state = `"BLOCKED"`, no failing_checks, no pending_checks, no CHANGES_REQUESTED — the sibling shape to `_is_blocked_pending_only` with the pending-checks condition inverted. Lives in `alan/teams/_pr_ready.py` beside `PrReadiness`, not in this module, because `alan/teams/pr_merge.py` cannot import `merge_recovery` upward under `lint-imports` and both this module's `classify_block` and the `pr_merge` lane need the predicate — `pr_merge.py` reaches it via its own sibling module, `alan/teams/_pr_merge_no_signal.py` (see "`blocked_no_signal` — routing away from code dispatch" below). Pure, total, single-argument — no clock, no I/O, no forge target.

### `blocked_no_signal` — routing away from code dispatch

A PR that reads `mergeStateStatus=BLOCKED` with nothing failing, nothing pending and no outstanding `CHANGES_REQUESTED` review carries no signal `classify_block`'s earlier rungs (or a fix worker) could act on — whatever holds it blocked lives outside the diff: a required status context that never reported, an unresolved review conversation, or an unsatisfied branch-protection rule. The most common trigger is transient: GitHub takes a moment to recompute mergeability after a stale `CHANGES_REQUESTED` review is dismissed and a fresh approval posted, and a readiness sample taken inside that window reads exactly this shape even though the PR is about to become mergeable on its own. Before this class existed, that shape fell through every rung to `genuine` and dispatched `implementation_fix` against a PR with nothing in the diff to fix — the verifier's own non-blocking findings became the brief, since there was no gate signal to hand over instead.

**Routing invariant.** `blocked_no_signal` never dispatches code, whether the underlying block turns out to be transient or genuine. `MERGE_LANE_POLL_CLASSES` (`alan/_dispatcher_merge_brief.py`) is the frozenset `{STILL_COMPUTING, BLOCKED_PENDING, BLOCKED_NO_SIGNAL}`; `routes_to_merge_lane(block_class)` is a single membership test. `dispatcher._pr_merge_remediation` calls it as its first line and returns the original, unmodified `pr_merge` decision when it's `True` — before ever calling `_merge_brief.pr_merge_remediation_context` (so `merge_recovery._STATIC_UNBLOCK_RECIPES` deliberately has no `BLOCKED_NO_SIGNAL` entry: one would be dead code on this path, unreachable exactly like the two pre-existing lane-routed classes) and before `block_class in _BOUNDED_RETRY_REMEDIATION_CLASSES` is ever consulted. `BLOCKED_NO_SIGNAL` is not, and must never become, a member of `_BOUNDED_RETRY_REMEDIATION_CLASSES` — `tests/test_dispatcher_merge_gate_blocked_no_signal.py::test_blocked_no_signal_is_excluded_from_bounded_retry_remediation_classes` asserts the exclusion by name so a future reorder of the two frozensets can't silently fold this class into the bounded-retry-then-`await_human` ladder.

**Persistence is the merge lane's own poll — no new mechanism.** Routing an unmodified `pr_merge` decision back means the PR simply re-enters `pr_merge`'s existing `_poll_until_done` loop (`alan/teams/pr_merge.py`): up to 20 polls at 30 s apart, bounded at 600 s, and — critically — `_confirm_ready_kind` re-samples `mergeStateStatus` on *every* poll and downgrades an apparently-clean rollup back to `pending` unless the sampled state is actually mergeable (see "Second line of defence" above). That is a finer-grained, better-bounded observation of persistence than a bespoke revisit counter sampling every 90 s would have been, it was already built and already tested for an unrelated race, and it resolves the common transient case on the very next poll rather than after a fixed wait. `blocked_no_signal` therefore adds **no new counter, no new sleep, no new timing knob, and no new persistent state** — `_pr_state_paths.remediation_retry_count_path`'s per-PR-per-forge budget (see "Bounded remediation retry" below) is never charged for this class, because the class never reaches the code path that charges it.

If the block genuinely persists for the full 600 s window, `pr_merge`'s own timeout handling — unchanged in shape by this class, already exercised by `tests/test_teams_pr_merge.py` — takes over: `_evaluate_checks` returns `kind="timeout"`, and `_build_handover` routes to `_await_human_handover`, never to `implementation_fix` (the `failed`/`timeout` → `implementation_fix` branch there is gated on `prior.dependency_bot_authorized`, which a verifier-approved PR reaching this gate never carries — pinned explicitly by `test_blocked_no_signal_timeout_without_dep_bot_authorization_awaits_human`, since `alan/teams/pr_merge.py:856-862` routes a dependency-bot-authorized timeout to `_dep_bot_rebase_handover` and nothing upstream of this class rules that flag out by construction). So a persisted `blocked_no_signal` block still parks for a human rather than falling back to code dispatch — `test_blocked_no_signal_persists_across_polls_parks_with_shape_matched_recipe` (`tests/test_teams_pr_merge.py`) is the DoD's third fixture: it drives two full BLOCKED-no-signal polls through the real `pr_merge` loop into the timeout branch and asserts both the park outcome and the recipe text below.

**The parked message names the shape, not the generic "checks are not settling" text.** The DoD for this class asks for an unblock recipe that specifically names a required-context/review-conversation/branch-protection cause and states none of those live in the diff. `alan/teams/pr_merge.py` is pinned shrink-only at exactly its current non-blank line count (`tests/size_baseline.py`), so the recipe text and the readiness re-probe that selects it live in a new sibling module, `alan/teams/_pr_merge_no_signal.py` — the same "sibling module holds a block-class-specific recovery recipe" shape `_pr_merge_conflict.py` already established for `DIRTY`. `_evaluate_checks`'s timeout branch calls `_pr_merge_no_signal.timeout_ctx(workspace, pr_number, elapsed, polls, forge_target=forge_target)`, which re-samples readiness once — via the fail-open `_pr_ready.readiness_or_unavailable`, one extra `gh pr view` call made only at the terminal timeout, never on the intermediate polls that keep re-entering the merge lane — and records `is_blocked_without_signal(readiness)` on the returned ctx as `blocked_no_signal`. `_checks_reason` then asks `_pr_merge_no_signal.timeout_recipe(ctx, default_recipe)` for the recipe text: when `blocked_no_signal` is true it returns `BLOCKED_NO_SIGNAL_TIMEOUT_RECIPE` (naming a required status context that never reported, an unresolved review conversation, or an unsatisfied branch-protection rule, and stating none of those live in the diff); every other timeout — and every other `ChecksKind` — falls back to the pre-existing generic recipe unchanged, via the same absent-tolerant `ctx.get("blocked_no_signal")` lookup that keeps `test_checks_reason_timeout_branch_has_label_and_recipe`'s readiness-less `ctx` call valid with no signature change. The two changed pr_merge.py call sites cost this file zero net non-blank lines against its pin: they're offset by re-wrapping four pre-existing multi-line recovery-text constants (`_CHECKS_RECOVERY_RECIPE["timeout"/"error"]`, `_TIMEOUT_OPTIONS[0]`, `_COPILOT_CAP_RECOVERY_RECIPE`) into fewer, still-under-100-column lines — no content changed, only where the line breaks fall. Four pre-existing tests that assumed exactly one `gh` call per poll iteration (`test_timeout_yields_await_human`, `test_ready_with_blocked_merge_state_classified_pending`, `test_ready_probe_gh_failure_classified_pending`, `test_policy_refusal_repeated_hits_timeout_await_human`) now queue the extra probe response for the iteration that times out; `test_evaluate_checks_immediate_timeout_with_zero_env` now passes a real `workspace` fixture and stubs `_pr_ready.readiness_or_unavailable` instead of calling `_evaluate_checks` with `workspace=None`. `tests/test_teams_pr_merge_no_signal.py` covers `timeout_ctx`/`timeout_recipe` directly.

**Audit bucket.** `blocked_no_signal` is a new `MergeBlockClass` value, so `record_merge_gate_audit` writes it as its own `block_class` in `merge_gate_audit.jsonl` — a fresh bucket starting at 0/0 in the per-class recovery-rate statistics (`scripts/merge_recovery_report.py`, `alan/learning_metrics.py`), never inheriting or polluting `genuine`'s history. Both consumers bucket dynamically by the `block_class` string already present in each audit row, so no fixed list of class names needed updating for this class to appear. On the routed path the row is always `recovered=False` (nothing was mechanically attempted), `outcome="pr_merge"` (the lane-routed decision's team), `brief_attached=False`.

### `no_check_results` — absence is not readiness

The 2026-09-05 incident this class closes: the branch legitimately gained a new commit, the forge briefly reported it `mergeStateStatus=CLEAN`/mergeable with an *empty* `statusCheckRollup`, and the merge lane cleared it — the reviewer had approved one commit and the lane merged a different one seconds later, before that commit's own checks had even been created. `mergeStateStatus` alone cannot distinguish "no results exist for this commit" from "all results are good"; both read `CLEAN`. Fixing this required treating absence as its own state at **two** conflation sites, not one — the readiness judgement (`_pr_ready.results_absent`, feeding `PrReadiness.failed_reasons`) and the merge lane's own check classifier (`_pr_merge_checks.classify_checks`/`confirm_ready_kind`, which previously looked only for a pending or a failing state in the result list and fell through to `"ready"` when the list was simply empty) — since fixing only the readiness judgement would still let the merge lane's classifier wave an empty result set through.

`results_absent(readiness)` takes only a real `PrReadiness` and is `readiness.check_count == 0 AND` all three bucketed check-name tuples (`failing_checks`/`pending_checks`/`passing_checks`) empty. `check_count` — the raw `statusCheckRollup` entry count, populated in `_pr_ready._bucketed_check_names_from_rollup` before any bucketing — is the authoritative discriminator, not bucketed emptiness alone: `_classify_rollup_item` drops `SKIPPED`/`NEUTRAL`/`CANCELLED` conclusions into an unbucketed fallthrough, so a skip-green docs-only PR (real rollup entries, none of them in any of the three buckets) would misread as having no results if the classifier used bucketed emptiness instead — and deadlock at the merge gate forever, since a docs-only PR's rollup shape never changes.

**Classified in `_classify_block_head`, last.** `_classify_block_head` handles `DIRTY` and `stale_measured_baseline` before ever consulting `results_absent` — those two conditions are structural signals the forge or a prior probe already gave; `no_check_results` fires only once none of them apply, so a genuinely dirty or stale-baseline branch is never misclassified as merely lacking check results.

**Bounded retry, not a poll-lane class, not a CI-reset delay.** `no_check_results` joins `dispatcher._BOUNDED_RETRY_REMEDIATION_CLASSES` (one line in `dispatcher.py`) — `attempt_mechanical_recovery` never has anything mechanical to attempt for it (it falls to the final `(False, block_class, None)` return, since no per-class recovery rung matches), so every hit re-enqueues `pr_merge` via the same delayed `RouterDecision(eligible_at=...)` and per-PR retry counter (`ALAN_PR_MERGE_REMEDIATION_RETRY_DELAY_S`, `loop_guard.REVISIT_CAP`) every other bounded-retry class already uses (see "Bounded remediation retry" above) — no new waiting primitive, no sleep, no fixed delay. It is deliberately **not** a member of `CI_RESET_DELAY_CLASSES`: that set defers a decision past a reset window because a *recovery* just fired an async rerun or rewrote the branch; `no_check_results` never recovers anything, so `_delay_for_ci_reset` would be dead code for it. It is also **not** a member of `MERGE_LANE_POLL_CLASSES`: that set routes the original `pr_merge` decision straight back to `pr_merge`'s own poll loop with no remediation-context or retry-counter involvement at all, which would let an unresolving absence spin forever without ever reaching a human; a bounded, counted retry is the correct shape here precisely because a commit whose checks were never scheduled at all is not guaranteed to resolve on its own the way a transient recomputation lag is.

**Unblock recipe reads as a transient wait, not a failure.** `_STATIC_UNBLOCK_RECIPES[MergeBlockClass.NO_CHECK_RESULTS]` carries no "failed"/"escalate" vocabulary — it tells a human the rollup came back empty for the measured commit, that this is expected to resolve shortly, and to re-dispatch `pr_merge` if it doesn't. Budget exhaustion (`REVISIT_CAP` retries spent) terminates at `await_human` carrying this recipe — never at `implementation_fix`, since there is nothing in the diff for a fix worker to act on.

**The measured commit travels with the judgement.** `PrReadiness` now carries `head_sha` (from `headRefOid`, appended to the shared `_READINESS_FIELDS`/`_VERIFIER_READINESS_FIELDS` query) and `check_count`. `_pr_merge_checks.confirm_ready_kind` — the merge lane's own ready-confirmation probe, relocated out of `pr_merge.py` into `alan/teams/_pr_merge_checks.py` — returns the measured `head_sha` alongside a `"ready"` kind, and `pr_merge.py` threads it through `_merge_or_dry_run`/`_execute_merge` as `expected_head_sha`. Inside `_MERGE_LOCK`, `_handle_behind_recheck` re-fetches readiness immediately before the merge subprocess and, for any merge state other than `BEHIND`, compares the freshly observed `head_sha` against `expected_head_sha`: a mismatch aborts with a `merge_deferred_head_moved` audit row and a benign re-poll (`PrMergeOutcome(kind="error", ...)`, distinct from the `BEHIND` deferral's reason text) rather than merging a commit whose checks were never the ones this poll actually measured. This is the guarantee that a judgement measured against one commit can never silently clear a different one, and it does not depend on any forge capability — it is a purely alan-side comparison.

**Audit bucket.** `pr_readiness_check` rows now name the measured commit (`head_sha`/`check_count` fields on every row, `alan/teams/_pr_ready.py::_audit_readiness`), so this class of incident is reconstructable directly from the audit trail rather than by correlating timestamps across `pr_readiness_check`/`merge_gate_audit`/`merge_ok` rows after the fact. `merge_gate_audit.jsonl` gets its own fresh `no_check_results` bucket in the per-class recovery-rate statistics, same as every other `MergeBlockClass` value.

## attempt_mechanical_recovery(...) → (recovered, block_class, reconcile_result)

I/O function. The third element is the `alan.teams._pr_reconcile.ReconcileResult` object — not a bare outcome string — when the `DIRTY` rung actually attempted a reconciliation, `None` for every other block class (and for `DIRTY` itself when the reconcile budget was already exhausted — see "Mechanical reconciliation for DIRTY" below). `dispatcher.py`'s two `record_merge_gate_audit` call sites extract `rec.outcome.value if rec else None` before writing the ledger row, so the audit row's `reconcile_outcome` field keeps its pre-existing string shape even though the value threaded through routing is now the richer object. Dispatch:
- `DIRTY` → `_recover_dirty` (see "Mechanical reconciliation for DIRTY" below) — the only rung that returns a non-`None` third element
- `BEHIND_PLUS_TRANSIENT` → `_pr_branch.update_pr_branch_outcome(pr_number, task_id, forge_target=forge_target) is _pr_branch.BranchUpdateOutcome.UPDATED` (only `UPDATED` counts as recovered; `CONFLICT` and `FAILED` both leave `recovered=False`)
- `STALE_REVIEW` → `_pr_branch.dismiss_stale_verifier_reviews(pr_number, task_id)` (at the time of writing this lived on `_pr_branch`; the review-cluster split moved `dismiss_stale_verifier_reviews` to `alan/teams/_pr_post.py`, so this module is now `_pr_post.dismiss_stale_verifier_reviews` — call shape unchanged):
  - Returns `True` → reclassified as `STALE_VERIFIER_REVIEW`, `recovered=True`
  - Returns `False` → stays `STALE_REVIEW`, `recovered=False` (human-only review; dispatcher routes to `await_human`)
- `PRE_EXISTING_RED` → `(False, PRE_EXISTING_RED)` immediately; dispatcher routes to `await_human`, never to `implementation_fix`
- `TRANSIENT_FLAKE` → `_recover_transient_flake` (factored out to keep CCN in budget):
  - If `_pr_flake_ledger.gate_reruns_exhausted(pr_number, head_sha, forge_target=forge_target)` → `(False, TRANSIENT_FLAKE)` immediately. Exhaustion is now scoped to the *current head SHA* (a fresh commit gets a fresh per-SHA budget) **or** to the non-resetting lifetime ceiling (`_GATE_RERUN_LIFETIME_CAP = 6`), whichever binds first; dispatcher routes to `await_human`, never `implementation_fix` — a check that keeps failing after the allotted reruns *on this commit* is treated as a real problem, but budget spent against a *previous* commit no longer counts against a later, different failure (see "Evidence-based classification" below for the full defect this closes).
  - Otherwise reruns every failing check via `_pr_branch.rerun_flaky_checks` (the same primitive the verifier lane uses). If nothing was triggered → `(False, TRANSIENT_FLAKE)`. If triggered → bumps the shared `pr_<n>_gate_reruns.json` counter (keyed to the head SHA `attempt_mechanical_recovery` resolved once via `_merge_lane_survivor_evidence`) and returns `(True, TRANSIENT_FLAKE)` so `pr_merge` re-polls — deferred past the rerun reset window by the dispatcher's `_delay_for_ci_reset` (see "Wiring in dispatcher.py"). This lane records **no** cross-PR flake-frequency-sidecar occurrence (see below): no post-rerun evidence exists yet at trigger time, and a pending-marker state file to defer that evidence to would add a new persistence surface — and a new `ALAN_*` state-isolation surface — for an advisory sidecar with zero gating power. The verification lane (below) observes the same PRs before merge, so the signal isn't lost, only recorded once, later, with actual evidence.
- All others → `(False, block_class, None)` immediately

Returns `(True, cls, reconcile_outcome)` if recovery succeeded, `(False, cls, reconcile_outcome)` otherwise. Every call appends one `merge_recovery_attempt` entry to `impl_audit.jsonl`, additively carrying `reconcile_outcome` (only when not `None`) alongside the pre-existing `block_class`/`recovered` fields — the row's existing shape for every other block class is untouched.

## Mechanical reconciliation for DIRTY

Before this rung existed, a `DIRTY` block (a real merge conflict between the PR branch and its base) was structurally unrecoverable: `attempt_mechanical_recovery` returned `(False, DIRTY, None)` immediately, and the dispatcher routed it to `await_human` with **no unblock instruction at all** — a dead end that burned a full human-triage cycle for a class of failure a mechanical rebase can usually clear on its own. `_recover_dirty` (in `merge_recovery.py`) and `alan/teams/_pr_reconcile.reconcile_branch` (the actual git mechanics, `alan/teams/_pr_reconcile.py`) close that gap.

**Budget.** `_MAX_RECONCILE_ATTEMPTS = 2` (per head SHA) and `_RECONCILE_LIFETIME_CAP = 6` (non-resetting) are fixed module constants in `merge_recovery.py` — no `ALAN_*` environment override, deliberately (this is a safety backstop, not an operator tuning knob; a new env var would also need registration in `tests/env_var_classification.py` and every state-isolation surface). `reconcile_attempts_exhausted(pr_number, head_sha, *, forge_target)` mirrors `_pr_flake_ledger.gate_reruns_exhausted` exactly: it reads `_pr_state_paths.load_reconcile_attempt_state` (`pr_<n>_reconcile_attempts.json` under `state_dir()/<owner>/<repo>/`, same `{"head_sha", "count", "lifetime"}` shape and legacy-fallback/reset semantics as `pr_<n>_gate_reruns.json` — see "Rerun-budget consistency" below), and is exhausted when the per-head-SHA `count >= _MAX_RECONCILE_ATTEMPTS` **or** the non-resetting `lifetime >= _RECONCILE_LIFETIME_CAP`, whichever binds first. `_recover_dirty` resolves `head_sha` via the same `_pr_branch.fetch_flake_guard_head_sha` the `TRANSIENT_FLAKE` rung uses, so a fresh push to the PR grants a fresh per-SHA budget (matching how the existing gate-rerun budget behaves) while the lifetime ceiling still bounds total spend under SHA churn. When exhausted, `_recover_dirty` audits and returns `(False, DIRTY, None)` **without calling `reconcile_branch`** — no reconciliation attempt, no `pr_reconcile_attempt` audit row, nothing spent.

**Only a real attempt spends budget.** `_pr_state_paths.bump_reconcile_attempt_count` is called only when `reconcile_branch`'s outcome is `RECONCILED` or `CONFLICT` — the two outcomes that mean the actor actually did something (moved the branch, or hit a genuine conflict while trying). `ALREADY_CURRENT` (the branch was already up to date — the merge-base check or a post-rebase no-op short-circuited before any push) and `RACED`/`TRANSPORT_FAILED` (the attempt could not complete for reasons unrelated to the branch's own conflict state) cost nothing, so a rerun of a merely-stale local view or a transient `gh`/network hiccup never eats into the bounded budget. `recovered` is `True` only for `RECONCILED` — `ALREADY_CURRENT` does not count as recovered even though it is not a failure, because the dispatcher's normal bounded-retry-then-`await_human` ladder (below) already handles re-polling a PR whose branch turned out not to need anything.

**Mechanics (`alan/teams/_pr_reconcile.py`).** `reconcile_branch(pr_number, task_id, *, forge_target)` never raises into the caller — every failure path returns a typed `ReconcileResult(outcome, base_sha, pre_sha, post_sha)` instead:
1. One `gh pr view <n> --repo <slug> --json headRefName,baseRefName` to resolve the head/base branch names. Failure → `TRANSPORT_FAILED`, nothing written to disk.
2. A fresh `tempfile.mkdtemp(prefix="alan-reconcile-")` per attempt, `git init -q` + `git remote add origin https://github.com/<slug>.git`, removed in a `finally: shutil.rmtree(..., ignore_errors=True)` — never reused across attempts and never rooted under `_engine_state_dir`, so a stale local view of the base branch is structurally impossible and a transient checkout never lands in the backed-up `~/.alan` tree.
3. A single `git fetch origin <base>:refs/alan-reconcile/base <head>:refs/alan-reconcile/head` (one network round trip, both refs, always live — the base is always freshly fetched, never read from a locally cached `origin/*` tracking ref) under `secrets_store.transport_env(forge_target)`, then `git rev-parse` against those two private-namespaced local refs to resolve `base_sha` and `pre_sha` (the head branch's tip **before** any rewrite).
4. `git merge-base --is-ancestor <base_sha> <pre_sha>` — if the base is already an ancestor of the head, the branch needs no rebase at all → `ALREADY_CURRENT`, no checkout, no rebase, no push.
5. Otherwise `git checkout -B <head> <pre_sha>` then `git rebase <base_sha>`. A conflicting rebase runs a best-effort `git rebase --abort` and returns `CONFLICT` — nothing is ever pushed on this path, so the remote branch is byte-identical to before the attempt.
6. A clean rebase whose `post_sha` (`git rev-parse HEAD`) equals `pre_sha` is a defensive no-op → `ALREADY_CURRENT`.
7. Otherwise `git push --force-with-lease=<head>:<pre_sha> -u origin <head>` under `transport_env` — the explicit `ref:sha` lease form (never the implicit no-argument form, which a preceding fetch would silently neutralize — see D6 in `pr_iteration_pipeline.md`), anchored to `pre_sha` so the push refuses rather than clobbers if the remote branch moved underneath this attempt. Success → `RECONCILED`; a lease rejection (`alan.teams._pr_push._is_lease_rejection`) → `RACED`; any other failure → `TRANSPORT_FAILED`.

Every invocation appends exactly one `_pr_audit_log.append_audit({"task_id", "action": "pr_reconcile_attempt", "pr_number", "outcome", "base_sha", "pre_sha", "post_sha"})` row to `impl_audit.jsonl` — a distinct action name from `merge_recovery_attempt`/`push_reconciled`/`push_diverged_escalate`, so the mechanism-level detail (SHAs, which outcome fired) never collides with either the existing merge-recovery ledger or the unrelated push-divergence-reconciliation path below.

**Deliberately not reused: `_pr_push.push_fix_branch_with_reconcile`.** `implementation_fix`'s own push-divergence reconciliation (D6 in `pr_iteration_pipeline.md`) rebases the *fix* branch onto `origin/<head>` — i.e. onto wherever the branch's own remote tip has drifted to since the worktree was created — and hardcodes the `push_reconciled`/`push_diverged_escalate` audit actions to describe *that* cause (a concurrent push landing mid-iteration). Calling it here would rebase onto the wrong ref (the stale head, not the PR's base) and would mislabel a genuine merge-conflict-with-base recovery as a same-cause-as-before push race — exactly the misleading-signal class this build exists to eliminate. `_pr_reconcile.py` reimplements the fetch/checkout/rebase/push sequence against the *base* branch instead, under its own `pr_reconcile_attempt` audit action.

**Degradation is intentional.** When mechanical reconciliation cannot succeed — a genuine content conflict on every attempt, or a concurrent push that keeps winning the lease race — the budget above bounds the damage. A non-terminal miss (`RACED`/`TRANSPORT_FAILED`) falls through to the same bounded-retry-then-`await_human` ladder every other recoverable block class already uses (`DIRTY` joins the `STALE_REVIEW`/`PRE_EXISTING_RED`/`TRANSIENT_FLAKE` tuple in `dispatcher._pr_merge_remediation`); a genuinely exhausted ladder (`rec is None`) or a terminal `CONFLICT` verdict instead routes straight to a fix worker — see "A human is no longer the terminal handler for a conflict" below, which supersedes the two paragraphs this note used to end on. There is deliberately **no LLM conflict-resolution tier of its own** for the *mechanical* rung above — `_recover_dirty` only ever runs `reconcile_branch`'s deterministic git mechanics; a worker with the checkout is what actually resolves a genuine conflict now, dispatched once the mechanical ladder gives up rather than an agent bolted onto this rung itself. `DIRTY` also joins `CI_RESET_DELAY_CLASSES` (see "Wiring in dispatcher.py" below) — a successful `RECONCILED` outcome creates a new head SHA, so the re-enqueued `pr_merge` decision is deferred past the CI-reset window exactly like a successful `TRANSIENT_FLAKE`/`SONAR_HOTSPOT` rerun.

## A human is no longer the terminal handler for a conflict

Before this build, a `DIRTY` block that survived the mechanical ladder — either a rebase that hit a genuine content conflict (`ReconcileOutcome.CONFLICT`) or a ladder whose per-PR budget was already spent (`rec is None`, `reconcile_attempts_exhausted` true) — dead-ended at `await_human`: a person had to check out the branch, rebase or merge by hand, resolve the conflict, and force-push. Measured recovery for this class was zero of twenty-one parked workspaces over thirty days. A worker with the checkout can do the same work unaided — observed resolving the conflict *and* adapting its own contribution to a constraint the base had newly tightened, something no mechanical rebase could achieve — so both terminal shapes now route to `implementation_fix` instead.

**The shared predicate.** `merge_gate.conflict_fix_decision(blockers, rec, block_class, head_sha) -> bool` is `block_class is DIRTY and (rec is None or merge_recovery.reconcile_verdict_is_terminal(rec))` — `reconcile_verdict_is_terminal` is unchanged, `True` only when `rec is not None and rec.outcome is ReconcileOutcome.CONFLICT` (the one-member `_TERMINAL_RECONCILE_OUTCOMES` frozenset). When it returns `True` it has already called `merge_gate.enrich_conflict_blockers(blockers, rec, head_sha)` as a side effect: with a real `rec`, that strips every `pending_check` blocker and every `failed_reason` blocker whose detail starts with `"pending checks: "` (both of which `blockers_from_readiness` unconditionally attaches upstream), appends one `conflicted_path` blocker per path in `rec.conflicted_paths` (capped at 10, `_CONFLICT_PATH_CAP`, with a `conflicted_paths_truncated` reason blocker naming the remainder), and appends a `reason`/`branch_head` blocker naming `rec.pre_sha or head_sha` — the branch's own head at the moment the ladder gave up; with `rec is None` (budget exhausted, no reconciliation was even attempted this pass) only the `branch_head` blocker is appended, since there is no conflicted-path data this pass ever produced. This is the one predicate both the dispatcher and the `/api/answer` route call — the routing decision is defined once, not reimplemented per surface.

**Surface 1 — the merge-lane return.** `dispatcher._pr_merge_conflict_or_retry` (called from `_pr_merge_remediation` for every class in `_BOUNDED_RETRY_REMEDIATION_CLASSES`, `DIRTY` included) now checks `conflict_fix_decision` first: a `True` result calls the same `_fix_or_await` helper the generic `implementation_fix`-or-`await_human` fallthrough already used (extracted from `_pr_merge_remediation`'s tail so the branch count there stays flat), which enqueues `implementation_fix` with `render_remediation_instructions` — naming the conflicted paths and the branch head as instructions, not merely as parked blockers — when the team is admitted, or falls back to `await_human` when it is not. A `False` result (non-terminal `RACED`/`TRANSPORT_FAILED`, or any other bounded-retry class) is unchanged: `_maybe_retry_pr_merge` still spends the bounded-retry counter exactly as before. No `pr_<n>_remediation_retries.json` attempt is charged on the fix-routed path — the handover/spiral ladder (`detect_spiral`, `check_loop_guard`) is what now bounds a fix worker that keeps failing on the same conflict, not a park-and-retry counter sized for a different failure shape.

**Surface 2 — a human answering the parked question.** `alan/routes/answer.py`'s `_should_repark_unrecovered_block` calls the identical `conflict_fix_decision` (via `_conflict_fix_instructions`) before falling back to its existing repark-or-dispatch-anyway logic, so a workspace that was **already parked before this build shipped** — the 0-of-21 backlog above — routes to `implementation_fix` the moment a human clicks "proceed" on the existing question, with no re-park on contact the way it used to. The one asymmetry from the dispatcher surface: the answer route has no `effective_teams` override to inject, so admission is checked against the workspace's own pinned posture and roster via the new non-raising `alan.dispatch.team_is_dispatchable(ws, "implementation_fix")` — a posture/roster denial falls back to the existing repark path (unaffected, no raise, no 422) rather than dispatching a team the workspace cannot run.

**What did not need to change.** The unblock sweep's `transient_failed_check` recipe (`alan/unblock_sweep.py`, [unblocker.md](unblocker.md)) only re-examines parked workspaces whose merge readiness has gone green since parking, and a genuine conflict never reads green, so the sweep was never a path this backlog could clear through.

**Second line of defence: `pr_merge`'s own per-poll conflict check.** `attempt_mechanical_recovery`'s classification is a one-shot snapshot taken before dispatch; a branch can go `DIRTY` after that snapshot but before — or while — `pr_merge` is polling it, and the budget-exhausted residual above means a retried dispatch can also land on an already-`DIRTY` branch with no verdict attached at all. `alan/teams/_pr_merge_conflict.py` closes this independently of the dispatcher-side routing rule: `MERGEABLE_MERGE_STATES` there is the old mergeable set with `"DIRTY"` removed (`{"CLEAN", "HAS_HOOKS", "UNSTABLE", "BEHIND"}`), and `gh_pr_state_and_merge_status(pr_number, *, forge_target)` fetches both `state` and `mergeStateStatus` in one `gh pr view --json state,mergeStateStatus` call — replacing the old `state`-only `_gh_pr_state` (deleted from `pr_merge.py`), so this costs zero additional forge-API calls. `pr_merge._poll_until_done` calls it every iteration and, immediately after the existing `MERGED`/`CLOSED` terminal-state check and *before* `_evaluate_checks` ever runs, returns a `kind="conflict"` `PrMergeOutcome` the moment `mergeStateStatus == "DIRTY"` — the reason string names the conflict and explicitly disclaims a check-settling timeout, logged as a `merge_gate_conflict_detected` audit row (`pr_merge_audit.jsonl`). `pr_merge._confirm_ready_kind`'s existing second-source rollup/merge-state race guard is pointed at the same narrowed `MERGEABLE_MERGE_STATES`, so a late-arriving `DIRTY` there now reads `"pending"` instead of the stale `"ready"` it used to (previously `DIRTY` was, incorrectly, a member of the mergeable set consulted there). `PrMergeOutcome(kind="conflict", ...)` needs no `_build_handover` change — it falls through the existing kind-dispatch chain straight to `_await_human_handover`, using its own `_pr_merge_conflict.CONFLICT_OPTIONS` recovery text via the added `"conflict"` arm in `_merge_block_options`. This is a **second, independent** line of defence for the same terminal-conflict routing rule above — not a substitute for it: the dispatcher-side gate is expected to catch the overwhelming majority of cases before a merge attempt is ever dispatched, and this poll-loop check exists for the residual race window between classification and polling (including the budget-exhausted-`rec=None` residual, above).

## Measured-baseline freshness

Some registered files are not claims made by the PR that carries them — they are point-in-time measurements of what `main` currently is: tightening-only, hand-edited ratchet pins with no regeneration mechanism. `strict: false` branch protection (deliberately — the fleet merges several changes an hour and forcing every branch to rebase for changes that cannot possibly interact would tax everything to protect against a rare interaction) means a PR can merge while behind `main` whenever the two branches cannot interact. For a measured-baseline file that reasoning breaks: if `main` has moved the file since the PR's branch was cut, or the PR itself edits the file against a stale view of what it's measuring, the assertion in the merged commit can be silently wrong the moment it lands — the 2026-08-19 incident this build closes. `alan/teams/_pr_freshness.py` is the detection half of the fix; the branch-forward/re-await half already existed (`_pr_branch.update_pr_branch_outcome`, `merge_recovery.CI_RESET_DELAY_CLASSES`).

### Why staleness must be probed, not read off `mergeStateStatus`

`strict: false` branch protection means GitHub never reports `mergeStateStatus=BEHIND` as a blocking reason for an otherwise-mergeable PR — the field the rest of this module's classification ladder reads (`PrReadiness.merge_state_status`) is not authoritative for this hazard. There is no free signal already inside `PrReadiness` this build can key off, so `is_measured_baseline_stale` does its own probe: one `gh pr view --json headRefOid,baseRefName` to resolve the PR's own head/base, then one `gh api repos/{slug}/compare/{head_sha}...{base_ref}` — the *reverse* compare (head...base, not base...head) — which returns both `ahead_by` (how many commits `main` has that the PR's branch does not) and the full list of files those commits touched, in a single round trip.

### The registered set — one declaration, one-line-edit rule

`_pr_freshness.MEASURED_BASELINE_PATHS` is the single declaration (a flat `frozenset[str]`, no per-entry metadata) of every tightening-only ratchet pin in the repo: the desktop and mobile UI audit baselines and their pinned high-water marks (`alan/web/e2e/desktop-audit/baseline.json`, `alan/web/e2e/desktop-audit/baseline-high-water.ts`, `alan/web/e2e/mobile-audit/baseline.json`, `alan/web/e2e/mobile-audit/baseline-high-water.ts`), the backend/test file-size ratchet (`tests/size_baseline.py` and the aggregate bounds in `tests/test_size_ratchets.py`), the legacy `gh` read-stub list (`tests/gh_read_baseline.py`), the frontend duplication threshold config (`alan/web/.jscpd.json`), the E2E flake baseline (`alan/web/e2e/flaky-baseline.json`), the E2E nightly stress-sweep floor (`alan/web/e2e/stress-floor.json`), and the per-job CI duration budgets (`.github/ci-duration-budgets.json`) — eleven paths in all.

`tests/test_pr_freshness.py::test_registered_measured_baseline_path_exists` is parametrized one case per path, so a rename or deletion fails exactly the one case that moved rather than silently dropping coverage for the whole set. Adding a future baseline is a one-line edit to `MEASURED_BASELINE_PATHS` — deliberately a flat set rather than a `(path, enforcement)` tuple, since the recovery action (`update_pr_branch_outcome`) is identical regardless of where or whether a file is enforced; see "Enforcement asymmetry" below for why that uniformity is safe.

### The two-direction rule

Staleness fires when the PR's head is behind `main` **and** the hazard is live on *either* side of the gap:

1. **The PR's own diff touches a registered file** — the classic case: this PR's own baseline update is being measured against a `main` the PR hasn't caught up to.
2. **`main`'s unabsorbed commits touch a registered file** — the 2026-08-19 incident shape: a *different* PR changed the interface a baseline measures, merged after this PR's branch was cut, and this PR's own diff never goes near the registered file at all.

Covering only (1) catches exactly one of the two orderings that produce the failure — reverse which PR merges first and the identical outage recurs with the gate silent, because the PR that actually needs to notice `main` moved never touches the registered file itself. The reverse compare's `files` array gives (2) essentially for free (the same call that already yields `ahead_by`); `ForgePort.changed_files(pr_number, ...)` — a **third**, conditional `gh` call, only reached when the PR is behind and the gap side is clean — covers (1). The common up-to-date case (`ahead_by == 0`) therefore costs exactly two `gh` calls and never three.

### Fail-open on probe error, and why

`is_measured_baseline_stale` never raises — every `gh` failure (subprocess spawn error, timeout, non-zero exit, unparseable JSON, a missing `headRefOid`/`baseRefName` field) returns `False` and writes a distinct audit row (`baseline_freshness_probe_failed` for the refs read, `baseline_freshness_compare_failed` for the compare) instead. The probe reaches the forge through `ForgePort` — `read_pr` for the refs, `compare_base` for the compare, `changed_files` for the PR diff — and still never raises. Two failure-path reason strings shifted with that move, because a parsed port result cannot tell the cases apart: an unparseable compare body now audits `ahead_by_missing` (it used to audit `json_malformed`), and a refs read that decodes to no fields — including a literal `{}` — now audits `json_malformed` (a literal `{}` used to audit `head_or_base_ref_missing`). All five reason strings are otherwise spelled as before, and both shifts stay fail-open. This module deliberately never calls `_forge_errors.raise_for_infra`. The gate's callers offer no path for an exception here to become a paused-and-retried queue: `dispatcher._route_after_handover` wraps the whole post-handover routing call, including `_enforce_pr_merge_gate`, in a bare `except Exception` that routes to `_surface_routing_error` (a `ROUTING_ERROR` park), and `_apply_router_decision`'s own call site has no handler at all. A raised `ForgeRateLimited` here would park the workspace or propagate uncaught rather than pause-and-retry the way the rest of the merge-gate machinery does — so the probe fails toward "not stale, re-checked next pass" instead.

### Fail-closed on truncation

The GitHub compare API pages its `files` array; `_COMPARE_FILES_PAGE_CAP = 300` in `alan/forge_gh.py` is that page size (`_GAP_FILES_PAGE_CAP` is gone from `_pr_freshness`). A response whose file list reaches the cap could be hiding a registered-file touch past the page boundary, so the adapter sets `CompareRead.truncated` and `is_measured_baseline_stale` treats a truncated compare as implicated without needing to find a match — the one place this probe fails toward "stale" instead of "not stale," deliberately: silently under-covering an unusually large merge gap is exactly the hazard this build exists to close.

### Failure taxonomy: `update_pr_branch_outcome` over `reconcile_branch`, two block classes

Recovery reuses `_pr_branch.update_pr_branch_outcome` — the same light fast-forward `BEHIND_PLUS_TRANSIENT` already uses — not `alan/teams/_pr_reconcile.reconcile_branch`'s heavier conflict-recovery mechanics. A measured-baseline-stale PR is, by construction, a routine "branch is behind, bring it forward" situation, not a content conflict; `reconcile_branch` carries its own separate attempt-budget bookkeeping (`_MAX_RECONCILE_ATTEMPTS`/`_RECONCILE_LIFETIME_CAP`) built for genuine merge conflicts, and reusing it here would double-count budget for a class of block this isn't.

`_pr_branch.update_pr_branch_outcome` returns a `BranchUpdateOutcome` (`UPDATED`/`CONFLICT`/`FAILED`) instead of a bare bool; the thin bool wrapper `update_pr_branch` that once sat over it was deleted in X2.7 PR21, and the `BEHIND_PLUS_TRANSIENT` rung now compares the outcome to `UPDATED` itself — the existing `pr_update_branch_ok`/`pr_update_branch_failed` audit rows are unchanged. `merge_recovery._recover_stale_measured_baseline` narrows on that outcome into two distinct `MergeBlockClass` members, mirroring the precedent `_recover_stale_review` set (narrowing `STALE_REVIEW` to `STALE_VERIFIER_REVIEW` on success):

- `STALE_MEASURED_BASELINE` — either the initial classification, or the outcome when `update_pr_branch_outcome` returned `FAILED` (the branch could not be brought forward at all — a transport/API failure, not a conflict).
- `STALE_MEASURED_BASELINE_CONFLICT` — `update_pr_branch_outcome` returned `CONFLICT` (the update itself hit conflicting content). Each has its own `_STATIC_UNBLOCK_RECIPES` entry so a human reading the parked PR sees which of the two happened, rather than one blended "couldn't update" message.

Both classes join `DIRTY`/`STALE_REVIEW`/`PRE_EXISTING_RED`/`TRANSIENT_FLAKE` in `dispatcher._pr_merge_remediation`'s bounded-retry tuple, sharing the existing `REVISIT_CAP = 3` via `_maybe_retry_pr_merge` — a failed update never falls through to `implementation_fix` (there is nothing in the diff for a worker to fix) and never doubles the retry budget the rest of the merge-gate ladder already uses. `STALE_MEASURED_BASELINE` also joins `CI_RESET_DELAY_CLASSES` (`STALE_MEASURED_BASELINE_CONFLICT` does not — a conflict never mints a new head SHA, so there is nothing to wait for a reset window on): a successful update mints a new head SHA, so the re-enqueued `pr_merge` decision must defer past the CI-reset window exactly like a recovered `TRANSIENT_FLAKE`/`SONAR_HOTSPOT`/`DIRTY`.

### Detection wiring: the green short-circuit in `dispatcher._enforce_pr_merge_gate`

`_enforce_pr_merge_gate` already had exactly one path a ready-to-merge PR takes: `readiness.ok or not readiness.failed_reasons` returns the unmodified `pr_merge` decision immediately. `_readiness_after_freshness_check` sits at that one seam — when `_dispatcher_merge_brief.stale_measured_baseline_forces_check` (a thin delegate to `is_measured_baseline_stale`) reports the hazard, the readiness is rewritten via `dataclasses.replace(readiness, ok=False, failed_reasons=readiness.failed_reasons + (MEASURED_BASELINE_STALE_REASON,))` and execution falls through into the existing `merge_recovery.attempt_mechanical_recovery` path unchanged. Gating the probe at the single path every green PR takes makes "an unaffected PR sees no extra update, no extra wait, no behaviour change" a structural property of the code, not only a tested one — a PR that never reaches this branch (because it already failed readiness for an unrelated reason) never pays the two extra `gh` calls either, since the probe only runs from the green short-circuit.

### Enforcement asymmetry: three of the eleven registered files can never redden `main`

The eleven registered files differ in blast radius, and the declaration stays flat anyway:

- `.github/ci-duration-budgets.json` is consulted by the `Duration budgets (advisory)` job in `.github/workflows/tests.yml`, which runs on `pull_request` only (`docs/architecture/ci_duration_budgets.md`), and by the daily drift watch, which files issues and never gates anything. A stale copy can therefore fail a PR's own check, but never `main`'s.

- `alan/web/e2e/stress-floor.json` is consulted only by the nightly `.github/workflows/e2e-stress.yml` sweep — no PR-time gate reads it, so a stale copy can never turn a PR's own CI red, let alone `main`'s. It stays registered because the *measurement* is still a point-in-time claim about `main`; that nothing enforces it at merge time is orthogonal to whether a PR should be allowed to merge a stale copy of it.
- `alan/web/e2e/flaky-baseline.json`'s enforcement point is not a workflow file's own gate declaration — `.github/workflows/tests.yml`'s "Flake ratchet" step runs `node scripts/report-flaky.mjs --ratchet`, which compares the run's actual flaky spec files against the checked-in baseline and exits 1 on a new flake class. That step is `pull_request`-only and `success()`-gated (a red run already has a first-order failure to report, and push-to-main must never be blocked by a residual flake — a red `main` freezes deploys). A stale baseline can therefore redden a PR's own required check, but never `main`'s, since a red required check cannot merge in the first place.

Neither asymmetry is encoded as per-entry metadata on `MEASURED_BASELINE_PATHS` — the recovery action is identical (bring the branch forward) regardless of where or whether a file is enforced, so a `(path, enforcement)` tuple would buy nothing behaviourally while breaking the one-line-edit rule above. The asymmetry is documented here and pinned by test names (`tests/test_pr_freshness.py`'s registry tests cover existence only, not enforcement point) rather than by runtime branching.

## Pre-merge closing-link read-back

Nothing previously compared the forge's own record of which issues a pull request will close against the set the workspace brief declared it fixes. A `Delivers-Issues:` trailer that produced a closing line broken by truncation, or one wrapped in a code span by the worker's own prose, shipped silently — the issue stayed open after merge, and nothing before this build ever checked. `alan/teams/_pr_closing.py::gh_pr_closing_issue_numbers` and `merge_gate.readiness_after_closing_links_check` close that gap by reading the record back and comparing before merge, not by rebuilding the write-side defences (fence-aware scanning, appended closing lines, reserved truncation space) that already exist for the write half.

**Where it runs.** `readiness_after_closing_links_check(ws, pr_number, readiness, forge_target)` is called from `merge_gate.attempt_recovery` immediately after `readiness_after_freshness_check`, before the `readiness.ok or not readiness.failed_reasons` green-shortcut check — the identical seam the measured-baseline freshness probe above already uses, for the identical reason: only a PR that otherwise reads ready is worth spending a forge call to double-check, and `attempt_recovery` is the one pre-merge gate both `dispatcher._enforce_pr_merge_gate` (before a handover's suggested `pr_merge` is ever enqueued) and `/api/answer`'s `_apply_merge_gate` (before a human's "proceed" answer dispatches the resolver) already funnel through — `pr_merge.py` itself stays untouched and out of the diff.

**Skip conditions, cheapest first.** The check returns the readiness unchanged, with no forge call at all, in two cases: the readiness already reads not-ready (nothing to double-check yet — a DIRTY or CI-red PR is not close to merging regardless of its closing links), and `_pr_closing.parse_delivers_trailer(ws.meta.description).issues` is empty (the brief declared no issues to close, so there is nothing to reconcile against). Only past both guards does it call `_pr_closing.gh_pr_closing_issue_numbers(pr_number, forge_target=forge_target)` — one `gh pr view --json closingIssuesReferences` call, following the exact pattern `_pr_merge_conflict.gh_pr_state_and_merge_status` already established (its own module, invoked from `_pr_closing.py`, `_pr_branch.py` untouched).

**The comparison.** When the declared trailer issues are not a subset of the forge's returned `closingIssuesReferences` numbers, the readiness is rewritten via `dataclasses.replace(readiness, ok=False, failed_reasons=readiness.failed_reasons + (f"{CLOSING_LINKS_MISSING_REASON} {missing}",))`, where `missing` names each undelivered issue as `#N`. Execution then falls through into the existing `merge_recovery.attempt_mechanical_recovery` path unchanged, exactly like a measured-baseline-stale rewrite does.

**Classification and routing.** `merge_recovery.MergeBlockClass.CLOSING_LINKS_MISSING` is a new rung at the very end of `_classify_block_head` — after `DIRTY`, `STALE_MEASURED_BASELINE`, and `NO_CHECK_RESULTS`, so every mechanically recoverable class still wins ahead of it. There is no recovery rung for it in `attempt_mechanical_recovery` (nothing to reconcile or rerun — the fix is a one-line edit to the PR body, not a mechanical git operation), and it is deliberately **not** a member of `CI_RESET_DELAY_CLASSES`, `MERGE_LANE_POLL_CLASSES`, or (unlike `NO_CHECK_RESULTS`) `dispatcher._BOUNDED_RETRY_REMEDIATION_CLASSES` either — a bounded retry only makes sense for a condition that might resolve on its own; a missing closing link never will without an edit. It falls straight through `dispatcher._pr_merge_remediation`'s bounded-retry check and its `SONAR_HOTSPOT` check to the generic `implementation_fix`-or-`await_human` fallthrough, carrying `_STATIC_UNBLOCK_RECIPES[CLOSING_LINKS_MISSING]`'s instruction to append the missing `Fixes #N` line(s) and re-dispatch `pr_merge`.

**Order-independent trailer parsing.** `_pr_closing.parse_delivers_trailer` used to read only the workspace description's *last non-blank line* — anything appended after the trailer (a worker's closing remark, a decomposer's amendment) hid it entirely. It now reuses `_pr_closing._scan_state`'s existing fence- and comment-aware line walk (the same one that finds `Fixes #N` closing lines) to collect every line starting with `Delivers-Issues:` anywhere in the description, taking the last one found — so a trailer quoted in prose or fenced inside a code block is still ignored exactly as before, but a trailer that is no longer the literal final line is no longer silently dropped. This is read from `ws.meta.description` — the workspace brief — and only ever that; the pull request body is a different, larger surface this change does not touch (see `pr_iteration_pipeline.md`'s D23 for why the two must not be conflated).

## Shared flaky-gate substrate (one source of truth)

`alan/teams/_pr_flake_ledger.py` (the shared flaky-check allowlist, rerun-budget accounting, and the cross-PR flake ledger) — together with `alan/teams/_pr_branch.py` for the rerun mechanics (`rerun_flaky_checks`/`rerun_external_gate`) and `alan/teams/_pr_state_paths.py` for the per-PR rerun counter — is the shared home for everything both the pre-approval verifier lane (`verification.py`) and the post-approval merge-gate lane (`merge_recovery.py` via the dispatcher) need to agree on, so the two lanes can never drift apart in what they consider flaky or how many reruns they allow:

- `SHARED_FLAKY_ALLOWLIST: frozenset[str]` — three members today: `"Frontend E2E (Playwright, blocking)"` (`_E2E_CHECK_NAME`, the original member), `"Backend tests + coverage"`, and `"Frontend tests + coverage (100/100/100/100)"` (the two test-executing unit-test checks, added later — see "Allowlist widened to the unit-test checks" below). A check that isn't on this allowlist (e.g. a static-analysis/quality gate, or `"SonarCloud (advisory)"` — deliberately excluded, see below) is left to its existing handling untouched; membership is exact-match against the job `name:` values in `.github/workflows/tests.yml`, never normalised/lowercased/stripped/guessed. `REBASE_SAFE_FLAKY_CHECKS: frozenset[str]` is a strict subset — today just `{_E2E_CHECK_NAME}` — that gates only the `BEHIND_PLUS_TRANSIENT` write rung; see "Write-path hold" below.
- `max_gate_reruns() -> int` — reads `ALAN_MAX_EXTERNAL_GATE_RERUNS` (default **2**, raised from the prior single-lane default of 1 so a genuine two-stage flake — one firing pre-approval, one firing at the merge gate — gets one attempt at each point off a single shared budget).
- `_pr_state_paths.load_gate_rerun_count` / `_pr_state_paths.bump_gate_rerun_count` (`pr_<n>_gate_reruns.json` under `state_dir()`) — the shared **per-PR-per-head-SHA** counter both lanes read and bump, plus a non-resetting **lifetime** ceiling (`_pr_flake_ledger._GATE_RERUN_LIFETIME_CAP = 6`). Because the per-SHA budget is shared *within a head SHA*, a flake cannot be retried more times than intended by bouncing between the two firing points on the same commit — and a new head SHA grants both lanes a fresh per-SHA budget, bounded in total by the lifetime ceiling. `_pr_flake_ledger.gate_reruns_exhausted(pr_number, head_sha, *, forge_target)` is the single decision point both lanes call instead of comparing counts themselves — see "Evidence-based classification" below for the full per-SHA-reset rationale and the two-directional `None` rule.
- `rerun_flaky_checks(pr_number, task_id, failing_checks, *, forge_target)` — loops every failing check through `rerun_external_gate`, returning `True` if any rerun was triggered. Both `_verification_gates._maybe_rerun_flaky_gates` and `merge_recovery._recover_transient_flake` call this instead of each keeping its own loop.

Never weakens a gate: nothing in this module edits `_KNOWN_FLAKE_REGISTRY` or skips a check from running — it only reruns the check and, on exhaustion, hands the PR to a human. The one sanctioned narrowing of `failing_checks` is the aggregate view below (`aggregate_set_aside`): it fires only for a check the forge target declares as an aggregate **and** authoritative, and only when a non-aggregate check also fails. It is not a relaxation, because the aggregate is the OR of the checks that remain in the list — `failed_reasons` and `ok` are never touched, so the PR stays red and the park text stays truthful.

### Evidence-based classification: `pr_<n>_gate_survived.json`

The allowlist above is a naming-based default posture: a first failure of any `SHARED_FLAKY_ALLOWLIST` member is treated as known-unreliable, full stop, regardless of whether that particular failure was ever actually re-run. That is wrong once a rerun *has* happened and the check stayed red on the unchanged commit — that outcome is decisive evidence the failure is not intermittent, and the naming-based default must stop overriding it.

`_pr_flake_ledger.py` records that evidence as the exact inverse of the rescue record above:

- `flake_survived_checks(before, after, *, head_sha_before, head_sha_after) -> tuple[str, ...]` mirrors `flake_rescued_checks` line for line, with the polarity flipped: it returns the checks that were failing before the rerun **and are still failing after** (`c in after.failing_checks`, not `not in`), under the identical three guards — `after` is a real `PrReadiness` (not a `ReadinessUnavailable`), no `after.pending_checks`, and `head_sha_before == head_sha_after` (a stale before/after pair proves nothing; a sha mismatch means a later commit landed, not that the rerun settled anything).
- `record_flake_survival(pr_number, survived, head_sha, *, forge_target)` does a read-modify-write of `pr_<n>_gate_survived.json` (`{check_name: head_sha}`, mkstemp + `os.replace`) — a *sha-keyed* record, not a counter: a fresh push invalidates every prior survival entry automatically because the recorded sha stops matching. No new lock (unlike `flake_failures.json`'s `_flake_failures_lock`) — one verification worker owns a PR at a time, so this file has no concurrent-writer hazard to guard against.
- `_verification_gates._maybe_rerun_flaky_gates` calls `record_flake_survival` right after the existing `record_flake_occurrence` call, on the same `readiness`/`settled`/`sha_before`/`sha_after` values — a rerun's outcome is either a rescue or a survival (or neither, if a guard above fails open), never both.

`evidenced_actionable_failing_checks(readiness, pr_number, head_sha, *, forge_target) -> tuple[str, ...]` is the classifier that consumes the record — deliberately a *sibling* of `actionable_failing_checks`, not a replacement:

```
evidenced_actionable_failing_checks(readiness, pr_number, head_sha)
    == actionable_failing_checks(readiness)
        ∪ {c in SHARED_FLAKY_ALLOWLIST : c in survived_at_head_checks(pr_number, head_sha)}
```

with one early exit that keeps it fail-open exactly where evidence is absent:

- **`head_sha is None`** (the caller could not resolve a current head sha) → returns `actionable_failing_checks(readiness)` unchanged. No sha, no evidence.
- Otherwise: every failing check that is **not** quarantined and (**not** on `SHARED_FLAKY_ALLOWLIST` **or** in `survived_at_head_checks(pr_number, head_sha)`) is included. A missing survivor entry, or one keyed to a different (stale) sha, contributes nothing — the check stays classified as known-unreliable exactly as before. A quarantined check is excluded regardless of survivor evidence — quarantine is a base-branch/known-flake-ownership judgement this evidence does not override.

The rerun *budget* is deliberately **not** consulted (changed 2026-08-04, incident PRs #944/#947): a settle-and-compare rerun that stayed red on the same sha is a controlled experiment and is sufficient on its own, while budget exhaustion is only accounting — the merge lane can burn the whole budget without ever settling (see the merge-lane gap below), so exhaustion carries no evidence in either direction. The old `load_gate_rerun_count >= max_gate_reruns()` conjunct made the verifier discard its own freshly-written survivor record (count 1 of 2), print `GATE_ACTIONABLE: no` against on-disk contrary evidence, and reroute a real diff-caused failure to `pr_merge`. Exhaustion-without-survivor-data still does NOT promote — promotion without an identified cause would send `implementation_fix` chasing possibly-flaky failures, the futile-fix loop this marker system exists to prevent. `survived_at_head_checks(pr_number, head_sha, *, forge_target)` is the shared sha-match helper both lanes use.

`actionable_failing_checks` itself is untouched by the evidence-based reclassification above. Its caller set has changed since, though: `merge_recovery._has_genuine_failing_check` (the `BEHIND_PLUS_TRANSIENT` recoverable-block predicate) now calls the narrower `rebase_blocking_failing_checks` instead of `actionable_failing_checks` directly — see "Write-path hold: `REBASE_SAFE_FLAKY_CHECKS`" below — so that auto-rebase/auto-merge path stays out of scope both for this evidence-based reclassification and for the later allowlist-widening change that made the divergence necessary. `actionable_failing_checks` itself is still consulted, unmodified, wherever the full `SHARED_FLAKY_ALLOWLIST` routing judgement is wanted. The classifier output is computed once per downgrade by `_verification_gates._resolve_actionable_gate_checks` and threaded through `_downgrade_output`/`_format_gate_block`/`_gate_actionability_lines`, which is what produces the `GATE_ACTIONABLE:` marker and the "attributable to this diff" prose in the posted PR review — so the classification the human reads and the classification a downstream tool parses can never disagree.

### Rerun-budget consistency: per-head-SHA, with a non-resetting lifetime ceiling

The survivor-evidence store above is keyed per head SHA (`record_flake_survival` writes `data[check] = head_sha`; `survived_at_head_checks` filters on equality). Before this fix, the rerun *budget* it was evaluated against was a single per-PR integer that never reset on a new head SHA — an internal inconsistency. Failure chain: a PR burns both reruns on genuine flakes under head SHA A; a real failure appears on head SHA B; `_flaky_gates_eligible`/`gate_reruns_exhausted` finds the exhausted counter and no rerun fires; with no rerun, `record_flake_survival` is never called for B, so `survived_at_head_checks(pr, B)` is empty; `evidenced_actionable_failing_checks` stays at the naming-based default (not actionable); when the diff-join fallback (`diff_attributable_e2e_checks`, below) *also* comes back empty — i.e. the failing spec isn't in the diff and no locator token was removed — the PR mis-parks on budget spent against a different commit.

`gate_rerun_count_path`'s on-disk payload is now `{"head_sha": <sha>, "count": <int>, "lifetime": <int>}` (parsed into `_pr_state_paths.GateRerunState`). `count` is the reruns spent on `head_sha` and resets whenever the stored head SHA differs from the current one; `lifetime` is the total reruns ever spent on the PR and never resets, capped at `_pr_flake_ledger._GATE_RERUN_LIFETIME_CAP = 6`. `gate_reruns_exhausted(pr_number, head_sha, *, forge_target)` is `True` when the per-SHA `count >= max_gate_reruns()` **or** `lifetime >= _GATE_RERUN_LIFETIME_CAP`, whichever binds first.

Two `None` rules resolve in opposite directions — do not merge them:

| Case | Rule | Why |
|---|---|---|
| Stored head SHA is `None` (legacy bare-int file, or never bumped) **and** a current SHA is available | reset `count` to 0 | Otherwise a PR already at `count >= max_gate_reruns()` deadlocks permanently — it can never reset (the stored SHA stays `None` forever) and can never bump (bumping requires passing eligibility first). |
| Current SHA is `None` (the `gh` fetch failed) | do **not** reset; use the stored `count` | Fail-closed — a persistent `gh` failure must not grant unlimited reruns by masquerading as "always a fresh commit." |

The legacy migration is **read-time**, not a one-shot rewrite: nothing writes the dict payload until a bump actually lands, so a legacy bare-int file re-parses and re-resets (`GateRerunState(None, N, N)`) on every read until then — not once. This is harmless: a pass that triggers no rerun spends nothing, and the first successful rerun converts the file to the dict payload permanently. The legacy count also counts against the lifetime ceiling (`GateRerunState(None, N, N)`, not `GateRerunState(None, N, 0)`), so the ceiling can never be bypassed by the migration. Rollback direction is equally benign: reverting this fix leaves the old bare-int parser reading the dict payload as a non-int, defaulting to `0` and granting in-flight PRs one fresh budget — no crash, no corruption.

**Amplification bound.** A rerun can indirectly produce a new head SHA, which is exactly the mechanism the reset predicate must tolerate without becoming unbounded: `attempt_mechanical_recovery` calls `_pr_branch.update_pr_branch_outcome` on the `BEHIND_PLUS_TRANSIENT` rung (`merge_recovery.py`) — a merge commit, therefore a new head SHA — reached precisely when no failing check is genuine (`_is_behind_plus_transient` → `_has_genuine_failing_check`). `dispatcher.py`'s recovered-decision path does not call `bump_remediation_retry_count` on that rung, so the remediation-retry counter does not bound the resulting chain; the only bound left is `loop_guard.REVISIT_CAP = 3`, roughly 4 `pr_merge` passes. Without a lifetime ceiling, per-SHA resets alone would let a single PR spend up to 8 reruns (2 per pass × 4 passes) against a hard 2-per-commit intent. `_GATE_RERUN_LIFETIME_CAP = 6` replaces that unbounded-by-8 worst case with a firm ceiling; the common case (0–2 reruns total) is untouched, and the rebase count itself is unchanged by this fix — `BEHIND_PLUS_TRANSIENT` fires today too, this only changes how many *job* reruns ride on top of full CI runs that were already going to happen. No env var controls the ceiling — it is a safety backstop, not a tuning knob; if `ALAN_MAX_EXTERNAL_GATE_RERUNS` is raised above 6, the backstop binds first.

### Diff-join attribution (fallback when no survivor evidence exists)

When `evidenced_actionable_failing_checks` comes back empty, `_resolve_actionable_gate_checks` consults `_pr_flake_ledger.diff_attributable_e2e_checks(readiness, pr_number)` — a first-pass attribution that joins the failing E2E specs' identity against the PR's own diff, no rerun needed. Two rules, either promotes every allowlisted (non-quarantined) failing check:

- **(a) spec-in-diff** — a failing spec's file is modified or added by the PR (`fetch_diff_files`, suffix-matched on path boundaries: annotation paths are web-relative `e2e/x.spec.ts`, diff paths repo-relative). The 2026-08-04 #944 shape: the PR's own new spec failing.
- **(b) removed-locator token** — a `getByTestId('…')`/`[data-testid=…]` token from the failure message (the `message` field of the check-run annotation, see "Where failing-spec identity comes from" below) appears on a removed diff line and on no added line (`fetch_pr_diff_patch`, capped at 1 MB — over-cap returns None rather than truncating, since a truncated patch could hide a token's re-add). The #947 shape: a testid the diff deletes, asserted by an untouched spec.

#### Where failing-spec identity comes from: check-run annotations, never the job log (2026-08-20, #1162)

`_pr_branch.fetch_failing_e2e_tests(pr_number, forge_target=…)` resolves the failing Actions job ids from the PR's `statusCheckRollup` (`fetch_failing_job_ids` → `failed_job_id`, the `/job/<id>` segment of each failing check's `detailsUrl`) and then reads `gh api repos/{owner}/{repo}/check-runs/{job_id}/annotations` for each (an Actions job's `databaseId` *is* its check-run id) — the shared `_pr_branch.fetch_check_run_annotations`, the same fetcher `_pr_sonar.list_sonarcloud_annotations` uses for SonarCloud, parameterised by `on_fail` (E2E audits `fetch_e2e_annotations_failed`, Sonar keeps `list_sonarcloud_annotations_failed`) and by `as_transport` (the E2E path reads as the forge-scoped transport identity through `transport_check_run_annotations`; Sonar keeps ambient `gh` auth through `check_run_annotations`). `alan/e2e_failures.parse_failing_e2e_annotations` keeps only `annotation_level == "failure"` rows whose `path` ends in `.spec.ts` and that carry a non-empty `title` — this drops the job's own `Process completed with exit code 1.` row (`path=.github`), the `🎭 Playwright Run Summary` notices, and any backend pytest annotation a multi-job failure would otherwise let through. `spec` is therefore the repo-relative path (`alan/web/e2e/x.spec.ts`); `_spec_matches_diff` suffix-matches and `_spec_ledger_key` takes the basename, so both consumers are path-shape agnostic.

Why not the job log: from #954 (2026-08-04) until #1162 this function scraped `gh run view --job <id> --log-failed` for `::error file=…,title=…::message` lines. The Actions runner **consumes** workflow commands — the rendered log carries `##[error]<message>` with the `file=`/`title=` properties stripped — so the regex matched nothing on any real job (measured on PR #1159's two E2E jobs: 0 `::error` lines, 2 `##[error]` lines) and `fetch_failing_e2e_tests` returned `None` on every PR. Every downstream consumer was silently dead for sixteen days: rules (a)/(b) above never promoted a check, the spec-granular flake ledger never wrote a `spec:` key (production `flake_failures.json` held 26 PRs under the bare check key and zero `spec:` keys), and the park-path blocker enrichment below always reported `e2e_detail_unavailable`. The tests had only ever fed synthetic `::error` fixtures. Annotations are also what makes a *flaky* spec attributable: Playwright's GitHub reporter annotates the attempt-1 failure even when the retry passes, and `report-flaky.mjs --ratchet` now emits its own `::error file=alan/web/e2e/<spec>,title=Flake ratchet: new flaky spec file` annotation per fresh flaky file (see `e2e_testing.md`), so a new spec that trips the PR-only flake ratchet reads as the PR's own defect (`GATE_ACTIONABLE: yes` via rule (a)) instead of the naming-based "known-flaky" default that parked PR #1159. `fetch_failed_log` itself stays — `dependency_sweep._detect_upstream_block` still parses npm ERESOLVE text from it (see `dep_sweep.md`); only the E2E identity path switched sources.

It only ever *promotes* — never demotes, never touches non-allowlisted checks, never promotes quarantined ones — and every fetch failure returns `()` (fail toward not-actionable): promotion without evidence would send `implementation_fix` chasing possibly-flaky failures, and the degraded behavior is exactly the pre-existing one, with survivor evidence converging the same shapes one rerun later. It runs only when the evidence path returned nothing, so it costs zero gh calls on already-actionable or green passes.

**Merge-lane survivor evidence (closed, 2026-09-02):** `merge_recovery._recover_transient_flake` (the post-approval `pr_merge` lane) triggers a rerun and bumps `pr_<n>_gate_reruns.json` but returns immediately — it never runs its own settle-and-poll loop, so it can never observe a `before`/`after` pair *inside one call* the way the pre-approval verifier's `_maybe_rerun_flaky_gates` does. What closes the gap instead is that the merge lane's own re-enqueue-and-re-sample cycle already produces that pair *across* passes: the dispatcher defers the re-enqueued `pr_merge` past the rerun's check-run reset window (`_delay_for_ci_reset`, see "Wiring in dispatcher.py"), and the next `_enforce_pr_merge_gate` pass re-samples `readiness` fresh and calls `attempt_mechanical_recovery` again — which is exactly a "before" (the readiness that triggered the rerun) and an "after" (the readiness on the following pass), no new poll loop required. `_merge_lane_survivor_evidence` writes `record_flake_survival` on that following pass when three guards all hold: the readiness fetch itself succeeded (`readiness.gh_ok`), nothing is still `pending_checks` (checks have settled one way or the other), and `gate_rerun_count_for_sha` shows at least one rerun already spent against the *current, unchanged* head SHA (`_rerun_concluded_at_head`) — the same head-SHA-keyed reset-awareness the rerun budget itself already relies on, so a fresh commit never gets credited with a stale rerun's evidence. If the check is still failing at that point, `evidenced_actionable_failing_checks` can now promote it out of the naming-based known-unreliable default on the *next* verifier or merge-gate pass, closing the second DoD requirement (repeated failure at an unchanged commit is genuine evidence, and the merge lane now acts on it exactly as the review lane already did). What remains verification-lane-only is the *rescue* side: `record_flake_occurrence` (the cross-PR flake-frequency sidecar behind the quarantine-proposal issue-filing) still has exactly one caller, `_verification_gates._maybe_rerun_flaky_gates` — a rescue means a rerun *actually cleared* the check, which is advisory-only information for a human deciding whether to add a check to the flaky allowlist, not gating evidence a merge-gate pass needs to act on, and adding a merge-lane producer for it would need its own settle poll for a signal nothing downstream of this build consumes; declining that is the same "no new mechanism beyond what the DoD requires" call the 2026-08-04 gap analysis made, now narrowed further because the *survival* half — the half this build's DoD actually needs — no longer has a gap to accept.

**Survivor proof is scoped to the check(s) the rerun actually targeted (closed, 2026-09-03, PR #1292 review):** the guard above (`_rerun_concluded_at_head`) is purely SHA/count-based — it proves *a* rerun happened at this head, not *which* check(s) it covered. Left that way, a rerun triggered for one allowlisted check (say the E2E gate) could wrongly credit a *different* allowlisted check that only started failing afterward at the same unchanged SHA (say the backend suite) as having "survived a rerun," when that check was never actually re-executed. `GateRerunState` (`_pr_state_paths.py`) now carries a fourth field, `checks: tuple[str, ...]`, populated from the same `readiness.failing_checks ∩ SHARED_FLAKY_ALLOWLIST` set `_recover_transient_flake` already passes to `rerun_flaky_checks` — the exact checks this rerun targeted, not a broader "was flaky-only at classification time" set. The JSON payload omits the `"checks"` key entirely when empty, so the on-disk shape for every caller that never passes `checks=` (the reconcile-attempt-count and pre-2026-09-03 gate-rerun call sites, which reuse the same `GateRerunState`/`bump_gate_rerun_count` machinery) is byte-identical to before this fix. `gate_rerun_checks_for_sha(pr_number, forge, *, head_sha)` is the new sha-matched reader (mirrors `gate_rerun_count_for_sha`'s reset-awareness: a SHA mismatch yields an empty set, same as no rerun at all). `_merge_lane_survivor_evidence` now intersects `readiness.failing_checks ∩ SHARED_FLAKY_ALLOWLIST` with that targeted set before calling `record_flake_survival` — a check that is failing at the settled head but was never part of the rerun that consumed the budget contributes no survivor evidence, exactly as the pre-approval verifier lane's `flake_survived_checks`(`before`, `after`) already guarantees by construction (its `before.failing_checks` *is* the targeted set, by definition of what a settle-and-compare rerun reruns).

### Survivor proof is additionally spec-gated for the blocking E2E check (closed, 2026-09-06)

The guards above prove a rerun happened, targeted the right check(s), and settled — but for the blocking end-to-end check specifically, a rerun that reds a *different* Playwright spec than the one that failed before it is not decisive evidence of a diff-owned defect; it is evidence of flake. The check's own name covers far more than Playwright — dependency sync, package install, the frontend build, browser install, a port-cleanup step, and the job timeout can all redden it with no resolvable spec names at all. `_pr_flake_ledger.spec_gated_survivors(survived, *, specs_before, specs_after)` is the pure gate both producers apply immediately before writing: it returns `survived` unchanged whenever either spec side is empty — undetermined means check-level, never silence, so a genuinely broken frontend build still produces an actionable gate and a fix worker exactly as before — and otherwise drops only `_E2E_CHECK_NAME` from the written tuple when the before/after spec basename sets are disjoint. The two coverage checks on `SHARED_FLAKY_ALLOWLIST` have no spec source and are never spec-gated. The stored record's shape (`{check_name: head_sha}`) and all three consumers' keying (actionable-gate promotion, `classify_block`'s routing, and `pr_merge`'s escalation diagnostics) are untouched — only the decision to write the E2E check's survival is gated.

The review lane (`_verification_gates._record_gate_survival`) derives `specs_before` from the same `failing_e2e_spec_names` fetch `_maybe_rerun_flaky_gates` already makes before triggering its rerun (via `_pr_flake_ledger.flatten_spec_names`, no duplicate fetch) and fetches `specs_after` via `_pr_flake_ledger.failing_e2e_specs` against the settled readiness. The merge lane observes its before/after pair *across* dispatcher passes rather than within one call (see "Merge-lane survivor evidence" above), so it has no in-process before side to reuse: `_recover_transient_flake` persists the before-side spec names into `pr_<n>_gate_reruns.json` as a flat `specs` list (`GateRerunState.specs`, written via `bump_gate_rerun_count(..., specs=...)`) at rerun-trigger time — before the trigger, not after, because `rerun_flaky_checks` resets the check-run rollup the annotations are read from, so a post-trigger fetch would persist an empty spec list on nearly every trigger and silently pin the merge lane to check-level forever. `_record_merge_lane_survival` (the extracted body of the compare-side write, called from `_merge_lane_survivor_evidence`) reads that persisted list back via `gate_rerun_specs_for_sha` and fetches the after-side specs fresh via `failing_e2e_specs` against the current readiness.

The persisted `specs` field degrades exactly like the pre-existing `checks` field, and deliberately not like the rerun counters: a malformed value (wrong type, non-string entries) yields `specs=()` on the same parse tier as `checks` in `_parse_gate_rerun_dict`, entirely independent of the `head_sha`/`count`/`lifetime` reset path — routing a malformed spec list through the counter-reset path would silently grant a fresh rerun ladder, a worse bug than the one this closes. Absent persisted specs — a record written before this change, or a rerun whose before-side lookup produced nothing — both lanes fall back to check-level via the same empty-side guard in `spec_gated_survivors`.

The review lane's rerun bookkeeping still persists neither targeted checks nor specs on its own bump call (`_maybe_rerun_flaky_gates`'s `bump_gate_rerun_count(pr_number, forge_target, head_sha=sha_before)` call, unchanged) — that asymmetry is deliberate and load-bearing, not an oversight: it is what forces the merge lane to fire its own rerun before it can ever credit survival, rather than crediting a review-lane rerun it never itself observed.

### Operator recovery: a stale pre-change stamp under a no-commit fix worker

This change gates future writes; it makes no claim about survivor records already on disk. An ordinary lap self-clears when the head SHA moves, since every survivor entry is keyed to a specific SHA and a fresh commit invalidates it automatically. A fix worker that produces no commit leaves the SHA unchanged, though — a recurring shape here, not a hypothetical — so a stale pre-change stamp stays live at that SHA and the loop guard's spiral detector keeps bailing on the resulting false `GATE_ACTIONABLE: yes`. The recovery is operator-facing: delete the affected pull request's `pr_<n>_gate_survived.json` under `state_dir()/<owner>/<repo>/` (the per-engine state directory). That drops the PR's survivor evidence at every SHA and re-enters it in the bounded rerun ladder from scratch — failing open toward "treat as flaky," the same direction this whole change moves.

### Observed and deferred: survivor-evidence files are never pruned

`pr_<n>_gate_survived.json` files accumulate indefinitely under the per-engine state directory — no sweep ever removes one, even long after the pull request it names has merged or closed. This is a real finding, not addressed by this change: the population is bounded by every pull request ever gated over the life of the repository, not by pull requests currently in flight. Recorded here for a future cleanup sweep, not absorbed into this build.

### `pr_merge`'s own diagnostics fetch stays a separate, unthreaded call

`pr_merge._escalation_diagnostics`'s `_diagnostics_e2e_lines` (see "Operator-facing failing-test detail" above) calls `_pr_branch.fetch_failing_e2e_tests` independently, to render the currently-failing spec names into the escalation message a human reads. This is deliberately not threaded through the spec-gating comparison above — it runs only at escalation time, after routing has already been decided, and exists to inform a human rather than to gate a write. A future reader should not read the absence of a shared code path here as an oversight.

### Verifier-lane parity: flaky-only downgrades route to `pr_merge`, not `implementation_fix`

`alan/teams/_pr_flake_ledger.py::flaky_only_failing(readiness) -> bool` is the single shared predicate behind three consumers that must never drift apart on "what counts as flaky-only":

1. `merge_recovery._is_transient_flake(readiness, survived_at_head)` — delegates to `_pr_flake_ledger.flaky_only_failing(readiness)` **after** excluding any failing check with survivor evidence at the current head: `attempt_mechanical_recovery` resolves `survived_at_head_checks` lazily (only when the failure already classifies flaky-only via `flaky_only_failing` — the sole condition under which the evidence can change the outcome; a failed head-sha fetch yields an empty set, failing open to today's behavior) and threads it through `classify_block(..., survived_at_head=...)`, so a proven-deterministic failure classifies `GENUINE` → `implementation_fix` instead of burning another rerun.
2. `_verification_gates._flaky_gates_eligible(pr_number, readiness, head_sha, forge_target)` — `flaky_only_failing(readiness) and not gate_reruns_exhausted(pr_number, head_sha, forge_target=forge_target)`, gating the verifier's own pre-approval rerun (`_maybe_rerun_flaky_gates`, above). `_maybe_rerun_flaky_gates` fetches the head SHA once, after the no-I/O `flaky_only_failing` early exit and before this eligibility check, and reuses it for the eventual `bump_gate_rerun_count(..., head_sha=...)` call — no duplicate `gh` call.
3. The verifier-lane downgrade route (new): `_verification_gates.resolve_external_gates` computes `flaky_only = flaky_only_failing(readiness) and not evidenced_actionable_failing_checks(readiness, pr_number, head_sha, forge_target=forge_target)` whenever it downgrades an `APPROVE` to `REQUEST_CHANGES` on external-gate failures, and returns it on a `GateDowngradeResult(output, downgraded, flaky_only, dirty)` dataclass — `dirty` is the sibling boolean, set from `readiness.merge_state_status == "DIRTY"` on the same downgrade. `VerificationTeam._build_verdict_handover` threads both — plus the `non_actionable` sibling described under "First-round dead-end guard" below — into `suggestions_for_verdict(last_output, pr_number, gate_flaky_only=flaky_only, gate_dirty=dirty, gate_non_actionable=non_actionable)`: on a `REQUEST_CHANGES` effective verdict, any of the three being `True` (with a resolvable `pr_number`) yields `("pr_merge",)` instead of `("implementation_fix",)` — independent booleans, not one merged flag, so a PR that is simultaneously `DIRTY` and flaky-only-failing still routes correctly regardless of which condition a future change removes first. `resolve_external_gates` also resolves PR-gate readiness on a `REQUEST_CHANGES` verdict carrying zero effective critical findings (the `rescue_only` gate-path mode — see `docs/architecture/pr_iteration_pipeline.md`'s D14 "Gate-path modes" note); that mode runs the settle-wait and the bounded flaky-gate rerun below but never sets `flaky_only`/`dirty` and never downgrades — both stay computed, and therefore possibly `True`, only on the `downgrade` (APPROVE) arm. Unlike `flaky_only`, `dirty` costs no extra `gh` call: `readiness` is already in scope by the time `_format_gate_block` runs, so `_downgrade_result`/`_format_gate_block` read `readiness.merge_state_status` directly — this is the "truthful actionability signal" half of the DIRTY build; see `_gate_actionability_lines`'s `dirty` branch, which emits `GATE_ACTIONABLE: yes` with no `GATE_ACTIONABLE_CHECKS:` line (so `implementation_fix` still sees zero fixable checks — `parse_actionable_gate_checks` requires both markers — while `loop_guard._has_actionable_gate_block` reads the bare `GATE_ACTIONABLE_YES` marker and stops treating a DIRTY-blocked verify↔fix pair as a stuck spiral).

**Symmetry (closed 2026-08-04):** both lanes now exclude survivor-evidenced checks from the flaky-only classification — consumer 1 via `_is_transient_flake`'s `survived_at_head` parameter, consumer 3 via `evidenced_actionable_failing_checks`. A check that survivor evidence has proven is *not* intermittent is never handed back to the bounded rerun ladder that already demonstrated it can't rescue it, from either lane.

**Self-review blindness (closed 2026-08-20, #1163):** `flaky_only_failing`'s `review_decision == "CHANGES_REQUESTED"` veto is sound on the merge lane (an unresolved human objection genuinely blocks merge) but, fed the raw GitHub aggregate, it also fired on the verifier's *own* prior-head REQUEST_CHANGES review — which `_pr_post.dismiss_stale_verifier_reviews` only removed at post time, after consumers 2 and 3 had already read it. After any verifier REQUEST_CHANGES, the next pass could therefore never classify flaky-only: no rerun, no survivor evidence at the new head, and the reroute above suppressed (PR #1159). The verifier-lane `PrReadiness` now carries a review decision that excludes the bot's own reviews (`_pr_ready._verifier_lane_review_decision`, from `latestReviews` in the same `gh pr view` call), and `_verification_gates._resolve_gate_readiness` dismisses the bot's stale reviews *before* the snapshot — see `pr_iteration_pipeline.md` D12a. The predicate itself is unchanged, so the merge lane's semantics are untouched.

**Consequence: the merge lane inherits the *remainder* of the shared rerun budget, never a fresh one — but a fresh head SHA still grants a fresh per-SHA budget to both lanes, bounded by the lifetime ceiling.** Because `pr_<n>_gate_reruns.json` (`load_gate_rerun_count`/`bump_gate_rerun_count`, now keyed per head SHA plus the lifetime ceiling — see "Rerun-budget consistency" above) is the one counter both lanes read and bump, a PR whose verifier pass already spent a rerun attempt on the *current* head SHA and then routes to `pr_merge` arrives at `_recover_transient_flake` with that spend already reflected — the remainder is shared within a head SHA exactly as before. `_pr_merge_remediation`'s bounded retry (`_maybe_retry_pr_merge`, a *different* counter — `pr_<n>_remediation_retries.json`) and the gate-rerun budget are independent budgets that both carry forward untouched by this reroute; neither resets when routing changes from `implementation_fix` to `pr_merge`. What *does* reset the gate-rerun budget's per-SHA `count` (never its `lifetime`) is the PR's head SHA itself changing — the fix this section documents.

**Convergence before evidence exists:** until a settle-and-compare has produced a survivor record for the current head, an allowlisted check still classifies flaky-only in both lanes — a genuinely-broken check's first appearance may route to `pr_merge` exactly like a true flake would, converging via the merge lane's bounded park + `_enrich_transient_flake_blockers`-enriched blockers. The moment the verifier lane's rerun settles red-on-same-sha, both lanes flip: the verifier prints `GATE_ACTIONABLE: yes` and routes `implementation_fix`; the merge lane classifies `GENUINE`. Both lanes now write survivor evidence, gated identically by `spec_gated_survivors` — the merge lane under the three guards in "Merge-lane survivor evidence" above, now including the spec gate for the blocking E2E check (see "Survivor proof is additionally spec-gated for the blocking E2E check" below).

**First-round dead-end guard (2026-08-20, #1164):** `flaky_only` and `dirty` were the only two routes out of a downgrade that avoided `implementation_fix`; a downgrade that was neither — most visibly, an allowlisted check red under a `CHANGES_REQUESTED` veto (PR #1159, where the veto came from the verifier's own stale review, #1163) — went to `implementation_fix` carrying a review whose gate block said `GATE_ACTIONABLE: no`, which that worker's prompt contractually answers with `non_actionable_feedback.yaml` → `await_human`. `loop_guard` cannot catch this on round 1 (`revisit_counts >= 1`). `_downgrade_result` now also returns `GateDowngradeResult.non_actionable = not actionable and not dirty` (and `actionable_checks`, the same tuple `_gate_actionability_lines` renders, so flag and text cannot disagree); `suggestions_for_verdict` routes it to `pr_merge`, whose `_enforce_pr_merge_gate` path re-snapshots readiness, runs `attempt_mechanical_recovery` and attaches named `Blocker`s before any bounded fall-through to `implementation_fix`. Two supporting changes ride along: `_resolve_actionable_gate_checks` fetches the failing E2E tests once (only when the E2E check is red) and threads them into `diff_attributable_e2e_checks(..., tests=)` and into the gate block as `GATE_FAILING_TEST: <spec> — <title>` lines; and the non-actionable escalation itself (`alan/teams/_fix_escalation.py`, relocated from `implementation_fix.py`) parses that block back (`parse_gate_cause`) so that, should an `implementation_fix` run still escalate on a gate-only review (legacy handovers, manual dispatches), the recommended answer names the failing checks, failing tests and flake-ratchet verdicts and resolves to `pr_merge` instead of the two generic options.

### Allowlist widened to the unit-test checks (spec attribution scoped to E2E; write path held)

`SHARED_FLAKY_ALLOWLIST` widened from the sole E2E member to three: `"Backend tests + coverage"` and `"Frontend tests + coverage (100/100/100/100)"` joined `"Frontend E2E (Playwright, blocking)"`, matched by exact equality against the job `name:` values in `.github/workflows/tests.yml` — a typo raises nothing, it just silently never becomes rerun-eligible. Before this, a flaky backend or frontend unit test always fell straight through every recoverable-block rung to `GENUINE` → `implementation_fix`, sending a worker hunting a bug in code the PR never touched.

Deliberately excluded:
- **`"SonarCloud (advisory)"`** — already has a strictly more precise classifier (`classify_block` splits a lone Sonar failure into `SONAR_HOTSPOT`/`SONAR_NO_ANNOTATIONS`/`SONAR_GENUINE`, and `needs_sonar_annotations` requires `len(failing_checks) == 1`). Allowlisting it would let the blunt rerun path pre-empt that annotation-driven recovery, and its correct retry is a Sonar re-analysis, not `gh run rerun --failed` — it `needs: [changes, test-backend, test-frontend, lint-frontend]` with `continue-on-error` artifact downloads, so rerunning it alone cannot rebuild what made it red.
- **`"CLAUDE.md drift gate"`** — a pure function of the PR's changed-file list (`dorny/paths-filter`); its `drift-ok` bypass label is read from the job-level `if:` off the *original* event payload, so a rerun can never observe a label added after the run started. Clearing it needs a new event, never a rerun — allowlisting it would spend rerun budget on an outcome that provably cannot change.
- **Every static-analysis check** (ruff+mypy+vulture, pyright strict, import-linter, the CCN/xenon gate, bandit+pip-audit) — true-positive rate ≈ 1, so a rerun only costs latency and pool contention for zero information.

**Spec attribution scoped to E2E only.** `failing_e2e_spec_names` and `diff_attributable_e2e_checks` used to select every `SHARED_FLAKY_ALLOWLIST`-member failing check; `failing_e2e_spec_names` then `dict.fromkeys`'d the *same* E2E spec tuple onto every one of them. That was vacuously correct while the allowlist had one member, but with three, a run where E2E and `"Backend tests + coverage"` both failed would have recorded the backend check's rescue under the E2E spec's `spec:` ledger key instead of its own literal-check-name key — inflating an unrelated spec's distinct-PR count and losing the backend check's own ledger entry entirely. Both functions now filter on equality with `_E2E_CHECK_NAME` instead of allowlist membership: `failing_e2e_spec_names` returns a dict with at most one key (the E2E check, only if it is itself failing); every other allowlisted failing check has no entry and falls through to `_flake_ledger_keys`'s existing `else` branch, recorded under its own literal check name. `_flake_ledger_keys` and `record_flake_occurrence`'s `eligible` filter — still the full `SHARED_FLAKY_ALLOWLIST` — are unchanged; narrowing `eligible` would have deleted the backend/frontend ledger entries outright, the opposite of the intent. `diff_attributable_e2e_checks` is scoped the same way and still only ever promotes `_E2E_CHECK_NAME`: no diff-join was built for the new members, so a genuinely self-inflicted backend/frontend unit-test break still costs one wasted rerun before the survival path (or a human) catches it — an accepted cost, not fixed here. Neither `_pr_branch.fetch_failing_e2e_tests` nor `alan/e2e_failures.py` gained a vitest/pytest analogue; per-test or per-file ledger keys for the new members were deliberately not built — check-level only, same as before.

Two known limitations this change does not fix:
- **`_E2E_JOB_INSPECT_CAP = 5`** (`_pr_branch.py`): with three allowlisted checks red plus their dependents, the E2E job can fall outside the five inspected job logs, degrading spec attribution to a check-level key for that run.
- **The Sonar cascade is a silent no-op for `sonar`.** `sonar` `needs:` the test jobs, so a test flake can drag it red too; `flaky_only_failing` requires *every* failing check to be allowlisted, and Sonar deliberately never is, so a run where Sonar is among the failures makes the predicate return `False` and this widening does nothing for that PR — bounded, not universal (the originating audit measured SonarCloud red on 1 of 156 sampled runs, against 5 combined test-check failures).

Expect one check-level quarantine proposal issue for `"Backend tests + coverage"` shortly after this lands — the originating audit measured it red on 4 of 156 sampled runs, no time window, at the existing `_DEFAULT_FLAKE_QUARANTINE_THRESHOLD = 3`. That is a ticket for a human, not a signal to weaken any gate. The frontend entry rests on a single observation (1 of 124 sampled runs) — too thin to estimate a rate on its own, but a red→green transition on an *unchanged* commit is exactly the nondeterminism `SHARED_FLAKY_ALLOWLIST` membership requires, and `"Frontend tests + coverage (100/100/100/100)"` shares a runner pool (see `tests.yml`) with the far-noisier 10-of-147 Playwright job, so pool contention is a plausible shared cause.

#### Write-path hold: `REBASE_SAFE_FLAKY_CHECKS`

Widening `SHARED_FLAKY_ALLOWLIST` also widens `actionable_failing_checks`, and `merge_recovery._has_genuine_failing_check` — the sole gate on the `BEHIND_PLUS_TRANSIENT` rung, which calls `_pr_branch.update_pr_branch_outcome`, a **write** — used to delegate to exactly that function. Left unchanged, widening the allowlist would have silently converted "BEHIND + a genuinely broken backend test" from `GENUINE` into an automatic `gh pr update-branch` on every pass, each one a full CI run; that auto-rebase/auto-merge path is explicitly out of scope for this reclassification (see the "only other caller" note above).

`_has_genuine_failing_check` now delegates to `rebase_blocking_failing_checks(readiness)`, which mirrors `actionable_failing_checks` but filters on `REBASE_SAFE_FLAKY_CHECKS: frozenset[str] = frozenset({_E2E_CHECK_NAME})` — a strict subset of `SHARED_FLAKY_ALLOWLIST` containing only the original member — instead of the full allowlist. Net effect: the write rung's input set is byte-identical to what it was before the allowlist widened, while the *routing* predicates (`flaky_only_failing`, `actionable_failing_checks`, `evidenced_actionable_failing_checks`) widen exactly as intended. `_is_transient_flake`/`flaky_only_failing` are untouched and still read the full allowlist — the rerun rung is a read, and widening what it reruns is the point of the allowlist change. `_has_genuine_failing_check` has exactly one caller, `_is_behind_plus_transient`; nothing else reads `rebase_blocking_failing_checks`.

This does not strand a PR. A BEHIND PR whose backend flake gets rescued by a rerun has no failing checks left, so `_has_genuine_failing_check` is `False` on the next pass and the rebase proceeds normally. A BEHIND PR whose backend failure is real still routes through `_is_transient_flake` → `TRANSIENT_FLAKE` (backend stays routing-eligible on the full allowlist) and works through the same bounded rerun ladder, survivor-evidence promotion, and eventual `implementation_fix`/`await_human` fallback as any other flaky-allowlisted check — see "Merge-lane survivor evidence" above for the guards under which the post-approval lane writes that evidence. Either way it does not spin indefinitely on an automatic rebase, and once a real fix lands, that commit produces the rebase as a side effect.

### Operator-facing failing-test detail

Classification (above) is the review-posting lane's problem. The dispatcher's park path has a separate, purely additive concern: when `_pr_merge_remediation` parks a `TRANSIENT_FLAKE`-classified PR (or re-enqueues `pr_merge` for a bounded retry — the enrichment call is unconditional on block class, not on the eventual routing outcome), `dispatcher._enrich_transient_flake_blockers` calls `_pr_branch.fetch_failing_e2e_tests(pr_number, forge_target=forge_target)` and appends one `Blocker(kind="failing_test", name=<spec>, detail=<title>)` per test the failing jobs' check-run annotations named, or — when `fetch_failing_e2e_tests` returns `None` (no job ids resolved, every annotation fetch failed, or no annotation named a spec file) — a single `Blocker(kind="reason", name="e2e_detail_unavailable", ...)` so the operator is told explicitly that the detail could not be recovered, rather than shown nothing or a misleading generic cause. `fetch_failing_e2e_tests` lives in `_pr_branch.py` (not `merge_recovery.py`) alongside the promoted `fetch_failing_job_ids` helper (see `dep_sweep.md`), the shared `fetch_check_run_annotations`, and `alan/e2e_failures.py`'s pure `parse_failing_e2e_annotations`; it caps the number of failing jobs it inspects (`_E2E_JOB_INSPECT_CAP = 5`) to bound `gh` latency on a sharded suite, and dedupes by `(spec, title)` across jobs, preserving first-seen order. `STALE_REVIEW` and `PRE_EXISTING_RED` block classes make zero extra `gh` calls here — the guard inside `_enrich_transient_flake_blockers` returns immediately for any block class other than `TRANSIENT_FLAKE`.

### Aggregate gate checks (a declared aggregate is set aside behind a failing job)

A public copy of alan makes one aggregate CI job — `gate`, which `needs` every other job in the shipped overlay workflow — its only authoritative check. `gate` fails whenever any job it depends on fails, and it is on no flaky allowlist. Without a rule, a known-flaky red (the end-to-end job) arrived as `{Frontend E2E…, gate}`: `flaky_only_failing` was `False` because of `gate`, so verification never ran its bounded rerun, the merge lane classified the PR `genuine` (or, when behind, refused to update the branch), and every flaky red cost a fix cycle. The owner's engine has no aggregate — its repository has no authoritative check at all — so it never met this.

**The declaration.** `ForgeTarget.aggregate_checks` (and `ForgeConfig.aggregate_checks`, see `engine_config.md`) names the checks an engine treats as aggregates. It is opt-in and empty by default, and the **effective** set is always `aggregate_checks & authoritative_checks`: a declared name that is not also authoritative has no effect, mirroring `authoritative_check_apps` (a non-authoritative pin is inert). For an install built from the default profile the declaration is filled in automatically with the template's aggregate check name when the profile names it authoritative.

**The view.** `_pr_flake_ledger.aggregate_set_aside(readiness, forge_target) -> PrReadiness` is a pure function, and `aggregate_set_aside_result` is its `ReadinessResult` form (a `ReadinessUnavailable` passes through unchanged). It removes the effective aggregates from `failing_checks`, order preserved, **only when at least one non-aggregate check also fails**. Every other field is untouched — `ok`, `failed_reasons`, `pending_checks`, `passing_checks`, `quarantined_checks`, `merge_state_status`, `review_decision`, `head_sha`. An aggregate failing alone, only aggregates failing, an empty declaration, or an aggregate absent from the failing list all return the **identical object**, which is what makes "aggregate alone behaves exactly as today" and "the owner is unchanged" structural rather than tested-for. The view is idempotent. A quarantined failing check counts as a non-aggregate failure (it is still in `failing_checks`), so `{gate, <quarantined>}` reads as `{<quarantined>}` and classifies `pre_existing_red`, exactly as the quarantined check alone would.

**Why a view and not a predicate argument.** `flaky_only_failing`, `actionable_failing_checks`, `rebase_blocking_failing_checks` and `flake_survived_checks` take no forge target, and none gains an argument: existing call sites, the owner's behaviour and every existing test keep their shape. Instead the five places that read a raw readiness and then reach those predicates are given the view first, so every flake-routing decision downstream — rerun eligibility, the actionable list, the rebase-blocking list, the evidenced actionable list, survival evidence and merge-lane classification — sees what the owner's engine would see for the same underlying job failures:

1. `_verification_gates._verifier_readiness` — the one verifier-lane readiness read. It is also what `_settle_wait` polls, so the readiness read **after** a rerun settles gets the same treatment as the one before it; `_maybe_rerun_flaky_gates`' eligibility, the `rerun_flaky_checks` argument list, `flake_survived_checks`, the ledger record and the gate-path audit row all derive from it, so none of them ever sees the aggregate.
2. `_pr_flake_ledger.evidenced_actionable_failing_checks` — first statement. The verdict rewrite (`_resolve_actionable_gate_checks`) and `_fix_non_actionable._blocking_state` both reach it, so a copy PR red on `{e2e, gate}` with reruns spent is no longer reported to the fix worker as contradicting its "nothing here is actionable" claim because of `gate`. `_fix_non_actionable.py` itself is not edited.
3. `merge_recovery.classify_block` — first statement; the branch order of `_classify_recoverable_block` is unchanged, so a behind PR still reaches the `BEHIND` rung before the transient-flake rung.
4. `merge_recovery.attempt_mechanical_recovery` — first statement, so `_resolve_shared_head_sha`, `_merge_lane_survivor_evidence`, `_record_merge_lane_survival` and `_recover_transient_flake` (the rerun argument list and the `bump_gate_rerun_count` check list) all see the viewed readiness; `classify_block` then applies the view a second time, which is a no-op.
5. `merge_recovery.needs_sonar_annotations` — `merge_gate._fetch_sonar_annotations_if_needed` decides whether to fetch Sonar annotations with this predicate **before** `attempt_mechanical_recovery` is called with them. If only `classify_block` saw the view, `{<sonar>, gate}` would classify as a Sonar block while its annotations had never been fetched, landing in `sonar_no_annotations` instead of the hotspot or genuine rung the sonar check alone reaches. The two must agree.

**Survival evidence.** Because the readiness `_maybe_rerun_flaky_gates` compares before and after is the viewed one on both sides, `flake_survived_checks` returns the end-to-end job without the aggregate, and `spec_gated_survivors` then applies its usual disjoint-spec rule to it. Without the view, a disjoint-spec red-to-red would have recorded the **aggregate** as a survivor at the head (the spec rule only exempts the end-to-end job), and the merge lane would then have classified a plain flake `genuine`. With it, disjoint specs leave no survivor, merge-lane classification at that head is `transient_flake`, and one rerun is still in the budget; overlapping specs record the end-to-end job, merge-lane classification is `genuine`, and `evidenced_actionable_failing_checks` lists the end-to-end job (never the aggregate).

**What is deliberately unchanged.** `SHARED_FLAKY_ALLOWLIST`, `REBASE_SAFE_FLAKY_CHECKS`, `max_gate_reruns()` and the lifetime cap; `rerun_flaky_checks`/`rerun_external_gate`; the flake ledger (`record_flake_occurrence` filters to the allowlist and the aggregate is never in the list it is handed, so the ledger never records it); the unblock recipes. `alan/merge_gate.py`, `MergeGateBlocked`, remediation context and the escalation diagnostics block keep reading the **raw** readiness, so a parked PR still names `gate` in its failing checks and the park text still lists it through `failed_reasons`.

**Known limits.** The rule assumes the aggregate and the jobs it depends on share one workflow run, so rerunning the flaky job's run reruns the aggregate with it; two failing checks sharing a run are still requested separately and deduplicating that request is out of scope. A dependency job that ended `cancelled` is not counted as failing, so such a red can be attributed to the flaky job — at most one bounded rerun, accepted. The aggregate's log and the workflow's `needs` are never read to attribute failures. Workspaces already in flight keep the engine snapshot (and therefore the forge section) they were created with.

## Cross-PR flake-frequency sidecar → quarantine proposal (zero gating power)

`record_flake_occurrence(pr_number, rescued_checks, task_id, *, forge_target)` has exactly one caller: `_verification_gates._maybe_rerun_flaky_gates`. It fires only after `_settle_wait` returns, and only for the checks `_pr_flake_ledger.flake_rescued_checks(before, after, *, head_sha_before, head_sha_after)` reports as rescued — an occurrence means **a rerun that actually rescued the check**, not merely a rerun that was triggered. All four of the following must hold, or nothing is recorded:

1. The post-rerun re-poll (`after`) completed without a forge/API error (`after` is a `PrReadiness`, not a `ReadinessUnavailable`).
2. No checks remain pending after settlement (`not after.pending_checks`) — a poll-budget timeout with the check still pending records nothing.
3. The check was failing before the rerun (`before.failing_checks`).
4. The check is not failing after (excluded from `after.failing_checks`).

The head-SHA guard is layered on top of that predicate: `_maybe_rerun_flaky_gates` captures the PR's head SHA via `_pr_branch.fetch_flake_guard_head_sha` immediately before triggering the rerun, and again immediately after `_settle_wait` returns; `flake_rescued_checks` only credits a rescue when the two match. Without this guard, a check that goes green because a *later* commit landed — not because the rerun did anything — still counts, which is exactly how issue #798 over-counted (see the Decision below). A plain before-minus-after comparison, with no gate on the transient-error or poll-exhausted exits, would introduce two new over-count paths in the very change meant to fix over-counting — that is why both exits above must record nothing rather than "record whatever `before`/`after` say."

The merge-gate lane (`merge_recovery._recover_transient_flake`) does **not** call `record_flake_occurrence` — see the `TRANSIENT_FLAKE` rung above for why.

- State: `state_dir() / "flake_failures.json"` — a flat `{ledger_key: sorted[pr_number, ...]}`, deduped per PR. Since 2026-08-05 the ledger is **spec-granular where the evidence allows**: `_maybe_rerun_flaky_gates` captures the failing E2E spec identities *before* triggering the rerun (`failing_e2e_spec_names` → `fetch_failing_e2e_tests`; after the rerun the rollup points at the new attempt's job ids, whose check runs carry no annotations from the red attempt) and threads them into `record_flake_occurrence(..., rescued_specs=...)`. A rescued check with captured specs records one `spec:<basename>` key per spec (the basename vocabulary matches `alan/web/e2e/flaky-baseline.json` / `report-flaky.mjs`); only when no spec identity was captured does it fall back to the bare check-name key. Old check-keyed entries parse unchanged — the namespaced keys ride the existing flat shape, so there is no schema migration. Read-modify-write is guarded by a module-level `threading.Lock` (`_flake_failures_lock`) since all writers are in-process dispatcher-worker threads of one FastAPI app.
- This sidecar has **zero gating power**: it never populates `_KNOWN_FLAKE_REGISTRY`, never removes a check from `failing_checks`, and can never cause a PR to merge or a check to be skipped on its own — only `attempt_mechanical_recovery`'s explicit rerun rung does that, gated by the shared rerun budget above.
- When a ledger key's distinct-PR count reaches `ALAN_FLAKE_QUARANTINE_THRESHOLD` (default **3**) and no matching open proposal issue exists yet (`_has_open_flake_proposal`, keyed by an exact-title `gh issue list --label flake-quarantine --state open --search "<title>"` query), `_maybe_open_flake_proposal` ensures the `flake-quarantine` label exists (`gh label create --force` — idempotent) and opens exactly one `gh issue create`. A `spec:` key proposes at spec granularity ("Flake quarantine proposal: spec `<file>`") with the concrete human actions: fix or `test.fixme` the flaky test in its own reviewed PR, or add the file to `alan/web/e2e/flaky-baseline.json` for the PR-only ratchet, with the nightly e2e-stress sweep as the evidence stream for shrinking the baseline back. A bare check key (spec identity unrecoverable from logs) proposes at check granularity and explicitly does NOT suggest allowlisting — the previous body's ask was circular (issue #946): rescues are only counted for checks already on `SHARED_FLAKY_ALLOWLIST`, so proposing to add them to it was a no-op by construction, and check-level quarantine is exactly what would have masked the real #944/#947 failures. This is a **proposal only**: it never quarantines anything, never weakens or removes any gate, and never suppresses the check from blocking. At most one open issue exists per ledger key at any time.
- Every proposal attempt appends a `flake_proposal_opened` entry (`check_name`, `pr_count`, `ok`) to `impl_audit.jsonl`.

### Decision, 2026-07-26: declined the Frontend E2E quarantine proposal (#798)

Issue #798 proposed quarantining `Frontend E2E (Playwright, blocking)` on the strength of the trigger-time counting this section used to document — an occurrence recorded whenever a rerun was *triggered*, not when it *rescued* anything. By the time this was re-examined, the live ledger listed 5 PRs (793, 794, 797, 803, 827). **Zero of five reruns rescued a PR**: each re-ran as attempt 2 on the same head SHA and failed again: a green result only ever arrived on a new commit, never from the rerun itself. PR #827 in particular was a genuine defect in that PR's own diff (a test id resolving to two elements), fixed by a later commit — not by the rerun. A real bug had been filed as flake evidence.

Decision: **decline** the quarantine. The known-flake registry stays empty, `SHARED_FLAKY_ALLOWLIST` is untouched, and the shared rerun budget (`max_gate_reruns`, still 2) is unchanged. No gate is weakened; Frontend E2E keeps full blocking power. This PR's rescue-based counting fix is what makes the 0-of-5 evidence visible in the first place — under the old trigger-time rule, all five still would have counted.

### Division of labour: this sidecar vs. the nightly E2E stress sweep

Rescue-counting makes this sidecar permanently silent for a check whose flakes reruns cannot fix — which is *correct* for a check-quarantine proposal: quarantining a check that reruns can't rescue would be exactly backwards, since quarantine exists to tolerate flakes a rerun clears, not to paper over a check that's genuinely broken. But that silence must not be misread as "this check is healthy." The "is this check actually flaky?" signal lives elsewhere: the nightly `.github/workflows/e2e-stress.yml` sweep (repeat-each 3, retries 0; weekly until 2026-08-10, promoted once the sweep moved to the dedicated `e2e` box) runs the suite under repetition with no rerun safety net and files flake issues directly — it produced issue #747. The stress sweep is the tool that *detects* flakiness; this sidecar only ever *proposes quarantine* for a check that reruns demonstrably rescue often enough to be worth tolerating. A silent ledger here means "reruns aren't rescuing this check" — it is not evidence the check is stable, and must not be read as a healthy-gate signal.

`_pr_branch.dismiss_stale_verifier_reviews` fetches the current PR head SHA and only dismisses verifier-bot CHANGES_REQUESTED reviews whose `commit_id` predates that SHA — reviews for the current head are left intact so genuine code rejections still block. (Now `_pr_post.dismiss_stale_verifier_reviews`, per the review-cluster split above.) This current-head rule holds on every path except one: a waiver answer's own dismissal of the review the *waived run itself* posted (`alan/teams/_pr_waiver_dismissal.py`, wired from `alan/routes/answer.py`) — see "Waiver exception to the current-head rule" below. The rule is unwidened everywhere else: the dispatcher's own pre-merge gate (`dispatcher._enforce_pr_merge_gate`), manual re-dispatch (`alan/routes/_workspaces_merge_gate.py`), the periodic merge-park sweep (`alan/_dispatcher_merge_park_sweep.py`), and the non-actionable park's `pr_merge` re-dispatch option (`alan/teams/_fix_escalation.py`) all still go through the unchanged `dismiss_stale_verifier_reviews`, which still skips the current head.

## Wiring in dispatcher.py

Forge threading has landed, and the readiness/annotation/recovery sequence now lives once in `alan/merge_gate.py` rather than inline in `dispatcher.py` (see "alan/merge_gate.py — the shared recovery attempt", below, for the module itself and its other callers). `dispatcher._enforce_pr_merge_gate` is a thin adapter: it calls `merge_gate.attempt_recovery(ws, pr_number, recovered_outcome="pr_merge")`, which internally resolves the workspace's pinned-engine `ForgeTarget` via `alan.teams._pr_forge.forge_target_for_ws` and passes it into `_pr_ready.check_pr_merge_readiness` (previously lived on `_pr_branch`; the readiness-cluster split moved `check_pr_merge_readiness` to `alan/teams/_pr_ready.py` — call shape unchanged), the module-private `_fetch_sonar_annotations_if_needed` (which forwards into `merge_recovery.needs_sonar_annotations`), and `merge_recovery.attempt_mechanical_recovery` — so a second engine's PR-merge gate resolves its own authoritative checks and its own `pr_<n>_gate_reruns.json` / `flake_failures.json` state (namespaced under `state_dir()/<owner>/<repo>/`, see `alan/teams/_pr_state_paths.py` and `alan/teams/_pr_flake_ledger.py`), rather than silently defaulting to the alan repo's. `attempt_mechanical_recovery`'s `TRANSIENT_FLAKE` rung (`_recover_transient_flake`) threads that same `forge_target` into `_pr_state_paths.load_gate_rerun_count`/`bump_gate_rerun_count`, closing the two-lane shared-rerun-budget gap described below.

`dispatcher._maybe_retry_pr_merge`'s remediation-retry counter (`pr_<n>_remediation_retries.json`) is threaded with the blocked attempt's own `forge_target` (`MergeGateBlocked.forge_target`, passed in through `_pr_merge_conflict_or_retry` as a required parameter; X2.7 PR16, see `forge_port.md`). A non-default engine's retry budget therefore lives under its own `state_dir()/<owner>/<repo>/` and starts fresh, while the default engine keeps the same namespaced file and the legacy unscoped fallback.

`_enforce_pr_merge_gate`'s decision mapping is unchanged by the extraction, still applied outside the dispatcher's workspace lock:
1. Call `merge_gate.attempt_recovery(...)`, which fetches sonar annotations lazily (only when sonar is the single failing check) and calls `merge_recovery.attempt_mechanical_recovery(...)` internally
2. When nothing was attempted (`MergeGateNotAttempted`: the PR was already ready, or the readiness read was unavailable) → return the original decision unchanged, no audit row
3. On `MergeGateRecovered` → return the `pr_merge` decision, passed through `_delay_for_ci_reset`: for the recovered classes that just fired an *asynchronous* re-run of an existing required check, or actually rewrote the branch, without the dispatcher itself observing the new state yet (`BEHIND_PLUS_TRANSIENT`, `TRANSIENT_FLAKE`, `SONAR_HOTSPOT`, and — since the mechanical-reconciliation rung — `DIRTY` on a `RECONCILED` outcome), the decision is re-issued with `eligible_at = now + ALAN_PR_MERGE_REMEDIATION_RETRY_DELAY_S` (the same 90 s knob as the bounded remediation retry) so `pr_merge` never reads the checks rollup inside the reset/re-push window — for `TRANSIENT_FLAKE`/`SONAR_HOTSPOT` that's the seconds-scale gap where `gh run rerun` has deleted the old check-run but the re-queued one has not yet registered; for `DIRTY`/`BEHIND_PLUS_TRANSIENT` it's the equivalent gap after a force-push/fast-forward, where CI on the rewritten head has not yet started. This deferral does **not** bump `pr_<n>_remediation_retries.json`: it is the continuation of a *successful* recovery, already bounded by its own shared budget (`max_gate_reruns()` for the flaky rungs, `_MAX_RECONCILE_ATTEMPTS`/`_RECONCILE_LIFETIME_CAP` for `DIRTY`), whereas the remediation counter bounds retries after *failed* recovery; charging both would double-count. Only `STALE_VERIFIER_REVIEW` recoveries stay immediate now (dismissal is synchronous — no new commit, nothing to wait on). `BEHIND_PLUS_TRANSIENT` joined the delay-eligible set for the same reason the system-head marker exists at all: the old reasoning — "the freshly-updated branch's empty checks rollup already reads as `pending`, so an immediate re-poll is harmless" — is exactly the assumption the post-approval verification gap exploited. Immediately after a fast-forward, `mergeStateStatus` can transiently read one of `MERGEABLE_MERGE_STATES` before GitHub has recomputed it, and `pr_merge`'s own `_confirm_ready_kind` reads that field as its ready/pending signal; without the delay, a race window exists where the gate could read "ready" and attempt a merge before CI has even started on the commit the update produced. The delay-eligible classes live in `merge_recovery.CI_RESET_DELAY_CLASSES` (relocated here from a dispatcher-local frozenset so the block-class taxonomy sits with its classifier, and so `dispatcher.py` — pinned at a 983-line shrink-only cap — gains headroom rather than growing to accommodate new members).
4. On `MergeGateAttemptFailed` → return the original decision unchanged. On `MergeGateBlocked` → `_pr_merge_remediation(..., attempt)` (the blocked attempt carries the readiness, block class, reconcile verdict and forge target) which:
   - `STILL_COMPUTING` or `BLOCKED_PENDING` → re-poll (return original `pr_merge` decision unchanged)
   - `STALE_REVIEW` → `await_human` (human CHANGES_REQUESTED with no stale verifier review — first-contact escalation, no wasted implementation_fix cycles); since P2.1 this path first passes through the bounded delayed retry (see "Bounded remediation retry" below); `DIRTY` takes the identical bounded-retry path for a non-terminal reconcile miss (`RACED`/`TRANSPORT_FAILED`), but a terminal `CONFLICT` verdict or an exhausted reconcile ladder (`rec is None`) now routes straight to `implementation_fix` instead of the retry ladder or the `await_human` dead end either used to reach — see "A human is no longer the terminal handler for a conflict" above
   - `CLOSING_LINKS_MISSING` → `implementation_fix` directly, bypassing the bounded-retry ladder entirely — see "Pre-merge closing-link read-back" above
   - Others → `implementation_fix` reason string includes `[block_class.value]`
5. `dispatcher._enforce_pr_merge_gate` writes the not-recovered audit row itself (via `merge_gate.record_merge_gate_audit`), once it knows the routing outcome the shared attempt could not have known; the recovered-outcome and `attempt_failed` rows are written inside `merge_gate.attempt_recovery` itself, since those two outcomes need no routing vocabulary at all.

Old module-level helpers removed: `_PR_MERGE_BEHIND_ONLY_REASONS`, `_PR_MERGE_OK_MERGE_STATES`, `_auto_update_branch_if_behind_only`, `_classify_pr_merge_blocker`.

`verification.py` and `remediation_verify.py` previously had their own private `_dismiss_stale_verifier_reviews` that did not check `commit_id` staleness. Both now delegate to `_pr_branch.dismiss_stale_verifier_reviews`; the private implementations are removed.

## alan/merge_gate.py — the shared recovery attempt and its callers

Pre-merge mechanical recovery — dismissing a stale verifier review, rerunning a flaky check, rebasing a behind-but-otherwise-green branch — used to be reachable only from `dispatcher._enforce_pr_merge_gate`, on the one routing path a completed `pr_merge` handover takes. Every other way of dispatching the `pr_merge` role bypassed it: a human answering a blocking question, or a manual re-dispatch, could spend a worker's entire poll budget on a block the fleet already knew how to clear in one `gh` round trip. `alan/merge_gate.py` closes that gap by giving every entry point that can reach a real pull request the same shared attempt, without duplicating the classifier or the recovery ladder.

`attempt_recovery(ws: Workspace, pr_number: int, *, recovered_outcome: str) -> MergeGateAttempt` derives the forge target internally (`alan.teams._pr_forge.forge_target_for_ws`, never taken as a parameter), establishes readiness (`_pr_ready.readiness_or_unavailable` plus the freshness overlay), fetches Sonar annotations only when the block class needs them, attempts `merge_recovery.attempt_mechanical_recovery`, and records the merge-gate audit row for two of its four outcomes. `MergeGateAttempt` is a union of four frozen dataclasses, so a caller branches with an exhaustive `match` instead of reading flags: `MergeGateNotAttempted`, `MergeGateAttemptFailed`, `MergeGateRecovered`, `MergeGateBlocked`. Callers that branch over the outcomes are `dispatcher._decision_for_gate_attempt`, `routes/answer._route_for_attempt` and `routes/_workspaces_merge_gate.apply_merge_gate_to_manual_dispatch`; the reconciler's separate `_ResumeAttempt` is not part of this union.
- **Readiness unavailable** (`ReadinessUnavailable` — the forge read failed transiently) → `MergeGateNotAttempted` carrying the unavailable value, returned before the freshness and closing-links checks run: neither is consulted, no merge-gate or merge-recovery audit row is written, and a manual dispatch gets no remediation text. The `pr_readiness_check` row the read itself wrote is unchanged. This is the one behaviour change of the result-union refactor: an outage no longer manufactures a `still_computing` block (and its audit sample) when the freshness overlay would otherwise have added a reason to an empty unavailable readiness.
- **Already ready** (`readiness.ok` or no `failed_reasons`) → `MergeGateNotAttempted`, no audit row — nothing was attempted, matching the pre-extraction behaviour of returning the original decision untouched.
- **Recovered** → `MergeGateRecovered(readiness, block_class, reconcile)`, audit row written with `outcome=recovered_outcome` (the caller's label for what happens next — `"pr_merge"` for the dispatcher, the resolver's team name for the answer route, `"dispatch"` for manual re-dispatch).
- **Not recovered** → `MergeGateBlocked(readiness, block_class, reconcile, forge_target)`, **no audit row** — only the caller knows the eventual routing/dispatch outcome, so recording it is the caller's job (`merge_gate.record_merge_gate_audit`, still exported).
- **The attempt itself raised** → wrapped in a handler that logs, writes an `attempt_failed` audit row (`block_class=None`), and returns `MergeGateAttemptFailed(readiness)` — never lets an unexpected exception (a malformed `gh` response, a bug in a recovery rung) propagate into an HTTP request or crash the caller. There is deliberately no per-PR lock around the attempt; that is filed as a follow-up, not solved here.

`MergeGateDecision` is the value `dispatch_team_core` (`alan/dispatch.py`) takes as a required keyword-only `merge_gate:` parameter — a result type, not a bare policy enum, so a caller can declare `policy="attempted"` only by constructing it from a real `MergeGateAttempt` (`MergeGateDecision.attempted(attempt)`); the other constructor, `MergeGateDecision.skipped(reason)`, carries a stated reason and no attempt. `dispatch_team_core` records the decision on the returned `DispatchOutcome.merge_gate` field but never executes it — the recovery attempt, if any, has already happened before `dispatch_team_core` is called. Supply is enforced by `tests/merge_gate_supply_gate.py`, an AST gate cloned structurally from `tests/dispatch_provenance_gate.py`: it resolves every local name bound to `alan.dispatch.dispatch_team_core` and requires a `merge_gate=` keyword on that reference's nearest enclosing call, covering both a direct call and the bare-reference-to-`run_in_threadpool` shape (`run_in_threadpool(dispatch_team_core, ..., merge_gate=...)`) that a function-signature check alone cannot gate.

**Per entry point:**
- **Answering a blocking question** (`alan/routes/answer.py`) — `_answer_and_maybe_dispatch` splits into a claim phase inside the process-global `_lock` (read-back, dedupe, resolver validation, `record_answer`, gold label, decision log, `record_intervention`) and an act phase outside it (the waiver dismissal, then the merge-gate attempt, then re-park or dispatch) — the lock never wraps a forge read. Immediately after the claim phase's `resolver is None` early return and immediately before the merge-gate attempt, `_act` calls `alan.routes._answer_waiver.apply(...)`, which dismisses the waived run's own current-head verifier review when the answer is structurally a waiver (see "Waiver exception to the current-head rule" below) and returns a `WaiverApplication` (defined in `_answer_waiver`; carries the `cleared` bool and an optional withheld-waiver blocker) threaded into `_apply_merge_gate`. When the resolver is `pr_merge` and the blocking handover carries a `pr_number`, the act phase attempts recovery; when it does not recover, it re-parks immediately with the real blockers (`AWAITING_INPUT`, `ParkReason.MERGE_BLOCK`, `merge_block_class` set) for a block class that is neither `merge_gate.routes_to_merge_lane`-eligible nor `SONAR_HOTSPOT` — concretely, a member of `dispatcher._BOUNDED_RETRY_REMEDIATION_CLASSES` or `SONAR_HOTSPOT` itself — **except** that a cleared waiver suppresses the re-park for `STALE_REVIEW` specifically (`_early_unrecovered_route`'s permit), routing that one case through to dispatch instead, and that a withheld or failed waiver whose fresh readiness still reports a change request re-parks under every block class (see "Waiver exception to the current-head rule" below); every other block class re-parks exactly as before. **This deliberately does not replicate the dispatcher's bounded-retry-then-`await_human` ladder** (no `pr_<n>_remediation_retries.json` counter is charged, no delayed re-enqueue is scheduled): the answer route's re-park is a one-shot outcome of a single human decision, not a background loop the dispatcher itself needs to keep bounded — a human who wants another attempt re-answers or re-dispatches. A poll-lane class (`STILL_COMPUTING`/`BLOCKED_PENDING`/`BLOCKED_NO_SIGNAL`) or a repair-worker-eligible class (`GENUINE`/`POST_UPDATE_RED`/`SONAR_GENUINE`/`SONAR_NO_ANNOTATIONS`) dispatches the resolver anyway, exactly as if nothing had been attempted (absent a withheld waiver) — `pr_merge` is equipped to poll the former, and the resolver mapping already sends the human's decision to the team that can act on the latter.
- **Manual re-dispatch** (`alan/routes/workspaces.py::perform_task_team_dispatch`, via the private sibling `alan/routes/_workspaces_merge_gate.py`) — resolves `prior_handover_for_task` unconditionally now (previously gated behind `record_redispatch`, which only the human-facing `/dispatch` route sets `True`; the propose-mode approval route in `alan/server.py` calls the same shared function with `record_redispatch=False` and now gets the same merge-gate attempt for free, no separate wiring needed), attempts recovery when a `pr_number` is present, and **dispatches regardless of the outcome** — attaching the block class and blockers to the worker's instructions on a genuine block via `render_remediation_instructions`. It never refuses: manual re-dispatch is the operator's escape hatch, a pinned invariant requires it to stay directly callable by recovery tooling, and the system's own park text instructs humans to use it. `apply_merge_gate_to_manual_dispatch` takes no `team` argument — the attempt runs for **any** team a workspace with a recorded `pr_number` is manually redispatched to, not only `pr_merge`. This is deliberate, not an oversight: "every entry point able to reach a real pull request attempts the recovery" is a property of the entry point (manual re-dispatch), not of the team being dispatched, and a mechanically clearable block (a stale review, a rebase) is equally worth clearing before spending *any* worker's turn on a PR that carries it.
- **Automated continuation on the terminal-transition seam** (`alan/auto_continue.py::maybe_auto_continue`) and **project-level roadmap advancement** (`alan/project_auto_continue.py::advance_project`) both declare `MergeGateDecision.skipped(...)` with a recorded reason and make zero forge calls. Both fire on (or immediately after) the seam `_enforce_pr_merge_gate` has already evaluated for the same handover, inside the dispatcher's own workspace lock — a second attempt against unchanged state buys no new information and must not run a forge read under that lock.
- **Both create-and-dispatch paths** (`alan/app/workspace_creation.py::dispatch_root_task_or_rollback`, used by `create_workspace`; `alan/project_auto_continue.py::advance_project`, which both seeds the workspace and dispatches it) also declare a skipped decision: a workspace created in the same call has no prior handover and structurally cannot carry a pull-request number yet.

No forge read, review dismissal, or rebase runs inside the dispatcher's workspace lock or inside the process-global answer lock (`alan/routes/answer.py`'s `_lock`) — every attempt happens after the respective lock has already been released. Hoisting the automated-continuation call itself out of the dispatcher's workspace lock is out of scope here and is tracked as its own follow-up.

## Waiver exception to the current-head rule

When a human waives a verification escalation, the `changes-requested` review our own verifier posted for the *waived run* usually still sits on the pull request's current head — exactly the shape `dismiss_stale_verifier_reviews`'s current-head skip exists to leave alone on every other path. Left alone here, the waiver never actually clears anything: the answer resolves to `pr_merge`, the merge gate reclassifies the same review as `STALE_REVIEW`, recovery fails (the review predates nothing), and the answer re-parks — the human's decision has no effect. `alan/teams/_pr_waiver_dismissal.py`, wired from `alan/routes/_answer_waiver.py` into `alan/routes/answer.py`'s act phase, is the one deliberate, narrow exception.

**Recognition, not a wording match alone.** `_answer_waiver.is_waiver(question, answer)` is a one-line projection of `clause_withdrawal.resolve_human_ruling(question, answer)`: `ruling is not None and ruling.resolver == "pr_merge"`. `resolve_human_ruling` tries its option-text branches first — the operator-only wordings, then the PR-state override wording, then the clause-stall wordings — and its structural check is only the last branch: `_resolve_generic_waiver_ruling` matches `question.question_class == "verification_escalation"` with `question.option_resolvers.get(answer) == "pr_merge"`. So a waiver is recognised by option text when the question is one of those named shapes and by class-and-resolver otherwise; there is still no `from_team` check. Every waiver option verification emits reaches `pr_merge` through one of those branches (the capability-boundary "Waive this finding and proceed to merge." through the generic structural branch, the clause-stall "Waive this clause and proceed to merge." through the clause-stall branch, both in `alan/teams/_verification_review_post.py`); the non-actionable park's own `pr_merge` re-dispatch option (`alan/teams/_fix_escalation.py`) carries `question_class="fix_escalation"` (a different class entirely), matches none of the option-text branches, and is excluded from the structural branch by that class, not by an explicit check.

**Safety floor — zero forge calls when it applies, and it now rests on the honest pre-fallback figure.** `_answer_waiver.waiver_floor_inputs(ws, blocking)` reads two things for the waived run's invocation id: the saved review artifact (`alan.teams._verification_artifacts.read_review_artifact`, for the raw `DIFF_FINDINGS_CRITICAL` count — never the in-scope figure split workspaces gate on) and the persisted pre-fallback count record (`alan.teams._verification_artifacts.read_count_record`) written alongside it. The record holds the `CriticalCountReport` verification computed *before* `_verdict._apply_reviewer_count_fallback` ever ran — whether the reviewer role reported a count at all, and what that figure was — so the floor sees the honest signal even on a run where `_apply_reviewer_count_fallback` later synthesized a `0` into the posted artifact text — that fallback keeps injecting unconditionally, since it serves the unrelated purpose of giving the posted GitHub review body a machine-readable count line to reconcile against even when the judge role never emitted one; the record captures what was actually reported, before that substitution ever runs. `waiver_floor_inputs` returns `(None, "count_not_reported")` whenever the artifact is missing, the record is missing, or the record's own `inv_id` doesn't match the invocation it was read for (a mismatch counts as absent, not as a stale-but-usable reading); otherwise it returns the record's `reviewer` figure alongside `alan.teams._verdict.count_floor_reason(critical, record)` — the same pure function the verifier's own post-approval thread-resolution pass already calls, so the waiver path and the verifier path can never apply two different rules to what "the count floor holds" means. `count_floor_reason` returns a reason string (`"count_not_reported"`, `"reviewer_nonzero"`, or `"posted_count_nonzero"`) whenever the floor should withhold, or `None` when it clears. `dismiss_for_waiver(pr_number, *, forge_target, question_id, floor_reason)` takes that precomputed reason directly: `floor_reason is not None` returns `WaiverDismissal("withheld_floor", (), False)` before making a single `gh` call. The former `floor_withholds` helper, which withheld on any critical count above zero read straight off the posted artifact, is deleted rather than kept as a second path — there is exactly one place this rule is evaluated now. When the floor applies the outcome is `withheld_floor`, and the floor's reason travels into the `waiver-dismissal-withheld` blocker that "Ordering and routing" below attaches to the park.

**Every verification escalation leaves the count record.** `reviewer_count_var` — the pre-fallback `CriticalCountReport` that `VerificationTeam` sets inside its pipeline — is defined in `alan/teams/_verification_artifacts.py`, below every emitter, and is the ambient fallback for `_write_review_artifact`: when the caller passes no explicit `counts=`, the writer reads the var and, if it is set, writes the record beside the artifact. The ordinary verdict path and every escalation emitter in `alan/teams/_verification_review_post.py` (review-post-failed, judge-parse, capability-boundary, clause-stall, pull-request-state) therefore leave the same record. Before this, an escalation park wrote the artifact with no record, so the floor read `count_not_reported` and withheld before contacting the forge — on exactly the parks that offer the waive option. `_emit_cannot_verify` runs outside the run-token scope, before any count exists, so the var is unset there and the floor still fails closed. The floor's rule itself is unchanged: a recorded count that does not clear it is withheld with its own `reviewer_nonzero` / `posted_count_nonzero` reason, and only a genuinely absent record reports `count_not_reported`.

**Scope of the dismissal.** Once the floor clears, `dismiss_for_waiver` lists every review on the PR (`_pr_post.fetch_review_stream` + `_pr_post.parse_review_objects`, the same listing `dismiss_stale_verifier_reviews` uses, factored out so both callers share one parse) and dismisses **every** `CHANGES_REQUESTED` review authored by `_pr_branch.verifier_login()`, with no head-SHA filter at all — this is the one place in the fleet a verifier review at the current head is intentionally dismissed. A review by any other author is never touched: `_pr_waiver_dismissal._other_author_blocking` separately tracks whether any other author's *latest* review (by stream order; `COMMENTED`/`PENDING` states are ignored) is itself `CHANGES_REQUESTED`, and `_answer_waiver.apply` carries that as a fact separate from the outcome itself: `WaiverApplication.cleared` is `dismissed and not other_author_blocking`. A waiver never permits a dispatch while another author's change request stands — a standing human rejection is never turned into a merge dispatch by a waiver that only concerned the verifier's own finding.

**Ordering and routing.** The dismissal runs in `alan/routes/answer.py`'s act phase, outside `_lock`, immediately after the claim phase's `resolver is None` early return and immediately before the merge-gate attempt — no forge call is ever made while an answer is being claimed under the process-wide answer lock. `_answer_waiver.apply` returns a frozen `WaiverApplication`, defined in `_answer_waiver`, carrying two independent facts: `cleared` (the dismissal succeeded **and** no other author's change request stands) and `blocker` (a rendered park blocker, set only when the outcome was `withheld_floor` or `failed`). `answer.py` never names the dismissal module, its types or its outcome strings — `tests/test_current_head_review_survives.py` keeps `_answer_waiver` the only module under `alan/` that does. The application is threaded through `_apply_merge_gate`, which acts only when the merge step attempted recovery and left the block unrecovered: a classified block goes to `_handle_unrecovered_block`, and an attempt that failed transiently before it could classify (`MergeGateAttempt.block_class` is `None`, after a forge rate-limit or transient error) goes to `_park_unclassified_withheld_waiver`. Two rules then apply, in this order:

1. **A waiver that cleared nothing parks.** When `WaiverApplication.blocker` is set **and** the merge step's own fresh readiness reading (`attempt.readiness.review_decision`; no extra forge read) still reports `CHANGES_REQUESTED`, `_route_unrecovered_block` checks it before any other routing and re-parks through `_repark_unrecovered_merge_block`: `AWAITING_INPUT`, `ParkReason.MERGE_BLOCK` (no new park reason), `merge_block_class` set to the real block class, carrying the class's ordinary blockers plus a `waiver-dismissal-withheld` blocker. An attempt with no block class parks the same way with `merge_block_class` cleared and the waiver blocker alone, and its `merge_gate_audit.jsonl` row carries a null `block_class`. The rule holds for every block class — poll-lane and repair-worker-eligible classes that would otherwise dispatch, `STILL_COMPUTING` included — and runs ahead of the conflict-fix decision: a `DIRTY` block with a withheld waiver parks instead of dispatching `implementation_fix`, because a fix worker must not run on a pull request whose verifier review is still standing (the conflict still appears among the park's blockers). The blocker's detail names the pull request, the waiver outcome and its reason (the floor's own reason, or `dismissal call failed`); its instruction is the operator's move: dismiss the verifier review by hand, then dispatch the `pr_merge` team, which is manually dispatchable. The `merge_gate_audit.jsonl` row records the outcome as `re_park`. The blocker name is deliberately absent from `alan/unblock_recipes.py`'s stale-review blocker set, and because the park keeps `merge_block_class == stale_review` beside several readiness blockers (so `single_blocker` is `None` and the recipe's class fallback would otherwise match), `_match_stale_review` also refuses any park carrying the `alan.park.WAIVER_WITHHELD_BLOCKER` blocker: a withheld safety floor is a stop a human clears knowingly, and no automated recipe acts on it.
2. **Everything else routes as it always has.** A `STALE_REVIEW` block dispatches `pr_merge` only when `cleared` is true, so a waiver never permits a dispatch while another author's change request stands. A dismissal that found nothing to dismiss, an answer that is not a waiver, a block the merge step itself recovered, and a review no longer standing all route exactly as before. After a successful dismissal the merge gate has still run against fresh readiness, so a red check, a Sonar hotspot or a dirty merge state routes as it always has — the waiver never overrides a block it did not clear. Because that readiness is read fresh after the dismissal, a `STALE_REVIEW` reclassification no longer has a review to find, and the answer proceeds to dispatch `pr_merge` even if the forge's own cached `reviewDecision` has not caught up with the dismissal yet.

**Failure is visible, never silent.** `_answer_waiver.apply` wraps `dismiss_for_waiver` in a bare `except Exception` (logged via `logger.exception`, BLE-compliant) and substitutes `WaiverDismissal("failed", (), False)` on any raise — a malformed `gh` response or an unexpected exception can never propagate into the answer request. A `failed` or `withheld_floor` outcome yields `cleared=False` plus the withheld blocker, so the operator is told at the park rather than after `pr_merge` burns a long poll on a pull request that cannot merge; a `none_found` outcome yields `cleared=False` and no blocker.

**Known gap: replay.** Everything above is bounded to an answer being recorded for the first time. An answer given a second time returns into `_act_replay` before `_answer_waiver.apply` runs, so a replay never evaluates the waiver at all; and one waiver wording — the pull-request-state override — re-dispatches on replay through `_act_replay` with `MergeGateDecision.skipped(...)`, a path with no merge gate, so it can still reach a `pr_merge` dispatch with no waiver evaluated. No mechanism lets an answer be given twice, and closing this door is out of scope here; it is tracked as its own issue.

**Audit.** Every waiver attempt with a PR number — including one withheld by the floor — writes exactly one row to `impl_audit.jsonl` via `alan.teams._pr_waiver_dismissal.record_waiver_dismissal`, `action="waiver_review_dismissal"`, carrying `task_id`, `pr_number`, `question_id`, `invocation_id`, `outcome` (`dismissed`/`withheld_floor`/`failed`/`none_found`), `review_ids`, `reviewer_count`, `floor_reason`, and `other_author_blocking`. `reviewer_count` and `floor_reason` replace the former `critical_count` field: `reviewer_count` is the pre-fallback count record's own `reviewer` figure (never the posted-artifact count), and `floor_reason` is the `count_floor_reason` result that drove the withhold-or-proceed decision — both `None` together only when no record was ever read. This is a distinct `action` from the pre-existing `review_dismissed`/`dismiss_stale_reviews_*` rows an ordinary stale-review dismissal writes, so waiver success can be re-measured after merge with a single filter on `action == "waiver_review_dismissal"` — the same log, a different action name.

**The narrowed guarantee.** A waiver guarantees only that the review the *waived run itself* posted does not stand in the way of the merge gate afterward, and that guarantee now rests on the honest pre-fallback critical-count record rather than the substituted zero a downstream fallback could otherwise inject into the posted artifact. It does not guarantee no `CHANGES_REQUESTED` review survives the PR (another author's standing rejection is deliberately left alone, via `other_author_blocking`), and it does not guarantee the clause or finding stays waived forever. Accepted edges, all deliberately out of scope for this build: a later verification run re-failing the same clause on the same PR is not this mechanism's concern (tracked separately, with its own evidence); a commit landing after the waived run merges without a fresh verification pass is existing behaviour, unchanged; a waiver answered on an older question can dismiss a later run's review if that later run also left a `CHANGES_REQUESTED` review from the same verifier identity outstanding at the time of the answer — an accepted edge case, not a defect; and the verifier identity this dismisses by is the single global `_pr_branch.verifier_login()` — no per-repository secondary-engine identity exists yet.

## Escalation diagnostics block (display-only)

A `pr_merge` escalation caused by a failed `gh pr merge` no longer carries only 200 chars of stderr. `pr_merge._escalation_diagnostics` assembles a best-effort `## Merge escalation diagnostics` block onto `PrMergeOutcome.diagnostics` (additive field, default `""`), and `_escalation_handover` appends it to `full_synthesis` after the short `reason` — every existing consumer of `reason` (audits, router credential park, `_merge_block_options`) is untouched. Contents: the merge rc + full stderr (capped at 4000 chars, fenced under `UNTRUSTED_CONTENT_NOTICE`), a readiness snapshot (mergeStateStatus / reviewDecision / failing / pending / quarantined), the shared rerun budget spent, any `pr_<n>_gate_survived.json` survivor entries, and the failing E2E specs from `fetch_failing_e2e_tests` (with an explicit fallback line when logs are unreachable). Every sub-fetch soft-fails independently; with no diagnostics the handover is byte-identical to before. The block deliberately matches neither `loop_guard.is_no_commit_escalation`'s substring nor the dispatcher's `## PROJECT_FACT` harvester (test-pinned). Display/diagnostic contract only — no routing behavior keys on it.

## Bounded remediation retry (Phase 2, P2.1)

When `_pr_merge_remediation` cannot clear a `stale_review`, `pre_existing_red`, or an exhausted `transient_flake` block, it no longer dead-ends at a human-visible `await_human` on the first miss (the former #493 runbook recipe: a human re-triggers the check and manually re-dispatches `pr_merge`). It re-enqueues `pr_merge` itself via a delayed `RouterDecision(eligible_at=...)` (`ALAN_PR_MERGE_REMEDIATION_RETRY_DELAY_S`, default 90 s) so the retry lands only once the external condition has had a chance to change. The loop is bounded by a dedicated per-PR counter (`_pr_state_paths.load_remediation_retry_count` / `bump_remediation_retry_count`, state file `pr_<n>_remediation_retries.json`) capped at `loop_guard.REVISIT_CAP` — deliberately not the general revisit-count mechanism, since `has_forward_progress` hardcodes `True` for `pr_merge` and would never trip it. Once the cap is reached the PR falls back to `await_human` as before, so a genuinely-stuck PR never spins. Every attempt (recovered or not) is recorded in the existing `merge_gate_audit.jsonl` row.

The `ALAN_PR_MERGE_REMEDIATION_RETRY_DELAY_S` knob now has two distinct users with different budget semantics: (1) this bounded retry — fires after a *failed* recovery, charges `pr_<n>_remediation_retries.json`; (2) `_delay_for_ci_reset` — fires after a *successful* rerun-firing recovery (`TRANSIENT_FLAKE` / `SONAR_HOTSPOT`), charges nothing, bounded instead by the shared `max_gate_reruns()` budget that gates whether `_recover_transient_flake` can fire at all.

The BEHIND-only `update_pr_branch_outcome` fast path audits `pr_update_branch_ok` / `pr_update_branch_failed` rows to `~/.alan/logs/impl_audit.jsonl`.

## System-authored heads: `pr_<n>_system_head.json`

Three recovery rungs mutate a PR's actual head commit without a human ever seeing the result: `BEHIND_PLUS_TRANSIENT`'s and `STALE_MEASURED_BASELINE`'s `_pr_branch.update_pr_branch_outcome` fast-forward on `UPDATED`, and `DIRTY`'s `_recover_dirty` on a `RECONCILED` reconcile verdict. Before this build, the resulting commit inherited the PR's pre-update approval unconditionally — a passing gate on that commit merged on the old review, and a failing gate dead-ended at `await_human` with no attempt made, since `PRE_EXISTING_RED`/`STALE_REVIEW`-shaped human-park classes were the only ones that ever reached `await_human` without first trying `implementation_fix`. `pr_<n>_system_head.json` (`_pr_state_paths.py`) is the record that closes both halves.

**Shape.** `SystemHeadMarker(*, head_sha: str | None = None, rung: str, forwarded: bool = False, written_at: float | None = None)` — a frozen, keyword-only pydantic model shared by the writer and the reader (X2.15) — `head_sha` is the post-update commit (fetched via `_pr_branch.fetch_flake_guard_head_sha` for the two `update_pr_branch_outcome` rungs; taken directly from `ReconcileResult.post_sha` for `DIRTY`, since a reconcile attempt already resolves it and a second `gh` call would be redundant), `rung` is a free-form string identifying which mechanism minted it (`"behind_plus_transient"`, `"stale_measured_baseline"`, or `"dirty"` — the three `MergeBlockClass.value` strings — for the `merge_recovery` rungs below; see the next paragraph for the two additional non-`MergeBlockClass` rungs), and `forwarded` is the one-shot flag described below. Written only on the *successful* branch of each rung, so a rung whose own recovery didn't actually land a new commit never writes a marker. When the branch update succeeded but the resulting head could not be learned (a failed fetch, a `ReconcileResult.post_sha` of `None`) the marker is still written, with `head_sha` **absent** — see "Unknown-head marker" below.

**Every automated branch-update path writes this marker, not just the three `merge_recovery` rungs (closed, 2026-09-03, PR #1292 review).** Two other call sites mutate a PR's head without human involvement and, before this fix, left it looking system-untouched to `classify_block`'s `system_head` check: `proactive_rebase._do_fan_out` (the idle-PR-freshening fan-out triggered after any merge) calls `_pr_branch.update_pr_branch_outcome` directly, and `pr_merge._handle_behind_recheck` (the merge-time race guard — a PR goes BEHIND between the readiness probe and the actual `gh pr merge` call) does too. Both are wired the same way as the three `merge_recovery` rungs — fetch the resulting head SHA via `fetch_flake_guard_head_sha` on a successful update, then `_pr_state_paths.save_system_head` — under their own rung labels, `"proactive_rebase"` and `"merge_time_behind"` respectively (`proactive_rebase._record_system_head`, `alan/teams/_pr_merge_post_update.py::record_merge_time_system_head_if_updated` — factored into the already-existing post-update sibling module, not `pr_merge.py` itself, to hold `pr_merge.py` under its pinned size-ratchet cap; see `tests/size_baseline.py`). Marker creation was deliberately *not* centralized into `_pr_branch.update_pr_branch_outcome` itself: the three `merge_recovery` rungs already resolve their own head SHA for other reasons (audit rows, `_recover_dirty`'s reconcile result) and pushing the write down into the shared low-level function would have meant either duplicating that fetch or reworking call sites with test coverage this PR does not need to touch — wiring the two actually-bypassing call sites individually is the narrower fix and leaves `update_pr_branch_outcome`'s contract (a plain enum, no side effect beyond the `gh` call and its audit row) unchanged for every other caller.

**Storage.** `system_head_path(pr_number, forge)` sits under `_engine_state_dir(forge)` — the same per-`(owner, repo)` scoping every other PR-state file in this module uses (`pr_<n>_gate_reruns.json`, `pr_<n>_reconcile_attempts.json`, …) — so it already resolves through `alan.roots.state_root()`, which `ALAN_STATE_ROOT` redirects everywhere tests and CI need it to. No new `ALAN_*` variable was needed: this is the same state-isolation surface every sibling file in `_pr_state_paths.py` already registers, not a new one. There is no legacy-fallback read for this file (unlike `acked_comments`/`gate_reruns`/`remediation_retries`) — nothing predates this store, so `load_system_head` reads the namespaced path directly and returns `None` on any missing-file, malformed-JSON, or schema-mismatched payload (non-dict, empty/non-string `head_sha`, a `null`/missing `head_sha` without a numeric `written_at`, empty/non-string `rung`, non-bool `forwarded`) — fail-open by construction, exactly like the sibling readers in this module. An empty-string `head_sha` is still rejected; an absent head (`null`, or a missing key, alongside a numeric `written_at`) is now a valid marker. `written_at` is read only when it is a finite number that fits a float and is not a bool, else `None`. It takes part in equality like every other field. The non-empty `head_sha`/`rung` and null-head-needs-`written_at` rules are applied at load time, never at construction.

**Unknown-head marker (alan#1630).** `save_system_head(pr_number, head_sha: str | None, rung, forge)` stamps `written_at=time.time()` on every write. When a fleet path moved the branch and the resulting head could not be read, it writes `head_sha=None` (JSON `null`) — **absent**, never `""`, because `PrReadiness.head_sha` defaults to an empty string and an empty string is a live value. Every existing comparison against a marker's head (`_is_system_head_match`, `is_system_authored_head`, `unblock_recipes._fleet_moved`) is an equality check that an absent head can never satisfy, so an unknown-head marker cannot authorise a `system_head` classification or a `pr_merge → pr_merge` forward (`forward_if_system_head` returns before spending a head read). The marker is written only after the update is known to have succeeded — inside the `ok` / `UPDATED` / `recovered` branch of each `merge_recovery` rung, the `UPDATED` branch of `proactive_rebase._do_fan_out`, and after the `update_ok` guard of `record_merge_time_system_head_if_updated`. A `CONFLICT`, a `FAILED` update, `update_ok=False` or a raise leaves the marker exactly as it found it; writing intent *before* the push was rejected because it would re-create a false decline on the conflict path. There is no clear or supersede primitive: the next successful update overwrites the marker with its own head. The unblocker's `hand_resolved_declared_blocker` recipe is the reader that uses `written_at`: an unknown-head marker written at or after the park handover's `timestamp_utc` (a naive timestamp is read as UTC) means the fleet moved the head. **Accepted residual:** a process dying between the push and the head read still leaves an unmarked head. **Rolling deploys:** a process older than this change rejects a `null`-head marker in its marker parser and treats the PR as having no marker — fail-open, the pre-change behaviour for a fetch failure.

**SHA-keyed self-invalidation.** The marker carries no expiry and needs none: `classify_block`'s `system_head` parameter (and the `pr_merge → pr_merge` forward path below) both compare the marker's `head_sha` against a *freshly fetched* current head before trusting it. A human push, a `pr_merge`-unrelated commit, or any other event that moves the PR's head SHA away from the marker's recorded value makes every future comparison fail — `attempt_mechanical_recovery`'s `_is_system_head_match` returns `False`, and `classify_block` falls back to the ordinary `genuine` fallthrough it always had. The marker file itself is left on disk (stale, inert) rather than deleted; the next successful `BEHIND_PLUS_TRANSIENT`/`STALE_MEASURED_BASELINE`/`DIRTY` recovery overwrites it with the new head SHA and a fresh `forwarded=False`, via the same read-then-`os.replace` write `save_system_head` already uses for every write.

**One-shot `forwarded` flag.** `mark_system_head_forwarded` flips `forwarded` to `True` without touching `head_sha`/`rung`, and is called exactly once, by `alan/teams/_pr_merge_post_update.py::forward_if_system_head` (below) at the moment it actually returns a forwarding `Handover`. `is_system_authored_head` (the shared predicate both the forward path and its own standalone tests read) treats a `forwarded=True` marker as non-matching — `not marker.forwarded` is one of its three conjuncts — so a single system-authored head can trigger the `pr_merge → pr_merge` forward at most once, never once per poll. `classify_block`'s own `system_head` boolean is **not** gated on `forwarded`: `attempt_mechanical_recovery` computes it from `marker.head_sha == head_sha` alone (`_is_system_head_match`), so a `POST_UPDATE_RED` classification keeps firing on every pass a check stays red at that commit, exactly like `GENUINE` always did — only the *forward* path is one-shot, because only the forward path spends a chain-continuation (`revisit_of`/`iteration`) that the loop-bounding backstops below are sized around.

**Head-SHA resolution stays lazy.** `attempt_mechanical_recovery` reads the marker (`_pr_state_paths.load_system_head`, a local file read, no `gh` call) unconditionally, but only resolves the *current* head SHA — the one extra `gh` call this build adds to the common path — when `flaky_only_failing(readiness)` is already true (the pre-existing condition `_merge_lane_survivor_evidence` gated on) **or** a marker exists at all (`_resolve_shared_head_sha`). A PR the system has never touched carries no marker, so this costs exactly zero extra `gh` calls versus before this build; a PR the system did touch pays one `fetch_flake_guard_head_sha` call, shared by both the survivor-evidence check and the `system_head` comparison — never two.

## The `pr_merge → pr_merge` forward path (`alan/teams/_pr_merge_post_update.py`)

`pr_merge._build_handover`'s final fallthrough — every outcome kind that isn't a terminal merge, an escalation-worthy `closed`/`error`/`unresolved_ceiling`, a Copilot-thread routing, or a dependency-bot rebase — used to go straight to `_await_human_handover`: a blocking `OpenQuestion` with `resolver_role="human"`, parking the workspace for a human to read and manually re-dispatch. `_build_handover`'s fallthrough now interposes `_pr_merge_post_update.forward_if_system_head` (via the `forward_or` helper described below) immediately before that park.

**The escalation branch gets the identical check (closed, 2026-09-03, PR #1292 review).** The `closed`/`error`/`unresolved_ceiling` branch used to escalate unconditionally, ahead of the fallthrough above — this is exactly where `_handle_behind_recheck`'s merge-time BEHIND outcome (`kind="error"`, above) landed, so that specific system-authored update could never reach `forward_if_system_head` no matter how the fallthrough's own check evolved: the `error` branch returned first. `_pr_merge_post_update.forward_or(workspace, prior, inv_id, outcome, fallback)` is the shared helper both branches now call — it runs `forward_if_system_head` and returns its result when not `None`, otherwise calls `fallback()` — so `_build_handover`'s escalation branch passes `lambda: _escalation_handover(...)` and its general fallthrough passes `lambda: _await_human_handover(...)`, the same one check with a different park-shaped ending. (This replaced the single-purpose `_system_head_forward_or_await_human` wrapper the fallthrough used before; folding both call sites onto one helper in the already-existing post-update sibling module, rather than adding a second near-duplicate wrapper to `pr_merge.py`, is what kept the module under its pinned size-ratchet cap — see `tests/size_baseline.py`.) Any of the three escalation-worthy kinds now gets one check for an unforwarded, current-head-matching `pr_<n>_system_head.json` marker before falling through to escalation. This is a genuine behaviour widening beyond the merge-time-BEHIND case named in the review — `closed`/`unresolved_ceiling` get the same check — but it is a pure no-op everywhere no marker matches (the identical `forward_if_system_head` early-return), so no other escalation shape observes any difference.

**What it replaces.** For the specific shape this build targets — a `failed`/`timeout`/other non-terminal `pr_merge` outcome on a PR whose current head SHA matches an unforwarded `pr_<n>_system_head.json` marker — the workspace no longer parks waiting for a human who would just re-dispatch `pr_merge` anyway. `forward_if_system_head` instead returns a `forward` `Handover` with `to_team_suggestions=["pr_merge"]`, shaped like the existing `_dep_bot_rebase_handover`/`_copilot_handover` forward-to-self-or-sibling patterns: it checks the marker locally first (no `gh` call at all when there is none, or it is already forwarded), then reads the current head SHA once (`_pr_branch.fetch_flake_guard_head_sha`), confirms `is_system_authored_head`, marks the marker forwarded, and returns. Every other fallthrough shape — no prior handover, no `pr_number`, no marker, a stale or already-forwarded marker — falls through unchanged to `_await_human_handover`, byte-identical to before this build.

**What happens on re-entry.** The forwarded handover re-enters `pr_merge`'s own `run()`, which calls `_enforce_pr_merge_gate` exactly like any other `pr_merge` dispatch. If the check is still red on the same commit, `attempt_mechanical_recovery` reads the same marker again (still matching — `classify_block`'s `system_head` boolean does not consult `forwarded`) and classifies `POST_UPDATE_RED`, routing to `implementation_fix` with the `POST_UPDATE_RED` unblock recipe attached — a genuine remediation attempt where the old code produced none. If the gate instead reads `STILL_COMPUTING` or `BLOCKED_PENDING` — the checks are still settling on the new commit — `merge_gate.routes_to_merge_lane` returns the unmodified `pr_merge` decision unchanged, and the re-entered PR simply falls into `pr_merge`'s existing `_poll_until_done` loop exactly like any other in-flight PR; no new poll mechanism, no new counter, one audit row per pass exactly as every other `MERGE_LANE_POLL_CLASSES` member already produces. If the checks come back green on the exact merge commit, `pr_merge` merges on that green state directly — grounded in the commit that will actually merge, not the pre-update approval — closing the first DoD requirement without any new verification re-dispatch (a system-authored head with green required checks and Sonar on the exact commit needed no `implementation_fix`/`verification` round trip; re-verifying every routine branch update would be exactly the update-triggers-verify-triggers-update cycle the brief forbids).

**Loop bounding — the explicit correction.** `loop_guard._is_spiral_pair` only recognizes the `implementation_fix ⇄ verification` pair; it does not, and was never intended to, cover `pr_merge ⇄ pr_merge` or `pr_merge ⇄ implementation_fix`. The binding backstops for this forward path are:
1. **The one-shot `forwarded` flag** — the forward itself can only ever fire once per system-authored head SHA (above), so the `pr_merge → pr_merge` hop this section describes cannot repeat on an unchanged commit even in principle.
2. **SHA-keyed marker invalidation** — any further branch mutation (another system-authored update, or a human push) changes the head SHA, so a *second* system-authored update gets its own fresh marker and its own fresh one-shot forward; the two never compound into an unbounded chain.
3. **`check_loop_guard`'s `REVISIT_CAP = 3`** — every `pr_merge → implementation_fix` hop the `POST_UPDATE_RED` classification produces (on re-entry, above) is a normal `implementation_fix` dispatch, subject to the same per-chain revisit cap every other merge-gate remediation class already is, since `POST_UPDATE_RED` reaches the identical bare `implementation_fix` fallthrough as `GENUINE`.
4. **`_GATE_RERUN_LIFETIME_CAP = 6` and `_RECONCILE_LIFETIME_CAP = 6`** — bound how many times, in total, a PR can even *produce* a fresh system-authored head via the `TRANSIENT_FLAKE`-adjacent rerun budget and the `DIRTY` reconcile budget, independent of this forward path.

None of these four is new mechanism this build introduces solely for looping — the one-shot flag and SHA-keying are properties of the marker store itself (above), and `REVISIT_CAP`/the two lifetime caps are pre-existing budgets this build reuses rather than duplicates.

## Layer placement

`merge_recovery` sits between `dispatcher` and `predispatch_scan` in the import-linter layer hierarchy (registered in `pyproject.toml`). It imports from `alan.teams._pr_branch`, `alan.teams._pr_ready` (the readiness-cluster split moved `PrReadiness` here from `_pr_branch`), `alan.teams._pr_flake_ledger`, `alan.teams._pr_freshness` (the `MEASURED_BASELINE_STALE_REASON` constant), and `alan.teams._pr_reconcile` (all below it, all inside the single `teams` layer entry) and is imported by `dispatcher` (above it). `alan.teams._pr_reconcile` and `alan.teams._pr_freshness` are both sibling modules inside the same `teams` layer entry — no new top-level `pyproject.toml` layer was needed for either.

## Flake quarantine (pre-existing / known-flake exclusion)

`alan/teams/_pr_ready.py` (at the time of writing this lived on `_pr_branch`; the readiness-cluster split moved the whole quarantine classifier cluster to `alan/teams/_pr_ready.py` — call shape unchanged) contains a classifier `classify_flake_quarantine` (executes `gh` subprocesses internally to fetch base-commit data) that runs inside `check_pr_verifier_blockers` and `check_pr_merge_readiness` to distinguish:

- **Pre-existing**: the failing check is also red on the PR's base branch (e.g. `origin/main`) tip — detected by fetching `baseRefOid` then `GET /repos/{owner}/{repo}/commits/{sha}/check-runs`.
- **Known-flake**: the check name is in `_KNOWN_FLAKE_REGISTRY` (static dict: check_name → owned file patterns) AND the PR diff (via `gh pr diff --name-only`) touches none of those owned files.

**Fail-safe defaults** — the classifier defaults to "blocking" (introduced by diff) when:
- The base SHA, owner/repo, or check-run data cannot be fetched.
- The base check result is anything other than `"fail"` (pass/pending/unknown all block).
- Any `pending_checks` exist alongside the failing check (we wait for CI to settle first).
- The diff file list is unfetchable for a known-flake candidate.

### `PrReadiness.quarantined_checks`

Both `check_pr_verifier_blockers` and `check_pr_merge_readiness` now populate `quarantined_checks: tuple[str, ...]` on the returned `PrReadiness`.

- **`check_pr_verifier_blockers`** (used by `_verification_gates.resolve_external_gates`): rebuilds `failed_reasons` and `ok` minus the quarantined checks, so an APPROVE verdict is NOT downgraded to REQUEST_CHANGES when every failing check is pre-existing or a known flake.
- **`check_pr_merge_readiness`** (used by `dispatcher._enforce_pr_merge_gate`): annotate-only — populates `quarantined_checks` but leaves `failed_reasons`/`ok` unchanged. This preserves the pr_merge safety invariant: `pr_merge` only calls `gh pr merge` when `ok=True`, and a pre-existing red check should NOT auto-merge the PR.

### Audit trail

Every quarantine decision is written to `impl_audit.jsonl` as a `flake_quarantine_decision` entry with fields: `check_name`, `base_result`, `head_result`, `reason` (`pre_existing` | `known_flake` | `blocking`), `quarantined` (bool).
