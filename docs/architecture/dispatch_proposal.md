# Dispatch proposal contract

**Source:** `alan/dispatch_proposal.py` — `DispatchProposal`, `LEGACY_ACTION_TO_TEAM`, `NEW_WORKSPACE_TEAM`, `ALLOWED_NEW_WORKSPACE_TEAMS_CONTEXT_KEY`, `_resolve_allowed_new_workspace_teams`, `_map_legacy_dispatch_action`.

This is the single shared proposal contract validated by both human dispatch doors: build chat (`alan.routes.build_chat.propose_build_dispatch`) and explore chat (`alan.routes.explore_chat.propose_explore_dispatch`). Both reach it only through `alan.routes._chat_router.run_dispatch_proposal`, which sends the shared `DISPATCH_PROPOSAL_SENTINEL` turn, parses the reply via `parse_dispatch_proposal_yaml`, and validates it against `DispatchProposal`. There is exactly one definition of this contract; no door keeps its own copy or a compatibility shim. (A third door, the per-workspace discussion chat, validated against this same contract until it was removed — see `docs/architecture/chat_shared_mechanics.md`'s removal record.)

## The gate invariant: `counter_case` is required

`counter_case: CounterCase` has no default. A `status: ready` reply missing it fails Pydantic validation inside `parse_dispatch_proposal_yaml`, and every door 422s identically (`dispatch_proposal_parse_failed`) — there is no door-specific error branch to diverge. This is the devil's-advocate gate: a proposal cannot silently dispatch without first producing the strongest argument against committing to the scope now (`against`), the cheapest cut that still delivers most of the value (`cheapest_80`), and a cost estimate. `tests/test_dispatch_gate_invariant.py` asserts this field is non-optional as its proof-test for the whole "no ungated human dispatch door" invariant.

The gate is advisory, not blocking: the counter-case is always produced and (when supplied to the raw dispatch endpoint) audited as a waiver, but nothing in the propose→dispatch path stops an autonomous caller — the roadmap-driver and primary instance dispatch through the same `create-workspace(title, acceptance_clauses, team) → dispatch` contract with no human to click a modal.

## The legacy `action`→`team` compatibility bridge

In-flight sessions can have persisted an older `action`-vocabulary system prompt to disk before the field was renamed to `team`. Without a bridge, the first post-upgrade propose call from such a session would 422 rather than migrate. `_map_legacy_dispatch_action` and the `_accept_legacy_action` `model_validator(mode="before")` translate a `data["action"]` key (when present and `data` has no `team` key already) through `LEGACY_ACTION_TO_TEAM` onto `team`, dropping `action` from the payload. An unrecognized legacy value passes through unchanged as the `team` value rather than being rejected — the mapping widens forward-compatibly, it never narrows. A `team` key already present in the payload always wins over a stale `action`.

## The `title`/`acceptance_clauses` new-workspace discriminant

`title: str | None` is the new-workspace discriminant. When present (and non-blank), the `_validate_new_workspace_shape` `model_validator(mode="after")` requires `team` to be a member of the allowed new-workspace team set (see below) — a proposal that hallucinates a `title` for a team outside that set 422s. `acceptance_clauses: FreeTextList` (default `[]`) may only be non-empty when `title` is also present; a proposal minting acceptance clauses with no title is rejected, since acceptance clauses only make sense as the definition-of-done for a workspace being freshly created.

`recorded_clauses: FreeTextList` (default `[]`) is a parallel list beside `acceptance_clauses`: outcomes whose only possible evidence is prose, which become record clauses (`Requirement.kind == "record"`, advisory — see `acceptance_gate.md`'s "Clause kind" section) at workspace creation. It is declared on the model because `extra="ignore"` would silently drop an undeclared key, and it is a plain list of strings rather than `{text, kind}` mappings because `FreeTextList` heals a mapping back into a prose string. It sits under the same title requirement — `acceptance_clauses` or `recorded_clauses` non-empty without a `title` is rejected, with one message naming both — so an untitled proposal carrying neither list is still valid. The model is shared with the explore chat, which accepts the field but whose contract never requests it, so it is empty in practice there. A text listed in both groups is not de-duplicated by the model or the view; the create-time collapse in `workspace._sanitize_requirements` makes it arrive once, blocking.

## The `ALLOWED_NEW_WORKSPACE_TEAMS_CONTEXT_KEY` validation-context mechanism

The allowed new-workspace team set is resolved from an optional Pydantic validation-context key, `ALLOWED_NEW_WORKSPACE_TEAMS_CONTEXT_KEY` (`"allowed_new_workspace_teams"`), read via `ValidationInfo.context` inside `_validate_new_workspace_shape`. `context is None` — the plain constructor, or any `model_validate(...)` call that passes no `context=` kwarg, which covers every build-door and autonomous call site — defaults to `frozenset({NEW_WORKSPACE_TEAM})` (`NEW_WORKSPACE_TEAM = "implementation_plan"`) byte-for-byte. `_resolve_allowed_new_workspace_teams` applies the same default when `context` is present but empty or missing the key. Only `explore_chat.propose_explore_dispatch` ever passes a non-`None` context, and it passes the *singleton* `frozenset({consultant.team})` for the session's own consultant — never the full team catalog — so a proposal claiming any other team still 422s. This context threads through `run_dispatch_proposal(allowed_new_workspace_teams=...)` → `parse_dispatch_proposal_yaml(...)` → `_build_dispatch_proposal_ready(...)` → `DispatchProposal.model_validate(proposal_obj, context={...})` in `alan/routes/_chat_router.py`.

## Layer position

`dispatch_proposal` sits in the `pyproject.toml` import-linter layers list immediately below `explore_chat_repo` and immediately above `_chat_core` — below every chat-surface module (`build_chat`, `explore_chat`) and `routes`, so every consumer can reach it, and above `yaml_normalize` and `scope_audit`, which it imports (`FreeTextList` and `CounterCase`/`ScopeGapFinding` respectively). `alan/routes/_chat_router.py` imports `alan.dispatch_proposal` directly.

## Sequencing note

This relocation was sequenced ahead of the removal of the workspace-discussion feature (`alan/workspace_chat.py`'s chat/session machinery, `alan/routes/ws_chat.py`, the `WorkspaceChatPanel` UI — see `docs/architecture/chat_shared_mechanics.md`'s removal record). Moving the shared contract out first meant that the later deletion read as a pure deletion, not a deletion tangled with a move of code the other two surfaces depend on.
