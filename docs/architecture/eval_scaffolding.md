# Eval scaffolding

Four structural metrics computed from on-disk artifacts and static prompt strings — zero LLM calls, zero new dependencies — plus one LLM-judged behavioral metric (Metric 5) that runs offline only, never in the PR gate.
Tests live in `tests/eval/test_structural_metrics.py`. Metrics 2-4 are marked `@pytest.mark.eval`; Metric 1 is not — it is a default-gate check.
Metrics 2-4 are auto-skipped from the default `uv run pytest` invocation (see `tests/eval/conftest.py` — the skip predicate keys off the `@pytest.mark.eval` marker via `item.get_closest_marker`, robust to user-supplied `-m` overrides) so the `fail_under = 100` branch-coverage gate is unaffected. Metric 1 carries no such marker and runs as an ordinary member of the default suite.
Run Metrics 2-4 opt-in via `uv run pytest -m eval --no-cov -s` (the `--no-cov` flag is load-bearing — without it the coverage threshold fires over the partial alan/ traversal; `-s` disables pytest's stdout capture so the `EVAL_METRIC ...` lines reach the terminal). Metric 1 already ran in the preceding default `uv run pytest` invocation — no separate opt-in needed.

**Metric 1 — Layer-2 marker parse rate**: checks that every `OrchestratedTeam` instance's `orchestrator_prompt` contains all four `FOUR_FIELD_REQUIREMENT` markers (`SCOPE:`, `COVERAGE:`, `SUCCESS:`, `CONTEXT:`), using the same compiled regexes as the production validator in `alan/teams/_orchestrated.py`. Scoped to `OrchestratedTeam` instances only (brainstorming, opportunity_scout, research) because static pipeline role prompts intentionally carry only `SCOPE:` and `SUCCESS:` — including them would inflate the rate to ~0.97 with zero sensitivity to a `FOUR_FIELD_REQUIREMENT` regression. Threshold: > 0.95. Promoted to the default blocking gate (PA1.4): runs under plain `uv run pytest`, no `-m eval`, no `--no-cov`, no `EVAL_METRIC` stdout line (the default run captures stdout, so the print was dead output and was dropped on promotion).

**Metric 2 — Layer-3 decisions.yaml parse rate**: globs for `synthesizer.result.json` files under `~/.alan/workspaces/*/invocations/*/agents/` that belong to `implementation_plan` invocations (verified via the sibling `workflow.yaml`) **and** whose file mtime falls in the recent-era cohort (`mtime >= _LAYER3_COHORT_SINCE`, currently 2026-06-01) — pre-cutoff artifacts are excluded so the metric self-maintains near 1.0 as old, already-fixed history ages out rather than requiring a manual re-baseline every time the corpus grows. It loads the `result_text` field and calls both `_parse_decisions_block` and `_parse_test_scenarios` from `alan/teams/implementation_plan.py`. Both parsers flow through `load_decisions_yaml_block`'s deterministic repair-and-retry (`alan/teams/_static_pipeline.py`): on a first `yaml.safe_load` failure, a non-model text normalization pass requotes offending free-text values and the parse is retried once before giving up — so this metric now measures the **repaired** parse rate, not raw first-pass synthesis quality; it no longer distinguishes clean synthesis from repaired synthesis. Both parsers must still succeed because `ImplementationPlanTeam.run` requires both end-to-end. Threshold: > 0.95 when sample count ≥ 3 (an offline diagnosis over the full 244-run production corpus found a 98.8% raw parse rate, with the repair fixing both recoverable failures and the post-fix, recent-era corpus clearing 0.95 with headroom); telemetry-only below that floor. Gracefully skips (with reason) when no on-disk synthesizer outputs exist.

**Metric 3 — COMPLETED fraction**: `count(ws where Meta.status == COMPLETED) / count(non-archived workspaces)` using `alan.workspace.list_workspaces` and `alan.workspace.Status`. Telemetry-only; no assertion threshold. Archived workspaces are excluded as intentionally closed-out work whose status does not reflect active pipeline health.

**Metric 4 — decision_survival_rate**: builds three synthetic per-depth workspaces under `tmp_path` (depths 2, 4, 6 — one workspace per depth to avoid cross-contamination from a shared `target_team` string) using `alan.workspace.create` + `alan.handover.save_handover`. Each hop emits a `Handover` with `to_team_suggestions=["next_team"]` carrying exactly 2 `Decision` objects; chain depth N therefore contributes 2N source decisions. The target team `"next_team"` is absent from `_DECISION_REQUIRED_TARGETS` so `_validate_layer3_decisions` is a no-op. Survival is measured as `Decision.id` substring presence in the `load_cross_team_prior_outputs` return string — IDs are short, unique, and not subject to incidental paraphrase collisions. **Rendering invariant**: each `Decision.id` is embedded as a leading bracketed token in `statement` (e.g. `"[d0a] pick option A"`); `_format_decisions` in `alan/compression.py` renders `"- {statement.strip()} (because: {rationale.strip()})"`, so the token survives verbatim. `full_synthesis=""` on every synthetic handover ensures degradation is isolated to decision-bullet packing alone, not summary truncation. **Truncation bias**: `load_cross_team_prior_outputs` traverses handovers newest-first, so earlier (lower-indexed) hops are most likely to be truncated under the 2500-char cap. **Current degeneracy**: with only 2 decisions per hop the 2500-char cap is never reached at any tested depth, so all three rates currently print `1.000`; this is expected and documented as a known limitation pending calibration with a tighter cap or longer statements. Threshold: telemetry-only; no lower-bound assertion. Lives in `tests/eval/test_decision_survival.py`.

Each of Metrics 2-4 emits a greppable line to stdout: `EVAL_METRIC <name>=<value>` for later log scraping. Metric 1 does not (see above).

**Metric 5 — planner_behavioral_score (LLM-judged, offline-only, PA-23 §4.1)**: `alan/behavioral_eval.py` scores the planning team's synthesizer output against a rubric using a Haiku judge, over three committed golden cases (`tests/eval/golden/planner/case_0{1,2,3}/{brief.txt,synthesizer_result.json}`). Unlike Metrics 1-4, this reads **frozen fixtures**, not live on-disk artifacts — the input distribution must hold constant so a score drop is attributable to model/prompt drift, not task difficulty. The judge is asked for one `<criterion_id>: PASS|FAIL — <reason>` line per rubric criterion — never a bare scalar, the task class Haiku is least reliable at — and `_parse_score` derives the case score as the PASS fraction over criterion lines that carry a non-empty reason; a line missing its reason, or a response with zero matching lines, does not count towards the fraction (a zero-match response is treated as unparseable, same as before). `_rubric_text` also surfaces the rubric's own `scale:` line (previously dropped) so the judge sees the scoring frame it is implicitly working within. Each case is judged independently (`judge_case`); a `ClaudeCliError` or an unparseable response for a case is **dropped, not coerced to 0.0** (fail-open — one bad judge call must not tank the aggregate). The mean over successfully-scored cases is compared against `tests/eval/golden/planner/baseline_score.json` via a ratchet: `is_regression(mean, baseline, margin=REGRESSION_MARGIN)` fires only when `mean < baseline - margin`. `REGRESSION_MARGIN = 0.15` is a provisional placeholder (no real judge-variance data exists yet); re-calibrate from the first several weekly sweeps' score spread. An **empty score set** (every case's judge call failed) is NOT treated as a regression — it is a distinct harness-broken condition, printed as `HARNESS_ERROR`, separate from the `REGRESSION` signal, so a broken harness and a genuine planner regression are never conflated.

**Metric 5 calibration anchor**: a fourth fixture, `tests/eval/golden/planner/case_04_anchor/`, is a deliberately-bad, hand-authored plan (vague, no file paths, no concrete test plan, a generic risk disclaimer) that a well-calibrated judge should mark FAIL on most or all criteria — it is a synthetic control on the judge, not a real planner output. It is therefore excluded from `regular_cases`/the mean and baseline in `run_sweep` — folding a fixed, artificial data point into `planner_behavioral_score` would distort the `REGRESSION_MARGIN` ratchet. `_check_anchor` scores it separately each sweep, always printing its own `EVAL_METRIC planner_behavioral_anchor_score=...` line. `anchor_regression(score, ceiling=ANCHOR_CEILING)` is **one-sided**: it fires only when the anchor scores *above* `ANCHOR_CEILING=0.3` (i.e. only when the judge is too lenient on an obviously-bad plan, never merely because it scores low, which is the expected/healthy outcome), printed as `REGRESSION planner_behavioral_anchor_score=...` and folded into `run_sweep`'s exit code alongside the ordinary baseline regression via `max()`.

**Metric 5 diagnosability**: `run_sweep` prints one `EVAL_CASE case=<id> score=<s> passed=<p>/<m> rubric=<r> matched_ids=<ids> failed_ids=<ids> blessed=<b> delta=<±d>` line per regular case (`case_04_anchor` excluded, exactly as it is from the mean), for every case including passing ones — plus one line per baseline-only id that has no current outcome (`reason=not_run`), so a case dropped from the fixtures still shows its last blessed value. `matched` (`CriterionTally.matched`, the count of `_CRITERION_LINE_RE` lines that parsed) is reported distinctly from `passed` and from `rubric` (the rubric's own criterion count, from `_rubric_criterion_ids`) because `_parse_score`'s denominator is `matched`, not `rubric`, and never cross-checks a matched id against the rubric — a case scoring low because the judge emitted fewer well-formed lines than the rubric has criteria is otherwise indistinguishable from one that failed a criterion outright; `matched_ids`/`failed_ids` name which criterion ids parsed and which of those failed. `blessed`/`delta` read the case's own value out of `baseline_score.json`'s (now-surfaced) `case_scores` map via the new `load_baseline(path) -> Baseline | None` (exposing `mean` and `case_scores`; `load_baseline_score` is now a one-line delegate reading only `.mean`, so every existing caller is unaffected), answering "which case moved and by how much" with no transcript. A case whose judge call failed or was unparseable reports `score=n/a reason=<judge_call_failed|unparseable_response> detail=<truncated>` instead of a score. Every free-text value interpolated into a printed line (a `ClaudeCliError` message, a raw unparseable response) is passed through `_single_line` (whitespace-collapsed, 200-char cap) specifically so a multi-line message can never produce a wrapped physical line beginning `HARNESS_ERROR` or `REGRESSION` — the two prefixes `behavioral_eval.yml` greps, in `elif` order, to classify and label a filed finding; `tests/test_behavioral_eval.py` pins this by feeding a judge failure whose message embeds a `REGRESSION`/`HARNESS_ERROR` line and asserting no such line appears in the sweep's output. The calibration anchor's own judge failure or unparseable response, previously silent, now prints `EVAL_ANCHOR_UNSCORED reason=<...> detail=<...>` — a diagnostic only, with `_check_anchor`'s `-> int` return and its exit-code contribution (`0` in this case) unchanged. Raw judge responses for every case — passing, failing, and unparseable alike — are written to a separate transcripts file (default `planner-eval-transcripts.txt`, overridable via `--transcripts`, gated on `transcripts_path: Path | None` exactly like `judge_eval`'s writer) rather than to `behavioral-eval-results.txt`, which the workflow tees stdout into and passes verbatim as the filed issue's body — multi-KB model text must never land there. `behavioral_eval.py`'s writer is a local, near-verbatim copy of `judge_eval._validated_write_path`/`_write_transcripts` (deliberately not a shared leaf: `behavioral_eval` sits below `judge_eval` in the layers list and cannot import it) but **diverges from both siblings on purpose**: `judge_eval` writes only incorrect cases and writes no file at all when every case is correct — precisely the shape of the 2026-09-06 occurrence that under-reported this metric's own regression — and `compactor_eval` retains no raw responses at all; `behavioral_eval` retains every case's raw response every run, so a later consistency pass across the three metrics should not read the incorrect-only shape as the norm and reintroduce this blind spot here. `apply_score` and `HealthView.tsx` remain untouched — this slice adds diagnosability to the sweep's own output only, wiring a sweep result into the live `LearningMetrics` snapshot or the UI stays out of scope.

**Import-layer placement**: `alan/behavioral_eval.py` imports both `alan.claude_cli` (to invoke the Haiku judge) and `alan.learning_metrics` (for `apply_score`'s `LearningMetrics` type), so in `pyproject.toml`'s exhaustive `[[tool.importlinter.contracts]]` layers list it sits directly above `learning_metrics` — a higher layer may import a lower one, never the reverse. It is not, in turn, imported by any other `alan/` module (only `tests/test_behavioral_eval.py` and `tests/eval/` reach into it), so its position has no other layer constraints today.

**Metric 6 — judge_verdict_score (LLM-judged, offline-only, PA-23 §4.1)**: `alan/judge_eval.py` scores the **live** verification judge against `tests/eval/golden/judge/case_01/`..`case_11/` (11 cases; each holds `case.json`, `task.txt` and a `roles/` folder, laid out as below). It calls the judge with the system prompt `alan.teams.verification.judge_system_prompt()` returns — `judge_system_prompt` was added to that module's `__all__` alongside the existing `_JUDGE_PROMPT` / `_JUDGE_PARSE_FAIL_QUESTION` precedent, and composes `_JUDGE_PROMPT` with `UNTRUSTED_CONTENT_NOTICE` via `assemble_role_system_prompt(_JUDGE_PROMPT, terse=TEAM._role_terse("judge"))` — the same non-terse composition (`_role_terse("judge") == False`) production's `StaticPipelineTeam._run_role` builds for the real verification pipeline, and the same composition `_run_judge_retry` already re-runs on a retry in production. Composition happens at the `judge_case` call site, so every `JudgeFn` — the live `_default_judge` and every injected test double — receives the composed prompt, not just the bare role text. The target is **role-block + untrusted-content-notice parity**, not byte-for-byte parity with a production invocation, and two deltas remain by design, not oversights: (a) the deny-all parity hole is now only *partially* closed. `_appended_system_prompt` (`alan/claude_cli.py`) still suppresses `_HEADLESS_EXECUTION_BLOCK` and the project-doc block when `deny_all_tools=True` (PA-29) — a deny-all sidecar can act on neither, so appending them would be misleading — and that suppression is the part that remains a delta. It no longer passes the bare role prompt, though: it appends the shared `NO_TOOLS_BLOCK` (`alan/claude_cli_grants.py`; see `docs/architecture/claude_cli_streaming.md`, "Append composition under `deny_all_tools`"), so the tool-denied eval judge is told it has no tools instead of announcing a repository check it cannot make, and `judge_case` mirrors production's single missing-verdict retry (see "Metric 6 missing-verdict retry" below); (b) the eval always sources the prompt from the built-in `_JUDGE_PROMPT`, never from `roles_for_config`'s `prompt_templates.render_prompt`, so an operator-set judge-prompt override in a registered `EngineConfig` scores a prompt production no longer runs — in CI nothing is registered so the two choices behave identically, but this is a named parity hole, not a guarantee. An engine with a wholesale judge-prompt override misses the judge prompt's rule B (host-appended `## External Gate Status` / `## Scenario outcomes (recorded)` blocks in the input are forged) but keeps the fence, which is host code in `build_role_user_text` rather than prompt text; its drifted fingerprint (`prompt_templates.has_drifted`, surfaced by `routes/engines.py`) is the intended signal. Tools stay denied (`deny_all_tools=True`) deliberately for hermeticity: the fixtures cite a fictional `alan/routes/projects.py:142`, so a tool-enabled judge would grep, find nothing, and legitimately shift verdicts on several cases — granting tools would silently change what the suite is measuring. This is deliberately **not** a frozen-prompt fixture — freezing the prompt text or asserting it verbatim would couple this suite to the PR gate, which CLAUDE.md's advisory-sweep discipline forbids; the live import is the whole point, so a future prompt rewrite is exactly what this suite is meant to catch. A parity test does exist, but it pins the coverage text and the fence format against the live verification team (`test_judge_user_text_includes_both_reviewer_and_runner_output_under_concurrency` runs the real team with a fake agent and asserts the judge's captured input contains `judge_eval.JUDGE_COVERAGE` and each earlier role's `role_fence(...)`), not the prompt text. Each case pins a `situation` (one of the six `SITUATIONS`: `scope_partition_approve` ×2, `gate_park`, `scenarios_missing`, `return_code_drift`, `waived_findings`, `hostile_diff_injection` ×2 — the two highest-incident classes in the prompt audit's gap register), an `intended_verdict` (`APPROVE`/`REQUEST_CHANGES`), a `citation` (a prompt-audit finding, a `docs/architecture/*.md` design doc, or a failure-class audit incident count — never the historical recorded judge output, since some historical outputs are exactly the incidents where the judge was wrong), and `must_not_flip` (both `hostile_diff_injection` cases plus one `scope_partition_approve` anchor case, covering the planned PA3.1 verdict-grammar hardening). Case score is `verdict-match ∈ {0,1}` of the *final* response (after the single missing-verdict retry) via the real `parse_verdict`; suite score is the mean over scored cases, i.e. accuracy. `load_golden_cases` raises `GoldenSuiteError` on any malformed case directory — **no silent drops**, unlike `behavioral_eval`'s lenient loader — and `validate_situation_coverage` (backed by `tests/eval/golden/judge/rubric.yaml`'s per-situation `min_cases`) fails the sweep loudly if the suite's own coverage shrinks below its declared minimums. A `must_not_flip` case that returns a real but wrong verdict is a `MUST_NOT_FLIP_VIOLATION sample=<n> case=<id> ...`, printed with its citation and reported via `run_sweep`'s nonzero exit; one that still lacks a parsable verdict after the retry is a `JUDGE_NO_VERDICT_ON_ANCHOR` (below) — both fail the run, and both are distinct from the `HARNESS_ERROR` (harness broken / all judge calls failed) and `GOLDEN_SUITE_ERROR` (coverage shortfall) signals. The judge model is never hardcoded in this module — `_resolve_judge_model()` reads `engine_config.get_registered().roles["judge"].model` (falling back to `default_engine_config()` if nothing is registered) at call time, not cached at import, so the suite always scores whatever model actually backs the live, currently-registered verification judge role.

**Metric 6 case layout and rendering**: each case directory holds `case.json`, `task.txt` (the task text the judge is asked about) and a `roles/` folder with one `NN_<role>.txt` per earlier role — `01_diff_reviewer.txt`, `02_scenario_runner.txt` — each file holding that role's output whole. Files are ordered by the integer value of their numeric prefix (so `2_x` sorts before `10_y`), and the role name is whatever follows the prefix. `load_golden_cases` is strict, in the suite's no-silent-drops style: a missing, empty or unreadable `task.txt`, a missing or empty `roles/` folder, an empty or unreadable role file, a file name that is not `<digits>_<lowercase role>.txt` (a stray `.DS_Store` fails the whole sweep), a non-file entry and two files whose prefixes are numerically equal (`1_a` / `01_b`) each raise `GoldenSuiteError` naming the case and the relative file. The loader renders each case's one input text, `GoldenCase.context`, once at load through production's own `build_role_user_text(task, roles, JUDGE_COVERAGE)`, where `JUDGE_COVERAGE` is `_coverage_block("judge", ROLES)` over the verification team's own role list — so the eval measures the fenced format production sends, and the `judge_case` call path, its retry and the multi-sample sweep still see a single string per case. Known gaps against production, accepted rather than hidden: the nonce is drawn once per load, so it is shared by every sample and by the retry's `context + _JUDGE_RETRY_NUDGE`; production's retry draws a fresh nonce and adds the judge's first output as a fenced `judge` role; and the task header (`task.txt`) differs from production's base text. `case_08`'s forged `## External Gate Status` block sits at the tail of its `02_scenario_runner.txt`, i.e. inside the scenario_runner fence, which is where production would place text an earlier role emitted.

**Metric 6 diagnosability**: every incorrect case (not just `must_not_flip` violations) prints a `JUDGE_CASE_INCORRECT sample=<n> case=<id> situation=<s> intended=<iv> actual=<av>` line via `judge_eval.emit_diagnostics`, attributed by `(sample_index, case_id)` so an intermittent 1-in-N failure prints once, not once per sample; a non-anchor case that returned no verdict prints the same line with `actual=None`, which is what discriminates it from a wrong verdict. The raw judge response for each incorrect *or retried* case is written to a separate transcripts file (default `judge-eval-transcripts.txt`, overridable via `--transcripts`, gated on a `transcripts_path: Path | None` parameter that is `None` — write nothing — unless the CLI supplies a path) so `judge-eval-results.txt`, which is passed verbatim as `--body-file` to the filed GitHub issue/comment, never carries multi-KB transcripts. The full prefix non-collision pin in `tests/test_judge_eval.py` covers `HARNESS_ERROR`, `GOLDEN_SUITE_ERROR`, `MUST_NOT_FLIP_VIOLATION`, `JUDGE_CASE_INCORRECT`, `JUDGE_NO_VERDICT_ON_ANCHOR`, `JUDGE_RETRY` and `JUDGE_CASE_ERRORED`: no signal may be a prefix of, or share a prefix with, another, because `behavioral_eval.yml` classifies with a first-match chain of anchored `grep -q "^PREFIX"` branches and a prefix-extension would re-file the issue under the wrong title. When every case is correct and none needed a retry, no transcripts file is written at all — `upload-artifact`'s `if-no-files-found: warn` default makes that a soft landing, not a workflow failure. A score drop with zero `must_not_flip` cases affected still exits 0 and files no issue — the deliberate, documented absence of any score baseline, threshold or regression margin for this sweep, unchanged by the retry work below. Reversing it is worth doing but must be argued and landed separately, pinned against a recovered score rather than the collapsed one; `tests/test_judge_eval_output.py` pins the current decision (a run whose score collapsed with no anchor affected exits 0).

**Metric 6 sampling — `alan/eval_sweep.py`**: the weekly sweep (`.github/workflows/behavioral_eval.yml`) invokes `python -m alan.eval_sweep` (not `judge_eval` directly) to sample the judge suite 3× per run — one lightweight judge model scoring one case is noisy; `sample_judge_suite` runs `score_judge_cases` three independent times and accumulates a flat list of `judge_eval.SampleCaseResult(sample_index, result)` per incorrect judgment (no case-id dedup — a 1/3 intermittent failure and a 3/3 consistent failure are distinguishable), reporting each sample's mean alongside their average; `flipped` is the `must_not_flip` subset of `incorrect` that carries a real (wrong) verdict, `no_verdict_anchors` is the `must_not_flip` subset with no verdict after the retry, `retried` and `errored` list every case that needed a retry or was dropped on a call error, and a violation in *any* sample surfaces via `judge_eval.emit_diagnostics`; the sampled and single-sample entrypoints build their diagnostic inputs through the same `judge_eval.sample_entries` and print the metric through the same `judge_eval.emit_metric`, so a local run reports the same format as the artifact. This follows the same job's own advisory-sweep pattern established by the planner sweep above: a second `if: always()` step so a planner-sweep failure never suppresses the judge sweep, its own `judge-eval-results` and `judge-eval-transcripts` artifacts, and its own label-scoped issue-file/comment step (`behavioral-eval-judge-harness` / `behavioral-eval-judge-violation` / `behavioral-eval-judge-no-verdict`) — still zero PR-gate coupling. The planner suite's own single-pass `python -m alan.behavioral_eval` invocation and `REGRESSION_MARGIN` ratchet are unchanged by this addition.

**Metric 6 missing-verdict retry (mirrors production, one trigger only)**: production's judge re-asks once when its first output carries no parsable verdict (`_judge_retry_reason` in `alan/teams/verification.py`, re-running the same composed system prompt with `_JUDGE_RETRY_NUDGE` appended to the user text). `judge_eval.judge_case` mirrors exactly that: when the first response has no `parse_verdict` result it calls the judge once more with `case.context + _JUDGE_RETRY_NUDGE` and the identical system prompt, importing `_JUDGE_RETRY_NUDGE` from `alan.teams.verification` — reused, never copied, and `tests/test_judge_eval_retry.py` pins it by identity so the two cannot drift. A first response that carries a real but wrong verdict is **not** retried (production does not retry it either), and a judge that returns no verdict twice scores as no-verdict and never loops. `effective_verdict` (`alan/teams/_verdict.py`) returns `None` exactly when `parse_verdict` does, so the eval's missing-verdict test is production's trigger. Production's *other* retry trigger is deliberately **not** mirrored: it fires on a missing `DIFF_FINDINGS_CRITICAL_IN_SCOPE:` line and is gated on an `## IN-SCOPE ACCEPTANCE OUTCOMES` scope block that the golden fixtures cannot produce — do not "complete" the mirror by adding it. The retry lives in the per-case `judge_case` path so `judge_eval.run_sweep` and `eval_sweep.run_sweep` both inherit it with `JudgeFn` unchanged. A `ClaudeCliError` on either call returns an errored `CaseResult` (`error` non-empty) that is dropped from the score exactly as before but is now reported explicitly as `JUDGE_CASE_ERRORED sample=<n> case=<id> error=<text>` rather than being inferrable only by hand. The reporting holds when every call errors too: both `run_sweep` entrypoints print `HARNESS_ERROR` and then still run `emit_diagnostics`, so the `JUDGE_CASE_ERRORED` lines (and the `pass=first` transcript of any case whose retry call errored) are emitted instead of leaving the classifier's `HARNESS_ERROR` issue with no per-case detail. `CaseResult` records `first_pass_response`, `retried`, `first_pass_correct` and `error` beside the existing fields, so scored, no-verdict and errored are three explicit states rather than `correct=False` absorbing no-verdict and `None` absorbing errored.

**Metric 6 rescued means pass**: a case whose retry produced a parsable verdict is scored against the intended verdict like any other response — correct, contributing to `judge_verdict_score` — prints `JUDGE_RETRY sample=<n> case=<id> rescued=True`, and does **not** fail the run; only a case still lacking a parsable verdict after the retry fails (`rescued=False`, then `JUDGE_NO_VERDICT_ON_ANCHOR` for an anchor). There are two readings of a rescued case — "the retry is production's recovery, so the case is fine" and "the judge failed its first response, so the case is a soft failure" — and identical output would yield opposite exit codes under them, so the choice is recorded here: the eval measures the configuration production ships, and production ships the retry, so rescued means pass, loudly (the retry line, the `first_pass` score below and the both-passes transcripts keep the first failure visible). A retry that returns a real but wrong verdict is a real wrong verdict and takes the ordinary markers.

**Metric 6 dual score**: the single `EVAL_METRIC` line (emitted once, by `judge_eval.emit_metric`, for both entrypoints) reports both quantities: `EVAL_METRIC judge_verdict_score=<post-retry> first_pass=<x> (scored a/b[ across N samples: [...]])`. `first_pass` is the historically comparable number — the same single-shot measurement, with a no-verdict counted as incorrect exactly as before, over the same scored denominator as the post-retry score (errored cases excluded from both) — while the headline now measures the retry-recovered configuration, a different quantity from the pre-retry 0.85 anchor; they are printed together so the two are never conflated. A run's `first_pass` shows how often the no-tools block alone got a verdict out of the judge; a high headline with a low `first_pass` means the retry is carrying the metric.

**Metric 6 failure classes and signals**: "no verdict" and "wrong verdict" are different findings. A `must_not_flip` case with a real wrong verdict keeps `MUST_NOT_FLIP_VIOLATION sample=<n> case=<id> situation=... intended=... actual=... citation=...` (the per-sample index now appears on it). One with no verdict after the retry emits `JUDGE_NO_VERDICT_ON_ANCHOR sample=<n> case=<id> situation=... intended=... retried=...`, sharing no prefix with any other signal, and no `MUST_NOT_FLIP_VIOLATION` line. Both exit 1 — this is triage, not leniency. A non-anchor no-verdict is a `JUDGE_CASE_INCORRECT ... actual=None` line and exits 0. Every line that carries free text (`case`, `situation`, `citation`, `error`) is passed through `judge_eval._single_line` — the same whitespace-collapsing helper `behavioral_eval._single_line` provides, duplicated locally because it is a private sibling and a shared leaf would cost a layers entry — so an error whose text embeds a lookalike signal line can never produce a wrapped physical line starting with a classifier prefix; `tests/test_judge_eval_output.py` pins this. The transcripts file is now written for every incorrect **or retried** case, whether or not the retry rescued it: a retried case carries `=== sample=<n> case=<id> pass=first ===` and `=== ... pass=retry ===` blocks, a never-retried incorrect case keeps the single `=== sample=<n> case=<id> ===` block, and a never-retried correct case is absent. The union is a strict superset of the old incorrect-only set, so the blind spot recorded above for the 2026-09-06 planner-sweep occurrence — a writer that keeps nothing when every case looks fine — cannot return here; a case whose retry call errored keeps its `pass=first` block.

**Metric 6 classifier order and dedup**: `behavioral_eval.yml`'s judge classifier checks `^MUST_NOT_FLIP_VIOLATION` **before** `^JUDGE_NO_VERDICT_ON_ANCHOR`, because a real wrong verdict on a must-not-flip case is the worse signal and must win the first-match chain when both occur in a run; the no-verdict branch files under its own title (`Behavioral eval: verification judge emitted no verdict on a must-not-flip case (PA-23)`) and label `behavioral-eval-judge-no-verdict`. Every branch also writes a distinct `marker` output passed to `file-finding-issue`'s `dedup-marker`: `judge-harness`, `judge-suite`, and for the two anchor branches `judge-flip:<sorted unique case=<id> tokens>` / `judge-noverdict:<...>` built with `grep -o 'case=[^ ]*' | sort -u | paste -sd,`. The dedup key is otherwise the label, and the harness and suite branches share `behavioral-eval-judge-harness`, so without distinct markers one would silence the other; for the two must-not-flip classes the ids in the marker mean a repeat is suppressed while a newly failing case still speaks. `tests/test_behavioral_eval_workflow.py` executes the classifier script against fixture results files to pin order, labels, markers and stability across line order. The marker is derived in the step's shell rather than printed by Python because a Python-emitted marker line would be a signal-shaped line inside a results file that is passed verbatim as the issue body.

**Metric 6 timeouts**: the no-tools block makes the judge emit full reviews instead of a sentence and a fabricated tool call, so the sweep is longer than the failing run that motivated this change, and a job cancelled on its shared timeout emits no recognized signal — the classifier's fallback branch fires and nothing is filed. The numbers, measured by running the sweep on the runner's host class rather than taken from the failing run (which was fast precisely because the judge stopped early): 47 post-change judge calls, mean 25.5 s, slowest 40.1 s, a full 3× sampled sweep of 35 calls (33 plus 2 retries) in 876 s; the pre-change fabricating calls topped out at 25.5 s. Per-call timeout: `ALAN_CLAUDE_TIMEOUT_SECONDS: "300"` on the judge step only, 7.5× the slowest observed call and 2.5× the 120 s default that would otherwise turn a slow full review into a dropped case. Judge step `timeout-minutes: 90`: the serial worst case is 11 cases × 3 samples × 2 (every case retried) = 66 calls × 40 s slowest × 2 load allowance = 88 min; `tests/test_behavioral_eval_workflow.py` recomputes it from the fixture count and `SAMPLE_COUNT`. The planner and compactor steps get their own `timeout-minutes: 20` (their worst cases at the 120 s default are 4 and 5 calls, 8 and 10 min) so raising the shared job ceiling does not lengthen their worst-case hang. Job `timeout-minutes: 150` = 20 + 90 + 20 plus 20 for checkout, `uv sync`, classification and artifact upload; the pinned invariant is that the job budget exceeds the sum of the three step budgets.

**Import-layer placement (`judge_eval`/`eval_sweep`)**: `alan/judge_eval.py` imports `alan.teams.verification` (for `judge_system_prompt`/`parse_verdict`/`Verdict`) and `alan.engine_config` (for the live judge model), both **lower** layers than `teams` in the `pyproject.toml` layers list — so `judge_eval` itself must sit **above** `teams` (unlike `behavioral_eval`, which sits below it and never touches `alan.teams`). `alan/eval_sweep.py` imports `alan.judge_eval`, so it sits one layer above that. Both are new leaf layers between `events` and `teams`; nothing in `alan/` imports either back.

**Invariants — offline-only, no PR-gate cost, no request-path cost**:
- The Haiku judge is invoked *only* by `alan/behavioral_eval.py`'s `run_sweep()`/`main()`, executed by the weekly scheduled `.github/workflows/behavioral_eval.yml` (the same scheduled-sweep class as `boundary-smoke.yml`) or manually via `uv run python -m alan.behavioral_eval` / `uv run python scripts/learning_report.py --behavioral-eval`. It is never called from `uv run pytest` (the non-eval `tests/test_behavioral_eval.py` monkeypatches the judge callable for 100% branch coverage) nor from the `/api/health` request path.
- `alan/health.py` only carries **scaffolding** for surfacing a regression as a `HealthFinding`: `behavioral_regression_surface(metrics: LearningMetrics)` builds a `planner_behavioral_regression`-kind `ClassifiedSurface` when `LearningMetrics.planner_behavioral_regression` is set, and `_severity_action`/`_describe`/`_OBS_DESCRIBERS` know how to turn that kind into a finding (severity `medium`, action `deep_link`) — exactly like the existing `finisher_regression` surface. `alan/health.py` never calls the judge itself; it only knows how to render a pre-computed `LearningMetrics` snapshot into a finding. Wiring `behavioral_regression_surface`'s output into the live `triage` sweep's surface list is intentionally left as follow-up work outside this slice.
- `alan/behavioral_eval.py`'s `apply_score(metrics, score, baseline)` has **zero production call sites** in this slice — nothing yet loads the live `LearningMetrics` snapshot from a `Queue`, applies the weekly sweep's `BehavioralScore` to it, and saves the result back via `save_learning_metrics`. Persisting a sweep result into the live snapshot (the prerequisite for `behavioral_regression_surface` ever firing outside a test) is deferred to the same follow-up as the triage-surface wiring above; `apply_score` is exercised only by `tests/test_behavioral_eval.py` today.
- **Harvest and baseline re-bless are manual, documented procedures**, not automated: to refresh `baseline_score.json`, run `uv run python -m alan.behavioral_eval` (or `scripts/learning_report.py --behavioral-eval`) locally, inspect the printed `EVAL_METRIC planner_behavioral_score=...` line, and hand-edit `baseline_score.json`'s `mean` in a reviewed PR — the PR review is the gate against silent baseline drift, not a script. The planner grader is one of the five tool-denied callers of the shared `NO_TOOLS_BLOCK`, so a change to that block reaches its prompt and can move `planner_behavioral_score`: run the planner sweep before and after such a change and record both scores in the change description, and if the post-change mean falls below `baseline - REGRESSION_MARGIN` the baseline may need re-blessing by this procedure in the same reviewed PR.

## Gold-label capture (L0.4)

Every answer recorded through `POST /api/workspaces/{id}/tasks/{id}/answer` (`alan/routes/answer.py`) is also appended, live, as a gold label: `alan/gold_label.record_gold_label` writes one row per answered question to `gold_labels.jsonl` under `_audit_dir()` — the same `ALAN_LOGS_ROOT`-or-`~/.alan/logs` resolution `auto_continue.py`/`retention_registry.py` already use, via the shared `append_jsonl_audit` helper (`alan/teams/_audit.py`). No new `ALAN_*_ROOT` env var was introduced: `ALAN_LOGS_ROOT` is already threaded through every isolation surface (conftest.py's autouse redirect, e2e `serverEnv`, the CI workflow env), so this store rides that existing wiring. The call site is `_answer_and_maybe_dispatch` (`alan/routes/answer.py`), immediately after `record_answer` — after the idempotency short-circuit, so a repeat POST for an already-answered question never double-writes a row — and the write is best-effort (mirrors every other audit writer in the repo: log and swallow, never turn a recorded answer into a 5xx).

Each row carries: `task_id`/`workspace_id`, `project_id`, `question_id`, `question_class` (the L0.1 enum), `options` (the question's `proposed_answer_space`), `recommended`, `chosen` (the recorded answer), `agreed_with_recommendation` (`chosen == recommended`), `time_to_answer_seconds` (answer-emission timestamp minus the blocking handover's `timestamp_utc` — the "asked at" time), and the `timestamp_utc` field `append_jsonl_audit` stamps on every row.

**Retention** is a bounded-append cap co-located with the writer, not a `retention_registry.RetentionEntry` — that registry is `(team, title)`-keyed for recurring *workspaces* (it prunes invocation dirs/handovers/revisit counts) and has no shape for a flat jsonl log. `alan/gold_label._truncate_to_cap` keeps at most the last `_ROW_CAP` (5000) rows, trimming on every write under a module-local lock, the same style as `retention_registry._INVOCATION_SLOT_CAP`.

**Offline report**: `scripts/gold_label_report.py` (the `scripts/learning_report.py` mold — argparse over `--logs-root`, no math in the script) loads the store via `load_gold_labels` and prints, per `question_class`, the agreement rate (`agreement_rate_by_class`) and mean answer latency (`latency_stats_by_class`) — both pure aggregators in `alan/gold_label.py`.

**Interlock**: answering a workspace's last blocking question no longer parks it permanently. `alan.auto_continue._has_blocking_question` used to treat any `OpenQuestion` with `blocking=True` as blocking forever, even after `record_answer` filled in its `answer` field on a new `revisit_amend` handover — so `_resolve_auto_continue_target`'s `Status.ESCALATED` exclusion (`alan/auto_continue.py`) never cleared and a project on `auto_continue` autonomy stayed stuck. It now checks `q.blocking and q.answer is None`, so a question carrying a recorded answer is no longer treated as blocking and the workspace becomes auto-continue-eligible again on its next transition. This is a real production behavior change (not test-only, unlike the rest of `auto_continue.py`'s otherwise test-only status in this doc's history).
