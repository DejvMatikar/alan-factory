# Dispatch instructions: authority and persistence

**Source:** `alan/teams/_pr_handover.py`, `alan/teams/_fix_prompt.py`, `alan/teams/_fix_forward.py`, `alan/sticky_instructions.py`, `alan/merge_gate.py`, `alan/workspace.py`, `alan/dispatch.py`, `alan/dispatcher.py`, `alan/queue.py`, `alan/dispatch_instructions.py`, `alan/routes/dispatch_instructions.py`.

Free-form `instructions` text attached to a dispatch (human-typed, or generated by the dispatcher's own merge-gate remediation route) is delivered into a worker's prompt via `## User dispatch instructions`. Two properties of that delivery are covered here: whether the instructions can override the role's standing scope prohibitions, and whether they survive past the one run they were attached to.

## Two-tier prohibition model

`_pr_handover.py`'s `_forbidden_actions_block` renders forbidden actions in up to two sections, via `_fix_prompt.render_forbidden_block(default, absolute)`:

- **`## Forbidden actions`** — `prior.forbidden_actions` (review-authored, dynamic) plus `TeamConfig.default_forbidden` (code-authored, static). This is the **overridable** bucket: `prior.forbidden_actions` lands here specifically so that a prior review reintroducing a scope objection the dispatch instructions are meant to override does not silently win.
- **`## Absolute prohibitions`** — `TeamConfig.absolute_forbidden`, rendered only when non-empty (so `implementation`'s `TeamConfig`, which leaves it `()`, renders byte-identically to before this split). Mechanical and safety rules — no editable installs, no amending prior commits, no pushing/publishing beyond what the host process already does — live here and are never overridable by any instruction. The section binds only what the executing run writes: pre-existing branch content that appears to violate one of these rules is reported in the run's `## Summary` / `## Open questions` and left in place, whether or not the worker believes it legitimate. A commit the `## Fleet commit ledger` (below) attributes to this workspace's own fleet runs remains revertible — that is an established remedy (a reviewer ruling earlier fleet work out of scope, and a later run undoing it), keyed to who produced the commit, not to which run is currently executing. A run whose review mixes an untouchable-content finding with genuinely actionable ones commits the latter normally and marks the declined finding `[BLOCKING]` under `## Open questions`; a run where every finding is of this kind and it commits nothing uses the existing `non_actionable_feedback.yaml` fence instead.

### The declared-blocker question offers a third answer

A `[BLOCKING]` bullet under `## Open questions` (`alan/teams/_declared_blocker.py`) parks the workspace on a `declared_blocker_*` question with three options. `HAND_RESOLVE_OPTION` asserts the human cleared the blocker by hand and resolves to `implementation_fix`; `BLOCKER_UNFOUNDED_OPTION` asserts it never held and resolves to `verification`; `WORKER_STEP_OPTION` — "The declared step is the worker's to do: widen scope to the files it needs and do it." — resolves to `implementation_fix`. The recommendation stays `HAND_RESOLVE_OPTION`, and the two older options and their resolvers are unchanged.

The third option exists because `routes/answer.py` delivers the chosen option verbatim as the worker's binding instruction ("The human has already decided this — do not re-ask or re-litigate it"), so the text must be true when chosen. When the ruling is "this step is yours", neither older option is true, and a human picking one would hand the worker a false premise it is told not to question. The option text is true because a dispatch instruction outranks the file-scope restriction and `## Forbidden actions`, and never `## Absolute prohibitions`. It needs no `alan/unblock_recipes.py` edit: `_match_declared_blocker` keys on the question-id prefix and both recipe plans name their option by value.

The one narrow class where the third answer correctly produces a second park is a repair whose file is itself a tightening-only baseline: the absolute prohibitions close such files to every worker, so the worker declares the step again with `[BLOCKING]`. No continuation is promised in that class. Not covered here, tracked as a follow-up: the autonomous recovery recipe that answers the hand-resolve option never selects the third option, and an answer choosing it at the fix-cycle ceiling is refused exactly as the hand-resolve option is, since `_maybe_grant_fix_cycle_override` grants an override only to the ceiling question's own option.

### `## Fleet commit ledger`

`_fix_forward.render_fleet_commit_ledger(workspace)` renders, for every repository (like `_current_scenarios_block`, which is likewise unconditional — see [acceptance_gate.md](acceptance_gate.md)), one `### <team> (<invocation_id>)` heading per fleet run recorded in this workspace's own handover history, each followed by a `- <sha> <subject>` bullet per commit that run's *forward* handover recorded in `artifacts_produced`. It reads `alan.handover.list_handovers` but keeps only `handover_type == "forward"` records: `record_answer`/`record_pr_attachment` copy a prior handover's `artifacts_produced` verbatim into a new `revisit_amend` record, and including those would repeat the same commits once per human answer or PR attachment. An artifact only counts as a commit bullet when its `path` and `description` are mutually consistent with the commit-artifact contract (`description`'s leading token, read the same way as `path`, must equal `path`) — a coincidentally hex-shaped path on an unrelated artifact does not pass. It is appended to `implementation_fix`'s user text in `_mid_blocks` (`alan/teams/implementation_fix.py`) unconditionally — not gated to the default repository or filtered by a decomposed subtask's `task_id` — so a non-default-repository worker sees its own fleet commit history exactly like a default-repository one. The rendered bullet list is wrapped in `UNTRUSTED_CONTENT_NOTICE` plus a break-proof fence, since a commit subject is branch-controlled content (including human-authored commits) interpolated into an instruction-bearing prompt. Absence of a commit from the ledger means the fleet has no record of it, never that a human authored it: the slot pool's preserved-commits path can leave committed work on the branch when a run is interrupted before writing its handover. Attribution comes from this ledger, the branch prefix and the commit message, never from git author identity or `Co-Authored-By` trailers.

Revert authorization is keyed to SHA, not subject: `## Absolute prohibitions` tells the worker it may revert a commit only when its exact current SHA appears in the ledger. Each bullet's subject is shown alongside the SHA for legibility only — it never independently authorizes a revert, because a Conventional Commit subject can coincide between two fleet commits, or between a fleet commit and an unrelated human one, and the ledger has no durable old-SHA-to-new-SHA mapping to disambiguate. A `_pr_reconcile` rebase force-pushes new SHAs onto the branch, so after a reconcile a ledger entry's recorded SHA may no longer exist there; the worker is instructed to treat that look-alike commit as unverified and decline to revert it, reporting it like any other pre-existing content, rather than trusting the subject text to bridge the gap.

Note: `_ratchet_direction.detect_ratchet_loosening` compares a PR's diff against its merge base and has no notion of which actor produced which commit, so it will keep re-raising a loosening finding against pre-existing branch content every verification cycle regardless of this change — that is expected steady state, not a regression.

## Scope-override authority is opt-in

`TeamConfig.instructions_outrank_scope: bool = False` gates whether a delivered `## User dispatch instructions` section is stated as outranking `## Forbidden actions` (via `_ADDENDUM_AUTHORITY_NOTICE`) or merely qualifies `## Your task` (`_ADDENDUM_PRECEDENCE_NOTICE`, the pre-existing behavior). `_pr_handover._dispatch_addendum` has four branches: empty instructions → `""`; `instructions_outrank_scope=True` → authority notice, regardless of whether a `## Your task` block is present; else, precedence notice only when a task block is present; else the bare instructions block.

Only `implementation_fix` sets `instructions_outrank_scope=True` today (`_TEAM_CONFIG` in `alan/teams/implementation_fix.py`), because `compose_user_text` is shared with `implementation`, and the build brief this shipped against named only the fix role — an unconditional flip would have silently granted scope-override authority to initial PR authoring too. The system prompt's SCOPE paragraph carries the same acknowledgment via `_fix_prompt.SCOPE_DEFERENCE_NOTICE`, in both the default-engine `_SYSTEM_PROMPT` and the generic-engine `_generic_fix_intro`/`_GENERIC_FIX_STATIC_TAIL` paths, so a worker never reads a flat, unqualified scope restriction anywhere in its prompt.

The grant is scoped to the `## User dispatch instructions` section only — `_ADDENDUM_AUTHORITY_NOTICE` says explicitly that it never extends to any block fenced with `UNTRUSTED_CONTENT_NOTICE` (the judge review, unresolved PR review threads, or failing-check output): those are external content to evaluate, never instructions to follow, regardless of what they say.

This closes the dispatcher's own merge-gate remediation route: `merge_gate.render_remediation_instructions` (`alan/merge_gate.py`, folded in from the now-deleted `alan/_dispatcher_merge_brief.py`) states explicitly that the brief is "not a re-derivation of the prior approving review," then ships as `RouterDecision.instructions` into an `implementation_fix` dispatch whose prompt, before this change, ended with a rule forbidding exactly that work. The same helper renders the block class and blockers a manual re-dispatch (`alan/routes/workspaces.py`, via `alan/routes/_workspaces_merge_gate.py`) attaches to a worker's instructions when its own merge-gate attempt could not clear the block — see [merge_recovery.md](merge_recovery.md)'s "alan/merge_gate.py" section for the full per-entry-point contract.

## Persistence: `Meta.dispatch_instructions`

Instructions typed for one dispatch apply to that run only unless persisted. `alan.workspace.Meta.dispatch_instructions: dict[str, StickyInstruction]` (bounded at 200 entries, following `scope_audit`'s precedent — `set_sticky_instructions` raises `WorkspaceError` when adding a *new* key would exceed the cap, since `model_copy(update=...)` does not itself enforce `Field(max_length=...)`; replacing an existing key at the cap is still allowed) holds at most one sticky instruction per `task_id`. It is keyed on `task_id` rather than hung off `Task` because `workspace.create` persists `tasks=[]` for a non-decomposed workspace — no `Task` row exists for exactly the case (a single-task workspace) where instructions going missing after an auto-routed re-run was originally reported. `StickyInstruction.origin: Literal["dispatch", "generated"]` records how the entry was written: `"dispatch"` for every human-initiated dispatch path, `"generated"` for `auto_continue.maybe_auto_continue`'s system-templated instructions.

`workspace.set_sticky_instructions`/`clear_sticky_instructions` follow the existing `model_copy` + `_write_meta` + reconstruct pattern used throughout `workspace.py`. `set_sticky_instructions` is one of the fresh-apply writes enumerated in [dispatcher_concurrency.md](dispatcher_concurrency.md)'s "`meta.json` write semantics" section: it re-reads `Meta` fresh from disk (`_read_meta(ws.path)`) rather than merging into the caller's possibly-stale `ws.meta`. `dispatch_team_core` calls it right after `enqueue_workflow`, whose first call for a workspace with no `engine_snapshot` yet stamps and writes one via its own locally-rebound `workspace` variable that never propagates back to the caller's `ws` — merging into that stale `ws.meta` would silently overwrite the just-stamped snapshot back to `None`. Re-reading from disk picks up whatever the enqueue step just persisted, which is the same hazard any future meta-writing enqueue step would otherwise reintroduce. `clear_sticky_instructions` is idempotent — it returns the workspace unchanged when the key is already absent, which is what makes the UI's DELETE safe to call more than once. Because storage is keyed by task_id, injecting child subtasks under a decomposed parent never inherits the parent's sticky instruction — `inject_tasks` does not touch `dispatch_instructions` at all.

### Write choke point: `dispatch_team_core`

`alan.dispatch.dispatch_team_core` is the single function behind a human's manual dispatch (`routes.workspaces.dispatch_task_team`), a propose-mode approval, and `auto_continue`/`project_auto_continue`'s cross-workspace continuation — every caller already funnels through it, so no caller needed editing when `instructions_origin` was added. It also takes a required keyword-only `merge_gate: alan.merge_gate.MergeGateDecision` parameter — recorded on the returned `DispatchOutcome.merge_gate`, never executed — that every caller must supply declaring whether it attempted the shared pre-merge recovery (`MergeGateDecision.attempted(attempt)`, built only from a real `MergeGateAttempt`) or skipped it with a stated reason (`MergeGateDecision.skipped(reason)`); supply is enforced by the AST gate `tests/merge_gate_supply_gate.py`, since two call sites hand `dispatch_team_core` to `run_in_threadpool` as a bare reference. See [merge_recovery.md](merge_recovery.md)'s "alan/merge_gate.py" section for the full per-entry-point policy. It takes an `instructions_origin: Literal["dispatch", "generated"] = "dispatch"` parameter; every human-initiated caller relies on the default, and `auto_continue.maybe_auto_continue` — the one caller whose `instructions` text is a fixed system template, not something a human typed or approved — passes `instructions_origin="generated"` so the job and any persisted sticky entry are labeled accurately. After `enqueue_workflow` returns and before it returns `DispatchOutcome`, when `instructions` is non-blank and `sticky_instructions.should_persist(team.name)` is true, it calls `workspace_mod.set_sticky_instructions(ws, task_id, instructions, origin=instructions_origin)`. It also stamps the freshly-enqueued job's `instructions_origin` directly with the same value (not through `sticky_instructions.for_enqueue`, since this call is the origin of the instructions, not a re-read of a prior one). Blank/`None` instructions leave the store untouched — the UI's DELETE is the only path that clears an existing entry. It also takes `keep_sticky: bool = False`, which only `routes.answer._dispatch` sets: when it is true, the team is consuming and a sticky entry already exists for the task, the enqueued text is `sticky_instructions.for_enqueue(ws, task_id, team.name, instructions)` (the stored text first, the supplied text after it, origin `"inherited"`) and the store is **not** rewritten, so an answer-triggered dispatch carries a human's `PUT` ruling instead of replacing it with the decision text. With no existing entry, or for a non-consuming team, the default behaviour above applies unchanged — the decision text still becomes the sticky entry, and the manual-dispatch route still replaces the entry with what the human typed.

### Read choke point: `_advance_or_enqueue`

`Dispatcher._advance_or_enqueue` is where every automatically-routed continuation is enqueued, after the router (`select_next_team`, the pr-merge gate, the deploy gate) has picked a team and possibly generated its own `instructions` (most notably the merge-gate remediation brief). It calls `sticky_instructions.for_enqueue(ws, task_id, decision.team, decision.instructions)`, which returns the text to enqueue plus an `InstructionOrigin` (`"inherited"` when a sticky instruction was found for the task, `"generated"` when only a freshly-generated `decision.instructions` applies, or `None` when neither applies or the team is in `NON_CONSUMING_TEAMS`). Both values are threaded straight into `enqueue_with_pending_workflow`.

### The `NON_CONSUMING_TEAMS` guard, on both sides

`pr_merge`, `triage`, `dependency_sweep`, and `deploy_verify` carry `RouterDecision.instructions` that is a machine-readable `GateRecord` JSON payload, not prose meant for a worker's prompt — `deploy_gate_route` and `deploy_wait_gate` both emit it through the same `instructions` field a sticky instruction would otherwise compose into. `sticky_instructions.NON_CONSUMING_TEAMS` (relocated verbatim from the pre-existing `dispatch_instructions._NON_CONSUMING_TEAMS`) guards this on both the write side (`should_persist`, called from `dispatch_team_core` — a human dispatching one of these teams with instructions never pollutes the sticky store) and the read side (`for_enqueue`'s first branch returns `decision.instructions` unchanged, origin `None`, without ever calling `resolve`). A sticky instruction set on a task is therefore never silently dropped into a `GateRecord` payload, and a `GateRecord` payload is never silently composed with human prose.

### Composition order and truncation

`sticky_instructions.compose(sticky, generated)` joins the persisted sticky text and a freshly-generated per-run brief with a blank line, **sticky first**. When the join exceeds `MAX_COMPOSED_CHARS` (40000), the **sticky half is truncated**, not the generated half: the generated remediation brief is the only copy of content a route like the merge-gate DoD requires the worker to act on, while the sticky text stays fully readable in the workspace UI regardless of truncation in any one prompt. A truncation event is logged via `_pr_audit_log.append_audit`. The hard cap holds even at the boundary where truncating the sticky half still can't make room: if `generated` alone (plus the separator and truncation marker) already meets or exceeds `MAX_COMPOSED_CHARS`, the sticky text is dropped entirely (a `sticky_instructions_dropped` audit row, not a truncation one) rather than emitting a result that overshoots the cap — generated content only gets truncated in the more extreme case where it alone already exceeds `MAX_COMPOSED_CHARS`.

## Origin, end to end

`Job.instructions_origin: str | None` (migrated column, nulled by `_ADVANCE_ELIGIBLE_AT_SQL` whenever it rewrites `instructions` so a re-parked deploy-gate job never renders a stale origin) flows into `DispatchInstructionsReadback.origin: InstructionOrigin | None` (`alan.dispatch_instructions`), returned by `GET /api/workspaces/{task_id}/dispatch-instructions` and rendered as a suffix on `InstructionBadge` — `"(typed for this run)"` / `"(persisted from a prior dispatch)"` / `"(generated by the system)"` — only when `status === "attached"`.

## API and UI: `GET`/`PUT`/`DELETE /api/workspaces/{task_id}/sticky-instructions`

`routes.dispatch_instructions` adds `StickyInstructionOut` (`text`, `origin`) alongside the existing per-invocation readback endpoint. The `{task_id}` path segment is always the workspace id. All three verbs resolve the key they act on through `alan.dispatch.owning_task_id` — the same resolver the manual dispatch route calls — so on a decomposed workspace the instruction lands on, is read from, and is cleared from the subtask that actually runs. `GET` and `DELETE` share one helper that falls back to the raw workspace id when resolution raises `AppError` (a decomposed workspace with no single owning subtask), so neither regresses to a 404 there; `PUT` does not fall back, because writing under a key no dispatch will ever read would be a silent no-op.

`PUT` takes `{"text": ...}` and returns `{"task_id", "text", "origin", "notice"}` with the **resolved** `task_id`; `notice` is `IN_FLIGHT_NOTICE`, carried in the response body so a caller who never opens the endpoint description still sees that a pass already running keeps the instructions it was enqueued with and under which conditions the text reaches a later dispatch (enqueued from a workspace read that follows the write; routed by the dispatcher or triggered by an answer; a team outside `NON_CONSUMING_TEAMS`; generated text that leaves room under `MAX_COMPOSED_CHARS`; a manual dispatch carries only what was supplied for it). It is the only one of the three verbs guarded by `require_control_token`: it injects binding instructions into code-writing agents inside a section documented as able to widen file scope, the highest-value injection surface among the routes that change what the fleet does. `DELETE`'s unguarded status is unchanged and is tracked with the UI issue, not here. The error map: 401/403/500 from the guard; 404 for an unknown workspace or a decomposed workspace with no single owner; 409 when adding a new key would exceed the 200-entry limit (`WorkspaceError` from `set_sticky_instructions`, caught wholesale); 422 for empty text, text that is empty after `normalize_instructions` (shared with dispatch-typed text via `alan.app.workspace_creation`, not imported from a sibling route), or text longer than `MAX_COMPOSED_CHARS` once normalized. The ceiling is checked in `_validated_text` after `normalize_instructions`, not as a field constraint on the raw body, so padded input whose trimmed form fits is accepted. It is enforced at the boundary because `compose` cannot keep text above it; text at or under it can still be discarded later when the generated half alone reaches the ceiling.

The write stores `origin="dispatch"` and adds no third origin literal, so `for_enqueue` stamps `"inherited"` for it exactly as for text typed at dispatch time — same section, same authority, same persistence across re-dispatch. When the stored `StickyInstruction` already equals `(text, "dispatch")` the store is skipped and `meta.updated_at` is deliberately not bumped: `StickyInstructionCard`'s `key={ws.updated_at}` remount and the workspace index ordering both depend on it, so a repeated write leaves the workspace unchanged. Every accepted write, including that idempotent repeat, is appended to `~/.alan/logs/sticky_instruction_write_audit.jsonl` (`workspace_id`, resolved `task_id`, `origin`, full `text`, `length`, `timestamp_utc`); requests refused with 401/403/404/409/422 are not recorded. The audit is best-effort (`append_jsonl_audit` logs and swallows write failures) and has no retention-registry entry, following `pr_attach_audit.jsonl`.

Delivery boundary: a write never alters or cancels a dispatch already running — a job snapshots its instructions at enqueue — and a dispatch enqueued from a workspace read that follows an accepted write carries the text when it is routed by the dispatcher (`for_enqueue`) or triggered by answering a question (`keep_sticky`), goes to a team outside `NON_CONSUMING_TEAMS`, and is composed with generated text that leaves room under `MAX_COMPOSED_CHARS` (`compose` drops the stored half when the generated half alone reaches it). A manual dispatch carries only the instructions supplied for it. The write is a read-modify-write on workspace metadata that is **not atomic**, and the dispatcher composes from an in-memory workspace stamped earlier in its cycle, so a write racing an in-flight cycle is on disk but invisible to that composition and can be **erased** by `workspace_mod.transition`'s stale-merge write from `stamp_for_advance`. That window is the pre-existing unlocked read-modify-write on `meta.json`; this route does not close it and claims no atomicity. `Meta.note` (the personal memo) reaches no worker prompt and is deliberately not routed into this section: memo text is often prohibition-shaped, and delivering it into a section that can widen scope past `## Forbidden actions` would present a refusal as permission.

`DELETE` is idempotent (204 whether or not an entry existed) and is the **only** way to clear a persisted instruction — there is no auto-expiry. `useStickyInstruction` (frontend) surfaces a fetch failure as an `error` state rather than silently rendering empty, since hiding a real persisted instruction is exactly the failure this feature exists to prevent; it resets `text`/`origin`/`error` at the start of every fetch (including the undefined-`taskId` branch) so a prior task's instruction can never survive on screen across a `taskId` change, either masking a fresh error or showing stale content. `StickyInstructionCard` renders nothing only when there is genuinely no persisted instruction and no error. Its parent, `WorkspaceBody` (`features/workspace/pages/Workspace.tsx`), keys the card on `ws.updated_at` rather than `taskId` alone: `taskId` never changes across a dispatch or re-dispatch of the same task, so a `taskId`-only effect dependency would never refetch after one — `updated_at` changes on every workspace meta write, including the `set_sticky_instructions` call a dispatch with instructions makes, and remounting the card via `key` forces a fresh fetch without any new callback/prop threading. Clearing unmounts the card's own Clear button, so `WorkspaceBody` hosts a sibling `<output ref tabIndex={-1}>` announcement that receives focus on the transition, following `RepoActionRow.tsx`'s `MaintenanceNotice` precedent.
