# Run summary (persisted, conversation-level)

**Source:** `alan/run_summary.py` (`RunSummary`, `ToolUseCount`, `derive_run_summary`), `alan/routes/_chat_router.py` (`compute_run_summary`, wired into `ChatSessionResponse` for build-chat), `alan/routes/explore_chat.py`.

Every chat family (build, explore) treats its whole conversation as one interactive LLM run. `derive_run_summary` parses the session's already-persisted `stream.jsonl` (see `docs/architecture/claude_cli_streaming.md` for how each turn tees its raw CLI events into that file) on every `GET /sessions/{id}` and folds every turn — including behind-the-scenes summarize/extract utility turns, since they run through the same `do_turn` / `stream_path` plumbing as ordinary messages — into a single `RunSummary`:

- `total_cost_usd` — sum of `total_cost_usd` across every `type == "result"` event in the file
- `total_output_tokens` / `total_input_tokens` — sum of `usage.output_tokens` / `usage.input_tokens` across the same events (input is the *billed* per-turn figure the CLI actually charged for, not a dedupe of conversation size — each turn re-sends the growing context)
- `tool_counts` — a single consolidated `[{name, count}]` list (sorted by count desc, then name asc for determinism) built by scanning every `type == "assistant"` event's `message.content` for `tool_use` blocks, mirroring `aggregateToolCounts` in `alan/web/src/components/streamSummary.ts` (see "Python↔TS drift guard" below)
- `model` / `effort` / `system_prompt` — the session's fixed setup. `model` defaults to `DEFAULT_CHAT_MODEL` ("opus", the constant every chat route already runs with — see `run_chat_turn` in `alan/claude_cli.py`); `effort` is derived from it via the imported `alan.claude_cli._effort_for_model`; `system_prompt` is supplied by the caller (see below), not parsed from the stream

`derive_run_summary` never raises: a missing file, an empty file, or a file with zero parseable JSON-object lines all degrade to `None` (legacy sessions predating this feature, or a session that never ran a turn). It is a pure read — no new persisted rollup, no message-storage change, no migration; the only state it reads is the `stream.jsonl` that already exists per session, so repeated calls on the same file are deterministic.

The Haiku collision-check spend (`alan/collision.py`) is a separate subprocess call that never writes to a chat session's `stream.jsonl`, so it is always structurally excluded from `run_summary`. When the collision check is session-scoped (see "Collision spend per chat session" below) its usage lands in a sibling `collision_stream.jsonl` and is surfaced as its own `collision_run_summary` field — a distinct run, never merged into `run_summary`'s totals.

## Non-chat consumer: manager-summary

`alan/manager_summary.py::read_manager_summary_usage(ws_path)` is a second, independent caller of `derive_run_summary` — not a chat session. It reads `ws_path / "manager_summary_stream.jsonl"` (a per-workspace file, not a per-session one) with a fixed `model="haiku"` and the manager-summary system prompt, returning the same `RunSummary` shape. Unlike the chat routes, this stream is reset (`unlink(missing_ok=True)`) immediately before every generation attempt (see `docs/architecture/manager_summary.md`'s idempotency section), so it is last-write-wins per stop rather than an ever-growing accumulation — `derive_run_summary` itself is unchanged (frozen) and has no opinion on that; the reset happens entirely on the write side. `alan/routes/workspaces.py` surfaces the result two ways: as `ManagerSummary.run_summary` on the workspace detail response (`GET /api/workspaces/{task_id}`), and folded into `WorkspaceSummary.total_cost_usd` on the list response (`GET /api/workspaces`) via `_fold_manager_cost` — see `docs/architecture/manager_summary.md` for both.

## Route wiring

`system_prompt` is not reconstructed from the stream — each caller supplies the value it already has:

- **build-chat / explore-chat** (`alan/routes/_chat_router.py::compute_run_summary`) — calls the route's existing `ChatRouterCtx.system_prompt(session)` callable (`format_build_system_prompt()` / `format_explore_system_prompt(session.consultant_key)`), the same closure `do_turn` uses to run the actual turn. `get_session_response` (consumed by `alan/routes/build_chat.py`'s `GET /sessions/{id}`) and `alan/routes/explore_chat.py`'s `get_explore_chat_session` both call it and attach the result to their response's `run_summary` field.

Both routes pass `run_summary` through as one optional field on their `GET /sessions/{id}` response model (`ChatSessionResponse`, `ExploreChatSessionResponse`); build-chat and explore-chat's `/extract` and `/summarize` utility turns already flow through the shared `do_turn`, which always tees to the same per-session `stream_path`, so they count toward the same total as ordinary messages without any special-casing.

## Collision spend per chat session

`POST /api/collision-check` (in `alan/server.py`) optionally carries `chat_family: "build" | "explore"` and `session_id` alongside `brief`. When both are present, `_resolve_collision_stream_path` looks up the matching `ChatCoreConfig` (`build_chat_mod.CONFIG` / `explore_chat_mod.CONFIG`) and the family's session-root dependency (`BuildChatSessionsRootDep` / `ExploreChatSessionsRootDep`), then resolves `_chat_core.collision_stream_path(cfg, session_id, root=root)` — a sibling of `stream_path()` that returns `<session_dir>/collision_stream.jsonl` instead of `stream.jsonl`, so it resolves through the same `ALAN_BUILD_CHAT_SESSIONS_ROOT` / `ALAN_EXPLORE_CHAT_SESSIONS_ROOT` overrides as the rest of the session. That resolved `Path | None` is threaded into `collision_mod.check_collision(..., stream_path=...)`. `None` (no family/session_id, or an invalid session_id) preserves today's global, uncounted, shared `collision/stream.jsonl` file used by the dispatch modal and workspace creation — those callers are unchanged.

Inside `check_collision`, a non-`None` `stream_path` is `unlink(missing_ok=True)`'d **before** the candidate pre-filter's early return, so a rerun with no candidates can never report a stale prior run's cost — the file only ever holds the most recent session-scoped run. `_chat_router.py::compute_collision_run_summary` reads it back per session via the same `_chat_core.collision_stream_path` + the frozen `collision_mod.read_collision_usage(stream_path=...)`, and attaches the result as `ChatSessionResponse.collision_run_summary` (`RunSummary | None`, `None` when no session-scoped collision check has run yet, or on any read failure — best-effort, never raises, never blocks the response).

## Python↔TS drift guard

`tests/fixtures/run_summary_stream.jsonl` is a canonical two-turn `stream.jsonl` (system init, `tool_use` blocks across `Read`/`Grep`/`Bash`, `tool_result` blocks, and a `result` event per turn with `usage`/`total_cost_usd`) used by `tests/test_run_summary.py` to pin `derive_run_summary`'s exact aggregation. It intentionally contains no malformed lines, so it can be consumed as-is by `alan/web/src/components/RunPricing.fixture.test.tsx`, which independently re-derives the same tool-count/cost/token totals from the raw fixture and asserts they match the numbers pinned in `tests/test_run_summary.py` — the two implementations must agree on tool counts and usage totals for this fixture. Python-only edge cases (missing file, empty file, malformed lines, non-dict blocks) are covered separately with inline fixtures in `tests/test_run_summary.py`.

## Frontend: `RunPricing`

`alan/web/src/components/RunPricing.tsx` renders one or more persisted `run_summary`-shaped rows above the tab strip for both chat surfaces: `ChatScaffold.tsx` (shared by build-chat and explore-chat) renders a two-row `RunPricing` ("Conversation" + "Collision check", the latter fed by `collisionRunSummary`) once, between the page heading and the tab row, so it stays visible on every tab instead of only the Chat tab. A row with a `null`/`undefined` `runSummary` is dropped, so a session with no collision run yet only renders the "Conversation" row. Every row survives reopen and server restart exactly like the rest of a chat session — it is derived from the same `GET /sessions/{id}` response the transcript itself loads from, no separate fetch. Each row shows the model/effort setup with a toggle between a distilled one-line system-prompt summary (default) and the full prompt, a cost headline with output/billed-input token totals, and a consolidated tool-count chip list; it never breaks totals out per message or replays the raw event stream, matching the feature's hard boundaries.

`useChatSessionGeneric` (build/explore) exposes `runSummary` (read from the `["chat-session", family, sessionId]` query cache — see `docs/architecture/frontend.md`'s "Chat-session family" section) and `refreshRunSummary()`, which is `useInvalidateChatSession(family, sessionId)`: an exact, non-cancelling `invalidateQueries` against that same key rather than a hand-rolled re-`GET`. A failed invalidation-triggered refetch leaves the query's `isError` set but its cached `data` untouched, so the rendered summary is always the last successful read and a flaky refresh never clobbers it — the same guarantee the old hand-rolled version's swallowed-catch gave, now structural rather than a `try`/`catch` around a single call site. Seven production call sites invalidate it: `applyEvent` inside `useChatSessionGeneric` (once each for `assistant_done`, `error` and `turn_stopped`, since all three end a turn that may have mutated the persisted stream), `useChatSessionGeneric.summarize()` (since `/summarize` runs a utility turn through the same `do_turn` plumbing as an ordinary message), `useProposePrefetch` (once its tracked prefetch entry settles, success or error), `useProposeTrigger` (after a triggered propose settles with `refreshOnSettle`), `useDispatchProposalFlow` (after a successful dispatch), and each chat page's `useCollisionCheck` `onSettled` callback (`BuildChat.tsx` and `ExploreChat.tsx`, once a collision check completes).
