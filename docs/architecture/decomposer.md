# Decomposer team

The `decomposer` is an internal team that runs **after `implementation_plan`** and decides split-vs-keep. It is the first real consumer of the Phase-0 injection primitive (`docs/architecture/task_injection.md`).

## Routing

`TEAM_TRANSITION_POLICY` (`alan/router.py`): `implementation_plan → decomposer`, and `decomposer → {implementation, architecture, research}`. `implementation_plan` no longer forwards straight to `implementation`; its handover now suggests `decomposer`. The decomposer is in `INTERNAL_ONLY_TEAMS` (so it is excluded from `MANUALLY_DISPATCHABLE_TEAMS` and `INITIAL_DISPATCHABLE_TEAMS`) — it needs a prior `implementation_plan` handover and is never user-dispatchable.

## The decision (`alan/teams/decomposer.py`)

`DecomposerTeam` (a `StaticPipelineTeam` with a single opus `decomposer` role) reads the prior plan handover (synthesis, `decisions`, `files_to_edit`) plus the workspace's acceptance clauses (`meta.requirements`, injected into the user prompt by id), then emits one fenced ```` ```yaml decomposition.yaml ```` block parsed by `parse_decomposition`:

- **Keep** (`split_count: 1`): `run()` builds a **forward** handover to `implementation` carrying the prior team's `decisions` (satisfying the Layer-3 producer rule) and `files_to_edit`, with `next_hop="implementation"` and `split_rationale` recorded on the handover.
- **Split** (`split_count: N>=2`): `run()` builds a **terminal** handover carrying `injected_tasks`. The router returns `done`, so `dispatcher._advance_workspace_dag` applies the injection (Phase-0 primitive) and enqueues the ready sub-DAG immediately — there is **no human-approval pause** in this phase (auto-execute; the split + lineage are surfaced read-only). `split_rationale` is recorded on the handover.

Each split subtask declares the `files` it edits and an optional `depends_on` (ids of earlier subtasks). **Dependency edges are the union of LLM-declared edges and edges derived deterministically from file overlap** (`_union_deps` over `_derive_dependencies`): a subtask is ordered after any earlier subtask it shares a file with OR declares a dependency on. Subtasks are listed in execution order (producers before consumers); a declared edge to self, to a later subtask, or to an unknown id is dropped, so edges stay strictly backward and the result remains a DAG by construction (no cycles — `injection.plan_injection`'s topo-sort never overflows on decomposer output). Declared edges let the decomposer capture producer→consumer contract/data dependencies (API field, SSE event, schema, data row, config key) that file overlap alone misses when subtasks edit disjoint files. Each subtask also declares a definition-of-done (`dod`): clauses with `covers` back-references to acceptance-clause ids. These flow onto the injected `Task`s via `injection.plan_injection` (which sets `dod_clauses` + `parent_task_id`, leaving `_content_hash` unchanged so replay stays idempotent), and `workspace.inject_tasks` back-links each parent's `child_task_ids`.

**A requirement has exactly one owning subtask, enforced at parse time.** A `covers` id absent from `meta.requirements` is rejected outright (`DecomposerParseError`, failing the node) — including when the workspace carries no requirements at all — mirroring `_validate_scenario_assignment`'s unknown-scenario-id rejection above. A requirement claimed by more than one subtask's `dod.covers` is repaired deterministically to the last claimant by position among the emitted `subtasks` list (`alan.acceptance.resolve_owners`, the same resolver the read side uses), and every dropped claim is recorded as a `ClauseOwnerRepair` — one `clause_owner_repaired` row per drop, appended to `clause_owner_audit.jsonl` (`alan/teams/decomposer.py::_write_clause_repairs`) — rather than failing the node: a double-claim is a judgement slip the host can repair deterministically, not a broken split worth a full re-run. This is host-side, structural enforcement, distinct from the prompt-level placement rule below (`_DECOMPOSER_PROMPT` additionally states that a requirement id must appear in exactly one subtask's `dod.covers`, the cheap half that makes a repair rare rather than routine) — and, like the scenario placement rule, it is deliberately **not** extended to test scenarios: the rule is stated for them in the prompt too, but nothing enforces or repairs it.

## Manifest threading (split path)

The declared `files` manifest survives from the decomposer's YAML all the way to the worker that implements the subtask, so it can later be enforced (`alan/overlap.py`) instead of being thrown away once it has served to order the subtasks. `_to_injected` (`alan/teams/decomposer.py`) also sets `InjectedTask.files=spec.files`; `injection.plan_injection` copies that onto the created `Task.files` (excluded from `_content_hash`, the same treatment as `dod_clauses`/`title`/`scenarios`, so replay stays idempotent). `_pr_handover.your_task_block` renders a `### Your files` section from `Task.files` inside the subtask's own `## Your task` prompt block — omitted when `Task.files` is empty or the task is `None` — so the implementer sees, in its own instructions, exactly which files it is expected to touch.

## KEEP bias

The decomposer prompt is additively hardened to bias toward keeping a task whole: split is chosen only when the subtasks are cleanly file-disjoint (share no files with each other) AND splitting has an explicit benefit (independently reviewable PRs, parallelizable work, or a plan too large to review as one PR). When subtasks would still need to touch overlapping files, or the benefit of splitting is unclear, the decomposer keeps the task whole instead. The existing keep/split criteria above are unchanged; this text is meant to lower the measured split rate.

## Schema

`Handover` schema bumped to **1.9**: `InjectedTask` gains `dod_clauses: list[TaskDoDClause]` and `Handover` gains `split_rationale: str | None`. Older payloads load unchanged (both default empty/None). `InjectedTask.depends_on` already existed in 1.9 — populating it from LLM-declared edges needs **no version bump**.

## Verification honors the split scope (in-scope critical count)

A split subtask's PR is reviewed against the `## IN-SCOPE ACCEPTANCE OUTCOMES` partition that `verification._build_base_user_text` composes from `acceptance.scoped_dod(meta, task_id)` (owned clause texts in-scope, sibling-owned out-of-scope). The `diff_reviewer` is **not** scope-aware — it reviews against the full plan/DoD and emits the raw `DIFF_FINDINGS_CRITICAL: <n>` — so a subtask that legitimately defers work to a sibling can accrue CRITICALs that belong to that sibling.

The judge reconciles this: when a scope block is present it also emits `DIFF_FINDINGS_CRITICAL_IN_SCOPE: <m>` (the raw CRITICALs that survive after excluding out-of-scope items, `<m> <= <n>`, sibling ownership named in `## Rationale`). `verification.effective_verdict` (via `effective_critical_count`) gates on `<m>` when that line is present and on `<n>` otherwise — so `APPROVE` with `<m> = 0` survives instead of being force-flipped to `REQUEST_CHANGES` by the raw count. **Anti-cheat host gate:** `_collect_outputs` strips the in-scope line (`_strip_in_scope_critical_line`) unless the prompt actually carried the scope block (`_scope_block_present`), so a non-split full-feature task can never fabricate the escape — the raw count still governs. `loop_guard` reads the same `effective_critical_count` for its spiral classification, and `_build_verdict_handover` audits `{critical_raw, critical_in_scope, effective_verdict}` to `verification_audit.jsonl`.

Without this, a green, correct split subtask (e.g. PR #505: the mobile-audit gate mechanism whose CI wiring is a `pending` sibling) self-inflicts a `CHANGES_REQUESTED` review, `implementation_fix` finds nothing to fix, and the workspace escalates to `await_human` with the dependent sibling deadlocked behind it.

Scope also depends on which `Task` in `meta.tasks` verification treats as "current": the dispatcher runs a split subtask's PR through `team.run(..., task_id=job.task_id)` where `job.task_id` is the subtask's own id, distinct from `workspace.task_id` (the root). `_find_current_task` resolves against `_effective_task_id(workspace)` (`_verification_task_id_var.get()` when set — an `is not None` check, so an explicit empty string is honored rather than being coerced to the root id by truthiness — else `workspace.task_id`) rather than `workspace.task_id` directly, so `_scenario_mode`, `_effective_scenarios`, and `_current_task_manifest` (hence `_out_of_manifest_files`) all key off the subtask actually being verified. This is fail-closed: an effective task id absent from `meta.tasks` yields `_find_current_task` → `None` → `_scenario_mode` → `MISSING`, never a silent fallback to the root task's scenarios or manifest. `_scoped_dod_for_current` already read `_verification_task_id_var` directly and is unchanged — it stays a separate, `None`-returning helper rather than being unified with `_effective_task_id`'s string-fallback contract.

## Scenario placement must respect the file fence (2026-08-20)

The prompt's scenario-assignment rule used to say only that every parent scenario id lands on exactly one subtask. PR #1159 showed the missing half: the decomposer put the end-to-end "no layout jump across the above-list region" assertion (and the e2e spec that carried it) on subtask A, whose instructions simultaneously forbade touching `Home.tsx` — the file whose async mounts were the remaining shift source and which subtask B owned. The assertion could only flake from inside A's fence: CI's flake ratchet reddened A's PR twice, the fix worker (correctly scope-locked) could not reach the cause, and the workspace escalated. `_DECOMPOSER_PROMPT` now states the placement rule explicitly — a scenario or DoD clause is assigned to a subtask only if it can be made to pass by editing that subtask's own `files`; a cross-subtask end-to-end assertion belongs to the **last** subtask in the dependency chain, and earlier subtasks assert only what their own files control. This is a prompt-level rule (pinned by `tests/test_teams_decomposer.py`), not a validator: the files a scenario *depends on* are not machine-derivable from its `when:` command, so the decision stays with the model that already holds the plan's file manifest. The host-side counterpart — the judge's scope fence falling back to the subtask's own DoD clauses when no `covers` resolve — lives in `acceptance_gate.md`.
