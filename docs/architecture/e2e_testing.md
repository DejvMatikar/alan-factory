# E2E testing

**Source:** `alan/web/e2e/`, `alan/web/playwright.config.ts`, stub at `alan/web/e2e/fixtures/claude`.

Playwright drives the full stack: real FastAPI + real frontend bundle + a stub `claude` binary on PATH.

## Stub `claude` binary

`alan/web/e2e/fixtures/claude` is prepended to PATH so we exercise the real subprocess path without burning Claude credits. The stub supports both output formats Alan uses:

- `--output-format json` — single envelope.
- `--output-format stream-json` — newline-delimited `system` / `assistant` / `result` events.

Routes by **system-prompt substring**. Notable cases:

- Research orchestrator → returns a scripted `{"agents":[…]}` payload so `ResearchTeam` fans out into two workers + a synthesizer (`workflow-flow.spec.ts` drives the whole pipeline and asserts the React Flow DAG renders).
- Implementation team → writes a marker file + commits inside `$PWD` (= worktree path) so `implementation-flow.spec.ts` can exercise the worktree flow end-to-end. Playwright forces `ALAN_IMPL_DRY_RUN=1` + `ALAN_VERIFICATION_DRY_RUN=1` so no real GitHub mutation happens.

## Per-worker servers + state isolation under `~/.alan-playwright/w<i>/`

The main suite runs `workers: E2E_WORKERS` (default 4, env-overridable; `fullyParallel: false` so spec files fan out across workers while tests within a file stay serial). **Each worker boots its own fully-isolated backend** via the worker-scoped `e2eServer` fixture in `e2e/fixtures/test-base.ts` (there is no config-level `webServer` and no config-level `baseURL` for the main suite):

- Worker `i` (Playwright `parallelIndex`) gets port `E2E_PORT + i` (local base 4300, range 4300-4303 for the default 4 workers — disjoint by construction from the other pid-derived ranges this repo uses, see `src/lib/derived-run-config.test.ts`'s disjoint-range assertion; CI derives a per-run base with stride 8, `tests.yml`) and state root `${ALAN_E2E_ROOT}/w<i>` (local base `~/.alan-playwright`).
- `e2e/fixtures/server-env.ts` owns the derivations plus `serverEnv(root, ghBranch)` — the full env block, everything root-derived so per-worker roots isolate the queue DB, workspaces, logs, stub marker and every trigger file. The one extra per-worker knob is `ALAN_E2E_GH_BRANCH=e2e-stub-pr-branch-w<i>`: verification/implementation_fix run `git worktree add -B <branch>` inside the worker's own **synthetic per-worker repo** (see below), so distinct per-worker branch names still avoid same-repo collisions even though each worker now has its own repo and no shared-checkout collision is possible in the first place.
- `serverEnv()` also points `ALAN_WORKTREE_REPO_ROOT` at a fresh synthetic repo created per worker at `<workerRoot>/worktree-repo` (`ensureWorktreeRepo`, `server-env.ts`) — `git init -b main` plus one empty commit, no `origin` remote, no `pyproject.toml`. This is what `alan/worktree.py::implementation_worktree`'s bare (non-pooled) path resolves to instead of the ambient process cwd — see `docs/architecture/ci_isolation.md`'s `ALAN_WORKTREE_REPO_ROOT` section for the full isolation contract and the gate that proves it. Per-worker (rather than one repo shared across workers) removes the concurrent prune-versus-add exposure a shared checkout would still carry, and the missing `pyproject.toml` short-circuits `_bootstrap_python_deps` — every `git worktree add` this suite triggers is now a plain directory copy with no `uv sync` behind it, so the suite no longer pays a dependency sync per created worktree. With no shared checkout for concurrent workers to collide branches in, the compensating `scripts/clean-e2e-branches.mjs` cleanup this suite used to run before/after every `e2e`/`e2e:reversed`/`audit:mobile`/`audit:desktop` invocation is deleted outright, together with its two `.github/workflows/tests.yml` and two `.github/workflows/e2e-stress.yml` steps — it force-deleted any local branch matching its patterns, which was itself a hazard once a real local branch could collide with one of those patterns.
- `startServer` (`e2e/fixtures/e2e-server.ts`) installs the default-engine profile before it spawns: `installTestDefaultProfile(root)` in `e2e/fixtures/default-profile.ts` copies `tests/fixtures/default_profile_test.yaml` byte for byte to `<workerRoot>/engines/default_profile.yaml`, after the root wipe and the `workspaces/` mkdir. That is the same file `tests/conftest.py` installs for the backend suite, so there is no second copy of profile values that could drift. The path is derived from `enginesRoot(root)` (`server-env.ts`), the same function that builds the server's `ALAN_ENGINES_ROOT`, so the install and the server cannot disagree about where the file lives.
- `e2e/fixtures/e2e-server.ts` spawns `uv run python -m alan` directly (no `bash -lc`; the root wipe happens in Node **before** the spawn, so SQLite never holds a deleted-inode journal), health-waits on `/api/health` (60s, exit-detected), and kills the detached process group on teardown. Stale `python -m alan` listeners on the worker's port are killed at boot (`freePortOrThrow`); foreign processes fail loudly. `e2e/global-teardown.ts` sweeps the whole port range as a backstop for hard-killed workers.
- Because Playwright **replaces a worker after any test failure**, a retried test automatically lands on a fresh server + wiped root — retry pollution is structurally impossible.
- Auto-fixtures: `triggerHygiene` clears one-shot trigger files at test *setup* (heals crash residue; `gh-delivery.json` excluded — delivery-summary seeds it in beforeAll); `stubGuard` asserts the worker's own `stub-marker.log` grew (skip via `@no-claude` tag); `serverLogOnFailure` attaches the failing test's byte-range of the worker's `server.log` to the report.
- Specs never import port/root constants: `e2eRoot` (worker-scoped fixture) is the state root, and `baseURL` is provided per worker so `page.goto("/…")` and the `request` fixture hit the right server.

## Flake visibility (advisory summary + PR-only ratchet)

In CI the config adds a `json` reporter (`playwright-results.json`, gitignored) and the workflow appends `scripts/report-flaky.mjs` output to the GitHub step summary on every run (`if: always()`): each FLAKY (passed-on-retry) and FAILED test is listed — otherwise `retries: 1` silently absorbs flakes inside green runs. The summary is advisory only, never blocking. A second, PR-only step (`report-flaky.mjs --ratchet`, gated on `github.event_name == 'pull_request' && success()` so it never stacks onto a real failure) compares the run's flaky spec files against the checked-in allowlist `e2e/flaky-baseline.json` (zero tolerance by default; a file only enters it as an explicit, reviewed last resort — currently empty — and shrinking it back is manual) and fails the job when a file outside it flakes — a new flake class fails in the PR that introduces it instead of degrading main for weeks. Push-to-main never runs the ratchet, so a residual flake cannot freeze deploys. The CI job invokes `npx playwright test` directly (not `npm run e2e`) so the `pree2e` hook doesn't rebuild the frontend a second time after the explicit build step; both this step and the earlier "Stress changed specs" step wrap their `npx playwright test` invocation in `uv run python ../../scripts/git_state_gate.py --` (see `docs/architecture/ci_isolation.md`'s `ALAN_WORKTREE_REPO_ROOT` section), which fails the step if the run mutated the checkout's branch refs or `.worktrees/` registry as a side effect, on top of the exit code the underlying Playwright run already produces. **The advisory and ratchet modes deliberately disagree on how to handle a missing or unparseable `playwright-results.json`.** Default (advisory, no `--ratchet`) mode exits 0 either way — it only ever annotates a step summary, so there is nothing for it to block. `--ratchet` mode fails closed: a missing or unparseable report exits 1, matching the existing fail-closed behaviour for a missing `e2e/flaky-baseline.json`, because `Frontend E2E (Playwright, blocking)` is a required status check and passing it having checked nothing is exactly the silent-degradation shape this ratchet exists to prevent. This failure is deterministic, not a flake — it means the Playwright json reporter didn't write the file the ratchet needs even though the suite reported success (e.g. a reporter config regression), and re-running will not clear it. **A ratchet failure is also machine-attributable (2026-08-20, #1162):** for every fresh flaky file the script emits a `::error file=<repo-relative e2e/<spec>>,title=Flake ratchet: new flaky spec file::…` workflow command on **stderr** (stdout is redirected into `$GITHUB_STEP_SUMMARY`; the runner scans both streams for commands), so the verdict lands on the check run as a file-anchored annotation alongside Playwright's own attempt-1 failure annotation. The fleet's external-gate classifier reads those annotations (`_pr_branch.fetch_failing_e2e_tests`, see `merge_recovery.md`) and joins the spec path against the PR's diff — a new spec that flakes in CI is the PR's own defect and is routed to `implementation_fix` as `GATE_ACTIONABLE: yes`, never parked as a "known-flaky" check. The path is resolved relative to `GITHUB_WORKSPACE` when set (`alan/web/e2e/<spec>` in CI, matching the Playwright reporter's vocabulary) and falls back to `e2e/<spec>` locally.

The mobile-audit and screen-capture derived-port lanes (`src/mobile-audit-config.ts`, `src/capture-config.ts`) now skip Chromium/WHATWG restricted ports (`src/lib/restricted-ports.ts`) when deriving a pid-based port. The skip lives solely inside `src/port-avoidance.ts`'s `candidatePorts`, the single seam both the walking picker (`firstFreePort`) and the single-shot picker (`resolveCachedPort`, which takes `candidatePorts(...)[0]`) draw their candidates from — so the two pickers can never disagree about which port is eligible. `e2e/mobile-audit/global-teardown.ts` depends on that agreement: it re-resolves the same port the config-load resolver already cached to decide which listener is safe to SIGKILL, and a second, independent skip check anywhere else would risk that equality drifting apart.

`playwright-results.json` is gitignored in the working tree but no longer implicitly transient in CI: `e2e-frontend`'s last step uploads it as the `playwright-results-json` artifact (`retention-days: 30`), gated on `always() && steps.e2e.outcome == 'success'` — the `steps.e2e` id belongs to the `Run Playwright E2E` step specifically, not the job's overall result, because a red `Flake ratchet` step (PR-only, runs after) would otherwise suppress the upload of an otherwise-healthy report. The gate exists to keep the retained series clean: `Stress changed specs` runs before the main suite and writes its own `playwright-results.json` (5x repeats of the PR's changed specs) to the same path, so if that step fails and skips the main suite (`Run Playwright E2E` carries no `if:`, so it defaults to `if: success()`), the file left on disk is the stress run's, not the full suite's — checking the main suite's own outcome, not the job's, is what stops that report from being archived under a name a future performance-drift consumer would trust as "the full suite." Only a green run's report is retained: failing runs are the wrong population to measure steady-state per-spec durations from. `e2e-stress.yml`'s nightly sweep deliberately gets no equivalent upload — it runs `--repeat-each=3 --retries=0` on a different cadence, worker count and contention regime than PR/push runs, so its per-spec durations are not comparable to the retained series and pooling them would corrupt it.

`e2e-stress.yml`'s own `Run Playwright 3x, no retries` step is wrapped with the same `git_state_gate.py --` prefix, even though `e2e-stress.yml` is not one of the four workflows `tests/test_roots_registry.py::CI_WORKFLOWS` checks for isolation-root env-var coverage (see `docs/architecture/ci_isolation.md`'s "e2e-stress.yml: isolated through server-env.ts" section — it isolates entirely through `serverEnv()`, with no top-level `ALAN_*_ROOT` block of its own to check). The git-state gate is wired at the command level, independent of that env-var registry check, so both call sites that actually run the browser suite — the PR-time job in `tests.yml` and the nightly sweep in `e2e-stress.yml` — are covered.

## Machine-load reading: separating infrastructure contention from a genuine spec defect

A failure on a contended CI machine and a spec that flaked on its own look identical to the flake ratchet above — both are just a FLAKY row. This section adds a measurement, not a verdict: every test whose final status diverges from its expected status (skips excluded) records how loaded the machine was at the moment that failure was detected, so a reader of the flake report can at least see whether the machine looked contended when a spec flaked, without the ratchet's pass/fail line moving at all.

**What is recorded, and when.** `e2e/fixtures/test-base.ts`'s `machineLoadOnFailure` auto fixture — declared alongside, not inside, `serverLogOnFailure` — runs after every test. It returns early on `testInfo.status === "skipped"` and on `testInfo.status === testInfo.expectedStatus` (nothing to measure on a clean pass), and otherwise pushes a `type: "machine-load"` annotation carrying the raw `os.loadavg()` triple and `os.availableParallelism()` — never a precomputed ratio, so the observation can't be pre-judged into a verdict on the way in. The push is wrapped in a `try`/`catch` that swallows and returns: a probe failure can never change a test's outcome. This covers every test uniformly; there is no curated roster of "starvation-sensitive" specs and no helper declares itself starved.

**Why the failing attempt's own record, never the summary.** Playwright's JSON reporter (`node_modules/playwright/lib/runner/index.js`'s `_onTestEnd`) sets `result.annotations = params.annotations` per attempt but also overwrites `test.annotations = [...params.annotations]` on every attempt end — so after a retried test finishes, the test's summary-level `annotations` reflect only its *final* attempt. For a passed-on-retry test that final attempt is the one that succeeded, which never pushes a reading at all. Reading the summary therefore returns nothing on precisely the case this measurement exists to catch, silently: a green ratchet, satisfied test coverage, no signal that anything was ever wrong. `scripts/playwright-results.mjs`'s `collectOutcomes` closes this by descending into each test's per-attempt `results[]` and returning the reading from the first result that carries one — the failing attempt — never from the test's own `annotations` field. This was confirmed against a real `CI=1 --retries=1` run of a fail-then-pass spec before being wired up: the failing attempt's `results[0].annotations` carried the reading and the summary-level `annotations` was empty.

**Only one failure shape is visible, and that's stated rather than hidden.** The ratchet only runs when the suite step itself succeeded, and only counts files that failed once and passed on retry. A run starved badly enough to fail both attempts reds the job before the ratchet executes, so first-attempt-failed/second-attempt-passed is the only shape this measurement can ever report on.

**Deliberately, no threshold.** Nothing anywhere classifies a reading as "starved" or "not starved" — the number is reported and left to the reader. A bare cut-off in a script has nothing ratcheting it, unlike every other baseline in this repository (`e2e/flaky-baseline.json`, `tests/size_baseline.py`, the mobile/desktop audit high-water pins), so defining one here would reintroduce exactly the laundering surface this measurement-not-verdict design exists to avoid. Calibrating a real cut-off, if one is ever justified, waits for a persisted series of runs — not built here (see Boundaries below).

**Where it surfaces.** `scripts/report-flaky.mjs`'s advisory step-summary output appends the reading to a FLAKY row when one is present (` — load <perCpu>/cpu (loadavg1 <x>, cpus <n>)`), rendering unchanged when absent. In `--ratchet` mode only, each fresh flaky file's summary bullet additionally carries the max `perCpu` reading across that file's failing attempts and how many attempts contributed one. The presence or value of a reading never changes the reporter's exit code in either mode — asserted directly against the real script in `report-flaky.test.mjs` — which is the clause that forecloses laundering: nothing about this measurement can turn a passing check red or a failing one green.

**The machine-readable signal is skipped by the existing consumer, by construction.** Alongside each existing `::error file=…,title=Flake ratchet: new flaky spec file::…` annotation, ratchet mode now also emits `::notice file=…,title=E2E machine load at failure::…` for any fresh flaky file that carries a reading. `alan/e2e_failures.py`'s `_coerce_failing_test` rejects anything whose `annotation_level != "failure"` before it ever inspects the path, so a `notice`-level annotation is unreachable by that parser regardless of its path shape — confirmed by `tests/test_e2e_failures.py::test_parse_failing_e2e_annotations_skips_notice_level_machine_load_signal`. Had this instead been emitted as another `::error` on a spec path, it would have been absorbed into the flake ledger's rescued-spec set as a second failing test for the same spec — the inverse of that ledger's purpose. `RATCHET_TITLE` ("Flake ratchet: new flaky spec file") and `annotationPath` are unchanged, because `alan/teams/_fix_escalation.py` partitions ratchet verdicts by string-matching that exact title marker; the new `LOAD_TITLE` ("E2E machine load at failure") deliberately shares no substring with it.

**Fixtures are typed against the real per-attempt shape.** `scripts/playwright-report-fixture.ts` builds report fixtures typed against `JSONReport`/`JSONReportTest`/`JSONReportTestResult` from `@playwright/test/reporter`, so a fixture shape that drifted from Playwright's real one would fail `npm run typecheck` rather than silently passing every gate while reading nothing in production — the machine-readable report is written only under CI, so nothing else exercises its real shape. `alan/web/tsconfig.json`'s `include` was extended to cover `scripts/` for this reason.

**Separately, a diagnosability fix, not a starvation signal.** `e2e/fixtures/helpers.ts`'s `waitForDispatcherIdle` used to poll `expect.poll(...).toBe(true)` with no message, folding a non-2xx response and a genuinely busy workspace into the same opaque timeout. It now polls to a string — `"idle"`, `` `busy: <task_id>(<status>/<latest_invocation_status>), …` ``, or `` `unreachable: GET /api/workspaces -> <status>` `` — and asserts `.toBe("idle")`, so a timeout names what it waited for and what it last observed. This is unrelated to the machine-load measurement above; it is shipped alongside it because it is a cheap, complete win in its own right and there is no reason to hold it hostage to the rest.

**Known limitations.** `os.loadavg()[0]` is a 1-minute exponentially-weighted average, so a short, sharp contention spike can be under- or over-represented depending on when in that window the reading lands. `os.availableParallelism()` and `os.loadavg()` are both platform-reported figures whose accuracy depends on the runner platform (e.g. containerized runners with a scheduler quota) and isn't independently verified here.

**Explicitly out of scope, and why:** a persisted run-over-run series (new persistent state plus a redirect on every state-isolation surface, disproportionate to a per-run reading — see `CLAUDE.md`'s `ALAN_*` rule); enriching `alan/teams/_pr_flake_ledger.py`'s flake-quarantine proposal with these readings (its persisted record stores only PR numbers per key with no per-occurrence payload, so this is a schema change with back-compat, not a body edit, and that module is also being edited concurrently elsewhere); and covering `tests.yml`'s pre-run "Stress changed specs" step (its own report is overwritten by the main run's before the ratchet ever reads it). None of these close the baseline-pressure half of the issue this measurement was scoped from — that half stays open.

## Nightly stress-sweep failure naming and dedup (self-describing failures)

Before this, a failing nightly's filed `e2e-flake` issue carried only aggregate counts — how many tests ran, passed, failed and skipped — plus the names of tests that skipped themselves. The tests that actually *failed* were reduced to a bare number, so acting on the issue meant opening the CI run and digging through a step log or HTML artifact, which the fleet's automated workers cannot do at all. `scripts/report-stress.mjs`'s default-mode output now names every failed test individually, in the exact `- FAILED: file › title` row shape `report-flaky.mjs` already uses for its own failure rows, deduped across the sweep's 3 repeats (one test failing on all 3 repeats is one row, not three) and sorted. Both scripts now source this from a single shared leaf, `scripts/playwright-results.mjs` (`readReport`/`collectOutcomes`), instead of each maintaining its own copy of the suites-to-specs-to-tests walk — two reports that parse the same `playwright-results.json` and disagree about what they extract was exactly the failure mode this change closes, and folding `report-stress.mjs` onto the same walk `report-flaky.mjs` already uses avoids reproducing it. The named-failure block sits directly below the truncation notice (when present) and above the skipped-tests block, so a truncated list still reads as a floor on the true total, not a complete accounting. `playwright-results.json` is now also retained in the failure-path `upload-artifact` list alongside the existing `playwright-report/` and `e2e-stress-results.md`, so a report can be regenerated or re-examined after the fact without re-running the sweep.

**Dedup: `--fingerprint`.** A nightly that fails with the same set of failing tests as the currently-open `e2e-flake` issue already records should not pile on a duplicate comment; a nightly whose failing set changed should still report, so a new or shifted failure is never silently swallowed. `report-stress.mjs --fingerprint` prints `stress-fail-<count>-<first 12 hex chars of sha256 over the sorted, newline-joined, deduped failed \`file › title\` keys>` — hashed over the run's **full** failed set as recorded in the report, never over `stats.unexpected`'s raw repeat-inflated count or wall-clock duration, both of which drift nightly even when the same tests are failing. `e2e-stress.yml` computes this in a `Compute stress-failure dedup marker` step (gated `if: failure() && steps.stress.outcome == 'failure'`, same gate as the issue-filing step) and passes it as `dedup-marker` to `file-finding-issue`, embedded as an HTML comment on the issue/comment body and checked against the open issue's body and comments before posting a repeat. Every degraded `--fingerprint` case — a missing or unreadable report, malformed JSON, or a report with zero named failures — prints nothing on stdout and exits 0, never a sentinel string, so the workflow's `dedup-marker` output is empty and `file-finding-issue` falls back to its default always-comment behaviour rather than silently collapsing every undiagnosable night into one suppressed comment. `--fingerprint` is a fully separate, self-contained code path that runs before the ordinary missing-report branch and never touches `printSummary`/the step-summary text — a `--fingerprint` invocation cannot also emit the human-readable report.

`scripts/e2e-isolation-sweep.mjs` has its own, separate `collectFailures` walk over the same report shape — it is deliberately **not** folded onto `playwright-results.mjs`: it extracts per-result error text for a one-time manual audit tool with no CI wiring, not `file › title` identity, so unifying it here would widen this change's scope without removing a real disagreement between two failure-reporting paths.

The two workflow steps below (`summary` / `floor`) are otherwise unchanged by this addition — they closed a different gap (a healthy-looking nightly that quietly ran too little) that this failure-naming work leaves in place:

- **`id: summary`, `if: always()`** — `node scripts/report-stress.mjs > e2e-stress-results.md`, appended to `$GITHUB_STEP_SUMMARY` exactly like the old flake report. This is default mode: it always exits 0, even when `playwright-results.json` is missing or unparseable (`_no report file found_` / `_report file unreadable_`), because `always()` also runs it after an infra failure where no report can exist — the same reasoning `report-flaky.mjs`'s default mode already uses.
- **`id: floor`, `if: steps.stress.outcome == 'success'`** — `node scripts/report-stress.mjs --enforce`, gated on the *stress step's own* outcome (not job success, since earlier steps could already have failed) so a floor breach can only ever fire when the sweep itself passed. `--enforce` fails closed: a missing/unparseable report or a missing/malformed `e2e/stress-floor.json` all exit 1 with a distinct message, on the same "passing a required-looking check having verified nothing is a silent gap" logic as the PR-only ratchet's fail-closed behaviour.

**Why two steps instead of one.** The classification invariant this build has to preserve is that a genuine test failure files `e2e-flake` and an infrastructure failure files `e2e-nightly-broken`, and the two must never both fire for the same run. Folding the floor check into the same step as the summary (or into the stress run itself) would blur that: a floor breach is discovered *after* the stress step already reported `success`, so it has to live in a step whose own failure routes through the existing `steps.stress.outcome != 'failure'` branch of the broken-job body-prep script (`.github/workflows/e2e-stress.yml`) rather than the `steps.stress.outcome == 'failure'` branch that files `e2e-flake`. The body-prep script's `FLOOR_OUTCOME` check (`steps.floor.outcome == 'failure'`) adds one new `REASON` branch that names the count-floor check explicitly and inlines `e2e-stress-results.md`'s counts, so the filed `e2e-nightly-broken` issue carries the same evidence as the step summary — but it can never fire alongside `e2e-flake`, because the floor step never runs when the stress step itself failed.

**Executed count and why runtime skips are reported, not fatal.** "Executed" = `stats.expected + stats.unexpected + stats.flaky` — skipped tests are runtime self-skips, not executions, and are deliberately excluded so a test skipping itself cannot inflate the floor-guarded number. The suite has exactly one known runtime self-skip today, `health-metrics-panel.spec.ts:54` (`test.skip(true, "no last_computed_at seeded in this environment")`), which would red the very first nightly this ships against if a new skip were made fatal outright. The build instead surfaces skips by name in the summary and leaves them non-fatal: each skip still mechanically shrinks the number the floor checks, so a suite that quietly grows more self-skips cannot stay green forever — it erodes the floor-guarded executed count until a floor breach catches it. Skip counts are printed two ways because `--repeat-each=3` makes them legitimately differ: `stats.skipped` is Playwright's raw count (a self-skipping test produces three `skipped` entries, one per repeat), while the named list is deduped by `` `${file} › ${title}` `` so that same test reads as one problem, not three — e.g. `Skipped: 3 (1 distinct tests)`.

**Truncation.** A run that hits `maxFailures` (`report.config.maxFailures`, falling back to the literal `5` matching `playwright.config.ts`'s CI value) stops early, so its printed counts are a floor on the true total, not the total itself. The summary labels this explicitly (`_counts truncated — run stopped early after hitting maxFailures_`) only when `unexpected >= maxFailures` — not whenever `unexpected > 0` — because a run with one to four genuine failures is not truncated by a `maxFailures: 5` config, and mislabelling it would itself be a small instance of the silent-gap problem this build exists to close.

**The floor file.** `alan/web/e2e/stress-floor.json` holds `minExecutedTests`, `minSpecFiles`, and a validation-ignored `_note` string. It is hand-edited, tightening-only, and has no regeneration mechanism — the same contract as `e2e/flaky-baseline.json` and `tests/size_baseline.py`, and deliberately without a second pinned high-water literal (unlike the mobile-audit baseline): this floor only surfaces in a nightly failure message, so an ordinary PR cannot silently loosen it the way a machine-compared number could drift. It is explicitly coupled to `--repeat-each=3`: `minExecutedTests` is roughly (distinct tests) × 3, so a future change to the repeat count must edit this file by hand in the same PR or the floor will (correctly) start failing every nightly. `minExecutedTests` is `840`, derived from a measured `npx playwright test --list` (299 tests across 79 spec files, × 3 repeats = 897, minus the one known `health-metrics-panel.spec.ts` runtime self-skip — which self-skips on every one of its 3 repeats under `--repeat-each=3`, contributing 3 skipped entries rather than 1, so 897 - 3 = 894 executed in a clean run) rather than the static per-file-count estimate this floor originally shipped with — 840 sits about 6% below that measured figure, leaving room for routine suite growth or shrinkage. `minSpecFiles` stays at `75` rather than moving toward the measured 79: that only leaves 4 files of margin, and any number closer to 79 would risk becoming a loosening rather than a tightening the next time the suite's file count dips slightly. Watch the first post-merge nightly run before treating the 840 floor as fully settled — it is derived from a local listing, not an observed `workflow_dispatch` run.

## Changed-spec execution in the worker lanes

2026-08-04 incident follow-up (PRs #944/#947): e2e specs used to be write-only for workers — the first execution of an authored or edited spec was the CI gate itself, so an unsatisfiable new spec and a retired `data-testid` still asserted by an untouched spec both surfaced as a red required check that the flake machinery then misclassified. Two layers now close that:

- **Verification host gate (deterministic):** `alan/teams/_changed_e2e.py` selects the spec files the diff adds/edits (`git diff --name-only <base>...HEAD` in the grounded checkout, filtered to `alan/web/e2e/**/*.spec.ts`, excluding `mobile-audit/`/`capture/` to mirror the Playwright `testIgnore`, dropping deleted files) plus any spec whose text references a `data-testid` token the diff removed without re-adding. Non-empty selection synthesizes a `changed-e2e-specs` `TestScenario` (`npm --prefix alan/web run e2e -- <web-relative paths>`, capped at `ALAN_CHANGED_E2E_MAX_SPECS`=10 with the overflow noted in the description) that `verification._compute_scenario_results` executes through the ordinary `_scenario_runner.run_scenario` harness with its own budget (`ALAN_CHANGED_E2E_TIMEOUT_S`, default 900 s — the `pree2e` SPA build plus per-worker server boots live inside it, and it is NOT charged against the 600 s scenario aggregate budget). It runs even when authored scenarios are MISSING, is skipped for WAIVED (dependency-bot) runs, and honors the resume short-circuit. The scenario-runner role prompt pins the semantics: a `changed-e2e-specs` FAIL is the diff's own defect, never flaky — so it FAILs the scenario verdict and routes to `implementation_fix`.

  **The `<base>` above is resolved fresh, never a cached local ref.** Before this build, `local_diff_files` diffed against whatever `origin/main` happened to already be in the grounded checkout — a checkout leased from a pool slot that had not fetched recently could carry an arbitrarily stale `origin/main`, so the "changed" set silently widened to include every file merged by anyone else since that stale point. Because a `changed-e2e-specs` failure is deliberately never downgraded to flaky, that widening turned into `implementation_fix` being routed a spec it did not touch, finding nothing to fix, and escalating a review that blamed the PR for someone else's file. `build_changed_e2e_scenario(checkout, *, env=None)` now calls `alan.base_ref.resolve(checkout, env=env)` once per invocation and threads the resolved ref into `local_diff_files`, `_removed_testids`, and `testid_referencing_specs`, returning a frozen `ChangedE2ESelection(scenario, base_unresolved)` rather than a bare `TestScenario | None`. `verification._compute_scenario_results` builds `env` from the workspace's own governing engine config (`engine_config.forge_target_for_workspace` + `secrets_store.transport_env`, degrading to `env=None` on `MissingSecretError` — an unauthenticated fetch still works against a public remote and fails closed for a private one) and passes it through.

  **An unresolved base is structurally distinct from a clean, empty selection — it is never read as "this PR changed no specs."** When `base_unresolved` is `True`, `_verification_scenarios._changed_e2e_results` synthesizes exactly one `ScenarioResult` with `status="ADVISORY"` (already in `NON_BLOCKING_STATUSES`, so it cannot gate the verdict) and a diagnostic naming the cause (`"changed-e2e base unresolved: git fetch origin main failed, timed out, or git was unavailable — selection skipped, NOT confirmed clean"`) — `run_scenario` is never called in this branch. This flows through the existing `_to_scenario_outcomes` truncation into the handover with no new code path, so a reviewer sees an honest "could not check" rather than a false-clean.
- **Implementation prompt (pre-push safety net):** the shared environment block in `alan/teams/implementation.py` (inherited by `implementation_fix`) now instructs workers to run exactly the changed spec files before finishing (`git fetch origin main && git diff --name-only origin/main...HEAD -- alan/web/e2e` — the worker's own checkout is refreshed before the raw comparison it is told to run by hand, closing the same staleness hole for the one comparison a human-readable prompt instruction still performs directly rather than through `alan.base_ref`), keeping the full-suite-stays-in-CI rule.
- **PR CI stress step (flake detection under repetition, 2026-08-10):** the two layers above execute a changed spec once; a spec can pass once and still be flaky. `tests.yml`'s `e2e-frontend` job runs a `Stress changed specs` step — PR-only, gated on the `changes` job's `e2e_specs` filter (`alan/web/e2e/**/*.spec.ts`, `list-files: shell` supplies the paths) — that runs exactly the added/edited spec files with `--repeat-each=5 --retries=0` **before** the main suite, so the main run's report is what the ratchet steps read. Deleted files are skipped; >8 changed spec files skips the step with a summary note (the nightly e2e-stress sweep covers bulk changes); state is isolated by an `ALAN_E2E_ROOT` suffix and the ports are reused sequentially. A new spec that cannot survive 5 repetitions fails the PR that introduces it — the same philosophy as the ratchet, applied at the only moment flake attribution is cheap. A spec can still pass the isolated 5× stress and flake only under the full suite's 4-worker contention (PR #1159's `home-refetch-stability.spec.ts` did exactly that, twice), so the implementation and implementation_fix prompts (`alan/teams/implementation.py`, shared) now spell out the third layer: when the flake ratchet names a spec the diff adds or edits, the attempt-1 failure is on the check run's annotations and in the review's `GATE_FAILING_TEST:` lines, and the fix is to make the measurement robust to contention (settle before capturing a baseline, `expect.poll` across the window) — never to loosen a threshold or touch `e2e/flaky-baseline.json`.

## Scoped one-shot stub triggers

The stub's behavior triggers (`usage-limit-trigger`, `server-error-trigger`, `stub-hang`) and the backend's `ALAN_E2E_VERIFICATION_CANNOT_VERIFY` file are **content-scoped**: the trigger file's content names the scope it applies to. For the stub triggers the scope is the workspace **title** (matched against the `Title: <…>` first prompt line every team-dispatch node receives); for cannot-verify it is the **task_id** (checked by `_cannot_verify_trigger_active` in `alan/teams/_verification_grounding.py`). An empty file keeps the legacy fire-for-anyone semantics.

Scoping exists because the dispatcher keeps running a workspace's job chain after the test that dispatched it has ended: an unscoped trigger could be consumed by a leftover background invocation from a previous spec — or by the still-running workspace of a failed attempt #1 when Playwright retries — which was the suite's top CI flake class. Specs that arm a trigger write their own unique `Date.now()`-suffixed title (or task_id) into it and first drain background work via `waitForDispatcherIdle` (`e2e/fixtures/helpers.ts`).

## Usage-limit pause simulation

`ALAN_E2E_USAGE_LIMIT_RESET_IN_MINUTES` (default `1`) — when set AND the trigger file matches (see scoped triggers above), the stub emits a usage-limit result event (`"You've hit your limit · resets in N minutes"`) and **deletes the trigger file** so the subsequent resume run goes through normally. The trigger file is created by `usage-limit-pause.spec.ts` (content = its workspace title) immediately before dispatching; the spec asserts the pause via `/api/health`'s `queue_paused`/`paused_until` keys (deterministic) before checking the workspace status.

`ALAN_E2E_USAGE_LIMIT_TRIGGER_FILE` — path to the one-shot trigger file (`<per-worker root>/usage-limit-trigger`, set by `serverEnv()` in `e2e/fixtures/server-env.ts`). The stub only emits the usage-limit error when this file exists and its scope matches; other specs are unaffected.

`ALAN_USAGE_LIMIT_SAFETY_BUFFER_SECONDS` (default `1` in E2E; production default `120`) — controls the safety buffer added by `alan.usage_limit.parse_reset_time`. Set to `1` in E2E so the queue-pause window is narrow enough for the spec to finish in <30 s.

## `makeWebServer` factory

`playwright.config.ts` exports `makeWebServer(port, root)` — built on `serverEnv()` — the classic single-server `webServer` factory. The main suite does not use it (it boots one backend per worker, above); `playwright.mobile.config.ts` (`audit:mobile`), `playwright.desktop.config.ts` (`audit:desktop`, one server per project — standard and max) and `playwright.capture.config.ts` (`capture:screens`, which prefixes its own `vite build &&` step) each call it with a pid-derived port and root (`src/mobile-audit-config.ts`, `src/desktop-audit-config.ts`, `src/capture-config.ts`) rather than a fixed one.

The boot command runs, in order: `rm -rf "$E2E_ROOT_DIR"` → `mkdir -p "$E2E_ROOT_DIR/workspaces"` → `mkdir -p "$ALAN_ENGINES_ROOT"` and `cp` of `tests/fixtures/default_profile_test.yaml` to `$ALAN_ENGINES_ROOT/default_profile.yaml` → `PATH` prefix → `uv run python -m alan`. The copy sits after the wipe on purpose — a copy before it would be deleted by it — and targets `$ALAN_ENGINES_ROOT`, the variable `serverEnv()` hands that same server, so the directory written is by construction the directory read. It runs once per boot: a Playwright retry reuses the live server and does not rerun the boot command, and nothing rewrites the file mid-run.

**Why every browser-suite server installs its own default-engine profile.** `alan/default_profile.py`'s `resolve()` reads the installed profile first, then the checked-in owner file when one exists, then reports unconfigured, and an unconfigured default engine makes workspace creation refuse with "not ready", failing the E2E specs and both audit gates. The installed file wins in that order, so the suite never depends on an owner file being present. Identity stays `DejvMatikar/alan` with an autonomous posture and no readiness requirements because dozens of specs, the `gh` stub and the audit routes hard-code that slug, and declaring requirements would make the sandbox's default engine not ready again.

The servers now resolve `Source.profile` instead of `Source.owner`. `auto_update_surfaces` keys on that source, but the updater status it reads lives under `<root>/deploy/`, which is always fresh in these roots, so the surface stays inert and no spec can observe the flip.

Behaviour cannot prove the install: on private `main` a missing or failed install silently falls back to the owner profile and every spec still passes. The proof is therefore byte identity at the path each server actually reads, in three named tests — `e2e/default-engine-profile.spec.ts` (worker server), the "mobile audit server's engines root" test in `e2e/mobile-audit/mobile-audit.spec.ts`, and the "standard and max desktop audit servers' engines roots" test in `e2e/desktop-audit/desktop-audit.spec.ts` — each asserting the installed file exists and equals `tests/fixtures/default_profile_test.yaml` byte for byte. The two audit tests take no fixtures and touch nothing the audit measures, so `baseline.json` and its high-water pin stay byte-unchanged.

## Mobile-UI audit capability (advisory, non-blocking)

**Source:** `alan/web/playwright.mobile.config.ts`, `alan/web/e2e/mobile-audit/`, `alan/web/src/mobile-audit/audit-helpers.ts`.

`npm run audit:mobile` (root `alan/web/package.json`) renders each screen in `e2e/mobile-audit/screens.ts` at the Phase-1 floor viewport width, using a second Playwright config — `playwright.mobile.config.ts` — that calls `makeWebServer` with a pid-derived port and state root (`resolveMobileAuditPort`/`resolveMobileAuditRoot`, `src/mobile-audit-config.ts`; `5700 + pid % 1000` / `os.tmpdir()/alan-mobile-audit/pid-<pid>`, honoring `ALAN_MOBILE_AUDIT_PORT`/`ALAN_MOBILE_AUDIT_ROOT` overrides but setting neither anywhere) — the same pid-cached pattern `src/capture-config.ts` uses for screen capture (`docs/architecture/screen_capture.md`) — so it never collides with the blocking `e2e` run, and two concurrent `audit:mobile` invocations no longer bind-conflict or `rm -rf` each other's live state root either. The `pid % 1000` modulo carries a latent residual: two invocations whose pids differ by an exact multiple of 1000 would still derive the same port. That risk is inherited unchanged from `capture-config.ts`'s pre-existing precedent, not newly introduced or newly fixed here — accepted as low-probability rather than solved via a bind-and-report scheme (see `docs/architecture/screen_capture.md`'s equivalent note). `preaudit:mobile` runs `npm run build` first so the audit measures the current build, not a stale `dist/` — that build step still writes the fixed `alan/web/dist` and is not yet made concurrency-safe (tracked as a follow-up, mirroring `ALAN_WEB_DIST_DIR`'s fix for capture).

`workspace-decision` is the one entry in `screens.ts` with no static route (`/workspaces/:taskId` is a placeholder token) — it needs a real, escalated workspace with a blocking, recommended question before `Workspace.tsx`'s `DecisionCard` renders anything. `mobile-audit.spec.ts`'s `seedWorkspaceDecisionFixture` creates that workspace against the running audit server (`POST /api/workspaces`) and seeds its handover on disk with `e2e/fixtures/seed.ts`'s `seedBlockingQuestion`, then substitutes the resolved `task_id` into the screen's route before the scan loop starts. The lookup is idempotent by design: it lists `/api/workspaces` first and reuses a workspace already titled `e2e-mobile-audit-decision` instead of always creating one, because a Playwright retry of this test (see the retry note below) reuses the same live server and root rather than resetting them — without the reuse check, each retry would mint another duplicate workspace on every retry.

For each screen the spec (`e2e/mobile-audit/mobile-audit.spec.ts`) captures: horizontal overflow (`document.documentElement.scrollWidth` vs. the viewport), tap-target sizing for every `a[href], button, [role="button"], input, select, textarea` element, an `@axe-core/playwright` scan scoped via `AxeBuilder.withRules([...])` to `color-contrast` plus a curated set of ARIA rule ids, and a full-page screenshot. All numeric thresholds (viewport floor width, tap-target minimum, contrast ratios) are read from `alan/web/src/ui-spec.json` — the Phase-1 source of truth — never re-declared. The config and spec files read `ui-spec.json` directly with `fs.readFileSync` + `JSON.parse` rather than importing `src/ui-spec.ts`: Playwright loads both files through Node's native ESM loader on this Node version, which requires an import attribute for JSON modules that `ui-spec.ts`'s bundler-style `import ... from "./ui-spec.json"` does not use.

Per-screen grading (pass/fail + violation detail) is pure logic in `src/mobile-audit/audit-helpers.ts` (100%-covered by `audit-helpers.test.ts` under the normal `vitest` gate), so it's testable without a browser; the spec only does browser/axe/screenshot orchestration and writes, per screen, `alan/web/mobile-audit-results/<name>.audit.json` (e.g. `home.audit.json`) containing that screen's `ScreenAuditReport` — overflow/tapTargets/accessibility results plus the screenshot's relative path — alongside a combined `report.json` summarizing every screen (both gitignored). The spec's only assertions are that each per-screen and the combined report file was written — a screen failing overflow, tap-target, or accessibility checks is recorded as a per-screen observation in the JSON rather than an assertion of its own (see the ratchet-baseline gate below for what actually fails the run). Tap-target scanning filters out non-visible interactive elements (`el.offsetParent !== null` plus a non-zero bounding-rect check) before grading, so `display:none` / zero-size / `type="hidden"` elements never register as spurious undersized-target violations. Measured widths/heights are rounded to the nearest pixel before the `< minPx` comparison (`gradeTapTargets`), so an element sized at exactly the minimum (e.g. a `min-h-11` = 44px nav link) is not tipped into a false violation by sub-pixel `getBoundingClientRect` snapping on the fractional-DPR mobile profile. The contrast ratios in `ui-spec.json` are echoed into the report's `spec` field for documentation only — axe-core's `color-contrast` rule enforces its own built-in WCAG 2.1 AA ratios (4.5:1 / 3:1) and has no option to accept these values, so the echoed numbers are informational and coincide with what axe actually enforces rather than configuring it. `playwright.config.ts` sets `testIgnore: ["mobile-audit/**"]` so the default `npm run e2e` (and therefore the blocking Playwright suite) never picks up this spec directly.

### Ratchet-baseline gate (merge-blocking)

The measurement above feeds a merge-blocking gate, not just an observation. `alan/web/e2e/mobile-audit/baseline.json` is a checked-in, per-screen, per-dimension count of currently-tolerated violations (`overflow`/`tapTarget`/`contrast`). `src/mobile-audit/baseline-compare.ts` (`compareToBaseline`, 100%-covered by `baseline-compare.test.ts`) diffs each screen's current counts against its baseline entry; a dimension passes only when `currentCount <= baselineCount`. The spec (`mobile-audit.spec.ts`) asserts `comparison.pass` at the end of the run, so it **fails** (no longer always exits 0) when a change introduces new violations beyond the baseline, while pre-existing debt recorded in `baseline.json` never blocks on its own. `assertBaselineNotRaised` encodes the intended direction: it throws if any edit would raise a tolerated count, so the baseline normally ratchets down as violations are fixed and is not loosened to absorb new debt. The rare, deliberate exception is correcting a mis-measured baseline — a count captured before an async payload rendered (e.g. `home.tapTarget` was seeded at 11 before the finisher tooltip mounted), or a screen whose fixture state changed for reasons unrelated to the ratchet itself (`home.overflow` moved from 0 to 1 once `workspace-decision`'s onboarding gave `home` its first-ever seeded workspace row — `WorkspaceList`'s table has always overflowed the floor viewport width whenever any workspace exists, this was simply never exercised by an always-empty audit fixture before) — where the tolerated number is raised under explicit review to match the screen's real fully-loaded state, not to admit a regression. The advisory screenshot capture is unaffected and never gates.

`assertBaselineNotRaised` is now called in production, not only unit-tested: `e2e/mobile-audit/load-baseline.ts`'s `loadRatchetedBaseline()` is invoked by `mobile-audit.spec.ts` at module scope, before any screen is captured, so a raise fails within seconds instead of after all thirteen screens have rendered inside the ~180s-timeout job. The predecessor it diffs the committed `baseline.json` against is not git history but a pinned literal, `e2e/mobile-audit/baseline-high-water.ts` — a hand-maintained copy of the last-approved baseline, the same shape as the backend's `tests/size_baseline.py`. The documented raise exception above is therefore now a **two-file** change made by hand: `baseline.json` and `baseline-high-water.ts` move together, with no regeneration mechanism for either. The pin's honest limit mirrors `tests/size_baseline.py`'s: a single PR that edits both files in lockstep still passes — exactly as a size-ratchet PR that raises a pin alongside the file it caps does — which is why the pin file's only job is to hold the last-approved numbers, giving a raising PR's diff an unambiguous, reviewable shape rather than making the raise itself undetectable.

Before measuring each screen the spec waits for the visible interactive-element population to stop changing (a capped stability poll in `waitForInteractiveCountStable`) rather than a fixed settle window, so a data-driven screen whose count grows as async payloads land (e.g. `HealthCard`'s tooltip buttons appear once `/api/health` resolves) is measured after it settles, not mid-arrival. Each `baseline.json` count is therefore the tolerated **fully-loaded, clean cold-start** violation count for that screen. `playwright.mobile.config.ts` sets `retries: 2` so a transient render flake can't fail the gate on its own; note the retried server is reused (the `rm -rf` reset and the default-profile install live in the one-shot boot command), so a retry sees a *warmer* backend — `home` is screen 1 and measured clean on the first attempt, but a retry can find draft sessions the audit itself created by visiting `/build` and `/explore`, whose delete buttons inflate `home.tapTarget`. The config `timeout` (`180_000`) is deliberately generous so all thirteen screens finish on the first attempt, keeping the gate on the clean cold-start measurement rather than a draft-polluted warm retry.

`npm run audit:mobile` now runs automatically in CI as the `mobile-audit-gate` job in `.github/workflows/tests.yml`, gated by the same UI path filter as the other frontend-only jobs (`needs.changes.outputs.frontend == 'true' || needs.changes.outputs.workflows == 'true' || github.event_name == 'push'`), so backend-only PRs are not taxed by a browser-driven render. The job runs in the repo checkout (`uv sync --locked --extra dev` + `npm ci`) so the measurement executes against real application code rather than a code-less location, and provisions its own browser via `npx playwright install --with-deps chromium` rather than assuming Chromium is present on the runner. The job no longer runs a "Free mobile-audit port" cleanup step before the audit: with a pid-derived port, that pattern-matching cleanup could kill a concurrently-running sibling job's healthy server on the shared runner pool just as easily as a genuinely stale one. `playwright.mobile.config.ts`'s `globalTeardown` (`e2e/mobile-audit/global-teardown.ts`) replaces it, scoped to exactly the port this run derived.

The job uploads each result directory as an artifact straight after the step that writes it (`if: always()`, 14-day retention): `mobile-audit-results` (`report.json` plus one `<screen>.audit.json` and screenshot per screen) after the mobile audit, `desktop-audit-results` after the desktop gate. `always()` covers a failed audit, not a missing directory: when the mobile audit fails the desktop step is skipped and its upload finds nothing to send, and a job killed by its timeout uploads only what earlier steps had already handed over — which is why the mobile upload does not wait for the desktop gate. They are the only sanctioned source of measured counts for a hand edit to either baseline pair — see [mobile_ui_spec.md](mobile_ui_spec.md)'s measurement procedure.

### Known blind spot: routes that need seeded state

The real exclusion criterion is not "has a variable route segment" — `explore-architecture` in `screens.ts` targets `/explore/architecture`, a concrete instance of the parameterized `/explore/:consultant` route, and renders with no setup because `architecture` is a fixed, statically-known consultant key (`ConsultantModal.tsx`). The criterion is routes that need **seeded application state** to render at all. `/workspaces/:taskId` no longer belongs to this gap — the `workspace-decision` screen above is the state-seeding recipe (create-or-reuse a workspace, write its handover directly to disk, substitute the resolved id into the route) this section used to say didn't exist yet. `/projects/:projectId` and `/workspaces/:taskId/invocations/:invId` still require a real project/invocation to exist before the screen renders anything meaningful, so they remain intentionally outside `screens.ts` and out of the ratchet — the same recipe pattern applies whenever one of them gets onboarded. This is a deliberate coverage gap, not an oversight; it has no active tracker (it was previously tracked under the now-delivered UI-capability roadmap's Phase U5).

## Wall-clock-wait ratchet: extending the timer ban to e2e specs

The unit-test suite bans wall-clock timers nested inside a mocked network handler (`alan/web/eslint.config.js`'s `no-restricted-syntax` block scoped to `src/**/*.test.{ts,tsx}`/`src/test/**`, locked in by `alan/web/src/test/lintRules.test.ts`). That ban exists because a `setTimeout`/`setInterval`/msw `delay()` nested inside an `http.*` handler, a `mockImplementation(Once)`, or a direct api-module reassignment races the test's own assertions against real elapsed machine time: too short a delay on a slow CI runner and the assertion fires before the "in-flight" state it's checking even exists; too generous a delay and the test is just slow. The fix in both shipped cases was to replace the guessed duration with an **armed gate** — a promise the test resolves explicitly once it has observed the state it needed (see `useConnectStates.test.tsx`, `EngineConfigProposalPanel.test.tsx`, `EngineConfigEditor.test.tsx`) — or a promise that deliberately never settles when only the in-flight window matters (`useProposePrefetch.test.ts`).

**Decision: extend the ban to the browser e2e suite, scoped to `e2e/**/*.spec.ts`, at `error` severity, with three grandfathered exclusions.** This closes the door on *new* `page.waitForTimeout()` calls in Playwright specs without touching the handful that already exist — a ratchet, not a sweep (see below for why a sweep is explicitly out of scope here).

**Why Playwright's waiting semantics don't automatically inherit the unit-test argument, and why the ratchet applies anyway.** Playwright's own primitives (`expect(locator).toBeVisible()`, `page.waitForResponse()`, `expect.poll()`, `test.step` retries) already auto-wait on a real condition rather than a duration for the overwhelming majority of assertions — unlike Vitest/MSW, where nothing auto-waits and a raw `setTimeout` inside a mock handler is the *only* way a test used to simulate latency. So the unit-test failure mode (an assertion racing a guessed duration because there was no condition-based alternative) is structurally rarer in Playwright: most of the time, an engineer reaching for `waitForTimeout` had a condition-based alternative available and skipped it. That is exactly the shape of a needless-risk pattern a lint ban should close off for *new* code, even though it does not retroactively indict every existing call — hence a ratchet (ban new instances) rather than a mandated rewrite of what's there (see the per-file justifications below: each surviving call is either a case Playwright genuinely has no built-in primitive for, or a case where mistiming degrades silently instead of flaking red).

**Measured scope, not the stale report's "substantial number" framing.** At the commit this decision was made against (`fac327cc`, PR #916), there are exactly **5** `page.waitForTimeout()` call sites, across 3 files:

| File | Lines | Count |
|---|---|---|
| `e2e/capture/capture.spec.ts` | 45 | 1 |
| `e2e/mobile-audit/mobile-audit.spec.ts` | 70 | 1 |
| `e2e/project-ops-panel.spec.ts` | 210, 216, 232 | 3 |

A prior circulating report characterized this as a "substantial number" of remaining wall-clock waits; measured against the actual tree, it is 5 sites in 3 files. The ratchet decision (ban new, grandfather existing) does not depend on that characterization being right or wrong — it holds either way — but the count is recorded here so the next person auditing this doesn't have to re-derive it.

**Per-file grandfather justification** (why each wait is load-bearing there, and why it isn't converted now):

- **`e2e/capture/capture.spec.ts:45`** — a flat 1s wait after `page.goto()`, before a full-page screenshot, so every named route's async content (including `/health`'s and the chat surfaces' own polling, which never goes networkidle) has a chance to settle before the pixels are captured. This spec produces **advisory screenshot artifacts** for design review (`npm run capture:screens`) — nothing downstream asserts on pixel content, so a too-short wait degrades the artifact (a screenshot taken slightly early) rather than failing the suite. That is precisely the "can only ever produce a false pass, not a red build" class the build brief scopes out of this ratchet's cleanup; converting it to a condition-based wait would need a per-route "is this screen fully settled" predicate that doesn't exist today, for a payoff (a marginally more accurate advisory screenshot) that doesn't justify the work right now.
- **`e2e/mobile-audit/mobile-audit.spec.ts:70`** — this is not a guessed total duration; it is the **sample interval** inside `waitForInteractiveCountStable`, a hand-rolled poll loop that already exists specifically *because* a fixed settle window was the wrong tool (see the comment directly above the function: a fixed window raced data-driven tap-target counts as backend payloads landed). The wait here is the polling cadence of a convergence-detection loop, not a substitute for a condition — removing it would mean busy-polling the DOM every microtask instead of every 250ms, which is strictly worse, not a fix. This is the mobile-audit ratchet-baseline gate's own deflake mechanism; it stays.
- **`e2e/project-ops-panel.spec.ts:210,216,232`** — these assert an **absence**: that no extra SSE-driven re-fetch happens during an idle dwell window (lines 210, 232) or while a stream is connected and nothing changed server-side (line 216). There is no event to build an armed gate around — the property under test is "nothing happens for N ms," which is structurally a duration-based assertion in a way "wait for X to appear" is not. This is the one case in this table where the unit-test argument doesn't transfer at all, by construction, not just by convenience.

**Not required, and deliberately not done: converting these 5 sites.** The build brief explicitly scopes out a broad conversion sweep of existing wall-clock waits that "can only ever produce a false pass — rather than a red build" — exactly the `capture.spec.ts` and `mobile-audit.spec.ts` cases above. `project-ops-panel.spec.ts`'s waits gate a real, merge-blocking assertion (a negative/absence claim), but converting them isn't a lint-rule-shaped fix (there's no armed-gate equivalent for "prove nothing happened"), so it's out of scope for this ratchet too. This PR bans *new* instances and grandfathers exactly these three paths; it does not touch the 5 existing call sites.

## Test isolation (H2.4): unit-side resets, the leak pin, and order-independent e2e

**Scope bound, stated up front:** this item fixes cross-test **state** leakage — a mock, a stubbed global/env, a fake-timer clock, or server-side accumulation surviving from one test into another. It does not and cannot fix load-driven flakes (host-daemon contention, CI oversubscription); those are a different failure class and are not evidence this work failed. A concrete example was encountered while building this — the e2e isolation sweep below flaked under concurrency purely from this machine's own resource contention, verified as a machine artifact by rerunning the same specs alone.

### Unit-side reset contract

`alan/web/vitest.config.ts` sets all four of Vitest's automatic reset options, each closing a different residue class:

- **`restoreMocks`** — calls `vi.restoreAllMocks()` before each test. This only restores `vi.spyOn()` spies to their original implementation (it tracks a `restore` callback that only spies have); a plain `vi.fn()` has nothing to "restore" to, so this option does **not** touch plain `vi.fn()` mocks at all, even ones with a configured `.mockResolvedValue(...)`/`.mockReturnValue(...)`. This nuance mattered directly: the inherited plan assumed enabling `restoreMocks` would break `InvocationGraph.test.tsx`'s module-scope `fitView = vi.fn().mockResolvedValue(true)` mock (since `mockRestore()` on a plain `vi.fn()` looks like it should reset to no-op). Empirically (see `@vitest/spy`'s `restoreAllMocks`, which iterates only a `MOCK_RESTORE` set populated exclusively by `spyOn`) it does not, and the full 3563-test suite passes unmodified with all four flags on — confirmed by running the file in isolation before touching the config, not assumed.
- **`clearMocks`** — calls `mockClear()` on every registered mock (spies and plain `vi.fn()` alike) before each test: clears call history/results, leaves any configured implementation alone.
- **`unstubGlobals`** — calls `vi.unstubAllGlobals()` before each test, reverting any `vi.stubGlobal(...)`.
- **`unstubEnvs`** — calls `vi.unstubAllEnvs()` before each test, reverting any `vi.stubEnv(...)`.
- **`vi.useRealTimers()`** — no Vitest config flag exists for this one, so `src/test/isolation.ts`'s `installIsolationResets()` registers it as an explicit `afterEach`. A test that calls `vi.useFakeTimers()` and never restores would otherwise leave every later test in the same file (Vitest isolates *per file*, not per test — see below) running against a frozen clock.

`src/test/setup.ts` is now just `installMswLifecycle(); installIsolationResets();` — both exported from `src/test/isolation.ts`, factored out of the setup file specifically so the negative control below can build on `installMswLifecycle()` alone without duplicating it (duplication here would otherwise be permanently frozen once H4.1's deferred jscpd-over-tests baseline lands).

**Vitest isolates per file, not per test.** With `isolate: true` (the default, unchanged here), each *file* runs in its own module registry, so cross-*file* leakage of the kind this section fixes does not exist — the leak domain is strictly "within one file, across tests in declaration order." Playwright's shared-per-worker-server leakage (below) is a different shape for a different reason; the fix for one does not imply the fix for the other.

### The leak pin and its negative control

`src/test/isolation-pin.test.ts` has three ordered pairs — `vi.spyOn` residue, `vi.stubGlobal` residue, `vi.useFakeTimers` residue — where each pair's first test deliberately leaves residue and the second asserts the original state is back. Declaration order is the mechanism: Vitest runs a file's tests in the order written (no shuffling configured).

The **negative control** proves the pin can actually fail: `vitest.no-isolation.config.ts` points at `src/test/setup.no-isolation.ts` (which calls `installMswLifecycle()` only — no reset flags, no `vi.useRealTimers()` afterEach) and restricts `include` to just the pin file. `npm run test:pin-control` runs the pin against that config with the shell's `!` inverting the exit code — the *underlying* vitest run must fail (all three "test 2" assertions) for the wrapping npm script to exit 0. Both run logs are committed as one-time evidence: `docs/audits/frontend-test-isolation-2026-08/pin-isolation-on.log` (passes) and `pin-isolation-off.log` (fails, all three pairs).

A handler-residue pin was considered and rejected: `server.resetHandlers()` already runs in `afterEach` (see below), so a pin built on MSW handler leakage cannot fail at HEAD and would be a pin that always passes — exactly the "rejected deliverable" the build brief calls out by name.

### Async-leak detector (tally-only)

`src/test/isolation.ts`'s `createRequestTally(emitter)` attaches to `server.events` and tracks `request:start` against `request:end`/`request:unhandled`. A request id present after `request:start` with no matching `request:end` by the time a test's `afterEach` runs is flagged — this single mechanism catches two distinct things named in the build brief: genuine async work still in flight when a test ends, **and** a request that hit `onUnhandledRequest: "error"`'s throw path, which (verified empirically, not assumed) fires `request:start` and `request:unhandled` but never `request:end` for that request id, so a component that swallows the resulting fetch rejection passes today with a silently missing default handler.

The detector is independently tested in `src/test/isolation.test.ts` against a hand-rolled fake emitter (not a second live MSW server, to avoid two `setupServer().listen()` instances fighting each other) — driven with a simulated leak and shown to flag it, a well-behaved request/response pair and shown not to, and a `request:unhandled` event and shown to count it.

It ships **tally-only**: `installIsolationResets()`'s `afterEach` calls `console.warn(...)` on a detected leak (visible with `vitest run --reporter=verbose`; the default reporter suppresses console output for passing tests) and never throws or fails a test. Running it across the full unit suite found 382 warnings; the dominant cluster was six endpoints with no default handler in `src/test/handlers.ts` at all (`InvocationGraph`'s `/handovers` fetch chief among them), fixed here by adding defaults matching the existing empty-response convention, cutting the count to 132 across 29 files. The remainder — mostly unawaited POST mutations and pre-existing-handler timing races — was recorded as follow-up, not fixed here; fixing everything the instrumentation surfaces was never this PR's commitment.

### E2E: the isolation sweep

`alan/web/scripts/e2e-isolation-sweep.mjs` (`npm run e2e:isolation-sweep`) runs every top-level spec **alone**, one `playwright test <file> --workers=1` per spec against a freshly booted backend, recording a three-state result per spec: `pass`, `pass_on_rerun` (failed once, passed on an immediate rerun — the signal that separates a load flake from real sibling-dependence), or `fail` (failed twice running alone). This is the mechanical proof of self-sufficiency the build brief asks for: a spec that passes alone provably depends on no sibling's accumulated server state. **Its explicit blind spot: this proves a spec does not depend on a sibling's state — it does NOT prove a spec tolerates pollution left by one.** Only the first property is claimed anywhere in this work.

Kept out of per-PR CI: 73 server boots (73 top-level specs; `mobile-audit/` and `capture/` are excluded, matching `playwright.config.ts`'s own `testIgnore`) would dwarf the existing ~2-minute e2e job. It's a one-time dated audit, not a baseline anything must refresh — its result was 73/73 passing alone.

Concurrent sweep child processes are each their own single-worker Playwright run, so every one reports `parallelIndex` 0 — without a fix, they'd all compute the same `e2e-stub-pr-branch-w0` and race `git worktree add -B` in the shared checkout. `server-env.ts`'s `ghBranchSuffix(parallelIndex)` folds in `process.pid` to keep them apart, following the same pid-derived convention as `resolveMobileAuditPort`/`resolveMobileAuditRoot` — no new `ALAN_*` env var. Port/root collisions across concurrent slots are handled entirely inside the sweep script itself (`E2E_PORT`/`ALAN_E2E_ROOT` overrides per slot, in a range disjoint from the normal e2e/capture/mobile-audit pid-derived ranges), since the sweep script controls those independently of the fixture.

### Declarative engine seeding: `seedEngines`

`e2e/fixtures/test-base.ts` exposes an opt-in fixture option, `seedEngines: SeedEngineSpec[]` (empty by default), settable per spec/describe block via `test.use({ seedEngines: [{ owner, repo }] })`. An `auto: true` fixture consumes it and calls the existing `registerGuardEngine` (`e2e/fixtures/seed.ts`) once per entry before the test body runs; the empty-list default is a fast path that adds no request and changes no behavior for a spec that never sets it. This is the **one** declarative seeding pattern this item adds — extending `helpers.ts`/`seed.ts`'s existing pattern rather than inventing a second one. It ships with zero live callers today: the isolation sweep found no spec that fails alone, so none needed retrofitting. It's infrastructure for the next spec that does.

### Reversed-order run (secondary evidence)

`scripts/generate-reversed-shims.mjs` (`npm run e2e:reversed`) generates one `NNN-<name>.spec.ts` shim per top-level spec under `alan/web/.reversed-shims/` (gitignored, eslint-ignored, outside `e2e/` so `playwright.config.ts`'s `testDir` never discovers it) — each shim is one line, `import "<relative path to the original>";`. NNN is assigned ascending as the specs' alphabetical order descends, so shim `001` imports the alphabetically *last* spec and the highest NNN imports the alphabetically *first*. `playwright.reversed.config.ts` points `testDir` at that directory with `workers: 1` — Playwright sorts discovered spec files by name itself, so this shim-rename is the only way to reorder execution; passing files in a different order on the CLI has no effect on Playwright's own sort.

T2-11 mandates this run, but as secondary evidence with its weakness stated rather than hidden: with the real config's `workers: 4` and `fullyParallel: false`, "run order" is four dynamically-fed queues whose composition shifts every run, so a single reversed pass samples one point in an already-nondeterministic space — and `workers: 1` here changes the timing profile from what CI actually runs, so this evidence is about ordering, not about the CI configuration. The committed result (`docs/audits/frontend-test-isolation-2026-08/reversed-order-run.json`): 254 passed, 1 pre-existing unconditional `test.skip` unrelated to ordering, 1 failed — a `build-chat.spec.ts` session-count assertion that the isolation sweep above already proves does not need any sibling's state to pass on its own. See the audit README for why that single failure is recorded rather than chased: it exercises the reversed run's own disclosed blind spot (pollution-tolerance), not the property this item fixes (state dependence), and is not touched here per the "no spec may be weakened... seed a precondition instead" rule, which only applies to genuine dependence.

### What this item is not: `ONE_SHOT_TRIGGERS`

The scoped one-shot stub triggers (`ONE_SHOT_TRIGGERS` in `e2e/fixtures/test-base.ts`, "Scoped one-shot stub triggers" above) are a *different*, already-solved leak surface — cleared at test *setup* by the existing `triggerHygiene` auto-fixture, not touched by this item. Nothing here changes that mechanism; it's noted only so a future reader doesn't conflate the two.

## Hit-test confinement: `elementFromPoint`/`elementsFromPoint` gated behind one helper

`repo-tabs-tooltip-layering.spec.ts` intermittently failed under host saturation because its local `assertTooltipOnTop` helper gated on `toBeVisible()`, which treats Tailwind's 1x1 `sr-only` clip as visible — so it measured the tooltip's bounding box before React had actually swapped `HoverReveal` into its open, unclipped layer, then hit-tested a stale, clipped rect. Six sibling specs (`keyboard-only-dashboard.spec.ts`, `repo-dashboard-density.spec.ts`, `home-repo-table.spec.ts`, `repo-chrome-accent.spec.ts`) already gate the same reveal correctly with `expect(description).not.toHaveClass(/sr-only/)`, an auto-retrying assertion that only resolves once the open class lands; the fix reuses that idiom instead of inventing a second one.

A second defect sat next to the first: the spec never waited for the workspace table itself to render, so on a slow render the hit test could pass **vacuously** — nothing sitting under the tooltip, `elementFromPoint` trivially returning the tooltip, and the test going green without ever exercising the layering it's named for. That matters because `stickyOffsets.test.ts` already proves the z-index ladder is numerically ordered; only a real hit test proves the sticky region's own stacking context doesn't clamp the reveal underneath it regardless of that ordering (see `DESIGN_SYSTEM.md`'s z-index ladder section for why the sticky region needed its own explicit z-index in the first place).

Both defects are fixed together in one shared helper, `expectRevealAboveSticky(page, revealId, beneathSelector)` in `alan/web/e2e/fixtures/layering.ts`: it waits for `beneathSelector` to be visible (the missing table-render wait), waits for the reveal to lose `sr-only` (the correct open-state gate), then runs a single `page.evaluate` that reads both elements' rects, finds the `beneathSelector` match that genuinely intersects the reveal, hit-tests the intersection's centre with `document.elementsFromPoint`, and returns a flat `{ revealIndex, beneathIndex, beneathHasSticky }` record. A missing reveal, no overlapping header, or a header missing the `sm:sticky` class all fail the same way `revealIndex >= revealIndex < beneathIndex` failing does — there is no code path back to a silent pass. Both call sites in the spec (`hover` and `focus`) route through this one function, so there is exactly one place that ever measures the DOM to prove layering.

`alan/web/src/e2e-hit-test.drift.test.ts` locks the confinement in: `document.elementFromPoint`/`elementsFromPoint` may appear only inside `fixtures/layering.ts`, no `*.spec.ts` may call it directly, the exemption list ships and stays pinned at `[]`, and a fourth check fails if `layering.ts` is ever hollowed out (deleted, or edited to drop either the hit-test call or its own `not.toHaveClass(/sr-only/)` reveal gate) — the same three-plus-one shape as `github-links.drift.test.ts`'s confinement of the `https://github.com/` literal. It lives under `alan/web/src/` rather than `alan/web/e2e/` because `vitest.config.ts` never discovers `e2e/**`, and it carries neither the coverage nor the `jscpd` duplication obligation for the same reason `github-links.drift.test.ts` doesn't (`vitest.config.ts` excludes `src/**/*.test.{ts,tsx}` from coverage, `.jscpd.json` ignores the same glob).
