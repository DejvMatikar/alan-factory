# Workspace API

**Source:** `alan/workspace.py`, `alan/server.py`, `alan/routes/` (sub-package).

`alan/server.py` mounts the routers defined under `alan/routes/`; that mount list is the authority and is deliberately not restated here. Route handlers, dependencies, and response models live in the sub-package; `alan/server.py` owns only app construction, lifespan wiring, and CORS middleware.

`tasks_router` carries the task-scoped canonical routes under `/api/workspaces/{workspace_id}/tasks/{task_id}/`. Legacy flat routes on `workspaces_router` (e.g. `POST /api/workspaces/{task_id}/dispatch`) issue a **308 Permanent Redirect** to the canonical path; clients that send `POST` must preserve method and body (RFC 7538 §3). For current single-task workspaces `workspace_id == task_id`.

Per-task state lives under `~/.alan/workspaces/<task_id>/{meta.json, history.json, handovers/}` (root configurable via `ALAN_WORKSPACES_ROOT`).

## Human-intervention markers (`Meta.interventions`)

`Meta.interventions` is an append-only list of `Intervention` records (`{action, timestamp_utc}`, `InterventionAction` enum in `alan/workspace.py`) stamped by `workspace.record_intervention` from the **route layer only** — it marks a human (or an external proxy driving the API) touching a workspace mid-flight. Automatic dispatch paths (`alan/auto_continue.py`, `alan/project_auto_continue.py`, the dispatcher's handover routing, create-and-dispatch) bypass the routes and never record. Recording routes: `answer` (answer route, only when an answer is persisted), `redispatch` (task dispatch when `prior_handover_for_task` is non-null — a first dispatch records nothing; the inbox propose-approval path dispatches via `perform_task_team_dispatch(..., record_redispatch=False)` and records nothing), `resume`, `force_complete` (out-of-band complete, both verified and forced paths), `scenario_override` (scenarios PUT), and `health_complete` (`POST /api/health/complete`). `record_intervention` re-reads `meta.json` before writing and returns the fresh `Workspace`, which call sites thread into their subsequent meta writes so the marker survives same-request status flips. Consumed by the fully-autonomous build rate — see [health.md](health.md) §`autonomous_rate`.

| POST | `/api/workspaces` | Create a workspace. Body: `{title, description?, tasks?: Task[], dependencies?: {from_id, to_id}[], engine_key?: string}`. Returns `{task_id, root_task_ids: string[]}` — `root_task_ids` lists tasks with no `depends_on` (roots of the DAG); for legacy single-task callers it is `[task_id]`. Multi-task bodies are validated: 422 on duplicate task id, dangling dep reference, or cycle. Incoming `task.status` values are overridden to `PENDING` server-side. `engine_key` (a `RepoIdentity` slug, e.g. `"owner/repo"`) names which registered engine governs the workspace; omitted/`null` means the existing default engine (unchanged behavior). A seeded `tasks[i].team` is validated before anything is created: 400 naming the offending task id and team when the team is unknown, when it is not manually dispatchable (an internal-only team — `decomposer`, `brief_refine`, `dependency_sweep`), or when it can reach the `decomposer` step (would re-plan the whole item) — the reconciler's auto-advance enqueues each unblocked subtask's stored team verbatim with no other check, so this is the only validation point on that path. A `requirements[]` entry that supplies a non-empty `id` on the raw request body returns 422 stating that clause ids are derived from clause text and must be omitted — this fires before any workspace, directory, predispatch-log row, or audit row exists, same as the team/engine/lane checks. See [lane_limit.md](lane_limit.md) for the seat rule, idle clock, and lock scope; this is the only workspace-creation path that can be refused this way — revivals (answer/re-dispatch/unarchive) and system-created workspaces (dependency sweep, project auto-continue, reconciler) are never refused. On success the slug is persisted as `Meta.engine_key` and resolved into the full `EngineConfig` at first dispatch — see [engine_config.md](engine_config.md) and [queue_and_dispatcher.md](queue_and_dispatcher.md). The referenced prep-chat session (`prep_chat_kind`/`prep_chat_session_id`) is archived onto the workspace on every successful create, whether or not the request also names a `team` — a failed archive is logged and never fails or rolls back the create. |

| POST | `/api/workspaces/{task_id}/archive` | 204 on success; 404 if missing; 409 if any job is `RUNNING`/`PENDING` (checked first, unchanged, via `queue.has_active_work` — which excludes workspaces present in `paused_tasks`, so a **paused** workspace can have a real running/pending job underneath and still pass this check straight through to the subtask guard below; that exclusion is precisely why the subtask check below cannot be replaced by "also check queued jobs"). Mirrored at the queue layer by `paused_tasks` so the dispatcher will not re-claim while paused. |
| POST | `/api/workspaces/{task_id}/resume` | 202 on success with `{queued_jobs}`; 404 if missing; 409 if status is neither `PAUSED` nor (`AWAITING_INPUT` with a resumable failed job). ## Deletion semantics

`DELETE /api/workspaces/{task_id}`:

1. Read state.
2. Reject with 409 if any job is `RUNNING` or `PENDING`. Both states must be checked — checking only `RUNNING` would leave a pending row that the dispatcher could claim between the check and the rmtree (50 ms poll TOCTOU).
3. Delete queue rows for the task: `queue.delete_jobs(task_id)`.
4. `shutil.rmtree` the workspace directory.
5. Publish `workspace_deleted` `TeamEvent`.

Rows-before-files: a crash mid-flow leaves recoverable orphan files rather than orphan rows that would confuse the dispatcher. Publishing the event **after** the destructive ops succeed means a partial failure doesn't emit a misleading deletion signal to SSE subscribers.

`workspace.delete` translates `FileNotFoundError` from `shutil.rmtree` into `WorkspaceError` so a TOCTOU race between the `is_dir()` check and `rmtree` still maps to a 404 (not a 500).

Claude Code sessions under `~/.claude/projects/` are **not** removed — no link between an Alan workspace and a CC session is tracked. The frontend confirmation dialog says this explicitly.

Frontend `useLiveWorkspace`'s `WORKSPACE_LIFECYCLE_KINDS` includes `workspace_deleted`, so any other tab open on the same workspace refetches and surfaces the 404 instead of staring at stale state.

CORS `allow_methods` was extended to include `DELETE`.

## Lifecycle

`Status` is exactly `{ACTIVE, AWAITING_INPUT, COMPLETED, ARCHIVED}`. Legacy on-disk values (`failed`, `escalated`, `plan_needs_revision` from earlier schemas) heal to `AWAITING_INPUT` via a `field_validator("status", mode="before")` on `Meta`; an unknown string still raises `ValidationError`. The next `transition` write persists the healed value, so the legacy strings disappear from disk on first interaction.

`COMPLETED` is written only by the `retrospective` team's terminal router decision (see [router.md](router.md)). `ARCHIVED` has exactly two writers: `POST /archive` above, and `alan/retention.py`'s `_archive_one`, which calls `workspace_mod.transition` directly as part of the retention sweep (already gated on the workspace being complete, idle past its dwell threshold, and free of active work) and therefore bypasses the `POST /archive` incomplete-subtask guard by design. No other path writes `ARCHIVED` — in particular, there is no archive-on-merge transition; a PR merging never by itself archives a workspace. Every `ARCHIVED` write — the manual archive, the forced archive and the retention sweep — records the status it replaced in `Meta.pre_archive_status`. The recording lives in `workspace.transition`, so no call site changes: it reads the status on disk (not the caller's snapshot, so a stale retention snapshot cannot record the wrong value) and stores it through the pure `lifecycle.pre_archive_status`, which keeps the saved value across an `ARCHIVED` → `ARCHIVED` rewrite and clears it on every other write. The field is internal; `WorkspaceDetail` does not expose it.

The reverse transition (`ARCHIVED` → …) is written only by `POST /unarchive`, through `alan._dispatcher_retire.restore_from_archive` and the pure `lifecycle.unarchive_target`. It restores status only — it never enqueues, dispatches or starts anything — so an operator must dispatch (or, from the `PAUSED` outcome, first resume, then dispatch) the workspace's outstanding subtasks afterward:

| Status when archived | Status after unarchive |
|---|---|
| `COMPLETED`, `FAILED`, `PARTIAL`, `ESCALATED`, `AWAITING_INPUT` | The same status, park state kept |
| `PAUSED` | `PAUSED`, Resume works as before |
| `ACTIVE` | `AWAITING_INPUT` with `ParkReason.UNARCHIVED`, blockers and merge-block class cleared |
| Archived before the status was saved (no `pre_archive_status`) | `AWAITING_INPUT` with `ParkReason.UNARCHIVED`, blockers and merge-block class cleared |

A pause marker for the task in `paused_tasks` takes precedence over every row and restores `PAUSED`. Unarchive never produces `ACTIVE`, because `ACTIVE` means an agent is really running and can be stopped, and unarchive starts none. There is no backfill: a workspace archived before the status was saved comes back as `AWAITING_INPUT`.

`ParkReason.UNARCHIVED` ("Restored from archive" in the UI) marks a workspace the operator brought back, not one that is stuck. While a workspace stays `AWAITING_INPUT` with that reason it produces no incident (`incident._EXEMPT_PARK_REASONS`), the unblocker skips it (`unblock_sweep.exempt_reason` returns `restored from archive`) and the orphan reconciler skips it (`_reconciler_orphans._orphan_eligible`); all three use the one predicate `lifecycle.held_by_unarchive`. The exemption needs no flag to end: dispatching a team or answering a question moves the workspace to `ACTIVE`, which clears the park reason (`WORKSPACE_TABLE`), and a later park carries its own reason and gets normal treatment. Leaving `ARCHIVED` never stamps `Meta.terminal_at` (`lifecycle.stamps_finish` is false whenever the previous status is `ARCHIVED`), so restoring a finished status keeps the original finish time.

Failures and the previous `escalate` decision both map to `AWAITING_INPUT` so the user picks the next move — there is no terminal failure state.
