# Worker records

`alan/worker_records.py` (records + identity probe), `alan/worker_reaper.py` (the boot-time sweep), `alan/claude_cli_journal.py` (the journal tailer, shared between the spawn path and attach), and `alan/teams/_node_attach.py` (attach) together let a team worker survive a service restart and let the restarted service re-attach to it and finish the interrupted work. Detachment (`start_new_session=True`) and journal-mode streaming turn on together, gated by the `ALAN_DETACHED_WORKERS` dial (see below) — a detached worker cannot stream through pipes.

## Schema (`WorkerRecord`, `RECORD_VERSION = 1`)

One JSON file per spawned worker process, at `<state_root()>/worker_records/<session_id>.json` (`~/.alan/state/worker_records/` in production; the writer creates the directory). `WorkerRecord` is a frozen pydantic model, and the writer (`model_dump()`) and the reader (`model_validate`) both go through it, so a file that fails the model is unreadable and the boot sweep deletes it. Types are strict (integer fields reject a boolean, and a float field accepts an integer), a missing optional key loads as `None`, unknown keys are ignored (`extra="ignore"`), and the schema check is equality with `RECORD_VERSION`. `SlotHold` (`<state_root()>/slot_holds/<workspace_id>.json`) is the same kind of model, with string ids and a lax float `written_at`. Fields:

- **Job identity**: `job_id` (nullable — only findable by the stop fallback when set; a `None` job_id still writes a record and still reserves its slot), `task_id`, `workspace_id`, `team`, `inv_id`, `node_id`, `role`, `model`.
- **Placement**: `engine`, `slot_path` (the resolved working-directory path this worker occupies — the pool has no slug of its own, and per-engine pool directories are hashed, so path is the only stable join key).
- **Session**: `session_id` (also the record's filename stem), `output_path` (the stream file the worker's output is tee'd to).
- **OS identity**: `pid`, `started_at` (wall-clock epoch), `lstart` (the OS's own process-start timestamp string, from `ps`), `cmdline` (the OS's own full command line, from `ps`) — `pid`/`started_at`/`lstart`/`cmdline` are all `None` until the process has actually been spawned.
- **Budget**: `deadline_at` (wall-clock epoch — `clock.now() + claude_cli.abs_timeout_seconds()` — expressed as an absolute timestamp precisely so it survives a machine reboot, unlike a monotonic duration), `idle_timeout_s`, `max_turns`.
- **Run identity**: `service_pid`, `service_started_at` (the OS `lstart` of the alan service process itself, memoized once via `this_service_identity()`), `host` (`socket.gethostname()`).
- **Detachment** (nullable, stamped only for a journal-mode/detached spawn — `RECORD_VERSION` stays `1` for these three additions; the `= None` defaults on the model plus `extra="ignore"` are what keep a rollback tolerant, so a binary that no longer recognises them still parses the rest of the record instead of discarding it): `pgid` (the worker's own process group id, captured via `os.getpgid` right after spawn — this is the field the boot sweep and attach both key on to recognise a genuine detached survivor), `journal_offset` / `err_offset` (the byte offsets `alan.claude_cli_journal.open_journal_handles` returned for *this* spawn, captured by the `on_journal_opened` callback before the child is even started — attach re-streams from these offsets rather than from the start of a journal file that may have been reused across a prior resume attempt).

## Write ordering and atomicity

`write_initial()` and `stamp_started()` both write via mkstemp + `os.replace()` — never a direct open-and-write — so a reader never observes a half-written file. The lifecycle:

1. **Before the process is spawned**, `write_initial()` writes the record with `pid=None`/`started_at=None`/`lstart=None`/`cmdline=None`. This call is unwrapped — an `OSError` here propagates and the spawn attempt itself is abandoned. There is no path where a worker starts running without a record already on disk for it.
2. **Immediately after the process is spawned**, `stamp_started()` read-modify-writes the same file with the real `pid`/`started_at`/`lstart`/`cmdline`. The caller's own `on_proc_started` callback (e.g. `ProcRegistry.attach`) runs *first*; the stamp then runs inside its own `try/except OSError: pass` — a stamp failure must never suppress the callback that lets the existing Stop path find the process, and (per the reserve/terminate asymmetry below) it degrades safely into an unsignalled reservation rather than corrupting bookkeeping.
3. **On normal completion**, `remove_record()` deletes the file (idempotent — `unlink(missing_ok=True)`), wrapped in its own `try/except OSError: pass` since a removal failure has a second line of defence (the boot-time reaper, and eventual job-level cleanup).

A partially written record — `pid` still `None`, or a record whose file has vanished — is therefore only ever the signature of **a crash between steps 1 and 2, or of a worker that has already finished**. It is never the signature of a live worker that went unrecorded, because step 1 always happens first and is never swallowed.

`alan/teams/_worker_record_hook.py`'s `worker_record()` context manager is the one call site that drives this lifecycle; it wraps the `run_agent_streaming()` call in both `_run_fresh_node` and `resume_workflow_node` (`alan/teams/_base.py`).

## The identity probe (`probe()` → `ProbeVerdict.LIVE | DEAD | UNKNOWN`)

Reading a record must distinguish a genuinely live worker from a stale artefact — not merely "is a process with this number still running" but "is it the *same* process we spawned", checked against both its OS start time (`lstart`) and its command line (`cmdline`), so a recycled PID cannot be mistaken for our worker.

| Condition | Verdict |
|---|---|
| `record.host` doesn't match this machine | `DEAD` |
| `(record.service_pid, record.service_started_at)` matches *this run* of the service | `DEAD` — see the non-relaxable rule below |
| `record.pid is None` (write_initial ran, stamp_started never did) | `UNKNOWN` |
| `os.kill(pid, 0)` raises (no such process) | `DEAD` |
| `ps` can't be read for that pid (transient failure, permissions) | `UNKNOWN` |
| `ps` succeeds but `lstart`/`cmdline` don't match the record (recycled pid) | `DEAD` |
| `ps` succeeds and both match | `LIVE` |

**The rule that current-run records are never `LIVE` is load-bearing and must not be relaxed.** A record written by *this* run of the service names a worker this run itself is actively tracking through its own in-memory `ProcRegistry` — it has no business being treated as a restart survivor. If that same-run exclusion were ever weakened to "match by pid+lstart like everything else", the boot sweep (`worker_reaper.reap_and_reserve`, invoked from the lifespan on every startup — including a restart mid-run, e.g. a crash-and-relaunch within the same process lifetime is not how this fires; it fires on genuine process restarts where `this_service_identity()` is freshly re-derived) would misclassify its own just-spawned workers as terminable and start killing the fleet it just started. The exclusion holds unconditionally, before any pid/liveness check runs at all. This same **previous-run-only filter** (`_is_same_service_run` ⇒ `DEAD`) is what makes attach safe to build on `probe()` unmodified: the sweep and attach's re-probes never touch this run's own workers, only ones a prior run spawned.

## Reserve vs. terminate: the asymmetry is the safety property

Two different questions get two deliberately different answers:

- **`is_reservable(verdict)`** — `LIVE` or `UNKNOWN`. Deciding to *protect* a working area is generous: a record that exists but cannot be confidently identified still protects its slot, and is never signalled (no termination is attempted against it).
- **`is_terminable(verdict)`** — `LIVE` only. Deciding to *terminate* a process is strict: it requires full identity confirmation.

This means a failure while writing or reading a record degrades into an over-cautious reservation — a slot that sits idle a little longer than strictly necessary — never into destructive action against a process that might still be someone else's live worker. Get the write ordering wrong, hit a transient `ps` failure, anything: the failure mode is always "wait", never "kill the wrong thing".

A third question, **is this a detached survivor** (`is_detached_survivor(record, verdict)` — `record.pgid is not None and verdict is LIVE`), sits above both and is checked first by the boot sweep: a record's own content, not the `ALAN_DETACHED_WORKERS` dial's current value, decides whether a record is a genuinely detached prior-run worker to reserve-for-attach rather than terminate. Keeping the discriminator content-based (not dial-based) is what makes a rollback to `off` safe — see the dial section below.

## Foreign-host and unknown-schema records are deleted outright

`load_all()` classifies each file into `(Path, WorkerRecord | None)`; `None` means unparseable JSON, a non-object payload, a `schema_version` this version of the code doesn't recognise, or a required field of the wrong type. `worker_reaper.reap_and_reserve` removes these outright — it does not attempt to protect or terminate a shape it cannot understand.

Combined with the foreign-host `DEAD` verdict above, this is what makes a restored backup safe regardless of how it was restored: a `~/.alan/state/worker_records/` directory copied in from a different machine, or written by a future schema version this build predates, is inert data that gets swept away on the very first boot rather than something the reaper tries to interpret.

## Termination: per-pid for a pre-detachment record, per-group for a detached survivor

`terminate_pid(pid, *, kill=os.kill, sleep=time.sleep)` is SIGTERM → `SIGTERM_GRACE_S` (5s) grace → re-check liveness → SIGKILL, injectable for tests. This stays the path for a **pre-detachment** record (`pgid is None`) — the pre-detachment spawn arrangement never put the worker in its own process group, so group-signalling it would be fatal to the service itself. `terminate_group(pgid, *, kill=os.killpg, sleep=time.sleep)` mirrors the same SIGTERM-grace-SIGKILL shape for a **detached** record's process group, used by the boot sweep's dial-off path and by attach's duplicate-record cleanup and deadline kill. `guard_no_group_signal(pid)` gates every group-signalling call site: it raises `GroupSignalGuardError` when `os.getpgid(pid) == os.getpgid(0)` (refusing to ever signal the service's own group), and returns cleanly — never raises — when `os.getpgid(pid)` itself raises `ProcessLookupError`, so a process that vanishes between the decision to kill it and the signal falls through to the caller's next step instead of erroring.

One shared `terminate_pid` + `SIGTERM_GRACE_S` serves both `worker_reaper` and `ProcRegistry.terminate`'s no-handle fallback (`alan/_dispatcher_base.py`) — two mirrored SIGTERM-grace-KILL implementations on either side of a layer boundary would drift on the grace constant over time.

## Boot sweep ordering (inverted: survivors are protected, not killed)

On startup, `worker_reaper.reap_and_reserve(queue)` runs — after the slot pools and the job queue are constructed — and **before** the job reconciler runs. For each record, `_reap_one` checks in this order: unparseable → removed; `is_detached_survivor` (non-null `pgid` + `LIVE`) → reserved for attach, `adoptable=True`, **never terminated**; else `is_terminable` (`LIVE`, `pgid is None`) → `terminate_pid` + `remove_record`, exactly the pre-detachment behaviour; else `is_reservable` (`UNKNOWN`) → reserved with `adoptable=(record.pgid is not None)`; else → removed. A record that reaches `is_reservable` with `pgid is None` is exactly this last case: it lands non-adoptable, so it can be adopted by no one (see `slot_pool.md`'s "Reservations" section for why that also means it can never enter the TTL re-arm loop below). `pgid is None` here does not by itself mean `stamp_started` never ran: `stamp_started` writes `pid` first, and `stamp_detached` writes `pgid` in a later, separate atomic update (see "Write ordering and atomicity" above), so a crash between the two — or a probe-time `ps` read that fails transiently — can reach this branch with a live, PID-stamped worker. Landing non-adoptable is the conservative default either way: it is not a claim that the record is dead, only that it cannot be confidently redeemed, the same asymmetry `is_reservable`/`is_terminable` already draws above. `alan/routes/infra.py`'s `lifespan()` then calls `reset_all(reserved, clean=clean_allowed)` on every slot pool — see the reservations section of [slot_pool.md](slot_pool.md) for how that map now splits into two capabilities keyed on `Reservation.adoptable`: every entry excludes its slot from the same reset pass's clean batch, with no window where a to-be-cleaned area could be claimed mid-clean, but only an `adoptable=True` entry also withholds its slot from `_free` pending adoption. A reservation whose record still probes live **re-arms instead of expiring** once its TTL elapses (attach arrives through job dispatch, which can queue behind fleet concurrency, so the boot-to-attach window isn't bounded by the restart itself) — this re-arm loop is only ever reachable for an adoptable (redeemable) reservation in the first place.

**The `queue.list_running()` cross-check now overrides the boot clean, reversing an earlier design.** This documentation previously stated that the reaper's cross-check against `queue.list_running()` was defence-in-depth logging only and never overrode the probe verdict. That is no longer true, and deliberately so: `worker_reaper.boot_clean_allowed(queue)` runs right after `reap_and_reserve`, reads `queue.list_running()` again, and returns `False` — refusing the startup git-clean pass across every slot pool for this boot — whenever any job reads RUNNING, or the read itself raises. The reason is a lifetime mismatch the record-based reservation above cannot close on its own: a worker record's lifetime is the worker subprocess it was written for (written at spawn, deleted when that subprocess ends — see "Write ordering and atomicity" above), but the clone hold a multi-role team run actually needs spans claim → dependency warm-up → every gap between one role's worker ending and the next role's worker starting → push → PR creation → handover write. During every one of those gaps there is no worker subprocess alive to have written a record, so an absent record is not evidence that nothing holds the clone — it is simply the record-based mechanism's blind spot. A RUNNING row in the job queue is independent evidence spanning exactly that blind spot, so it is treated as sufficient reason to hold, overriding the probe verdict for the boot clean specifically. This changes nothing about reservation or termination semantics above — `is_reservable`/`is_terminable` and their probe-verdict inputs are exactly as documented — and it changes nothing about correctness even when it is wrong: a suppressed boot clean only delays `_clean_slot` until that slot's next `lease()`, which always cleans unconditionally before use (see the "startup clean is a pre-warm" note in [slot_pool.md](slot_pool.md)). The suppression is deliberately accepted **indefinitely**, even against a queue row that turns out to be permanently stale — job reconciliation (which would clear such a row) runs only after this reset, see `_run_job_reconciler` in `alan/routes/infra.py` — because the failure mode of over-suppressing is one extra un-pre-warmed boot, never data loss.

Before the sweep, `alan/routes/infra.py` calls `detached_mode.log_resolved_mode()` once (the single boot log line naming the resolved mode and why). When the resolved mode is `off`, it also calls `worker_reaper.terminate_all_detached()` **before** `reap_and_reserve` — this walks every record with a non-null `pgid` and `terminate_group`s it, one log line per kill, then lets the normal sweep pass clean up. Off therefore means "spawn attached from now on **and** terminate surviving detached workers by process group at boot" — never "skip reconciliation" and never "reserve without an owner". The discriminator that decides whether a record is a detached survivor is the record's own `pgid`, not the dial's current value (see above), so a rollback to `off` cannot misclassify a genuinely detached worker as a pre-detachment one and leave it running unreserved.

## Durable per-clone hold records (`SlotHold`) close the multi-role gap

The `queue.list_running()` cross-check above is pool-wide and coarse: it suppresses the boot clean for *every* slot pool whenever *any* job is RUNNING, which is the right trade-off for a job whose worker is genuinely mid-turn, but it does nothing for the gap between two roles of the same multi-role team — `implementation` finishes, pushes, and hands over; the router enqueues `implementation_fix` as PENDING and, in the same routing pass, marks the finished job COMPLETED (`alan/dispatcher.py`'s `_route_after_handover`). Between that completion and the moment the successor job is actually claimed, `queue.list_running()` is empty, no worker subprocess is alive to have written a `WorkerRecord`, and the in-memory `SlotPool._lease_times` the predecessor held is long gone — a restart landing in that window has no RUNNING row, no worker record, and no live lease to read, yet the clone the predecessor just released still carries its checked-out branch.

`SlotHold` (`alan/worker_records.py`) closes this specific, narrower gap with a **per-clone**, not pool-wide, durable record — one JSON file per workspace at `<state_root()>/slot_holds/<workspace_id>.json`, holding `{workspace_id, slot_path, written_at}`. `alan/teams/_slot_affinity.py`'s `_persist_affinity` — the single choke point both `worktree_iteration` (`implementation`/`implementation_fix`) and verification's grounded checkout already funnel through — writes (and overwrites) this record every time a lease resolves a real slot index, gated by the same `persist_base_ref` flag that already distinguishes the resumable implementation path from verification's read-only checkout: only the former writes a hold, since only the former is the round-trip this record protects. The write happens right alongside the existing `graph.set_slot_index`/`save_workflow` call, so every successful claim across every role of a workspace's affinity chain refreshes it.

`worker_reaper.reap_and_reserve` reads every `SlotHold` at boot, alongside the worker-record sweep, and folds each **fresh** one (`is_slot_hold_fresh`, TTL `HOLD_STALE_TIMEOUT_S` = 8h, mirroring `SlotPool._STALE_LEASE_TIMEOUT_S`) into the same `reserved: Mapping[Path, Reservation]` map `reset_all` already protects from `_clean_slot` — a worker-record-derived reservation for the same path always wins (a hold is never allowed to override real liveness evidence). A hold's own ownership token (`f"hold:{workspace_id}"`) is not, and can never be, a worker session identifier, so a hold is always folded in as `Reservation(token, adoptable=False)`: it can never be adopted by anyone, and — since **this build** — it therefore only ever excludes its slot from the boot clean pass, never from `_free`. Because reservation is per-path (see `slot_pool.md`'s "Why reservation is by resolved slot path"), a hold protects *only* the one slot it names — it cannot broaden protection pool-wide the way an over-reported RUNNING or PENDING queue row could, so it sidesteps the queue's own over-reporting problem entirely rather than needing a second instance of it.

There is deliberately **no explicit release** on normal completion — no code path deletes a `SlotHold` when a workspace's routing chain reaches a terminal state. The TTL is the only cleanup: `reap_and_reserve` unlinks any hold whose file is unparseable or has gone stale on every boot (mirroring the unparseable-worker-record cleanup above), and a hold that is never refreshed again simply stops excluding its slot from the boot clean pass after 8h. This is the same "fail toward the wasted warm boot" trade-off as the pool-wide RUNNING check above, chosen for the same reason: wiring proactive release into every place a workspace's chain can end (done, blocked, escalated, abandoned) is real additional surface in `dispatcher.py`'s routing for a payoff that, since a hold is non-adoptable and never withholds capacity, is now genuinely just **warmth** — skipping one fewer un-pre-warmed boot-clean pass over that one slot — that only ever costs one extra un-pre-warmed boot if skipped. Before this build this framing was false — an unreleased hold withheld the slot from `_free` too, so the cost of skipping proactive release was lost *capacity*, not merely lost warmth; that mis-costing is exactly why the omission previously looked more acceptable than it was. It also directly answers the crash-orphan question a durable record raises that an in-memory one does not: a service killed mid-run leaves its `SlotHold` files on disk with no process left to release them, and without a TTL those would read as held forever and freeze `_clean_slot` on those paths permanently; the 8h expiry is `_STALE_LEASE_TIMEOUT_S`'s exact answer to the same shape of problem, applied here.

The per-clone identifier is the resolved `slot_path` a lease actually claimed, not the persisted `WorkflowDoc.slot_index` alone — a fresh workspace invocation always starts with `slot_index=None` (`workflow.seed_pending_workflow` never copies it forward from a prior team's own invocation), so a successor job's own graph cannot be used to predict which physical slot it will land on before it is claimed. `SlotHold` therefore records the *previous* role's resolved path, keyed by `workspace_id` (stable across every role, unlike `inv_id`), which the successor may or may not reclaim — see "Decisions the plan must make" caveat above about `slot_index` being written inside the hold: it is absent before a first claim, and can point at a slot no future claim in this workspace ever revisits. Both cases degrade safely: an absent hold reserves nothing (no worse than today), and a stale-pointing hold excludes a slot from the boot clean pass a little longer than strictly necessary — never withholding it from a waiting job — the always-safe direction.

## The `ALAN_DETACHED_WORKERS` dial

`alan/detached_mode.py`'s `resolve_detached_mode()` reads a tri-state dial — `auto` (default) follows the environment-level working-area-pool predicate (`ALAN_SLOT_POOL_ROOT` configured ⇒ on; empty ⇒ off, matching `alan.roots.slot_pool_root() is not None`), `on` and `off` are explicit overrides, and an unrecognized value falls back to `auto` with a warning. `alan.teams._worker_record_hook.worker_record()` resolves it once per node spawn and exposes it as `WorkerHooks.journal_stream` — reusing the existing journal-mode spawn parameter rather than adding a second boolean, since detachment and journal streaming turn on together by construction (`alan/claude_cli.py`'s `_stream_subprocess_journal` always passes `start_new_session=True`). Production resolves `on` (the slot pool is configured there); CI, e2e, and local dev/pytest all resolve `off` and keep today's semantics exactly — `ALAN_DETACHED_WORKERS` is classified `EXCEPTED_CONFIG` (ops tuning knob) in `tests/env_var_classification.py`, not a state-isolation root, and is pinned to the literal `"off"` in both `alan.claude_cli._worker_env` (the worker subprocess environment) and `alan/web/e2e/fixtures/server-env.ts` (the e2e server environment) so neither a worker subprocess nor an e2e run can pick up a stray `on` from the ambient environment.

## Attach

`alan/teams/_node_attach.py::attach()` is the fourth branch `alan.teams._base.run_or_resume_node` tries, between the cached-result check and the existing `resume_workflow_node` fallback — precedence is **cached → attach → resume → fresh**. It only runs for a node the reconciler has already flipped to `interrupted` (a captured `claude_session_id`), exactly the precondition `resume_workflow_node` already required, so with the dial off (no detached records ever exist) this branch is a pure no-op and existing behaviour is unchanged.

1. `find_survivor_records(task_id, inv_id, node_id)` — a pure, side-effect-free, newest-first query (sorted by `started_at`) over every record matching the triple with a non-null `pgid`. Returns `[]` when there is no survivor, and `attach()` returns `None` immediately so the caller falls through to `resume_workflow_node` unchanged.
2. **Duplicates.** Any record after the first (newest) is a stale duplicate — from a retried or racing requeue of the same invocation-and-node — and is terminated by group and removed before the primary is touched; this is idempotent against an already-dead group.
3. **State transition.** The primary's node is moved `interrupted → running` via `graph.resume_node()`, the same transition `resume_workflow_node` performs, and `node_started` is re-emitted (`alan.teams._base.emit_node`) so a reconnected UI sees a fresh start-of-node marker rather than nothing.
4. **Re-stream.** `claude_cli_journal.tail_to_result` is driven by a `PidHandle` (a `ProcessHandle` backed by `worker_records.probe()` re-probing the record, rather than a child `Popen` the service owns — the pipe-era `_wait_with_grace` wait path stays unreachable from this path) starting at the record's `journal_offset`/`err_offset`, re-emitting each parsed line through `stream_emitter` exactly like a live run. The two clock domains are seeded independently: the **absolute ceiling** translates the record's wall-clock `deadline_at` into the attaching process's monotonic domain (`mono_now + (record.deadline_at - wall_now) - abs_timeout`, so `deadline_state`'s existing formula needs no change), while the **idle clock** starts fresh at attach-entry time — never from `record.started_at`, which would instantly idle-kill any worker older than the idle window.
5. **Terminal classification.** A terminal `result` event found by `last_result_event` — regardless of whether it arrived before or after a deadline fired, see Kill ownership below — completes the node via `alan.teams._base.complete_node` (the same completion path a live run uses) and writes `attached` to `resume_audit.jsonl`. No terminal event (attach genuinely lost the worker, or any `OSError` surfaced while attaching) reverts the node back to `interrupted` (`graph.mark_interrupted(..., error="attach_lost")`, preserving the captured `claude_session_id`) and writes `attach_lost`; the caller then falls through to `resume_workflow_node` with the session id intact — the ladder is never worse than today's resume-only path.

## Kill ownership

The terminal result event in the journal is authoritative, not the deadline. On deadline expiry, the `kill` callback attach hands to `tail_to_result` (1) re-probes the record's identity — a worker that already finished in the race window is `DEAD`, and the callback returns without signalling anything; (2) passes `guard_no_group_signal`, which refuses to ever touch the service's own group and returns cleanly (not raising) for a pid that has already vanished, falling through to the same next step as a live one; (3) `terminate_group`s the pgid; (4) `tail_to_result`'s own `_deadline_kill_and_reread` then performs exactly one bounded post-kill re-read of the journal file before `attach()` classifies the outcome — so a worker that writes its terminal line in the exact race window between the kill decision and the signal still wins.

**The ordinary-exit path needs the same drain, and did not have it until 2026-08-28.** `tail_to_result`'s loop reads whatever the journal holds, then asks `PidHandle.poll()` whether the worker is still alive. `poll()` is not a cheap flag read — it re-probes the record through `ps` — so between the read and the verdict there is a window of tens of milliseconds, wide open on a loaded box, in which the worker can append its terminal `result` line *and* exit. The loop then observed `DEAD` and broke out **without reading those bytes**, so `last_result_event` returned `None` and step 5 above marked a worker that had finished perfectly as `attach_lost`. The loop even noticed the file had grown (`size > prev_size`) and still did not re-read it. Both sibling paths already did the right thing — the deadline path via `_deadline_kill_and_reread`, and the *spawn* path via `run_journal_pump`'s `reread_tail` after `_wait_with_grace` — so the attach path was the only one missing its post-exit drain. It now performs exactly one `_pump_iteration` after `poll()` reports exit, before computing the resume offset. The 2026-08-25 nightly mutation sweep caught this as a flake in `tests/test_detached_worker_survival.py` (five `progress` events collected, the `result` line missed); `tests/test_claude_cli_journal_attach.py::test_tail_to_result_drains_a_line_written_while_the_exit_was_being_probed` pins it deterministically with a handle that writes the terminal line during the exit probe.

## Event replay is idempotent by design

`alan/events.py`'s `PubSub` is in-process pub/sub with no de-duplication, and the web live view merges node events by node id (`workflowLive.ts`, `~:82`) rather than appending a log — so attach re-emitting a bare `node_started` for a node the UI already has a card for is naturally idempotent (the merge replaces, it doesn't duplicate) and re-streaming already-seen `stream` lines for a reconnected tab is likewise a no-op UI-wise. No defensive de-duplication belongs in `_node_attach.py` or the frontend on top of this — the merge-by-node-id shape already provides it.

## `SingleAgentTeam` has no live caller

`SingleAgentTeam` (`alan/teams/_base.py`) routes its dispatch through `run_or_resume_node` exactly like every other team — it no longer inlines its own cached/interrupted branching. No team registered in `alan.teams.TEAMS` is built on `SingleAgentTeam` today (see `docs/architecture/merge_recovery.md`'s single-engine residual ledger), so this class currently has no live caller in production. It is kept because the `Team` protocol needs a reference single-node implementation and because `run_or_resume_node` itself is exercised through it in tests; recorded here so the gap stops being rediscovered on every audit.

## The queue-row resume contract: cleared on every terminal transition, not just read once

Distinct from the worker-record/`SlotHold` mechanisms above (which answer "does a
process still hold this clone"), the job queue carries its own, narrower resumability
signal on each row: `Job.resume_inv_id`. `alan/queue.py`'s `_FINISH_SQL` — the shared
statement behind both `complete()` and `fail()`, and so every ordinary terminal
transition off `RUNNING` — now clears `resume_inv_id = NULL` as part of that same
update. Before this, a job that had once been requeued for resume via
`requeue_for_resume` but subsequently ran to a clean completion or a genuine failure
kept the stale id on its row indefinitely, so a reader of the table couldn't tell "was
interrupted, still resumable" from "finished (or failed) cleanly, nothing to resume."
`mark_interrupted_and_fail`'s own SQL variants are untouched — the one path that
legitimately needs to *set* a fresh `resume_inv_id` on a terminal-but-interrupted row
still does.

Consumers read this as a property of the **most recent** failed job for a workspace, not
as "any failed job ever had one": `alan/routes/_workspace_detail.py::has_resumable_failed_job`
takes `list_jobs_for_workspace(..., status=JobStatus.FAILED)`'s last (highest-id) row and
reports resumable only when that row both carries a `resume_inv_id` and its team passes
`alan._reconciler_never_started.team_supports_resume` — the same capability helper the
boot-time reconciler already relies on. Both the workspace-detail flag and the
`/resume` endpoint's own dispatch guard in `alan/routes/workspaces.py` now derive from
this one helper, so the affordance a human sees and the request the endpoint will
actually honor can never disagree with each other the way two independently-shaped
queries once could.

## Non-goal: `run_chat_turn` sessions are unrecorded

Interactive chat turns (`alan.claude_cli.run_chat_turn`, `alan/build_chat.py`, `alan/explore_chat.py`) have no job id, no slot lease, and no queue row for the reservation/stop/attach machinery here to bind to — wiring a second hook for them remains unbudgeted scope. This is a deliberate, documented omission, not a silent gap.
