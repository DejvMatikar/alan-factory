# Agent catalogue

**Source:** `alan/agent_catalogue.py` (assembly, notes, summary), `alan/agent_catalogue_models.py` (the response shape), `alan/agent_catalogue_helpers.py` (runtime slots, segment splitting, `ResolvedAgent`, `ResolverGroup`, `to_entry`), `alan/agent_catalogue_flags.py` (flag derivation), `alan/agent_catalogue_node.py` (the shared fleet-node builder, mirroring `alan/teams/_base.py`'s `_stream_node`), the resolver modules — static-pipeline teams (`agent_catalogue_teams*.py`), orchestrated teams (`agent_catalogue_teams_orchestrated.py`), implementation / implementation_fix / verification / the drift backstop (`agent_catalogue_teams_impl*.py`) and everything that is not a fleet node (`agent_catalogue_standalone*.py`: chats, helpers, evals, operator sessions, driver loops, the legacy planning endpoint) — and the route `alan/routes/engines_agents.py`. All catalogue modules sit above `teams` in the import layers (they import team internals directly) and below `routes`. The launch seam it is built on is described in [claude_cli_streaming.md](claude_cli_streaming.md); the per-run counterpart is the `launch` record in [workflow_visibility.md](workflow_visibility.md).

`GET /api/engines/{owner}/{repo}/agents` answers "what exactly does each agent alan starts run with, for this repository?" without anyone reading the code: model, effort, the full system prompt alan appends, the first-user-message template, turn limit, permission mode, stored and effective allowed tools, denied tools, extra directories, session behaviour, working directory, timeouts, environment handling and process priority, one entry per agent. `GET .../agents/summary` is the short form for the engine page entry point (totals by model, effort and kind, plus warning/info/error counts). Both routes are read-only (no `POST`/`PUT`/`DELETE` exists), return the shared `404 {"detail": "engine not found"}` for an unregistered engine (they are rows of `tests/test_engines_require_engine.py`'s collapsed table), and never serialise an environment variable value, secret or token — environment appears by name and category only. The route module is a member of the routes-independence contract and only imports `alan.agent_catalogue`.

## Generated from the launch definitions, not a copy

Every resolver builds its `ResolvedAgent` by calling the **same** builders the run path uses: the team's own `_role_system_prompt` / `_role_overrides` / `build_role_user_text`, `format_build_system_prompt`, `prompt_templates.render_prompt`, and — for the launch itself — `claude_cli.streaming_spec` / `oneshot_spec` / `chat_launch_spec`, `driver_loop_cmd.build_spec` and `operator_launch.operator_spec`. The text those builders return is the prompt shown. Values that exist only at run time (task title and description, dispatch instructions, prior handover, earlier agents' outputs and the random nonce that fences each of them (`ROLE_OUTPUT_NONCE`, passed to `build_role_user_text(..., nonce=...)` so the fence markers in the first-user-message template keep the nonce open), a checkout path, the adaptive turn budget, an orchestrator-chosen worker role, the project-doc pointer) are passed to the builders as `runtime_slot(NAME, "what gets inserted")` sentinels; `agent_catalogue_helpers.segments_from_text` then splits the result into `PromptSegmentOut`s: `text` segments, labelled `placeholder` segments that carry the description, and `shared=True` text segments for the blocks several agents share (terseness, untrusted-content notice, confidence reporting, UX lens, headless-execution tail, no-tools tail, the verifier/merge-gate safety clauses, …; a resolver can add its own through `ResolvedAgent.extra_shared_blocks`). Agents that run with tools always end in an optional `PROJECT_DOC_BLOCK` placeholder because the project-doc pointer depends on the workspace. Run-time directory arguments appear as `{{NAME}}` in `add_dirs`, and a directory a launch adds only in some cases (the brief-refine source-conversation workspace, the operator's docs folder for another repository) is listed in `conditional_add_dirs` with its condition instead of being guessed.

Page-level notes (`AgentCatalogue.notes`) say that every text is appended to Claude Code's own built-in system prompt (which is not reproduced) and name — without reading or showing their contents — the things every agent inherits from Claude Code on the machine: user-level settings, the repository guidance file Claude Code loads from the working directory, user-level permissions, hooks, MCP servers and plugins.

## Entry shape and the three source kinds

`AgentEntry` carries `id` (`AgentKey.id`), `name`, `kind` (`team_role`, `chat`, `background_helper`, `operator_launched`), `tags` (`eval`, `driver_loop`, `legacy`, `consultant`, `template`), `scope` (`repo` when the prompt or model depends on the viewed repository's engine config, `machine` when identical for every repo, `default_engine` when it always uses the default/registered engine), `when_runs`, `model` and `effort`, `prompt` and `user_message` segments, `prompt_overridden`, `turn_limit` (static cap, adaptive-budget behaviour), `permission_mode`, `tools` (`stored` / `effective` / `denied`), `add_dirs` (plus `conditional_add_dirs`), `session`, `working_directory`, `timeouts`, `environment` (name and category only, with `environment_note`), `process` and `flags`. Orchestrated-team worker roles chosen at run time all share one `worker` entry (`agent_key.canonical_team_role`); `legacy_planning/<role>` and `driver_loop/<name>` keys are built by `agent_key.legacy_planning` / `agent_key.driver_loop`. A resolver failure never blanks the page: `agent_catalogue.resolve_all` isolates each `ResolverGroup`, logs the exception, and returns an entry with `error` set for it; `agent_catalogue.build_catalogue` isolates each resolved agent's entry construction the same way (one agent that cannot be turned into an entry becomes its own `error` entry) and reports a failing unread-role check as an `other_mismatch` catalogue flag. `runtime_slot` registrations are guarded by a lock because resolvers run in the threadpool, and a slot name declared twice with different descriptions raises.

`model` and `effort` are `ValueOut`s: the value the CLI actually receives (`"CLI default"` shown explicitly, with source `cli_default`, whenever alan passes none — for example haiku's effort, or a driver loop without a `model`) and the declared source: **`engine_role`** (the run path reads `cfg.roles[...]`, named in the detail), **`builtin`** (a constant in code decides) or **`cli_default`**. The effort alan derives from the model (`launch_spec.effort_for_model`) is `builtin`. A saved prompt override is applied by `prompt_templates.render_prompt` inside the same builder the run path calls, so the displayed prompt *is* the overridden one and the entry is marked `prompt_overridden`. Nothing in the catalogue can edit a model, effort, prompt or setting; the prompt-override backend (endpoints, history, storage) is untouched.

## Flags — shown, never fixed

`alan/agent_catalogue_flags.py` derives flags from the resolved launch and the viewed engine config; each is a follow-up, not something this change corrects:

- `unread_stored_role` (page level): a role stored in `cfg.roles` that no agent reads for its model or effort — today `remediator` and `failure_scanner` on the default engine. Follow-up: remove the unused stored roles.
- `ignores_engine_roles`: the agent's model is `builtin` although an engine role of the same (or hinted) name exists; `info` when the values are equal, `warn` when they differ. Today every orchestrated-team agent, the architecture `judge`, and any other agent that copied its model from the default engine's roles at import time. Follow-up: make every team honour the engine's roles.
- `ignores_engine_effort`: the engine role carries an effort but the agent starts with another one (or the CLI default). Follow-up: make every team honour the engine's effort.
- `legacy_planning_endpoint`: the six `legacy_planning/<role>` entries — `implementation_plan.run_team` has no caller in the app and runs every role on the one-shot default model (`sonnet`) regardless of `Role.model` (`model_mismatch` is raised alongside for the opus roles). Follow-up: delete the legacy standalone planning endpoint.
- `model_mismatch` / `effort_mismatch` / `other_mismatch`: any other configured-vs-effective difference a resolver declares — the implementation drift backstop, which resumes the implementer session with the module's built-in prompt, model and effort instead of the engine's `implementer` role; orchestrated-team agents, which have no working directory and so run in alan's own checkout and read alan's files when the viewed repository is not alan (one warning per agent, only for a non-default repository); `maintenance/ci_dependency_auditor` when its prompt names a pre-approved `Bash(gh run list:*)` grant that the engine's tool lists do not contain; and `brief_refine`'s correction re-ask, which resumes with the bare role prompt (without the terseness and untrusted-content blocks) unlike every other static team.

## Completeness is enforced

`tests/test_agent_catalogue_parity.py` (helpers in `tests/agent_catalogue_parity*.py`) fails CI when:

1. a production call of `run_agent` / `run_agent_streaming` / `run_chat_turn` in `alan/` omits `agent=` or passes the constant `None` (an AST scan; the scanner is itself tested against a synthetic tree), or an `AgentKey` constant exists that is not enumerated in `agent_key.STATIC_KEYS`;
2. an `AgentKey` that production can produce has no catalogue entry, or two entries share a key: the expected set is derived independently — static keys, every `CONSULTANTS` entry, every operator `Scope`, `implementation_plan.ROLES`, the driver-loop registry (or its single `template` entry when the registry is empty) and, for every registered team, the roles its team object really launches; a new team must be classified or the test fails;
3. the catalogue disagrees with a real launch: for every entry a **driver** (`tests/agent_catalogue_parity_drivers_*.py`) runs the real production path — `team.run()`, `_chat_router.do_turn`, `collision._call_model`, `driver_loop_runs.spawn_run`, `operator_launch.*_plan`, … — with only the subprocess layer stubbed and `launch_spec.to_argv` spied, and the captured `LaunchSpec` must equal the resolved one field by field (model, effort, output format, max turns, permission mode, requested and effective tools, denied tools, add-dirs, session mode, timeouts, fleet, detached, priority, environment entries), the template regex built from the entry's prompt segments (`template_regex`: text segments escaped, placeholders `(?s:.*)`) must `fullmatch` the appended system prompt actually captured, and the first-user-message template must fullmatch the text sent on stdin. For the `operator_launched` and `driver_loop` entries the spied spec comes from `operator_launch.operator_spec` / `driver_loop_cmd.build_spec` — the very builders the catalogue calls — so for those two kinds the check proves the entry matches the builder the launch path uses and its argv; it does not inspect the process-start call (`Popen` or the tmux session) for its working directory or environment. The operator session's environment is the driver-loop allow-list plus `TERM`, which `operator_tmux.session_env` sets and `operator_launch.operator_spec` lists as a `fixed_override` entry;
4. a declared model/effort source is wrong — the **sentinel-mutation proof** reruns every driver with `cfg.roles[<role>]` replaced by sentinel values: an `engine_role` source must make both the real launch and the catalogue follow the sentinel, a `builtin`/`cli_default` source must leave the real launch unchanged (an effort that is derived from the model — `launch_spec.effort_for_model` — follows a model that follows the role, and nothing else).

The comparison runs for the default and a customised engine (changed `implementer`/`judge`/`diff_reviewer` roles) against both an empty and a populated driver-loop registry, and `tests/test_agent_catalogue_parity_bites.py` proves the gate itself bites: a drifted model, effort, turn limit, permission mode, tool grant, prompt template or user-message template, an agent that never launches, a missing driver and a source declaration that lies each produce a failure. The `driver_loop/template` entry describes no real launch and is the only exemption from the driver requirement.

Adding an agent therefore means: pass `agent=` at its launch, add a resolver, add a driver. Each is enforced by one of the checks above.

## Out of scope

The frontend (engine page entry point, the searchable catalogue screen, the run view), removing the prompt-overrides UI, deleting the legacy planning endpoint, making all teams honour engine roles/effort, and removing unread roles are separate work items. Secret values and environment values are never displayed; Claude Code's machine-local settings are named, never read.
