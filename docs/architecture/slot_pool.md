# Slot pool

`alan/slot_pool.py` — bounded pool of independent git clones used as isolation substrates for implementation workers.

## Motivation

The original approach used `git worktree add` from the single repo checkout. Worktrees share the `.git` object store, ref namespace, and index, so two concurrent workers on the same repo can corrupt each other's index or produce confusing `git diff` output that leaks refs from sibling branches.

The slot pool replaces worktrees with **N fully independent git clones** (own `.git/`, own object store, own index). Workers operate in their own clone; there is no shared mutable git state.

## Key env vars

| Var | Purpose |
|---|---|
| `ALAN_SLOT_POOL_ROOT` | Absolute path to the directory that holds `slot_0 … slot_{N-1}` for the **default engine's** pool, and (see "Per-engine keyed pools" below) the parent directory under which every other registered engine gets its own `<sanitized-slug>/slot_0 … slot_{N-1}` subtree. Unset → all pools disabled (worktree fallback) for every engine. |
| `ALAN_SLOT_REPO_ROOT` | Clone source passed verbatim to `git clone` **for the default engine's pool only**: a **GitHub URL** (`https://…` / `git@…` / `ssh://…`) **or** a local path. Unset → auto-detected via `git rev-parse --show-toplevel` (a local path). Carried as a `str`, never a `Path`, because `pathlib.Path` collapses `https://` → `https:/`. Secondary engines never read this var — their clone source is derived from their own `EngineConfig.repo` (see below). |
| `ALAN_SLOT_UV_CACHE` | Isolation override for the `UV_CACHE_DIR` `cache_env` entry (test/CI redirect only — see `engine_config.md`'s "Stack cache configuration"). Unset → `~/.alan/cache/uv` (or `<ALAN_STATE_ROOT>/../cache/uv` when `ALAN_STATE_ROOT` is set). Shared across every engine's pool that declares `UV_CACHE_DIR` in its `cache_env`. |
| `ALAN_SLOT_NPM_CACHE` | Isolation override for the `npm_config_cache` `cache_env` entry, same mechanism as above. Unset → `~/.alan/cache/npm` (or the `ALAN_STATE_ROOT`-derived equivalent). Shared across every engine's pool that declares `npm_config_cache` in its `cache_env`. |

## Lifecycle

### Startup (`pool.reset_all()`)

Called once from `_create_slot_pool()` during `lifespan()`, before the dispatcher starts. For each slot:

- If the slot directory already exists and is a valid git clone (`is_git_clone` checks for `.git/` being a **directory**, not a worktree `.git` file), run `git reset --hard` + `git clean -fd` (NOT `-fdx` — preserves `.venv` so `uv sync` warm-boot is fast; `node_modules/` is also preserved but `npm ci` deletes and rebuilds it anyway, so speed there comes from the shared `npm_config_cache`). HEAD is left wherever it was; it is hard-reset to `origin/main` on the next `lease()` call.
- If the slot does not exist or is not a clone, it is left untouched — the slot is initialised lazily on the first `lease()` call via `git clone` followed by that **pool's own** `warmup_commands` (see "Generic warmup" below — no longer hardcoded to `uv sync` + `npm ci`).
- Mark all slots as free.

Every keyed **boot-time** pool built by `_create_keyed_slot_pools()` gets the identical treatment synchronously, in-line, before `lifespan()` proceeds to construct the `Dispatcher` — `reset_all()` then `mark_warm()`, in that order, for each engine's pool. A pool constructed at runtime (see "Runtime lifecycle" below) instead warms **asynchronously** in a background thread: the boot path can afford to block server startup on a git-clean pass over a handful of engines, but a `POST /api/engines` request must return promptly, so `register_pool` inserts the pool into the dispatch-visible dict synchronously and defers `reset_all()`/`mark_warm()` to a daemon thread. Both paths converge on the same `warm` bit — see "Runtime lifecycle" below for why dispatch correctness never depends on it.

### Runtime lifecycle (`Dispatcher.register_pool` / `Dispatcher.dispose_pool`)

Before R1.3, every keyed pool was built once at boot in `_create_keyed_slot_pools()` and handed to `Dispatcher.__init__` — there was no way to add or remove a pool while the process was running. `Dispatcher` now accepts an optional `pool_factory: Callable[[EngineConfig], SlotPool] | None` (built by `alan.routes.infra._build_pool_factory(alan.roots.slot_pool_root())`, `None` when `ALAN_SLOT_POOL_ROOT` is unset) and exposes two runtime mutators, both guarded by `Dispatcher._slot_pools_lock` (a plain `threading.Lock`, distinct from any individual `SlotPool`'s own `_cond`):

- **`register_pool(cfg)`** — called by `POST /api/engines` (`create_engine`) and by `PATCH /api/engines/{owner}/{repo}` (`update_engine`, only when `pool_size` changed). Builds the pool via `pool_factory(cfg)` (a no-op returning immediately if `pool_factory is None` — e.g. no `ALAN_SLOT_POOL_ROOT`), inserts it into `_slot_pools_by_engine[cfg.repo.slug]` **synchronously** under `_slot_pools_lock`, then spawns a daemon thread running `reset_all()` + `mark_warm()`. **Guardrail: the pool is present-in-dict, and therefore dispatch-eligible, the instant `register_pool` returns** — `SlotPool.__init__` is zero-I/O and `lease()` lazy-clones on first claim (see "Startup" above), so there is no unsafe window between "registered" and "usable". `warm` is observable state only; nothing in `_pool_for_workspace` or `SlotPool.lease` ever branches on it.
- **`dispose_pool(slug)`** — called by `DELETE /api/engines/{owner}/{repo}` (`delete_engine`) and by `update_engine` when `pool_size` changed (dispose-before-persist, then `register_pool` with the new size — see `engine_config.md`). Three-phase, matching the concurrency-seam invariant pinned in `dispatcher.py`:
  1. `pool.begin_dispose()` — under the pool's own `_cond`, raises `PoolBusyError` if any lease is currently held (`free_count < size`) and otherwise sets `pool._quiescing = True`. Mutates nothing on refusal — the pool stays fully registered and leaseable.
  2. Dict-removal: `_slot_pools_by_engine.pop(slug, None)` under `_slot_pools_lock`, **between** `begin_dispose` and `finish_dispose` — a workspace dispatch racing in this exact window hits `Dispatcher._pool_for_workspace`'s fail-closed guard (`NoPoolForEngineError`, pool absent from the dict) rather than a pool that is present but silently refusing every claim.
  3. `pool.finish_dispose()` — `shutil.rmtree(root, ignore_errors=True)`, then verifies the directory is actually gone, raising `PoolDisposeIncompleteError` if not (a busy file descriptor can make `rmtree` partially fail; the caller must not report success on a half-reclaimed disk).
  `dispose_pool` is a no-op if `slug` is already absent from the dict (an engine that was never pooled, or already disposed) — deletion must succeed idempotently.

  A pool's own `_claim`/`_claim_preferred_under_lock` also check `_quiescing` as their first action (raising `PoolBusyError`) — a second, pool-level layer of the same invariant, defensive against any caller that holds a direct `SlotPool` reference obtained before dict-removal.

- **`pool_states()`** — returns `dict[slug, PoolState]` for every keyed pool plus the default pool (keyed by the live default engine's slug), each built via `SlotPool.snapshot(slug)`. Backs the read-only `GET /api/engines/{owner}/{repo}/pool` route (`alan/routes/engines.py`); the SSE push of this same shape is R1.7, not built here.

### Observable state: `warm`, `disk_usage()`, `PoolState`, `snapshot()`

- **`warm: bool`** (property, backed by `_warm` under `_cond`) — `True` once `reset_all()` + `mark_warm()` have completed for this pool, whether at boot (synchronous) or at runtime (background thread after `register_pool`). Purely observable: no dispatch-path code ever reads it to decide whether a lease may proceed (see Guardrail note above — presence in `_slot_pools_by_engine` is the only thing that matters).
- **`disk_usage() -> int`** — sum of `st_size` over every file under the pool's root (`0` if the root doesn't exist yet). Uncached by design — call sites that need this on a hot path (there are none yet) should cache themselves; R1.3 is a read-only snapshot surface, not a metrics pipeline.
- **`PoolState`** (frozen dataclass: `slug`, `size`, `free_count`, `leased_count`, `warm`, `quiescing`, `disk_usage_bytes`) — deliberately **excludes the filesystem root path**; `alan/routes/engines.py`'s `PoolStateResponse` mirrors this shape field-for-field so the HTTP response never leaks a local path.
- **`snapshot(slug) -> PoolState`** — reads `free_count`/`warm`/`quiescing` under `_cond` (a single atomic read of the three), then computes `disk_usage()` outside the lock (pure filesystem I/O, doesn't touch `_free`/`_lease_times`).

### Leasing (`pool.lease(task_id, inv_id, *, existing_branch, preferred_idx, resume_base_ref)`)

Context manager:

1. `_claim(preferred_idx)` — blocks on `threading.Condition` until a slot is available; returns `(idx, token)`. When `preferred_idx is None` it pops **any** free slot (`_claim` any-slot loop). When `preferred_idx` is a valid index it waits for **that specific** slot via `_claim_preferred_under_lock` (same 1-second `Condition.wait()` + stale-reclaim loop). An out-of-range `preferred_idx` (e.g. the pool shrank between restarts) logs a WARNING and falls back to any free slot. Records `_lease_times[idx]` via the injected clock's `.monotonic()` reading (see `docs/architecture/clock_seam.md`) so stranded-slot detection can fire.
2. Prepares the branch. The `is_resume` flag is `True` when `preferred_idx is not None and resume_base_ref is not None`:
   - **Fresh run** (`is_resume=False`, `existing_branch=None`) → `_prepare_new_branch`: fetches `origin/main`, hard-resets, creates `teams/<task_id>-<inv_id>`.
   - **Fresh fix iteration** (`is_resume=False`, `existing_branch=<name>`) → `_prepare_existing_branch`: fetches the named branch from `origin`, runs `git checkout -B <branch> origin/<branch>` (hard-reset to the remote tip) then records base as HEAD sha. **Uncommitted local progress is intentionally discarded on non-resume leases.** The worker recovers its conversational state via `claude --resume <session_id>`.
   - **Resume** (`is_resume=True`) → `_prepare_resume`: called when the job is resuming after an interruption on the **same slot** with a known baseline SHA (`resume_base_ref = WorkflowDoc.base_ref_sha`). The prepare logic inverts the discard-on-prepare invariant when committed-but-unpushed work exists:
     1. Compute `branch = existing_branch or f"teams/{task_id}-{inv_id}"`.
     2. `_count_commits_ahead(path, base_sha, branch)` — counts `base_sha..branch` on the **local** branch ref. If the branch ref doesn't exist or has 0 commits ahead, falls back to `_fallback_prepare` (normal fresh prepare).
     3. If commits exist: anchor a local rescue ref at the branch tip via `git branch -f rescue/<safe_task_id>@<inv_id> <branch>` (immutable before any mutation), then fetch from origin, `_clean_slot`, and `git checkout <branch>` (without `-B`, so the branch ref is not reset).
     4. If checkout succeeds → **preserve**: return `(base_sha, branch, n_commits, None)`. The `base_sha` is the original baseline, so `captured_commits` continues to see all commits from the start. The `slot_work_preserved` SSE event is emitted with `n_commits` so the operator sees the activity in the workspace feed.
     5. If checkout fails → **rescue**: the rescue ref is already anchored at the prior tip; fall back to `_fallback_prepare` (fresh start from origin) and return `(fb_base, branch, 0, rescue_ref)`. The `slot_work_rescued` SSE event is emitted so the operator knows the rescue ref name and can inspect the orphaned commits if needed.
   - Preserve info is stored in `pool._preserve_info[idx]` and retrieved by the caller via `pool.get_preserve_info(idx)` to populate `WorktreeHandle.preserved_commits` and `WorktreeHandle.rescued_ref`.
3. Yields `(path, base_ref, branch, idx)` to the caller.
4. On exit (normal or exception): `_release(idx, token)` — clears `_lease_times[idx]`, returns slot to the free set, notifies waiting threads.

### Sticky slot affinity on resume (`preferred_idx` / `WorkflowDoc.slot_index`)

The `claude` CLI stores each conversation transcript **per working directory** at `~/.claude/projects/<munged-cwd>/<session_id>.jsonl`, and `claude --resume <id>` only finds it when run from the **same cwd** (i.e. the same `slot_N`). Because `_claim` is otherwise free to hand out any slot, a job interrupted by a deploy bounce / restart and later resumed would land in a *different* slot than the one that holds its session — the CLI then reports *"no conversation found with session id"* → `ResumeSessionLostError` → the job fails terminally even though the transcript is intact on disk.

To prevent this, both real callers persist the leased slot index into the per-invocation `workflow.yaml` (`WorkflowDoc.slot_index`, schema 1.6) **before the node runs**, via the shared `alan/teams/_slot_affinity.py` helper described below: on a fresh run it records whichever slot was claimed; on resume it reads `graph.slot_index` back and passes it as `preferred_slot` → `implementation_worktree(preferred_slot=...)` → `pool.lease(preferred_idx=...)`, so the resumed worker re-leases the *same* slot. After `reset_all()` at startup every slot is free, so the preferred slot is immediately available. `implementation`, `implementation_fix`, and **`verification`** lease slots; the non-pool worktree path uses a fixed `task_id+inv_id` dir (stable across restart) and leaves `slot_index=None`. There is deliberately **no** fresh-start fallback — if affinity genuinely cannot be honored the failure stays loud rather than silently resuming in the wrong cwd.

The `verification` team does **not** go through `worktree_iteration` — it leases a slot for its **grounded checkout** (`_try_acquire_grounded_checkout` → `leased_with_affinity(existing_branch=<PR branch>)`, whose cwd every verification role reuses via the `_grounded_cwd_var` ContextVar). Before this was wired, verification always left `slot_index=null`, so a restart mid-verification re-leased an arbitrary (usually the lowest-free) slot and lost its `claude` session — the exact `ResumeSessionLostError` above, made near-certain by concurrency (two live verifications occupy higher-index slots, but the un-pinned re-lease grabs `slot_0`). `_try_acquire_grounded_checkout`'s `_grounded_slot_graph(workspace, inv_id)` returns `None` when no pool is active, else loads the invocation graph (or `None` when it fails to load) for `leased_with_affinity` to read `graph.slot_index` from and persist onto. It is deliberately **pin-only** — verification calls `leased_with_affinity` with `persist_base_ref=False` (the default), so `resume_base_ref` is never threaded and `lease` stays `is_resume=False`, checking the PR branch out fresh via `_prepare_existing_branch` (verification is read-only and does not need the implementation resume-git rescue), while `_claim(preferred_idx)` still pins the original slot so `claude --resume` finds the transcript. The leased slot is also stamped onto the `verifier_checkout_ok` audit row. Because `leased_with_affinity`'s `save_workflow` persistence now runs inside its pre-yield body (see "Shared affinity ctxmgr" below), a persistence failure there — not just a branch-lookup or checkout failure — is caught by `_try_acquire_grounded_checkout`'s `except Exception`, audited as `verifier_checkout_failed`, and degrades to `cannot_verify` rather than propagating a loud crash out of `run()`. This is intentional: verification's grounded-checkout failure mode is designed to degrade gracefully whenever *any* part of acquiring or pinning the checkout fails, including its own bookkeeping write, so a transient workspace I/O error surfaces as an actionable `cannot_verify` handover instead of a bare traceback.

### Shared affinity ctxmgr (`alan/teams/_slot_affinity.py`)

`leased_with_affinity(workspace, graph, task_id, inv_id, emit, *, existing_branch=None, persist_base_ref=False, worktree_factory=implementation_worktree)` is the single context manager both real callers (`_pr_handover.worktree_iteration` and `verification._try_acquire_grounded_checkout`) use to lease a worktree pinned to a workflow graph's slot affinity and persist the result. It lives in `alan/teams/`, not `alan/worktree.py` — the import-linter layering forbids the worktree layer from importing `WorkflowGraph`/`TeamEvent`, and both callers already live under `alan/teams/`.

- `graph: WorkflowGraph | None` — `None` takes the no-affinity, no-persist path (e.g. verification's grounded checkout when the invocation graph failed to load): `preferred_slot` and `resume_base_ref` are both `None`, and the post-lease persistence block is skipped entirely.
- `persist_base_ref` folds the impl-only `base_ref_sha` behavior into the same single `save_workflow` call as the slot-index persistence: `True` (used by `worktree_iteration`) threads `graph.doc.base_ref_sha` as `resume_base_ref` and updates it in the save when `base_ref_sha is None or handle.rescued_ref is not None` (preserving the exact pre-existing condition); `False` (the default, used by verification) never threads or updates `base_ref_sha`, matching verification's read-only, always-fresh-checkout contract.
- `worktree_factory` defaults to `alan.worktree.implementation_worktree` but every real call site passes its **own** module-level `implementation_worktree` name explicitly (the one each module imported via `from alan.worktree import implementation_worktree`) — Python resolves that name fresh at call time, so `monkeypatch.setattr(<module>, "implementation_worktree", fake)` in tests keeps working exactly as it did before this ctxmgr existed, with no change to either module's test-patching surface.
- The post-lease persistence block runs `if graph is not None and handle.slot_index is not None:` — identical to the pre-existing per-caller conditions — before calling `workflow_mod.save_workflow`.
- Both yield sites (the re-adoption path and the fresh-lease path) wrap their `yield handle` in `alan/teams/_slot_derived_data.py`'s `per_slot_derived_data(workspace, handle.slot_index)` context manager — see "Per-slot DerivedData" below.

### Blocked-on-preferred-slot visibility (`on_blocked` / `slot_resume_waiting`)

`SlotPool.lease(..., on_blocked: Callable[[], None] | None = None)` threads an optional callback down through `_claim(preferred_idx, on_blocked)` to `_claim_preferred_under_lock(idx, on_blocked)`. Previously, a resumed job whose pinned slot was still held by another worker waited **silently** — the 1-second `Condition.wait()` loop gave no external signal that anything was happening. Now, the first time `_claim_preferred_under_lock` observes its preferred slot is not free, it fires `on_blocked()` exactly once (a `notified` flag guards repeat wait cycles) with `self._cond` **released** — the callback may run arbitrary caller I/O (emitting an SSE event, appending to an audit log) and must not hold the pool's lock while doing so, or it would stall every other thread's `_claim`/`_release` call. A one-shot `logger.warning` fires alongside it, independent of whether a callback was supplied. This is layered purely at the pool level: `SlotPool` never imports `TeamEvent`, so it stays decoupled from the `alan/teams/` event vocabulary.

`leased_with_affinity` is what actually supplies `on_blocked`: it builds a closure over `emit`, `task_id`, `inv_id`, and the resolved `preferred_slot`, and passes it to `worktree_factory(..., on_blocked=...)`, which threads it further through `implementation_worktree` → `_pool_worktree` → `pool.lease`. On fire, it emits `TeamEvent("slot_resume_waiting", {"task_id": ..., "inv_id": ..., "slot_index": str(preferred_slot)})`. Both `worktree_iteration` and `_try_acquire_grounded_checkout` get this visibility for free since both route through `leased_with_affinity`. The non-pool `implementation_worktree` path accepts and ignores `on_blocked` — a plain `git worktree add` has no lease contention to report on.

### Blocked-on-any-slot visibility (`_SLOT_WAIT_WARN_THRESHOLD_S`)

The preferred-slot path above has always had a diagnostic; the ordinary any-slot claim path (`_claim(preferred_idx=None)`, used by every non-resume lease) did not — it blocked in `_await_free_slot_under_lock`'s `Condition.wait()` retry loop with nothing in the log, which is exactly why an hour-long capacity freeze once required a forensic reconstruction to find. `_await_free_slot_under_lock` now measures elapsed wait time on the pool's own injected clock (`self._clock.monotonic()`, never the wall clock — every other timing decision in this module already routes through the same seam, and using the wall clock here would force real sleeps into the test suite) and, the first time elapsed time exceeds `_SLOT_WAIT_WARN_THRESHOLD_S` (60 seconds), logs one `logger.warning` naming the pool root, and the free/size counts, then never logs again for that same wait (a `warned` flag scoped to the call, mirroring the preferred-slot path's `notified` flag).

This is a diagnostic, not a deadline: there is no hard timeout on this loop, deliberately — a claim timeout would convert a capacity problem into a job failure, which is strictly worse than the wait it would be replacing. The threshold exists so the warning doesn't fire on the very first miss: the default pool is sized to dispatcher concurrency, so any blocking there is already anomalous, but a keyed secondary pool is sized to a small constant (`_DEFAULT_SECONDARY_POOL_SIZE = 2`) against the same, much larger, shared dispatcher concurrency — for that pool, briefly blocking on a free slot is routine, and an unconditional first-miss warning would fire constantly and train an operator to ignore it. Logging while still holding `self._cond` is fine, matching the existing precedent elsewhere in this class (e.g. `_reclaim_stale_under_lock`'s warning) — but that precedent does not extend to running a caller-supplied callback under the lock, which is exactly why this path, unlike the preferred-slot path, takes no `on_blocked` callback at all: `_claim`'s any-slot branch has never accepted one, and this diagnostic doesn't add one.

On the frontend, `slot_resume_waiting` is registered in `workflowLive.ts`'s `WORKSPACE_LIFECYCLE_KINDS` (so it reaches `noticeFromEvent`) and in `workspaceNotices.ts`'s `DYNAMIC_HANDLERS` at `warn` severity, rendering "Resumed session waiting for its pinned slot (`<n>`) to free up" in the workspace activity feed — mirroring the existing `slot_work_preserved`/`slot_work_rescued` notice wiring.

### Admission control under host load (`_await_load_under_lock`)

`_claim` runs one more check before either the any-slot or preferred-slot wait loop: `_await_load_under_lock()`, called immediately after `_raise_if_quiescing()` so it applies uniformly to both branches. It reads the pool's optional `load_sampler: Callable[[], float] | None` constructor parameter — `None` by default, which makes the guard fully inert (no sampler call, no wait), matching pre-existing behavior for every `SlotPool(...)` construction in the test suite that never passes one, including tests that run on the very host the guard would trigger on. Production wires both `alan/routes/infra.py` factories (`_create_slot_pool`, `_create_slot_pool_for_engine`) to `alan.fleet_load.read_load1` — `os.getloadavg()[0]`, standard library, no subprocess.

The threshold is `alan.fleet_load.load_threshold()`: `os.cpu_count() or 1` times `FLEET_LOAD_THRESHOLD_MULTIPLIER` (2.0), computed at call time from the live host — never a hardcoded core count. A reading at or below the threshold returns immediately with no logging and no wait. A reading above it logs one one-shot `logger.warning` naming the measured load, the derived threshold, and the core count it came from, then enters a tick loop shaped exactly like `_await_free_slot_under_lock`'s: `self._cond.wait(timeout=_LOAD_TICK_S)` (1 second — never `time.sleep`, since `_claim` holds `self._cond` and sleeping under it would block every other thread's claim and release, not just this one's), followed by `_raise_if_quiescing()`, `_reclaim_stale_under_lock()`, and `_expire_reservations_under_lock()` re-run each tick, identical to the free-slot wait loop — a reservation past its TTL still expires and a stale lease still gets reclaimed while a claim is deferred on load. The loop re-samples load each tick and exits normally the moment a reading clears the threshold.

The deferral is bounded at `_LOAD_DEFER_MAX_S` (60 seconds, timed via the pool's injected clock — the same seam every other timing decision in this module already uses). At the bound, the guard logs a second, distinctly-worded one-shot warning ("admitting claim anyway") and returns normally: the claim proceeds even though load is still above threshold. This is deliberate — load the guard cannot influence (a host already buried by workers that claimed and are now holding hours-long leases) must never be able to stall the pool — so the two log lines are the only way an operator distinguishes a delay that cleared from an admission forced through under load.

The guard never fires `on_blocked`: that callback means "a resumed session is waiting for its own pinned slot to free up" (see "Blocked-on-preferred-slot visibility" above), a different condition from "the host is too loaded to admit any claim right now." Reusing it would either mislabel a load deferral as a resume-wait, or never fire at all since `on_blocked` is threaded only through the preferred-slot branch. This is recorded as a short invariant comment at the call site in `_claim`, under the module's one concurrency-seam exception to the no-comments rule.

This is admission control only, scoped to the front of a claim — it does nothing about load already in flight. `lease()` wraps an entire worker invocation, so a worker that has already claimed and is deep into an hours-long run is invisible to this guard: it can only defer the *next* claim, never influence one already granted.

### Stranded-slot detection

If a worker thread is killed or hangs without releasing its slot, the in-memory `_free` set never gets the index back. On process restart `reset_all()` fully recovers all slots. For within-process hangs (thread alive but stuck), `_claim()` calls `_reclaim_stale_unlocked()` after each 1-second `Condition.wait()` timeout. Any slot whose `_lease_times` entry is older than `_STALE_LEASE_TIMEOUT_S` (8 hours) is reclaimed: the entry is deleted and the index is added back to `_free`. A WARNING is logged. The 8-hour threshold is generous — any `claude` subprocess taking 8+ hours is either hung or finished; the pool should reclaim it rather than block indefinitely.

### Integration with `implementation_worktree()`

`alan/worktree.py` checks `get_active_pool()` first. If a pool is active, it delegates to `_pool_worktree()` which wraps the lease in a `WorktreeHandle`. Callers are source-stable — they see the same `WorktreeHandle(path, base_ref, branch, slot_index, preserved_commits, rescued_ref)` dataclass regardless of pool vs. worktree mode (`slot_index` is the leased pool slot, or `None` on the non-pool worktree path; `preserved_commits`/`rescued_ref` are always 0/None on the non-pool path). `implementation_worktree(..., preferred_slot=..., resume_base_ref=..., on_blocked=...)` threads the resume affinity, the baseline SHA, and the blocked-on-preferred-slot callback down to `pool.lease(preferred_idx=..., resume_base_ref=..., on_blocked=...)` (pool path only — `on_blocked` is accepted and ignored on the non-pool path).

### `base_ref_sha` persistence (`WorkflowDoc`, schema 1.7)

`_pr_handover.worktree_iteration` is the single site that wires the preserve-on-resume feature to the workflow lifecycle:

- **First lease**: after obtaining the handle, if `graph.doc.base_ref_sha is None` (never stored), it calls `graph.set_base_ref_sha(handle.base_ref)` and saves the workflow. This records the starting SHA (origin/main or the fix-iteration HEAD at creation time) so the baseline is known even across service restarts.
- **Normal resume** (`handle.rescued_ref is None`): `base_ref_sha` is left unchanged. The stored SHA is passed back as `resume_base_ref` on the next resume, and `captured_commits` uses it as the lower bound — ensuring all commits from the original start are captured.
- **Rescue resume** (`handle.rescued_ref is not None`): the prior commits are anchored in the rescue ref; the slot has been reset to a fresh baseline. `set_base_ref_sha(handle.base_ref)` is called with the new fresh base so the next potential resume uses the correct starting point.
- Both `slot_work_preserved` and `slot_work_rescued` TeamEvents are emitted via the `emit` function (SSE to the ActivityFeed) and appended to `impl_audit.jsonl` for operator visibility.

### ContextVar propagation

`SlotPool` is injected into `Dispatcher.__init__(slot_pool=..., slot_pools_by_engine=...)` and stored on the instance. `_execute(job)` — not `_loop()`'s thread-start preamble — calls `set_active_pool(self._pool_for_workspace(workspace))` once the job's workspace has been read and before the team runs, so the correct pool is selected **per job**, not once per worker thread. This matters because a single persistent worker thread processes many jobs across its lifetime, and (with a second engine co-hosted) consecutive jobs on the same thread can belong to different engines; each must see its own pool. Python `ContextVar` does not auto-propagate across threads, but does persist across sequential calls within the same thread, so setting it at the top of every `_execute` call is both necessary (no auto-propagation) and sufficient (synchronous call stack — no other pool-sensitive code runs between the `set_active_pool` call and the team's `run()`). See "Per-engine keyed pools" below for how `_pool_for_workspace` resolves the pool.

### Verification cwd isolation

`_role_overrides()` is a base-class extension hook on `StaticPipelineTeam` (default: returns `None`, meaning no per-role override). `VerificationTeam._role_overrides()` overrides it to return `WorkerOverrides(cwd=_grounded_cwd_var.get() or workspace.path)` for every role: the grounded PR checkout when one was acquired (see `implementation_pipeline.md`), falling back to the workspace directory — never the server's working directory. The fallback `git diff main...HEAD` prompt instruction has been removed — the diff-reviewer must use `gh pr diff <n>` from the inbound handover's `pr_number`.

## Generic warmup (`warmup_commands` + `cache_env`, not a hardcoded stack table)

`SlotPool.__init__` takes two optional, independently-defaulted per-engine parameters:

- `warmup_commands: list[list[str]] | None` — defaults to the default engine's own `_ENGINE_DEFAULT.warmup_commands` (`uv sync --locked --extra dev` then `npm --prefix alan/web ci`), reproducing today's behavior for Alan's own pool exactly. When supplied — as every keyed per-engine pool does (see below) — the pool warms a freshly-cloned slot by running **exactly that list**, in order, via `_run_warmup(path, commands, cache_env, forge_target)` → `_run_warmup_command(path, argv, cache_env, forge_target)` for each `argv`.
- `cache_env: dict[str, str] | None` — defaults to the default engine's own `_ENGINE_DEFAULT.cache_env` (`{"UV_CACHE_DIR": "uv", "npm_config_cache": "npm"}`). Every keyed per-engine pool instead gets its own engine's `EngineConfig.cache_env` (`_create_slot_pool_for_engine`, `alan/routes/infra.py`) — a dotnet engine's `{"NUGET_PACKAGES": "nuget"}`, or a Cargo-only engine's empty `{}` (no shared cache substrate declared, so none is injected).

`_run_warmup_command` never indexes into `argv` beyond `argv[0]` (only to detect an `npm … ci …` invocation for the offline-flag carve-out below) and iterates whatever length list it is given — this generalizes what used to be Alan-specific positional unpacking (`warmup_commands[0]` for the uv command, `warmup_commands[1][2]` to pull `--prefix` out of the npm command) that would `IndexError` or silently misbehave for an engine with one command, zero commands, or a differently-shaped list.

Cache-dir injection is **config-driven, not argv-sniffed**: `_warmup_command_env(cache_env, forge_target)` calls `engine_config.resolve_cache_env(cache_env)` — relocated from this module into `engine_config.py` so `claude_cli._worker_env` can reuse the identical resolver for the worker-command reuse seam (see "Worker-command cache reuse" in `engine_config.md`) and so cache configuration lives as engine state, never a hardcoded stack-to-cache table in code. `resolve_cache_env` maps each `cache_env` entry's env-var name to an absolute path anchored under the shared slot cache base (`engine_config._slot_cache_base()`: `<ALAN_STATE_ROOT's parent>/cache`, or `~/.alan/cache` when `ALAN_STATE_ROOT` is unset), honoring the two isolation overrides in the table above for `UV_CACHE_DIR`/`npm_config_cache` specifically — any other `cache_env` key (e.g. `NUGET_PACKAGES`) always anchors on the shared base with no override to register. A failing or missing warmup command (nonzero exit, `FileNotFoundError`, or timeout) is logged at WARNING and does not raise — warmup failures are advisory; see "Safe degradation" in the goal list this build implements (an engine whose local toolchain isn't present on the host still gets a slot, just an unwarmed one, and its authoritative merge gate remains its declared CI checks, never a missing-gate-as-approval).

One semantic (not positional) carve-out survives the generic runner: `_run_warmup_command` calls `_with_npm_ci_offline_flag(argv)` before executing, which appends `--prefer-offline` to any `npm … ci …` command that doesn't already declare it. This preserves the old `_npm_ci`'s always-offline-first behavior for Alan's own `["npm", "--prefix", "alan/web", "ci"]` warmup command (and for any other engine's plain `npm ci`) without hardcoding a position — an engine that already spells out `--prefer-offline` (or a different npm subcommand entirely) is left untouched.

### Warm-up duration measurement (`on_warmup_measured`)

`SlotPool.__init__` also takes an optional `on_warmup_measured: Callable[[float], None] | None`, mirroring the `on_blocked` decoupled-callback pattern already used for slot-affinity visibility (see "Blocked-on-preferred-slot visibility" below). `lease()` times the bootstrap `_init_slot(...)` call (clone + warmup — the one-time-per-slot cost) with the injected clock's `.monotonic()` reading (see `docs/architecture/clock_seam.md`) and, only when the slot did not already exist as a clone, calls `self._on_warmup_measured(elapsed)` inside a private `_safe_measure_warmup` wrapper that swallows and logs any exception the sink raises — a broken measurement sink must never fail slot creation. `alan/routes/infra.py`'s `_create_slot_pool_for_engine` wires this to `engine_registry_store.write_warmup_seconds(config.repo.slug, elapsed)` for every keyed per-engine pool (boot-time and runtime-registered alike); the default engine's own pool (`_create_slot_pool`) does not wire it — this build's warm-up figure is scoped to the secondary/keyed engines the ops console surfaces it for. `GET /api/engines/{owner}/{repo}/pool`'s `warmup_seconds` field reads this figure back from disk (`engine_registry_store.read_warmup_seconds`), not from any in-memory `SlotPool` state, so it survives a service restart.

## Per-engine keyed pools (`alan.routes.infra` / `Dispatcher.slot_pools_by_engine`)

A co-hosted second engine (see `docs/architecture/engine_config.md`) gets its **own** `SlotPool` — its own clones, its own directory subtree, its own warmup — never Alan's. This is wired at three points:

1. **Creation (`alan/routes/infra.py`)**: `_create_keyed_slot_pools(size)` reads `alan.roots.slot_pool_root()` (same `ALAN_SLOT_POOL_ROOT` as the default pool; unset → `{}`, no keyed pools at all) and, for every `EngineConfig` in `engine_config_mod.registered_engines()` **other than** the currently-registered default engine, builds one `SlotPool` via `_create_slot_pool_for_engine(pool_root, size, config)`:

   `registered_engines()` and the `get_registered()` call alongside it are lock-taking accessors: `alan/engine_config.py` guards its module-level `_registry` dict with a single `_registry_lock` (`threading.RLock`), held for every mutation (`register()`) and every read (`get_registered`, `lookup_by_repo`, `lookup_by_slug`, `registered_engines`, `registered_secret_env_names`, and the `_stamp_snapshot`/`_governing_engine_config` reads dispatcher makes at snapshot-stamping time). No module — including this one — ever reads `_registry` directly, so `_create_keyed_slot_pools`'s snapshot of the registry at pool-creation time is race-free against a concurrent `POST /api/engines` registration without this file needing any locking of its own.
   - **Root**: `pool_root / _engine_pool_dirname(config.repo.slug)`, where `_engine_pool_dirname` replaces every character outside `[A-Za-z0-9_.-]` with `_` and appends an 8-hex-char suffix of `sha256(slug)` (so `sprocket-co/sprocket` → `sprocket-co_sprocket-<digest>`). The digest is derived from the *unsanitized* slug, so two engines whose sanitized names would otherwise collide (e.g. owner/repo `a_b`/`c` vs `a`/`b_c`, both naively sanitizing to `a_b_c`) still land in distinct directories. This keeps every engine's `slot_0 … slot_{N-1}` physically isolated from the default pool's `slot_0 … slot_{N-1}` and from every other engine's, even though they all live under the same `ALAN_SLOT_POOL_ROOT`.
   - **Clone source**: `_clone_source_for_engine(config)` → `f"https://github.com/{config.repo.owner}/{config.repo.repo}.git"`, derived from the engine's **own** `EngineConfig.repo` identity — never from `ALAN_SLOT_REPO_ROOT` (that env var feeds only the default pool). This is the same GitHub-HTTPS-clone-source convention documented in "Remote / push" below, generalized per engine so each engine's slots push to and open PRs against *that* engine's repository.
   - **Warmup**: `config.warmup_commands` passed through verbatim (including an empty list, which is a legitimate "no warmup needed" declaration — see "Generic warmup" above; it is never treated as "unset" and back-filled with Alan's uv/npm commands).
   - `pool.reset_all()` then `pool.mark_warm()` run synchronously for every boot-time keyed pool, immediately after `_create_keyed_slot_pools()` builds it and before `lifespan()` proceeds — a no-op reset the first time (no slot directories exist yet), a cleanup on process restart thereafter. A pool registered later at *runtime* (via `POST /api/engines`, see "Runtime lifecycle" above) instead warms asynchronously in a background thread — the boot path can afford to block startup on a handful of engines; a live HTTP request cannot.
   - `lifespan()` calls `_load_engines()` (which runs `_import_legacy_engines_once()` and then the saved-record boot merge that registers every connected engine from the `ALAN_ENGINES_ROOT` store, see `docs/architecture/engine_config.md`) **before** `_create_keyed_slot_pools`, so a freshly-registered second engine's pool exists from the first request onward, not lazily.
2. **Wiring**: `lifespan()` passes `slot_pool=<default pool or None>`, `slot_pools_by_engine=<the dict from _create_keyed_slot_pools, or {} when disabled/no root>`, and `pool_factory=<the closure from _build_pool_factory, or None>` into `Dispatcher.__init__`. `Dispatcher._slot_pools_by_engine` is keyed by `EngineConfig.repo.slug` (e.g. `"sprocket-co/sprocket"`); `_slot_pools_lock` (a plain `threading.Lock`, never held simultaneously with any pool's own `_cond`) guards every read and write of that dict, including runtime `register_pool`/`dispose_pool` calls (see "Runtime lifecycle" above).
3. **Selection (`Dispatcher._pool_for_workspace(ws)`)**: resolves `cfg = governing_engine_config(ws)` (the workspace's pinned-at-first-dispatch engine, see `docs/architecture/engine_config.md`) and looks up `cfg.repo.slug` under `_slot_pools_lock`. The guard is **asymmetric by design** (R1.3 — this is the one thing to get right):
   - Found in `_slot_pools_by_engine` → that keyed pool.
   - Not found, but `cfg.repo.slug` matches the live default engine's slug → `self._slot_pool` (the default pool — identical object and behavior to before this build, satisfying "Alan's own behavior is unchanged"; **may be `None`**, in which case the default engine still falls through to the unpooled worktree substrate exactly as before R1.3 — this branch is never refused).
   - Neither → **raises `NoPoolForEngineError(cfg.repo.slug)`** (a `DispatcherError` subclass carrying `.slug`). `Dispatcher._execute` catches it and fails the job via `_fail_job` before `set_active_pool`/`team.run()` ever execute — so `alan/worktree.py`'s bare-worktree fallback is never reached for a non-default engine. Before R1.3 this branch silently returned `None`, which `set_active_pool(None)` then let `implementation_worktree()` interpret as "no pool active" → a `git worktree add` cut from the **Alan** checkout (`worktree.py:139-151`, wrong repository). A pool-less non-default engine — whether because `ALAN_SLOT_POOL_ROOT` was never set, the keyed pool was never registered, or it was since disposed — is refused, never silently misrouted.

Per-secondary sizing: at boot, `_create_keyed_slot_pools()` sizes each secondary engine's pool at `config.pool_size or _DEFAULT_SECONDARY_POOL_SIZE` (2) — **not** `ALAN_DISPATCHER_CONCURRENCY` — since a co-hosted low-traffic engine rarely needs the same fan-out as Alan's own pool; the same formula (`alan.routes.infra._secondary_pool_size`) governs pools built at runtime via `_build_pool_factory`. The default engine's own pool is unaffected and stays sized at `concurrency`. See `docs/architecture/dispatcher_concurrency.md` for how a `pool_size` below the intra-workspace cap behaves (blocks, does not deadlock).

**Resume / sticky slot affinity is preserved for free.** Slot-index affinity (`WorkflowDoc.slot_index`, see "Sticky slot affinity on resume" above) operates entirely *within* whichever `SlotPool` object is selected. Because `_pool_for_workspace` is a pure function of the workspace's pinned engine (which never changes across a workspace's lifetime), the same workspace resolves to the same `SlotPool` object on every resume — so `preferred_idx` continues to address the correct slot inside the correct engine's pool, exactly as it did before keyed pools existed for the single-pool case.

## Slot-cleaning policy

`_clean_slot(path)` runs before every branch preparation:

```
git reset --hard  # drop staged AND unstaged tracked-file changes
git clean -fd     # remove untracked files and directories
```

`git reset --hard` (not `git restore .`) is deliberate. `git restore .` only rebuilds the worktree *from the index*, so **staged** edits survive — and a crashed or `error_max_turns`-killed worker leaves the slot with staged changes. `_prepare_new_branch` masks this (it follows `_clean_slot` with its own `git reset --hard <base>`), but `_prepare_existing_branch` (used by `implementation_fix` and existing-branch resume) goes straight to `git checkout -B <branch>`, which **aborts** with "Your local changes … would be overwritten by checkout" when staged leftovers conflict with the target branch. A hard reset discards both staged and unstaged tracked changes, so the subsequent checkout always succeeds.

`-fd` is deliberate: **NOT `-fdx`**. The difference:

| Flag | What it removes |
|------|----------------|
| `-fd` | Untracked non-ignored files and directories |
| `-fdx` | All untracked files including gitignored ones (`.venv/`, `node_modules/`, `__pycache__/`) |

Keeping gitignored directories means:
- **`.venv/`** — `uv sync` skips the network on a warm slot; only changed deps are reinstalled.
- **`node_modules/`** — `npm ci` skips the network similarly.
- **`__pycache__/`** — Python mtime-validates bytecache at import time; stale `.pyc` files are auto-recompiled. Keeping them avoids cold-start overhead with no correctness risk.

Shared `UV_CACHE_DIR`, `npm_config_cache`, and (for a dotnet engine) `NUGET_PACKAGES` each point every slot's installs at a single content-addressed cache on disk. Content-addressed caches are immune to cross-slot contamination even if multiple slots use the same cache simultaneously.

**Exception: `DERIVED_DATA_PATH` (the `ios` preset's `cache_env` entry) is not
content-addressed** — it is a folder of mutable build intermediates and an index store that
two concurrent `xcodebuild`/`tuist` invocations can corrupt or race on if they share it. The
sharing argument above simply does not apply, so this one name resolves per-slot instead of
to the shared cache base, for the length of a slot lease — see "Per-slot DerivedData" below.

### Per-slot DerivedData

`alan/teams/_slot_derived_data.py`'s `per_slot_derived_data(workspace, slot_index)` context
manager wraps both yield sites of `leased_with_affinity` (above). It reads the ambient
per-job cache env `Dispatcher._execute` already set via `claude_cli.get_active_cache_env()`
and, only when that value carries `DERIVED_DATA_PATH` and a slot is actually held, overrides
just that one key to `slot-deriveddata/<sanitized-engine-slug>-<sha8>/slot_<N>` — resolved
under `roots.cache_root()` by the same `resolve_cache_env` every other `cache_env` entry
uses — restoring the saved per-job value in a `finally` when the lease ends. The location
depends only on the leasing engine and slot index, so a slot keeps the same location across
leases and service restarts (one cold build per slot, not per run), and two slots — whether
in the same engine or two different ones — never collide. This location sits under the
cache root but outside the pre-existing shared `cache/deriveddata` folder and outside every
slot's own checkout tree, so `disk_usage()`, `reset_all`'s clean pass, `git clean -fd`, and
`dispose_pool`'s `rmtree` never see it. No change was needed to `SlotPool`, `resolve_cache_env`,
or `_CACHE_ISOLATION_OVERRIDES` — the override is applied entirely at the `claude_cli` ambient
cache-env layer, keyed on the `DERIVED_DATA_PATH` name rather than on the `ios` preset label,
so warm-up (which resolves the pool's own `cache_env` directly, never through this override)
and `swift package resolve` are unaffected. See `docs/architecture/engine_config.md`'s "Per-slot
exception: `DERIVED_DATA_PATH`" section and `docs/architecture/engine_presets.md`'s "Per-slot
DerivedData" section for the full contract.

**Existing behaviour, not changed here: verification's host-side scenario runs.** These runs
invoke an iOS-preset engine's own gate script without the `DERIVED_DATA_PATH` variable set — `claude_cli`'s
ambient cache env is not threaded to the scenario-runner subprocess the way it is to the
`claude` CLI's own worker environment. `scripts/gate.sh` (that engine's own repository) then falls back to
`$REPO_ROOT/.build/DerivedData`, inside the leased slot's own checkout — already per-slot by
construction, since each slot is an independent clone. That build output sits inside the slot
tree, where `disk_usage()`'s walk already counts it.

This is a pinned regression-fence invariant, not incidental: `tests/test_slot_pool.py::test_clean_slot_preserves_gitignored_dotnet_build_outputs` proves a dotnet slot's git-ignored `bin/`/`obj/` build outputs survive `_clean_slot`, exactly like `.venv/`/`node_modules/` already did. `tests/test_deploy_cleanup_boundary.py` separately pins that deploy's own cleanup (`.github/workflows/ci-deploy.yml`, `git clean -fdx`) is a distinct, untouched policy — the two cleanup contexts must never be blurred into one.

## Shared caches

`UV_CACHE_DIR` points each slot's uv installs at a single shared content-addressed download cache on disk, so warm `uv sync --locked` in re-used slots skips the network entirely.

`npm_config_cache` is the per-slot npm download cache. Unlike uv, `npm ci` **deletes `node_modules/`** before every install, so the `node_modules/` directory preserved across slot reuse by `git clean -fd` provides no speed benefit — `npm ci` rebuilds it from the shared `npm_config_cache` regardless. The speed-up for Node therefore comes entirely from the shared download cache, not from preserved `node_modules/`.

`NUGET_PACKAGES` (the dotnet preset's `cache_env`) is the equivalent shared download cache for `dotnet restore`/`dotnet build`/`dotnet test`: NuGet reads this variable to relocate its global packages folder, so a warm slot's restore reuses previously-downloaded packages instead of re-fetching them from the network.

This reuse is not warmup-only. `claude_cli._worker_env` threads the same `cache_env` (resolved the same way, via `engine_config.resolve_cache_env`) into the environment of the `claude` subprocess itself — see "Worker-command cache reuse" in `engine_config.md` — so the worker's own gate/verification `Bash` tool calls (`dotnet build`, `dotnet test`, …) inherit the identical cache directory the one-time warmup populated. Without this second seam, only the slot's initial `dotnet restore` would be warm; every subsequent `dotnet build`/`dotnet test` invocation during the run itself would still restore cold — this second seam is what actually makes a dotnet engine's *second run* demonstrably faster, not just its first slot bootstrap.

## Remote / push (clone from GitHub, not the local checkout)

The implementation worker, after committing in its slot, runs `git push -u origin <branch>` (`alan/teams/_pr_push.py:push_branch` — at the time this doc was written it lived at `alan/teams/_pr_branch.py:push_branch`; the H5.1 shrink program's push-reconcile-cluster move relocated it, so that no longer holds) and `gh pr create` (`alan/teams/implementation.py:_open_pr`) from the slot's cwd. Both resolve the GitHub repo from the slot's `origin` remote. `git clone` sets `origin` to the **clone source**, so the source must be the GitHub URL — cloning from a local checkout would make `origin` a filesystem path, the push would land in the local repo instead of GitHub, and `gh pr create` would fail with "no remote points at a GitHub host". This is why `ALAN_SLOT_REPO_ROOT` is set in production to the GitHub HTTPS URL rendered from the checkout's origin (see `docs/architecture/deploy.md`) rather than the local repo path.

`_create_slot_pool` accepts either a URL (`is_remote_url`) or a local git checkout (`is_git_clone`). A local-path source is fine for tests and dev (no PRs created) but is **not** a valid production substrate — only a URL source gives slots a GitHub `origin`. Authentication for the https clone/push is handled by the global `gh auth git-credential` helper in `~/.gitconfig`; no per-slot token is needed.

## Production activation

The pool is **enabled in production**: `deploy/ai.alan.plist` (the tracked template, rendered to `~/Library/LaunchAgents/ai.alan.plist` by `deploy/render_plist.sh` before every deploy — see `docs/architecture/deploy.md`) sets `ALAN_SLOT_POOL_ROOT=__ALAN_HOME__/.alan/slots` (rendered to `~/.alan/slots`) and `ALAN_SLOT_REPO_ROOT=__ALAN_SLOT_REPO_URL__` (rendered from the checkout's origin; caches left at their `~/.alan/cache/{uv,npm}` defaults). On startup `lifespan` calls `_create_slot_pool(concurrency)` (size = `ALAN_DISPATCHER_CONCURRENCY`, default 6), which constructs the `SlotPool` object and runs `pool.reset_all()`. `reset_all()` only cleans clones that **already** exist (`git reset --hard` + `git clean -fd`) and marks all slots free — it does **not** clone. The actual `git clone <url>` for a slot happens lazily on its first `lease()` (see Leasing above), so the cost — a one-time full network clone from GitHub per slot, plus disk growth of ≈ one repo per slot (up to ≈ 6× total) — is incurred the first time each slot is used, not at server startup. Warm `.venv`/`node_modules` then persist across subsequent leases (`git clean -fd`, not `-fdx`). With a pool active, `alan.routes.infra._intra_workspace_cap` raises the intra-workspace fan-out cap to `INTRA_WORKSPACE_CAP_POOLED = 2` (see `docs/architecture/dispatcher_concurrency.md`), so a single workspace's DAG can advance two nodes concurrently, each in its own clone. The cap is tied to the returned `SlotPool` object: `_create_slot_pool` returns `None` (cap stays 1) when `ALAN_SLOT_REPO_ROOT` is missing or is neither a URL nor a local git checkout, so the cap can never rise to 2 without a usable isolation substrate. `_intra_workspace_cap` looks only at the default pool — a keyed second-engine pool does not independently raise the cap for that engine's own workspaces beyond the shared value already in effect.

`lifespan` also calls `_create_keyed_slot_pools(concurrency)` right after `_create_slot_pool`, using the same `ALAN_SLOT_POOL_ROOT`. Every engine registered by the time `lifespan` reaches this point — via the `ALAN_ENGINES_ROOT` persisted store, loaded by `_load_engines()` (see `docs/architecture/engine_config.md`) — gets its own keyed pool under `<ALAN_SLOT_POOL_ROOT>/<sanitized-slug>/`, sized identically to the default pool, cloned lazily from that engine's own GitHub repo, warmed with that engine's own `warmup_commands` — see "Per-engine keyed pools" above.

## Reservations (surviving worker records)

`alan.worker_reaper.reap_and_reserve` (invoked once from `alan/routes/infra.py`'s `lifespan()`, before the job reconciler runs — see [worker_records.md](worker_records.md)) derives a `Mapping[Path, Reservation]` of resolved slot path → `Reservation(token, adoptable)` from two independent sources folded into the same map: worker records that survived a restart and could not be confidently confirmed dead (`token = session_id`), and fresh durable `SlotHold` records (`token = f"hold:{workspace_id}"`) that protect the narrower multi-role-team gap a worker record's own subprocess-bound lifetime cannot see — see [worker_records.md](worker_records.md)'s "Durable per-clone hold records" section. Each pool receives the combined map as an argument (`SlotPool.reset_all(reserved)` / the `reserved=` constructor parameter) — **the pool is queried through, never embedded in**: `SlotPool` has no dependency on `alan.worker_records` or the reaper, it only ever sees the already-resolved path→`Reservation` mapping its caller hands it.

**Reserving a slot grants two capabilities that this build deliberately separates, keyed on `Reservation.adoptable`.** Every entry, adoptable or not, excludes its slot from `reset_all`'s clean pass — there is always some evidence a live working area may sit there, so pre-warm protection is unconditional. Only an `adoptable=True` entry *also* withholds its slot from `_free` pending adoption — that capability is warranted only when the reservation is genuinely redeemable, i.e. some worker record exists whose `session_id` equals the token and whose `pgid` is non-null, which is exactly `SlotPool.adopt`'s own precondition (via `_find_survivor_reservation` in `alan/teams/_slot_affinity.py`) for ever actually being claimed. `alan.worker_reaper._reap_one` computes this with no extra I/O, from information it already has: a detached survivor (non-null `pgid`, confirmed `LIVE`) is `adoptable=True`; a merely-reservable record (`is_reservable`: `LIVE` or `UNKNOWN`) is `adoptable=(record.pgid is not None)`; and a `SlotHold` is always `adoptable=False` — its token is `f"hold:{workspace_id}"`, which is not, and can never be, a worker session identifier, so it could never satisfy `adopt`'s owner-token check regardless of how long it sits. A record that reached `is_reservable` with `pgid is None` is the second, more dangerous unadoptable case, regardless of why the `pgid` is missing: this covers a record that genuinely never reached `stamp_started` (`pid` itself is still `None`), but just as much a live, PID-stamped record whose `pgid` write raced with a crash (`stamp_started` writes `pid`; `stamp_detached` writes `pgid` in a later, separate atomic update) or whose boot-time `ps` read simply failed transiently. Either way the record cannot satisfy `adopt`'s owner-token check, so treating it as non-adoptable is the same conservative default `is_reservable` already applies to any record it cannot confidently confirm dead — never a claim that the worker is dead, only that its slot cannot be redeemed. Before this build it was folded in indistinguishably from a genuine survivor, and because `worker_records.reservation_is_live` returns `True` unconditionally for a `None` pid, its reservation would re-arm forever at every TTL check rather than ever expiring (see "Owner-token adoption and the two release paths" below). Marking it `adoptable=False` here removes it from `_reserved` entirely, so it is not merely never re-armed — the re-arm code path is unreachable for it, because it is never assigned a TTL clock (`_reserved_at`) in the first place.

Internally, `SlotPool` keeps two disjoint maps built by the module-level `_split_reservations(by_idx)`: `_reserved`/`_reserved_at` (both `dict[int, str]`, exactly the shapes that existed before this build) hold only the `adoptable=True` entries and are the only ones `_free`, `adopt`, `adopted_lease`, and the TTL machinery below ever consult; `_clean_excluded` (`dict[int, str]`) holds *every* entry and is the only map `_to_clean_under_lock` consults. A `"hold:"` token, or any other non-adoptable entry, is therefore **not** "treated exactly like any other reservation" — it is not released by the 1-hour reservation TTL because it is never in `_reserved` to begin with, and it never withholds its slot from `_free`. It is released only by `_clean_excluded.clear()` at the end of `reset_all` — see "Startup clean is a pre-warm, not a correctness step" below for why that release point is safe.

### Why reservation is by resolved slot path, not `(slug, idx)`

A `SlotPool` instance doesn't know its own engine slug — `snapshot(slug)` takes the slug as a caller-supplied argument precisely because the pool has no notion of it internally — and per-engine pool directories are hashed (`_engine_pool_dirname`, `alan/routes/infra.py`). The only value both the worker-records layer and a `SlotPool` can independently compute and agree on is the resolved filesystem path (`pool.slot_path(idx)`), so that is the join key. `reset_all` resolves each path in the reservation map against `{self.slot_path(i): i for i in range(self._size)}`. A path outside this pool's own root (a reservation belonging to a different pool, or a different engine) is silently dropped — simply not this pool's concern, and every other keyed pool in the fleet receives the identical combined `reserved` map from `_reset_and_warm_pools`, so a path is routinely "unresolved" here precisely because it resolved somewhere else. A path *under this pool's own root* that still fails to resolve to a valid slot index (out of range, stale slot count after a shrink) is different — that is a genuine anomaly for this pool specifically, not routine cross-pool noise — and is logged at WARNING, scoped by `_is_under_root` so a sibling pool's legitimate reservations never masquerade as a dropped one.

### Reserve-and-reset atomicity

Reserving and resetting happen inside the **same** locked section (`self._cond`) that `reset_all` already used for the lease-vs-clean invariant. `_apply_reserved_under_lock` assigns both `_reserved`/`_reserved_at` (the adoptable subset) and `_clean_excluded` (every entry) together, in that one locked section, before `_to_clean_under_lock` reads either of them — a slot named in `reserved` is pulled out of both `_free` (if adoptable) and the to-clean batch before the lock is released, regardless of which of the two capabilities it carries. There is no window between "reservation computed" and "reservation applied" where a concurrent `_claim()` could grab a slot it shouldn't, and no window where `_clean_slot` could run against it. A separate `reserve()` call issued after `reset_all()` returns would leave exactly that window open — the same race that has already destroyed a live worker's checkout once in production.

`reserved=None` (every pre-existing no-argument caller, and the runtime `register_pool` background-thread reset) deliberately leaves the pool's current reservation state untouched rather than clearing it — see "Lazily built pools" below for why that matters. Only an explicit mapping (including an empty `{}`, as boot-time `reap_and_reserve` always returns) is authoritative over `_reserved`.

### Startup clean is a pre-warm, not a correctness step

`reset_all`'s `clean: bool = True` keyword-only parameter gates only the git-clean batch (`_to_clean_under_lock` plus the `_clean_slot` loop) — it is a completely independent axis from `reserved` above. Passing `clean=False` still runs `_apply_reserved_under_lock` and its `_free` bookkeeping exactly as `clean=True` does; only the actual `git reset --hard` / `git clean -fd` pass over unleased, unreserved slots is skipped.

`alan/routes/infra.py`'s `lifespan()` computes `clean=worker_reaper.boot_clean_allowed(queue)`: `False` whenever any job reads RUNNING in the queue at boot, or the read itself fails — both are treated as "something may still hold a clone" rather than as proof it doesn't (see [worker_records.md](worker_records.md)'s reversed boot-sweep-ordering note for why a record-based reservation alone cannot see this). Skipping the clean in that case is safe precisely because the boot clean was only ever a pre-warm: `_prepare_new_branch`, `_prepare_existing_branch`, and `_prepare_resume` all call `_clean_slot` unconditionally on every `lease()`, before any branch preparation runs, and `-fd` (not `-fdx`) already preserves the ignored dependency directories a warm slot needs (see "Slot-cleaning policy" below). A slot that skips its startup clean simply sits dirty until its own next lease, at which point that lease's own clean makes it correct again — the cost is one dirty clone occupying disk between boot and first use, never a correctness gap.

`reset_all`'s `finally` block clears `_clean_excluded` unconditionally — even on the `clean=False` refused-boot-clean branch, where nothing was cleaned and nothing was withheld either way, so there is nothing unsafe about releasing the exclusion immediately. This is the concrete release event a `Reservation(adoptable=False)` entry (a hold, or a never-stamped record) waits for: its only job was to keep its slot out of *this* `reset_all` call's clean batch, and once that call has run — or been refused — to completion, there is no further work for the exclusion to do. The next `lease()` for that slot cleans it unconditionally anyway (the paragraph above), so nothing is lost by not carrying the exclusion forward to a hypothetical future `reset_all` call that, outside of `_warm_pool`'s single post-`register_pool` reset, does not happen again for the life of the pool.

The suppression is accepted **indefinitely**, even against a queue row that turns out to have been permanently stale — job reconciliation, which would otherwise clear such a row, runs only *after* this reset (`_run_job_reconciler` in `alan/routes/infra.py`), so a stale RUNNING row can suppress the boot clean forever without anything downstream ever correcting it. This is a deliberate, not accidental, one-way ratchet: the failure mode of over-suppressing is an un-pre-warmed boot, while the failure mode of under-suppressing is destroyed work, and this build's stated preference is to always fail toward the wasted warm boot. Every suppression is logged at WARNING by `alan.worker_reaper`, naming the RUNNING job ids (or the read failure) that caused it.

### Lazily built pools cannot claim a reserved area

`_build_pool_factory` (`alan/routes/infra.py`) captures the boot-time reservation map in its closure; `_create_slot_pool_for_engine` threads it into `SlotPool.__init__`'s `reserved=` parameter, which seeds `_reserved`/`_reserved_at`/`_free` purely in memory — no filesystem I/O, preserving `SlotPool.__init__`'s existing zero-I/O contract. This matters for exactly one path: a second engine registered live via `POST /api/engines` *after* boot gets a freshly constructed pool whose background warmup thread then calls `pool.reset_all()` with no arguments (see "Runtime lifecycle" above). Had construction not already seeded `_reserved`, that bare `reset_all()` call — using the `reserved=None` "leave as-is" semantics above — would have nothing to leave as-is, and a slot area named by a still-unconfirmed-dead worker record could be claimed by the newly registered engine's first job. Seeding at construction closes that gap before the pool is ever published to `_slot_pools_by_engine`.

### Owner-token adoption and the two release paths

`adopt(slot_path, owner_token)` hands a reserved slot to the caller only when `owner_token` exactly matches the `session_id` the slot was reserved under — any other token (or a path that isn't currently reserved) raises `SlotReservedError`. This is strict by design: it is the only path in this file that transitions a reserved slot into a live lease, and it must never be satisfiable by a guess. `adopt` ships **inert** in this build — attaching to a surviving worker is explicitly out of scope for this block; it exists now, fully tested, so that the next block's attach path has a primitive that cannot silently regress.

A reservation ends one of two ways:

- **Prompt release** — `release_reservation(slot_path)`, called (by a future caller; also inert today) the moment a stale worker is confirmed terminated, returning the slot to `_free` immediately.
- **TTL backstop** — `_expire_reservations_under_lock()`, wired into the same `Condition.wait()` retry loops as `_reclaim_stale_under_lock()` (both `_claim`'s any-slot loop and `_claim_preferred_under_lock`'s pinned-slot loop), expires any reservation older than `_RESERVATION_TTL_S` (1 hour) whenever a thread is blocked waiting for a slot. Reservations get their own bookkeeping (`_reserved_at`, distinct from `_lease_times`) specifically so this backstop can apply an independent, shorter-scoped timeout than `_STALE_LEASE_TIMEOUT_S` (8 hours) — a reservation is evidence a worker *might* still be running, not evidence one is, so it should not survive as long as an active lease's stale-reclaim window.

  The TTL is not an unconditional deadline: on expiry, `_expire_reservations_under_lock` re-probes the reservation's worker record (`_session_still_live`, via `worker_records.reservation_is_live`) before releasing anything. A record that still probes live re-arms the reservation — `_reserved_at[idx]` resets to now instead of the slot returning to `_free` — so expiry only ever fires against a reservation confirmed dead (or unrecorded). This is what lets a reservation outlive the gap between boot and attach: attach arrives through job dispatch, which can queue behind fleet concurrency, so the boot-to-attach window is not bounded by the TTL above, and a prematurely released working area could otherwise be handed to another job and cleaned out from under a running worker. The probe can shell out to `ps`, so the pool lock is released around it and re-validated (`self._reserved.get(idx) != session_id`) before either re-arming or releasing, guarding against a concurrent `adopt()`/`release_reservation()` changing or removing that same reservation while unlocked — see `is_pid_alive_or_ambiguous` in `worker_records.py` for the matching fail-safe on the attach-side liveness check.

  This entire TTL/re-arm machinery only ever runs against an `adoptable=True` reservation — `_reserved`/`_reserved_at` hold nothing else. `worker_records.reservation_is_live` returns `True` unconditionally for a `None` pid (a record whose `stamp_started` never ran), which before this build meant a never-stamped record's reservation would re-arm every single time its TTL elapsed and never expire — a permanent slot leak for the life of the process, not an hour-long one. Marking that record `adoptable=False` at reap time (see "Reservations" above) removes it from `_reserved` before this loop ever sees it, so the unconditional-`True` behavior of `reservation_is_live` for a `None` pid is now unreachable from here rather than merely rare.

Either way, a released reservation re-enters `_free` **dirty** — exactly like an ordinary lease release. Cleaning is not re-triggered; the next `lease()`'s own `_prepare_*` step already runs `_clean_slot` unconditionally, so re-cleaning here would be redundant I/O on a slot most likely to be claimed again momentarily.

### No ordering hands a reserved slot to the wrong claimant

Because `_claim`/`_claim_preferred_under_lock` never special-case a reserved index — a reserved slot is simply absent from `_free`, exactly like a leased one, until legitimately released — the ordinary claim path can wait for a reservation to end but can never skip it. Combined with `adopt`'s strict token check, this is a property that holds under *any* interleaving of reset, claim, release and adopt across threads, and is covered by a dedicated property-based test (`tests/test_slot_pool_reservation_properties.py`) rather than only by example-based cases.

### Survivor adoption is best-effort, not fatal

`leased_with_affinity` (`alan/teams/_slot_affinity.py`) treats `SlotPool.adopt()` failure as a recoverable bookkeeping problem, never a run-ending one. `_adopt_or_degrade` wraps the `adopted_lease` entry in a `try`/`except SlotReservedError`: on success it hands back the adopted `WorktreeHandle`; on `SlotReservedError` — the reservation's owner token no longer matches (a restart erased the in-memory claim, or a different live worker now holds it) — it closes the partially-entered `ExitStack`, emits `TeamEvent("slot_adoption_lost", {"task_id", "inv_id", "slot_path"})`, and returns `None` rather than letting the exception propagate out of `run()`. The caller falls through to the normal `worktree_factory` lease path with `preferred_slot` forced to `None` (`_resolve_lease_params(..., prefer_slot=False)`) — a non-`None` preferred index would make `_claim_preferred_under_lock` wait for that specific slot up to the full reservation TTL, which defeats the point of degrading onto a fresh one. `resume_base_ref` is unaffected: it still threads through from `graph.doc.base_ref_sha` exactly as it would on a first lease, so an implementation resume still recovers its captured commits on the new slot.

**The adopted branch resolves its base ref from the same persisted anchor, not from the clone's post-commit HEAD.** Before this build, `_adopted_handle` set `WorktreeHandle.base_ref` to `git rev-parse HEAD` in the *already-running* clone — by the time a restart's service adoption reaches this code, that HEAD already includes every commit the worker made before the bounce, so `captured_commits`' `base_ref..HEAD` range came out empty by construction: the push was skipped, the run finalized as having produced nothing, and the real commits sat in the clone until the next lease erased them. `leased_with_affinity` now computes `resume_base_ref = _resume_base_ref(graph, persist_base_ref)` — the same `graph.doc.base_ref_sha` read `_resolve_lease_params` already used for a fresh lease — **once, before** branching on adoption, and threads it into `_adopt_or_degrade` → `_adopted_handle` → `_adopted_base_ref(stored, slot_path, record)`. Resolution is three-way and fail-safe, mirroring the validate-then-fallback idiom `slot_pool.py`'s own `_prepare_resume`/`_count_commits_ahead` already use for the non-adopted resume path:

- `stored is None` (no anchor was ever persisted for this invocation) → falls back to the clone's current HEAD; resolution `"no_stored_anchor"`.
- `stored` is not an ancestor of the clone's current HEAD (checked via `git merge-base --is-ancestor <stored> HEAD`, returncode `!= 0`) → falls back to HEAD; resolution `"ancestor_check_failed"`. Two distinct shapes collapse into this one branch: the sha may be genuinely unresolvable in this clone, or it may have been valid once but is now unreachable because the branch was rebased onto a new upstream tip mid-run — remediation text handed to fix workers routinely instructs exactly that rebase. Both must fall back the same way: using an unresolvable sha reproduces the original empty-range bug with a new cause, and using a rebased-away sha would over-capture commits already on the remote.
- `stored` is a valid ancestor (`rc == 0`) → used as-is; resolution `"stored_anchor"`.

The ancestor check deliberately does **not** reuse `_git_ref` — that helper masks any git failure (non-repo cwd, timeout, detached-HEAD oddities) as the literal string `"HEAD"`, which is a plausible-looking but non-concrete value. Feeding it into the fix team's push anchor would make `_pr_push`'s `_SHA_RE` reject it as non-concrete and convert what should be a data-loss bug into a divergence escalation. `_ancestor_check_rc` instead runs `git merge-base --is-ancestor` directly and returns the raw integer return code (or a `_ANCESTOR_CHECK_ERROR_RC` sentinel of `-1` if the subprocess call itself raises, e.g. a timeout), never a ref string.

All three outcomes are recorded as one JSON line in `slot_adoption_audit.jsonl` under `node_turns_audit_dir()` (`~/.alan/logs/` in production), with `task_id`, `inv_id`, `team`, `slot_path`, `resolution`, `stored_anchor`, `ancestor_rc`, and the `resolved_base_ref` that was actually used — this is the only way to tell "no anchor was ever stored" apart from "the stored anchor failed its ancestor check" after the fact. Neither fallback shape sets `WorktreeHandle.rescued_ref` — that field stays reserved for the pool's own checkout-rescue path (`_prepare_resume`'s rescue branch, above) — so neither one trips `worktree_iteration`'s pre-existing `slot_work_rescued` TeamEvent either; the stale-anchor re-persist signal (`force_refresh_base_ref`) is threaded internally through `_adopt_or_degrade`/`_persist_affinity` instead. No new user-facing `TeamEvent` is added (the frontend's event-name allowlist would silently drop one anyway), so the audit row above is the only after-the-fact trace of which branch ran.

`handle.base_ref` is not just the lower bound for `captured_commits`: it is also the fix team's `push_fix_branch_with_reconcile` `--force-with-lease` expected-remote value, its rebase target on a lease rejection, and the sha printed in the divergence-recovery instructions. Resolving it correctly on the adopted path therefore also fixes push semantics, not just capture — before this build, the adopted anchor was a post-commit local head that could never match the remote's actual state; now it is the branch head at lease time, which is what the remote actually was.

The degrade branch deliberately never calls `release_reservation` on the lost reservation. `release_reservation` has no owner-token check — it unconditionally frees whichever index maps to the given path — so calling it here on the "a different live token now owns this reservation" arm of `adopt()`'s failure would release a **live worker's** slot into `_free`, and the next `lease()`'s `_clean_slot()` would then destroy that worker's in-progress checkout out from under it. The TTL expiry path (`_expire_reservations_under_lock`) is the only safe releaser, because it re-probes `worker_records.reservation_is_live` before releasing and re-arms the reservation if the record still probes live. Leaving `release_reservation` caller-less (it remains fully tested but unused in production code, same as `adopt()` shipped inert before this build) is a deliberate consequence of that asymmetry, not an oversight.

Because the degrade branch swallows `SlotReservedError` entirely, that exception can no longer surface from `leased_with_affinity` itself. What can still surface is `PoolBusyError` from the *fallback* `worktree_factory` lease, if the pool happens to be mid-`dispose_pool` at that exact moment — a second, independent kind of infrastructure trouble. `alan/teams/_recovery_fault.py` names this pair (`RECOVERY_FAULT_TYPES = (SlotReservedError, PoolBusyError)`, `is_recovery_fault(exc)`) as a small classifier shared by any caller of `leased_with_affinity` that needs to distinguish "the substrate is having a bad moment" from "this checkout is genuinely broken." `verification._try_acquire_grounded_checkout` (`alan/teams/_verification_grounding.py`) is the one caller that matters today: its `except Exception` re-raises immediately when `is_recovery_fault(exc)` is true, *before* logging, auditing `verifier_checkout_failed`, or degrading to `cannot_verify` — so a pool-busy blip during checkout propagates as a genuine job failure (recoverable via the normal `_fail_genuine`/resume machinery) instead of verification posting an honest-looking "this run did not review your changes" comment to the PR for what was actually a bookkeeping hiccup. `NoPoolForEngineError` is deliberately absent from `RECOVERY_FAULT_TYPES`: it is raised by `Dispatcher._pool_for_workspace` before `team.run()` is ever called, so it never reaches this `except` block, and even if it did it names a genuinely operator-fixable condition (a disposed or renamed engine pool) rather than a transient one.

## Acquisition-route base refresh (defence-in-depth)

Two acquisition routes never refreshed a slot's local `origin/main` before this build: leasing onto an already-existing branch (`_prepare_existing_branch`, used by `implementation_fix` and existing-branch resume) and adopting a checkout that survived a service restart (`adopted_lease`). A slot can sit idle across many prior leases without ever fetching, so its `origin/main` ref can be arbitrarily far behind the real branch — exactly the staleness `alan/base_ref.py` (see `docs/architecture/drift_gate.md` and `docs/architecture/e2e_testing.md`) exists to correct at the point of use. This section is belt-and-braces on top of that point-of-use resolution, not a substitute for it: every consumer that actually gates on the diff (the changed-e2e selection, the drift-gate backstop) still calls `base_ref.resolve` itself.

`_refresh_base_best_effort(path, forge_target)` runs `git fetch origin main` via the module's own credentialed `_run_git`/`transport_env` (not `alan.base_ref.resolve` — this module already holds a `ForgeTarget` and a credentialed git wrapper, and `base_ref.resolve` is a stdlib-only leaf with no secrets access of its own) and discards the result; a nonzero git exit, a missing `git` binary, or a timed-out fetch are all swallowed (logged at WARNING), never raised. Two call sites:

- **`_prepare_existing_branch`** calls it after the `git checkout -B` succeeds, refreshing the slot's `origin/main` immediately after the branch that will be diffed against it is checked out.
- **`adopted_lease`** calls it after `adopt()` returns, **outside** `self._cond` — `adopt()` holds the pool's condition lock for its whole body, and a 30s network fetch inside it would stall every concurrent `claim`/`release` on every other slot in the pool. This is the longest-idle acquisition route by construction (a restart-surviving checkout may have sat unfetched since before the restart), so it is the route most likely to actually need the refresh.

Both refreshes are best-effort, not load-bearing: a failed refresh here does not fail the lease, and the checkout still resolves its base correctly later through `base_ref.resolve` at each real point of use.

## CI behaviour

CI does not set `ALAN_SLOT_POOL_ROOT` (`tests.yml` sets it to `""`), so `_create_slot_pool()` returns `None`, `_create_keyed_slot_pools()` returns `{}`, `_build_pool_factory(None)` returns `None`, and the dispatcher is constructed with `slot_pool=None, slot_pools_by_engine={}, pool_factory=None`. No pools are ever created for any engine; the cap stays `INTRA_WORKSPACE_CAP = 1`. For the **default** engine, tests/CI continue using the existing worktree substrate exactly as before (scoped to whatever repo the test process itself is running in). For a **non-default** engine, since R1.3 there is no pool-less fallback at all: `_pool_for_workspace` raises `NoPoolForEngineError` and the job fails closed — tests that dispatch a non-default-engine workspace must construct their own `Dispatcher` with an explicit `slot_pools_by_engine` (see `tests/test_dispatcher_slot_pools.py`), not rely on an implicit worktree substrate.
