# Automatic brief refinement (first hop)

Every workspace created with a `team` runs `brief_refine` as its first, automatic, non-optional step, before the requested team ever sees the brief. The step never parks, blocks, escalates, or asks a question — on every path, including every failure path, it hands off to the originally requested team.

## Why

Before this change, a brief got expanded into a flat list of "must be true when done" clauses with no distinction between what the user actually asked for and what an agent invented along the way — yet every clause carried equal power to fail the job. Refinement splits a workspace's acceptance clauses into two buckets: `Meta.requirements` (traceable — user text, a cited source, a standing house rule, or a prior requirement carried forward) and `Meta.assumptions` (system-inferred, visible but non-blocking). Only `Meta.requirements` is read by `alan/acceptance.py`; `Meta.assumptions` never gates completion.

## Wiring: how a workspace gets refined

`POST /api/workspaces` (`alan/routes/workspaces.py`) is the only entry point. When `body.team is not None`:

1. `workspace_mod.create(..., pending_first_hop=body.team)` stamps the *originally requested* team onto `Meta.pending_first_hop` at creation time, before anything is dispatched.
2. `alan/app/workspace_creation.py::should_refine(ws)` — `not workflow_mod.list_invocations(ws)` — is checked. For every workspace reaching this call site it is true by construction (the workspace was just created in the same request), but the predicate exists so the hazard below stays checkable and testable rather than assumed.
3. When refining: the human's `body.instructions`, if any, is persisted via `workspace_mod.set_sticky_instructions` (not threaded into `brief_refine`'s own prompt) so the *originally requested* team receives it once refinement hands off, via the same sticky-instruction composition `alan/sticky_instructions.py` already applies to every auto-routed enqueue. For a target team in `sticky_instructions.NON_CONSUMING_TEAMS` (`pr_merge`, `triage`, `dependency_sweep`, `deploy_verify`), `for_enqueue` deliberately skips sticky composition for the general router-advance path — so `alan/_dispatcher_brief_refine.py::apply` resolves the sticky instruction itself and stamps it directly onto the overriding `RouterDecision.instructions` for exactly those targets, since it is the only caller that ever needs a *first*-dispatch instruction (as opposed to an accumulated, composed one) delivered to a non-consuming team.
4. `alan/routes/_brief_refine_source.py::write_brief_refine_source` best-effort writes the live (pre-archive) prep-chat transcript, if `body.prep_chat_kind`/`body.prep_chat_session_id` are set, to `<ws.path>/brief_refine_source.md` — filtered to `role == "user"` messages only, so an assistant-authored sentence in the transcript can never itself satisfy a `user_text` origin locator check. A missing, unreadable, or absent session writes no file — refinement proceeds normally either way. This lives in `alan/routes/` (not `alan/teams/`) because `alan.teams` sits *below* `alan.prep_chat`/`alan.build_chat`/`alan.explore_chat` in the `pyproject.toml` layers list — a team module may never import a chat-session reader.
5. `dispatch_root_task_or_rollback` gains a `dispatch_as` override: when refining, `body.team` is still resolved and validated exactly as before (`resolve_dispatchable_team` + `assert_team_dispatchable` — so an unknown or internal team still 400s and rolls back the workspace, precisely as if refinement did not exist), but the team actually *dispatched* is `TEAMS["brief_refine"]`, with `instructions=None` (the human's instructions already live on the sticky-instruction side channel).

This is why `brief_refine`'s dispatch bypasses the manual-dispatch machinery deliberately, not by omission — it follows the same "driven directly" precedent as the `decomposer` internal step (`docs/architecture/decomposer.md`), and the hands-off auto-continue allowlist (`alan.teams.AUTO_CONTINUE_TEAMS`) is untouched by this feature; `brief_refine` runs on every project regardless of that dial.

## Registration

`brief_refine` is registered in `TEAMS` and `INTERNAL_ONLY_TEAMS` (`alan/teams/__init__.py`) and mirrored across every engine-config surface that also lists `decomposer`/`dependency_sweep`: `alan/engine_config.py`'s `_DEFAULT_FLOW_POLICY`, `config/engines.d/alan.yaml`, every other connected engine's own `config/engines.d/<repo>.yaml`, `tests/owner/engine_config_default.yaml` — each gets a `brief_refine` entry in `internal_only_teams` and an empty `restricted_predecessors["brief_refine"]` (no team may legitimately hand off *to* it; the only caller is the create-workspace route). It is deliberately **absent** from `_TRANSITION_GRAPH`/`TEAM_TRANSITION_POLICY` and from `alan.teams.AUTO_CONTINUE_TEAMS` and `MANUALLY_DISPATCHABLE_TEAMS` — `tests/test_dispatch.py::test_auto_continue_teams_pre_change_membership_unwidened` pins `AUTO_CONTINUE_TEAMS`'s exact pre-change membership so a future change cannot silently widen it via this feature. `alan.engine_config._TEAM_MIN_POSTURE["brief_refine"] = Posture.propose` (matching `decomposer`) keeps it out of `observe`-posture's admitted set (so `admitted_teams`'s "observe withholds everything" invariant survives) while still being part of the "autonomous admits every registered team" invariant those same tests assert.

Because `brief_refine` never appears in the transition graph, the ordinary router (`alan.router.select_next_team`) cannot resolve a handover whose `from_team` is `brief_refine` — `_resolve_forward` sees an unknown `from_team` and would normally escalate. `alan/_dispatcher_brief_refine.py::apply(ws, handover, decision)`, wired as the very last step of `Dispatcher._apply_router_decision` (immediately after `deploy_wait_gate.apply`), intercepts this: whenever `handover.from_team == "brief_refine"`, it unconditionally replaces whatever decision the router (and every intervening gate) produced with `RouterDecision(kind="enqueue", team=ws.meta.pending_first_hop)` — regardless of what that decision was, so the step can never park, block, or escalate. It sits in the `_dispatcher_*` band of the `pyproject.toml` layers list (immediately after `_dispatcher_resume_outcome`), since it needs `alan.router.RouterDecision` and `alan.workspace.Workspace`, both well below `dispatcher`.

## The worker contract

`alan/teams/brief_refine.py` (`BriefRefineTeam`, a single-role `StaticPipelineTeam`) prompts the worker to read the brief (title, description, prior requirements by id, and an `@`-reference to `brief_refine_source.md` when present) and emit one fenced block:

```yaml brief_refine.yaml
requirements:
  - id: req-abc123def456   # present => a prior clause, kept or lightly reworded
    text: "the exact (possibly reworded) clause text"
  - text: "a NEW clause you are promoting to a requirement"
    origin: user_text        # user_text | cited_source
    locator: "a short verbatim quote from the brief that supports this"
assumptions:
  - "something you inferred but cannot trace to the brief"
```

`alan/teams/_brief_refine_block.py::parse_brief_refine(text, prior_ids)` is the fence parser. It discards the **whole payload** (returns `None`, and the original brief proceeds entirely unchanged) on any structural malformation — missing fence, invalid YAML, wrong shape, a new item (no `id`) missing `origin`/`locator`, or any `origin` label outside the closed vocabulary `ORIGIN_LABELS = {"user_text", "cited_source", "house_rule"}` — and on either surviving invariant guard: a prior id absent from the output's `requirements[].id` union, or a non-empty prior set paired with an empty output `requirements` list. (A third guard — total output item count below the prior count — is not a separate branch: given the id-subset guard already holds, it is mathematically implied and was removed as unreachable dead code rather than kept as an untestable branch.) Anything that isn't a structural or invariant violation resolves per item in `alan/teams/brief_refine.py::merge`.

**Floors and intent, never exact counts.** `_SYSTEM_PROMPT` instructs the refiner to phrase any verification-shaped obligation it promotes to a requirement as a floor or as intent — "at least one negative-control fixture," "negative-control coverage exists" — never as an exact count, since delivering more coverage than what was asked for must never register as a clause failure downstream (a requirement phrased as "add one negative-control fixture" turns a delivery of two fixtures into a violation, and the cheapest way for a fix worker to clear it is to delete one — the exact failure mode this instruction exists to prevent). This is **instructed, not gated**: there is no validation step that rejects a worker-authored clause for carrying a number, because a wording gate would be either too loose to catch the pattern reliably or tight enough to reject a legitimate clause that genuinely needs an exact count (a schema field count, a fixed API response shape). The instruction shapes what the refiner writes; nothing downstream enforces it structurally.

`merge(prior_requirements, payload, source_text)`:

- **`prior_requirements is None`** (the workspace opted out of the requirements gate entirely): `Meta.requirements` is left untouched (stays `None` — `alan.acceptance`'s "`None` = no gate" contract is never flipped on for a workspace that never asked for it); every worker-proposed item, kept or new, is folded into `Meta.assumptions` instead.
- **Otherwise** (a non-empty supplied list, or an empty one), per requirement item:
  - `id` present and matches a prior requirement: **kept or rewritten**. `test_ref`, `status`, and `merged_pr_url` always carry forward verbatim from the prior `Requirement`, and so does its `kind`: `_carry_forward` keeps a clause's kind unchanged, including across a text rewrite, and no later stage chooses a kind. If the text changed, `alan.obligation_direction.direction_preserved(prior.text, new_text)` is checked first — direction ("must" vs "must_not") is classified from the *original* text before any rewrite is considered, never from the candidate. A direction-reversing rewrite is rejected outright (the prior text survives unchanged, audited as `rewrite_direction_reversal_rejected`) rather than accepted or silently dropped — reversing is treated as strictly worse than dropping, and dropping is already forbidden.
  - **Over a non-empty supplied list**, every item that does not match a prior id — `id` absent, or an `id` that matches no prior — is demoted to `Meta.assumptions` whatever its `origin` (quoted brief text or a cited source), audited as `requirement_demoted_supplied_list` with the item's `origin` and `text`. The result therefore contains no clause text other than the supplied clauses (carried forward, possibly reworded) plus the house rules; the curated list is never grown by re-reading the prose, and clauses removed at propose time are not re-minted. The origin check below never runs on this path.
  - `id` absent (a genuinely new item) **and the prior list was empty**: only here does origin resolution run. `house_rule` **never** resolves for a worker-emitted new item — house rules are already unioned unconditionally below, so a worker restating one is redundant, and accepting a valid house-rule id as proof for *any* accompanying `text` would let unrelated worker-invented text ride in disguised as a house rule; an item claiming `origin: house_rule` is always demoted to `Meta.assumptions` regardless of its `locator`. `user_text` resolves iff its `locator` (whitespace/case-normalized) is a literal substring of the workspace's title + description + source-conversation text — no similarity scoring, per the feature's explicit non-goal; `cited_source` resolves iff its `locator` matches an issue/PR/URL shape (`#\d+` or `https?://`) — the citation is never fetched or content-matched, per the same non-goal; obligation-direction classification is the backstop against an unresolvable cited claim reversing meaning. An item that resolves becomes a fresh `Requirement` (id re-derived from its own text, same as any other newly-minted clause — safe only because refinement is the *first* thing that ever touches this workspace, before anything downstream has bound an id or `test_ref` to the old text). An item that fails resolution is demoted into `Meta.assumptions` instead of being dropped.
  - After every item resolves, `alan.house_rules.HOUSE_RULES` is unioned into `Meta.requirements` unconditionally (deduped by content-hash id) — this is what lets house rules "count as requirements without the user having to restate them," and it also guarantees `Meta.requirements` can never end up empty when it is populated at all, even if a worker's entire payload gets demoted to assumptions.

On a **rejected** (malformed) payload, `alan.teams.brief_refine._apply_refinement` still writes an audit row (`brief_refine_rejected`) and returns the workspace's prior requirements/assumptions unchanged — Meta is never touched. On an **accepted** payload, every per-item audit row plus a final `brief_refine_accepted` row is appended to `<logs_root>/brief_refine_audit.jsonl`, and `Meta.requirements`/`Meta.assumptions` are written via `alan.workspace.update_requirements`/`update_assumptions` — chained through the same returned `Workspace`, since both are copy-on-write and calling the second on the pre-first-write reference would silently clobber it. `BriefRefineTeam.run()` always returns a **terminal** `Handover` (`from_team="brief_refine"`, `to_team_suggestions=[]`) carrying `outcome.assumptions` on the handover's existing `assumptions: list[str]` field — the router never needs to resolve `brief_refine`'s own forward edges, because `_dispatcher_brief_refine.apply` always overrides the decision anyway.

If the underlying role pipeline itself raises (a worker/subprocess crash, as opposed to a worker that produced malformed YAML), `BriefRefineTeam.run()` catches it, appends a `brief_refine_pipeline_failed` audit row, and still returns a terminal handover treating the brief as unchanged — the same "hands off on every failure path" guarantee, just one layer earlier. `UsageLimitError` and `ServerErrorRetryable` are re-raised rather than swallowed, so the dispatcher's existing usage-limit pause and server-error backoff/retry handling in `_call_team` still applies to `brief_refine` exactly as it does to every other team.

`alan/teams/_brief_refine_block.py::_invariants_hold` also rejects the whole payload if any non-null requirement id in the output repeats — without this, one prior clause could expand into multiple worker-authored requirements (each bypassing origin validation as a "kept" rewrite of the same id) while still satisfying the id-subset guard.

## House rules and obligation direction (pure leaves)

`alan/house_rules.py` — `HOUSE_RULES: tuple[HouseRule, ...]`, a versioned (`HOUSE_RULES_VERSION`), id-unique, frozen list; each `HouseRule` carries a closed-vocabulary `direction: ObligationDirection`. `alan/obligation_direction.py` — `ObligationDirection = Literal["must", "must_not"]`, `classify(text) -> ObligationDirection` (a negation-marker heuristic: "must not", "should not", "never", "don't", "avoid", a standalone "no", …), and `direction_preserved(original, candidate) -> bool`. Both are pure leaves with zero `alan.*` imports beyond each other (`house_rules` imports `obligation_direction`), placed at the very end of the `pyproject.toml` layers list, directly below `teams` (their only consumer) and in that dependency order.

## Schema

`alan.workspace.Meta` gains two total-with-default fields: `assumptions: list[str] = Field(default_factory=list)` and `pending_first_hop: str | None = None`. Both default such that a `meta.json` written before this change (carrying neither key) still validates unchanged. `Meta.requirements` keeps its existing three-state contract (`None` = no gate, `[]` = declared-but-never-satisfiable, populated = active gate) — refinement's house-rule union is what keeps a populated list from ever being reduced back to `[]`.

## Out of scope (see the original feature spec for the deferred half)

Re-invoking refinement against an already-running workspace is not implemented — it is exactly the path that would silently orphan item identity, since ids are content-hash-derived from text and everything downstream of the first hop already trusts them. The supplied-list rule above keys on the prior list being non-empty when refinement runs, which equals "the create body supplied it" only because refinement never re-runs today; if re-refinement is ever built, previously minted clauses would become permanently supplied, and that design must revisit this rule. Similarity scoring, fetching cited-issue bodies, and the assumptions-checklist UI surface are likewise out of scope for this change.
