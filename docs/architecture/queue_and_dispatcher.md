# Queue + dispatcher

**Source:** `alan/queue.py`, `alan/dispatcher.py`, `alan/workspace_dag.py`, `alan/events.py`

## Queue

SQLite job queue at `~/.alan/queue.db` (override via `ALAN_QUEUE_DB_PATH`).

Atomic claim via `UPDATE … RETURNING` — requires `libsqlite3 >= 3.35`. The dispatcher polls every ~50 ms.

`_CLAIM_SQL` enforces per-workspace serial execution: a job is only claimable when its `task_id` has no other `status='running'` row. This prevents two workers from claiming sequential jobs for the same workspace at the same time.

Job rows carry `triggered_by_invocation_id` so the pre-allocated pending `inv_NNN` (see [workflow_visibility.md](workflow_visibility.md)) can be resolved when the dispatcher picks the job up.

`queue.delete_jobs(task_id)` is used by workspace deletion (see [workspace_api.md](workspace_api.md)).

## Dispatcher

N-worker background thread pool (default `ALAN_DISPATCHER_CONCURRENCY=6` in production, `concurrency=1` in unit tests). Each worker runs the same poll loop, claims one job at a time, calls `team.run(workspace, prior, emit, *, inv_id)`, then post-processes:

1. Persist the returned `Handover` via `handover.save_handover`.
2. Emit `job_completed` SSE event with the artifact path.
3. Increment `revisit_counts[handover.from_team]` on the workspace.
4. Run `router.select_next_team` → `loop_guard.check_loop_guard`.
5. Apply the resulting `RouterDecision`:
   - `enqueue` → `_dispatcher_base.enqueue_with_pending_workflow(queue, pubsub, workspace, team, prior, parent_handover_id=…)` (H5.2: moved from `alan/dispatcher.py` to `alan/_dispatcher_base.py`; `alan.dispatcher` and the route handlers that dispatch manually now import it from there) — pre-allocates the next team's pending `workflow.yaml` and writes the queue row with `triggered_by_invocation_id`. `parent_handover_id` is preserved so the dispatcher can load the prior `Handover` and pass it to `team.run(...)`; on a subtask that prior is the subtask's own handover, never a sibling's (see §Resolving a subtask's prior handover). On the **first enqueue** for a workspace (when `Meta.engine_snapshot is None`), the function also stamps `EngineSnapshot` onto the workspace meta via `_dispatcher_base._governing_engine_config(meta.engine_key)` — resolving `Meta.engine_key` against the registry (`engine_config.lookup_by_slug`), falling back to `get_registered() or default_engine_config()` when `engine_key` is `None` or unresolvable — and pinning `posture`, `transition_graph`, **and** the full resolved `EngineConfig` (`EngineSnapshot.config`) at dispatch time. A later engine-config edit is inert for already-dispatched workspaces; only new workspaces (whose first enqueue happens after the edit) see the updated values. `dispatcher.pinned_engine_config(ws)` (kept on `alan.dispatcher` — `tests/test_posture_routing.py` imports it from there directly) returns the pinned `(posture, transition_graph)` pair — using the same `engine_key`-aware resolution for workspaces created before their first dispatch (or before snapshot support existed at all), so posture admission checks (e.g. `_reject_posture_withheld`) see the named engine's posture even pre-pin.
   - `await_human` → workspace transitions to `AWAITING_INPUT`; in a multi-task workspace the specific subtask's `Task.status` is also set to `TaskStatus.AWAITING_INPUT` and `Task.blocked_handover_id` is stamped with the handover's id (see §Mid-chain escalate/await_human below).
   - `escalate` → workspace transitions to `ESCALATED`; same per-subtask stamp as `await_human` in multi-task workspaces.
   - `done` → `Dispatcher._advance_workspace_dag` delegates to `workspace_dag.advance_workspace_dag` — marks the completed task COMPLETED, runs `injection.plan_injection` if `handover.injected_tasks` is non-empty (see [task_injection.md](task_injection.md)), enqueues ready successors, evaluates requirements, and transitions the workspace to `COMPLETED`/`FAILED` when all tasks are terminal.

On exception during `team.run`, the dispatcher flips `meta.status` to `Status.AWAITING_INPUT` via `_fail_workspace`. The reconciler does the same for jobs interrupted by a restart. `_fail_workspace` swallows and logs any `OSError` from the meta write so a failed dispatch never leaves the workspace stuck at `active`. Multi-task workspaces that exhaust every task path in failure use `Status.FAILED` (see d7 below).

### Park-state clearing on recovery (`Meta.park_reason` / `Meta.blockers`)

`workspace.transition` clears `Meta.park_reason` and `Meta.blockers` whenever the status being **written** is `ACTIVE` or `COMPLETED`, and retains both on every other status (`AWAITING_INPUT`, `ESCALATED`, `FAILED`, `PARTIAL`, `ARCHIVED`, `PAUSED`) — retain is the fallthrough, so a `Status` value added later preserves history by default until someone decides otherwise. The rule keys on the target status, not on a comparison with the status the workspace held before the call: a non-transition (writing `ACTIVE` onto a workspace that is already `ACTIVE`) still clears, which is what lets a workspace whose park state was already stale — recovered once, but still carrying its `park_reason`/`blockers` from before the recovery, because nothing before this had a way to clear them — heal on its very next status write instead of needing manual repair. `clear_park_reason`/`clear_blockers` (both `bool`, default `False`) let a caller force the clear on a status that would otherwise retain, mirroring the pre-existing `clear_merge_block_class` flag; an explicit `park_reason=`/`blockers=` value always wins over both the flag and the status rule. Clearing blockers writes `[]`, never `None` — `Meta.blockers` is a non-nullable `list[Blocker]` and `model_copy` skips validation, so a `None` would serialize as `null` and make the next `_read_meta` raise, silently dropping the workspace from `list_workspaces` (which swallows `WorkspaceError`) on every surface.

**Deliberately not extended to `merge_block_class`.** `park_reason`/`blockers` are display-only — they describe why a workspace is currently stopped, for a human reading the workspace or the manager summary — whereas `merge_block_class` feeds merge-lane routing (`_enforce_pr_merge_gate`) that can legitimately span a re-dispatch. Clearing it on the same transitions would change routing behaviour, not just reporting; `tests/test_workspace_merge_block_class.py::test_omitting_both_leaves_a_populated_merge_block_class_untouched` pins that a bare `transition(ws, Status.ACTIVE)` leaves a populated `merge_block_class` untouched, and that test is unchanged by this rule.

**Escalation rollback (`alan/workspace_dag.py`'s `stamp_for_advance`/`restore_escalated`, planned by `lifecycle.advance_target` — see [lifecycle.md](lifecycle.md)).** `Dispatcher._handle_decision` optimistically stamps an `ESCALATED` workspace to `ACTIVE` before attempting to advance it (`_workspace_dag.stamp_for_advance`), because the router may resolve a forward path for a workspace a human previously escalated. Since `ACTIVE` is a clearing status, that stamp — on its own — would wipe the very park state the workspace was escalated with. `stamp_for_advance` therefore captures a `ParkRollback(park_reason, blockers)` snapshot of the pre-stamp values unconditionally whenever the workspace is `ESCALATED` (including on the `has_awaiting_subtask` early-return branch, where no stamp happens at all but a rollback is still returned so the shape is uniform), and returns it alongside the (possibly stamped) workspace. If `_advance_or_enqueue` then raises, `_handle_decision`'s `except` clause calls `_workspace_dag.restore_escalated(ws, rollback)`, which writes `Status.ESCALATED` back with the captured `park_reason`/`blockers` passed **explicitly** — not left to retain-by-default, since by the time of the restore the workspace's in-memory `park_reason`/`blockers` are already `None`/`[]` from the optimistic `ACTIVE` stamp. `restore_escalated` passes no `merge_block_class` keyword at all, reproducing the pre-existing rollback behaviour on that field exactly. On the success path, the workspace simply proceeds `ACTIVE` with its park state cleared — which is the fix's actual target: an escalation that resolves and advances stops reporting the escalation it recovered from.

### Deploy-wait re-parking (`alan/deploy_wait_gate.py`)

`Dispatcher._apply_router_decision` runs one more rewrite after `_enforce_loop_guard` and before `_handle_decision`: `decision = deploy_wait_gate.apply(handover, decision)`. `deploy_wait_gate.apply` is a pure function — no `Queue`/`Dispatcher` access — that passes `decision` through unchanged unless `decision.kind == "done"` and `handover.from_team == "deploy_verify"` and `handover.deploy_wait is not None`, in which case it rewrites the decision into `kind="enqueue", team="deploy_verify"` with `eligible_at` set to the wait's deadline and a `GateRecord(path="awaiting_restart", ...)` (`alan/deploy_verify.py`) carrying the same `deadline`/`race_deadline` forward as `instructions`. This is what turns `deploy_verify`'s `wait`-kind evaluation (see [deploy_verify.md](deploy_verify.md)) into a re-parked `PENDING` job rather than a completed workspace.

**Placement is the whole point.** `select_next_team` returns `kind="done"` for any `handover_type="terminal"` handover — which is what a `wait`-kind `deploy_verify` outcome produces, deliberately, so it routes through the same `done` early-exit as a genuine `CONFIRMED` outcome. `_enforce_loop_guard` (`Dispatcher._enforce_loop_guard`) short-circuits immediately whenever `decision.kind != "enqueue"` — so as long as `deploy_wait_gate.apply` runs *after* `_enforce_loop_guard`, the loop guard never sees the wait cycle in its `enqueue` shape at all, and `check_loop_guard`'s `REVISIT_CAP` comparison and `detect_spiral` are never invoked for it. Running the rewrite *before* `_enforce_loop_guard` instead would hand the guard a `kind="enqueue", team="deploy_verify"` decision on every wait cycle; because `has_forward_progress` returns `False` for a repeating identical wait (no verdict change, no artifact change), a chain that legitimately needs to wait out an 85-minute deploy would eventually cross `REVISIT_CAP` and get escalated as a stall — the exact "false escalation of the deploy-still-in-progress kind" the event-driven rebuild exists to eliminate. Placing the rewrite after the guard, and before `_handle_decision`, is therefore load-bearing, not incidental: it is what lets a `deploy_verify` wait cycle re-park an unbounded number of times without ever touching the revisit-count machinery that would otherwise cap it.

`alan/dispatcher.py`'s own `_route_after_handover` still runs its ordinary `has_forward_progress`/`increment_revisit_count` bookkeeping against the pre-rewrite `kind="done"` decision (`decision.team is None`, so it always takes the `increment_revisit_count` branch) — that counter keeps climbing across repeated wait cycles, but since `check_loop_guard` is never reached for this decision shape, the climbing counter has no observable effect. It decays, and matters again, only once `deploy_verify` produces a genuine forward-moving outcome (`confirmed` or an `escalate`), neither of which is `kind="enqueue"` either.

## DAG mechanics (`alan/workspace_dag.py`)

The DAG-advance/stall machinery — `advance_workspace_dag`, `ready_tasks`, `task_blocked`, `dag_has_active_work`, `maybe_surface_stall`, `propagate_task_failure`, `workspace_terminal_status`, `stamp_evidence`, `enqueue_ready` — lives in `alan/workspace_dag.py` as dependency-passing free functions (no `Dispatcher` import; `queue`/`pubsub`/`teams` are passed explicitly). `Dispatcher` keeps same-named methods (`_advance_workspace_dag`, `_ready_tasks`, `_task_blocked`, `_dag_has_active_work`, `_maybe_surface_stall`, `_enqueue_ready`) as one-line delegations, still called under the per-workspace lock (see [dispatcher_concurrency.md](dispatcher_concurrency.md)).

`advance_workspace_dag` and `maybe_surface_stall` take a `schedule_manager_summary` callback (bound to `alan._dispatcher_base._schedule_manager_summary`, which lives in the lowest dispatcher-seam module since it triggers the investigator and is shared by multiple seams) rather than importing it directly — this keeps `workspace_dag` free of a reverse import back onto `dispatcher`. Likewise `apply_injection` and `evaluate_requirements` are passed in as callbacks bound to `Dispatcher._apply_injection`/`Dispatcher._maybe_evaluate_requirements` (H5.2: both now `alan/_dispatcher_reconcile.py::ReconcileMixin`, resolved on the `Dispatcher` instance via MRO exactly as before) because they reach into verification/scenario machinery a layer below `workspace_dag`. `alan._dispatcher_reconcile` (H5.2; previously `alan.dispatcher`) re-exports `_propagate_task_failure`, `_stamp_evidence`, and `_workspace_terminal_status` as module-level aliases of the `workspace_dag` functions, both for its own `_propagate_and_cancel` (used by `_observe_task_failure`, which stays on `Dispatcher` in `alan/dispatcher.py` and reaches `_dispatcher_reconcile._propagate_and_cancel` module-qualified) and for backward compatibility.

## PubSub (`alan/events.py`)

In-process publisher/subscriber keyed by `task_id`. Used to fan out `TeamEvent`s (`node_started`, `node_completed`, `stream`, `workflow_created`, `job_completed`, `workspace_deleted`, `chat_event`, `assistant_done`, `error`, …) to the workspace's SSE endpoint.

Subscriber exceptions are isolated — one bad listener cannot abort the fanout to the others.

`PubSub` and the `TeamEvent` re-export live in `alan/events.py`, a layer below `alan/reconciler.py` and `alan/routes/*` so both can depend on the event bus without importing the dispatcher. `alan/dispatcher.py` imports `PubSub` from `alan.events` and re-exports it for its own callers (`Dispatcher.__init__`'s default `PubSub()`, and any code that still does `from alan.dispatcher import PubSub`).

## Lifespan wiring

FastAPI `lifespan` constructs:

- `Queue` at `ALAN_QUEUE_DB_PATH` (default `~/.alan/queue.db`).
- `PubSub`.
- Workspace root at `ALAN_WORKSPACES_ROOT` (default `~/.alan/workspaces`).
- Calls `reconciler.reconcile_on_startup` (when the dispatcher is enabled) — see [Restart resilience](#restart-resilience).
- Calls `reconciler.seed_triage_sweep(queue, workspaces_root)` — idempotent; creates the long-lived triage workspace and enqueues the first sweep if none is pending/running. See [docs/architecture/triage.md](triage.md).
- Dispatcher thread pool (N = `ALAN_DISPATCHER_CONCURRENCY`, default 6), unless `ALAN_DISABLE_DISPATCHER` is truthy (`1` / `true` / `yes` / `on`) — in that mode the queue + pubsub are still wired so the endpoints stay reachable, but no team work runs in-process. Invalid or non-positive values of `ALAN_DISPATCHER_CONCURRENCY` log a warning and fall back to 6.

The dispatcher's team registry starts from `alan.teams.TEAMS` and is extended with a `TriageTeam` instance (constructor-injected `queue` + `workspaces_root`). `TriageTeam` is not in the static `TEAMS` dict because it requires runtime deps at construction time.

## Restart resilience

**Source:** `alan/reconciler.py`, `alan/teams/_node_attach.py`, `alan/worker_reaper.py`

Node dispatch precedence on every restart is **cached result → attach to a surviving worker → resume an interrupted session → run fresh** (`alan.teams._base.run_or_resume_node`; see [worker_records.md](worker_records.md) for the attach mechanics). Whether a `claude` subprocess dies with the parent on restart, or survives it, depends entirely on the `ALAN_DETACHED_WORKERS` dial: with the dial off (CI, e2e, local dev/pytest, and the default until a deploy turns it on), every in-flight subprocess is killed with the parent exactly as before — the paragraph below is what makes that case safe. With the dial on (production), a journal-mode worker starts in its own process session and keeps running and writing to its journal file after the restart; the reconciler and boot sweep below are unchanged, but node dispatch now finds that survivor via attach before it would fall through to resume. The reconciler is otherwise unmodified by attach — it still requeues interrupted work back through node dispatch, which is what makes the survivor reachable at all.

Either way, without intervention the queue row stays `status='running'` and the corresponding `workflow.yaml` keeps its `running` nodes — zombies that no further dispatcher tick will ever claim.

`reconciler.reconcile_on_startup(queue, workspaces_root, pubsub, replay_routing=...)` runs once during `lifespan`, **before** `Dispatcher.start()` (but after the Dispatcher is constructed so its `replay_handover_routing` bound method can be passed as the `replay_routing` callback), and sweeps every `status='running'` queue row. When replay, an eligible never-started re-run (see §Auto re-run for never-started jobs below), resume, and re-derive all decline to apply, the row falls through to this terminal fallback:

1. Load the workspace; load the pre-allocated `workflow.yaml` at `invocations/<inv_id>/`.
2. Flip every `running` node to `failed` with `error="interrupted_by_restart"` and finalize the workflow as `failed`.
3. Call `queue.mark_interrupted_and_fail(job_id, "interrupted_by_restart", resume_inv_id=marker, clear_resume=marker is None)` — flips the row to `failed`, sets `finished_at`/`error`, and bumps `interruption_count` (a new column distinct from any future `retry_count`). `marker` is computed independently of *why* the fallback was reached: `team_supports_resume(job.team)` and the just-interrupted workflow document actually holding an `"interrupted"` node; when either is false the `clear_resume=True` keyword actively NULLs any stale `resume_inv_id` a prior cycle may have left, rather than advertising a Re-queue control the row cannot honor. A present marker is the precondition for `list_resumable_failed_by_workspace` to see the row, which is what makes `POST /api/workspaces/{id}/resume` return `202` instead of `409` and `Dispatcher.resume_task` actually requeue it — a terminally-parked run genuinely-unrecoverable by resume or re-derive still carries its own way back in, satisfying "no declared fallback that can't be reached in practice." The resume-audit row for this fallback (`interrupted_failed`, or `rerun_cap_exhausted` when a never-started re-run's own retry budget is what was exhausted) always carries the job's real `triggered_by_invocation_id`, decided independently of `marker` — a defaulted empty string here is what misdiagnosed a past incident, since every such row ever written carried it.
4. Flip `meta.status` to `Status.AWAITING_INPUT`, with `Blocker.detail` naming the restart as the cause (`RESTART_PARK_MESSAGE` when the fallback was reached for any other reason, or `RERUN_CAP_MESSAGE` when a never-started job exhausted its own re-run budget — both defined once, in `alan/_reconciler_orphans.py` and `alan/_reconciler_never_started.py` respectively, and imported by `alan/reconciler.py` so every sweep shares the same wording per case) rather than the bare `interrupted_by_restart` error token. `Blocker.instruction`/`action_url` stay unset: neither has a non-test frontend consumer, so populating them would ship a dead button.
5. Publish a `workspace_interrupted` `TeamEvent` so any open SSE subscriber refetches.

Per-row failures are logged and recorded in `ReconciliationReport.errors`; one bad row never aborts the sweep.

Before the per-row sweep even starts, `reconcile_on_startup` also calls `_reconciler_orphans.reconcile_orphaned_workflows(queue=queue, workspaces_root=workspaces_root, pubsub=pubsub)` — a second pass that catches a different failure shape than an orphaned `RUNNING` queue row. A crash between `interrupt_workflow_on_disk` marking a node `"interrupted"` on disk and the corresponding queue-row bookkeeping (or a workspace whose queue row was separately cleaned up, e.g. by an operator) can leave a workflow doc with an `"interrupted"` node, no successor invocation, and no live queue row for any sweep to find — a state that, left alone, is permanently in flight: no path back, not even for a human dispatch to notice via the normal `RUNNING`-row sweep. `find_orphaned_interrupted_workspaces` scans every `AWAITING_INPUT`/`ACTIVE` workspace (`alan._reconciler_orphans`, keyed on workflow docs rather than the queue because there is no live queue row to key on by construction) except `AWAITING_INPUT` workspaces parked `ParkReason.UNARCHIVED` (`_orphan_eligible`, via `lifecycle.held_by_unarchive`) — a workspace the operator restored from archive still carries the workflow docs of its earlier runs, and re-parking it as `CRASH` at the next restart would make it an incident and an unblocker candidate that auto-dispatches, which the restore promised never to do — resolves each workspace's **latest** invocation only, and keeps those whose loaded `WorkflowDoc` has any task in `"interrupted"` status. `reconcile_orphaned_workflows` then skips any workspace that still has a live `RUNNING` job (`queue.list_jobs_for_workspace(ws.workspace_id, status=JobStatus.RUNNING)` — no new `Queue` method) and parks the rest exactly like the per-row sweep's `_fail_workspace` (`ParkReason.CRASH`, the same restart-naming `Blocker.detail`). It **never requeues** — this pass runs at boot before any resume attempt, so there is no "took a real action" signal that would justify auto-requeue; the operator's re-drive path is a direct dispatch against the parked workspace (e.g. from its own workspace page, or the `dispatch_remediation` action on its Health finding — see [health.md](health.md)), not `/resume` (there is no `FAILED` queue row with a `resume_inv_id` for `/resume` to find here).

The ordering — orphan pass first, per-row sweep second, both inside the same `reconcile_on_startup` call — is load-bearing, not incidental. At the instant the orphan pass runs, every job the per-row sweep is about to resume is still sitting `RUNNING` in the queue (that `RUNNING` row is exactly what makes it visible to `queue.list_running()` a moment later), so the orphan pass's RUNNING-only live-job check correctly recognizes it as "something else already owns this" and skips it. Running the orphan pass **after** the per-row sweep instead would race a resume the sweep just performed: a successful resume flips the queue row `RUNNING → PENDING` (not yet claimed) and stamps the corresponding node `"interrupted"` on disk by design — the exact shape `find_orphaned_interrupted_workspaces` looks for — so an orphan pass running afterward would wrongly park a workspace that had just been correctly handed back to the dispatcher, flipping it to `AWAITING_INPUT` out from under a live `PENDING` row. Only the resume path produces this ambiguity: the terminal mark-failed path and a successful re-derive's old invocation both call `interrupt_workflow_on_disk` without `resumable=True`, which flips nodes to `"failed"` rather than `"interrupted"`, so neither is ever mistaken for an orphan regardless of ordering.

### Re-derive for `restart_rederivable` teams

Before falling through to the mark-failed path, the reconciler also tries to **re-derive** any orphan whose team has `restart_rederivable = True`. `PrMergeTeam` and `DeployVerifyTeam` carry this flag (`supports_resume = False` because there is no LLM session to checkpoint). `VerificationTeam` also carries it while keeping `supports_resume = True`. For a resume-capable team the reconciler tries resume first via `_try_resume`, which now returns a `_ResumeAttempt(succeeded, attempted)` pair rather than a bare bool — `attempted` is `True` the instant a resume target is found eligible (workspace present, not archived, an invocation id, and `team.supports_resume`), independent of whether the resume itself then succeeds. `_rederive_eligible` threads `resume_was_attempted=resume_attempt.attempted` down to `_resume_would_lose_captured_session(job, workspace, inv_id, resume_was_attempted=...)`, which now short-circuits to `False` (does not block re-derive) whenever a resume was attempted — it only consults `_workflow_has_captured_session(workspace, inv_id)` when resume was **never** applicable (`attempted=False`, e.g. the team doesn't support resume, or there is no invocation id). This corrects a defect where the old code blocked re-derive for **any** node anywhere in the invocation carrying a captured `claude_session_id`, even when `_try_resume` had already been attempted and failed for reasons unrelated to that session (a mechanical `interrupt_workflow_on_disk`/`requeue_for_resume` failure, or — the historically-hit case for verification — a restart landing during the grounded checkout, before any node had started, so `_interrupt_for_resume` found no `"interrupted"` node to hand back to resume even though an earlier node's session was still recorded on disk). Since verification always supports resume and re-derive is only ever reached after `_try_resume` ran, `attempted` is essentially always `True` by the time `_rederive_eligible` runs for it — making `restart_rederivable` actually reachable in practice, not merely declared. A doc-load failure inside `_workflow_has_captured_session` still returns `True` (conservatively blocks re-derive) for the one case that guard still gates: resume never applicable at all. Unlike resume, re-derive does not recover in-progress work — it enqueues a fresh copy of the interrupted step so the service can continue without human escalation.

The re-derive branch runs after the resume branch and before the mark-failed fallback:

1. Verify `team.restart_rederivable is True` (via `getattr`; teams absent from the registry return `False`).
2. Check the workspace is not `ARCHIVED`.
3. Check `job.triggered_by_invocation_id` is not `None`.
4. Scan the workspace's handovers for a terminal entry whose `from_invocation_id` matches the interrupted job's `inv_id`. If one exists, the job completed before the crash — skip re-derive (the stalled-DAG repair covers this delivery).
5. Count prior FAILED jobs for this `task_id` and `team`. If the count is ≥ 3 (`_REDERIVE_CAP`), fall through to the mark-failed path to prevent indefinite re-derives under a bounce-storm.
6. Call `queue.mark_interrupted_and_fail(job_id, "interrupted_by_restart")` — flips the old RUNNING row to FAILED.
7. Best-effort: interrupt the old `workflow.yaml` on disk (`_interrupt_workflow`).
8. Call `team.plan_workflow(workspace, None)` + `seed_pending_workflow` + `queue.enqueue` to create a fresh PENDING job, propagating `parent_handover_id` so the dispatcher loads the correct prior handover.
9. Append one JSON line to `~/.alan/logs/rederive_audit.jsonl` (override root via `ALAN_LOGS_ROOT`).
10. Publish a `<team>_rederived` SSE event (e.g. `pr_merge_rederived`, `verification_rederived`) so any open tab refetches.

If step 8 fails (any exception), the workspace is flipped to `AWAITING_INPUT` and a `workspace_interrupted` event is published (same fallback as the normal interrupted path). D5 idempotency ensures a re-derived `pr_merge` job that detects an already-merged PR terminates cleanly via the `MERGED` short-circuit in `pr_merge.run()`.
### Saved-but-unrouted handover replay

There is a short crash window inside `Dispatcher._run_team` between `save_handover` (which persists the team's `Handover` to disk) and `_route_after_handover` (which enqueues the next team and calls `queue.complete`). A deploy bounce in this window leaves:

- The queue row still `RUNNING`.
- The `workflow.yaml` finalized as `"success"`.
- The handover file on disk with `from_invocation_id == job.triggered_by_invocation_id`.
- No successor job yet enqueued.

Without intervention the normal reconciler sweep (which looks for `"running"` or `"interrupted"` workflow nodes to mark failed) sees a `"success"` doc and does not call `interrupt_workflow_on_disk`. The row would then be flipped to `FAILED` via `mark_interrupted_and_fail` and the workspace would go to `AWAITING_INPUT` — stranding a workspace that was actually done.

`_replay_unrouted_handover` detects this exact signature and replays the routing decision **before** `_try_resume`:

1. If `replay_routing` is `None` (not provided), skip — no-op to preserve existing behavior.
2. If the job's `triggered_by_invocation_id` is absent, or the workspace is missing, skip.
3. Call `_handover_to_replay(workspace, inv_id)` — returns the most-recent handover whose `from_invocation_id` matches `inv_id` and whose workflow doc has `status == "success"`; returns `None` if either condition fails (not present, unreadable, or status ≠ "success").
4. If handover is `None`, fall through to the normal path.
5. If the workspace is already in a terminal state (`COMPLETED` or `FAILED`), call `queue.complete(job_id)` to retire the zombie row and record the audit outcome `"already_terminal"`.
6. If a successor job already exists (`parent_handover_id == handover.handover_id` in any job for that workspace), call `queue.complete(job_id)` and record `"successor_exists"` — idempotent guard against double-enqueue.
7. Otherwise, record `"handover_replay_invoked"` and call `replay_routing(job, handover)` — which resolves to `Dispatcher.replay_handover_routing`. That method loads the workspace and delegates to `_route_after_handover`, which enqueues the next team and calls `queue.complete` in its `finally` block.

Audit rows are appended to `~/.alan/logs/handover_replay_audit.jsonl` (override root via `ALAN_LOGS_ROOT`).

**Idempotency**: `_has_successor_job` checks `parent_handover_id` across all jobs for the workspace. Because `_advance_or_enqueue` always stamps `parent_handover_id=handover.handover_id` when creating successor jobs, a second reconcile pass after the routing was already replayed finds the successor and takes path 6 instead of double-enqueuing.

**Lifespan ordering**: the `Dispatcher` is constructed *before* `_run_job_reconciler` is called so that `dispatcher.replay_handover_routing` (a bound method) can be passed as the `replay_routing` callback. `dispatcher.start()` is still called *after* reconcile completes — no worker threads run during the sweep.

### Auto re-run for never-started jobs

**Source:** `alan/_reconciler_never_started.py`

A job whose invocation never captured a `claude_session_id` anywhere and never completed a node produced no partial work — there is nothing for a plain re-run to collide with, unlike the general resume path. This is not a rare race: it is deterministic for any team that runs as a single worker, supports resume but not re-derivation (`implementation`, `implementation_fix`), on any restart landing before that worker reports its session — and restarts are routine here because every merge to `main` auto-deploys.

`_reconcile_one_job` calls `never_started.try_rerun(job, queue, workspace)` immediately after `_replay_unrouted_handover` and **before** `_try_resume`. The ordering is load-bearing, not incidental: `_try_resume`'s own `interrupt_workflow_on_disk(..., resumable=True)` call, for a single-node invocation with no captured session, defers the sole running node, finds no interrupted sibling to settle against, fails the task, and **saves** the workflow document as `failed` — after that write, a plain pending requeue would re-enter an invocation whose node is already `failed` and crash with `WorkflowError("duplicate node id")` on the next `_activate_pending`. The never-started decision therefore has to be made, and the re-run prepared, before `_try_resume` ever runs.

Eligibility (`try_rerun`'s private `_rerun_target`) is keyed on the same captured-session read `_resume_would_lose_captured_session` already uses — `has_captured_session`, which fails safe to `True` on any workflow-load error — deliberately not on a missing `triggered_by_invocation_id`: every enqueue call site in the application tree supplies one except the DAG-subtask path, so a branch keyed on a missing invocation id would not have fired on the incident that motivated this feature and would not fire on the next one either. A job is eligible only when: the workspace is present and not `ARCHIVED`; it carries a `triggered_by_invocation_id`; `team_supports_resume(job.team)` is true and `team_supports_rederive(job.team)` is false — exactly the class `implementation`/`implementation_fix` occupy, keeping `pr_merge`/`deploy_verify`/`verification` (all `restart_rederivable`) on their existing re-derive path unchanged; `has_captured_session` is false; and `has_completed_node` is false.

An eligible job is capped at `RERUN_CAP` (3, matching `_REDERIVE_CAP`'s bound) re-runs, read from the job's own `interruption_count` — the same counter every requeue already bumps, so no new column is needed. Below the cap, `try_rerun` calls `workflow.reset_failed_nodes_for_rerun(ws, inv_id)` (flipping any `failed`/`running` node back to `pending`, clearing `error`/`started_at`/`completed_at`/`claude_session_id`), reloads the document and confirms every task is now `pending`, then calls `queue.requeue_pending(job.id)` — a plain `RUNNING → PENDING` flip that clears any stale `resume_inv_id` and bumps `interruption_count`, with `triggered_by_invocation_id` left untouched so the re-run stays attached to the same invocation an operator can already see, rather than orphaning it as permanently in-flight. `reconciler._reconcile_one_job` records the outcome as `"rerun_never_started"` (with the job's real invocation id) and appends to `ReconciliationReport.rerun`; no workflow-interrupt call and no queue-row failure happen on this path at all.

At the cap, `try_rerun` returns `"exhausted"` without touching the queue row itself — flipping the row is deliberately left to the pre-existing terminal fallback (§ above), the invariant being that a `RUNNING` row is unrecoverable by any means other than that one code path (see the `RUNNING`-is-unrecoverable note under §The requeue ladder below). `_reconcile_one_job` still runs `_try_resume`/`_try_rederive` on an exhausted job exactly as it would for any other never-started job (both decline, since there is still no captured session and the team does not re-derive), so the terminal fallback's own marker computation and `interrupt_workflow_on_disk` call fire unchanged — only the audit outcome (`"rerun_cap_exhausted"`) and the park message (`RERUN_CAP_MESSAGE`, naming the exhausted budget) vary. `RERUN_CAP_MESSAGE`'s own text (`alan/_reconciler_never_started.py`) still literally says "Re-dispatch this workspace from the inbox" — stale since the inbox HTTP surface was deleted (delete-the-inbox-http-surface, 2026-09); out of this doc-sweep's file scope to correct, flagged here for a follow-up. This is what keeps the queue-row flip in exactly one place while still surfacing a bounded, visible park instead of an unbounded per-restart retry loop.

Both new outcome strings are added to `alan.teams._resume_audit.ResumeOutcome` and `alan.learning_metrics._RESTART_RECOVERY_OUTCOMES` — the latter is an independent tuple, since `learning_metrics` sits below `teams` in the layers list and cannot import `ResumeOutcome` to derive its own list; `tests/test_learning_metrics.py` pins `set(get_args(ResumeOutcome)) <= set(_RESTART_RECOVERY_OUTCOMES)` so a value added to one and not the other fails loudly instead of silently vanishing from the weekly restart-recovery digest.

### Auto-resume for all LLM teams (PR2 + PR3)

Before falling through to the mark-failed path above, the reconciler tries to **resume** any orphan whose team supports it. A team is resume-capable when `team.supports_resume is True`. Single-node teams (`SingleAgentTeam`, `ImplementationTeam`) shipped resume in PR2; multi-node teams (`StaticPipelineTeam`, `OrchestratedTeam`, `ResearchTeam`, `ImplementationPlanTeam`, `VerificationTeam`) ship in PR3. The only `supports_resume = False` team is `PrincipalProxyTeam` — it has no LLM call to resume. `implementation` and `implementation_fix` route through the same `run_or_resume_node` primitive as the multi-node teams (see below), so they now gain **attach** to a restart-surviving worker, not resume alone.

The resume branch:

1. Load the workspace + invocation's `workflow.yaml`.
2. Call `workflow_interrupt.interrupt_workflow_on_disk(workspace, inv_id, resumable=True)` — flips every `running` node whose `claude_session_id` is set to a new `"interrupted"` status. A running node with no captured session id is deferred rather than flipped immediately: once every node in the doc has been classified, a deferred node settles to `"pending"` (the interrupt marker carried forward in `error`, `started_at`/`completed_at`/`claude_session_id` cleared) when at least one sibling landed on `"interrupted"` — so a mixed parallel stage recovers as a whole instead of the sessionless node crashing re-entry with `duplicate node id` — and still flips `"failed"` exactly as before when no sibling is `"interrupted"`. The workflow top-level stays `"running"` when at least one interrupted node remains.
3. Call `queue.requeue_for_resume(job_id, inv_id)` — single-statement SQL that flips the row back to `pending`, sets a new `resume_inv_id` column to the orphan invocation, clears `started_at`/`finished_at`/`error`, and bumps `interruption_count`.
4. Append one JSON line to `~/.alan/logs/resume_audit.jsonl` (override the root via `ALAN_LOGS_ROOT`). `alan.teams._node_attach` writes to the same file with outcome `"attached"` or `"attach_lost"` (see [worker_records.md](worker_records.md)#attach), so the reconciler's own `"requeued_for_resume"` line and attach's outcome for the same invocation together give the full attach/resume/fail rate per restart.
5. Publish a `workspace_resuming` SSE event so any open tab refetches.

The dispatcher claims the requeued row on its next tick and calls `team.run(..., resume_inv_id=inv_id)`. Resume-capable multi-node teams branch to `run_or_resume_node`, which — per the restart-resilience precedence above — tries attach before falling through to `resume_workflow_node`, which calls `WorkflowGraph.resume_node(node_id)` (flips `interrupted → running`, clears `completed_at` and `error`) and shells out to `claude --resume <session_id>` instead of `claude --session-id <uuid>`. If `claude` reports `"No conversation found with session ID …"`, the helper raises `ResumeSessionLostError` (a `ClaudeCliError` subclass) and the dispatcher falls back to the normal job-failed path. The `--allowedTools` / `--permission-mode` / `--cwd` overrides flow through unchanged, so the worktree-isolated `ImplementationTeam` resume hits the same sandbox as the fresh run.

Resume is best-effort: any failure inside the resume branch (workflow write failure, queue write failure) falls back to the PR1 mark-failed path so we never leave a zombie. The pause/retry paths reach the same guarantee by a different route — see the requeue ladder under §Usage-limit auto-pause, which recovers a row that moved out of `RUNNING` and parks the workspace to `AWAITING_INPUT` when it cannot. The dispatcher's `_run_team` passes `job.resume_inv_id` through to `team.run`, and a `job_started` SSE event now carries `resume_inv_id` so the frontend can distinguish fresh vs resumed.

### Multi-node resume (PR3)

Multi-node teams resume by replaying their pipeline node-by-node. Every `_run_fresh_node` / `resume_workflow_node` call writes the role's final output to `~/.alan/workspaces/<task>/invocations/<inv>/agents/<role>.result.json` (atomic `.tmp` + rename). On resume, `_base.run_or_resume_node` decides per node:

- **status="success"** → `_cached_result_for` reads the result document and returns its cached `result_text` (no CLI call). If the document cannot be read back — missing, malformed, or the node's cache was deliberately invalidated (see `StaticPipelineTeam._parse_or_invalidate` in [workflow_visibility.md](workflow_visibility.md)) while the node's own status stayed `success` — it raises `WorkflowError` naming the node and invocation, rather than the pre-fix behaviour of silently falling through to a fresh run or replaying an empty string.
- **status="interrupted"** → call `resume_workflow_node` (CLI gets `--resume <session_id>`), reached via the same `_attach_or_resume` branch that first tries to attach to a restart-surviving worker.
- **anything else** (pending / missing) → call `_run_fresh_node` for a fresh run. `run_or_resume_node` is the sole caller of `_run_fresh_node`; the fresh-only entry point is not itself a public name on `alan.teams._base`, so a runtime-spawned retry step (e.g. `clause_auditor_retry`, `judge_retry` — see below) started through `run_or_resume_node` is resume-safe without its author needing to know that choice exists.

`StaticPipelineTeam`, `OrchestratedTeam`, `ResearchTeam`, `ImplementationPlanTeam` and `VerificationTeam` all opt in via `supports_resume = True` and route every role through `run_or_resume_node`. The orchestrator's `dispatched` list (the worker roles it emitted) is persisted via `WorkflowGraph.set_dispatched` so that a resumed `_phase_workers` re-reads the same dispatch from the (cached or re-emitted) orchestrator output.

**Runtime-spawned retry nodes resume the same way as planned nodes.** Two roles in the verification pipeline spawn an extra node at runtime when their first attempt's output can't be parsed — `clause_auditor_retry` (`alan/teams/_clause_audit.py`) and `judge_retry` (`alan/teams/verification.py`) — neither is declared in the pipeline's up-front `plan_workflow` (a pre-declared node would sit unstarted forever on the majority of runs where no retry fires). Both start through `run_or_resume_node`, exactly like every planned node, so a service restart landing after either retry step completes finds a `success` node on resume and reuses its recorded output instead of re-entering `_run_fresh_node` and crashing on `duplicate node id` — the failure mode this section's `WorkflowError("duplicate node id")` note describes for a mismatched cache. A restart landing while the retry step is still in flight resumes it through the ordinary `interrupted` branch above, `--resume <session_id>` and all — but only once the node has captured a `claude_session_id`. A restart landing before that capture leaves `interrupt_workflow_on_disk(..., resumable=True)` marking the node `failed` rather than `interrupted`, so `run_or_resume_node` still falls into the fresh arm and raises `duplicate node id` on the next resume attempt — a pre-existing, out-of-scope failure mode this PR does not close (`test_retry_node_without_captured_session_id_still_fails_on_resume` pins it unchanged).

`PrincipalProxyTeam` keeps `supports_resume = False` — it has no LLM step to resume. It raises `ResumeUnsupportedError` if a `resume_inv_id` somehow arrives (defense in depth; the reconciler already filters via `supports_resume`).

### Terminal resume outcome (`alan/_dispatcher_resume_outcome.py`)

`ResumeOutcome` (`alan/teams/_resume_audit.py`) gained two values this build: `"resume_succeeded"` and `"resume_failed"`. Every other `ResumeOutcome` value recorded up to this point describes a *decision* the reconciler or attach path made (`"requeued_for_resume"` — decided to try; `"attached"`/`"attach_lost"` — a survivor-attach outcome; `"interrupted_failed"` — decided not to try) rather than what actually happened to a resumed run once the dispatcher picked it back up — a requeued job that then failed again recorded nothing terminal, so the resume recovery rate had no denominator beyond "scheduled to continue."

`record_terminal_resume_outcome(job, *, succeeded: bool)` closes that gap: it is a no-op unless `job.resume_inv_id` is set (i.e. this specific job execution was itself a resume, however it got there — reconciler resume, manual Re-queue, or usage-limit/server-error auto-pause requeue), in which case it appends one row to the same `~/.alan/logs/resume_audit.jsonl` via the same `record_resume_outcome`/`append_jsonl_audit` machinery every other `ResumeOutcome` uses — no new store, no new env var. The audited unit is **the job row**, not the workspace or the team: a workspace can accumulate multiple resume cycles across its lifetime, and each terminal outcome is attributed to the specific job execution that produced it.

Two call sites cover the two ways a job execution ends terminally:

- **Success** — `Dispatcher._route_after_handover`'s `finally` block, immediately after `self._queue.try_complete_or_current(job.id)` returns a non-`None` `completed` row (i.e. this call is what actually flipped the row `RUNNING → COMPLETED`, not a concurrent path that beat it there).
- **Failure** — three sinks, one per way a job execution ends in a terminal failure: `BaseMixin._fail_job` (`alan/_dispatcher_base.py`) is the sink for every *non-recoverable* job failure — the same sink that already writes `job_failure_audit.jsonl` and calls `_observe_task_failure`. `Dispatcher._fail_genuine`'s recoverable branch and `_fail_recoverable_subtask` (`alan/dispatcher.py`) both bypass `_fail_job` — they call `mark_interrupted_and_fail` directly so the workspace parks instead of terminating outright — so each calls `record_terminal_resume_outcome(job, succeeded=False)` itself, right alongside its own `mark_interrupted_and_fail`, to still count a resumed job that fails back into a recoverable park even if the operator never re-queues it.

`alan.learning_metrics._RESTART_RECOVERY_OUTCOMES` and `alan.shop_stats._restart_recovery_lines` both extend to carry `resume_succeeded`/`resume_failed` counts per team, so the weekly digest's "Restart recovery" block reads a `resume_succeeded=N resume_failed=M` pair alongside the existing `attached`/`attach_lost`/`interrupted_failed` counts — the recovery rate is `resume_succeeded / (resume_succeeded + resume_failed)`, computable post-ship instead of disappearing between "scheduled to continue" and silence.

### Re-entry contract for requeue-to-pending paths

Any path that returns a job to `PENDING` while leaving its `triggered_by_invocation_id` pointed at the same invocation must first call `workflow_mod.reset_failed_nodes_for_rerun(ws, inv_id)`. `WorkflowGraph._activate_pending` (the sole gate `start_node` reaches when a node id already exists in the graph) refuses to reactivate a node whose recorded status is anything other than `pending`, raising `duplicate node id: {id} (status={status})`. That guard is load-bearing, not a bug: a second activation of an already-`running`/`failed` node would overwrite its `role`/`model`/`started_at` while silently retaining the first attempt's `stream_path`, `claude_session_id` and accumulated cost fields — worse than the park the guard causes instead. Resume-capable teams never hit this guard on their own re-entry: they come back through `resume_node`, which requires the node's status to already be `interrupted` and is a distinct code path from `start_node`.

Four call sites requeue to `PENDING` against an existing invocation id today:

- `_reconciler_never_started.try_rerun` — resets before requeuing (`workflow_mod.reset_failed_nodes_for_rerun` then `queue.requeue_pending`).
- `UsageLimitMixin._handle_server_error` (`alan/_dispatcher_usage_limit.py`) — resets before requeuing, unconditionally: the server-error retry ladder has no resume concept at all, so every retry is a fresh re-entry from `pending`.
- `UsageLimitMixin._requeue_for_pause` (`alan/_dispatcher_usage_limit.py`) — resets before requeuing, but only on the non-resume branch (`resume_inv_id is None`); the resume branch calls `queue.requeue_for_resume` instead, which re-enters through `resume_node` and correctly does not touch `reset_failed_nodes_for_rerun`. This single function backs both of `_requeue_for_pause`'s production triggers: the usage-limit hour-boundary pause (`_handle_usage_limit`) and a user-initiated Stop on a non-resume team (`Dispatcher._pause_job`) — both funnel through it, so the one fix covers both.
- `_reconciler_paused.requeue_paused_job` (`alan/reconciler.py`'s paused-task branch of `_reconcile_one_job`) — mirrors `_requeue_for_pause`'s shape: for a resume-capable team, it calls `interrupt_workflow_on_disk(..., resumable=True, recover_finalized=True)` first and, when that leaves a node `interrupted` (i.e. a session had actually been captured), requeues through `queue.requeue_for_resume` instead of resetting — resetting a still-resumable session would clear its `claude_session_id` and force the next pickup's fresh-run arm, duplicating work. Otherwise (a non-resume team, or a resume-capable team whose running node never captured a session) it resets before requeuing to `pending`, skipping the reset only when the job carries no `triggered_by_invocation_id` or when the workspace failed to load. This branch fires for the reconciler's two production triggers: `Dispatcher.interrupt_task` (a user-initiated Stop reaching the reconciler's per-task pause table) and `repo_quiesce`'s task-level pause.

`reconciler._requeue_for_resume` (the reconciler's own resume branch, distinct from the usage-limit mixin's `_requeue_for_pause`) is the resume path and, like every resume path, does not call `reset_failed_nodes_for_rerun` — it re-enters through `resume_node`, not `start_node`.

This does not extend to a central reset at re-pickup time inside `workflow.py` itself: that would silently re-run genuinely `failed` nodes on paths that never intended a re-entry, which is guard relaxation through a side door.

## Server-error auto-retry

When a dispatched job fails because the model API returned a server-side error (HTTP ≥ 500; the triggering incident was a sustained 529 "Overloaded") **or because the model connection dropped mid-stream** (a transport disconnect carrying no HTTP response at all, and therefore no status code), the dispatcher automatically requeues the job with a per-job, jittered backoff delay instead of failing it immediately. Up to three automatic re-attempts are made; if all are exhausted the job falls through to the existing failure path. Every automatic re-attempt is a **bounded, fresh re-run from zero** — never a `claude --resume` of the failed session — so a long run that retries this way starts over from scratch; that is far better than losing the run outright, but it is not "recovery."

**Detection — 3-tier structured signal** (`alan/claude_cli._is_server_error`):

1. **Tier 1 — numeric status code.** If the stream-json result event carries `api_status_code >= 500` this is definitively a server error.
2. **Tier 2 — API error-type enum.** If `api_error_type` in the event is one of `{"overloaded_error", "api_error", "internal_server_error", "service_unavailable_error"}`.
3. **Tier 3 — documented text fallback.** Substring match on `"overloaded"`, `"internal server error"`, `"service unavailable"`, or `"the response stopped arriving"` in the result/subtype field (evaluated only after tiers 1–2 do not match). The fourth member is the transport-disconnect signal — the only one of the four that is not a 5xx shape, since a dropped connection never carries an HTTP status for tiers 1–2 to see.

The detection is applied in `_result_event_text` **after** the usage-limit check, so rate-limit / 429 signals are always caught by the existing `UsageLimitError` path first. `rate_limit_error` is not in the tier-2 set. `ClaudeCliError("claude CLI stream-json server error: …")` with subclass `ServerErrorRetryable` is raised; the dispatcher catches it specifically.

**Both CLI exit codes are classified.** `_result_event_text` runs only on the success path (CLI exit 0 with an error result event). When the `claude` CLI exits **non-zero** while emitting an error result event — the more common shape for a sustained 529 (the triggering incident: `exit 1`, `subtype=success`, `stop_reason=stop_sequence`, `result="API Error: 529 Overloaded"`) — `_await_completion` now calls `_maybe_raise_transient(events)` **before** the generic fallback. That mirror of the usage-limit-then-server-error classification raises `UsageLimitError` / `ServerErrorRetryable` so the transient retry fires on a non-zero exit too, instead of becoming a terminal `ClaudeCliError`. A genuinely non-classifiable error result falls through to `_describe_stream_error`, which now appends the truncated `result=` text to the raised message (and the WARNING log) so the real API error is no longer dropped in favour of just `subtype`/`stop_reason`.

**Per-job durable backoff** — two new columns on the `jobs` table:

- `eligible_at REAL` — unix timestamp before which the job must not be claimed. `NULL` means immediately eligible.
- `server_error_retry_count INTEGER NOT NULL DEFAULT 0` — counts only server-error retries; independent of `interruption_count`.

`_CLAIM_SQL` adds `AND (eligible_at IS NULL OR eligible_at <= ?)` (current `time.time()` passed as a parameter) so a job in backoff is invisible to claim without affecting other jobs or workspaces. The backoff is durable: if the process restarts while a job is mid-backoff, the PENDING row with `eligible_at` in the future is untouched by the reconciler (which only sweeps RUNNING rows) and is not prematurely claimed.

**Backoff formula** — `min(cap, base × 2^attempt + SystemRandom().uniform(0, raw × 0.25))`.  
Defaults: `base = 120 s`, `cap = 600 s`, `max_retries = 3`.  
Configurable via `ALAN_SERVER_ERROR_BASE_DELAY_S` and `ALAN_SERVER_ERROR_DELAY_CAP_S` (positive floats; invalid/non-positive values fall back to defaults). E2E tests set these to `1` and `5` so the retry cycle completes in seconds.

**`_handle_server_error(job, ws, exc, inv_id, team)` in `Dispatcher`**:

- Non-exhausted (`server_error_retry_count < 3`): first calls `workflow_mod.reset_failed_nodes_for_rerun(ws, inv_id)` to reset any `failed`/`running` nodes back to `pending` on disk, so the backoff retry re-enters `run_or_resume_node`'s fresh path (`_run_fresh_node`) cleanly via `_activate_pending` instead of crashing with `WorkflowError("duplicate node id")`. Then calls `queue.requeue_with_server_error_backoff(job.id, eligible_at)` (RUNNING → PENDING, clears `resume_inv_id`, sets `eligible_at`, bumps `server_error_retry_count`). Publishes a `job_retry_scheduled` SSE event with `{attempt, eligible_at}`. Does NOT call `_fail_workspace` — the workspace stays ACTIVE. Does NOT call `_fail_job` — no sibling propagation.
- Exhausted: routes through `_fail_genuine(job, ws, exc, inv_id, team)` — identical to the generic exception path. So a transient 5xx that burns all three retries is now **recoverable on the same terms as any other genuine failure**: when `_is_recoverable_failure` holds (resume-capable team, single-task workspace, ≥1 cached upstream node) the failed/running nodes are reset to `pending` via `reset_failed_nodes_for_rerun`, `resume_inv_id` is persisted, and the workspace's Re-queue control appears. Without reusable cached work it falls back to a plain `_fail_workspace` + `_fail_job`. Previously the exhausted branch always took the plain-failure path, so an exhausted 529 was a dead end even when prior nodes had completed.

**On retry** — `triggered_by_invocation_id` is preserved, so `_resolve_inv_id` returns the same `inv_id` and the already-successful upstream nodes reuse their `<role>.result.json` cache. Any node that was `failed` or `running` (left in that state by `workflow_lifecycle`'s exception finalizer) was already reset to `pending` by `reset_failed_nodes_for_rerun` before the requeue, so `run_or_resume_node` can activate the node cleanly via `_run_fresh_node` → `_activate_pending`. `resume_inv_id` is cleared so the retry is a fresh run, not a session resume of the possibly-corrupted failed session.

**All PENDING-transition requeue SQL** clears `eligible_at = NULL` so a manually resumed job is immediately claimable (no stale backoff window). The readiness hold (below) is not a requeue and does the opposite on purpose.

**Process kill without a structured error result** (SIGKILL / OOM) — when the worker process is killed before the CLI produces any stream-json output, there is no `ServerErrorRetryable` to catch; the reconciler's restart sweep sees the orphaned `RUNNING` row and routes it to the existing `_pause_job` / `requeue_for_resume` path (for resume-capable teams) or `mark_interrupted_and_fail` path (for others). No `server_error_retry_count` is incremented and no backoff is applied. This is intentional: a process kill is an infrastructure event, not an API-side overload, so the standard reconciler remediation (prompt human / resume) is the appropriate recovery rather than a silent auto-retry with backoff.

**Frontend** — `job_retry_scheduled` is registered in `WORKSPACE_LIFECYCLE_KINDS` to trigger a workspace re-fetch; no DAG/UI change in this build.

**Migration** — two new columns added via `_MIGRATIONS`:
- `ALTER TABLE jobs ADD COLUMN eligible_at REAL`
- `ALTER TABLE jobs ADD COLUMN server_error_retry_count INTEGER NOT NULL DEFAULT 0`

## Readiness hold (`HOLD_UNTIL_READY`)

`LoopMixin._execute` asks `engine_preflight.blocking_issues` about the job's engine between `_read_workspace_and_pool` and `set_active_pool`, so a job on an engine whose install requirements do not hold is put back before it takes a slot, a worker record or a session. The transition is `JobTransition.HOLD_UNTIL_READY` (`Queue.hold_until_ready`): `RUNNING → PENDING`, `started_at` NULL, `eligible_at` SET to now (the queue's clock) + `READINESS_HOLD_DELAY_S` (60 s), and every other column KEEP — `error`, `resume_inv_id`, `interruption_count`, `requeue_count` and `server_error_retry_count` are untouched. It is deliberately not `REQUEUE_PENDING` (bumps `interruption_count`, clears `eligible_at` and `resume_inv_id`), `REQUEUE_SERVER_ERROR` (bumps `server_error_retry_count`) or the failed-job requeues (bump `requeue_count`): a hold is not an interruption, a server error or a human re-queue, and must not spend the budgets those counters gate.

It writes no `error` and publishes no event — a held job is not a failure. The reason lives in the per-engine readiness report (`/api/health` `dispatch_readiness`) and in one log line per change of readiness. `_CLAIM_SQL`'s `eligible_at <= now` filter keeps the held job out of `claim` for 60 s without blocking other jobs, and the next pickup after the requirements hold runs it normally. Only `not_ready` holds (an `unknown` readiness is allowed and logged), and a `QueueError` while holding is logged and swallowed so `_execute`'s catch-all does not fail the job. The unblocker's and merge-gate remediation's dispatches are held here like any other job; `team_is_dispatchable` does not consult readiness. Design and the requirement semantics: [engine_preflight.md](engine_preflight.md).

## Job-lifecycle observability

Default Python logging emits at WARNING, so before this the dispatcher's per-job progression never reached `~/.alan/logs/alan.log` — a failed run left only the raw `agents/<role>.stream.jsonl` to spelunk. Now `alan/__main__.py` calls `logging.basicConfig(level=ALAN_LOG_LEVEL or INFO)` (and pins the `alan` logger to that level) on `python -m alan` startup, and the dispatcher logs each job's lifecycle:

- INFO `team start: task=… team=… inv=…` (`(resume)` suffix when `resume_inv_id` is set) before `_call_team`.
- INFO `team done: task=… team=… inv=… next=…` after a successful handover save.
- WARNING `job failed: task=… team=… inv=… error=…` in `_fail_job`. The `error` carries the real CLI text now that `claude_cli` preserves it (see §Server-error auto-retry); a transient 529 is no longer masked behind `subtype`/`stop_reason`.

Every **terminal (non-recoverable) job failure** — the `_fail_job` sink, i.e. everything except the recoverable `_fail_genuine` branch (which surfaces the Re-queue control instead) — also appends one line to `~/.alan/logs/job_failure_audit.jsonl` via the shared `append_jsonl_audit` (`alan/teams/_audit.py`): `{task_id, workspace_id, team, inv_id, error, server_error_retry_count}`. Root overridable with `ALAN_LOGS_ROOT` (the test-suite autouse fixture points it at a tmp dir, so the audit never pollutes the real logs dir). This gives a single greppable record of what died and why, alongside the per-team audits (impl / pr_merge / verification / resume / triage / loop_guard / predispatch).

## Usage-limit auto-pause

When the `claude` CLI returns an Anthropic usage/session-limit error, `alan.claude_cli` raises `UsageLimitError(ClaudeCliError)` carrying `raw_message` and `reset_at` (unix epoch + 120s safety buffer). Two independent detection signals trigger this:

- **Signal A — text phrase match.** `alan.usage_limit.is_usage_limit_message` matches the final `result.result` against `_LIMIT_PHRASES` (`"hit your limit"`, `"you've hit your limit"`, `"usage limit"`, `"session limit"`, `"rate limit exceeded"`). The reset epoch is parsed from the same text via `parse_reset_time` (timezone-aware → relative → local → 1h fallback). Covers both legacy "usage limit" wording and current "You've hit your session limit · resets …" wording. A failed result is classified against the spend-cap matcher first (§Spend-cap stop) and only falls through to this phrase list when that does not match.
- **Signal B — structured stream event.** `_StreamPumpState.handle` (`alan/claude_cli.py`) runs every parsed stream line through `_maybe_raise_rejected_rate_limit`: a `rate_limit_event` with `rate_limit_info.status == "rejected"` (via `reset_epoch_from_rate_limit_event`) raises `UsageLimitError("rate limit rejected mid-stream", resetsAt + buffer)` **as the event arrives**, after the line has been teed to the journal and passed to `on_event`. It does not wait for the final `result` event and does not depend on that result being an error, so a later successful result cannot mask a rejection. Wording-independent — protects against future Anthropic copy changes. It is always an ordinary auto-expiring pause, even when spend-cap text follows it in the same stream (the event raises before the result is read).

The dispatcher catches `UsageLimitError` between `team.run(...)` and the generic exception handler in `_run_team`. It calls:

1. `queue.pause_until(exc.reset_at)` — persists the pause epoch in `queue_meta` with monotonic-max semantics (SQL-level `MAX(CAST ... AS REAL)` so concurrent workers cannot race it down).
2. `_requeue_for_pause(...)` → the requeue ladder below: `queue.requeue_for_resume(job_id, inv_id)` for resume-capable teams, else `queue.requeue_pending(job_id)` for `PrincipalProxyTeam` / `PrMergeTeam`.
3. Publishes a `queue_paused` `TeamEvent` with `{reset_at, team, job_id, mode}`.

Crucially, `_fail_workspace` is NOT called on the success path — the workspace stays active and auto-resumes without human intervention.

### Forge (GitHub) failures ride the same two paths

`alan/teams/_forge_errors.py` classifies `gh` CLI failures in exactly one place (`classify_forge_failure`: `domain_absent` / `rate_limited` / `transient` / `auth` / `unknown`, marker tables shared with `classify_credential_failure`, which now delegates to it) and defines two exceptions that reuse the retry contract by subclassing — no dispatcher changes. Two marker-table invariants are load-bearing and pinned by named tests in `tests/test_forge_errors.py`: rate-limit markers are checked BEFORE auth markers, because GitHub's rate-limit rejections are also HTTP 403s and a rate limit is never a credential problem (`test_rate_limited_wins_over_auth_for_403_rate_responses`); and domain-absent markers use full phrases — bare "could not resolve" would collide with the DNS failure "could not resolve host" in the network table (`test_dns_failure_classifies_transient_not_domain_absent`).

- `ForgeRateLimited(UsageLimitError)` — raised when gh stderr carries a rate-limit marker (including the 2026-08-17 incident string "API rate limit already exceeded", which the pre-split marker table missed). `reset_at` is a fixed `now + FORGE_RATE_LIMIT_PAUSE_S` (900s) rather than a `gh api rate_limit` probe: the probe can itself fail under the same degradation, and the monotonic-max pause self-corrects if a premature resume re-trips. Rides §Usage-limit auto-pause — one shared queue pause, existing UI banner, auto-resume.
- `ForgeTransientError(ServerErrorRetryable)` — raised for network/5xx/timeout failures. A minority of call sites also raise it for `auth`/`unknown` gh failures, where a non-zero exit is never domain evidence: `_pr_branch.resolve_existing_branch` (via `_handle_pr_view_failure`, which raises on every classification except `domain_absent`) and `pr_merge._gh_pr_state` / `pr_merge._gh_pr_checks` (via `raise_for_infra`, whose non-raising return — `auth`/`unknown`/`domain_absent` — those callers fold into their own no-verdict fallback instead of raising further). By contrast, the merge-readiness probe (`_pr_ready._gh_pr_view_readiness`, backing `check_pr_merge_readiness`/`check_pr_verifier_blockers` — used by both the merge step and the verification gates) and the merged-state probe (`deploy_verify._pr_merge_info`) are deliberately narrower: only `rate_limited`/`transient` raise there, while `auth`/`unknown`/`domain_absent`/an empty decoded payload keep the no-verdict shape their escalation paths depend on (a `ReadinessUnavailable` for the readiness probe, `gh_ok=False` for the merged-state probe) — their `readiness_or_unavailable` callers (`dispatcher._enforce_pr_merge_gate`, `pr_merge._diagnostics_readiness_lines`) additionally absorb a `rate_limited`/`transient` raise into the same no-verdict shape rather than letting it surface as a routing error. Rides §Server-error auto-retry — ≤3 attempts with jittered backoff.

Only positively classified *infra* failures raise (`raise_for_infra` is the choke point); `domain_absent` (e.g. GraphQL "Could not resolve to a PullRequest", REST 404) returns to the call site, which owns domain policy — `resolve_existing_branch` returns `None` (audit `pr_view_not_found`) only on that confirmed shape, so verification's precondition escalation now states a confirmed fact instead of guessing "PR may be closed" during an outage. The global pause stops only `claim()`: already-running jobs finish, and if one hits GitHub meanwhile its own gh call raises the same way (monotonic-max keeps concurrent trips safe). Teams never consult pause state — they have no `Queue` handle by design.

On a `ForgeRateLimited` trip, `_handle_usage_limit` additionally writes `queue_meta['forge_degraded_v1']` (`FORGE_DEGRADED_META_KEY` in `alan/queue.py`) with a `ForgeDegradedMarker` (`{reset_at, detail[, remaining, limit]}`, the headroom keys written only when both values are known) and records `"github rate limited"` (instead of `"usage limit reached"`) as the workflow interrupt error. The meta row is never explicitly cleared: the `forge_degraded` health surface (`gather_forge_degraded` in `triage_pregate`, describer in `alan/health.py` — see [health.md](health.md)) reports blocked only while `reset_at` is in the future, so the finding self-expires exactly when the pause does. A later trip simply overwrites the row unless the stored window already reaches at least as far: the writer's guarded compare and the `triage_pregate` reader share `parse_forge_degraded` (`alan/queue.py`). Any stored value that fails the model — bad JSON, non-object JSON, a missing or non-numeric `reset_at` — is logged and overwritten by the writer, and read as absent by the pre-gate, rather than raising inside the handler before the pause. A non-text `detail` is coerced to text and never discards a marker with a usable `reset_at`.

### The requeue ladder (`UsageLimitMixin._requeue_after_interrupt`)

Every requeue in step 2 is keyed `WHERE id = ? AND status = 'running'`, so it raises `QueueError` if the row left `RUNNING` for any reason while this worker was still alive — which happens when a second process reconciles the same queue DB, or when an operator edits a row by hand. Swallowing that error stranded the job permanently: the workflow doc on disk was already `interrupted` (resumable, session id intact) but no queue row any loop would ever claim, and — because the workspace stayed `active` — no health finding and no inbox item either. See the 2026-08-10 incident.

The three pause/retry paths (`_handle_usage_limit`, `_handle_server_error`, `Dispatcher._pause_job`) therefore share one ladder, whose invariant is: **the job ends the call either runnable (`PENDING`) or parked to `AWAITING_INPUT` — never silently gone.**

1. Attempt the path's own requeue. Success → done.
2. On `QueueError`, re-read the row with `queue.get_job(job_id)` and branch on what it actually is:
   - `PENDING` → something already made it runnable; log at INFO and let the caller publish its `queue_paused` / `job_retry_scheduled` / `job_paused` event as usual, because the job really will run again. Parking here would mark healthy work broken.
   - `COMPLETED` → the work finished out-of-band while this worker was in its exception handler. Log at INFO and return "not requeued", which suppresses the caller's event: announcing `job_paused` or `job_retry_scheduled` for a finished job would promise a run that will never happen. Do not park either — the job succeeded. (Suppressing `queue_paused` here costs nothing: the pause banner reads `/api/health`'s `queue_paused` / `paused_until`, not this event, and `pause_until` has already been persisted.)
   - `FAILED` → `queue.requeue_failed_with_resume(job_id, resume_inv_id, eligible_at=…, server_error_retry_count=…)`, the `status='failed'`-keyed sibling of the normal requeues. Unlike `requeue_failed_for_resume` (which preserves the column, and is what the manual Re-queue path uses), this one *sets* `resume_inv_id` — necessary because the reconciler's terminal `mark_interrupted_and_fail` leaves it NULL. `None` clears it, so a non-resume team can never end up carrying a marker that `reject_resume_inv_id` would reject on the next run. The server-error path passes its computed `eligible_at` and incremented `server_error_retry_count` so recovery preserves the backoff window and the retry budget rather than restarting either.
   - `RUNNING`, or the row is gone, or the recovery requeue also raises → not recoverable.
3. Not recoverable → log `<label> requeue failed for job <id>` at WARNING, publish a `job_stranded` `TeamEvent` with `{reason}`, and call `_fail_workspace` so the workspace lands in `AWAITING_INPUT` with a synthetic blocker. That park is what makes the strand *visible*: `ws_stuck` (health) and `alan.incident.derive_incidents` both key off `{awaiting_input, escalated, failed, partial}`, so an `active` workspace with a dead job surfaces nowhere. Known limit: `_fail_workspace` returns early for a DAG parent (`ws.meta.tasks`), so a stranded subtask job emits `job_stranded` but does not park its parent.

`RUNNING` is deliberately treated as unrecoverable rather than as "already fine": the requeue SQL is keyed on `status='running'`, so a `QueueError` proves the row was not running when it ran. A row that reads `RUNNING` afterwards is a zombie no worker will re-claim — the reconciler's next startup sweep is the correct owner of it.

`Queue.claim()` returns `None` while `paused_until() > time.time()`, so no worker claims new jobs during the pause. `_loop` caps its idle sleep to `min(paused_until - now, _poll_interval)` so a worker re-claims promptly once the pause lapses.

`queue_meta` is a `TEXT PRIMARY KEY` k/v table created by `_SCHEMA` (idempotent `CREATE TABLE IF NOT EXISTS`); no schema version bump is required.

`/api/health` returns `{"ok": True, "queue_paused": bool, "paused_until": float | null, "spend_cap_stop": {cause, fix, regain_at?} | null, …}` so operators and the frontend banner can observe the pause state. `spend_cap_stop` is optional (defaulted to `null` in the response model, so `schema.ts` marks it `?`) and is described in the next section.

### Spend-cap stop (stops until Resume, not until a timestamp)

Anthropic refuses work with a spend-cap response when a monthly spend limit is reached: the tier spend cap (HTTP 429), or an organisation/workspace limit the operator set themselves (HTTP 400). Retrying hourly until the month rolls over is wrong for this cause, so it is the one usage-limit failure that stops the fleet **until the operator presses Resume** (decision PD17). Every other rate-limit and usage-limit behaviour above is unchanged.

**Detection.** `alan.usage_limit.is_spend_cap_message` matches a failed result's text case-insensitively: `you have reached your [specified] [workspace] API usage limits`, or the literal token `enforced_spend_limit_reached` (which also covers the CLI's `API Error: 4xx {json}` wrapping). `claude_cli._raise_if_limit` is the single check shared by the three failed-result sites (`_extract_result_text`, `_maybe_raise_transient`, `_raise_for_error_event`) and runs the spend-cap check **before** Signal A, because the spend-cap wording also contains "usage limit". It never applies to rate-limit stream events (Signal B), stderr, driver-loop logs, or successful results. `SpendCapReached(UsageLimitError)` carries `reset_at = SPEND_CAP_HOLD_EPOCH` and `regain_at` (an ISO-8601 UTC string from `parse_regain_at` when the message states "regain access on YYYY-MM-DD [at HH:MM]", else `None`). It is still a `UsageLimitError`, so chats, brief refinement, verification grounding and driver-loop runs classify it exactly as before; only the dispatcher's `_handle_usage_limit` distinguishes it.

**The hold.** `SPEND_CAP_HOLD_EPOCH = 4102444800.0` (2100-01-01 UTC) is finite, serialises as a plain JSON number, and converts to a date in Python and in a browser (`Date` accepts up to ~8.64e15 ms). It is deliberately not infinity: `paused_until` reaches JSON, SQLite `CAST … AS REAL`, `datetime.fromtimestamp` and `new Date(...)`, and a non-finite value breaks at least one of them. `Queue.stop_until_resume(regain_at)` writes the hold through the same monotonic-`MAX()` `_PAUSE_UNTIL_SQL` as `pause_until`, plus the marker `queue_meta['spend_cap_stop_v1'] = {regain_at, stopped_at}`, inside one explicit `BEGIN`/`COMMIT` (rolled back together on error, so a hold without its marker cannot persist from a failed write). Both live in the existing queue database, so the stop survives a service restart. No provider text is stored: the marker holds only the parsed regain date and alan's own timestamp, and the user-facing cause/fix wording is alan's own (`SPEND_CAP_CAUSE`/`SPEND_CAP_FIX` in `alan/health.py`).

**Everything that respects the pause respects the stop.** `claim()` returns `None`; `_loop` caps its idle sleep to `min(paused_until - now, poll_interval)`; `driver_loop_schedule`, `unblock_sweep` and every other `paused_until()` reader see an ordinary future pause; the reconciler's triage sweep is a queued job and cannot run. The stop never ends on its own — not at the stated regain date, which is informational only. An ordinary usage-limit or GitHub pause that trips during the stop goes through `pause_until`'s `MAX()` and can neither end nor shorten it.

**The tripping job.** `_handle_usage_limit` calls `stop_until_resume` instead of `pause_until`, then takes the same interrupt-and-requeue path as an ordinary pause (`_requeue_for_pause` → the requeue ladder below) and publishes `queue_paused` with the hold. The job is never failed because of the spend cap, and the workspace stays active. After Resume the job is claimed normally; if the cap still applies, that job trips the stop again.

**Reporting.** `GET /api/health` builds `spend_cap_stop` (`SpendCapStop`: `cause`, `fix`, `regain_at` when stated) on every request straight from the marker via `load_spend_cap_stop`, independent of the periodic health sweep: it appears when no sweep has ever run and when the sweep's state has gone stale. There is deliberately no Health findings row and no change to the health verdict. A stored marker that fails to parse (bad JSON, a non-object, a `regain_at` that is not a timezone-aware ISO-8601 string) reads as absent; the hold still holds the fleet and the frontend shows the ordinary pause banner — accepted. The frontend's pause banner has a stop variant that renders the cause, the fix and the regain date as text with the existing Resume control and no countdown of its own.

**Owner proof.** `tests/test_spend_cap_owner_proof.py` pins the pre-change classification of every input that must not become a stop — the ordinary "hit your limit" / session-limit / "usage limit exceeded" / "rate limit exceeded" wording, the legacy `usage limit reached|<epoch>` form, a rejected rate-limit event followed by spend-cap text, an ordinary API 429 ("would exceed the rate limit", still a failed job), the GitHub rate limit (still a 900 s pause), the near-misses "check your API usage limits" / "You have reached your limit" / "Character limit for this field is 500", a successful result that quotes the spend phrase, and "Your credit balance is too low" (still a failed job) — comparing exception type and pause duration under a frozen clock. The file was committed first and passes on the code that predates the stop.

**Residual risk.** The wording shown when a paid Claude plan's extra-usage limit is exhausted is undocumented and unverified. If that response happens to contain the spend-cap phrase or token, it would trigger a false terminal stop that needs a manual Resume. Handling subscription extra usage is out of scope; the risk is recorded here rather than mitigated.

### Operator-triggered clear (`Queue.clear_pause` / `POST /api/queue/resume`)

`Queue.clear_pause() -> float | None` is the operator-triggered counterpart to `pause_until`: it reads the current `paused_until()` value, then DELETEs both the `paused_until` meta row and the `spend_cap_stop_v1` marker inside one explicit `BEGIN`/`COMMIT`, and returns the prior value — all inside one `self._lock` (`RLock`) acquisition, so the returned value is atomic against a concurrent trip landing between the read and the delete, and a Resume never leaves a marker without its hold or the reverse. It DELETEs rather than writing a past epoch through `pause_until` itself, because `_PAUSE_UNTIL_SQL`'s `ON CONFLICT DO UPDATE SET value = MAX(old, new)` would silently discard a smaller (past) value and leave the existing future pause in place. `clear_pause()` on an already-unpaused queue is a harmless no-op that returns `None`.

`POST /api/queue/resume` (`alan/routes/infra.py`) is gated by the same `Depends(require_control_token)` dependency as every other state-changing control (driver-loop pause/resume, engine posture, …) — 401 with no token, 403 on a mismatch. On success it calls `clear_pause()` in a threadpool, appends one row (`cleared_at`, `prior_paused_until`) to `queue_pause_audit.jsonl` under `logs_root()` via the shared best-effort `append_jsonl_audit` (a dropped audit write never fails the request — the pause is already cleared by the time the write is attempted), publishes a `TeamEvent("queue_resumed", {})` on the global pubsub channel, and returns `QueueResumeAck {ok, queue_paused, paused_until}` reflecting the post-clear state. It never calls `workspace.record_intervention` or `gold_label.record_gold_label` — an operator clearing a fleet-wide pause is not a judgement about any specific piece of work, so it must not feed the learning-metrics surfaces those calls back.

No dispatcher, driver-loop, or `alan/routes/events.py` change was needed to make the clear self-resuming: `Queue.claim()` already re-reads `paused_until()` on every call, `LoopMixin._loop` already caps its idle sleep to `min(paused_until - now, poll_interval)`, `driver_loop_runner` already ticks on a flat 30s cadence, and `"queue_resumed"` already falls through `_kinds_for` to the default SSE kind set (which includes `"health"`) since it names no more specific kind — so the frontend banner's own `refetch()` call (see [frontend.md](frontend.md)) is what makes the UI update promptly, not the SSE event itself carrying pause state.

The clear deliberately leaves `queue_meta['forge_degraded_v1']` untouched. The usage-limit pause, a `ForgeRateLimited` trip and the spend-cap stop all write the *same* `paused_until` row (§Usage-limit auto-pause, §Forge (GitHub) failures, §Spend-cap stop above), and `clear_pause` never inspects which of them wrote it: it deletes that one row, plus the spend-cap marker unconditionally — a single Resume ends the hold, the stored stop reason, the reported `spend_cap_stop` and the banner's stop variant at once — and stays cause-blind otherwise (making it cause-aware is out of scope by design). This means the `forge_degraded` health finding can keep reporting blocked by its own `reset_at` even after `/api/queue/resume` has made the queue claim work again; that finding self-expires on its own schedule regardless of the queue-level clear.

`ALAN_USAGE_LIMIT_SAFETY_BUFFER_SECONDS` (positive int; default `120`) — overrides the safety buffer added to the parsed reset time in `alan.usage_limit.parse_reset_time`. Non-positive or unparsable values fall back to 120. Set to `1` in E2E tests so the pause expires quickly.

## User-initiated pause (Stop / Resume)

Orthogonal to the global wall-clock pause above, a user can pause an individual workspace from the task-detail header (`Stop` / `Resume` buttons in `alan/web/src/features/workspace/pages/Workspace.tsx`). The state lives in a separate `paused_tasks(task_id TEXT PRIMARY KEY)` table created idempotently by `_SCHEMA`; `Queue.claim()`'s `_CLAIM_SQL` adds `AND task_id NOT IN (SELECT task_id FROM paused_tasks)` so paused tasks are skipped without blocking work on other workspaces. `Queue.delete_jobs(task_id)` also clears the `paused_tasks` row to keep the table from accumulating orphans.

The dispatcher owns two new pieces of state: a `ProcRegistry` (per-job `Popen` map with SIGTERM → 5s grace → SIGKILL) and a `_user_paused: set[int]` of job IDs whose subprocess was killed by an explicit user action. The team-run plumbing exposes `on_proc_started: OnProcStarted` from `alan/claude_cli.py:23` through every `Team.run` so the dispatcher can register the live `Popen` in the registry without coupling teams to the registry directly.

`Dispatcher.interrupt_task(task_id)`: finds the running job via `queue.list_jobs(task_id=…, status=RUNNING)`, atomically adds `job.id` to `_user_paused`, calls `queue.pause_task(task_id)`, then terminates the registered Popen. Returns `False` (404) if no running job is found.

`Dispatcher.resume_task(task_id)`: calls `queue.unpause_task(task_id)` (clears the per-task paused_tasks row), then checks `queue.list_resumable_failed(task_id)` — FAILED rows with a non-null, non-empty `resume_inv_id`. If one exists, it calls `queue.requeue_failed_for_resume(job_id)` to flip the row FAILED → PENDING (preserving `resume_inv_id`, incrementing `interruption_count`, clearing `error` / `finished_at`) and publishes a `job_requeued_for_resume` event. The dispatcher's existing claim loop then picks it up and calls `team.run(..., resume_inv_id=inv_id)` as usual.

The exception handler split via `_handle_team_exception` branches on `_user_paused` before falling through to `_fail_workspace`. The user-pause branch (`_pause_job`) mirrors `_handle_usage_limit` structurally: (a) `workflow_interrupt.interrupt_workflow_on_disk(ws, inv_id, error="user paused", resumable=team.supports_resume)`; (b) the shared `_requeue_for_pause(job, ws, team, inv_id, label="user-pause")` — i.e. the same requeue ladder, so a Stop whose row moved underneath it recovers or parks instead of vanishing; (c) publishes a `job_paused` `TeamEvent`. It passes the live `inv_id`, not `job.triggered_by_invocation_id or ""` — an empty-string `resume_inv_id` is excluded by the `resume_inv_id != ''` filter in `list_resumable_failed*`, so the old fallback produced a row the Re-queue control could not see. On the success path Stop NEVER calls `_fail_workspace` — the workspace flip to `Status.PAUSED` is the server endpoint's responsibility, not the dispatcher's.

Diff vs. the global `paused_until` mechanism: the global pause is wall-clock-based (auto-resumes after the Anthropic reset epoch); the per-task pause is user-flag-based (only the explicit `/resume` endpoint clears it). Both can coexist; `Queue.claim()` checks both gates.

### Resuming from a failed-with-resume_inv_id job (reconciler fallback and manual Re-queue)

A recovery path handles workspaces stuck in `AWAITING_INPUT` because they landed there via either (a) the reconciler's partial resume fallback, or (b) a genuine node failure on a multi-node resumable workspace where at least one prior node succeeded. In both cases the failed queue row carries a non-null `resume_inv_id` that serves as the recoverability marker.

`queue.mark_interrupted_and_fail` accepts an optional `resume_inv_id` keyword argument; when provided it sets the marker atomically in a single SQL statement (used by the dispatcher's `_fail_genuine` helper on the recoverable path, and by the reconciler's re-derive flip which leaves the old row's marker alone since a fresh job has already been enqueued). When both `resume_inv_id` and `clear_resume` are omitted, the `INTERRUPT` row of `lifecycle.JOB_TABLE` applies (`resume_inv_id` is `KEEP`) and `resume_inv_id` stays at whatever the prior value was (usually NULL for a genuine crash, or the last good inv_id for a usage-limit requeue). The reconciler's own terminal fallback (§Restart resilience above) is the one caller that always decides explicitly: it computes a fresh marker every time and passes `clear_resume=True` whenever that marker is absent, so a stale `resume_inv_id` from an earlier cycle can never survive onto a row the fresh computation says is not resumable.

The recoverability predicate (`_is_recoverable_failure` in `alan/dispatcher.py`) requires both:
1. `team.supports_resume is True`
2. `not ws.meta.tasks` (single-task workspace)

For **multi-task** workspaces where `ws.meta.tasks` is populated and `team.supports_resume` is True, `_fail_genuine` delegates to `_fail_recoverable_subtask` instead of cascading failure. That method: acquires the per-workspace lock (`_get_workspace_lock(job.workspace_id)`); re-reads the workspace; resets nodes via `workflow.reset_failed_nodes_for_rerun`; flips the workspace to `Status.AWAITING_INPUT` (does NOT call `_propagate_and_cancel`, leaving dependent subtasks in their current pending/blocked state so they can run after recovery); and marks the job `interrupted+failed` with `resume_inv_id=inv_id`. On Re-queue the recovered job runs fresh (not via `claude --resume`) because `reset_failed_nodes_for_rerun` resets nodes to `pending`, making `node_is_interrupted` return False.

Before marking the failure, `workflow.reset_failed_nodes_for_rerun(ws, inv_id)` resets any `failed`/`running` nodes back to `pending` (clearing `error`, `started_at`, `completed_at`, `claude_session_id`) so that re-entry takes `run_or_resume_node`'s fresh path (`_run_fresh_node`) instead of crashing with `WorkflowError("duplicate node id")` from `_activate_pending`. The `node_is_interrupted`-driven two-arm ladder that used to live separately in `run_or_resume` (`_pr_handover.py`) and `SingleAgentTeam.run` (`_base.py`) no longer exists as its own code — both are now thin callers of `_base.run_or_resume_node`, whose cached → attach → resume → fresh ladder is the sole place this routing decision is made. This separates the "a recovery resume_inv_id exists" signal (queue layer) from the "this specific node was interrupted mid-run" signal (workflow layer).

`GET /api/workspaces/{task_id}` exposes:
- `has_resumable_failed_job: bool` — drives the Re-queue control's visibility. Computed by `alan/routes/_workspace_detail.py::has_resumable_failed_job`, which reads only the workspace's **most recent** FAILED job (`queue.list_jobs_for_workspace(task_id, status=JobStatus.FAILED)[-1]`) and requires both a non-empty `resume_inv_id` on that job **and** `team_supports_resume(latest.team)` (`alan._reconciler_never_started`) — not "any resumable failed job ever" (the workspace-wide `list_resumable_failed_by_workspace` query this replaced, the mechanism behind the contradictory-flag bug in #1510). See [worker_records.md](worker_records.md) for the full resume contract this flag participates in.
- `requeue_count: int` — `MAX(requeue_count)` across all jobs for the task; a dedicated column bumped exclusively in `requeue_failed_for_resume` so it accurately counts manual re-launches independently of `interruption_count` (which conflates crashes, usage-limit pauses, and user stops).

`POST /api/workspaces/{task_id}/resume` accepts the call when the workspace is `AWAITING_INPUT` and a resumable failed job exists (in addition to the normal `PAUSED` path), then delegates to `Dispatcher.resume_task` which requeues the row to `PENDING` via `queue.requeue_failed_for_resume`. On success the server flips the workspace meta to `Status.ACTIVE`.

The frontend shows:
- **Re-queue** button (testid `requeue-button`) when `status == "awaiting_input"` and `has_resumable_failed_job`; calls the same `/resume` endpoint as the user-pause Resume flow.
- **Resume** button (testid `resume-button`) when `status == "paused"`.
- A **"retried N×"** span (testid `requeue-count`) adjacent to either control when `requeue_count > 0`.

Double-activation is idempotent: after the first activation the job is `PENDING` (not `FAILED`), so `requeue_failed_for_resume` raises `QueueError("not a failed job")` which `resume_task` silently swallows; the workspace is already `ACTIVE` so the endpoint's status gate returns 409 to the second request.

**Test coverage.** The recoverable-failure path is verified by unit + integration tests: `tests/test_dispatcher.py` (the `_fail_genuine` → recoverable-vs-not branch, `_fail_recoverable_subtask` multi-task path including no-propagation to dependents, OSError fallback, QueueError swallow, and manager-summary trigger; idempotent double-activation, `job_failed` SSE on the `QueueError` branch), `tests/test_queue.py` (`requeue_count` column, `mark_interrupted_and_fail(resume_inv_id=…)` marker, `requeue_failed_for_resume` accumulation, `requeue_count_for_task` aggregation), `tests/test_workflow.py` (`reset_failed_nodes_for_rerun` clears poisoned session ids), and `tests/test_teams_pr_handover.py` (`run_or_resume` routing: pending node → fresh run, interrupted node → resume, `resume_inv_id` parameter ignored). The Re-queue UI surface (button visibility, "retried N×" indicator, `/resume` dispatch) is covered by `alan/web/src/pages/Workspace.test.tsx`. A full-stack Playwright spec is intentionally **deferred**: driving a live genuine-failure that leaves a `resume_inv_id`-set row does not reach the recoverable state deterministically under the shared E2E webServer, so an always-failing spec would gate CI without adding real signal. The unit/integration layer above is the source of truth for this feature.

## Multi-task DAG execution (d6/d7/Gap 1/Gap 2)

### Per-workspace serialization (d6)

The `_CLAIM_SQL` per-workspace guard (`workspace_id NOT IN (SELECT workspace_id FROM jobs WHERE status = 'running')`) is intentionally kept for multi-task workspaces. Tasks within the same workspace always execute serially in dependency order; parallelism is only across distinct workspaces. Intra-workspace parallel execution (multiple tasks of the same workspace running concurrently) is deferred future work.

### FAILED-parent policy (d7)

When a task in a multi-task workspace fails:

1. `Dispatcher._observe_task_failure` runs best-effort inside `_fail_job` (after the durable `queue.fail()` call) and calls `_propagate_task_failure` to mark the failed task and all its transitive dependents as `TaskStatus.FAILED`.
2. Any task whose `depends_on` parent is in `FAILED` state is blocked by `_task_blocked` (the parent is neither in `completed_ids` nor can become COMPLETED). `_ready_tasks` therefore never returns such tasks.
3. Once every task in `ws.meta.tasks` is in `{COMPLETED, FAILED}`, `_workspace_terminal_status` fires:
   - ≥1 COMPLETED → `Status.COMPLETED`
   - 0 COMPLETED (all FAILED) → `Status.FAILED` (definitive failure; no user action can recover; distinct from `AWAITING_INPUT`)

Legacy single-task workspaces (`meta.tasks == []`) are unaffected: the observer returns early when `meta.tasks` is empty, and the existing `_advance_workspace_dag` / `_fail_workspace` paths handle their transitions unchanged.

### Reconciler restart safety for multi-task workspaces (Gap 1)

`reconciler._load_workspace` now reads by `job.workspace_id` when set, falling back to `job.task_id` for rows where `workspace_id` is empty (pre-migration legacy rows). For multi-task workspaces `job.task_id` is the per-task id (e.g., `"step-a"`) while the workspace directory lives under `job.workspace_id` (e.g., `"my-project"`). Without this fix a service bounce mid-DAG would fail to load the workspace and flip the job to FAILED without a clean workflow interrupt.

### Stalled-DAG repairer (Gap 2)

**Source:** `reconciler._repair_stalled_dag`, helpers `_terminal_pr_merge_handovers`, `_build_inv_to_task`, `_build_lineage_deliveries`, `_apply_deliveries`, `_try_complete_subtask`, `_is_subtask_live`.

A subtask DAG can stall when the `pr_merge` team completes its handover (writing a terminal handover file) but the `_advance_workspace_dag` call that should have marked the subtask COMPLETED never ran — because the worker restarted before it could post-process the handover. On the next startup `reconcile_on_startup` calls `_repair_stalled_dag` for every multi-subtask workspace.

**Handover scan** (`_terminal_pr_merge_handovers`): reads every handover file in the workspace directory. Only records where `from_team == "pr_merge"` AND `handover_type == "terminal"` are considered. Non-`pr_merge` handovers, and `pr_merge` handovers of any other type (`"escalation"`, `"forward"`, etc.) are ignored even when they carry a `pr_number`.

**Lineage-based PR assignment** (`_build_lineage_deliveries`): instead of positional matching (the old `_pr_merge_pr_numbers` approach), the repairer joins two sources of truth:
1. Each terminal handover carries `from_invocation_id` — the `inv_id` of the `pr_merge` run that produced it.
2. Each queue job carries `triggered_by_invocation_id` set to the inv_id pre-allocated for that job's own run. A `pr_merge` job also has `task_id == subtask_id`.

The join `handover.from_invocation_id == queue_job.triggered_by_invocation_id` (both equal the same inv_id for the same run) resolves `queue_job.task_id` as the genuine subtask owner, with no positional ambiguity. If a handover's `from_invocation_id` does not appear in any `pr_merge` queue job, that handover is silently ignored (no lineage, no completion).

**Deduplication**: the same `(subtask_id, pr_number)` pair can appear in multiple handover records (e.g. a retry after a restart). `seen_pairs: set[tuple[str, int]]` tracks visited pairs; duplicates are skipped before accumulation so they cannot inflate the completion count.

**Conflict resolution**: two types of ambiguity are detected and both result in the subtask being excluded from the repair:

- *Same subtask, two different PRs* (`_accum_delivery`): a subtask already in `deliveries` that is seen again with a different `pr_number` is removed from `deliveries` and added to `conflicted`. Subsequent records for a conflicted subtask are ignored (early-return guard).
- *Same PR, two different subtasks* (`_drop_cross_pr_conflicts`): iterates `pr_to_subtasks` (accumulated alongside `deliveries` during the scan); if any `pr_number` maps to more than one distinct subtask, all those subtasks are removed from `deliveries`.

**Liveness check** (`_is_subtask_live`): before marking a subtask COMPLETED the repairer checks `queue.list_jobs(task_id=subtask_id, workspace_id=…, status=PENDING)` and `…, status=RUNNING`. If either returns a non-empty list, the subtask still has active work in the queue and must not be completed.

**Evidence stamping**: when a subtask is completed by the repairer, `workspace.record_task_evidence` stamps `"PR #<n>"` on the subtask's DoD clauses — identical to the evidence the normal `_advance_workspace_dag` path would stamp.

## Mid-chain escalate/await_human in multi-task workspaces

When a subtask's chain reaches an `escalate` or `await_human` router decision inside a multi-task workspace, `_finalize_blocked_decision` performs two updates:

1. **Workspace-level**: `workspace_mod.transition` sets the workspace to `ESCALATED` (for `escalate`) or `AWAITING_INPUT` (for `await_human`) — same as the single-task path.
2. **Subtask-level** (multi-task only, i.e. `ws.meta.tasks` non-empty): `workspace_mod.update_task_status` sets the specific subtask's `Task.status` to `TaskStatus.AWAITING_INPUT` and stamps `Task.blocked_handover_id` with the handover's id. This makes the blocked subtask's state truthful in the DAG, pins the rescue handover the subtask's next dispatch inherits (see §Resolving a subtask's prior handover below), and prevents `_workspace_terminal_status` from firing prematurely while the task awaits human input.

### Resolving a subtask's prior handover

`alan.dispatch.prior_handover_for_task(ws, task_id)` decides which earlier handover a manual, propose-mode, auto-continue or operator-attach dispatch inherits. Handovers are stored per workspace and `Handover.task_id` is the *workspace* id, so a handover carries no subtask identity of its own; workspace recency alone would hand a sibling subtask's newest handover to whichever subtask is dispatched next. A sibling's correctly PR-less escalation then reached another subtask's `implementation_fix`/verification dispatch, which reported "no resolvable pull request" and parked with an escalation carrying no question.

**Resolution order**, for a dispatch onto a subtask:

1. the subtask's pinned `Task.blocked_handover_id`, if it has one — terminating: a pin naming a handover that is not on disk resolves to nothing and never falls through to recency;
2. otherwise the most recent handover attributed to that subtask — the subtask's own handovers;
3. otherwise none. A subtask that has never produced a handover inherits nothing, never a sibling's.

**Attribution** is `handover.from_invocation_id` → that invocation's `WorkflowDoc.source_task_id`, the durable record written when each unit of work is created (`enqueue_with_pending_workflow`, the dispatcher's own enqueue paths and the reconciler all seed it; pre-split invocations carry the workspace id). It is read through `workflow.load_workflow_cached` once per resolution — one pass over the distinct `from_invocation_id` set, never once per candidate handover, and `list_invocations` is never consulted. A missing, unreadable, malformed-id or corrupt workflow document, or one with a blank `source_task_id`, leaves its handovers unattributed. No handover field and no `SCHEMA_VERSION` change is involved, and the filter is deliberately **not** `handover_chain_id`: that field is a different, real filter (revisit resets, recorded answers) and one subtask can carry more than one of it.

**Pull-request recovery** is applied to whichever handover the order above selects — the pinned one included — on split and unsplit workspaces alike. When the selected handover carries no `pr_number` and an earlier handover attributed to the same subtask does, the nearest earlier such handover donates its number and only that field is filled in (`model_copy`); `handover_id`, `handover_chain_id`, `from_invocation_id`, summary, forbidden actions and instructions are untouched, so the returned object still names a handover on disk and `dispatch_team_core` still records it as the job's `parent_handover_id`. A sibling's pull request is never a source, and an unattributed handover is never a donor. This is what frees a subtask pinned to its own PR-less escalation (the pin `_finalize_blocked_decision` stamps on the very escalation it just wrote) without a hand repair.

**Fallback.** If no handover on the workspace attributes to any subtask id (`{t.id for t in ws.meta.tasks}`, or the workspace id when unsplit) — a restored, salvaged, pre-attribution or all-pre-split workspace — the resolver behaves exactly as it did before: the pin if present, else the newest handover, with no recovery. The switch is all-or-nothing at the workspace level. Where only some handovers attribute, an unattributed one is returned for a subtask only through that subtask's pin.

**The in-memory limit.** Recovery is not persisted. The queue row's `parent_handover_id` still names the PR-less escalation, and `alan.dispatcher._load_prior` — the one place a job's parent is re-read from disk — re-applies the recovery through `alan.dispatch.recover_prior_pr(ws, job.task_id, found)` so the worker sees the same handover the host resolved. Any other reader of that id sees no PR. The `_MissingParentHandoverError` raise is unchanged.

**Known limit.** A subtask that has never produced a handover cannot have a pull request attached to it, and the operator attachment repair (`POST …/attach-pr`) remains the answer for a subtask whose own history genuinely carries no PR (it refuses `no_prior_handover` for such a subtask). Attaching a PR the subtask's own handovers already carry now takes the same-PR re-pin path instead of appending an amendment.

**Accepted consequence.** `assert_team_dispatchable` also runs when a human answers a blocking question and when a workspace is created with a team, so a recovered number makes the operator fix-cycle count and the fix-cycle ceiling apply where they previously no-op'd on a null. A subtask past its ceiling meets the existing ceiling refusal, which carries an answerable override — a better outcome than a question-less park.

**Sibling signal-preservation**: `_stamp_status_for_advance` guards against a completing sibling clearing the human-attention signal. When the workspace is `ESCALATED` and any task is in `TaskStatus.AWAITING_INPUT`, the method returns without flipping the workspace to `ACTIVE` — the escalation signal persists until the blocked subtask is actually resolved (marked `COMPLETED` by a subsequent run).

**Stall guard**: `_maybe_surface_stall` uses `_has_awaiting_subtask` to skip the stall-detection path when any task is in `AWAITING_INPUT`. The apparent DAG stall (no queue jobs for the non-terminal tasks) is intentional in this case — the blocking subtask is waiting for human input, and re-surfacing `AWAITING_INPUT` from `_maybe_surface_stall` would fire a duplicate manager summary and overwrite `ESCALATED` with `AWAITING_INPUT`.

## Worker job-failure containment

**Source:** `alan/dispatcher.py`, `alan/handover.py`, `alan/routes/_deps.py`, `alan/routes/infra.py`

Unhandled exceptions inside a worker used to propagate out of `_loop`, killing the thread permanently. The containment changes ensure worker threads never die from job-level errors.

### `_execute` top-level containment

`Dispatcher._execute` wraps its entire body in `except Exception as exc:` (noqa BLE001). Any exception not already handled by the inner `team.run` / workspace / prior-handover paths is caught here, logged at ERROR via `logger.exception`, and then handed off to `_safe_fail_job` so the queue row is not left RUNNING. The error message stored on the failed job starts with `"internal error: "` followed by the exception message.

### `_safe_fail_job` fault-tolerant failure recorder

`Dispatcher._safe_fail_job(job, reason)` is the single call site used by the `_execute` containment path. It calls `self._fail_job(job, reason)` and catches two exception shapes:

- `QueueError` — raised by `queue.fail()` when the job is no longer RUNNING (e.g., it was already failed by a concurrent path). Logged at WARNING; the caller continues normally.
- Generic `Exception` — an unexpected error inside `_fail_job` itself (e.g., disk full, SQLite I/O error). Logged at ERROR via `logger.exception`; the caller continues normally.

`_safe_fail_job` never re-raises. Its sole purpose is to guarantee that a failure in the failure-recording path cannot crash the worker.

### `_loop` per-iteration backstop and `_on_worker_exit`

`Dispatcher._loop` wraps each `while not self._stop.is_set()` iteration in `try/except Exception:` (noqa BLE001). Any exception that escapes `run_once()` — including unexpected exceptions from `_execute` that bypass the inner containment — is caught, logged at ERROR via `logger.exception` with the message `"_loop: unexpected error in iteration; continuing"`, and the loop continues on the next iteration.

The outer `try/finally` structure ensures `_on_worker_exit()` is always called when the loop exits, regardless of how it exits (normal `_stop` signal or a pathological unrecoverable raise):

```python
def _loop(self) -> None:
    set_active_pool(self._slot_pool)
    try:
        while not self._stop.is_set():
            try:
                ...
            except Exception:  # noqa: BLE001
                logger.exception("_loop: unexpected error in iteration; continuing")
    finally:
        self._on_worker_exit()
```

### Worker liveness tracking

`Dispatcher` maintains a count of live (still-running) worker threads:

- `_alive_worker_count: int` — protected by `_alive_lock: threading.Lock()`, initialized to `0` in `__init__`.
- `Dispatcher.start()` increments `_alive_worker_count` **before** launching each thread (under `_alive_lock`) so the count is never transiently below the true value.
- `Dispatcher._on_worker_exit()` decrements `_alive_worker_count` (under `_alive_lock`). Called exclusively from `_loop`'s `finally` block, so it fires on normal shutdown AND on any unexpected loop termination.
- `live_worker_count` property — acquires `_alive_lock` and returns `_alive_worker_count`. Zero before `start()`, equals `concurrency` while running, zero after `stop()` completes.
- `configured_worker_count` property — returns `self._concurrency`; no lock needed (immutable after construction).

### Worker-pool heartbeat (`alan/worker_liveness.py`)

Beyond the in-process counters above, `_publish_worker_state` (`LoopMixin`, `alan/_dispatcher_loop.py`) durably records the same `_alive_worker_count`/`_concurrency` pair to `queue_meta` (key `dispatcher_worker_state_v2`, `WORKER_STATE_META_KEY`) as a `worker_liveness.DispatchLoopReading(live_loops, configured_loops, observed_at)` — a frozen validated pydantic model; an infinite, NaN or out-of-range `observed_at` fails validation, which `worker_liveness.parse` maps to "no reading" — this is what feeds the `worker_pool` health finding (see [health.md](health.md)) once the dispatcher process itself is gone and there is no in-process handle left for a health sweep to consult. `_maybe_republish_worker_liveness` (mirroring `_maybe_sweep_deploy_gates` below) refreshes this reading's `observed_at` every 60s from inside `_loop`, under the same `_alive_lock` used to guard `_alive_worker_count`. `_publish_worker_state` deletes the `queue_meta` key outright — instead of writing `live_loops=0` — whenever `self._stop.is_set()` is already true, so a clean `Dispatcher.stop()` never leaves behind a reading a later sweep could misread as an active deficit; the check and the write share one lock so a concurrent periodic republish can never resurrect a stale reading after the clean-stop delete. `worker_liveness.classify` treats a reading older than `HEARTBEAT_TTL_S` (180s, three republish cycles) as absent rather than alerting, and — before raising an alert for a real deficit — checks `queue.list_running()` and `worker_liveness.probe_active_workers()` (a `worker_records` scan for detached survivor processes, see [worker_records.md](worker_records.md)) so genuinely active work never trips the finding.

## Unblock sweep (`alan/unblock_sweep.py`)

The merge-park green sweep that used to live at `alan/_dispatcher_merge_park_sweep.py` is now one recipe (`transient_failed_check`) of the host-side recipe unblocker, and `LoopMixin._maybe_sweep_unblocks` (`alan/_dispatcher_loop.py`) replaces `_maybe_sweep_merge_parks` in `_loop`, on a 60 s interval gated by the same `_deploy_gate_sweep_lock` compare-and-set against `DispatcherState._unblock_sweep_next_at` (class default `0.0`, so the first tick after a restart sweeps). The watch-state schema, write-ahead ordering, backoff ladder, per-tick forge-read cap and the park-restore-on-failed-dispatch invariant all carry over unchanged in shape; the merge gate is no longer attempted at dispatch time (the sweep dispatches with `MergeGateDecision.skipped`), because `_enforce_pr_merge_gate` runs it on the `pr_merge` invocation itself. `Queue.run(sql, params)` is the accessor the sweep's ledger uses for its own INSERT-only table on the queue's connection. Everything else — trigger, exemptions, recipes, ledger, ceilings, issue filing — is in [unblocker.md](unblocker.md).
