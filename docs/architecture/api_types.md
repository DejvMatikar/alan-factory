# Generated API types and the drift gate

The frontend's view of the backend's data models is **generated**, not hand-mirrored. `alan/web/src/api/schema.ts` is produced by `openapi-typescript` from the backend's own OpenAPI export, and a blocking CI job fails any change whose committed copy no longer equals a fresh generation. Roadmap item X2.4 migrates the hand-written types in `alan/web/src/api.ts` onto it family by family; until a family is migrated, both exist.

## If you change the API surface, regenerate

**Any change that alters the exported OpenAPI schema must regenerate and commit `schema.ts` in the same PR.** That includes a backend-only change with nothing under `alan/web/`:

- adding, removing, renaming or retyping a field on a pydantic request/response model;
- adding, removing or re-pathing a route, or changing its `response_model`, status codes, query/path params or tags;
- changing model metadata that FastAPI exports (`Field(description=…)`, enum members, defaults, optionality).

```bash
cd alan/web
npm ci                        # only if node_modules predates the generator
npm run gen:api               # rewrites src/api/schema.ts from a fresh backend dump
npm run check:api-types       # must print: src/api/schema.ts matches a fresh generation
git add src/api/schema.ts     # commit it on its own; never hand-edit the file
```

`check:api-types` is the local form of the CI gate — run it before pushing whenever the diff touches `alan/routes/`, a pydantic model, `alan/server.py`, `scripts/dump_openapi.py` or `pyproject.toml`. It needs the backend environment (`uv sync --locked --extra dev`) because it imports the application to dump the schema.

### A PR that was green can go red without being touched

The host's branch-freshness step merges `main` into an open PR branch shortly after every merge to `main`. If that PR changes the schema, the `schema.ts` it inherits from `main` is stale **for that branch**, and `api-types-drift` goes red on the merge commit even though nobody pushed. This is the gate working, not a flake: regenerate on the branch and commit. The same applies in the other direction — when two open PRs both change the schema, whichever merges second must regenerate after merging `main`. Resolve a `schema.ts` merge conflict by regenerating, never by hand.

A red `api-types-drift` is therefore never answered by re-running the job, by waiving it, or by adding an exclusion. The failure message names the remedy (`run npm run gen:api and commit the result`).

## Pieces

- **`scripts/dump_openapi.py`** — thin wrapper over `alan.server.openapi_json()`, byte-stable output (see `health.md`'s "OpenAPI export" section).
- **`alan/web/scripts/api-types.mjs`** — two subcommands sharing one `generateTypes`, so what `generate` writes is exactly what `check` compares against. `generate` = `npm run gen:api`; `check` = `npm run check:api-types`. `checkTypes` is a pure function over injected `dump` / `readCommitted` / `isTracked` seams, unit-tested in `scripts/api-types.test.mjs`; `main(argv, seams)` is the CLI wiring (exit 0 match, 1 divergence or dump failure, 2 usage).
- **`alan/web/src/api/schema.ts`** — the generated artefact, committed. `openapi-typescript` is pinned to an exact version, so a generator bump produces a regeneration diff that is committed in the bump.
- **`alan/web/src/api/client.ts`** — `createApiClient()` wraps `openapi-fetch` over the generated `paths` and attaches the control token to every same-origin request whose method is not GET/HEAD/OPTIONS. There is no per-endpoint exemption list; same-origin is a credential-safety boundary, not an exemption.
- **`api-types-drift`** job in `.github/workflows/tests.yml` — runs `npm run check:api-types` from `alan/web`, 10-minute timeout, and is a `needs` of `main-red-report` so a stale schema on `main` files an issue.

## Invariants

- **The gate runs on backend-only changes.** `lint-frontend` and `test-frontend` are gated on the `frontend` path filter and would skip a pydantic-only PR, so the drift check is its own job whose `if` carries `backend_code == 'true'` and `backend == 'true'` (the latter covers `scripts/dump_openapi.py` and `pyproject.toml`) plus the push escape. `tests/test_ci_path_filters.py` pins the condition and evaluates it for a backend-only and an exporter-only PR. Dropping either term ships a gate that skips exactly the change it exists to catch and surfaces it as red `main` after merge.
- **Four ways a drift gate falsely passes, all closed.** (1) Closed loop: no schema JSON is committed — every run dumps fresh from the live application object into a temp path. (2) Untracked file: the comparison is on file *content*, and the file must be tracked (`git ls-files --error-unmatch`), because a plain `git diff` is blind to an untracked file. (3) Swallowed dump: a non-zero exit, an empty dump, or a dump with no paths fails hard. (4) Conditional routes: no router registers behind an environment variable; `tests/test_openapi_schema_stability.py` exports the schema from a fresh interpreter with every classified `ALAN_*` variable unset and again with every one set, and asserts byte equality.
- **The generated file is excluded by entry, not by comment.** `src/api/schema.ts` has one deliberate exclusion entry each in vitest coverage (`vitest.config.ts`), ESLint (`eslint.config.js`), knip (`.knip.json`), jscpd (`.jscpd.json`) and `sonar.exclusions` (`sonar-project.properties`). It carries no suppression comments, and hand-written files never join those lists.
- **Module resolution.** `src/api/` sits beside `src/api.ts`, so the bare `./api` specifier resolves two ways. `src/api/` therefore has **no index module**, and `src/api/resolution.test.ts` pins that `../api` resolves to `api.ts`. Import the generated surface by its full path (`./api/client`, `./api/schema`).
- **The `typescript` peer override is scoped, and stays scoped.** Every `openapi-typescript` release declares a `typescript@^5` peer while this repo is on `^6`, so `package.json` carries `"overrides": {"openapi-typescript": {"typescript": "$typescript"}}` — one package's one peer edge, resolved to the repo's own version. A blanket override, `.npmrc` `legacy-peer-deps`, `--legacy-peer-deps`, or downgrading the repo's `typescript` all change repo-wide peer resolution and are refused; if one looks necessary, escalate rather than deciding it in a diff.

## Rule for a declaration that mirrors an unexported backend base class

A hand-written declaration that mirrors a pydantic base class no route references reaches no OpenAPI component, so `schema.ts` has no counterpart to alias it to. The rule:

- **Deleted when unconsumed.** Nothing imports it, so nothing needs a replacement.
- **Kept as a local declaration when consumed.** It stays hand-written, in the module that consumes it.
- **Either way it does not count against the programme's "zero mirrors" target.** A later slice must not treat it as an unfinished migration.

The worked case is `UnblockActivitySummary`, which mirrored the base class at `alan/routes/health.py:406`. Only two `extends` clauses referenced it, both replaced by the generated `UnblockFleetActivity` / `UnblockScopedActivity`, so it was deleted outright.

## Windowed health metrics on `/api/health/repos`

`GET /api/health/repos` serves the 7-day and 30-day figures from `alan/health_windows.py` for every health metric, fleet-wide and per repository, behind the same 30 s TTL cache the route always had. It answers without any triage state: with no stored health state `computed_at` is `null` and each row's `outstanding_findings` is `{value: null, sample: 0, low_data: false}`, while the windowed figures are still computed from the workspaces, audit files and unblocker ledger.

- **Envelope.** `computed_at` (the triage timestamp, `null` without state), `metrics_computed_at` (when the windows were computed, always present), `unattributed` (block-correction rows in the last 30 days whose `task_id` matches no known workspace), `fleet` and `rows`.
- **Row.** `repo`, `outstanding_findings` and `in_flight` keep their `RepoRateValue` shape. The flat per-row rate fields (`build_success_rate`, `outcome_rate_30d`, `autonomous_rate_30d`, `first_pass_approval_rate`, `rescue_success_rate`, `rescue_load_rate`) are gone; everything windowed lives under `windows`.
- **`HealthScopeWindows`** (used by `fleet` and by each row's `windows`) has nine `HealthMetricWindows` entries — `outcome`, `autonomous`, `build_success`, `first_pass_approval`, `unproven_clauses`, `format_error`, `correction_recovery`, `rescue_success`, `rescue_load` — plus `funnel`, a `HealthFunnelWindows` of two `FunnelCounts` (`d7`, `d30`). A `HealthMetricWindows` is `{d7, d30, verdict, higher_is_better}` where each window is a `HealthWindow` `{value, sample, covered_days}` and `verdict` is the `Verdict` enum (`better`, `worse`, `same`, `insufficient`). The backend already folded the direction of the metric into `verdict`; `higher_is_better` is carried so the client can say so in words.
- **`covered_days`** is how many days of the window the underlying records actually reach. A 30-day window with `covered_days` below 30 is labelled as covering the shorter period by `alan/web/src/lib/metricWindow.ts`, never presented as a full month.
- **A repository with no activity** still gets a row: its windows are the empty-scope windows (no value, zero samples, `insufficient`), so no row is missing by construction.
- **Per-repository format error and correction recovery** count only correction rows attributable to a repository; the fleet rows count every row. The repository page states this and shows `unattributed`.

`api.ts` exposes `HealthWindow`, `HealthMetricWindows`, `HealthScopeWindows` and `HealthVerdict` as `export type` aliases over the generated components, and `RepoHealthRow` / `RepoHealthResponse` follow the regenerated schema; nothing is hand-declared.

## Rule: a defaulted response field is optional by artefact, not by contract

`openapi-typescript` marks a response field optional (`field?:`) **when its pydantic default is `None` or a `default_factory`** (the second trigger is covered under "Workspace family migration (X2.4 PR 5)" below), and required when the default is any other value. Verified across the repo-status and recurring families in `schema.ts`: `CostField.total_cost_usd?: number | null` against `CostField.unknown_count: number` (`@default 0`), and `LastRun.at?: string | null` against `LastRun.state` (`@default unknown`). The backend serialises the whole model, so it emits every key on every response — `null` for "no data" — and never omits one; the routes set no `response_model_exclude_*` option. The optionality is a generator artefact, not a statement that the field can be absent from the wire.

- **How to narrow.** Widen the existing null check to the total form, `== null`, which covers `null` and `undefined` as one Istanbul branch. This is already house style (`recurringFields.ts`, `recurringLinks.ts`, `RecurringProcessesPanel.tsx`), so a widened check adds no branch and no coverage debt. A prop that receives such a field widens to `T | null | undefined` and keeps its single existing guard.
- **What not to delete.** A non-null assertion that documents a paired-population invariant stays. `statusFields.ts` asserts `red_count!`, `authored_by_alan!` and the second sibling number because the backend populates the sibling numbers together; the note at the top of that file names the invariant. Replacing an assertion with `??` adds a branch no reachable input can exercise, which total branch coverage then blocks.
- **What not to fixture.** No test constructs a body with the key omitted. Fixtures reproduce the wire the backend emits: every key present, `null` for "no data". A fixture for the omitted-key shape asserts behaviour for an input the backend cannot produce, and would pin a consumer branch that exists only because of the artefact.
- **Where the honest fix belongs.** Declaring the defaulted fields on `alan/repo_status.py` and `alan/recurring_status.py` required-and-nullable (`X | None` with no default) makes the generated types match the wire, after which the widened checks could return to `=== null`. It is deferred to the queued item whose declared file list contains `alan/repo_status.py`, and is recorded here as a pointer, not performed: it alters the exported schema, so it regenerates `schema.ts` and changes no behaviour. Whoever owns that module next should take it.

Accepted behaviour deltas:

- Both reads no longer send the control token. Before, `fetchOk` copied a stored token onto every request it made, GETs included; the generated client's middleware attaches one only to mutating same-origin requests, so these two GETs now go out without it. This is safe because the server reads the header only inside the `require_control_token` dependency, and neither `GET /api/engines/{owner}/{repo}/status` nor `GET /api/engines/{owner}/{repo}/recurring-status` declares it, so neither route ever inspected the header. Dropping it cannot change a read's outcome, including when the stored token is missing or expired.
- Neither read sends a body, so neither sets `Content-Type: application/json` any more.

Not done here, deliberately: the six workspace mutations that send no credential, and the chat-session, project and engine-configuration families, stay on the hand-written helpers. The first three contain mutation call sites whose migration would start sending a credential they send none of today; the engine-configuration family round-trips a model whose generated shape marks many fields optional that the hand-written type declares required. Each is its own slice.

### The control-token decision: consistency closed, enforcement open

Six workspace mutations — `deleteWorkspace`, `archiveWorkspace`, `unarchiveWorkspace`, `stopWorkspace`, `resumeWorkspace` and `clearStickyInstructions` — used to call `fetch` directly and so sent no `X-Alan-Control-Token`. They now go through `apiClient`, whose `controlTokenMiddleware` attaches a stored token to every same-origin request whose method is not GET/HEAD/OPTIONS, so **all six now send the header**.

**The server does not inspect it.** None of the six routes declares `require_control_token`; `workspaces_router`, `tasks_router` and `dispatch_instructions_router` carry no router-level dependency, the application declares no blanket one, and the only middleware is CORS. `tests/test_workspace_mutation_token_inventory.py` records exactly that: a positive control on `PUT /api/workspaces/{workspace_id}/tasks/{task_id}/scenarios` (which does declare the dependency) proves the walker sees a declared token, and each of the six routes is asserted **not** to. That file is the durable record. Without it, a reader who sees `require_control_token` imported in `alan/routes/workspaces.py` (it is used once, on the scenario override) could infer a server requirement that does not exist.

So this change closes only the *consistency* half of the reserved decision. **The six mutations remain unauthenticated after it.** Whether they should require the token is a security-boundary change reserved to the repository owner, and no route's authentication requirement was added or removed here. Sending the header protects nothing on its own, either: the middleware skips cross-origin requests, and a cross-origin caller is the case a token would matter for. The four POSTs carry no body and no custom header, so a browser sends them cross-origin as simple requests without a preflight; the two DELETEs are not simple requests and need a preflight that the CORS allow-list refuses for other origins. ### Rule: a `default_factory` field is optional with no `| null`

The rule above says a defaulted response field is optional when its pydantic default is `None`. There is a second trigger. A field declared with `default_factory=list` is emitted optional with **no `| null` and no `@default`**, because pydantic emits no `default` key for a callable. `WorkspaceDetail.tasks` and `scope_audit`, `Task.depends_on`, `TaskDoDClause.covers`, `Handover.decisions` / `open_questions` / `assumptions` / `artifacts_produced` / `forbidden_actions` / `test_scenarios` / `to_team_suggestions`, `OpenQuestion.prior_attempts` / `proposed_answer_space`, `WorkflowDoc.tasks`, `WorkflowTask.depends_on`, `RunSummary.tool_counts` and `WorkspaceDelivery.files_changed` / `commits` are all of this shape. The backend still sends every one of them on every response.

- **Only correct resolution: a non-null assertion at the read, never `??`.** The hand-written types declared these fields required, so no guard exists in the code, and `?? []` adds a branch no reachable input can exercise, which total branch coverage blocks. `@typescript-eslint/no-non-null-assertion` is `"off"` in `alan/web/eslint.config.js`, and `statusFields.ts` is the standing precedent above. Where a component reads one such field several times it takes it once into a local (`const tasks = ws.tasks!`).
- **Not a type-level wrapper.** A shared `Required<Pick<...>>` or `Omit` alias that flips these fields required would be a second pattern to maintain, and it would force fixtures to spell fields the backend fills for them.
- **Fields already optional in the hand-written type keep their guards.** `WorkspaceDetail.blockers` and `cost_breakdown`, and `Task.dod_clauses`, were `?:` before, so their existing `?? []` and `?.` reads stay and stay covered.
- **PR 6–PR 9 hit the same shape.** Classify each drifted field by its generated form. Optional with `| null` takes the total `== null` check or a widened prop. Optional with no `| null` and no default is a `default_factory` field and takes `!`. Required with `@default` is a now-required field and loses its guard.

### The control-token decision: inverted, and the server does inspect it

**Every mutating engine route requires the control token; no engine read does.** This is the opposite of PR 5, PR 6 and PR 7, each of which recorded that the server does not inspect it. Here it does: sixteen mutating routes across `engines_router`, `engines_accent_router`, `engines_lane_router` and `engines_visibility_router` declare `require_control_token` (`alan/routes/_deps.py`) in their `dependencies`, and none of the fifteen reads on the seven engine routers does.

`GUARDED` in the same module is **not** the requirement. It is a `responses` documentation dict (the 401, 403 and 500 descriptions) that every guarded route spreads into its OpenAPI `responses`; it adds no enforcement, and a route that documents `GUARDED` without declaring `require_control_token` is unauthenticated. It is what a later reader will mistake for the dependency.

`tests/test_engine_mutation_token_inventory.py` records the posture with inverted polarity: every mutating route is asserted to declare the dependency, every read is asserted not to, and completeness checks fail with "classify this route" when a route is added or removed without the inventory being updated. Its controls are negative: a synthetic route with no dependency, a synthetic route that documents `GUARDED` but declares no dependency, and the real workspace archive route (documented unauthenticated in PR 5) each assert the walker reports absence. The inventory covers the four routes with no frontend wrapper — lane read and write, the pinned-work read and `DELETE /api/engines/{owner}/{repo}` — because an inventory that walks only wrapped routes is not an inventory. `onboarding_router` (`/api/onboarding`, project-scoped, with its own router-level dependency) is deliberately excluded; the readiness read this family types is `GET /api/engines/{owner}/{repo}/onboarding` on `engines_router`. The route walker gained `non_get_routes` and `get_routes` in `tests/control_token_inventory.py`.

The credential clause is over **migrated** mutations: the twelve send the token through the client's middleware on same-origin non-GET requests, as `fetchOk` did. The two bespoke wrappers attach it by hand. No route gained or lost a requirement, and whether any should is still reserved to the repository owner.

### The round-trip hazard, and the protection that is an acceptance clause

`update_engine` (`PATCH /api/engines/{owner}/{repo}`) is a full replace with no `exclude_unset`: a field omitted from the body is persisted as its backend default. Six fields are exempt from the server's 409 divergence guard — `PROJECTION_EXCLUDE` in `alan/engine_config.py` names `posture`, `accent`, `hidden`, `hidden_restore_posture`, `prompt_overrides` and `dependency_sweep.enabled` — so overwriting one of them is not rejected: it succeeds silently. They are the same fields a past production incident touched on the default engine. The hand-written `EngineConfig` declared none of `hidden`, `hidden_restore_posture`, `accent`, `unblock_enabled`, `scenario` and `cache_env`, all of which the wire carries.

The wizard's step-2 save was safe only by accident of construction: `buildStep2Payload` is `{ ...live, ...draft }`, and that spread preserves fields the type never declared. The same mechanism is also the delivery mechanism for a wipe. A key that is present with the value `undefined` in the second operand overwrites the first operand's real value; `JSON.stringify` then drops the key; the server fills the backend default. The moment a seed helper lets `undefined` through, the thing that protected the payload erases live configuration.

- **Type-level resolution.** The first act was a typecheck of `Step2Draft` against the generated component. `Pick<EngineConfig, …>` keeps compiling, its keys turn optional, and under `exactOptionalPropertyTypes` a seed that assigns `T | undefined` no longer compiles, so the two seed sites (`seedDraft`, `seedDraftFromLive`) had to be resolved. The six `default_factory` fields (`gate_commands`, `warmup_commands`, `base_tools`, `team_tools`, `roles`, `transition_graph`) take a non-null assertion, per the rule above. The three optional-and-nullable fields (`flow_policy`, `code_quality`, `pool_size`) take `?? null` instead: a `!` there would compile, because the target accepts `null`, but it would strip a genuine `null` from the expression's type, and `?? null` turns a missing key into an explicit `null` where `!` would emit a key-present-`undefined`. The pre-decided fallback, a local `Required<Pick<…>>` for the draft type only, was not needed. `EnginePresetSeedButton` follows the same split for its overlay.
- **The assertion is not the guarantee.** It fixes today's two seeds only. The guarantee is behavioural. `connectStep2ConfigureLogic.test.ts` and `api.engine.test.ts` both call `expectFullWireParity` (`alan/web/src/test/engineFixtures.ts`), which serialises the payload, asserts the key set equals the live configuration's, and asserts no key holds `undefined` at any depth, so `dependency_sweep.enabled`, one of the six, is covered as well as the top-level keys. They run it over a full-wire live configuration and a partial-wire one (lacking the six fields the old type never declared), name each of the six `PROJECTION_EXCLUDE` fields at a non-default live value, feed `createEngine` a preset-shaped baseline exactly as `ConnectStep1Identify` does, and carry four negative controls: a draft holding `undefined`, `undefined` spread over the live `hidden` flag, `undefined` nested under the live `dependency_sweep`, and a payload that dropped keys must each fail the helper. One test demonstrates the mechanism itself. `npm run test:engine-roundtrip` runs the step-2 files and `npm run test:engine-types` the transport file.
- **Blast radius is exactly two write paths:** `buildStep2Payload` with the PATCH, and `createEngine(baseline)`. `useEngineConfigDoc` is read-only and was not touched defensively.
