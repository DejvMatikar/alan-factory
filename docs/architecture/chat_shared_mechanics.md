# Chat shared mechanics (stop-and-redirect, propose-time collision fold)

**Source:** `alan/_chat_core.py`, `alan/routes/_chat_router.py`, `alan/claude_cli.py`. This doc replaces `docs/architecture/workspace_chat.md` (removed) as the canonical description of machinery shared by the surviving chat doors — build chat (`docs/architecture/build_chat.md`) and explore chat (`docs/architecture/explore_chat.md`). It carries forward the sections that described shared behavior, and adds the removal record for the per-workspace discussion feature at the bottom.

## Stop-and-redirect: recorded resume, the `TurnEntry` lock lifecycle, and `turn_stopped`

Stopping an in-progress turn and immediately sending a redirected message is a normal interaction, not an edge case — this section is the shared mechanics both surviving chat families (`build_chat.py`/`explore_chat.py`) get for free through `alan._chat_core`/`alan.routes._chat_router`.

- **Resume is a recorded fact, never an inference.** `_chat_core.ChatSession.cli_session_id: str | None` is the ONLY signal `alan.routes._chat_router.do_turn` uses to decide `--resume <id>` vs a fresh `--session-id <uuid>` — there is no inference from transcript shape. `cli_session_id` is populated live, mid-turn, from the CLI's own `system`/`init` stream event via `run_chat_turn`'s `on_session_id` callback (`alan/claude_cli.py`) — `do_turn` passes a closure that persists it with `_chat_core.update_session(ctx.core, sid, {"cli_session_id": ...}, root=root)` the instant the CLI reports its session id, not after the turn finishes. This is what makes the earliest-possible stop safe: if a turn is killed before `system`/`init` ever arrives, `cli_session_id` simply never gets set, so the session correctly looks exactly like a fresh conversation on the next message. When not resuming, `do_turn` mints a brand-new `uuid4()` for `--session-id` rather than reusing `session.session_id` — a turn that was killed mid-spawn may already have registered that id with the CLI's own session store, and reusing it would collide.
- **One-shot legacy bridge for pre-fix session.json files.** `_chat_core.load_session` parses the raw JSON before validating it: if the `cli_session_id` key is absent from the file entirely (not present-and-`null`) AND the transcript already has ≥1 assistant message, it backfills `cli_session_id = session_id` and persists it once (`_bridge_legacy_cli_session_id`). Keying on key-*absence* rather than a null value means no session written after this fix can ever re-enter the bridge.
- **`TurnEntry` replaces the old `sid -> Popen | None` map, keyed by per-acquisition identity, not just `session_id`.** `_chat_core.ChatSessionLocks` tracks one `TurnEntry(session_id, proc, cancel_requested, released: threading.Event)` per in-flight turn, and `acquire(session_id)` returns that entry to the caller — the caller's own object reference is the identity token, not the session_id string. `cancel()` sets `cancel_requested=True` and terminates `proc` immediately if one is already registered; it also succeeds (returns `True`) in the accept-to-spawn window before any process exists yet — `set_proc(entry, proc)` checks `cancel_requested` and terminates the process the instant it spawns. `was_cancelled(entry)` and `release(entry)` both take the entry object itself, so a turn's own background thread always reads and clears *its own* acquisition — `release()` only pops `self._entries[session_id]` when the currently-stored entry `is` the one passed in, so it can never clobber a newer turn's entry.
- **`run_interrupt` always returns `204`.** The old `409 no chat turn in progress` response for an idle session is gone — pressing stop is never wrong. After `cancel()`, `run_interrupt` waits on `locks.wait_released(session_id, _RELEASE_WAIT_SECONDS)` (`_RELEASE_WAIT_SECONDS = 5`) for the background turn thread to actually finish releasing the slot; if that bound is exceeded, `force_release()` SIGKILLs the process and pops the entry unconditionally.
- **A stopped turn is an outcome, not an error.** `execute_turn` accumulates the assistant's partial reply as it streams via `_PartialTextTracker`. When `run_chat_turn` raises because the process was killed, `execute_turn` checks `locks.was_cancelled(entry)` *before* falling into the generic error path: if true, it appends `ChatMessage(role="assistant", content=<accumulated text>, interrupted=True)`, clears `in_flight_turn`, and publishes a `turn_stopped` event carrying `{content}` — deliberately the same payload shape `assistant_done` uses.
- **`ClaudeCliError` never reaches the client as raw text — at the chat-turn call site.** `execute_turn`'s error branch maps the exception through `_plain_chat_error_text` — a small `isinstance` dispatch to a fixed, human-readable string per known failure family (`UsageLimitError`, `ClaudeCliTimeout`, `ResumeSessionLostError`, generic fallback) — before it goes out in the `error` SSE event's `detail`. Separately, and unconditionally for every `do_turn` caller, a `ResumeSessionLostError` clears `cli_session_id` back to `None` before re-raising — the next turn on that session self-heals by starting fresh.

## Commitment gate as an action — two gated dispatch doors

`alan.dispatch_proposal.DispatchProposal` is the single shared proposal contract (see `docs/architecture/dispatch_proposal.md`), and `alan.routes._chat_router.run_dispatch_proposal` is the single implementation both surviving doors call: build-chat's `propose_build_dispatch` and explore-chat's `propose_explore_dispatch`. `tests/test_dispatch_gate_invariant.py`'s `HUMAN_DISPATCH_DOORS` registry pins this set to exactly two entries.

**No replacement dispatch control exists for a live workspace.** Dispatching a team onto a live workspace is now API-only (`POST /api/workspaces/{id}/tasks/{id}/dispatch`, unchanged). A UI control mirroring the retired per-workspace discussion chat was considered and rejected: it would be another ungated door against the very "no ungated human dispatch door" invariant `test_dispatch_gate_invariant.py` enforces — a gate downgrade, not a fix.

## Propose-time collision fold, server-side and session-attributed

`alan.routes._chat_router.run_dispatch_proposal` runs a door-supplied async closure, `collision: Callable[[], Awaitable[CollisionResult]]`, as a peer `asyncio.create_task` alongside the scan task — both are created before the propose turn starts and awaited only after it completes, so the check overlaps the turn (normally the longest leg) for zero added wall-clock. `_safe_collision_check` fails open to `alan.collision.SAFE_RESULT` on any exception. The verdict is returned as `DispatchProposalReady.collision: CollisionVerdictOut`, defaulting to the green `SAFE_RESULT` verdict so a headless caller (the roadmap-driver, the primary instance) is never blocked on it. See `docs/architecture/build_chat.md` and `docs/architecture/explore_chat.md` for each door's own `collision` closure.

## `_CHAT_UX_LENS` sharing

`_CHAT_UX_LENS` (`alan/claude_cli.py`) is a single constant shared verbatim across the build-planning prompt (`format_build_system_prompt`) and the `brainstorming`/`architecture`/`ui_review` explore consultants (`ConsultantInfo.carries_ux_lens`). It instructs the model to reason from `docs/DESIGN_SYSTEM.md` and the user's experience when a conversation concerns the web UI, and to say so explicitly in its answer. Purely advisory — it never feeds a severity, verdict, gate, or dispatch decision.

## Ungated-raw-routes rationale table

`tests/test_dispatch_gate_invariant.py::NON_GATED_RAW_ROUTES_RATIONALE` documents, with rationale, why two raw endpoints are intentionally NOT gated through `run_dispatch_proposal`: the raw dispatch endpoint (`workspaces.dispatch_task_team`, recovery/scripted dispatch must still work without a chat turn) and raw workspace creation with an optional `team` field (`workspaces.create_workspace`, same rationale — the gate lives at the ACTION layer, not the creation layer).

## Removal record: the per-workspace discussion feature (X2.6 slice 3)

The per-workspace advisor chat (`WorkspaceChatPanel`, `EXTRACT_DISPATCH_YAML` dispatch-advisor flow scoped to a single live workspace) is removed as of this slice:

- **Backend.** The eight routes under `/api/workspaces/{task_id}/chat` (`alan/routes/ws_chat.py`), the `alan/workspace_chat.py` module (session config, preamble-building, `WsChatSessionLocks`), `alan.claude_cli`'s `format_workspace_chat_system_prompt`/`run_workspace_chat_turn`/prompt block, and the `_WORKSPACE_CHAT_NO_IMPL` grant constant are all deleted.
- **Startup reconcile.** `alan/reconciler.py`'s `reconcile_workspace_chat_sessions_on_startup` startup sweep is deleted along with `ChatReconciliationReport`; the workspace-chat sweep step is gone from `alan/routes/infra.py`'s `_run_chat_reconcilers` (now build-chat then explore-chat only).
- **Repo quiescing.** `alan/repo_quiesce.py::quiesce_repo` no longer takes a `ws_chat_locks` parameter, and `_cancel_workspace_chats` is deleted. `QuiesceReport.chats_cancelled` stays a single summed `int` — it simply stops including workspace chats; there was never a per-kind breakdown and this change introduces none.
- **Dispatch-door registry.** `HUMAN_DISPATCH_DOORS` (`tests/test_dispatch_gate_invariant.py`) shrinks from three doors to exactly two: build-chat and explore-chat. No replacement dispatch control was added — see "Commitment gate as an action" above.
- **`Meta.chat_session_id` is now write-dead.** The field, its `WorkspaceDetail.chat_session_id` response entry, and the "Other" affordance's former resolver hook all stay in place for this slice — removing the field itself is deferred to the next slice. Existing workspaces keep whatever value they already had; new workspaces get `null` and nothing sets it again.
- **On-disk `chat/` directories are deliberately left in place.** `alan/workspace_cost.py`'s cost reader finds a workspace's discussion cost via its own local `_CHAT_DIR_NAME = "chat"` literal, not via the now-retired `ALAN_WORKSPACE_CHAT_SESSIONS_ROOT` registered root — that root was a vestigial default nothing on disk under a workspace ever actually used (workspace-chat sessions lived under `<workspace>/chat/`, not a separate global sessions root). Removing the registered root from `alan/roots.py` therefore moves no cost totals and deletes no directory; a project's historical burn total is unaffected. `tests/test_roots_registry.py::test_state_root_subdirs_excludes_retired_workspace_chat_sessions_root` pins the root's absence, mirroring the existing `ALAN_CHAT_SESSIONS_ROOT` precedent.
- **Frontend.** `WorkspaceChatPanel.tsx` and its dispatch-proposal modal mount are gone (the modal component itself, `DispatchProposalModal.tsx`, was already orphaned by the prior slice's removal of its other production mounts and is deleted here as dead code). `DecisionForm.tsx`'s "Other" radio affordance — which only ever rendered when a caller supplied an `onOther` handler, and no caller does anymore — is deleted; it was never an answer path, since the answer endpoint validates the chosen option against the question's enumerated option space.
- **Known follow-ups, not claimed here.** `GET /api/teams` (the team catalogue) now has no client at all — no surviving door lists it. `POST /api/workspaces/{task_id}/dispatch` (`alan/routes/workspaces.py:996`, the legacy 308 redirect to the per-task dispatch route) also lost its only client when `api.dispatchTeam` was deleted in slice 4 — the route stays; deleting a redirect is a behaviour change nobody asked for. Both are flagged so neither is swept in silently nor lost; fixing either is out of scope for this slice.

## Removal record: `chat_session_id` and `api.dispatchTeam` (X2.6 slice 4)

Discharging the deferral noted above:

- **`Meta.chat_session_id` is deleted**, along with `WorkspaceDetail.chat_session_id` and the `api.ts` `WorkspaceDetail.chat_session_id` type. No migration of persisted records is performed — `Meta` has no `model_config`, so pydantic's default `extra="ignore"` silently swallows a stale `chat_session_id` key on an existing `meta.json`, pinned by `tests/test_workspace.py::test_meta_ignores_stale_chat_session_id_field`.
- **`api.dispatchTeam` is deleted**, along with its three test blocks — superseded by the atomic create-and-dispatch flow (`api.createAndDispatchWorkspace`) every surviving dispatch door already uses. `api.dispatchTask` (the per-task dispatch helper with a live caller on `Workspace.tsx`'s "Restart the check" button) is unaffected.
