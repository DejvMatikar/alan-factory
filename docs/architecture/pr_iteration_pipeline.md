# PR iteration pipeline (Pattern B)

**Status:** Accepted — 2026-05-18 (Phase 3 auto-dispatch wiring landed)
**Source (to be added):** `alan/teams/implementation_fix.py`, `alan/teams/pr_merge.py`, `alan/teams/_pr_branch.py`
**Touches:** `alan/router.py`, `alan/teams/__init__.py`, `alan/teams/verification.py`, `alan/teams/implementation.py`, `alan/teams/implementation_plan.py`, `alan/workspace.py`, `alan/handover.py`, `alan/web/src/api.ts`

This ADR locks the design for an automated review→fix→merge loop. Pattern B splits the existing single-purpose `implementation` team into three responsibilities and removes the human gate between `implementation_plan` and `implementation` when the workspace opts in.

## Context

The current pipeline ([implementation_pipeline.md](implementation_pipeline.md)) iterates verification→implementation on `REQUEST_CHANGES` and pauses at `AWAITING_INPUT` on `APPROVE` for the human to merge. Three frictions emerged:

1. **`implementation` carries two responsibilities** — open the first PR AND fix it on iteration. The function `implementation.run` is at the 60-line lizard ceiling; any additional iteration logic trips the gate.
2. **No automated merge.** Every approved PR sits in `AWAITING_INPUT` even when CI is green and review threads are resolved. The Mac launchd deploy already pushes + reviews live; merge is the only step still manual.
3. **`implementation_plan → implementation` requires a human dispatch.** For tasks where the plan is routine (e.g. small refactors), this is the largest source of latency in the pipeline.

## Decisions

### D1 — `Meta.auto_dispatch: bool` opts the workspace into automatic plan→implementation handoff
**Source of truth:** workspace metadata, not per-handover.
**Producer-side:** `ImplementationPlanTeam.run()` reads `workspace.meta.auto_dispatch` and emits `to_team_suggestions=("implementation",)` when true, `()` otherwise. The router applies its existing forward-target precedence ([router.md](router.md#forward-target-precedence)) — no router branches added.
**Rationale:** task-level intent is durable per-workspace; emitting it per-handover would scatter the policy. The router's `_pick_forward_target` is at CCN 7 — one new branch trips the `CCN < 8` gate.
**Confidence:** 0.9 / reversibility: high.

### D2 — Verification routes exclusively: `implementation_fix` on `REQUEST_CHANGES`, `pr_merge` on `APPROVE`+PR, `await_human` on `APPROVE`-without-PR
`verification → implementation` is **removed** from `TEAM_TRANSITION_POLICY` in the same PR that registers `implementation_fix`. No iteration-1 fallback. The `APPROVE`-without-PR case (dry-run, push failure, manual verification dispatch with no upstream PR) yields `to_team_suggestions=()` so the router returns `await_human` — there is no merged code to retro on, and silently routing to `retrospective` would mark the workspace `COMPLETED` without anything landing in main.
**Rationale:** a permanent fallback to `implementation` would leave dead code forever. Bundling the policy change with the registration eliminates a half-broken intermediate state. The deploy procedure (see below) drains the verification queue first so no in-flight handover suggests the removed team. `retrospective` is reachable only transitively via `pr_merge → retrospective`, so `COMPLETED` always implies a real merge happened.
**Confidence:** 0.85 / reversibility: medium.

### D3 — `pr_merge` is a Python-only `Team` (no `claude` subprocess, no worktree)
Polls `gh pr checks` + `gh api graphql` for unresolved review threads, attempts `gh pr merge --squash --delete-branch` when green, terminates via `retrospective` on success or `await_human` via a blocking `OpenQuestion` on timeout/failure.
**Rationale:** the work is a state machine over `gh` subprocess calls. An LLM gate would burn tokens on deterministic checks and require calibration. `principal_proxy.py` established the precedent of host-process logic teams before its 2026-07-13 removal (see [principal_proxy.md](principal_proxy.md)); `triage.py`/`dependency_sweep.py` are the current examples. Keeps the module ≤ 200 lines and gates-friendly.
**Confidence:** 0.85 / reversibility: medium.

### D3-ext — `pr_merge` routes to `implementation_fix` on unresolved Copilot review threads AND PR-level Copilot comments / review bodies

**Superseded by D18.** As designed below, this gate shipped with a malformed query (`author` does not exist on `PullRequestReviewThread`) that GitHub rejected outright, an unverified identity constant that matched neither GitHub API surface, and a fail-open swallow on query failure — the combination left it live but never once blocking a merge for roughly three months. D18 repairs all three defects in a new `alan/teams/_pr_feedback.py` module and additionally holds the `issue_comment`/`review_body` categories in shadow mode pending evidence. The query/classification/audit-action details below describe the pre-repair design and are historical; see D18 for current behavior.

The `gh api graphql` query is extended in a single round-trip to fetch (a) `reviewThreads` (with `id`, `author { login }`, `comments(first:1) { nodes { body, databaseId } }`), (b) PR-level `comments(first:100)`, and (c) `reviews(first:100)` — see `alan/teams/pr_merge.py:_gh_feedback_raw`. `parse_thread_info` keeps its prior shape; `parse_comment_info` builds a sibling `CommentInfo(copilot_items, human_items, total)` from the `comments` + `reviews` sections, classifying each non-thread node via `_classify_non_thread_node` (skips empty bodies for both sources, skips Copilot reviews whose `state == "APPROVED"`). When *any* Copilot feedback surface (thread, issue comment, or review body) is present and the human-unresolved count is zero, `pr_merge` emits a forward handover to `implementation_fix` instead of `await_human`. The handover's `full_synthesis` carries thread IDs / comment database IDs / bodies and a `Decision` (required by Layer-3 validator). `implementation_fix` addresses each thread by code fix or explicit acknowledgement via `scripts/alan_copilot_resolve.py`. The script has two modes: (1) the original `fix` / `acknowledge` thread modes call `resolveReviewThread` (real GitHub mutation); (2) the new `comment_ack` mode handles PR-level issue comments / review bodies — there is no GitHub `resolveIssueComment` mutation, so it posts a reply via `gh pr comment` and persists the acked `database_id` to `~/.alan/state/pr_<n>_acked_comments.json` (overridable via `ALAN_STATE_ROOT`). The classifier filters acked database IDs out via `pr_merge._filter_acked_comments`, so a successfully-acked comment cannot re-block merge on the next poll. All resolution actions append to `~/.alan/logs/copilot_review_audit.jsonl` (mode 0o600); `pr_merge` writes a `comment_unresolved` audit entry per Copilot comment to `~/.alan/logs/pr_merge_audit.jsonl` (sibling to the existing `copilot_thread_routed` action). Each invocation that routes to `implementation_fix` (or hits the escalation cap) also writes a per-invocation structured JSONL artifact `<workspace>/.alan/copilot_audit_<inv_id>.jsonl` (file mode `0o600`) and attaches it as a second `ArtifactRef` on the Copilot-bounce handover (alongside the `.md` threads file), or as the sole `ArtifactRef` on the escalation-cap handover, so `HandoverDetailPanel` → `ArtifactsSection` renders a download link via `GET /api/workspaces/{task_id}/artifacts?path=<abs_path>` with no additional frontend plumbing. Each JSONL row carries `timestamp_utc` plus the same keys and value types as the corresponding `pr_merge_audit.jsonl` row for the same action; `timestamp_utc` is captured independently for each sink (two `datetime.now()` calls), so timestamps between sinks may differ by microseconds — join on `(task_id, pr_number, action, database_id)` rather than `timestamp_utc`. When `ALAN_PR_MERGE_AUDIT_DISABLE=1`, neither the global log nor the per-invocation artifact is written (one off-switch). `~/.alan/logs/copilot_review_audit.jsonl` is **not** touched by `pr_merge` — it remains the resolution-side log written only by `scripts/alan_copilot_resolve.py`.

**Escalation counter semantics (operator note):** one shared per-workspace counter (`<workspace>/.alan/copilot_escalation_count`) covers Copilot threads AND Copilot comments. `ALAN_COPILOT_ESCALATION_MAX` (default 3) is the cap. The counter is intentionally *sticky* after the cap fires. Once `count >= ALAN_COPILOT_ESCALATION_MAX`, every subsequent `pr_merge` invocation on the same workspace immediately routes to `await_human` without dispatching `implementation_fix` again, preventing unbounded retry loops. The await-human cap path carries forward both `copilot_threads` AND `copilot_comments` (D10), so the human triager sees the full unresolved set. To give `implementation_fix` additional attempts after manual human triage, delete `<workspace>/.alan/copilot_escalation_count` (resets the count to 0). The counter is automatically deleted on successful merge (dry-run or real).

**Rationale:** Copilot review threads have a server-side `isResolved` bit, but Copilot also posts feedback as PR-level issue comments and review bodies that have no such bit. Without this extension, those slip past the gate and ship unaddressed. Conservative-but-not-noisy filtering (empty-body + `APPROVED` review skips) avoids spurious `implementation_fix` round-trips while still catching every actionable Copilot comment. The existing `await_human` path for human-authored threads / comments is preserved unchanged.
**Confidence:** 0.88 / reversibility: high.

### D4 — `implementation_fix` reuses `implementation_worktree(existing_branch=...)` via shared `alan/teams/_pr_branch.py`
Extract `resolve_existing_branch`, `push_branch`, and `_run_subprocess` from `implementation.py` into `alan/teams/_pr_branch.py`. Both `implementation` and `implementation_fix` import it. `pr_merge` imports only `_run_subprocess`.
**Rationale:** single source of truth for PR-branch primitives prevents drift. Drops `implementation.run` below the 60-line lizard ceiling. Avoids jscpd 1% duplication on the shared subprocess wrapper.
**Confidence:** 0.9 / reversibility: medium.

### D5 — `pr_merge.run()` short-circuits when `gh pr view --json state` returns `MERGED`
Restart-after-crash invariant. `supports_resume=False` alone does not protect against the dispatcher reconciler re-running `run()` from scratch.
**Rationale:** `MERGED` → emit forward handover to `retrospective`. `CLOSED` → emit escalation. `OPEN` → proceed with checks-and-threads polling. This is the only safe invariant for an idempotent merge gate.
**Confidence:** 0.92 / reversibility: low.

### D6 — `implementation_fix` pushes with an explicit-SHA lease: `git push --force-with-lease=<branch>:<base_sha>`
An implicit `--force-with-lease` (no argument) is neutralised if a `git fetch` runs immediately before the push, because the fetch updates the remote-tracking ref the lease is compared against — the guard always sees "nothing changed" and overwrites concurrent commits. The fix anchors the lease to `WorktreeHandle.base_ref` (the 40-hex SHA of the branch HEAD at worktree-creation time), so the guard fires against the actual state the worker started from regardless of any subsequent fetches. No pre-push fetch is run in the fix path.

When the lease is rejected ("stale info" in git stderr), `push_fix_branch_with_reconcile` attempts a fetch-then-rebase reconciliation: `git fetch origin -- <branch>`, then `git rebase --onto origin/<branch> <base_sha>` (with a best-effort `git rebase --abort` on any failure to keep the worktree clean for reuse). A clean rebase is re-pushed via `_pr_push.py::_repush_reconciled`, which pins the lease to the just-fetched remote revision — `--force-with-lease={branch}:{remote_sha}`, identical in spelling to `_pr_reconcile.py`'s pinned form (see D20 below) — and fails closed with `PushOutcome.PUSH_FAILED` plus an audit row naming the empty resolve if `remote_sha` somehow comes back empty, rather than falling back to an unpinned push; a rebase conflict or subprocess error during the rebase step emits `PushOutcome.DIVERGED_ESCALATE`, which causes `implementation_fix.run()` to return an escalation handover with `base_sha`, remote tip, and concrete by-hand recovery commands. A subprocess error during the re-push step (second-order race) emits `PushOutcome.PUSH_FAILED` rather than `DIVERGED_ESCALATE`.

`PushOutcome` enum values: `PUSHED` (clean push), `RECONCILED` (rebase + re-push succeeded), `DIVERGED_ESCALATE` (rebase conflict or rebase subprocess error), `PUSH_FAILED` (transient subprocess error or re-push failure). Both `PUSHED` and `RECONCILED` count as success.

**Rationale:** the implicit-lease + pre-push-fetch pattern silently overwrites concurrent commits on branches shared with external tools (Copilot autofix, manual hotfixes). Explicit-SHA lease is the minimal correct fix. The reconcile path handles the legitimate case where a prior review suggestion landed on the branch between iterations.
**Confidence:** 0.95 / reversibility: high.

**D6-ext — `implementation`'s own (non-reconcile) push carries the same pushed-vs-not distinction into its escalation text.** D6 above is about `implementation_fix`'s fetch/rebase/re-push path. `implementation.py`'s first-run push (`_push_branch`, a plain `git push -u origin <branch>` — no lease, no reconcile) is a separate, simpler call, but it shares the same underlying problem `implementation_fix` never had: before this change, whether `git push` itself failed or the push succeeded and only `gh pr create`/PR-number parsing failed afterward, both collapsed into one `pr_number=None` return and one escalation reading "committed work was lost when the worktree was removed" — true only for the first case. `_push_changes` now returns a frozen `PushChangesResult(pr_number, credential_failure, pushed)`; `pushed` is `True` whenever `push_result.outcome is PushOutcome.PUSHED` (which — for this call site — is the only non-failure outcome `push_branch` ever returns; `RECONCILED`/`DIVERGED_ESCALATE` are exclusive to `push_fix_branch_with_reconcile` above) and `False` otherwise. It threads through `_pr_handover.finalize_handover`/`build_handover` — both bundle it into a `push_failure: PushFailureContext | None` keyword rather than a bare `pushed` keyword, since it's one of five push-outcome fields (`pushed`, `continuing_pr`, `branch`, `credential_failure`, `forge_target`) both functions forward as a single unit; `PushFailureContext` defaults `pushed` to `True` — into `push_failed_handover`, which composes the escalation text: `pushed=False` keeps the original "lost" wording, `pushed=True` instead states the commits are safe on the named remote branch and tells the reader not to re-implement. A sibling boolean carried in the same `PushFailureContext`, `continuing_pr` (also defaulting to `True`), separately answers whether this iteration actually resolved and checked out the *inbound* `pr_number`'s branch (`existing_pr is not None` in `ImplementationTeam.run`) rather than merely inheriting a `pr_number` on the prior handover — `push_failed_handover` only takes the "push to PR #N failed" wording when `continuing_pr` is `True`, so a stale `pr_number` whose branch this run couldn't resolve (closed PR, forge hiccup) falls through to the same `pushed`-gated safe/lost wording as a first-ever run instead of falsely claiming the (never-touched) existing PR's push failed. See [implementation_pipeline.md](implementation_pipeline.md)'s "Escalation text distinguishes a failed push from a failed PR create" for the full mechanics — this note exists here only to flag that D6's reconcile ladder and `implementation`'s plain push are two different code paths that happen to share the downstream escalation composer.

### D7 — Verification writes the full untruncated judge review to a workspace file and exposes it as an `ArtifactRef`
Path: `<workspace>/.alan/verification_review_<inv_id>.md`. `implementation_fix._build_user_text` reads the file when the `ArtifactRef` is present and falls back to `summary_for_downstream` when absent (older handovers, manual dispatches).
**Rationale:** the 2500-char `summary_for_downstream` truncation has caused verification→implementation→verification loops on dropped issues in production (`pr1-4-backlog-deferred-topics-im` item #11). The full review is data, not a summary, and must not be lossy.
**Confidence:** 0.8 / reversibility: medium.

### D8 — The `verification → implementation` policy removal ships **bundled** with `implementation_fix` registration; deploy drains the verification queue first
Documented as an explicit deploy step on the policy-flip PR. Reconciler re-runs the *source* team on interruption, so any verification in-flight at deploy time re-emits a fresh handover under the new policy. Tasks waiting in the queue with a pre-deploy verification handover suggesting `"implementation"` are rejected by the router and surface as `await_human` (graceful failure mode).
**Rationale:** a staged removal means carrying dead fallback code forever. A brief queue drain (≤ 10 min under typical load) is operationally cheaper than permanent policy ambiguity.
**Confidence:** 0.78 / reversibility: low.

### D9 — `pr_merge` is filtered out of the frontend `DispatchPanel`; `implementation_fix` remains manually dispatchable
A `non_manual_teams: ReadonlySet<string>` is added to `alan/web/src/api.ts` near `ALL_TEAMS`. `DispatchPanel` filters it from the team picker. `pr_merge` is not meaningful without an inbound `pr_number` and would commit a worker for up to `ALAN_PR_MERGE_TIMEOUT_S` on a half-formed handover.
**Rationale:** `implementation_fix` is a legitimate human-triggered re-work entry point ("the judge missed something — re-fix"); `pr_merge` is not.
**Confidence:** 0.82 / reversibility: high.

### D10 — Verification downgrades `APPROVE → REQUEST_CHANGES` only on hard CI failures or merge conflicts; the dispatcher safety-net still uses the full readiness signal for `pr_merge`
The dispatcher continues to call `alan/teams/_pr_ready.check_pr_merge_readiness(pr_number, task_id) -> ReadinessResult` (a `PrReadiness`, or a `ReadinessUnavailable` carrying only its transient reason) for the `enqueue → pr_merge` branch (previously lived on `_pr_branch`; the readiness-cluster split moved `check_pr_merge_readiness` and `PrReadiness` to `alan/teams/_pr_ready.py` — call shape unchanged) — `gh pr view <n> --json mergeStateStatus,reviewDecision,statusCheckRollup,headRefOid` (the `headRefOid` field was appended 2026-09-05 so `PrReadiness` carries the measured commit's `head_sha` and a `check_count`) with `failed_reasons` covering `mergeStateStatus not in {CLEAN, HAS_HOOKS}`, `reviewDecision == "CHANGES_REQUESTED"`, failing checks, pending checks, and — new — `"no check results"` when `_pr_ready.results_absent` reports the rollup came back empty for a real (available) readiness (`COMMENTED` reviews still ignored).
The verifier uses a narrower sibling, `check_pr_verifier_blockers(pr_number, task_id) -> ReadinessResult` (a `PrReadiness`, or a `ReadinessUnavailable` that callers narrow away with `isinstance` before reading any readiness field), that reads the **same** `gh pr view` JSON but only treats two signals as `failed_reasons`: `mergeStateStatus == "DIRTY"` (real merge conflict) and `FAILURE|ERROR|TIMED_OUT` status checks. `reviewDecision == "CHANGES_REQUESTED"` and pending checks are **not** verifier blockers.
Verification consumes the narrower helper post-judge: if the LLM verdict is `APPROVE` but the verifier-blocker readiness is not OK, the embedded `VERDICT:` line is rewritten to `REQUEST_CHANGES`, a `> PARKED ON EXTERNAL GATES` banner is prepended, and an `## External Gate Status` block appended to the judge output (which then flows into `full_synthesis` and the `gh pr review` body). Otherwise the `APPROVE` ships through to `pr_merge`. Transient gh failures (`FileNotFoundError`, `TimeoutExpired`, non-zero returncode, unparseable JSON) leave the verdict untouched — `pr_merge`'s own polling remains the final gate. The downgraded output is posted to the forge as a **blocking change request** when its gate block names at least one actionable check, and as a **non-blocking comment** otherwise — no actionability lines at all, `GATE_ACTIONABLE: no`, or `GATE_ACTIONABLE: yes` with no named check (the base-conflict case). The trigger is the named check itself, never the `GATE_ACTIONABLE: yes` line on its own (D27).

Both verifier readiness reads (the initial one and each `_settle_wait` poll) go through `_pr_ready.verifier_lane_without_advisory`: a red check posted by a non-Actions app that is not in `forge.authoritative_checks` (today the SonarCloud app's code-analysis check) is dropped from the gate's view, so an advisory-only red neither downgrades the verdict nor skips the pending wait; a blocking red beside it leaves the readiness, the downgrade text and the rerun decision exactly as before. See [sonarcloud.md](sonarcloud.md) for the definition.

**Routing verdict vs GitHub review event are decoupled for the gate case (D10a, PR #265; updated PA-03, gate-park review uses effective count).** The rewritten `VERDICT: REQUEST_CHANGES` line drives *routing* (`suggestions_for_verdict` → `implementation_fix`, which can fix a fixable gate failure such as a coverage gap) and the `loop_guard._classify_external_gate_blocked` signal, but the *GitHub review event* is chosen separately by `github_review_event(judge_output)`: when the verdict is `REQUEST_CHANGES` **and** the *effective* critical count is zero — `effective_critical_count(judge_output)`, the same in-scope-aware primitive `effective_verdict` and the loop-guard already consume, which reads `DIFF_FINDINGS_CRITICAL_IN_SCOPE` when the judge emitted it (decomposer-scoped subtask) and falls back to the raw `DIFF_FINDINGS_CRITICAL` otherwise — **and** the `## External Gate Status` marker is present (the external-gate-only case) **and the block names no actionable check**, the review is posted as a **non-sticky `gh pr review --comment`**; when the block names at least one actionable check, it posts as a sticky `--request-changes` instead (D27). This closes PA-03: a judge that approves on the merits but names issues it explicitly ruled out of scope emits a non-zero *raw* count alongside a zero *in-scope* count, and keying on the raw count previously posted a sticky change-request under a header stating no blocking issues were found — self-contradictory, and self-sustaining because stale-review dismissal keys on the head commit. `_classify_external_gate_blocked` (and `_classify_scenarios_missing`) are now also reachable via `_verifier_reports_persistent_clean_block` when `implementation_fix` keeps committing: if ≥ 2 consecutive verifier passes show 0 CRITICAL + the external-gate or scenarios-missing marker, `detect_spiral` short-circuits to a typed escalation without burning the full `REVISIT_CAP`. See `docs/architecture/loop_guard.md` (Condition 4). Genuine in-scope code defects (effective critical count > 0) still post `--request-changes`. A missing/unparseable `VERDICT:` line is not posted at all — `_maybe_post_review` returns early with an `action: skip` audit row, so `github_review_event`'s defensive `None → COMMENT` branch is never reached from the posting path. `_REVIEW_FLAGS` maps the three `ReviewEvent` values (`APPROVE`/`REQUEST_CHANGES`/`COMMENT`) to the matching `gh pr review` flag; the audit row records both the routing `verdict` and the GitHub `event` (same key name across the `dry_run`, `review_ok`, `review_failed`, and `review_*_inline` actions). The inline-review path (`_apply_inline_pr_review`, taken when a `## INLINE_FINDINGS_YAML` block is present) also posts under the same `event`, so an anomalous gate-block + inline-findings combination posts under the same actionability-gated event as the non-inline path (D27): non-sticky `COMMENT` when the block names no actionable check, sticky `REQUEST_CHANGES` with the inline comments attached when it names at least one. Raw-count telemetry (the `critical_raw` audit field, the dry-run `critical` field) is unaffected — those remain deliberately raw; only the review-event decision keys on the effective count.
**Rationale:** the original (full-signal) verifier downgrade caused a self-blocking loop (PR #187, 2026-05-24). On the first verification pass, `mergeStateStatus=BLOCKED` from CI still pending six minutes after PR creation flipped `APPROVE → REQUEST_CHANGES`; on the next pass, `reviewDecision=CHANGES_REQUESTED` (from the verifier's own stale prior review) flipped it again. Stacked CHANGES_REQUESTED reviews blocked merge even though the code was verified correct. Narrowing the verifier-side gate to "real failure" signals + adding the dismissal step in D12 fixes the loop: pending CI and self-stale CHANGES_REQUESTED are `pr_merge`'s problem to wait on, not the verifier's reason to request changes. PR #265 then exposed two residual defects in the surviving downgrade: (1) it rewrote only the machine `VERDICT:` line, leaving the human prose reading "**APPROVE** — criteria met" beside a `REQUEST_CHANGES` footer (self-contradictory body); and (2) it still posted a *sticky* `--request-changes` review, so `reviewDecision` stayed `CHANGES_REQUESTED` until a *later* verifier pass dismissed it (D12) — if none ran, the PR stayed blocked even after CI went green. D10a fixes both: the banner reframes the stale prose, and — for a block that names no actionable check — the `--comment` event no longer pollutes `reviewDecision`, leaving GitHub's own required-checks gate + `pr_merge`'s polling as the sole authority for that case. D27 below reinstates a sticky `--request-changes` specifically when the block names an actionable check: that shape is not the PR #187 loop, because the named check is the branch's own defect, `pr_merge`'s own gate already routes a `CHANGES_REQUESTED` readiness to `implementation_fix` (D13/D19) rather than parking on it, and the verifier's stale-review dismissal (D12/D12a) plus the `verifier_rejections_at_head` ceiling it now counts toward (D27) keep it from becoming a new stacking loop.
**Confidence:** 0.85 / reversibility: high.

### D12 — Verifier dismisses its own stale `CHANGES_REQUESTED` reviews before posting a fresh one
Before `verification._apply_pr_review` (at the time this ADR was written; the H5.3 PR-2 review-posting split relocated this to `_verification_review_post._apply_pr_review`) calls `gh pr review --approve|--request-changes`, it lists every review on the PR via `gh api --paginate --jq '.[]' /repos/{owner}/{repo}/pulls/{n}/reviews` (NDJSON — one review object per line so each `gh` pagination page is independently parseable), filters to `state == CHANGES_REQUESTED && user.login == verifier_login()` (env-overridable via `ALAN_VERIFIER_LOGIN`, defaulting to `alan-verifier`), and dismisses each via `gh api -X PUT /repos/{owner}/{repo}/pulls/{n}/reviews/{review_id}/dismissals -f message='superseded by re-review' -f event=DISMISS`. The subprocess inherits the env from `secrets_store.verifier_gh_env(forge_target)` (the reviewer record in the secrets store first, then the resolved `ForgeTarget.credential_env_name`, `ALAN_VERIFIER_GH_TOKEN` for the default engine), so the bot dismisses under its own identity; owner/repo for the API calls come from the same `forge_target.repo` (D15) — there is no more `gh repo view` lookup that can fail. Each dismissal emits an `action: review_dismissed` (or `review_dismiss_failed`) audit entry. All failures are non-fatal — the new review still posts.
As of D10a (PR #265) the external-gate-only case no longer *creates* a sticky `CHANGES_REQUESTED` review (it posts `--comment`), so D12's dismissal now matters only for genuine-defect `--request-changes` reviews. That did **not** eliminate the self-stale class at the source, as this paragraph used to claim: a genuine-defect REQUEST_CHANGES on pass N is still standing when pass N+1 snapshots readiness, because the dismissal ran at post time — after `resolve_external_gates` had already read `reviewDecision=CHANGES_REQUESTED` and `_pr_flake_ledger.flaky_only_failing` had vetoed both the bounded gate rerun and the `pr_merge` reroute on that signal (PR #1159, 2026-08-20: pass-1 scenario FAIL → sticky REQUEST_CHANGES on `6e2a6fd9`; pass-2 judge APPROVE on `3019286a`, dismissal at 08:01:51, classification several seconds earlier → `flaky_only=False` → `implementation_fix` → `non_actionable_feedback` → human). Issue #1163.

### D12a — The verifier lane never lets the bot's own review veto its own classification (2026-08-20, #1163)
Two independent layers, either sufficient:
- **Truthful signal.** `_pr_ready.check_pr_verifier_blockers` requests `latestReviews` in the same `read_pr` port call (`_VERIFIER_READINESS_FIELDS`, now a tuple; the merge lane's `check_pr_merge_readiness` keeps `_READINESS_FIELDS` — GitHub's own `reviewDecision` still governs mergeability there) and derives the verifier-lane `PrReadiness.review_decision` via `_verifier_lane_review_decision`: a `CHANGES_REQUESTED` aggregate survives only when some latest review **not** authored by `verifier_login()` is `CHANGES_REQUESTED`; when the only such review is the bot's own, the lane reads `""`. Absent or malformed `latestReviews` keeps the aggregate (fail toward today's blocking behaviour), and an authorless `CHANGES_REQUESTED` entry counts as human. This makes `flaky_only_failing` immune both to the bot's stale review and to GitHub's review-decision recompute lag (#1161), while a human CHANGES_REQUESTED keeps blocking exactly as before.
- **Clean aggregate.** `_verification_gates._resolve_gate_readiness` calls `_pr_post.dismiss_stale_verifier_reviews` as its first statement — before the snapshot, in the `downgrade`/`rescue_only` modes it is reached from (zero-critical verdicts only; the `skip` mode never touches reviews early). The post-time call in `_verification_review_post._apply_pr_review` stays as the idempotent safety net. The dismissal still filters on `commit_id != current head`, so a verifier REQUEST_CHANGES on the *current* head is never dismissed early — and the truthful-signal layer above is what keeps such a same-head review from vetoing a fresh flaky-only classification.
**Rationale:** GitHub's review-decision aggregation takes the latest non-dismissed review per reviewer, so a fresh APPROVE would already supersede a prior CHANGES_REQUESTED in principle. Dismissing explicitly (a) cleans up the UI history so the PR doesn't accumulate review-spam across iterations, (b) makes the aggregate flip deterministic on branch-protection setups that count *open* CHANGES_REQUESTED reviews rather than the per-reviewer-latest signal, and (c) closes a class of races where the GitHub API hasn't propagated the new APPROVE before pr_merge polls.
**Confidence:** 0.82 / reversibility: high.

### D13 — `pr_merge` gate routes remediable blockers to `implementation_fix` instead of `await_human`

Before D13, `Dispatcher._enforce_pr_merge_gate` collapsed every non-OK `PrReadiness` from `check_pr_merge_readiness` into a single `RouterDecision(kind="await_human")`. With branch protection on `main` requiring conversation-resolution, Copilot review comments left between verification dispatch and verifier APPROVE flipped `mergeStateStatus` to `BLOCKED`, the gate killed the workspace at `Status.AWAITING_INPUT`, and the loop stalled — even though `pr_merge` itself, if allowed to run, already knows how to forward Copilot threads to `implementation_fix` (D3-ext).

D13 splits the gate's downgrade path through a new private helper, `_classify_pr_merge_blocker(readiness) -> "implementation_fix" | "pr_merge"`:

- `merge_state_status` non-empty and outside `{CLEAN, HAS_HOOKS}` (BLOCKED for unresolved threads, DIRTY for merge conflicts, BEHIND, UNSTABLE, etc.), `review_decision == "CHANGES_REQUESTED"`, or any failing required checks ⇒ `implementation_fix`. The gate rewrites the decision to `RouterDecision(kind="enqueue", team="implementation_fix", reason=<failed_reasons joined>)` so the loop self-heals.
- All other non-OK readiness shapes (only pending checks; a transient gh failure, which is a `ReadinessUnavailable` and passes the merge gate as `MergeGateNotAttempted`) ⇒ pass the original `pr_merge` decision through. `pr_merge`'s own polling loop (`ALAN_PR_MERGE_TIMEOUT_S`/`MAX_POLLS`, A1) remains the final gate for "wait for CI to finish."

The gate falls back to `await_human` only when `implementation_fix` is not in the registered teams dict — practically, a misconfigured deploy. `_enforce_loop_guard` runs **after** this gate (`_apply_router_decision` order: `select_next_team → _enforce_pr_merge_gate → _enforce_loop_guard`) so spiral/revisit checks apply to the rewritten `implementation_fix` target: `detect_spiral`'s `verification ↔ implementation_fix` pair detection and `check_loop_guard`'s per-team revisit cap both run uniformly, whether `implementation_fix` was the original suggestion or came from the gate rewrite.

**Rationale:** observed on `fix-architecture-team-decisions-and-devil-advocate` / PR #192 (2026-05-24): verifier APPROVE, CI green, Copilot left 3 review comments mid-flight, `mergeStateStatus=BLOCKED`, gate downgraded to `await_human`, workspace required manual re-dispatch. D13 closes the most common silent-stop path. Failing CI under APPROVE is technically a verifier miss, but routing to `implementation_fix` is still the right remediation regardless of how we got there.
**Confidence:** 0.88 / reversibility: high (single helper + one branch change; gate behavior fully covered by `tests/test_dispatcher.py::test_pr_merge_gate_*`).

**Superseded (D19).** `_classify_pr_merge_blocker` no longer exists in `alan/` — it was replaced by the centralized ladder in `alan/merge_recovery.py` (`classify_block` + `attempt_mechanical_recovery`), which every non-OK readiness now routes through before the dispatcher ever sees an `implementation_fix`-vs-`pr_merge` choice. The bullet-list dispatch table above describes D13-era behavior only; `DIRTY` in particular no longer falls into the generic "outside `{CLEAN, HAS_HOOKS}` ⇒ `implementation_fix`" bucket it describes — see D19 immediately below. This note exists specifically so a future reader does not go looking for `_classify_pr_merge_blocker` at a stale line number, the exact trap this section's own history has already sprung once.

### D11 — Verifier posts findings as inline PR review comments; `implementation_fix` reads unresolved review threads from the PR

The verification team's `diff_reviewer` emits a `## INLINE_FINDINGS_YAML` block listing each CRITICAL finding with `path / line / body`; the judge relays it verbatim. `verification._apply_pr_review` (at the time this ADR was written; the H5.3 PR-2 review-posting split relocated this to `_verification_review_post._apply_pr_review`) parses the block via `parse_inline_findings` and, when non-empty, calls `_pr_branch.post_pr_review_with_inline_comments(pr_number, body, event, findings)` (at the time this ADR was written; the review-cluster split relocated this to `_pr_post.post_pr_review_with_inline_comments`) — a single REST `POST /repos/{owner}/{repo}/pulls/{n}/reviews` with `comments: [{path,line,side:"RIGHT",body}]` that creates one PR review with N inline review threads. When the block is empty or absent (e.g. APPROVE path, or zero CRITICAL findings), the verifier falls back to `gh pr review --approve|--request-changes --body <stripped>` — `strip_inline_findings_block` removes the YAML section so the human-readable body never leaks raw YAML.

`implementation_fix._maybe_fetch_threads` calls `_pr_branch.list_unresolved_threads(pr_number)` (at the time this ADR was written; the review-cluster split relocated this to `_pr_threads.list_unresolved_threads`) (`gh api graphql` on `reviewThreads`) when the prior handover carries a `pr_number`. Each resolved/outdated/structured thread becomes an entry in a new `## Unresolved PR threads` prompt block (author, `path:line` or `(non-inline)`, break-proof fenced body — see D17, plus an untrusted-content notice so reviewer-controlled body text can't smuggle instructions to the worker). The block sits alongside the existing `## Judge review` block — the latter still carries PR-level Copilot issue comments / review bodies that `pr_merge` forwards via the handover summary (those are NOT review threads, so `list_unresolved_threads` doesn't see them). The new flow lands in production via PRs #175 (Phase 1: helper + dual-write behind flag), #176 (Phase 2: impl_fix + flag flipped live in `deploy/ai.alan.plist`), and PR #178+ (Phase 3: flag dropped, always-on).

`implementation_fix` adds a third input block, `## Failing required checks`, from one of two sources (#1430):

**(a) Gate block present.** `implementation_fix._maybe_fetch_gate_failures` reads the actionable check names out of the prior verification handover's gate block (`verification.parse_actionable_gate_checks`, keyed on `GATE_ACTIONABLE_CHECKS:` — populated by `_resolve_actionable_gate_checks`: survivor-evidenced promotion with a diff-join fallback, see `merge_recovery.md`) rather than re-querying readiness — the verifier already decided actionability, and a second readiness snapshot could disagree with the one that produced the block. Only when that list is non-empty does it call `_pr_branch.fetch_failing_check_details(pr_number, names)`, one `gh api .../check-runs` read that returns each check's `output.title` / `output.summary` / details URL. That summary is the only place a Sonar **quality-gate condition** (e.g. `6.0% Duplication on New Code (required ≤ 5%)`) is reachable: it is a measure, not an issue, so `list_sonarcloud_annotations` returns nothing for it. A `GATE_ACTIONABLE: no` block, or one produced by a `DIRTY` merge state, yields no actionable names and so no block — unchanged.

**(b) No gate block after a verification pass.** A verification pass in `rescue_only` or `skip` gate-path mode (see D14's "Gate-path modes" below) writes no gate block at all, so before #1430 the next fix round heard about a red required check only if the judge happened to mention it in prose. `alan/teams/_fix_gate_checks.py::live_failing_checks` closes this: when `_maybe_fetch_gate_failures` returns nothing, `implementation_fix._build_user_text` calls it. It is eligible in exactly two cases, both requiring a `pr_number` already carried on the prior handover (`_blockless_pr_number`; there is no workspace-level pull-request lookup, so the decomposed-workspace failure mode of alan#1594 is not inherited). Originally (#1430) only the first existed, restricted to verification: the prior's `from_team == "verification"` and `gate_block_section(prior.full_synthesis)` empty — keyed on section presence, not on an empty actionable list, so a present-but-`no` block (case (a)) never reaches it. The second, added by the park-options work (alan#1644), admits an answer-recording handover from `implementation_fix` specifically: `from_team == "implementation_fix"` and `handover.is_answer_recording(prior)`, the `revisit_amend` handover `record_answer` writes after a `non_actionable_feedback_*` park is answered. That is the round that used to render no failing-check section at all, because the fix team's own answered park is neither verification-sourced nor a gate-block carrier. Admitting it is safe without the gate-block veto: an answered park has no gate block of its own, and the veto is deliberately not applied to this branch because a fix worker's synthesis can echo a gate block verbatim (the answer-recording handover carries that synthesis forward) and would silently disable the lookup. Fix-sourced priors generally — a plain forward handover from the fix team — are still not eligible. When eligible, it does exactly one non-waiting, non-mutating read — `_pr_ready.readiness_or_unavailable(pr_number, task_id, forge_target=forge_target)`, never the verifier's `check_pr_verifier_blockers` — filters the result through the same, unchanged `_verification_gates._resolve_actionable_gate_checks` the approving path uses (survivor-evidenced promotion with the diff-join fallback, at the readiness snapshot's own `headRefOid`), and on a non-empty actionable set fetches details the same way as (a). It never calls `_resolve_gate_readiness` or `_settle_wait` — no settle-wait poll loop, no bounded flaky-check rerun, no review dismissal, no ledger write (flake occurrence, flake survival, or gate-rerun count), and no `gate_path` audit row; the only rows it can produce are the diagnostic ones `readiness_or_unavailable`'s own read already writes. A check still pending when the round starts is therefore never presented as a failure — `_resolve_actionable_gate_checks` derives actionability from `failing_checks`, not `pending_checks`. A forge failure, rate limit, or unreadable response during the read never fails the fix round: `readiness_or_unavailable` already catches the two exceptions `raise_for_infra` can raise and returns a `ReadinessUnavailable`, which `live_failing_checks` narrows out, and every downstream leaf (`fetch_failing_check_details`, the flake-ledger helpers) fails soft on its own — `live_failing_checks` needs no `try`/`except` of its own. A `pr_merge`-sourced prior, a fix-sourced prior that is not an answer-recording handover, or one with no `pr_number`, gains no new lookup at all. Measured against `verification_audit.jsonl`'s `gate_path` sequences, five workspaces in a four-week window lost a full verification-and-fix round to this exact gap before landing green on a later approving pass that did carry a block: #1134 (Mobile-UI ratchet), #1159 (E2E), #1279 (E2E), #1322 (Python lint), and one from a second engine's own `ios-ci` check.

Either source renders through the same block, `_fix_gate_checks.gate_failures_block`, which states explicitly that these checks are in scope for the round — without that, `implementation_fix`'s scope-lock to review findings makes a worker decline them as somebody else's problem, which is exactly what happened on PR #855. This section previously stated that it does not inline CI logs; that is reversed. The block now carries a bounded, fenced failure excerpt per check (`_fix_gate_checks.with_evidence`, called once at `_build_user_text`'s join after the source-(a)-or-(b) selection, so both sources carry it): the check's failure-level CI annotations where they are usable, and the tail of the failed job's log (`_pr_branch.fetch_failed_log`, `gh run view --job <id> --log-failed`) where they are not. An annotation is sufficient only when its `annotation_level` is `failure` and its `path` is a non-empty string whose **first path segment** is not `.github` — a step that died with no test reporter attached publishes an annotation whose path is exactly `.github` (no trailing slash), which a "not under `.github/`" prefix test would accept, so the log fallback would never fire for the incident that motivated this; bare `.github`, `.github/workflows/ci.yml`, `./.github/x` and `/.github/x` all fall through, `alan/teams/x.py` does not. The log is read only when the details URL has a `/job/<n>` segment (`_pr_branch.job_id_from_details_url`, the same regex `failed_job_id` uses, no second rollup listing); the coincidence between job ids and check-run ids that `fetch_failing_e2e_tests` relies on is deliberately not generalised, so a check with no job segment gets annotations only. Each excerpt is filtered generically (ANSI/CSI escapes and control characters other than newline and tab stripped, GitHub token-shaped runs redacted, each line capped, then a 2,000-character bound — head-kept for annotations, tail-kept for logs because assertions sit at the end — with a truncation marker), and fenced through `_fence.fence` so no backtick run inside it can close the fence; there is no per-engine parser and no engine configuration. At most `_EVIDENCE_INSPECT_CAP` (3) checks are inspected per dispatch, serially — up to one annotation call and one log call each, all reusing `GH_TIMEOUT_S` — and checks beyond the cap still render their name and link. Any fetch failure or exception yields an empty excerpt, never a failed dispatch. `_GATE_OUTPUT_UNTRUSTED_NOTICE` names check-run title/summary, CI annotation messages and CI log lines as untrusted data. The block still does not tell the worker to run any `gh` command — fix workers hold no `gh` grant (see CLAUDE.md's auto-mode boundary), so the previous "`gh pr checks` / `gh run view --job <id> --log-failed`" instruction was always denied when a worker attempted it; the host fetches the evidence instead. It also points at the details URL and tells the worker to reproduce the failure locally with the matching gate command from CLAUDE.md before changing anything, then re-run it to confirm the fix. The rule that a red required check with a green local gate is a divergence to investigate, not grounds to give up, lives once in `_fix_prompt.NON_ACTIONABLE_GUIDANCE` (the system prompt), not in this block. When the E2E check is among the actionable names and its failing tests can be read (`e2e_failures.FailingE2ETest`, gated on the E2E check name specifically being in the actionable set, not merely in the raw failing-checks list), the block also names each failing spec/title under a `### Failing E2E tests` heading.

**Rationale:** before Phase 1, the verifier posted a single `gh pr review --body <markdown>` thread on the PR, but `pr_merge`'s gate (PR #164) required all unresolved review threads — including Copilot's inline threads — to be resolved before merge. Copilot's findings never entered the `implementation_fix` loop because impl_fix only read the verifier's handover. Result: PRs with Copilot-only findings escalated to humans. With Phases 1-3, every reviewer surface (verifier inline + Copilot inline + human inline) lands as a review thread on the PR, and `implementation_fix` iterates over them uniformly via `list_unresolved_threads`. The remaining non-thread Copilot items (PR-level issue comments / review bodies) keep the `pr_merge → impl_fix` forwarding path via the handover summary; they aren't part of the inline review-comment surface.

**Confidence:** 0.85 / reversibility: medium (verifier marker format is the lock-in; switching to a different `path/line` extraction would require a prompt + parser rewrite).

**Approval resolves the verifier's own threads (#1411).** After an approving verification pass, the host resolves the verifier's own earlier review threads on the same PR under the verifier's own identity — `alan/teams/_verifier_thread_resolution.py`. Trigger: only after verification has successfully posted an APPROVE review — never after a change request, a comment-only review, a failed post, or a dry run. Count floor: nothing is resolved unless the pass's posted raw CRITICAL count is 0 and was actually reported, either by the judge's own verdict section or by the diff reviewer — a count the reviewer-count fallback merely supplied because neither role reported one counts as absent (`_verdict.report_critical_counts` / `CriticalCountReport`), and a diff reviewer that itself reported a nonzero count holds resolution even when the judge approved. Author scope: only threads whose root comment is authored by the configured verifier identity are candidates — threads rooted by Copilot, a human, or any other account are never touched by this path. Replies: a candidate thread with any reply, or one whose reply count can't be read, stays open. Identity is confirmed (`gh api user`) before anything is resolved, and it stops on the first forge failure for that pass, recording every remaining candidate as refused rather than retrying or changing the verdict or routing. Three audit actions in `verification_audit.jsonl` — `verifier_thread_resolved`, `verifier_thread_refused` (`has_replies`, `reply_count_unreadable`, `forge_refused`, `stopped_after_failure`), and `verifier_thread_resolution_held` (`count_not_reported`, `reviewer_nonzero`, `posted_count_nonzero`, `no_reviewer_credential`, `verifier_login_unconfigured`, `identity_check_failed`, `login_mismatch`, `thread_read_failed`) — let the unresolved-thread park rate be re-measured after merge. `verifier_login_unconfigured` is the hold when no verifier login resolves (D28, "Verifier identity"): the pass makes no `gh api user` call and reads no threads, and the thread filter would select none even if it did. `pr_merge`'s unresolved-thread check and the conversation-resolution branch-protection requirement are unchanged; this never becomes a route to dismissing a finding.

### D14 — Verifier syncs working tree to PR head before judging; settle-waits on pending CI before downgrading

Two coupled behaviors added to `VerificationTeam.run()` and `resolve_external_gates`:

**Head-sync (superseded).** This paragraph originally described `_pr_branch.sync_to_pr_head`/`_git_checkout_detached` — `git fetch origin <branch>` then a force-checkout-and-detach onto `FETCH_HEAD`. Both were deleted: the helper had no production caller (verification never called it) and, being a `git checkout --force`, was the one call on this path that would have destroyed uncommitted work had anything ever reached it. The verifier's actual head-sync is `_try_acquire_grounded_checkout` (`alan/teams/_verification_grounding.py`), which leases a worktree via `leased_with_affinity(..., existing_branch=branch, worktree_factory=implementation_worktree)` and checks out the PR branch fresh into it — the mechanism the rest of this ADR entry (settle-wait, changed-e2e scenario, gate-path modes) already assumes.

**Changed-e2e scenario.** `_compute_scenario_results` appends a host-synthesized `changed-e2e-specs` scenario (see `e2e_testing.md` — "Changed-spec execution in the worker lanes") whenever the diff touches Playwright spec files or removes a `data-testid` an e2e spec asserts on. It runs in the grounded checkout via the ordinary scenario runner with a dedicated `ALAN_CHANGED_E2E_TIMEOUT_S` budget, independent of the authored-scenario mode (MISSING still runs it; WAIVED skips it).

**Settle-wait.** When the verifier's verdict would be APPROVE but `check_pr_verifier_blockers` reports only *pending* checks (no `failed_reasons`, non-empty `pending_checks`), the verifier waits within a bounded budget rather than treating the pending state as a hard block. The budget is **wall-clock**: `ALAN_VERIFIER_SETTLE_MAX_POLLS` × `ALAN_VERIFIER_SETTLE_POLL_INTERVAL_S` seconds (default 108 × 30 s = 3240 s / 54 min — sized against the `e2e-lane` concurrency group's worst-case single-PR lane-drain bound, see `docs/architecture/ci_isolation.md`'s settle-wait section), spent in **backed-off wake-ups** rather than fixed-interval polls: sleeps of 1×, 1×, 2×, 4×, 8× the interval, then 10× the interval (`_SETTLE_BACKOFF_MULTIPLIERS`, `_SETTLE_BACKOFF_CAP_MULTIPLIER`, `_settle_sleep_s`), the last one clipped to whatever budget remains — at the defaults that is 30, 30, 60, 120, 240 s, nine 300 s sleeps and a 60 s remainder, 15 wake-ups summing to exactly 3240 s. The budget arithmetic is unchanged; only the wake-up count dropped from 108 to ≤ 15. The budget is tracked as a monotonic deadline (`time.monotonic()`, `_settle_next_sleep_s`): each sleep is `min(backoff, deadline − now)`, so probe and fetch latency count against the budget and the wait stops at the deadline rather than at the sum of the sleeps it asked for. The wake-up count is additionally bounded by `max_polls`, which is what keeps a zero `ALAN_VERIFIER_SETTLE_POLL_INTERVAL_S` (accepted by `float_env`) meaning "`max_polls` immediate rechecks", exactly as before, instead of "no wait at all". At each wake-up the verifier first re-reads the PR's current head SHA (`_pr_branch._fetch_pr_head_sha`, `gh pr view --json headRefOid`, ~1 GraphQL point) and compares it with the head SHA of the last authoritative readiness snapshot (`PrReadiness.head_sha`, from `headRefOid`). A mismatch means a push landed mid-wait: the probe is skipped, a `verifier_settle_head_moved` row (`pinned_sha`/`head_sha`) is written and the authoritative fetch runs on this very wake-up, re-pinning to the new SHA — an old commit's still-queued check can never hold the wait on a stale head. On a match it runs the cheap REST **probe** — `_head_has_pending_check_runs` → `_pr_branch._iter_check_runs(forge_target, ..., strict=True)`, which reads the page through the port's `commit_check_runs_page` (`gh api repos/{owner}/{repo}/commits/{head_sha}/check-runs?per_page=100`, 0 GraphQL points) bucketed by `_pr_ready.pending_check_run_names`. `strict=True` is the one opt-in knob added to the shared `_iter_check_runs`: a payload without a list-valued `check_runs` field is reported through `on_fail` (`check_runs_field_missing`) and read as *unavailable*, where the lenient default the quarantine and Sonar paths use still normalises it to an empty list. While the probe says something is still `queued`/`in_progress`, the wake-up ends there: the ~100-point `statusCheckRollup` readiness fetch is skipped. Only when the probe reports nothing pending, when it is unavailable (head-SHA read or check-runs read failed, malformed payload — audited as `verifier_settle_probe_unavailable` with the `reason`; that name and `verifier_settle_head_moved` are deliberately free of every `_FAILURE_KEYWORDS` token so the triage pre-gate never counts them as recurring fleet errors), or when there is no head SHA to probe does the verifier make the authoritative `check_pr_verifier_blockers` fetch. **The verdict always comes from that authoritative fetch**, never from the probe: on check concluding green: approval stands; on check concluding failed: REQUEST_CHANGES is issued; on transient gh failure during settle: approval proceeds immediately; on budget exhaustion: approval proceeds (no downgrade). Before the 2026-09 quota incident every one of the up-to-108 polls made the rollup fetch (~10 800 GraphQL points per fully drained wait); now a wait spends at most 15 head-SHA reads and REST probes plus one rollup fetch per wake-up whose probe came back clear or unavailable, or whose head moved. Audit rows: `verifier_settle_poll` per wake-up (carrying `poll`, `pending` and the chosen `sleep_s`); on resolution, `verifier_settle_green` (check concluded green), `verifier_settle_fail` (check concluded failed), `verifier_settle_transient` (gh failure), or `verifier_settle_timeout` (budget exhausted; carries the actual wake-up count as `polls` and the wall budget as `budget_s`). Helpers `_settle_wait`, `_settle_next_sleep_s`, `_settle_fetch_exit`, `_head_has_pending_check_runs` and `_resolve_gate_readiness` live — since the H5.3 PR-3 external-gate-cluster split — in `alan/teams/_verification_gates.py`, keeping every function at CCN≤7.

**Gate-path modes (rescue_only, PR "reachable-gate-recovery-on-non-approve-verdict").** `resolve_external_gates` classifies every invocation into one of three modes via `_gate_path_mode` before doing anything else: `downgrade` (the effective verdict is `APPROVE` — behavior identical to the paragraphs above), `rescue_only` (the verdict line explicitly parses as `REQUEST_CHANGES` **and** `effective_critical_count(...) == 0`), or `skip` (everything else, including an unparseable/missing `VERDICT:` line and any effective critical count > 0 — no `gh` call is made at all). `rescue_only` exists because the settle-wait and bounded flaky-gate rerun above were originally reachable only on the `downgrade` arm, so a genuine `REQUEST_CHANGES` verdict with zero criticals (e.g. a missing-scenarios rejection with no connection to CI) left a red flake unrerun. On `rescue_only`, `_resolve_gate_readiness` still runs in full — settle-wait on pending checks, then the bounded flaky-gate rerun and its ledger occurrence/survival writes on a failure — but the judge output is returned byte-identical (`is` the same object) and `GateDowngradeResult.downgraded`/`flaky_only` are always `False`: the *downgrade* itself (rewriting `VERDICT:`, appending the `## External Gate Status` block, routing `flaky_only` into the merge lane) stays `APPROVE`-only. Every invocation with a resolvable `pr_number` appends a `gate_path` row to `verification_audit.jsonl` carrying `mode` and, when readiness was resolved (`downgrade` or `rescue_only`), `gh_ok`/`failing_checks`/`pending_checks`; `skip` and the no-`pr_number` case carry no readiness fields (the latter carries no row at all — the `pr_number is None` short-circuit is the push-to-main invariant and runs before classification).

Neither `rescue_only` nor `skip` writes an `## External Gate Status` gate block — that section only exists on the `downgrade` (APPROVE-only) arm. So the next fix round, if any, reads the red required checks itself via source (b) above (`_fix_gate_checks.live_failing_checks`) instead of inheriting them from the verification handover's prose.

**Flaky-gate rerun (bounded).** Before downgrading APPROVE→REQUEST_CHANGES for a *failed* external check, `_resolve_gate_readiness` calls `_maybe_rerun_flaky_gates`. When the failing checks are **all** in the timing-sensitive allowlist `_RERUNNABLE_FLAKY_GATES` (currently `{"Frontend E2E (Playwright, blocking)"}`), the merge state is not `DIRTY`, the review is not `CHANGES_REQUESTED`, and the per-PR rerun counter is under `ALAN_MAX_EXTERNAL_GATE_RERUNS` (default 1), the verifier re-requests that check's check-suite (`_pr_branch.rerun_external_gate` → the same `check-suites/{id}/rerequest` primitive Sonar uses, resolved by name via `_find_check_suite_id_for_name`), bumps the counter (`_pr_state_paths.bump_gate_rerun_count`, persisted at `~/.alan/state/pr_<n>_gate_reruns.json`, honoring `ALAN_STATE_ROOT`), and then `_settle_wait`s for the rerun to conclude. If the rerun goes green the original APPROVE stands (→ `pr_merge`); if it fails again — or the counter is exhausted, or any non-allowlisted/real check is also failing — the normal downgrade → `implementation_fix` path runs unchanged. This gives a genuinely flaky gate a bounded second chance to produce real green signal instead of burning a futile `implementation_fix` cycle and escalating to a human (`loop_guard.external_gate_blocked`). Audit rows: `external_gate_rerun_ok` / `external_gate_rerun_failed` in `impl_audit.jsonl`. A doubly-flaky (or genuinely broken) gate still escalates after the cap.

**Rationale:** Without head-sync, a fast-push implementer leaves the verifier judging a stale commit. Without settle-wait, the verifier fires REQUEST_CHANGES on a PR whose CI is still in-progress, creating a spurious `implementation_fix` round-trip. Without the bounded flaky-gate rerun, a timing-flake in a check unrelated to the diff (e.g. a Playwright visibility race) downgrades to `implementation_fix` — which cannot fix a test its diff never touched — and the loop guard escalates to a human.

**Confidence:** 0.9 / reversibility: high (non-fatal sync; settle budget exhaustion preserves prior behavior; both paths covered by unit tests).

### D16 — Verdict-grammar hardening: both-directions marker discipline, reviewer-count backstop, widened retry trigger, count-flip banner (PA3.1: PA-09, PA-10, PA-31b/c)

Four coupled hardenings to the verification judge's machine-readable grammar, closing the gap between what the judge is asked to write and what the harness actually trusts, without changing the set of allowed verdict values or how `effective_verdict`/`effective_critical_count` are computed.

**Both-directions `SCENARIOS_MISSING` marker discipline (PA-09).** `loop_guard._classify_scenarios_missing` classifies an escalation by a plain substring check (`SCENARIOS_MISSING_MARKER in verif.full_synthesis`) over the judge's free-form prose — nothing previously constrained the judge to write the token only when it was true. Production judges were observed writing it *in negation* ("this is not a `SCENARIOS_MISSING` case"), which the substring check reads as a positive hit, and were also observed omitting it via paraphrase when scenarios genuinely were missing. `_JUDGE_PROMPT` now states the rule both ways: emit `SCENARIOS_MISSING` verbatim on its own line **only** when absent test scenarios are the reason for `REQUEST_CHANGES`; in every other case, never write that token anywhere — not negated, not quoted, not hypothetically. The loop-guard's classification code itself is unchanged; its input is simply more trustworthy now.

**Worked verdict-block example (PA-10).** The `## IN-SCOPE ACCEPTANCE OUTCOMES` grammar (`DIFF_FINDINGS_CRITICAL:` / `DIFF_FINDINGS_CRITICAL_IN_SCOPE:` / `VERDICT:`, in that order) was previously described only in prose. `_JUDGE_PROMPT` now shows a literal 3-line worked example immediately after that prose, so the exact grammar — not just its description — reaches the judge.

**Reviewer-count fallback (PA-10).** The post-#508 critical-findings backstop (`effective_verdict` downgrading `APPROVE → REQUEST_CHANGES` when the critical count is nonzero) previously depended entirely on the judge *echoing* the diff_reviewer's `DIFF_FINDINGS_CRITICAL:` line — a judge that dropped the line silently defaulted to a count of 0 via `parse_critical_count`'s zero-default, defeating the backstop with no error signal. `alan/teams/_verdict.py`'s `_apply_reviewer_count_fallback(judge_output, diff_reviewer_output)` is called from `VerificationTeam._collect_outputs` (after the retry step, before `_strip_in_scope_critical_line`): when the judge's `## Verdict` section (extracted by `_verdict_section`, falling back to the whole output when no `## Verdict`-equivalent heading is found) has no `DIFF_FINDINGS_CRITICAL:` line, it splices in a normalized one carrying the diff_reviewer node's own `parse_critical_count` result. Scoping the "already present" check to the `## Verdict` section — rather than searching the whole judge output — stops a stray or quoted example line elsewhere in the review (e.g. a worked example inside `## Rationale`) from defeating the fallback.

The injection point is `_restoration_anchor(judge_output)`: the earliest `.start()` among the first matches of `DIFF_FINDINGS_CRITICAL:`, `DIFF_FINDINGS_CRITICAL_IN_SCOPE:`, and `VERDICT:` anywhere in the judge output (not just inside the `## Verdict` section), defaulting to append-at-end when none match. This replaced an anchor that only ever considered `DIFF_FINDINGS_CRITICAL_IN_SCOPE:` or the first `VERDICT:` line: every downstream reader of the critical count (`parse_critical_count`, `effective_critical_count`, the loop guard) is a first-`.search()`-match, so an injection landing *after* an earlier stray or quoted `DIFF_FINDINGS_CRITICAL:` line elsewhere in the prose was never the value those readers actually parsed — the restoration reported success (the text really did contain the new line) and changed nothing observable. Anchoring at the earliest candidate, rather than the maximum of the judge's and reviewer's counts, is deliberate: both real production divergences had the judge substantively right (one finding was explicitly out of scope, the other a false positive the judge disproved by running the linter itself), so restoring the *reviewer's* count only where nothing else already claims that position preserves the judge's authority everywhere it already spoke.

`_VERDICT_HEADING_RE` is now case-insensitive and depth-tolerant (`^(#{2,6})\s+Verdict\b`, `MULTILINE | IGNORECASE`) instead of requiring an exact `## Verdict`; the section ends at the next heading at the *same or shallower* depth, derived from the captured heading's own hash run, replacing a fixed `^##\s` cutoff. Both holes had to close together: case-insensitivity alone still missed a `### Verdict` heading entirely (falling back to the whole document, where a stray count anywhere would suppress the fallback even though the judge's own verdict block never got one), and depth-tolerance alone without a same-or-shallower rule would let a nested subheading (e.g. `#### Evidence`) end the section early and make the fallback override a count the judge did emit inside it.

**Widened retry trigger (PA-31b).** The judge-retry mechanism (see [implementation_pipeline.md](implementation_pipeline.md) §"`VerificationTeam`") previously fired only when the `VERDICT:` line itself was unparseable. `_judge_retry_reason(workspace, judge_output) -> Literal["missing_verdict", "missing_in_scope_count"] | None` widens this: it also fires when a `## IN-SCOPE ACCEPTANCE OUTCOMES` block is present in the prompt (`_scope_block_present`) but the judge's output omits `DIFF_FINDINGS_CRITICAL_IN_SCOPE:` — the exact situation that previously force-flipped an APPROVE to REQUEST_CHANGES via the raw-count backstop with no second attempt. The retry stays one-shot; the nudge constant is renamed `_JUDGE_VERDICT_MISSING_NUDGE` → `_JUDGE_RETRY_NUDGE` (reason-agnostic) and now asks for a COMPLETE re-emit of every mandatory line, matching the fact that the retry node's output wholesale-replaces the original judge output rather than patching a single line. The audit action string `judge_verdict_missing_retry` is unchanged (an existing test pins it); the reason is threaded as an added `"reason"` field on that same audit row.

**Count-flip banner (PA-31c).** Previously, when `effective_verdict` downgraded a judge's literal `VERDICT: APPROVE` to `REQUEST_CHANGES` because of a nonzero critical count (whether self-reported, in-scope-overridden, or reviewer-count-fallback-supplied), the posted review body kept the judge's original prose verbatim — including a `VERDICT: APPROVE` line and possibly "no blocking issues" framing — while GitHub recorded a `REQUEST_CHANGES` review, an internally contradictory posted body (the same class of defect D10a fixed for the external-gate case). `_maybe_flag_count_flip(judge_output)` is called from `alan/teams/_clause_audit.py::apply`, which `_build_verdict_handover` invokes immediately after `resolve_external_gates` and before the `verdict_counts` audit row; it detects exactly this mismatch (literal verdict is `APPROVE`, `effective_verdict` is `REQUEST_CHANGES`) and, mirroring `_downgrade_output`'s existing convention, both rewrites the literal `VERDICT:` line via `_VERDICT_RE.sub` **and** prepends a `>`-blockquoted banner naming the reconciled critical count. No review is ever posted whose body text contradicts the decision it records. Before the reviewer-count-fallback anchor fix above, this banner had never appeared in any production review artifact: the only realistic route to `APPROVE` + a positive effective count was a successful reviewer-count restoration, and the anchor defect made restoration parse-invisible on every path that needed it.

**Scenario gate (2026-08-21).** `alan/teams/_scenario_gate.py::apply(judge_output, workspace, inv_id)` runs in `_build_verdict_handover` immediately after `_clause_audit.apply`, giving it the same placement relative to `_maybe_post_review`, `_write_review_artifact`, `suggestions_for_verdict`, and `_verdict_decisions` that the clause-audit rewrite already has. It loads outcomes persisted at derivation time (see below) from `<inv_id>/scenario_outcomes.json` via `load_outcomes`, and blocks — rewriting the verdict to `REQUEST_CHANGES` and prepending a named banner via the shared `alan/teams/_verdict.py::rewrite_verdict_to_request_changes` helper — on any scenario status that is neither `PASS` nor a member of `alan/teams/_scenario_runner.py::NON_BLOCKING_STATUSES` (`{"SKIPPED", "DOCUMENTED", "ADVISORY", "BUDGET_EXHAUSTED"}` — a later change added the blocking `TIMEOUT` status and the non-blocking `BUDGET_EXHAUSTED` status as distinct `ScenarioStatus` literals; only `BUDGET_EXHAUSTED` joined this frozenset, so `TIMEOUT` blocks exactly like `FAIL` — see [acceptance_gate.md](acceptance_gate.md)'s status table); an unrecognized future status fails closed (treated as blocking). When outcomes are unavailable (`load_outcomes` returns `None` — no file, corrupt JSON, or schema mismatch), `apply` returns the judge output unchanged and appends a `scenario_gate_no_outcomes` audit row, so gate inertness is a logged, queryable event rather than silent. `VerificationTeam.run()` persists the derived `ScenarioOutcome` list via `save_outcomes` immediately after computing scenario results and *before* `run_pipeline` starts, but only when `_scenario_runner_already_succeeded(workspace, inv_id)` is false — i.e. only on a fresh derivation, never on a resumed invocation whose scenario-runner node already succeeded. This ordering and guard together are the correctness property: persisting unconditionally on every call would let a resumed invocation's necessarily-empty recomputation (`_compute_scenario_results` short-circuits to `[]` specifically so the resume path doesn't repeat a full scenario suite plus a browser run) overwrite the good data a prior, interrupted attempt already derived; persisting only *after* the pipeline runs would leave a worker killed mid-pipeline with the scenario-runner node marked successful and no outcomes ever recorded. Read and write both live inside the invocation's own directory alongside the node result and config caches, so the mechanism inherits the workspace root's existing state-isolation contract and registers no new `ALAN_*` variable.

`verdict_counts` audit rows now also carry `critical_reviewer` (the diff_reviewer's own raw count via `alan/teams/_verdict.py::parse_critical_count_or_none`, `None` when the reviewer's output has no parseable `DIFF_FINDINGS_CRITICAL:` line, reset per invocation via a context-var token so a value never leaks across sequential invocations in the same process) and `reviewer_divergence` (`True` when the reviewer's raw count disagrees with the raw count that shipped in the final output). Both are recorded unconditionally, with no banner and no verdict change on that path: when a scoped `DIFF_FINDINGS_CRITICAL_IN_SCOPE:` line is present, it continues to shadow the raw count for `effective_verdict`/`effective_critical_count` exactly as before — the divergence field makes disagreement *visible in the audit log* without reopening the scope-partition mechanism two real production cases already depended on.

**Coverage.** Each prompt-level change (marker discipline, worked example) is covered by a new case in the existing `tests/eval/golden/judge/` suite (`case_09` under `scenarios_missing`, `case_10` under `scope_partition_approve`) — advisory only, scored by the weekly `alan.eval_sweep` run, never a PR gate; a golden case there does not by itself discharge mechanical test coverage for the reviewer-count or scenario-gate backstops, which is why `tests/test_verification_verdict_composition.py` drives the real `VerificationTeam.run()` path end to end rather than calling `_maybe_flag_count_flip`/`_scenario_gate.apply` directly. `rubric.yaml` and `judge_eval.py` are unchanged.

**Rationale:** all four defects share a root cause — the harness placed more trust in the judge's free-form prose than the prose's own grammar earned. Tightening what the judge is told to write, parsing defensively when it doesn't, retrying when the retry is actually warranted, and being honest in the posted body about when the harness overrode the judge closes all four without touching `effective_verdict`'s semantics or the loop-guard's classification code.
**Confidence:** 0.87 / reversibility: high (prompt text + small pure-function harness changes; every branch covered by unit and integration tests in the `tests/test_teams_verification_*.py` siblings).

### D17 — Break-proof backtick fences guard every genuinely-external body or subprocess-output tail forwarded into an agent prompt

`alan/teams/_fence.py` (new, dependency-free — stdlib `re` only) exports `fence_delimiter(body: str) -> str` and `fence(body: str, *, info: str = "") -> str`. The delimiter is the longest run of consecutive backticks anywhere in `body`, plus one, floored at 3 — so no substring of `body`, however many backticks it contains, can prematurely close the fence. `body` is never mutated, truncated, or escaped; only the delimiter length varies with content. When `body` contains no backtick run of 3 or more, `fence()` reproduces the plain ` ``` ` fence used everywhere before this change.

Applied at every site where text an outside party controls (a GitHub review thread/comment body, or a captured subprocess stdout/stderr tail) is interpolated into a prompt that reaches a code-editing worker:

- `implementation_fix._pr_threads_block` — each `ReviewThread.body` (Copilot bot or human reviewer) is now fenced via `_fence.fence`. `_PR_THREADS_UNTRUSTED_NOTICE` (the stronger, thread-specific notice — D11) is preserved verbatim; only the previously-hardcoded ` ``` ` fence became break-proof.
- `implementation_fix._judge_review_block` — now prepends `UNTRUSTED_CONTENT_NOTICE` and fences the body. This block renders either the verification judge's own review (system-authored, trusted) or, via `_load_judge_review`'s fallback to `prior.full_synthesis`, a `pr_merge`-forwarded Copilot summary (genuinely external) — the two cases are indistinguishable at this call site, so both are guarded uniformly.
- `pr_merge._copilot_summary` — each `CopilotThread.body` / `CopilotComment.body` is fenced, with a `UNTRUSTED_CONTENT_NOTICE` prefix. This text becomes `full_synthesis` on the handover routed to `implementation_fix` and, per the point above, flows straight into `_judge_review_block`'s fallback path — closing the gap where Copilot bodies previously reached a write-capable worker unfenced and unguarded.
- `pr_merge._thread_block` / `_comment_block` — the same `CopilotThread.body` / `CopilotComment.body` values also flow through a second, parallel path: `_write_copilot_threads_file` renders them into the `.alan/copilot_threads_<inv_id>.md` artifact, which is attached as an `ArtifactRef` and surfaced directly in `implementation_fix`'s prompt via `_pr_handover._prior_artifacts_block`. Both block builders now fence the body, and the file is prefixed once with `UNTRUSTED_CONTENT_NOTICE` ahead of all blocks — this parallel artifact-file path was left unguarded when `_copilot_summary` was first hardened and is closed here.
- `_scenario_runner.format_results_block` — a `UNTRUSTED_CONTENT_NOTICE` after the `## Scenario execution results` header, and each `ScenarioResult.stdout_tail` / `stderr_tail` fenced. Captured subprocess output can itself carry attacker-influenced content (e.g. a test that echoes file contents back), and this block is spliced directly into the `scenario_runner` role's prompt via `VerificationTeam._role_user_prefix`.

Sonar findings (`_sonar_fix_block.sonar_findings_block`) are semi-trusted — hard containment stays out of scope for them (forcing structured internal output into a delimited block is awkward and low-value); a guard-notice-only pass over those and the remaining chat prompts is tracked as a separate, file-disjoint slice. That judgement is reversed for static-pipeline role outputs only: the verifier's own diff/judge prose is system-authored, but a later role reads it verbatim as prompt text, and a forged `## External Gate Status` block hidden in an earlier role's output got the verification judge to approve the must-not-flip hostile-injection case (alan#1959). `build_role_user_text` now wraps every earlier role's output in per-call nonce markers (`alan/teams/role_output_fence.py`; format and nonce rules in [teams_taxonomy.md](teams_taxonomy.md)), so for role outputs hard containment is applied, not skipped.

**Rationale:** the well-worded data-not-instructions guard previously existed at exactly one ingestion surface (`_PR_THREADS_UNTRUSTED_NOTICE`), and even there the fence itself was breakable — a reviewer who opens a thread with a body containing a run of 3+ backticks on its own line closes the fence early and appends arbitrary "instructions" that render as prompt text, not quoted data. On a public, self-deploying repo, any GitHub user can open such a thread, and `pr_merge` already forwarded unfenced Copilot comment/review bodies into `full_synthesis`. `_fence.py` is a single, dependency-free helper reused (not duplicated) at every site of this class, so a leftover unfixed interpolation is treated as a defect.
**Confidence:** 0.9 / reversibility: high (additive; delimiter computation is the only behavior change, and the default case — no backtick run ≥ 3 in `body` — reproduces the exact prior fence byte-for-byte).

### D18 — Repair the unresolved-feedback merge gate: malformed query, unverified identity, fail-open on failure (three-defect stack)

The gate D3-ext describes shipped with three stacked defects (introduced by `0b3d9bb9` / #164), live for roughly three months without ever blocking a single merge:

1. **Malformed query.** `pr_merge._gh_feedback_raw`'s GraphQL selected `author { login }` directly on the `PullRequestReviewThread` node. `author` does not exist on that type — GitHub rejects the query outright (`undefinedField / PullRequestReviewThread / author`), confirmed live.
2. **Unverified identity.** Because the query above always failed, the classifier's `copilot_login` comparison (`_COPILOT_BOT_LOGIN = "copilot-pull-request-reviewer[bot]"`) never once ran against a real response. Live verification against PR #1017 found three different values for "the same" identity: GraphQL `author.login` → `copilot-pull-request-reviewer` (no `[bot]` suffix), REST `user.login` → `Copilot`, and the hardcoded constant → `copilot-pull-request-reviewer[bot]`, matching neither.
3. **Fail-open on failure.** `_gh_feedback_raw` returned `""` on any non-zero `gh` exit or transport error; the parsers read an empty string as "zero threads, zero comments" — a failing query was indistinguishable from a clean PR, so the gate reported itself healthy while silently never blocking. This is the root cause of the three-month silence and the most important of the three to fix.

Because the query was unreachable, defect 3's swallow was never exercised by the codebase's own tests either — every existing parser test fed synthetic JSON straight to the parsers, never the query against a live API.

**The fix — `alan/teams/_pr_feedback.py`** (new module; the whole feedback path — query, parse, classify, fetch — extracted out of `pr_merge.py` and `_pr_threads.py`, both already at their `tests/size_baseline.py` line caps).

- **Query.** Modeled on `alan.forge_gh._REVIEW_THREADS_QUERY` (unmodified; moved there from `_pr_threads` by X2.7 PR1): `reviewThreads` selects `id,isResolved,comments(first:1){totalCount,nodes{body,databaseId,author{login,__typename}}}` — authorship comes off the thread's first comment, never the thread node itself; `totalCount` (added by D28) is the thread's whole comment count, while `nodes` still holds only the first comment. The PR-level `comments`/`reviews` sections already had a valid `author` field (only the thread node's `author` was malformed); both now additionally select `__typename`.
- **Identity.** `GraphQLActorLogin` is a frozen dataclass wrapping a single `login: str`, pinned to the GraphQL surface: `_COPILOT_GRAPHQL_LOGIN = GraphQLActorLogin("copilot-pull-request-reviewer")` (the MEASURED value above). Every parser takes `copilot_login: GraphQLActorLogin`, never `str` — passing the REST-sourced login (`"Copilot"`) where this type is expected is a mypy-strict and pyright-strict argument-type error, not a maybe-runtime-bug; a future surface mismatch is caught by the type checker before it ships. Classification reads `author.__typename` three ways: non-`Bot` (including a missing author) is `"human"`; `Bot` whose login matches the pin is `"copilot"` (routes to `implementation_fix`); any other `Bot` is `"other_bot"`, counted in the new `ThreadInfo.other_bot_unresolved` / `CommentInfo.other_bot_items` fields — informational, never blocking. This relaxes the old (broken) design, which treated any non-matching login — including other review bots — as `"human"` (blocking); a non-Copilot bot's feedback (e.g. a future second reviewer app) no longer blocks or routes, matching "route only the verified Copilot identity, never guess." The Copilot app's `__typename` itself was not independently re-verified live for this change (the implementing session had no live API access); the anchors above already establish the login pin via a live measurement, and the three-way split degrades safely if a future check finds a different `__typename` for Copilot — such feedback falls into `"human"` (still blocking, via the human path rather than the automated-fix path) rather than being silently treated as safe-to-merge. This assumption is exactly what the tracked live-drift check below exists to catch.
- **Fail-closed.** `fetch_feedback()` returns a `FeedbackSnapshot(ok, thread_info, shadow_comment_info, blocking_comment_info, failure_reason)`. `ok=False` on: a non-zero `gh` exit, `TimeoutExpired`, `FileNotFoundError`, an unparseable body, a non-empty GraphQL `errors` array, or a missing `data.repository.pullRequest`. GitHub's GraphQL surface can return `data` alongside a non-empty `errors` array (a partial-success response per the GraphQL spec) — verified possible; the fetch does not attempt to salvage that partial `data`, since a partially-failed fetch cannot distinguish "the thread list is complete" from "the thread list was silently truncated by the same error." `pr_merge._evaluate_checks` maps `ok=False` to `ChecksKind "pending"` (no new `ChecksKind` added) plus a `feedback_fetch_failed` audit row (`pr_merge_audit.jsonl`) carrying the failure reason — the poll loop keeps waiting under the existing `ALAN_PR_MERGE_TIMEOUT_S`/`MAX_POLLS` budget (A1) exactly like a pending check, converging to `timeout` → `await_human` on exhaustion rather than ever reaching `ready`. D28 adds a second fail-closed rule inside review-thread counting: a thread stops counting only on a positively read, non-collaborator permission; every other case keeps counting. This mirrors how `_pr_threads.list_unresolved_threads` already fails closed on the same class of failure on the separate, unmodified thread-listing path `implementation_fix` consumes (D11) — that one returns an empty tuple on failure, which is safe there because an empty unresolved-thread list is advisory input to a worker prompt, not a merge-blocking decision.

**Shadow-mode activation (safety-critical sequencing).** The gate was off for three months; repairing it changes behavior for every open PR simultaneously, and the two feedback categories have opposite risk profiles. Review threads are already effectively blocked by an existing forge-side branch rule, so repairing that category cannot newly block anything — it only converts an opaque timeout into an actionable route, and ships live with this change. (D28 later narrows which review threads count: only a collaborator's, or one alan cannot positively classify, still blocks.) Standalone comments and review summaries (`issue_comment`, `review_body`) are genuinely ungated today; every PR routinely carries several automated comments nobody can resolve, since no resolution mechanism exists for that category (`scripts/alan_copilot_resolve.py comment_ack` is a human-invoked acknowledgement, not an automated fix). Turning that category on immediately would stall the fleet indefinitely.

`_pr_feedback._SHADOW_CATEGORIES: frozenset[CommentSource] = frozenset({"issue_comment", "review_body"})` holds both back. `fetch_feedback` still computes and returns a full `shadow_comment_info` (all categories combined, ack-filtered) alongside a `blocking_comment_info` that excludes any source present in `_SHADOW_CATEGORIES` — currently always empty, since both sources are members. `pr_merge._record_shadow_feedback` writes one `shadow_feedback_recorded` audit row per poll (`pr_merge_audit.jsonl`: `thread_other_bot_unresolved`, `shadow_comment_total`/`_human`/`_copilot`/`_other_bot`) so the category is computed and recorded for observation. `pr_merge._classify_checks` and `_UNRESOLVED_CEILING` (100) only ever see `blocking_comment_info`, so today the ceiling and the `unresolved`/`copilot_unresolved` classification are thread-totals-only: a PR with 60 unresolved threads and 50 outstanding comments does not trip the ceiling.

This is deliberately not a config switch or environment variable: activating a category is a deletion of its member from `_SHADOW_CATEGORIES` — `blocking_comment_info` is derived generically per-source inside `fetch_feedback`, not hardcoded to "threads only," so removing a member alone re-populates it with no other code change.

**Tracked follow-up — flip `issue_comment`/`review_body` live.** Not scheduled by this change; a dependent follow-up PR, gated on evidence rather than a calendar date. Flip criterion: once this repair has run in production long enough to accumulate a representative sample of `shadow_feedback_recorded` rows in `~/.alan/logs/pr_merge_audit.jsonl`, the category may go live once the observed distribution shows (a) outstanding non-thread Copilot/human comments are rare enough on merge-ready PRs that gating on them would not stall a meaningful fraction of the fleet, and (b) an automated resolution path exists for what's found (today only a human-invoked ack does) — mirroring the precondition the review-thread category already met via `resolveReviewThread` (D3-ext) before it was safe to gate on. Until both hold, the category stays in `_SHADOW_CATEGORIES`.

**Live-drift detection.** Out of scope for this change, tracked separately: a scheduled, non-merge-blocking live check of the feedback query shape and the pinned Copilot identity against the real GitHub API, so a future schema change or an upstream rename of the Copilot reviewer's login is caught on a cadence instead of silently — the exact failure mode this defect stack was. Deliberately never a PR gate: a network-dependent check would itself be a weakened merge gate.

**Moves.** `CopilotThread`, `CopilotComment`, `ThreadInfo`, `CommentInfo`, `parse_thread_info`, `parse_comment_info`, and their private parsing helpers moved from `alan/teams/_pr_threads.py` to `alan/teams/_pr_feedback.py`, gaining the `GraphQLActorLogin`-typed identity parameter and the `other_bot_*` fields along the way. `_pr_threads.py` keeps `_thread_author_login`, `list_unresolved_threads`, and the rest of the working thread-listing path; `_REVIEW_THREADS_QUERY` and `_FEEDBACK_QUERY` now live in `alan/forge_gh.py`, behind the `ForgePort` operations (`docs/architecture/forge_port.md`). `pr_merge.py` deletes `_gh_feedback_raw`, `_gh_feedback_snapshot`, `_has_unresolved_human`, `_has_unresolved_copilot`; `_pr_feedback.has_unresolved_human`/`has_unresolved_copilot` replace the latter two. The parser tests moved from `tests/test_pr_branch_reviews.py` to the new `tests/test_teams_pr_feedback.py`; the two fail-open assertions this repair inverts, plus the comment-category blocking tests, live in `tests/test_teams_pr_merge.py`.

**Rationale.** A merge gate that reports itself healthy while never blocking is worse than no gate — it gives a false sense of enforcement. Fixing the query alone (defect 1) without also fixing the identity pin (defect 2) would have misclassified all live Copilot feedback as human, parking every affected PR on a blocking `await_human` question — a regression, not a fix. Fixing both without also fixing the fail-open default (defect 3) would have left the gate one flaky API response away from silently reverting to its three-month failure mode. All three had to land together, and the shadow-mode split is what makes landing them together safe: repairing review-thread blocking alone cannot newly stall anything (already forge-blocked), while comment/review-summary blocking is deferred until there's evidence it won't.
**Confidence:** 0.85 / reversibility: medium (query + type changes are structural; shadow-mode activation is a frozenset-member deletion, cheaply reversible either direction).

### D19 — Mechanical reconciliation actor for `DIRTY`: a working actor for the state neither detection point could previously act on

Before D19, a PR blocked solely by a real merge conflict (`mergeStateStatus=DIRTY`) had no actor that could clear it. Both places that see the conflicted state independently sent it toward `implementation_fix` — a team structurally incapable of resolving a branch conflict, since its worktree is a fresh checkout of the *existing* branch, not a rebase-with-conflict-resolution session — burning a full worker run for zero commits, then landing at `await_human` anyway. D19 gives `DIRTY` a real actor (`alan/teams/_pr_reconcile.reconcile_branch`, `merge_recovery._recover_dirty` — see `docs/architecture/merge_recovery.md`'s "Mechanical reconciliation for DIRTY") and corrects both detection points that previously misrouted it.

**Dispatcher-side route (was: `DIRTY` ⇒ `implementation_fix`).** `merge_recovery.attempt_mechanical_recovery` now classifies `DIRTY` first and dispatches straight to `_recover_dirty` instead of falling into the generic non-OK-readiness bucket the stale D13 prose above describes. A `RECONCILED` outcome recovers the gate exactly like `BEHIND_PLUS_TRANSIENT`/`TRANSIENT_FLAKE` already do: the dispatcher re-issues the `pr_merge` decision (deferred past the post-force-push CI-reset window via `_delay_for_ci_reset`, since `DIRTY` joined `CI_RESET_DELAY_CLASSES`), so the PR proceeds to merge on the next poll if nothing else blocks it. Any other outcome (`ALREADY_CURRENT`, `CONFLICT`, `RACED`, `TRANSPORT_FAILED`, or the budget already exhausted) is *not* recovered, and `DIRTY` now joins the `STALE_REVIEW`/`PRE_EXISTING_RED`/`TRANSIENT_FLAKE` tuple in `_pr_merge_remediation` — the same bounded-retry-then-`await_human` ladder those classes already use, capped at `loop_guard.REVISIT_CAP`. Once that cap is spent, the PR reaches `await_human` carrying `unblock_instruction(DIRTY, ...)`'s explicit recipe ("bring this branch up to date manually … then re-dispatch pr_merge") — before D19 this class of block reached a human with **no instruction line at all**; that is fixed here, in the same PR as the routing, not after it (see "boundaries and out of scope" below for why that coupling is load-bearing).

**Verification-side route (was: the verifier's own `DIRTY` detection also downgraded toward `implementation_fix`).** `_verification_gates._downgrade_result` now also sets `GateDowngradeResult.dirty` from `readiness.merge_state_status == "DIRTY"` — no new `gh` call, since `readiness` is already in scope for the downgrade. `VerificationTeam._build_verdict_handover` threads it into `suggestions_for_verdict(..., gate_dirty=downgrade.dirty)`: a `REQUEST_CHANGES` effective verdict with `gate_dirty=True` (and a resolvable `pr_number`) routes to `("pr_merge",)` instead of `("implementation_fix",)`, exactly mirroring the existing `gate_flaky_only` path — the two are independent booleans (`gate_dirty or gate_flaky_only`), not merged into one, so a PR that is simultaneously `DIRTY` and flaky-only-blocked still routes correctly. This closes the "earlier detection point downgrades and misroutes before the merge gate is ever reached" half of the fix; **fixing only the dispatcher-side merge gate reproduces the original failure exactly**, because the verifier's own downgrade fires first, on the very first `APPROVE` pass, before a conflicted PR's handover ever reaches the merge gate at all.

**Corrected actionability semantics.** Before D19, `_gate_actionability_lines` printed `GATE_ACTIONABLE: no` for a `DIRTY`-only block — a **false** signal, since a mechanical rebase genuinely can clear this class of block; the gate's own actionability line was the reason the original escalation read as a dead end. It now special-cases `dirty`: when no ordinary actionable check was resolved but the merge state is `DIRTY`, it emits `GATE_ACTIONABLE: yes` with **no** `GATE_ACTIONABLE_CHECKS:` line (the two-marker parse contract `parse_actionable_gate_checks` enforces means `implementation_fix` still sees zero fixable checks named — it cannot act on a bare conflict either, so it must not be told to). The practical effect is on `loop_guard._has_actionable_gate_block`, which reads the bare `GATE_ACTIONABLE_YES` marker: a verify↔fix pair blocked purely by `DIRTY` no longer looks like a stuck spiral to `detect_spiral`'s classification, because there genuinely is a working actor for it now (the reconciliation rung above) — parking it as a spiral would have been exactly as wrong as the old `GATE_ACTIONABLE: no` signal, just for a different consumer.

**Coupling is a hard requirement, not a sequencing preference.** Shipping the corrected `GATE_ACTIONABLE`/`gate_dirty` signal without the reconciliation actor behind it would have removed the pipeline's only loop exit for `DIRTY`: the old (truthful-by-accident) `GATE_ACTIONABLE: no` signal was what let a `DIRTY`-blocked PR terminate in a clean two-round human escalation instead of bouncing `verification ↔ implementation_fix ↔ pr_merge` forever with each hop believing the block was someone else's to fix. D19 lands the classification fix and the actor in the same unit of work for exactly this reason.

**Boundaries and out of scope.** No LLM-driven conflict-resolution tier exists or is planned here — an agent that resolves conflicted hunks itself was considered and explicitly cut (this failure occurs roughly once a month and has not occurred in the last month; a new team would carry a 100%-branch-coverage obligation and a third headless file-mutation surface, not justified at that rate). When mechanical reconciliation cannot succeed, it abandons the attempt cleanly (nothing is ever pushed on a `CONFLICT` outcome — the remote branch is byte-identical to before the attempt) and escalates to a human with the instruction above; that degradation is intentional. `pr_merge._MERGEABLE_MERGE_STATES` (`alan/teams/pr_merge.py`) still includes `DIRTY` in its pass-through set unchanged — this remains safe precisely *because* the merge gate now intercepts and (attempts to) clear `DIRTY` at routing time, before `pr_merge` is ever dispatched with a still-conflicted branch; see the "Ready confirmation probe" note below for the pinned-by-regression-test detail. The existing push-divergence reconciliation path (`_pr_push.push_fix_branch_with_reconcile`, D6 above) is deliberately not reused — it rebases onto `origin/<head>` (the branch's own drifted remote tip) for a different cause (a concurrent push mid-iteration) and hardcodes `push_reconciled`/`push_diverged_escalate` audit labels describing that cause; reusing it here would have reproduced exactly the misleading-signal class this build exists to eliminate. Overlap/collision advisories stay advisory — nothing here promotes them to blocking. Retry budget (`_MAX_RECONCILE_ATTEMPTS`, `_RECONCILE_LIFETIME_CAP`) is a fixed constant in `merge_recovery.py`, not an `ALAN_*` environment knob — a new env var would need registration in `tests/env_var_classification.py` and every state-isolation surface for no operational benefit. Per-PR reconcile-attempt state (`pr_<n>_reconcile_attempts.json`) resolves per repository via the existing `_engine_state_dir(forge)` namespacing, exactly like the sibling `pr_<n>_gate_reruns.json` — no repository-agnostic path collision when two repositories happen to share a PR number.
**Confidence:** 0.85 / reversibility: medium (new module + widened return-type threading; every branch covered by unit tests in `tests/test_pr_reconcile.py`, `tests/test_merge_recovery_dirty.py`, and the `tests/test_dispatcher_merge_gate_*.py` / `tests/test_teams_verification_*.py` siblings).

### D20 — The pull request body is an explicit, amendable worker deliverable, not a mechanical side effect

Before D20, the PR body was written exactly once — `implementation._open_pr` derived it from the opening worker's closing synthesis via `_pr_body.build_pr_body(synthesis)` — and nothing downstream could ever change it. `verification` reads the live PR body and can fail acceptance criteria on its contents, but no team dispatched after the PR is opened had any mechanism to amend what it said. A review whose only findings concerned the body's own text — wrong rationale, a stale decision record, a missing rollback note — was structurally unfixable by `implementation_fix`: there was no code change to make, and the team had no channel to speak to the forge. The workspace dead-ended at `non_actionable_feedback` → `await_human` even though the fix was one `gh api` call away.

**The convention: a fenced ` ```pr_body ` block, shared by both authoring teams.** `alan/teams/_pr_body.py::PR_BODY_BLOCK_INSTRUCTIONS` is a single instruction string appended to the *result* of `prompt_templates.render_prompt(...)` in both `implementation.render_system_prompt` and `implementation_fix.render_system_prompt` — one edit per team, covering the alan-default, generic-engine, and stored-template paths uniformly, since a stored prompt template can replace the composed base entirely and appending post-render is the only single-site change that guarantees every worker path is told. It tells the worker: this text becomes the *public* PR body, the permanent squash-merge record of *why* (load-bearing because this codebase's no-comments rule depends on that record existing) — a different artifact with a different audience from the `## Summary` / `## Decisions` handover synthesis the next internal stage reads. Omitting the block entirely is always safe and reproduces exactly today's derived-from-synthesis behavior; a worker is never required to supply one.

**Superseded (parsing).** The paragraph below described the original single-regex extractor. It has been replaced by a line lexer, `alan/teams/_pr_body_block.py`, because the regex's lazy `.*?` closed on the *first* same-length bare fence after the opener — including a nested block's own bare-opened delimiter — truncating the authored body at that point (observed on a second engine's repository). The regex-as-design claim below no longer holds; see the replacement paragraph that follows it.

`_pr_body.extract_authored_body(synthesis) -> str | None` now delegates to `_pr_body_block.extract_pr_body_block(synthesis)`, a stdlib-only line lexer. The opener match is identical to the legacy regex's opening half (`^(`{3,})pr_body[ \t]*\r?\n`, column 0, `re.MULTILINE`) — an `L`-backtick run — so widened-fence bodies (```` ````pr_body ````) extract exactly as before. Finding the *closer* is where the lexer differs: `scan_markdown` classifies every column-0 backtick-run line in the response as bare (nothing but backticks and trailing spaces/tabs) or info-string-opened (non-empty trailing text containing no backtick, the same CommonMark exclusion the legacy regex never modeled); `_pair_and_collect` then walks the lines in order and, for every info-string opener of length `M`, consumes the next bare line of length `>= M` as its closer — exactly CommonMark's own fence-closing rule — or, finding none, consumes every remaining line to end of response (an unclosed inner block runs to EOF, taking anything after it with it). Lines consumed this way never become candidates for the outer close, which is what stops a later host-parsed block (` ```yaml decisions.yaml `) from being swallowed regardless of where the true `pr_body` closer falls. What remains — bare lines the pairing step didn't consume — is filtered to exactly `L` backticks (CommonMark requires a closer at least as long as its opener, but the outer close must match the opener's own length precisely, same as the legacy regex's backreference), and `_choose` picks the *last* one that leaves an even number of same-length candidates strictly before it (0-indexed: the last even index). This is a balanced-pairing heuristic, not a formal proof: it was measured against 246 historical authored bodies and missed none. Wherever it agrees with the legacy first-match rule — no inner fences, a widened outer fence, or an inner block whose own delimiters are a different length than the outer's — the result is byte-identical, which is what keeps widening the outer fence a sound piece of worker-facing advice even though closing correctly no longer depends on it. When more than one candidate qualifies, `alan/teams/_pr_closing.py`'s `pr_body_publish` audit row records the body lengths the unchosen qualifying candidates would have produced (`alternative_lengths`), once per published body — a diagnostic trail, not a second decision. A block reduced to zero qualifying candidates after pairing (no closer survives) is `None`, exactly like an unterminated block today; `extract_authored_body` keeps its `str | None` signature, so the routing call site at `implementation_fix.py`'s extraction line is unchanged. `_pr_body.authored_body` no longer exists — its role (extract-or-fallback, then normalize) was folded into `alan/teams/_pr_closing.py::compose_pr_body`, the single body producer described in the new section below; `implementation._open_pr` and `implementation_fix._maybe_amend_body` both call it now, and neither calls `build_pr_body` directly.

**Amendment: host-only, wholesale, on ambient auth.** `_pr_body.amend_pr_body(pr_number, new_body, *, forge_target, task_id, team) -> BodyAmendResult` is the sole amendment path: it fetches the current live body first (`fetch_pr_body`, a plain `gh pr view --json body`, used as the audit's `previous_body` snapshot regardless of outcome), then issues `gh api -X PATCH /repos/{owner}/{name}/pulls/{pr_number}` with `{"body": new_body}` via the new shared helper `run_gh_api_json_input` (extracted from the review-post path below; it lives in `alan/forge_gh.py` since X2.7 PR15, having moved from `_pr_branch`) — **no `env=` override**, so the call runs under the same ambient `gh` auth every other host-side forge write already uses. This is the credential-boundary invariant this build is built around: workers gained the ability to *determine what the body says*, never a forge credential, a widened Bash allowlist, or a new command surface reachable from their own worktree. Every byte that reaches GitHub is written by the host process parsing a worker's *text*, exactly like `gh pr create --body <text>` already was.

A revision **replaces the body wholesale**, never patches it — the instructions tell the worker this explicitly, and `amend_pr_body` has no partial-update code path. The pre-amend body is preserved: `pr_body_amend_ok` in `impl_audit.jsonl` carries `previous_body` and `new_body` **untruncated** (siblings like `pr_view_failed` truncate at 500 chars; reconstructing a superseded body from the audit trail is an explicit acceptance criterion here, and the only consumers are line-wise JSONL readers with no truncation-sensitive UI). `BodyAmendResult(ok, previous_body, new_body, error=None)` is a frozen dataclass; a non-zero `gh api` return classifies through the same `_forge_errors.raise_for_infra` ladder every forge call uses — `rate_limited`/`transient` raise for dispatcher-level retry, everything else (domain-absent, auth, unknown) returns `ok=False` with `error` set rather than raising, so a permanently-rejected PATCH (PR closed mid-round, for instance) surfaces as a failed amendment instead of crashing the fix round.

**Ordering: amend after a successful push, or immediately when the round made no commits at all.** `implementation_fix._maybe_amend_body` gates on the actual push outcome: `None` when the worker supplied no block or there is no resolvable `prior_pr`; `None` when commits exist but `push_result.outcome` is neither `PUSHED` nor `RECONCILED` (a failed or diverged push means there is no reason to describe unlanded code); otherwise it proceeds — including the no-commits case, where `push_result.outcome` is `PUSH_FAILED` by construction (`_push_fix_branch` returns that sentinel when `commits` is empty) but the `commits and ...` guard short-circuits false, so a body-only round is never blocked by the not-pushed-because-nothing-to-push state. No CI check ever reads the PR body — only `verification` does, once the round returns — so there is no benefit to amending *before* the push lands, and real cost to amending a body that describes commits that never made it to the branch. Under `ALAN_IMPL_DRY_RUN`, `_maybe_amend_body` still exercises the full routing decision (`pr_body_amend_dry_run` audit row, a synthesized `BodyAmendResult(ok=True, previous_body=None, new_body=body)`) without ever calling `gh`, mirroring how the rest of the dry-run path fabricates success without a real forge write.

**Precedence over `non_actionable_feedback.yaml`.** `alan/teams/_fix_non_actionable.py::check_non_actionable` gained a keyword-only `authored_body: str | None` parameter and returns `None` (not non-actionable) the instant a body block is present, checked *before* the existing no-commits-and-a-reason branch — so a worker that emits both a `non_actionable_feedback.yaml` block (because it made no code change) and a `` ```pr_body `` block (because the fix *was* the body) is routed through the amendment path, not the human-escalation path. The precedence lives in the check function's own early return rather than in the call-site ordering, because `check_non_actionable` writes a `non_actionable` audit row when it fires — reordering the call site and ignoring its return value after the fact would still emit a spurious audit entry even though the round wasn't actually escalated.

**The park reads the pull request's blocking state before offering choices (alan#1644).** `check_non_actionable` also gained a required keyword-only `forge_target: ForgeTarget` (never defaulted: a default-engine target is the default-engine bug class), threaded from `implementation_fix._run_after_worker`. After the audit row is appended — so no forge call fires on a path that does not park — it calls `_blocking_state`: one non-waiting, non-mutating `_pr_ready.readiness_or_unavailable` read at the prior handover's `pr_number`, then `_pr_flake_ledger.evidenced_actionable_failing_checks` used as-is as the "is this red check really the diff's fault" predicate (quarantined checks and allowlisted flaky checks without survivor evidence at that head are excused; no new predicate, no change to the allowlist). A non-empty result contradicts the worker's "nothing here is actionable" claim: `_fix_escalation.non_actionable_question` then names the check(s) and `head_sha[:12]` (at most five names plus `and N more`) in the question text and offers `[fix option, RESOLVE_BY_HAND]` with `option_resolvers={fix option: "implementation_fix", RESOLVE_BY_HAND: "verification"}` and the fix option recommended. The fix option's text states the contradiction, so round *n+1*'s `"Recorded answer for question …: <option text>"` synthesis carries it forward with no new channel and a second attempt differs from the first even when no excerpt was available. The contradiction branch runs **before** `parse_gate_cause`: live head state beats parsed prose, and the gate-cause branch routes to `pr_merge` — the escape being contradicted. At the per-pull-request fix-cycle ceiling (`load_fix_cycle_state(...).count >= fix_cycle_budget(...)`, re-expressed inline because `alan.loop_guard` sits above `alan.teams` in the import layers; a parity test pins the two definitions together) the fix option is replaced by a ceiling option with no `implementation_fix` resolver, because dispatch would refuse, and `RESOLVE_BY_HAND` is recommended. `RESOLVE_BY_HAND` is the same constant in every composed answer space — `unblock_recipes._match_non_actionable` keys on `QUESTION_ID_PREFIX` plus that exact string, so the automated unblocker never stops recognising this class of park (its own `_usable_readiness` still declines on any red check, so it does not auto-answer the contradiction park). An unavailable read (`ReadinessUnavailable`), a prior with no pull request, or no unexcused red check leaves the canned `GENERIC_OPTIONS` / gate-cause pair exactly as before; the park is always minted and the read can never fail the give-up path. On an engine whose allowlist is empty every red required check contradicts a "flaky" claim; survivor evidence is written only by the pre-approval verifier lane, so after a merge-lane rerun the canned pair is conservatively kept.

**The merge team's timeout park reads the review record too (alan#1644).** `_pr_merge_no_signal.timeout_ctx` takes its single readiness snapshot; when it shows no failing checks, no pending checks and `review_decision == "CHANGES_REQUESTED"` (`settled_review_block`) it writes a state line naming the decision and `head_sha[:12]` (not "checks not settling") and sets `ctx["timeout_blocker"]`. `pr_merge._outcome_from_checks` carries that onto `PrMergeOutcome.timeout_blocker`, and `_await_human_handover` passes it to `_pr_merge_escalation.merge_block_options`, which returns `SETTLED_REVIEW_OPTIONS` (dismiss the stale change-request review, or address the requested changes and re-request review, then re-dispatch `pr_merge`) instead of `TIMEOUT_OPTIONS`. One snapshot serves both the text and the options, so they cannot name different heads; nothing matches on rendered reason prose. `blocked_no_signal` cannot collide: `is_blocked_without_signal` requires `review_decision != "CHANGES_REQUESTED"`.

The system does not read an empty commit list as failure here: the live body changed, and that is real, forward-moving work exactly as a code-bearing round is.

### D21 — Every concurrently-true merge blocker is reported; the failed-checks fix option routes to `implementation_fix`

Before D21, `classify_checks`'s short-circuit ladder (`alan/teams/_pr_merge_checks.py`) picked exactly one leading kind — `failed` before `unresolved_ceiling` before `unresolved` before `copilot_unresolved` — and the escalation reason named only that kind, even though the ladder's own inputs (thread/comment/Copilot counts, already unconditionally assembled by `_checks_ctx`) proved the other conditions true at the same moment. An operator who cleared the named check and retried the merge could hit a second, previously-silent block (unresolved threads) that had been true the whole time. Separately, every option on a merge-block `OpenQuestion` carried no `option_resolvers`, so `dispatch.resolver_team_for_answer`'s class-map fallback sent every answer — including the `failed`-kind option that already reads "inspect the logs, fix the underlying failure, and push a new commit" — to `pr_merge`, a team that cannot edit code. Issues #1323 and #1324.

**Relocation, forced by the zero-headroom pin.** `alan/teams/pr_merge.py` is pinned shrink-only in `tests/size_baseline.py` with no headroom at HEAD. The reason-composition surface (`checks_reason`/`checks_detail`/`unresolved_human_reason`, the `CHECKS_CLASS_LABEL`/`CHECKS_RECOVERY_RECIPE` tables, `UNRESOLVED_CEILING`), the four per-kind option tuples plus the Copilot-cap tables, and their selector all move verbatim into a new sibling, `alan/teams/_pr_merge_escalation.py`, alongside every other `_pr_merge_*` sibling already in `alan.teams` with no `[tool.importlinter]` entry (the layer is flat). **The classifier is untouched; the blocker set is a separate pure computation over the same context.** `_pr_merge_escalation.concurrent_blockers(kind, ctx) -> tuple[str, ...]` re-derives, independently for each condition, which of `failed` / `unresolved-ceiling` / `unresolved` / `copilot-unresolved` are true in the `ctx` dict `_checks_ctx` already assembles for every kind — the same counts `classify_checks` (unmodified — not reordered, not re-signatured, not extended) inspects on its way to picking one leading kind. **The `failed`-kind fix option routes to `implementation_fix`.** `merge_block_options(kind: str) -> tuple[list[str], str, dict[str, str]]` (re-signatured on a bare `kind: str` rather than the `PrMergeOutcome`-typed outcome the old `_merge_block_options` took, to avoid a `pr_merge → _pr_merge_escalation → pr_merge` import cycle) returns, for `kind == "failed"`, `{FAILED_OPTIONS[0]: "implementation_fix"}` as its third element — `FAILED_OPTIONS[0]` is the pre-existing "inspect the logs, fix the underlying failure, and push a new commit" option, already the recommended one; no option text changed and no third option was added. Every other kind (`no_pr`, `timeout`, `unresolved`, `copilot_unresolved`, `conflict`) returns an empty resolver map, so its options keep resolving through `dispatch._RESOLVER_BY_CLASS["merge_block_escalation"] = "pr_merge"` exactly as before. `_await_human_handover` (`pr_merge.py`) threads the third element straight onto `OpenQuestion.option_resolvers`; `dispatch.resolver_team_for_answer` already reads `option_resolvers` before falling back to the class map (no change needed there), and `routes/answer.py`'s existing `_validate_resolver` — roster membership plus `assert_team_dispatchable` — applies unbypassed, exactly as it already does for `_fix_escalation.py`'s and `_verification_review_post.py`'s pre-existing per-option resolvers.

### D22 — Copilot resolution moves host-side via a worker-emitted `copilot_resolution.yaml` block; comment acknowledgement is namespaced per forge target

Before D22, every worker-facing instruction for resolving a Copilot review thread or PR-level comment told the fix worker to invoke `uv run python scripts/alan_copilot_resolve.py` directly (`implementation_fix.py`'s system prompt and its `## Unresolved PR threads` block; `pr_merge.py`'s `_resolution_command`). That script imports `alan.teams.*`, which is not installed in a secondary engine's clone, and the fix worker's environment has every `registered_secret_env_names()` entry stripped (`alan/claude_cli.py`) and every `ALAN_*_ROOT` redirected to a throwaway sandbox — so on any non-default engine the invocation reliably fails (`FileNotFoundError`/`ImportError`), the thread stays unresolved, `pr_merge` re-detects it on the next poll, and the workspace stalls once `revisit_cap` (3) trips. Separately, `scripts/alan_copilot_resolve.py`'s `comment_ack` mode called `save_acked_comment_id(pr_number, database_id)` with no forge argument — always the default engine's namespace — while the reader (`_pr_feedback._filter_acked`) looks under the real engine's namespace, so an acknowledged comment on a secondary engine never reads as acknowledged and re-escalates forever. Issues #1388 and #1400.

**Resolution executes on the host, not the worker.** `alan/teams/_copilot_resolution_block.py` defines `CopilotResolutionRow` (pydantic, frozen) — `thread_id`/`database_id`/`mode: Literal["fix","acknowledge","comment_ack"]`/`body`, each mode requiring the fields it needs — and `parse_copilot_resolution_yaml`, which locates a ` ```yaml copilot_resolution.yaml ` fence (the `scenario_rebind.yaml` precedent) and rejects any row carrying a nested mapping/list value wholesale rather than partially honoring it. `alan/teams/_copilot_resolution.py` holds the executor: `apply(rows, *, pr_number, forge_target, head_sha, listed)` dispatches each row by mode and never raises out of a single row's failure (isolated into a `CopilotRefusal`). `implementation_fix._run_after_worker` calls `_copilot_resolution.maybe_resolve(workspace, handle, synthesis, prior_pr, forge_target, role=..., listed=threads)` unconditionally, ahead of both the non-actionable early return and the push-outcome check, and only when a `copilot_resolution.yaml` fence was actually attempted in the synthesis — parsing runs through `alan.block_correction.run_correction` in AUDIT-ONLY mode (`_block_correction_audit.record_unreachable_attempt`, the same wrapping `_fix_non_actionable.py`/`_verification_review_post.py` already use), so a malformed or absent block degrades to the pre-D22 re-escalation behavior rather than raising. A per-mode `allow_fix` filter then applies: `fix`-mode rows still require the branch push outcome to be `PUSHED` or `RECONCILED` (never on `DIVERGED_ESCALATE`, since resolving a thread whose fix never reached the remote would be a new correctness bug — the row asserts a code change that must actually be on the branch), while `acknowledge`/`comment_ack` rows run regardless of push outcome, since both are commit-free by design and would otherwise be silently dropped on a pure acknowledgement turn. The worker-facing instruction text moved out of `implementation_fix.py` entirely into `RESOLUTION_BLOCK_GUIDANCE` (a sibling constant, appended after `SCENARIOS_BLOCK_GUIDANCE`/`REBIND_BLOCK_GUIDANCE` in both the default and generic system prompts, and in the `## Unresolved PR threads` block) — no worker-facing site names `scripts/alan_copilot_resolve.py` any more. `pr_merge.py`'s `_resolution_command` likewise now emits a `copilot_resolution.yaml` row stub instead of a shell command.

**The listed set and the code-reviewer identity gate `fix`-mode resolution (2026-09).** `implementation_fix.run` fetches `_maybe_fetch_threads` exactly once per iteration — the same "unresolved threads on this PR" listing already shown to the worker in the `## Unresolved PR threads` prompt block — and threads that single tuple through both `_build_user_text` (for the prompt) and `_copilot_resolution.maybe_resolve(..., listed=threads)` (for enforcement); the listing is never re-read at apply time, so the worker's authority to resolve a thread can never grow between when the prompt was composed and when its `copilot_resolution.yaml` block is applied. Inside `_copilot_resolution.apply`, `_resolvable_thread_ids(listed)` derives a `frozenset[str]` of thread ids from `listed` whose `author_login` equals `_pr_feedback._COPILOT_GRAPHQL_LOGIN.login` — the one comparison site for the code-reviewer identity, reusing the existing constant rather than adding a second one. The check lives once, in `_apply_row`, applied uniformly regardless of which helper first computed it: a `fix` row whose `thread_id` is not in that set is refused `thread_not_listed` — covering both a thread the host never showed the worker and a thread it showed but that a human (not the code reviewer) authored, under one reason. An `acknowledge` row is never refused on this basis; it always attempts its reply (subject to the pre-existing ack cap and claim ledger), but the terminal `resolve_review_thread` call only fires when the thread is in the resolvable set — an acknowledgement on a human's conversation posts the reply and leaves the thread unresolved. This also closes the one re-entry hazard the identity check would otherwise open: `_apply_acknowledge_row`'s replay branch (a thread already claimed, replied, but not yet resolved) now gates its retry through `_reentry_resolve_ok`, which folds the pre-existing replied-and-not-resolved pair together with the same listed-set membership test — without that fold, an acknowledged human thread would retry `resolve_review_thread` forever on every subsequent iteration instead of falling through to `already_handled`. When the prompt-time listing came back empty (a failed `gh` read, or genuinely nothing unresolved), every `fix` row in that iteration is refused `thread_not_listed`; a `fix` row against an already-resolved thread in the listed set is a harmless idempotent no-op, since `resolve_review_thread` succeeds trivially on a thread GitHub already shows resolved. `comment_ack` rows are untouched by any of this — they were never review threads to begin with.

**Thread resolution takes no `ForgeTarget`; comment acknowledgement takes all of it.** A review thread's GraphQL node id is globally unique, so `fix`/`acknowledge` modes call `_pr_threads.resolve_review_thread(thread_id)` unchanged. `comment_ack` is repo-scoped by construction (no `resolveIssueComment` mutation exists), so it threads `forge_target` throughout: `post_pr_comment(pr_number, body, forge_target=...)` adds `--repo <owner>/<repo>` to the `gh pr comment` call, and `save_acked_comment_id`/`load_acked_comment_ids` (`_pr_state_paths.py`) write/read the forge-namespaced ledger the same way every other per-PR state file in that module already does (`_engine_state_dir(forge)`).

**Exactly-once acknowledgement: claim before post, never after.** `_pr_state_paths.acked_threads_path`/`claim_acked_thread(pr_number, thread_id, forge)` is a new, brand-new (no legacy-fallback) per-engine ledger. `acknowledge` mode claims the thread id before posting the reply; if the claim already exists (a resumed run replaying the same synthesis after a host restart), the reply is never re-posted. `comment_ack` reuses the pre-existing `acked_comments_path` ledger the same way — claim (`save_acked_comment_id`) before `post_pr_comment`, not after, inverting the original script's post-then-save order. The accepted failure mode on a crash between claim and post is a **missed** reply, never a **double** one; `fix` mode carries no claim and retries freely, since resolving an already-resolved thread is an idempotent no-op. A claimed thread does not always mean "fully done": `_pr_state_paths.replied_threads_path`/`mark_thread_replied`/`is_thread_replied` track, separately from the claim, whether the reply was actually confirmed posted, and `resolved_threads_path`/`mark_thread_resolved`/`is_thread_resolved` track whether `resolve_review_thread` actually succeeded. If a reply posts but the subsequent `resolve_review_thread` call fails, the thread is claimed and marked replied but not resolved; a replay of the same row detects "replied, not resolved", skips the post and the `ACK_CAP` check entirely, and retries only `resolve_review_thread` — safe because resolving an already-resolved thread is idempotent. Once that retry succeeds the thread is marked resolved too, so a further replay refuses as `already_handled` instead of issuing another GraphQL call for a thread already closed on GitHub. A claimed-but-not-replied thread (the ambiguous-post case) still refuses as `already_handled` with no retry of either call, since the reply may or may not have actually landed.

**The acknowledgement guardrail: `ACK_CAP = 3` per `(pr_number, head_sha)`, failing closed.** Moving resolution host-side makes "acknowledge, don't fix" free for the worker to choose, and under `revisit_cap=3` the cheapest path to zero unresolved threads is to acknowledge everything — a bug fix must not land as a quality-gate erosion. `_pr_state_paths.ack_budget_path`/`load_ack_budget`/`bump_ack_budget` track a `(head_sha, count, lifetime)` state identical in shape to the pre-existing `GateRerunState`: `count` resets on a new head sha (a genuine new review round earns a fresh budget), but when the head sha can't be resolved at all (`head_sha=None`) the check falls back to the ever-growing `lifetime` counter instead of a value that would never reset — failing closed rather than granting unlimited budget to an unreadable head. The cap is enforced before the claim, so an over-cap row never claims and can still be attempted (and refused again) on a later round. This ledger is deliberately separate from the pre-existing `.alan/copilot_escalation_count` cap, which counts *escalations*, not *acknowledgements* — unifying them would let an escalation silently consume acknowledgement budget or vice versa.

**Refusals are surfaced back to the worker.** Every resolution action and refusal appends to the existing `copilot_review_audit.jsonl` (`_pr_audit_log.append_copilot_audit`) with `repo`, `mode`, `resolved`/`acked`/`refused`, and — on a refusal — `reason` (`"ack_cap_exceeded"`, `"forge_call_failed"`, `"already_handled"`, or `"thread_not_listed"`). `_copilot_resolution_block.refused_resolutions_block(workspace, pr_number)` tail-reads that file, filters to `copilot_resolution_refused` rows matching both this PR number and this workspace's resolved forge slug (a bare PR-number filter would collide across two engines both hosting a "PR #42"), and renders the most recent 20 into `implementation_fix`'s next-iteration prompt unconditionally on every forge target — like `_current_scenarios_block`, which is likewise unconditional (see [acceptance_gate.md](acceptance_gate.md)), a refusal is exactly the information a non-default-engine worker needs to see. Each reason's rendered text comes from `_copilot_resolution_block._REFUSAL_MESSAGES`, a `str`-keyed dict covering all four reasons in worker-facing prose (an unmapped reason falls back to the raw slug); the audit log itself keeps storing the raw slug.

**The two human-facing recipes gained `--repo`, not a block-guidance rewrite.** `_pr_merge_escalation.py`'s `COPILOT_CAP_RECOVERY_RECIPE`/`COPILOT_OPTIONS` (surfaced only in the `await_human` escalation a human reads from the alan checkout, where the script genuinely resolves) keep naming `scripts/alan_copilot_resolve.py` — a human can still run it — but `copilot_cap_recovery_recipe`/`copilot_ack_option`/`copilot_options` now take an optional `repo_slug: str | None`, appending `--repo <owner>/<repo>` and a second line naming the new `pr_<n>_ack_budget.json` ledger alongside the pre-existing `.alan/copilot_escalation_count` when the engine is known. `checks_reason`'s general-purpose recipe (`_pr_merge_escalation.copilot_recovery_recipe`, reachable both by a human reading `PrMergeOutcome.reason` and by the worker via the Copilot-bounce handover's `full_synthesis`) instead points primarily at the `copilot_resolution.yaml` block, with the manual script as a qualified `--repo`-aware fallback — this is the site that previously carried the bare, unreachable script path with no qualifier at all. `pr_merge._outcome_from_checks` and `_await_human_handover`/`_copilot_handover_or_escalate` resolve `repo_slug` from the workspace's own `ForgeTarget` (`_pr_forge.forge_target_for_ws`), never from a hardcoded default.

**Confidence:** 0.85 / reversibility: high (the host-side executor is new and isolated; the worker-facing prompt text shrank; every branch — including the second-engine forge-target-threading path this defect actually reproduces on — is covered in `tests/test_copilot_resolution_block.py`, `tests/test_copilot_resolution.py`, `tests/test_teams_implementation_fix_copilot.py`, and the repointed tests in `tests/test_teams_pr_merge.py` / `tests/test_teams_pr_merge_escalation.py` / `tests/test_scripts_alan_copilot_resolve.py`).

- **A1 — Loop-guard cap on `pr_merge` polling.** Hard ceiling: `ALAN_PR_MERGE_TIMEOUT_S` seconds OR `ALAN_PR_MERGE_MAX_POLLS` iterations (whichever first). On exhaustion, emit a blocking `OpenQuestion("PR <n> not mergeable after <N> polls: <reason>")` → `await_human`. The Jaccard trigram stall detector ([loop_guard.md](loop_guard.md)) keys on `summary_for_downstream` not team name, so the `implementation_fix → verification → implementation_fix` cycle is guarded automatically; an explicit regression test goes in.
- **A2 — Calibration window closed 2026-05-20.** Initial production rollout ran `pr_merge` in dry-run with `ALAN_PR_MERGE_DRY_RUN=1` set in `deploy/ai.alan.plist`; gates D5/D10/A1/A3 + Copilot escalation cap accumulated enough evidence (≥10 tasks where gating agreed with human merge decisions) and the env var was removed from the plist. The variable is still honoured by `dry_run_enabled()` when exported locally (`export ALAN_PR_MERGE_DRY_RUN=1` before `python -m alan`) for prompt experimentation. Tests opt out of audit-log pollution via the sibling `ALAN_PR_MERGE_AUDIT_DISABLE=1` env var (`_audit()` early-return).
- **A3 — Layer-3 validator extended.** `_validate_layer3_decisions` ([handover.md](handover.md)) currently rejects empty `decisions` on forward to `implementation`/`verification`. Extend to `implementation_fix` too. `pr_merge`'s forward handover is exempt (it carries the merge SHA in `artifacts_produced`, not in `decisions`).
- **A4 — `auto_dispatch` does NOT override router precedence.** It pre-populates `to_team_suggestions` in the producer (`implementation_plan.run()`). `next_hop` still wins if set by a downstream agent. No special-case in `_pick_forward_target`.
- **A5 — Per-workspace serialization is the concurrency interlock.** The existing `_CLAIM_SQL` guard ([dispatcher_concurrency.md](dispatcher_concurrency.md)) prevents `implementation` and `implementation_fix` from running concurrently on the same workspace. The ADR commits to NOT loosening this for "parallel fix on different files" — that would re-introduce branch-divergence races. Different workspaces still parallelize up to `ALAN_DISPATCHER_CONCURRENCY`.
- **A6 — `SKIP=mypy,tsc,eslint` inherits on `implementation_fix` worktree commits.** Same pre-commit-hook discipline as `implementation`. The shared `_pr_branch.py` helper holds the env-var setup; both teams inherit by importing.
- **A7 — Loop-guard exhaustion on `implementation_fix` surfaces as `Status.ESCALATED`, not `AWAITING_INPUT`.** Distinguishes "I tried and failed" from "I need a human decision to proceed." **Required schema change** (the only one in Pattern B): `alan/workspace.py` currently has `Status` enum members `ACTIVE | AWAITING_INPUT | COMPLETED | ARCHIVED` and `_LEGACY_STATUS_HEAL = {"failed", "escalated", "plan_needs_revision"}` which silently heals `"escalated"` to `AWAITING_INPUT`. The Pattern B PR must (1) add `ESCALATED = "escalated"` to the `Status` enum and (2) remove `"escalated"` from `_LEGACY_STATUS_HEAL`. Historical `meta.json` files containing `"escalated"` will then load as `ESCALATED` instead of being healed — a deliberate behavior change, not a migration loss. No data rewrite is needed.
- **A8 — Module-level `_MERGE_LOCK` in `pr_merge.py` serializes concurrent `gh pr merge` calls.** Under N-worker concurrency (`ALAN_DISPATCHER_CONCURRENCY=6`) two workers can reach `_execute_merge` simultaneously for different workspaces. If Worker A merges first, Worker B's PR becomes BEHIND before its `gh pr merge` runs. The lock forces serialization; after acquiring, `_execute_merge` calls `_handle_behind_recheck` (which calls `check_pr_merge_readiness`) before issuing the subprocess. If `mergeStateStatus == "BEHIND"`, it calls `update_pr_branch_outcome`, counts only `UPDATED` as a successful update, and returns an error outcome without attempting the merge — the dispatcher's reactive `_enforce_pr_merge_gate` handles the re-merge once CI passes on the rebased branch. Audit action: `merge_deferred_behind` (with `update_ok` field) in `merge_gate_audit.jsonl`.
- **A9 — Proactive rebase fan-out after a successful merge, widened to cover parked workspaces (2026-09-06).** When `_run_team` observes a `pr_merge` team producing a `terminal` handover (successful merge), the dispatcher calls `alan/proactive_rebase.maybe_trigger_proactive_rebase` in a daemon thread. This fires only in the wake of a fleet merge — a fully-parked fleet with no merge in flight triggers nothing at all; a periodic or park-time trigger is out of scope. **Eligibility is an allowlist, not an ACTIVE-only test.** `_ws_eligible` accepts any workspace whose status is in `_ELIGIBLE_STATUSES` (`ACTIVE`, `AWAITING_INPUT`, `ESCALATED`, `PAUSED`, `PARTIAL`) rather than only `ACTIVE` — a parked workspace's branch is frozen while the base keeps moving, so leaving it out of the fan-out slowly converts every park into a merge conflict (the 2026-09-06 incident: five of six open PRs conflicted simultaneously, four of them parked for reasons unrelated to merge conflicts and having acquired the conflict while parked). Being an allowlist rather than an equality check means a future status is excluded by default rather than silently swept in. The second guard is untouched: a workspace still carrying queued or running work (`queue.has_active_work`) is excluded regardless of status — this is what keeps a `deploy_wait`-parked workspace (which sits as a pending job) out of the fan-out; the criterion is not an absolute about "any parked workspace." **Ordering: active-before-parked, each tier oldest-first.** The candidate pool stays capped at `ALAN_PROACTIVE_REBASE_CAP` (default 5), so once parks became eligible, sorting purely by `created_at` would let a handful of long-lived parks sit permanently at the head of the list and starve every actively-worked branch out of the fan-out — worse than the conflict-rot bug being fixed. `_collect_targets` sorts on `(0 if ACTIVE else 1, created_at)`: every ACTIVE workspace is considered before any parked one, and each tier is still oldest-first internally. A parked workspace can never displace an actively-worked one from the capped fan-out; it can only take a slot left over once every ACTIVE candidate already has one. **Attempt and classify; never pre-check merge state.** The fan-out never reads a PR's `mergeStateStatus`/`mergeable` field to decide whether to act on it — a batch PR listing routinely reports that state as unknown rather than computed, and gating on "behind and not conflicted" would refuse to act on exactly that value, reintroducing the rot under a new name. Instead each candidate's `gh pr update-branch` attempt is classified via `_pr_branch.update_pr_branch_outcome` into `BranchUpdateOutcome.UPDATED` / `CONFLICT` / `FAILED`, recorded respectively as `proactive_rebase_ok` / `proactive_rebase_conflict` / `proactive_rebase_failed` rows in `merge_gate_audit.jsonl` — each row also carries `repo` (the resolved `ForgeTarget.repo.slug`) alongside the pre-existing `triggered_by_merge_of` (the merged PR number that triggered the fan-out). A conflicted branch is left alone because the forge refused the update, never because the state was predicted in advance; `proactive_rebase_conflict` is its own action distinct from `proactive_rebase_failed` so several rows from one base movement are greppable under a shared cause. **Per-workspace forge resolution.** Every candidate resolves its own `ForgeTarget` via `_pr_forge.forge_target_for_ws(ws)` at collection time (bundled into a frozen `_RebaseTarget` alongside its `task_id`/`pr_number`), and both the branch-update call and the `_record_system_head` marker write use that resolved target — previously both defaulted unconditionally to the default engine's repository regardless of which repository the workspace's PR actually lived in, silently applying a secondary-repository workspace's PR number against the wrong repository; secondary-repository workspaces park heavily, so widening eligibility without this fix would have made that defect worse. **Closed pull requests are skipped without spending a cap slot.** `_target_for` calls the fail-open `_pr_branch.pr_is_open(pr_number, task_id, forge_target=...)` (a bare `gh pr view --json state` read — no merge-state fields, no audit write) after resolving the latest `pr_number` from handover history; a definite `False` (closed or merged) drops the candidate before it can consume a slot in the capped fan-out, since parks are exactly where closed-as-superseded pull requests accumulate. Any failure to determine the state — non-zero exit, empty output, a raised exception — reads as `None` and the candidate is attempted anyway (fail-open), consistent with never pre-checking merge state to decide whether to *act*; this check only ever skips a pull request that is structurally gone. **The workspace record is untouched; the pull request genuinely moves.** No status change, no job enqueued, no question answered, no resumption — `_do_fan_out` never touches `Workspace` or `Meta`. But bringing a branch forward pushes a real commit onto it: a new head, a full CI re-run, a possibly-dismissed prior approval, and previously recorded readiness that now reads pending — up to a capful of these per merge, on a machine already contended for test capacity. This cost is accepted deliberately, not minimized away. Source: `alan/proactive_rebase.py`; wired via `Dispatcher._maybe_trigger_proactive_rebase`. `alan/collision.py` still calls `_pr_branch` unthreaded by forge target — out of scope here.

## `implementation_fix` charter

**Role:** address `REQUEST_CHANGES` review on an existing PR.
**Type:** bespoke (mirrors `implementation`), **not** a `SingleAgentTeam`.
**Model:** `sonnet`.
**Permission mode:** `acceptEdits`.
**Allowed tools:** identical to `implementation._ALLOWED_TOOLS`.
**Worktree strategy:** `implementation_worktree(task_id, inv_id, existing_branch=<resolved>)`. The branch is resolved from `prior.pr_number` via `_pr_branch.resolve_existing_branch` (extracted from current `implementation._resolve_existing_branch`).
**System prompt outline:**
- "You fix issues raised by code review. The PR is open; the branch is checked out."
- "Read the full review at the `ArtifactRef` path. Address every finding."
- "Commit each finding as its own commit with a one-line subject. Do NOT amend prior commits."
- Forbidden actions: same baseline as `implementation` (`don't push`, `don't open a PR`, `don't pip install -e .`, `don't modify files outside the plan's scope`).
**Push:** `_pr_push.push_fix_branch_with_reconcile(worktree, branch, task_id, base_sha)` (D6) — at the time this ADR was written this was described as `push_branch(branch, force_with_lease=True)` on `_pr_branch`, a signature `push_branch` never had; the H5.1 shrink program's push-reconcile-cluster move relocated the cluster to `_pr_push`, where the force-with-lease behavior lives on `push_fix_branch_with_reconcile` (which attempts `--force-with-lease` and falls back to a fetch/rebase/repush reconcile), so that no longer holds.
**Handover-builder list (Layer 3):**
- `decisions` — one per commit (mirrors `implementation`).
- `artifacts_produced` — commit SHA + subject.
- `pr_number` — propagated unchanged from `prior.pr_number`.
- `next_hop` — unset; `to_team_suggestions=("verification",)`.

## `pr_merge` charter

**Role:** gate-check CI + review threads, then merge or escalate.
**Type:** Python-only `Team`. No `claude` subprocess, no worktree, no `model` field consumed.
**`PendingTaskSpec.model`:** uses the `"none"` sentinel — the same no-LLM-node convention `principal_proxy.py` established before its 2026-07-13 removal; `triage.py`'s `ROLE_SPECS` is the current example.
**State table (`pr_merge.run()`):**

| State | Trigger | Action |
|---|---|---|
| `no_pr` | `prior.pr_number is None` | emit blocking `OpenQuestion("verification approved without a PR number — manual review needed")` → `await_human` |
| `already_merged` | `gh pr view <n> --json state -q .state` == `"MERGED"` | emit **terminal** handover; `decisions=[]`, `artifacts_produced=[ArtifactRef(path=f"https://github.com/<owner>/<repo>/pull/<n>", description=f"PR #<n> already merged")]` |
| `closed` | state == `"CLOSED"` | emit escalation handover (`Status.ESCALATED`) |
| `pending` | `gh pr checks <n>` reports any `PENDING`/`QUEUED` | sleep `ALAN_PR_MERGE_POLL_INTERVAL_S`, re-poll. The advisory-tolerance readiness fetch (`_pr_merge_checks._tolerated_kind`, ~100 GraphQL points, see `merge_recovery.md`) is attempted on a pending poll only when it could possibly apply — `forge_target.authoritative_checks` is non-empty and none of them is itself pending in the local rollup (`_advisory_floor_possible`); otherwise the poll costs one `gh pr checks` call and nothing more |
| `failed` | `gh pr checks <n>` reports any `FAILURE`/`ERROR` | emit blocking `OpenQuestion("PR #<n> failed checks: <names>")` → `await_human`, reason front-loaded with every other concurrently-true blocker, fix option routed to `implementation_fix` via `option_resolvers` (D21) |
| `unresolved` | human-authored unresolved threads > 0 (and total ≤ 100) | emit blocking `OpenQuestion("PR #<n> has <k> unresolved review threads")` → `await_human` |
| `copilot_unresolved` | Copilot-bot threads unresolved, no human threads (D3-ext) | emit forward handover to `implementation_fix` with thread bodies; or escalation if cap reached |
| `ready` | all checks green AND threads resolved AND `_confirm_ready_kind` probe passes | `gh pr merge <n> --squash --delete-branch`; emit **terminal** handover |
| `timeout` | total elapsed > `ALAN_PR_MERGE_TIMEOUT_S` OR polls > `ALAN_PR_MERGE_MAX_POLLS` (A1) | emit blocking `OpenQuestion("PR #<n> not mergeable after <N>s: <last_state>")` → `await_human` |
| `error` | any subprocess raises non-`MERGED`-state error | log + emit escalation |

The `gh pr checks`, `gh pr merge` and readiness `gh pr view --json <fields>` commands in this ladder are what `GhForge` runs, not commands `pr_merge.py` or `_pr_ready.py` build: they reach the forge through `active_forge().read_checks` / `merge_pr` / `read_pr` (X2.3 PR3, `docs/architecture/forge_port.md`). The PR-state read (`gh pr view --json state,mergeStateStatus`), the review-thread GraphQL read, the flake-guard head read and the failing-e2e read stay on direct `gh` calls until X2.7.

Two 2026-08-04 race guards sit inside this ladder (incident: rerun reset window read as all-green → policy-refused merge → 3-second terminal escalation):
- **Ready confirmation probe** — an all-green rollup verdict is second-sourced against `check_pr_merge_readiness()` (`alan/teams/_pr_merge_checks.py::confirm_ready_kind`, relocated out of `pr_merge.py`): only `{CLEAN, HAS_HOOKS, UNSTABLE, BEHIND, DIRTY}` proceed to merge; `BLOCKED` (a required context missing from the rollup — the reset-window shape), `UNKNOWN`, empty, or a failed probe read all classify `pending`, falling into the existing A1 budget. As of the 2026-09-05 no-check-results fix, an empty rollup now classifies `pending` **regardless of merge state** — `confirm_ready_kind` checks `_pr_ready.results_absent(readiness)` before ever consulting `merge_state_status`, so a `CLEAN`-but-empty-rollup commit (checks not yet created) is demoted the same way a `BLOCKED` one is; a mergeable state with a missing/empty `head_sha` (a malformed `headRefOid`) is likewise demoted to `pending` by `_readiness_confirms_mergeable_head` rather than confirming `"ready"` with nothing to compare against (corrected 2026-09-05, Copilot review on PR #1322). On success, `confirm_ready_kind` returns the measured, non-empty `head_sha` alongside the `"ready"` kind, threaded by `pr_merge.py` through `_merge_or_dry_run`/`_execute_merge` as `expected_head_sha`; inside `_MERGE_LOCK`, `_handle_behind_recheck` re-fetches readiness and — for any merge state other than `BEHIND` — requires `_pr_merge_checks.recheck_confirms_target` to hold (the recheck itself succeeded, its results are not absent, and its observed `head_sha` equals a non-empty `expected_head_sha`) before letting `_execute_merge` proceed to `gh pr merge`. Failing that check no longer raises a terminal `merge_deferred_head_moved` error (corrected 2026-09-05): it audits the mismatch and returns `(False, None)`, which `_execute_merge` propagates as `None` so `_poll_until_done` simply re-polls — a concurrent push moving or emptying the commit is not this workspace's failure. `gh pr merge` itself now carries `--match-head-commit <expected_head_sha>`, gh's own atomic, server-side version of the same guard; a refusal on that flag (`_is_head_mismatch_refusal`, matched on "head branch was modified") is likewise audited and retried, never escalated. BEHIND/DIRTY pass through so `_handle_behind_recheck` and conflict handling keep their semantics. `DIRTY`'s presence in this pass-through set (`_MERGEABLE_MERGE_STATES`) is safe without any change here because the merge gate (D19) already intercepts and attempts to clear `DIRTY` at routing time, *before* `pr_merge` is ever dispatched with a still-conflicted branch — a regression test pins this interception rather than narrowing the set itself.
- **Policy-refusal re-poll** — `gh pr merge` rc≠0 whose stderr contains "base branch policy prohibits the merge" (case-insensitive) audits a `merge_policy_hold` row and re-enters the poll loop instead of mapping to `error`; repeated refusals converge to `timeout` → `await_human`. All other rc≠0 stderr keeps the `error` → escalation path (including the expired-token credential recipe).

**Absence is not readiness (2026-09-05).** `PrReadiness` now carries `head_sha` (from `headRefOid`, appended to the shared `_READINESS_FIELDS` query so every lane gets it in the existing round-trip) and `check_count` (the raw `statusCheckRollup` entry count, before bucketing — the discriminator that keeps a `SKIPPED`/`NEUTRAL`-only rollup from misreading as absent). `_pr_ready.results_absent(readiness)` (which takes only a real `PrReadiness`) is `check_count == 0 AND` all three bucketed check-name tuples empty; when true, `_build_failed_reasons` appends `"no check results"` to `failed_reasons` (the merge lane's reason builder only — `_build_verifier_blocker_reasons` is unchanged, so verifier approval semantics do not move) and `_pr_ready._audit_readiness` writes `head_sha`/`check_count` into every `pr_readiness_check` audit row, making this incident class reconstructable directly from the audit trail. See `docs/architecture/merge_recovery.md`'s `no_check_results` row for how this reaches the dispatcher's merge gate.

**Env vars (all defaulted):**
- `ALAN_PR_MERGE_TIMEOUT_S` — default `600` (10 min).
- `ALAN_PR_MERGE_POLL_INTERVAL_S` — default `30`.
- `ALAN_PR_MERGE_MAX_POLLS` — default `20`.
- `ALAN_PR_MERGE_DRY_RUN` — default unset (calibration window closed); when `1`/`true`/`yes`/`on`, logs the `gh pr merge` call without executing and still emits the success handover (A2).
- `ALAN_PR_MERGE_AUDIT_DISABLE` — default unset; when `1`/`true`/`yes`/`on`, `_audit()` early-returns so test fixtures (`task_id="pr-merge-task"`) do not pollute `~/.alan/logs/pr_merge_audit.jsonl`.

**Idempotency:** every entry point through `run()` starts with the `already_merged` check (D5). `supports_resume=False`; if the dispatcher reconciler re-runs the team, the `MERGED` check absorbs it.

**Audit log:** `~/.alan/logs/pr_merge_audit.jsonl` (file mode `0o600`). Routing decisions (action `copilot_thread_routed` for review threads, `comment_unresolved` for PR-level Copilot issue comments / review bodies) are written here alongside other `pr_merge` events. In addition, each invocation on the Copilot-bounce or escalation-cap path writes `<workspace>/.alan/copilot_audit_<inv_id>.jsonl` (file mode `0o600`) and attaches it as a second `ArtifactRef` on the Copilot-bounce handover (alongside the `.md` threads file), or as the sole `ArtifactRef` on the escalation-cap handover; this per-invocation artifact is suppressed by `ALAN_PR_MERGE_AUDIT_DISABLE=1` (same switch as the global log). Resolution records — action `fix` / `acknowledge` for review threads, `comment_ack` for non-thread comments, all written by `scripts/alan_copilot_resolve.py` — go to `~/.alan/logs/copilot_review_audit.jsonl`; `pr_merge` does not write to this file. Per-PR acked comment IDs are persisted to `~/.alan/state/pr_<n>_acked_comments.json` (override root with `ALAN_STATE_ROOT`); `pr_merge`'s classifier consults this file every poll to avoid re-blocking on a Copilot comment that has been acked.

**Operationally.** `pr_merge` is a normal dispatcher job, not a separate polling daemon. It uses the same enqueue/run/handover pipeline as every other team — the only difference from `verification` etc. is that `run()` does its work in Python (a synchronous `gh` poll loop) instead of streaming a `claude` subprocess.

- **One DAG node per invocation.** Each `pr_merge` run creates an `inv_NNN/` directory and a `workflow.yaml`; the frontend renders it as one node in the task-detail DAG, identical in shape to a `verification` node. Internal poll cycles are hidden inside that single invocation — they are not surfaced as separate nodes (kept opaque deliberately; if per-poll visibility becomes desirable later, the team can write each poll as an `io.alan.SubprocessStep` row in its `workflow.yaml`'s `tasks[]` without changing the dispatcher contract).
- **Terminal routing on success.** On success, `pr_merge.run()` returns a `Handover` with `handover_type="terminal"`. The router's early-return at step 2 of `select_next_team` fires `kind="done"` immediately, completing the workspace without routing to any downstream team (including `retrospective`). `retrospective` remains manually dispatchable via `POST /api/workspaces/.../dispatch`. No team — including this one — ever calls the dispatch API from inside `run()`.
- **Failure surfaces as `await_human` in the task detail.** Timeout, failed checks, unresolved threads, or `> 100` threads each emit a `Handover` whose `open_questions` contains a blocking `OpenQuestion(resolver_role="human", text="PR #<n>: <reason>")`. The router's blocking-question branch fires before the forward branch, returns `RouterDecision(kind="await_human")`, and the dispatcher writes `Status.AWAITING_INPUT`. The frontend then shows the open-question text inline plus the handover's `summary_for_downstream` (which carries the structured failure: check names, thread count, last-seen state). The UX shape is identical to today's `verification → APPROVE → await_human` flow, just with a richer failure reason. The `error` state (subprocess raises) emits an escalation handover instead → `Status.ESCALATED`.
- **Worker-slot cost.** A mid-poll `pr_merge` holds one of the `ALAN_DISPATCHER_CONCURRENCY` worker threads (default 6) for up to `ALAN_PR_MERGE_TIMEOUT_S` seconds (default 600). Per-workspace serialization already prevents deadlock; cross-workspace, six simultaneous merges still leave headroom on the default sizing. If saturation becomes real, the fix order is: (1) raise `ALAN_DISPATCHER_CONCURRENCY`, (2) lower `ALAN_PR_MERGE_TIMEOUT_S`, (3) refactor to one-poll-per-invocation with the dispatcher re-enqueuing. (3) is a bigger architectural shift and is **not** pre-emptive — left as a documented escape hatch.

## Ownership gate (CODEOWNERS self-merge refusal)

Before `pr_merge` self-merges a PR, `alan/teams/_pr_merge_checks.py::_apply_ownership_gate` can
turn a `"ready"` verdict into a refusal on an opted-in engine whose changed files touch an owned
path. Issue **DejvMatikar/alan#1686**.

**Placement.** The gate sits at the single exit of `resolve_checks_kind`, wrapping both of its
return points: the tolerant path's early return (`_tolerated_kind`'s "ready" result, which bypasses
`confirm_ready_kind` entirely) and the confirmed path's return (`confirm_ready_kind`'s result). It
deliberately does **not** sit inside `confirm_ready_kind` itself — that function is unreachable from
the tolerant path, so a guard placed there would fail open whenever advisory tolerance produced the
"ready" verdict. `_apply_ownership_gate` no-ops unless the incoming kind is `"ready"`; on the allow
path it returns the input tuple **unchanged, by identity** — the third element (a `PrReadiness` the
tolerant path attaches for `audit_advisory_tolerated`) survives untouched, so an unowned PR merged
via the tolerant route still gets its advisory-tolerated audit row.

**The read is base-branch, decision-time, forge-only.** The gate reads the PR's `baseRefName` via
`active_forge().read_pr` at the moment `resolve_checks_kind` runs — not the engine's configured
default branch, and not a value captured when the workspace was dispatched — then reads
`.github/CODEOWNERS` via `active_forge().repo_file(..., ref=base_ref)`, the forge's contents API
pinned to that ref. It is never read from the PR's own head or from the worker's local checkout:
a worker's clone is not guaranteed fresh, and reading the head would let a PR's own diff decide
whether it needs review — the same self-authorship hole this feature closes, one level up.

**The opt-in is presence-independent and profile-driven.** The install profile's optional
`codeowners_repos` (`alan.default_profile.DefaultProfile`; `docs/architecture/engine_config.md`'s
profile schema) is a frozenset of `owner/repo` slugs, validated with the profile's owner and
repository name patterns and stored casefolded, empty by default. `_ownership_gate_enforced` reads
`default_profile.resolved().profile.codeowners_repos` through the module attribute at call time and
compares it against `forge_target.repo.slug.casefold()`; with none named, every repository passes
through and the gate makes no forge call. There is no env var or API surface — the set is install
data, so no repository name is a literal in `alan/`. Critically, the rule does **not** key off
whether `.github/CODEOWNERS` exists: alan's own repository ships one whose first rule
(`* @DejvMatikar`) owns every path in the tree, and alan's posture is `autonomous` (at or above
`self_merge`). Presence-keying would refuse every alan PR, including this feature's own follow-ups.
`test_ownership_gate_passes_every_repo_through_when_the_profile_names_none` pins the empty default.

**Supported syntax, and the "owned iff any rule matches" invariant.** The matcher implements only
the two forms a connected engine's CODEOWNERS file's rules use: an anchored path/directory (a pattern with a leading or
interior `/`, which owns that exact path and every descendant) and an unanchored single segment
(matches a same-named file at any depth). CODEOWNERS has no negation, so "owned" is simply "any
parsed rule matches" — `_path_is_owned` is `or`-ed across every rule and every changed path. Any
other glyph — `*`, `?`, `[`, `]`, `!`, a backslash, an inline `#` comment, or an owner-less line — is
refused **loudly**: `_parse_rule` raises `UnsupportedCodeownersSyntax`, which `_match_verdict` turns
into the distinct `"codeowners_unsupported"` kind rather than either treating the line as owning
nothing (a silent permit) or letting the exception escape `pr_merge` (a crash). This is why alan's
own `* @DejvMatikar` rule is safe even under a mistaken opt-in: `*` is an unsupported glyph, so it
raises loudly instead of silently matching every file.

**The three-way failure split.** A missing base ref, a missing CODEOWNERS file (`FileRead.outcome
== "absent"`), undecodable contents, or `changed_files` returning `None` all refuse immediately as
`"codeowners_blocked"` — fail-closed, no retry. A raised transport fault or a `stderr` that
`_forge_errors.classify_forge_failure` calls `"transient"` retries with a fixed `time.sleep` between
attempts (`_OWNERSHIP_READ_ATTEMPTS = 3`, `_OWNERSHIP_RETRY_INTERVAL_S = 5.0`, module constants —
deliberately not `ALAN_*` env vars, to stay out of the env-var classification surface) and only then
refuses. Every other failure class refuses on the first attempt. Keeping these three distinct means
a transient forge blip does not stall every unrelated PR on the engine for the full retry budget,
while a genuinely missing file or hard failure never silently permits a merge either.

**The deliberate fail-closed inversion.** `alan/teams/_pr_freshness.py::is_measured_baseline_stale`
is this repository's house pattern for "a forge read failed, so don't act on it" — it returns
`False` (don't treat the baseline as stale) on every failure path. The ownership gate inverts that on
purpose: every failure path here returns `"codeowners_blocked"` (refuse), not "allow through." A
future reader tempted to "fix" this into a fail-open read to match the neighbor would reopen the
exact self-merge hole this feature exists to close.

**Two kinds, one no-re-dispatch recipe family.** `"codeowners_blocked"` and
`"codeowners_unsupported"` are new `ChecksKind`/`OutcomeKind` members. `_pr_merge_escalation.py`
gives each a kebab-case `CHECKS_CLASS_LABEL` (`codeowners-blocked` / `codeowners-unsupported`), a
pinned `checks_detail` string naming file ownership and `.github/CODEOWNERS` explicitly (so an
operator can tell what blocked the merge without depending on a term surviving future prose edits),
and a `CHECKS_RECOVERY_RECIPE` / `merge_block_options` entry drawn from `CODEOWNERS_OPTIONS` — a
human reviews and merges by hand, or the owner declines and the PR is closed. Both kinds are the
sibling-convention's one deliberate exception: every other `merge_block_options` recipe tells the
human to "re-dispatch pr_merge" once resolved; these two never do, because re-dispatching just re-hits
the same ownership block (nothing about a human's out-of-band GitHub review changes what the gate
reads). `OWNERSHIP_KINDS: frozenset[str]` names both for callers that need to recognize the pair
without hardcoding the strings twice.

**The unblocker exclusion.** `alan/unblock_recipes.py::_match_green_not_merging` — the recipe that
re-dispatches `pr_merge` for a parked `pr-merge-*` blocker once the PR reads green — explicitly
declines when the blocker's kind is in `OWNERSHIP_KINDS`. Without this, the 60s unblocker sweep would
re-dispatch `pr_merge` every cycle, which re-evaluates the same CODEOWNERS state and re-parks
immediately: an endless refuse/park spin that never reaches the human the refusal was meant to route
to.

**Reused mechanics, no new frontend.** The refusal renders through the existing blocking
`OpenQuestion` → `await_human` path (`_await_human_handover`), so the `OpenQuestionItem` UI component
already renders it with no frontend change. `merge_block_options` returns an empty resolver map for
both kinds, so neither option auto-resolves back into a dispatch — a human must act.

**Accepted limits.** The forge-side "require review from code owners" branch-protection setting
stays off; this is a fleet-side gate, not a forge-side one. A direct push to the base branch, or a
pull request not opened by the fleet, is not covered — the gate only runs inside `pr_merge`'s own
merge decision.

## Verification routing

`alan/teams/verification.py` changes:

```python
def suggestions_for_verdict(
    judge_output: str, pr_number: int | None, *, gate_flaky_only: bool = False
) -> tuple[str, ...]:
    verdict = effective_verdict(judge_output)
    if verdict == "REQUEST_CHANGES":
        gate_owned = any((gate_dirty, gate_flaky_only, gate_non_actionable))
        if gate_owned and pr_number is not None:
            return ("pr_merge",)
        return ("implementation_fix",)
    if verdict == "APPROVE" and pr_number is not None:
        return ("pr_merge",)
    return ()  # APPROVE without PR (dry-run / push failure / manual dispatch) → await_human
```

| verdict | gate flag | `pr_number` | route |
|---|---|---|---|
| `REQUEST_CHANGES` | all `False` (default) | any | `implementation_fix` — the judge named a defect, or the gate block carries `GATE_ACTIONABLE: yes` with fixable checks |
| `REQUEST_CHANGES` | `gate_flaky_only=True` | not `None` | `pr_merge` — the downgrade was flaky-only with no gate-survivor evidence at the current head; the merge lane's own `TRANSIENT_FLAKE` ladder (`docs/architecture/merge_recovery.md`) owns the outcome instead of a futile `implementation_fix` pass |
| `REQUEST_CHANGES` | `gate_dirty=True` | not `None` | `pr_merge` — the merge gate's mechanical reconciliation actor owns a DIRTY branch (D19) |
| `REQUEST_CHANGES` | `gate_non_actionable=True` | not `None` | `pr_merge` — the downgrade's gate block reads `GATE_ACTIONABLE: no` (nothing attributable to the diff, branch not DIRTY). `implementation_fix` is contractually required to answer such a review with `non_actionable_feedback.yaml`, so dispatching it is a guaranteed first-round dead end (PR #1159, issue #1164); `pr_merge` re-snapshots readiness, runs `attempt_mechanical_recovery`, and attaches named `Blocker`s before any bounded fall-through |
| `REQUEST_CHANGES` | any `True` | `None` | `implementation_fix` — no PR to gate, the gate flags are defensively ignored |
| `APPROVE` | — | not `None` | `pr_merge` |

## Deploy procedure (D8)

When merging the policy-flip PR:

1. **Drain the verification queue.** Wait until `SELECT count(*) FROM jobs WHERE team='verification' AND status='running'` returns 0. Under typical load this is ≤ 10 min.
2. **Bounce the launchd service** (`ci-deploy.yml` already does this).
3. **Verify** `gh api /repos/.../check-runs` shows the post-deploy `Tests` workflow green on the policy-flip PR before merging.

If a queued handover with `to_team_suggestions=("implementation",)` outlives the drain, the router rejects it (legal-transition check) and the workspace surfaces as `AWAITING_INPUT` — the human can then manually dispatch `implementation_fix` or close.

## Verifier identity boundary

Review POSTING by the verification team runs under a separate GitHub identity when the resolved `ForgeTarget`'s credential env var is set (`ALAN_VERIFIER_GH_TOKEN` for the default engine — see D15). The helper `secrets_store.verifier_gh_env(forge_target)` (it lived on `_pr_branch` until X2.7 PR22) resolves the reviewer credential at call time — the secrets store's `reviewer` record for the repository first, then `os.environ[forge_target.credential_env_name]` as the fallback — and returns `{"GH_TOKEN": <stripped token>}` when the result is non-empty, `{}` when it is unset or blank. `verification._apply_pr_review` (at the time this ADR was written; the H5.3 PR-2 review-posting split relocated this, along with `_apply_legacy_pr_review` and `_apply_inline_pr_review`, to `_verification_review_post.py`) resolves the workspace's `forge_target` once (in `run()`) and threads it into both the legacy `gh pr review` call (via `_apply_legacy_pr_review`, which also carries `--repo <forge_target.repo.slug>`) and the inline-comments path (`_apply_inline_pr_review` → `_pr_branch.post_pr_review_with_inline_comments`; at the time this ADR was written, relocated by the review-cluster split to `_pr_post.post_pr_review_with_inline_comments`). The underlying `process_runner.run_subprocess` merges the caller-supplied env over `os.environ` (`{**os.environ, **env}`) when the kwarg is not None, preserving the parent process's full environment. The same bot identity also covers the approval-time thread read/resolve calls (`_pr_threads.fetch_unresolved_threads` / `resolve_thread_as`, called from `_verifier_thread_resolution.resolve_after_approval` — see "Approval resolves the verifier's own threads" above): both take `forge_target` and reach the forge with `as_verifier=True`, so the adapter derives `secrets_store.verifier_gh_env(forge_target)` itself (no port operation takes an environment mapping — `docs/architecture/forge_port.md`); `_prepare` keeps its own `verifier_gh_env` read for the `no_reviewer_credential` hold and the identity check, so an empty credential still holds the pass rather than running under the ambient identity.

The following actions are explicitly **excluded** from the bot identity and use the default `gh auth` identity (the PR author / `DejvMatikar`):
- `_pr_branch.list_unresolved_threads` (at the time this ADR was written; relocated by the review-cluster split to `_pr_threads.list_unresolved_threads`) — reading threads for `implementation_fix`
- `_pr_push.push_branch` (at the time this ADR was written, `_pr_branch.push_branch`; relocated by the H5.1 shrink program's push-reconcile-cluster move) / `_pr_branch.resolve_existing_branch` — git operations
- `gh pr create` inside `implementation` / `implementation_fix`
- `gh pr merge` inside `pr_merge`
- `alan/teams/_copilot_resolution.py` (and its thin CLI wrapper, `scripts/alan_copilot_resolve.py`, for manual human recovery) — Copilot thread/comment resolution, executed host-side since D22

Note: if `GH_TOKEN` is already present in the parent process environment (e.g. set by the shell or launchd), `gh` will use that token for the excluded calls too — `ALAN_VERIFIER_GH_TOKEN` does not strip or override `GH_TOKEN` for any subprocess other than the review-POSTING/dismissal and verifier-thread read/resolve calls. If a hard boundary is required in environments where `GH_TOKEN` is injected globally, strip it from the excluded subprocess calls explicitly. The review-posting/dismissal and verifier-thread read/resolve calls always pass an explicit `GH_TOKEN` built from the resolved credential, which overrides an ambient one for that subprocess.

Audit entries for `review_ok`, `review_failed`, `review_ok_inline`, and `review_failed_inline` carry a `gh_user_override: bool` field so operators can verify which identity was used. The token value is never logged. `verifier_thread_resolved`, `verifier_thread_refused`, and `verifier_thread_resolution_held` are the three approval-time thread-resolution audit actions (see "Approval resolves the verifier's own threads" above), each with its own reason vocabulary — `has_replies` / `reply_count_unreadable` / `forge_refused` / `stopped_after_failure` for a refusal, and `count_not_reported` / `reviewer_nonzero` / `posted_count_nonzero` / `no_reviewer_credential` / `identity_check_failed` / `login_mismatch` / `thread_read_failed` for a held pass.

## Credential lifecycle: proactive expiry warning (and the reactive park it complements)

The forge/verifier tokens this pipeline depends on (D15, "Verifier identity boundary" above) are opaque to the provider — GitHub does not expose a fine-grained PAT's expiry date over the API. Two mechanisms exist to keep an expiring or revoked credential from surfacing only as a mysterious mid-workspace push/review failure weeks later:

**Proactive expiry warning (implemented here).** `POST /api/secrets` accepts an optional `expires_at` (ISO 8601 `YYYY-MM-DD`, validated in `alan/secrets_store.py`) recorded by the operator at storage time — there is no other source. `alan.secrets_store.due_expiry_warnings(now)` scans the store and returns (marking `expiry_warned_at`, so each record fires **exactly once**) every record whose `expires_at` falls inside the fixed `EXPIRY_WARNING_DAYS = 7` window; a record with no recorded `expires_at` never appears here. This check piggybacks on `TriageTeam`'s existing 30-minute sensor sweep via a new injected `check_credential_expiry: Callable[[datetime], None] | None` constructor argument (mirrors the existing `reconcile_incidents`/`run_retention` injection points) — no new background timer. `alan/routes/infra.py`'s `_build_triage_team` wires the concrete callable, which calls `due_expiry_warnings` and appends one row per due record to `~/.alan/logs/credential_expiry_audit.jsonl` via `alan.teams._audit.append_jsonl_audit`. `alan/routes/inbox.py` reads that file the same way it already reads `AUTO_CONTINUE_AUDIT_FILE`/`AUTO_DISPOSE_AUDIT_FILE` and renders each row as a `fyi`-typed `InboxItem` (`_credential_expiry_fyi_item`) — guidance lives in the required `recommendation` field (never `instruction=`, matching the other `fyi` builders, since `FyiList` on the frontend renders only `recommendation`), with `workspace_id`/`task_id` `None` and `actions=[]` since there is no single workspace to link to.

**Reactive credential park (separate work, not implemented by this section).** The complementary mid-flight path — typing a genuine credential-authentication failure on the author push path or a reviewer/API call into a distinct park classification (rather than a generic failure), with a rotate-under-the-stable-fallback-name-then-re-dispatch recovery recipe — is a distinct classification problem (genuine auth failure vs. transient/rate-limit rejection) tracked separately from the proactive warning above; it is not wired into `TriageTeam` or the inbox in this change.

### D23 — A `Delivers-Issues:` trailer on the workspace description guarantees a plain closing line on every host-published body

Before D23, the only channel for a PR to close an issue was the worker's own prose — nothing checked that a body claiming to deliver an issue actually said so in a form GitHub's closing-keyword parser recognizes, and a worker that forgot (or that D20's fence-lexer bug silently truncated the line out of) left the issue open after the work shipped.

**The trailer.** `alan/teams/_pr_closing.py::parse_delivers_trailer(description) -> Trailer` reads the workspace's `Meta.description` — never the worker's `pr_body` text, and never the pull request body; implementing this against the PR body would be a different, larger change and is out of scope. It is **order-independent**: `_scan_state`, the same fence- and comment-aware line walk that finds `Fixes #N` closing lines below, also collects every line starting with `Delivers-Issues:` anywhere in the description (skipping one inside a fenced code block or an HTML comment exactly as a closing line would be skipped), and the trailer is the *last* such line found — not necessarily the last line of the description. This was a deliberate correction during implementation: an earlier design read only the description's last non-blank line, so anything appended after the trailer (a worker's closing remark, a later amendment) hid it entirely; a real workspace brief is not guaranteed to end on the trailer, so requiring that shape silently dropped a declared trailer more often than it should have. The found line is stripped of surrounding whitespace and required to equal `Delivers-Issues: ` followed by one or more positive integers separated by `, `, with nothing else on the line — no leading `#`, no trailing prose. No candidate line at all yields an *absent* trailer (the host adds nothing, exactly as if this feature didn't exist). A candidate that fails the strict grammar (non-numeric, a stray `#`, extra trailing text, a `0`) yields a *malformed* trailer — the host still adds nothing, but records the offending line in the audit row so a human can see why. A well-formed trailer's issue numbers are deduplicated, order-preserving; there is no write-back to `Meta` or `Task` — the description is parsed fresh on every publish, so amending the description later changes what the *next* publish does without any migration.

**Outcome precedence.** `plan_pr_body(ws, base_text, trailer) -> ComposedBody` decides one of five `PublishOutcome`s, in this order: `malformed` (trailer parse failed) or `absent` (no trailer) short-circuit first — there's nothing to check presence against; then `split_skipped` when `len(ws.meta.tasks) > 1` — a decomposed workspace's issue-to-task mapping isn't derivable from the single workspace-level trailer, so the host writes nothing and records the skip rather than guessing; only then, for a declared single-task workspace, `present` (every declared issue already has a qualifying closing line) or `appended` (the host added the missing ones).

**Presence is strict; appending is the default on any doubt.** A closing line only counts when it is a *standalone* line at the start of its own line — the raw line, right-stripped only (never left-stripped), matches (case-insensitively) `close|closes|closed|fix|fixes|fixed|resolve|resolves|resolved` followed by `#N` and nothing else, so a line with any leading whitespace (an indented "code block" paragraph, a continuation line inside a list item) never counts — and sits outside both a fenced code block and an HTML comment. Fence tracking is CommonMark-aware, not a column-0 backtick toggle: `_pr_closing._fence_marker` recognizes a fence line up to 3 spaces of leading indentation, backtick- or tilde-delimited, and records its character and run length; `_pr_closing._advance_fence` only closes an open fence on a later bare line (no info string) of the *same character* and *at least as long* — a narrower or differently-delimited or info-string-bearing line can never close it, so a nested ` ```` markdown ` / ``` ``` ``` /`Fixes #N`/ ```` ```` ```` transcript reads the closing line as still fenced, not present. HTML comments use the same `<!-- … -->` scan as before, run only outside an open fence. Prose like "this fixes #42 as part of the migration" does not count, nor does a `Fixes #42` line quoted inside a code fence at any indentation. The brief's own instruction is to err toward appending: any form the strict check doesn't recognize is treated as missing, so the worst case is a harmless duplicate closing line, never a falsely-confirmed "already present."

**Placement and the size-budget guarantee.** When issues are missing, `_plan_single_task` re-normalizes the body with `build_pr_body(base_text, reserve=_reserve_for(issues, base_text))` — sized against the *full declared set*, not just the issues missing on the first pass, plus the widest backtick or tilde fence run found anywhere in `base_text` (`_max_fence_run`, floor 3) and the HTML-comment closer. That distinction matters because the reserved re-truncation can itself turn an already-present closing line into a missing one (a word-cut landing right after a `Fixes #N` line can leave a previously non-standalone line standalone, or vice versa cut one away entirely), so the second pass's `final_missing` is only ever a subset of `issues` — never a superset of whatever the reserve was sized for. Sizing against `missing` alone would leave the second truncation pass with no guaranteed headroom for a `final_missing` that turned out larger; sizing against `issues` makes the reserve a safe upper bound for any subset that can result, so a second truncation pass can never cut a line the append step is about to add. It then recomputes the missing set against *that* (possibly truncated) body — truncation can itself remove a closing line the author wrote, so presence is always evaluated against what will actually ship — closes any code fence or HTML comment left open by the truncation (`_close_open_blocks`, which writes a closer matching the actual open fence's character and length rather than assuming three backticks), and appends a blank line followed by one `Fixes #N` per still-missing issue, in the trailer's declared order. Because the reserve is computed before the append, and is sized against a superset of whatever ends up missing, the final body's length never exceeds `PR_BODY_MAX_CHARS` (60000): this is the same guarantee AC7 states, proved by construction rather than checked after the fact.

**Repository targeting: no new forge read.** `compose_pr_body` never queries GitHub — it composes purely from the workspace's own `Meta.description` and the body text already in hand (the worker's `pr_body` block, or the fallback synthesis). The short `#N` form is repository-relative by GitHub's own convention, so it resolves correctly wherever the PR is opened without qualification. `implementation._open_pr` creates the PR in the worktree's origin remote; `implementation_fix._maybe_amend_body` amends via the workspace's own `forge_target_for_ws(workspace)` — both already routed to the workspace's engine before this change, so no new repository-resolution logic was added, including for a secondary engine.

**One audit row per publish, on every host write.** `compose_pr_body(ws, synthesis, *, team, pr_number) -> str` is the sole body producer at both `implementation._open_pr` (every PR create — an authored `pr_body` block, a salvaged body, or the bare-synthesis fallback all funnel through it, so `pr_number=None` at this call site) and `implementation_fix._maybe_amend_body` (every amend the existing gating logic decides to perform; the gating itself — whether an amend happens at all — is unchanged). Each call appends exactly one `pr_body_publish` row to `impl_audit.jsonl`: `task_id`, `team`, `pr_number`, `outcome`, `issues` (the trailer's declared set), `appended` (the subset actually written this call), `body_length`, and `alternative_lengths` (from the extractor, see D20 above); a `malformed` outcome additionally carries a `trailer_line` excerpt. Routing extraction (`_pr_body.extract_authored_body`, used to decide *whether* a round is body-only) never audits — only the composer does, so a round that reads the authored body twice (once for routing, once for composing) still produces exactly one `pr_body_publish` row.

**What stayed out of scope.** Split workspaces get no host-written line at all, not a best-effort guess at which task owns which issue. Nothing here changes what the worker is told to write, or adds the trailer format to the host-parsed-block inventory — the trailer lives in the *workspace description*, a field no worker-authored fence ever populates. (#1422, the absence of a merge-time reconciliation check, is closed below — see D24.)

### D24 — A pre-merge read-back reconciles the trailer's declared issues against the forge's own closing record

D23 above guarantees the *write* side: a declared issue gets a syntactically valid closing line somewhere in the published body. It never checked the *read* side — whether GitHub's own parser actually recognized that line and will close the issue on merge. A closing line broken by `_pr_body`'s truncation math, or one a worker wrapped in a code span despite D23's own presence check treating that as absent, would still ship: the write-side defences (fence-aware scanning, the appended line, reserved truncation space) exist precisely so this is rare, but "rare" is not "impossible," and nothing before this build ever looked back at what actually landed (#1422).

`alan/teams/_pr_closing.py::gh_pr_closing_issue_numbers(pr_number, *, forge_target) -> frozenset[int]` reads GitHub's own verdict directly: one `gh pr view --json closingIssuesReferences` call, following the identical pattern `alan/teams/_pr_merge_conflict.py::gh_pr_state_and_merge_status` already established (its own sibling module, invoked from `_pr_closing.py`; `_pr_branch.py` itself is untouched, since two other workspaces hold it live). `merge_gate.readiness_after_closing_links_check(ws, pr_number, readiness, forge_target)` calls it from `merge_gate.attempt_recovery` — the one pre-merge gate both `dispatcher._enforce_pr_merge_gate` and `/api/answer`'s `_apply_merge_gate` already funnel through — immediately after the measured-baseline freshness check and, like it, only at the green short-circuit: a PR that is not otherwise ready to merge never pays the extra forge call, and a brief that declared no issues (`_pr_closing.parse_delivers_trailer(ws.meta.description).issues` empty) never triggers one either. When the declared set is not a subset of the forge's returned numbers, the readiness is downgraded (`ok=False`, a `closing_links_missing #N,#M` failed-reason) and falls through into the existing mechanical-recovery classification, landing on the new `MergeBlockClass.CLOSING_LINKS_MISSING` — routed straight to `implementation_fix` to append the missing `Fixes #N` line(s) and re-dispatch `pr_merge`, never a bounded retry, since nothing about a missing closing line resolves on its own. See `merge_recovery.md`'s "Pre-merge closing-link read-back" for the full classification and routing detail.

**Rationale.** The write-side defences reduce the failure rate; only a read-back can catch what they miss. Reusing the merge-state read pattern (`_pr_merge_conflict.py`'s own module, called from a sibling rather than folded into the shared `_pr_branch.py`) keeps the hot, contended branch module out of the diff. Gating on the green short-circuit — the same seam D23's sibling freshness check uses — keeps the cost at zero for the overwhelming majority of PRs that never reach it.
**Confidence:** 0.85 / reversibility: high (one new read, one new classification rung, no write-path change).

### D25 — A per-(PR, engine) fix-cycle ceiling parks the workspace instead of dispatching `implementation_fix` forever

Before this decision, a PR whose blocker no fix worker could clear kept cycling verification → implementation_fix indefinitely: one walled PR observed 15 cycles over 15 hours and 33 invocations, roughly a fifth of the spend landing *after* the wall was provably established, with no question ever asked of a human. `REVISIT_CAP` (`loop_guard.py`) cannot bind on this shape — it caps revisits to a single *team* on a single *handover chain*, and a chain reset (`dispatch_team_core`, on every human re-dispatch) or a forward-progress decay (a changed artifact set, a changed verdict) both legitimately zero it out. The fix-cycle ceiling is a second, independent counter with neither escape hatch.

**The counter.** `alan/teams/_pr_state_paths.py` adds a `FixCycleState(count, allowance, granted_question_ids)` record, persisted at `pr_<n>_fix_cycles.json` under the same per-engine state directory every other PR-scoped counter in that module uses — no new state-isolation surface. Unlike `GateRerunState`, it carries no `head_sha` and no reset-aware accessor: the schema itself makes "read the lifetime figure, never the head-aware one" structurally impossible to violate, since there is no head-aware figure to accidentally read. `FIX_CYCLE_CEILING = 6`, `FIX_CYCLE_ESCALATE_AT = 3`, `FIX_CYCLE_OVERRIDE_GRANT = 3`. `fix_cycle_budget(pr_number, forge) = FIX_CYCLE_CEILING + allowance`.

**Two increment sites, one invariant.** `bump_fix_cycle_count` fires from exactly two disjoint funnels, both unconditionally, so no origin can launder the count: `SelfHealMixin._enforce_fix_ceiling` (`alan/_dispatcher_selfheal.py`) on the autonomous route, called from `Dispatcher._apply_router_decision` immediately before `_enforce_loop_guard`; and `dispatch_team_core` (`alan/dispatch.py`) on every operator dispatch, propose-mode approval, and auto-continue that targets `implementation_fix` with a resolvable prior PR number. "An operator re-dispatch does not change the count" means it does not *reset* it — every dispatch, autonomous or human, still counts. A different PR number starts at zero; the file is keyed by `(pr_number, engine)`, nothing else.

**The park is answerable.** At the ceiling, `_enforce_fix_ceiling` returns `RouterDecision(kind="await_human", team=None, block_class=None, ...)` — never `kind="escalate"`, since `park.park_reason_for_decision` maps a block-class-less `escalate` to `ParkReason.ESCALATED` (no question renders) but a block-class-less `await_human` to `ParkReason.QUESTION` (the frontend renders one). The paired handover is built by `alan/teams/_spiral_handover.py::fix_cycle_ceiling_handover`, which — unlike the pre-existing `escalation_skeleton`/`no_commits_handover` precedents it reuses as its skeleton — populates `open_questions` with a real, blocking, `resolver_role="human"` question (`fix_cycle_ceiling_question`) naming the cycle count and the last verifier finding (`decision.reason`, falling back to the incoming handover's `full_synthesis`). The two proposed answers are `option_resolvers`-mapped directly (`FIX_CYCLE_OVERRIDE_OPTION → implementation_fix`, `FIX_CYCLE_HAND_RESOLVE_OPTION → verification`), bypassing the `fix_escalation` class default the way the existing non-actionable-feedback and declared-blocker questions already do.

**The override, and the ordering hazard it has to survive.** Choosing the override option grants exactly `FIX_CYCLE_OVERRIDE_GRANT` (3) more cycles via `_pr_state_paths.grant_fix_cycle_override`, idempotent on the question id (`granted_question_ids`) so a replayed POST cannot double-grant. The operator-facing dispatch path (`alan/dispatch.py::assert_team_dispatchable`, called from `answer.py`'s `_validate_resolver`, `workspaces.py`'s manual dispatch, and its propose-approval route) refuses `implementation_fix` past the ceiling with the same `409` conflict status already used for an archived workspace, its detail text naming the override as the recovery — checked after the archived check, so an archived workspace's 409 still wins. This creates a genuine ordering hazard: the same `assert_team_dispatchable` call sits inside `_validate_resolver`, which the override answer itself must pass through to dispatch `implementation_fix`. `alan/routes/answer.py::_maybe_grant_fix_cycle_override` is therefore called *before* `_resolve_answer_resolver` in `_claim`'s fresh-answer branch — the grant lands on disk first, so the ceiling check downstream reads the widened budget rather than refusing the very answer meant to lift it. A workspace recoverable only by hand-editing state would have been a failure of this item, not an acceptable edge.

**Severity escalation reads the counter, never recomputes it.** `alan/teams/triage_pregate.py::_classify_build_task` (via a `_fix_cycle_obs` helper) attaches `obs["fix_cycle_count"]` and `obs["fix_cycle_escalate"]` (`_pr_state_paths.should_escalate_fix_cycle_severity(count, job_running)`) to the `build_task` surface. `alan/health.py::_build_task_severity_action` takes this as a third, defaulted parameter and escalates the `pr_checks_failing` branch from medium to critical when fix work is in flight *and* escalated (≥3 cycles); the not-running case is untouched (already critical). `health.py` never imports the threshold literal — it lives in exactly one place, `_pr_state_paths.FIX_CYCLE_ESCALATE_AT` — and `triage_pregate` is the only caller, keeping `alan.health -> alan.teams.triage_pregate` the sole existing import-linter exception rather than adding a second. `_describe_build`'s existing "work is running" running-tag grows a `(N fix cycles)` suffix when the count is non-zero.

**Two false-terminal repairs riding the same mixin.** `SelfHealMixin._maybe_self_heal` also gains `_route_noop_no_commit`, wired immediately after the merged-sibling self-heal path declines (so a merged sibling still resolves first). A no-commit escalation (`is_no_commit_escalation`) on an atomic workspace (`ws.meta.tasks` non-empty, no merged sibling) whose carried PR reads live as green — no failing check, no pending check, no `CHANGES_REQUESTED` review, via one `_pr_ready.readiness_or_unavailable` call — now routes to `verification` instead of dead-ending in a question-less `escalate`. And `alan/teams/_declared_blocker.py::_marked_bullets` now drops a `[BLOCKING]` bullet whose remainder is a no-op token (`none`, `n/a`, `no`, `nothing`, `-`, any case, optional trailing `.`/`!`) before it ever reaches `_declared_blocker_question` — a worker writing "- [BLOCKING] none." no longer manufactures a question with nothing to decide.

**Rationale.** Every route that can dispatch `implementation_fix` — the verification forward-route, the merge-gate remediation route, and the operator/answer route — shares one funnel-independent counter precisely so none of them can be used to launder cycles past the other two. `REVISIT_CAP` and `detect_spiral` (`loop_guard.py`) are untouched: they bound a different, narrower shape (one handover chain) and still fire well inside six cycles when they apply; this ceiling is the backstop for the chains that outlive both, by construction.
**Confidence:** 0.85 / reversibility: high (a new counter file, two increment call sites, one dispatcher line, no change to existing routing for any workspace under the ceiling).

## Consequences

**Positive.**
- Removes the largest human-gate latency in the routine PR path (plan → implementation).
- `implementation.run` drops below the 60-line lizard ceiling once `_pr_branch.py` is extracted; new gate headroom for future iteration.
- Long judge reviews stop silently losing findings to truncation (D7).
- `pr_merge` is reusable for any team that ends in an approved PR — `maintenance` could opt in later.

**Negative.**
- One-time queue-drain procedure on deploy (D8). Documented; small operational cost.
- Two new teams to maintain; `pr_merge`'s state machine is the only non-trivial new state.
- Loss of the iteration-1 fallback (`verification → implementation`) means the policy-flip PR must be the same PR that registers `implementation_fix`; partial rollouts are not safe.

**Neutral.**
- `auto_dispatch` defaults to `False`. Existing tasks behave exactly as before until a user opts in at creation.
- `pr_merge` runs live; calibration window closed 2026-05-20 (A2). Dry-run remains available locally via `export ALAN_PR_MERGE_DRY_RUN=1`.

## D20 — A salvaged handover publishes honestly, and every force-push it triggers pins its lease

**The PR body for a salvage-only PR is composed from the workspace brief and the diff, never from a worker's final message.** `alan/teams/_pr_closing.py::is_salvage_only(worktree, base_ref)` checks the author email of every commit in `base_ref..HEAD` (one `git log --format=%ae`); the PR is salvage-only only when every commit — and there is at least one — was authored under the `alan-salvage` identity (see [implementation_pipeline.md](implementation_pipeline.md)'s salvage section). When `_open_pr` (`implementation.py`) finds this true, it calls `compose_salvaged_pr_body` instead of the normal `compose_pr_body(synthesis)` path: the salvaged body is assembled from the workspace's own title/description plus a capped `git diff --stat` of the salvaged commits and an explicit statement that the PR was salvaged and no worker synthesis is reflected — then handed to the same `compose_pr_body` so the closing-line/`Delivers-Issues:` trailer machinery (D7's earlier fix) still runs once, on the honest text. This applies only to `implementation`, the team that opens the PR; `implementation_fix`'s later body amendment is untouched, since a fix round only ever amends an already-open PR's body and the brief this composer reads from is the whole-feature description, not a per-iteration one.

**Every salvage notice now says the same true thing: the worker's own gate never ran.** The five salvage notice/clause strings in `alan/teams/_pr_handover.py` (`_SALVAGE_NOTICE`, `_SALVAGE_FAILED_NOTICE`, and the three `_CEILING_SALVAGE_*_CLAUSE` variants) no longer tell downstream verification/fix to "judge these commits on their merits like any other contribution" — a salvaged commit's local gates (pytest, lint, coverage) were never run by anything, so treating it as equivalent to a worker-verified contribution was simply false. Each notice instead states plainly that the worker's own gate result was never observed and must be re-run before anything downstream relies on it. This holds even for the "clean" ceiling clause (the worker's own commits, made before the ceiling hit): the ceiling means the worker never reached its own success-block gate run either, so the same caveat is correct there too. `with_salvage_notice` also takes an optional `skipped_count` and, for the `"salvaged"` outcome only, appends how many build-artifact paths were left out of the commit — see [implementation_pipeline.md](implementation_pipeline.md).

**The reconciled re-push now pins its lease, matching its siblings.** `_pr_push.py::_repush_reconciled` used a bare `--force-with-lease` (no pinned ref), the one remaining unpinned force-push call site after D6 pinned the first-push and reconcile-detection paths — an unpinned lease is neutralized by the very fetch this function's caller just ran, exactly D6's original problem statement. It now pushes `--force-with-lease={branch}:{remote_sha}`, spelled identically to `alan/teams/_pr_reconcile.py`'s pinned form. `remote_sha` was already resolved and in scope (previously used only for the audit row); when it resolves empty — near-impossible immediately after a successful fetch, but the failure mode of guessing wrong here is exactly the bug this fixes — `_repush_reconciled` fails closed with `PushOutcome.PUSH_FAILED` and an audit row naming the empty resolve, attempting no push at all rather than falling back to an unpinned one.

**The conflict route's human-facing instructions now carry the same pinned-lease command as a copy-pasteable recipe.** `alan/merge_gate.py`'s `_branch_head_blocker`/`enrich_conflict_blockers`/`conflict_fix_decision` each take a defaulted `branch: str = ""` (all pre-existing call sites stay compiling and line-neutral); `_branch_head_blocker` renders `Blocker.instruction` as `git push --force-with-lease={branch}:{starting_sha} origin {branch}` — the existing `_blocker_line` renderer already prints `instruction` when present, so `render_remediation_instructions` needed no edit. The branch name itself is threaded onto the shared `PrReadiness`/`_READINESS_FIELDS` read: `_READINESS_FIELDS` (`alan/teams/_pr_ready.py`) now requests `headRefName` alongside the existing fields on the same `gh pr view` call `check_pr_merge_readiness`/`check_pr_verifier_blockers` already make on every poll, and `PrReadiness.head_ref_name` carries it — no dedicated second `gh` call. `Dispatcher._pr_merge_conflict_or_retry` (`alan/dispatcher.py`) and `routes/answer.py`'s `_conflict_fix_instructions` both call the plain `conflict_fix_decision(blockers, rec, block_class, readiness.head_sha, readiness.head_ref_name)`, passing the readiness snapshot's own `head_ref_name` as the `branch` argument. (An earlier design sketch here routed this through a dedicated `conflict_fix_decision_with_branch` wrapper and a standalone `fetch_pr_head_ref_name` call specifically to avoid touching the shared, heavily-pinned `_READINESS_FIELDS` literal; it was reverted mid-implementation once threading the field onto the existing read proved not to trip any of the pinned call-site assertions after all — dispatcher-level DIRTY-conflict tests mock `check_pr_merge_readiness` directly, so widening its returned payload needed no second live `gh` read and could not trip `tests/gh_guard.py`. Neither symbol from that sketch exists in the shipped code.) The fix team's own divergence-escalation narrative (`implementation_fix.py::_build_divergence_escalation`) uses the identical `--force-with-lease={branch}:$(git rev-parse origin/{branch})` spelling in its by-hand recovery recipe, so a human reading either surface sees the same command shape.

**Confidence:** 0.85 / reversibility: high — five string edits, one new composer function gated on git-authorship (never on a text marker a worker could echo), one previously-unpinned push call site, and a defaulted parameter threaded through an existing renderer.

### D26 — Every process that can reach merge-family code installs a forge at startup, from a module-level holder

X2.3 PR2 (`docs/architecture/forge_port.md`) gives the merge family's direct forge calls a
substitution point: `alan/forge.py::set_active_forge`/`active_forge`. This section documents the
installation side — where the real adapter gets installed in this pipeline's own process, and
why the fake installs itself for every test.

**The mechanism is a module-level global holder, not a `ContextVar` or `app.state`.** A `ContextVar`
set inside the ASGI `lifespan` task is invisible to every request handler — each `asyncio.Task` a
request handler runs in gets its own copy of the context at creation, so a `.set()` made while the
lifespan's own task is running is discarded once that task's `async with` block moves on, before any
request has been served. It is doubly invisible to `run_in_threadpool` work (the collision-check and
amendment-approval routes above both hand work to the thread pool) and to the in-process job runner
the dispatcher owns, neither of which shares the lifespan task's context. `app.state` has the
opposite problem: it is visible to request handlers but not to the in-process job runner, which is
constructed and driven independently of any single request. A plain module-level global is visible
to all three reachers uniformly, which is why `alan/forge.py` holds `_active_forge` as a bare
variable rather than either alternative.

**Installation happens once, at server startup, never at import and never per job.** `alan/server.py`'s
`lifespan` calls `set_active_forge(GhForge())` as its first statement, strictly before
`async with _infra_lifespan(app)` constructs the dispatcher and the in-process job runner
(`alan/routes/infra.py`) — a later install would race whichever of those reaches the forge first.
Module-import-time installation was rejected because it would fire for every test that merely
imports `alan.server`, making import order load-bearing for what the active forge is. Per-job
installation was rejected because `GhForge` carries no per-job state at all — every `ForgePort`
method already takes its `ForgeTarget` as a call parameter, so there is nothing job-scoped to
install.

**The test suite installs a strict fake for every test, so an unstubbed call fails loudly instead of
succeeding silently.** `tests/fakes/forge.py::FakeForge` implements all eight `ForgePort` methods;
each raises `AssertionError(f"unstubbed forge call: {name}")` unless the test registered a stub via
`.stub(name, fn)`. An autouse fixture in `tests/conftest.py` saves the current holder value, installs
a fresh `FakeForge()`, yields it to the test, then restores the saved value by direct attribute
assignment — mirroring the existing `_reset_registry` save/set/restore shape already used for
`alan.engine_config`'s module registry. A permissive fake was rejected on the same reasoning as the
strict accessor: once PR3 migrates the rest of the merge family onto the port, a fake that quietly
returned a default for anything unstubbed would let roughly a hundred still-unported transcript
setups keep passing while testing nothing, with coverage still reading 100%. PR3 kept the fake
strict: the tests that reach `check_pr_merge_readiness` only incidentally (implementation-fix and
clause-audit suites that never scripted `gh pr view`) each declare a module-local autouse
`_gh_down` fixture that stubs `read_pr` with the rc=86 result `tests/gh_guard.py` used to return,
rather than the fake growing a default.

**Exactly one merge-family read is migrated in PR2, chosen for narrowness rather than as the start of
PR3's migration.** `alan/teams/_pr_reconcile.py::_resolve_head_base` — the branch reconciler's
head/base-ref lookup — is the only forge call in its module, has a single production caller, and no
test names it directly; its transcript setups live in one test file
(`tests/test_pr_reconcile.py`). It is reached both from the dispatcher's job runner and from
`alan/routes/answer.py`'s merge-gate HTTP path (via `alan/merge_recovery.py`), so migrating it
exercises both installs described above. It keeps its existing
`except (FileNotFoundError, subprocess.TimeoutExpired): return None` swallow at the call site,
unchanged from before the migration — see `docs/architecture/forge_port.md`'s Error contract
section for why that swallow could not move into `GhForge` without deciding, ahead of PR3, whether
the port should absorb transport faults for the whole family.

**PR3 migrates the covered remainder — seven call sites — and stops there.** `pr_merge.py` reaches
the forge for `merge_pr` (`_execute_merge`) and `read_checks` (`_gh_pr_checks`); `_pr_ready.py` for
`read_pr` (`_gh_pr_view_readiness`, `_fetch_pr_base_sha`) and `changed_files`
(`_gather_quarantine_inputs`). The two branch-update callers, `_behind_during_merge_outcome` and
`merge_recovery.py`'s `_recover_behind_plus_transient`, were PR3's `update_branch` sites; that operation was
deleted in X2.7 PR21, and both now reach `request_branch_update` through
`_pr_branch.update_pr_branch_outcome`, counting only `UPDATED` as success. The merge-failure classifiers take a
`MergeAttempt` instead of a `CompletedProcess`, and the readiness parsers take the parsed field
dict the port returns instead of stdout; `docs/architecture/forge_port.md` records the contract
changes (empty-`fields` guard, base-sha extraction moved into the caller). Everything the family
sends to the forge that has no port operation yet — the PR-state read, the review-thread GraphQL
read, the flake-guard head read, check reruns, the failing-e2e read, the branch-update outcome read
and stale-review dismissal — is unchanged and is X2.7's. `tests/test_forge_seam_merge_family.py`
fails any of the five brief components that regrows a `gh pr view|checks|merge` argv or names the
branch-update or changed-files helpers directly.

### D27 — A downgrade the branch can fix posts as a blocking change request, not a comment

D10a made the gate-park review event `--comment` whenever the verdict was rewritten
`APPROVE → REQUEST_CHANGES` on a zero-critical output carrying the `## External Gate Status`
marker, regardless of whether the named blocker was something the branch could fix. That collapsed
two different situations into one non-blocking posting: a required check that is red for a reason
outside this diff (merge state, a pending check, a quarantined/known-flaky check — nothing the fix
team can act on) and a required check that is red *because of* this diff and is already dispatched
to `implementation_fix` (`suggestions_for_verdict` has routed an actionable downgrade to
`implementation_fix` since before this change — see D10 above; only the forge event was wrong). One
measured instance spent roughly nine hours and $32 across three verification passes, posting under a
"parked on external gates" heading that told the reader nothing blocked, while the fix loop worked
the very defect that heading disclaimed — a human ruling merged it within the hour once seen.

`github_review_event` (`alan/teams/verification.py`) now adds a fourth clause to its COMMENT branch:
`and not parse_actionable_gate_checks(judge_output)`. The trigger is **at least one named actionable
check**, never the `GATE_ACTIONABLE: yes` line by itself — the base-conflict branch of
`_gate_actionability_lines` (`alan/teams/_verification_gates.py`) emits `GATE_ACTIONABLE: yes` with
no `GATE_ACTIONABLE_CHECKS:` line at all (a conflicting branch has no fixable check; the mechanical
reconciliation actor owns it, not a code change), and that shape — like `GATE_ACTIONABLE: no`, no
actionability lines at all, a bare `GATE_ACTIONABLE_CHECKS:` prefix, or a whitespace-only names
list — still yields `()` from `parse_actionable_gate_checks` and still posts `COMMENT`. Re-parsing
the emitted body (rather than threading a new parameter through `resolve_external_gates` /
`_maybe_post_review`) keeps the posted body the single source of truth: emitter and parser can only
drift by editing the same block, and any divergence between them fails closed to `COMMENT`, never
open to a spurious blocking review.

`_GATE_PARK_HEADER_ACTIONABLE` (`alan/teams/_verification_gates.py`) is reworded to match: it keeps
its `> PARKED ON EXTERNAL GATES` opening and its "in scope for the fix round" clause, but its final
sentence now reads "Posted as a blocking change request; it clears when those checks go green on a
new push," replacing "Posted as a non-blocking comment." The near-identical non-actionable twin,
`_GATE_PARK_HEADER`, is untouched: its own "Posted as a non-blocking comment" sentence stays true,
because that path still posts a comment.

**Wanted consequence: two actionable downgrades at an unmoved head now count toward the verifier
rejection ceiling.** An actionable downgrade is a `CHANGES_REQUESTED` review at the current head
where before it was a non-sticky comment. `unblock_recipes.verifier_rejections_at_head` already
counts live `CHANGES_REQUESTED` reviews from the verifier identity at a given head commit, and
`VERIFIER_REJECTIONS_AT_HEAD_CEILING = 2` already gates both `_head_retry_probe` (the
`green_named_check_blocker` recipe) and `_probe_non_actionable` (the `non_actionable_green_head`
recipe). Nothing in `alan/unblock_recipes.py` changes: the two actionable downgrades a fix pass with
no commits would previously have posted as comments now post as `CHANGES_REQUESTED` reviews at the
same unmoved head, so both recipes decline with their existing "the verifier already rejected this
head twice; a third pass adds nothing" reason — by design, two rejections at an unmoved head is
already a verdict, and both recipes exist to recover a park whose head is green or has moved, not to
retry a head the verifier has already judged twice.

**Wanted consequence: a downgrade carrying inline findings now posts a blocking review with the
inline comments attached.** `_apply_pr_review`'s inline-findings path keys on the `##
INLINE_FINDINGS_YAML` block and the (already-rewritten) verdict, not on the critical count, so a
zero-critical actionable downgrade that happens to carry stale or attributable inline findings from
the diff reviewer now posts under the actionability-gated event exactly like the non-inline path —
`REQUEST_CHANGES` with the findings as inline comments when a check is named, `COMMENT` when none
is. The posting path itself (`_apply_inline_pr_review` vs. the legacy body-only post) is unchanged;
only the event value it posts under differs.

**Out of scope, unchanged by this decision:** the actionability classifier itself — a required check
outside the three-name shared flaky allowlist that reds for a reason outside the diff was already
classified actionable and already dispatched to `implementation_fix` before this change (D11's
`_maybe_fetch_gate_failures` / `_fix_gate_checks.live_failing_checks`); this decision only changes
which forge event that already-actionable classification posts under, and creates no new
misclassification. The `_pr_state_paths` fix-cycle ceiling in `alan/dispatch.py` and the review
waiver/dismissal path in `alan/teams/_pr_waiver_dismissal.py` are likewise unchanged: a waiver answer
still dismisses an actionable downgrade's review exactly as it dismissed a genuine-defect one, and
the red check it named still blocks the merge gate independently of the review's dismissal.
**Confidence:** 0.88 / reversibility: high — one added clause re-parsing an existing emitted block,
one header reword, zero production changes in `alan/unblock_recipes.py` (pinned by two new
characterization tests).


### D28 — Only collaborator review threads block; stranger single-comment threads are auto-resolved

On a public copy of alan anyone can open an inline review thread on a PR. Before this decision the
merge gate counted every unresolved thread started by a human as blocking feedback, and GitHub's own
"require conversation resolution" branch rule (which alan's protection setup turns on) blocked the
merge as well, so one stranger's single comment could stall any PR. This is a deliberate production
change (PD17); the owner's fleet behaves identically, pinned by
`tests/test_pr_feedback_owner_characterization.py`. Only review threads are affected: PR conversation
comments and review summaries stay observational (the shadow categories above) and are never looked
up.

**Collaborator definition.** A collaborator is an account whose *repository permission* is `admin`,
`maintain` or `write`, read from the collaborator-permission endpoint
(`repos/{slug}/collaborators/{login}/permission`, `.permission`, through the `repo_permission` forge
port operation), never from GitHub's comment `authorAssociation` label. The endpoint's legacy
`permission` field folds `triage` into `read` and `maintain` into `write`; a custom role reports the
base role it inherits. The closed set is: `read`, `triage`, `none` resolve; `admin`, `maintain`,
`write` block; any other value (including a different case such as `READ`), an empty or missing value,
or a failed lookup blocks too.

**Skipped accounts and invariants.** The repository owner (`forge_target.repo.owner`) and the reviewer
account (the login of `_pr_branch.verifier_identity()`, when one is configured) always count as
collaborators, compared case-insensitively, and are never looked up. With no verifier login configured
only the repository owner is skipped: `_pr_feedback._skip_logins` adds the verifier's login to the set
only when `verifier_identity()` returns an identity, so no account is exempted from the lookup on the
verifier's behalf and every other human-started single-comment thread is classified by permission like
any stranger's. Bots are classified by `__typename` exactly as D18 says: Copilot threads
route to `implementation_fix`, other bots stay informational, and no lookup is made for either. A
thread whose author is missing or unreadable keeps blocking and is never resolved (`_parse_actor`
still returns `None`, which classifies as `human` with an empty login).

**Verifier identity.** Which account is alan's verifier is data, not code. `_pr_branch.verifier_identity()`
resolves it once per call in this order: `ALAN_VERIFIER_LOGIN` from the service environment (stripped; a
blank value counts as unset), then the default profile's `verifier_login` (`alan.default_profile`,
`engine_config.md` "Profile schema"; the owner's checked-in profile carries its bot there, an installed
copy's profile carries none), then nothing. There is no built-in login. A configured login is a frozen
`VerifierIdentity`; "not configured" is `None`, never an identity with an empty login, and
`VerifierIdentity.matches(author)` is true only for a non-empty author exactly equal to the login (case
sensitive), so an item with no author, a null login or an empty login never matches. Every consumer takes
the identity as an argument and treats `None` as "no account is the verifier", which fails closed:

| Consumer | With a login | With none configured |
|---|---|---|
| `_pr_post._fetch_changes_requested_ids` (stale-review dismissal) | the verifier's `CHANGES_REQUESTED` reviews on older heads are dismissed | returns no ids before the review stream is fetched; nothing is dismissed as a stale verifier review |
| `_pr_waiver_dismissal.dismiss_for_waiver` | the verifier's `CHANGES_REQUESTED` reviews are the dismissal targets; other authors' reviews are tracked as other-author blocks | no review is a target; every reviewer counts as another author, so a blocking review of any author stands |
| `_pr_ready._verifier_lane_review_decision` | a `CHANGES_REQUESTED` decision is cleared only when no latest review requesting changes belongs to someone other than the verifier | the `CHANGES_REQUESTED` decision is returned as GitHub reported it, so the verifier lane keeps the block it cannot attribute to itself; a latest review with no author is likewise not the verifier's |
| `_verifier_thread_resolution` | `gh api user` under the reviewer credential must equal the login (`login_mismatch` otherwise); only threads rooted by the login are candidates | held as `verifier_login_unconfigured` before any forge call; `_verifier_threads` selects none |
| `_pr_feedback._skip_logins` | the repository owner and the login skip the permission lookup, compared case-insensitively | only the repository owner is skipped |
| `unblock_recipes` (`other_author_requested_changes`, `verifier_review_position`, `verifier_rejections_at_head`) | the verifier's reviews are told apart from other authors' | any review with a string `user.login` (including an empty one) whose latest state is `CHANGES_REQUESTED` counts as another author's (the recipe declines "a human review requests changes"); a review whose `user.login` is missing or not a string is skipped by `other_author_requested_changes`, so an authorless `CHANGES_REQUESTED` review is not counted as another author's request, with or without a login configured; the verifier's review position is `none` and its rejections at a head are zero |

Setting the login stays an install decision with no new variable: a copy sets `ALAN_VERIFIER_LOGIN` through
the setup `verifier` step, and the owner's install gets its login from its checked-in profile with no
secrets edit and no installed profile.

**Candidate rule.** `fetch_feedback` settles a thread only when it is unresolved, has a non-empty node
id, was started by a human (per D18) with a non-empty login that is neither the owner nor the reviewer
account, and has exactly one comment: `ThreadInfo.human_threads` (a tuple of `HumanThread(thread_id,
login, comment_count)`) carries every unresolved human-classified thread, and `comment_count` comes
from the new `comments{totalCount}`; a missing, non-integer or boolean count makes the thread a
non-candidate. Threads with replies — including a stranger replying to their own thread — are never
candidates and keep today's named "unresolved feedback" park. The filter runs cheapest-first, so an
owner-shaped payload never reaches the forge. The reviewer credential
(`secrets_store.verifier_gh_env`) is checked once per evaluation, only if a candidate exists; without
it there is no lookup and no write.

**Lookups.** Each candidate author's permission is looked up at most once per author (compared
case-insensitively) per evaluation, i.e. per merge-gate poll, under the ambient transport identity like
the feedback read; the answers live in a per-call dict and nothing is kept between evaluations. A
failed, raised or `OSError`/`TimeoutExpired`-faulted lookup, and a missing or unrecognised value, count
the thread and write one `stranger_permission_lookup_failed` audit record per author.

**Resolve and read-back.** When the permission reads `read`, `triage` or `none`, `_pr_feedback` calls
`resolve_thread_checked`, which runs the `resolveReviewThread` mutation selecting
`thread{isResolved,comments{totalCount}}` **only** under the reviewer identity: the adapter takes
`secrets_store.verifier_gh_env` directly and, when it is empty, returns a failed `ApiResult` without
spawning `gh`. It never uses `_verifier_env`'s fallback to the ambient token, and no reply is posted.
The thread stops counting only when the mutation succeeded, `isResolved` reads back `true` and the
read-back comment count is exactly 1. If the read-back count is anything else (more than one comment,
or unreadable), alan calls `unresolve_thread` (`unresolveReviewThread`, same strict identity) and the
thread counts for that evaluation; a failed un-resolve — non-zero exit, fault, unparseable payload, or a
payload still reading `isResolved: true` — also counts the thread and is audited.

**Fail-closed cases.** Each of these leaves the thread counted, which yields today's named `unresolved`
outcome: a failed lookup, a missing or unrecognised permission, a missing reviewer credential, a resolve
that is refused, faults, hits a transient error or is rate-limited (stderr is audited, nothing is
re-raised), a mismatched read-back, a thread with replies or an unreadable count, and a failed
un-resolve. `ThreadInfo.total`, `copilot_threads` and `other_bot_unresolved` are never changed, so the
100-item unresolved ceiling cannot be bypassed by settling.

**Audit.** Records go to `impl_audit.jsonl` through `_pr_audit_log.append_audit`, exactly one per
attempted operation plus one per failed lookup: `stranger_permission_lookup_failed` (fields `login`,
`error`), `stranger_thread_resolved`, `stranger_thread_resolve_failed`, `stranger_thread_unresolved`
and `stranger_thread_unresolve_failed` (fields `thread_id`, `login`, `permission`, `comment_count`,
`error`, capped at 500 characters), each also carrying `action`, `pr_number`, `repo` and the sink's
timestamp. A `stranger_thread_resolved` followed by a `stranger_thread_unresolve_failed` marks the
accepted residual-risk case below. There is no dry-run gate: `ALAN_PR_MERGE_DRY_RUN` is scoped to the
merge call, e2e and stage run without a reviewer credential (so they never resolve), and a resolve is
reversible.

**One set of counts.** The settle step returns a snapshot whose `ThreadInfo.human_unresolved` and
`human_threads` are net of the settled threads, so the blocking decision (`_classify_feedback`), the
escalation reason (`unresolved_human_reason`), the concurrent-blocker list and the `ctx["threads"]`
audit fields, all derived from that one snapshot in `pr_merge._evaluate_checks`, always agree;
`pr_merge.py` itself is unchanged.

**Unblocker opt-out.** `fetch_feedback` is `read_feedback` (today's pure read, byte-for-byte) followed
by the settle step. `unblock_sweep.default_deps` calls `read_feedback`, so the unblocker's
human-feedback check keeps today's counting with zero lookups and zero writes; a stranger's thread
still makes its `green_not_merging` probe decline, and treating stranger threads as non-blocking there
is out of scope.

**Accepted residual risk.** A collaborator's reply could land between alan's read of the feedback and
its resolve, or after the mutation response (GitHub does not resurface a thread on a late reply), and
the un-resolve could then also fail; the thread may then stay resolved. The audit trail makes this case
findable.

**Out of scope.** Making conversation comments or review summaries blocking; a stranger's "changes
requested" review affecting the unblocker's recovery checks; a stranger posting enough threads to hit
the unresolved ceiling; stranger threads with replies. No branch-protection, conversation-resolution or
interaction-limit change is made.
**Confidence:** 0.85 / reversibility: high — one new read path in `_pr_feedback.fetch_feedback`, three
forge-port operations, and no change to the merge team's module; reverting restores the previous
counting.
