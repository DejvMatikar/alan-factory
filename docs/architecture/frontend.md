# Frontend

**Source:** `alan/web/src/`, mounted by `alan/server.py:_SPAStaticFiles`.

Single React 19 + TS + Vite + Tailwind v4 page. All task state lives in React `useState` — there is no client-side DB, queue, workers, or persistence. Closing the tab discards everything.

## Source layout

The source root (`alan/web/src/`) holds at most 12 non-test `.ts`/`.tsx` modules. The count is `ls src/*.ts src/*.tsx | grep -v test | wc -l`, run from `alan/web/`; it counts `vite-env.d.ts` and excludes every `*.test.*` file. Everything else lives in a folder: providers and server-state code in `api/`, app-shell providers in `shell/`, shared helpers in `lib/`, per-screen code in `features/`. The 12 that stay at the root, and why:

- `main.tsx` — Vite entry point: `index.html` loads it by path, coverage excludes it by path, and `.dependency-cruiser.cjs` names it.
- `vite-env.d.ts` — Vite's ambient-types shim, kept at the root by convention.
- `App.tsx` — the composition root: the one production module the `feature-inbound` rule lets import every feature. It stays next to `main.tsx` by choice.
- `api.ts` — the hand-written API module (see the API client section); layout moves do not edit it, and the bare `../api` import resolves to it because `api/` has no index module.
- `controlToken.ts` and `projectFeatures.ts` — e2e fixtures and specs import them by path.
- `port-avoidance.ts` — e2e fixtures and the audit teardowns import it by path. It is also imported by `lib/derived-run-config.ts` (a back-edge from `lib/` to the root) and imports `lib/restricted-ports.ts`; it cannot move until the e2e tree may be edited.
- `mobile-audit-config.ts` and `desktop-audit-config.ts` — the Playwright configs and the audit specs import them by path.
- `capture-config.ts` — finds its screenshot output folder relative to its own location.
- `mergeBlockLabel.ts` — a CI path filter (`.github/workflows/tests.yml`) and backend tests name it.
- `ui-spec.ts` — backend prompts (`alan/teams/ui_review.py`, `alan/teams/implementation_plan.py`) name it, and a backend test checks that name.

`index.css` and `ui-spec.json` also sit at the root but are not `.ts`/`.tsx`, so they are not counted.

`lib/derived-run-config.ts` and its chain (`../port-avoidance.ts` → `./lib/restricted-ports.ts`) keep explicit `.ts` import endings, because `scripts/derived-run-config-fixture.mjs` loads them under plain Node, whose resolver cannot follow an extensionless specifier.

## SPA fallback for the workflow permalink

`_SPAStaticFiles` in `alan/server.py` subclasses Starlette's `StaticFiles`. When `html=True` would otherwise 404 on a non-asset path that **doesn't look like an API call** (`!path.startswith("api/")` and the last segment has no `.`), it serves `index.html` instead.

That's what makes `/workspaces/:taskId/invocations/:invId` resolve from a fresh browser tab (bookmark, share link, server-side redirect). Asset 404s still 404 — only SPA-route shapes fall through to React Router.

## `WorkflowView` at `/workspaces/:taskId/invocations/:invId`

`alan/web/src/features/workspace/pages/WorkflowView.tsx`. Renders the Kestra YAML as a `@xyflow/react` DAG:

- One custom node per `WorkflowTask` (role, model, `NodeStatusBadge`, duration).
- Edges from `depends_on`.

Subscribes to the existing workspace SSE stream and applies live `node_started` / `node_completed` events via `parseTaskFromEvent` + `mergeNodeUpdate` (in `alan/web/src/features/workspace/hooks/workflow.ts`).

Clicking a node opens a right-side stream panel that:

- Fetches `/agents/<role>/stream` once.
- Then appends live `stream` events that arrive on SSE.

The `StreamPanel` accepts an optional `nodeError` prop and pins a red footer "node failed: <message>" at the bottom when the selected task's `status === "failed"`, fed by `selected.error` from `InvocationCard`. `WorkflowDAG` also renders the error inline (small red text) AND as a `title=…` tooltip on failed nodes.

## Workspace detail page

Links into the `WorkflowView` via an `Invocations` section (one link per `inv_NNN`). A pending `InvocationCard` appears in the Timeline immediately when a job is dispatched (`workflow_created` SSE event triggers a refetch of `listInvocations`) so the user isn't waiting for the first `node_started` to see something.

The header (`Workspace.tsx` `Header` component) renders the workspace `StatusBadge` plus a small `StopResumeButton` component that switches between **Stop** (visible when `ws.status === "active" && ws.has_running_job`) and **Resume** (visible when `ws.status === "paused"`, or when `ws.status === "awaiting_input" && ws.has_resumable_failed_job`). The second Resume condition covers workspaces that landed in `AWAITING_INPUT` because the reconciler's resume branch failed and fell back to `mark_interrupted_and_fail` while the job still carries a valid `resume_inv_id`. The button is hidden entirely when none of those conditions hold — chat-only workspaces with no running job don't render it. Both modes share the busy-state / error-toast pattern used by the existing Archive button. The button extraction keeps `Header` under the ESLint `complexity: 8` cap. SSE event kinds `workspace_paused` / `workspace_resumed` / `job_paused` are wired into `WORKSPACE_LIFECYCLE_KINDS` in `workflowLive.ts` so the badge updates without a manual refresh.

Pending invocations hide the inv-level duration; the per-node `NodeStatusBadge` already renders the `pending` style.

Handovers are no longer shown as a standalone "Latest handover" section. They render as clickable nodes inside `InvocationGraph` (`alan/web/src/features/workspace/components/InvocationGraph.tsx`), inserted between invocation group nodes. Selecting a handover node opens `HandoverDetailPanel` (`alan/web/src/features/workspace/components/HandoverDetailPanel.tsx`) below the flow, which renders the full handover payload. Handover data is fetched from `GET /api/workspaces/{task_id}/handovers` (see [workspace_api.md](workspace_api.md)) and typed to schema 1.4 (see [handover.md](handover.md)).

Acceptance-clause / decomposition surfacing (see [acceptance_gate.md](acceptance_gate.md)): a "Definition of done" section renders `TaskDoDPanel` (per-task `dod_clauses` with `covers` + delivery `evidence`) when any task carries clauses; a read-only "Decomposition" section shows `latest_handover.split_rationale`; and `InterTaskDAG` nodes carry a small `planning_state` badge (O/D). These two sections are grouped in a `ClauseSurfacing` sub-component of `Workspace.tsx` to stay under the ESLint complexity cap.

## Queue-paused banner

`alan/web/src/components/QueuePausedBanner.tsx` is mounted in `Shell` (between `<header>` and `<main>`) and polls `/api/health` to detect when the dispatcher is paused for an Anthropic usage/session limit. When `queue_paused: true`:

- Renders `"Queue paused — auto-resumes at HH:MM (in MM:SS)"` using `Intl.DateTimeFormat` for the locale-aware time.
- Polling cadence: 5 s while not paused, 1 s while paused for a live countdown.
- A separate 1 s `setInterval` drives the countdown display independently of the polling timer.
- Both timers are cleaned up on unmount; errors from `/api/health` are swallowed silently (no banner, no crash).
- Accessible: `role="status"` + `aria-live="polite"`, `data-testid="queue-paused-banner"`.

`alan/web/src/hooks/useQueuePauseStatus.ts` encapsulates the polling logic as a hook returning `{ queuePaused, pausedUntil }` to keep `QueuePausedBanner` under the ESLint `complexity: ["error", 8]` limit.

When paused, the banner also renders `alan/web/src/components/QueueResumeButton.tsx` — a shared `Button variant="action"` labelled "Resume queue" — delegated to its own file rather than inlined, again to hold `QueuePausedBanner` under the complexity cap. It `POST`s `/api/queue/resume` (`api.resumeQueue()`), disabling itself for the duration of the call via a local `pending` boolean so a single click cannot double-fire, and reports success/failure to the banner via `onResumed`/`onFailed` callback props rather than owning any pause-state itself. There is no confirmation step, matching the Stop control's precedent (`docs/DESIGN_SYSTEM.md`'s Stop-fires-immediately entry).

A successful click calls `refetch()` (from `useHealthContext()`) so the banner clears on the next `/api/health` response rather than waiting out the up-to-5s poll interval. Because the pause is a single fleet-wide state used for more than one underlying cause, a clear is not guaranteed to stick — the very next piece of work can re-trip it — so `QueuePausedBanner` renders a persistently-mounted sr-only `<p role="status" aria-live="polite" data-testid="queue-resume-announcement">` as a sibling of (never nested inside) the banner `div`, carrying both the success and failure text. It is mounted unconditionally, even while the queue isn't paused and the region is empty, because a live region only mounted at the moment of the announcement is not reliably picked up by assistive tech. The announcement is cleared on the `queuePaused` transition to `true` via the "adjust state during render" pattern (a mirrored `prevQueuePaused` state compared against the live value, `setAnnouncement`/`setPrevQueuePaused` called directly in the render body when they differ) rather than inside a `useEffect`, since `react-hooks/set-state-in-effect` flags an unconditional `setState` call in an effect body — so a re-trip after a clear always shows the fresh countdown rather than a stale "resumed" announcement, and the countdown itself takes precedence over the announcement by construction.

## Server state (react-query)

`@tanstack/react-query` is the single server-state layer (roadmap X2.8). Reads move onto it one family at a time; a fetch lifecycle that has not moved yet stays on its hand-rolled path. On it today: the health family's two core reads — the app-wide health context (`HealthProvider`) and the health digest (`useHealthDigest`) — and the unblocker-activity read (`useUnblockerActivity`); the engine-resource family (`useEngineResource`: the repo-status and recurring-process summaries, the five engine ops tiles and the accent picker); the control-token lifecycle status read (`useControlTokenStatus`); the keyed document reads (`useProjectDoc`, `useEngineConfigDoc`, `useProjectEngineKey`, `useInvocationDocs`); the app-wide engine list (`useEngines`); the chat-session family (`useBuildChatSession`, `useExploreChatSession`, and the shared `useChatSessionGeneric` both are layered on); the workspace detail page's refresh (the workspace read and its invocation-list read, `useWorkspaceDetailQuery` / `useWorkspaceInvocationsQuery` / `useRefreshWorkspaceDetail`); the chat-draft rows (`useDraftRows` on the project page and `useRepoConversations` on the conversation rail, one shared scoped fetcher); the agent catalogue and its summary (`useAgentCatalogue`, `useAgentCatalogueSummary`); the project detail (`Project`) and projects list (`Projects`) loads; the workspace sticky instruction (`useStickyInstruction`) and dispatch-instruction readbacks (`useInstructionReadbacks`); the invocation graph's handovers, the invocation card's document (`useInvocationDoc`), the delivery summary and the workspace prep-chat transcript; and the chat-draft delete mutation (`useDeletableDraft`, through `useActionMutation`). Not on it: `useDriverLoops`, `useRepoHealthMetrics`, `useHomeData` and `useConnectStates` (the Home page's workspace/project list read and connect-resume read, which keep their stale guards), the connect wizard's readiness poll, the live stream panel, the node detail modal's per-tab fetches, and the auto-dispatch chain's cancellation token.

**Layout.** Everything that names the library lives in three modules under `alan/web/src/api/`:

- `queryClient.ts` — the single `queryClient`, a module singleton, plus the one `notifyManager.setScheduler(queueMicrotask)` call.
- `QueryProvider.tsx` — `<QueryClientProvider client={queryClient}>`, mounted once at the root of `App.tsx` outside `ServerEventsProvider`. It has no markup and no other responsibility.
- `queries.ts` — the only module that calls `useQuery` / `useQueryClient` / `useMutation`. Query keys are private constants here. Hooks are named for what they read (`useHealthQuery`, `useHealthDigestQuery`) and return the library's result unchanged, except `useEngineResourceQuery`, which returns the alan-owned `EngineQueryView<T>` projection (`data`, `isError`, `error`, `isFetching`, `isPlaceholderData`) — `query-lib-confined` forbids a `UseQueryResult` type crossing the module boundary, and building that object inside the hook is what marks `isFetching` and `isPlaceholderData` as tracked props; `useInvalidateHealthContext` / `useInvalidateHealthDigest` return a stable `() => void`, never a promise, because callers invoke them fire-and-forget.

**Explicit binding.** Every hook in `queries.ts` passes `queryClient` as the second argument to `useQuery` / `useQueryClient` instead of relying on context. The provider is still mounted (it starts the library's focus/online listeners and is what `renderWithQuery` wraps), but no consumer needs an ancestor. That is deliberate: tests such as `features/health/pages/HealthView.test.tsx` render `HealthProvider` bare, so a provider requirement would force a wrapper line into each of them. Because the client is a singleton shared by every test in a worker, `installIsolationResets()` calls `queryClient.clear()` after each test; without it a later test finds the previous test's cached read, the defaults below suppress the refetch, and every request-count assertion fails. `src/test/queryCacheIsolation.test.ts` is the residue pin for that reset.

**Client defaults.** Stock defaults break behaviour the health family depends on, so each is overridden and each has a test (`api/queries.defaults.test.tsx`):

| Default | Value | What it prevents |
| --- | --- | --- |
| `retry` | `false` | A failed read staying `pending` for ~7 s of backoff, which delays the paused-state reset after a health failure and makes the failure invisible for that long. |
| `networkMode` | `"always"` | Reads pausing while `navigator.onLine` is false. The service is on this machine; a browser that thinks it is offline can still reach it, and a paused read would keep a stale "queue paused" banner up. |
| `refetchOnMount` | `false` | A remount issuing a request the event bus did not ask for; `home-refetch-stability.spec.ts` asserts exact request counts on controls fed by the health context. |
| `refetchOnWindowFocus`, `refetchOnReconnect` | `false` | Focus and reconnect refetches the hand-rolled code never made. |
| `staleTime` | `Infinity` | Any read going stale on a timer. Freshness is driven by invalidation, never by age. |
| `placeholderData` | `keepPreviousData` | A keyed read collapsing to a pending placeholder when its key changes, which unmounts the refetching region and drops its busy indication. |
| `throwOnError` | `false` | A failed read throwing into render. |

`notifyManager.setScheduler(queueMicrotask)` replaces the library's default `setTimeout(0)` notification hop, so a settled read reaches its consumers in the same tick the hand-rolled `setState` did instead of one macrotask later; consumers that were tuned to the old latency keep their timing.

**Result props are tracked.** The library only re-renders a consumer when a property that consumer actually read changes. `HealthProvider` reads `data` and `isError`; `useHealthDigest` reads `data`, `isFetched` and `isError`. A test that asserts `isFetching` or `fetchStatus` must read it inside the hook callback, or the assertion sees a stale snapshot.

**The event bus is the invalidation source.** `useChangeRefetch("health", invalidate[, enabled])` from `ServerEventsProvider.tsx` stays the bridge, called from `HealthProvider.tsx` and `useHealthDigest.ts` (bucket `"health"`), from `useEngineResource.ts` (bucket `"engines"`, once per consumer) and from `useEnginesRefresh` in `useEngines.ts` (bucket `"engines"`, once for the whole app — see the engine-list section below) — never from `queries.ts`, so `useHealthQuery` stays bridge-free and the no-refetch-on-remount default is testable in isolation. Reusing it inherits its `document.hidden` guards and the 15 s disconnected fallback poll; the bus itself (connection handling, backoff, visibility, its other two namespaces) is unchanged. Every invalidation passes `exact: true` and `cancelRefetch: false`: the keys are disjoint (`["health","context"]`, `["health","digest"]`) so a health event does not double-fire the digest, and `useChangeRefetch` fires on mount, so a default (cancelling) invalidation would cancel and restart the query's own mount fetch and change the exact request counts the e2e specs assert.

**Health invariants that the types do not express:**

- On a failed health read the previously fetched values are retained, except `queuePaused` resets to `false` and `pausedUntil` to `null` (`_publish` in `HealthProvider.tsx`). The failure mode being avoided is a confidently wrong fleet status: a stale "queue paused" banner, or a real pause cleared, rather than a blank one.
- The paused-queue poll is `refetchInterval` on the health read: 5 s while `queue_paused` is true, `false` on error (the library retains data on error, so without the error branch a failed read would keep polling on the stale flag) and `false` otherwise. `refetchIntervalInBackground: true` on that read only preserves the old hidden-tab cadence, so `QueuePausedBanner` never shows an expired countdown on return. The one-second countdown ticker inside `QueuePausedBanner` initiates no fetch and is not part of this.
- A health change event triggers no fetch while the tab is hidden (`useChangeRefetch`'s guard). An explicit `refetch()` from the context still fetches.

**Known behaviour differences from the hand-rolled reads** (by construction; no payload renders differently):

- Re-render and mount timing differ. An identical payload no longer changes the published health context value, because structural sharing keeps `data` referentially identical.
- `useHealthDigest.error` after a failed first fetch reads `false` while the retry is in flight, where the hand-rolled hook held `true` until a fetch succeeded.
- Mounting `HealthProvider` in a hidden tab issues the observer's own mount fetch, where the hand-rolled provider fetched nothing until the tab became visible. `useHealthDigest(true)` does the same: its mount fetch is issued by the query observer whenever `enabled` is true, so it no longer depends on the bus and fires in a hidden tab, where the hand-rolled digest waited for `useChangeRefetch`'s visibility guard. Both are accepted: the hidden-tab clause is about health change *events*, which still trigger no fetch while hidden.
- `useHealthDigest.loaded` is now the query's `isFetched`, and the cache outlives the hook, so a remount that finds a cached digest reports `loaded: true` on its first render, where the hand-rolled hook always started `false` and flipped after its own fetch. The payload fields are unchanged.
- The health context's `refetch()` is now an exact, non-cancelling `invalidateQueries`, which refetches only active observers, where the hand-rolled callback fetched unconditionally. `HealthProvider` is mounted at the app root, so its observer is always active and the two are equivalent today; an invalidator called while no `useHealthQuery` observer is mounted would silently do nothing.
- `useEngines().loaded` is the query's `isFetched`, and the cache outlives the hook, so a remount that finds a cached engine list reports `loaded: true` on its first render, where the hand-rolled hook always started `false` (the same shape as `useHealthDigest`, above). It removes a loading flash and changes no payload.
- `useEngines().loadFailed` survives a remount the same way: a remount that finds a cached list left by a failed refetch reports `loadFailed: true` at first paint, where the hand-rolled flag started `false` and stayed so until its own fetch settled. The list is still the retained last-known one; `loaded` is `true` with it.
- Mounting `useEngines` in a hidden tab issues the query observer's own mount fetch (when nothing is cached), where the hand-rolled hook fetched nothing until the bus's visibility guard let `useChangeRefetch` fire. Same shape as `HealthProvider`, above; the hidden-tab clause is about change *events*, which still trigger no fetch while hidden.
- `structuralSharing: false` on the engine list re-renders every `useEngines` consumer on every engines tick even when the payload is identical. That is exactly the hand-rolled cost (every fetch called `setState` with a freshly parsed list), so it is not a new one.

**Engine-resource family.** `useEngineResource(resource, engineKey)` in `src/hooks/useEngineResource.ts` keeps its `EngineResourceState<T>` union (`loading` / `error` / `ready` with `refreshing` and `refreshError`) and `refetch`, so `RefreshCue.tsx` and the seven call sites are untouched; the fetch lifecycle underneath is `useEngineResourceQuery` and `useInvalidateEngineResource` in `queries.ts`. The Home page's workspace list and its connect-state fan-out are outside this family, and so is the app-wide engine list (`useEngines`, its own section below). `useConnectStates` reacts to the identity of the `engines` array, which default structural sharing would make stable across a tick that changes nothing; the engine-list change **preserved** that trigger rather than re-pointing it, via `structuralSharing: false` on `["engines","list"]`. Re-pointing would have edited `useConnectStates.ts`, which is out of that change's diff, and its own comment argues an independent `useChangeRefetch("engines", …)` is racier than reading `useEngines`' identity (it could fire before `useEngines`' own fetch resolves and strand the resume list on a stale engine list). This family, by contrast, **keeps** its per-consumer `"engines"` bridges: it is keyed per engine, so each bridge invalidates a different key; the bus is therefore not single-subscription in general, only for the engine list.

- **Key and registry.** The key is `["engine", resource, engineKey]` (`engineKey` is `null` while the query is disabled). `resource` is one of `engineConfig`, `pool`, `preflight`, `depSweep`, `onboarding`, `repoStatus`, `recurringStatus`, mapped in a private registry in `queries.ts` to its `api.*` fetcher and an optional `pollMs`. `engineConfig` is one resource because `PostureTile` and `AccentPicker` both read the full `EngineConfig`.
- **Adapter mapping, in this order.** `isPlaceholderData` → `loading`; no `data` and `isError` → `error`; no `data` → `loading`; otherwise `ready`, with `refreshing` from `isFetching`. `isPlaceholderData` is checked first because the client-wide `keepPreviousData` default would otherwise show one repository's counts under another's heading on a key change; checking it first scopes that default to same-key refetches, and a key change enters the `loading` arm. `data` is compared against `undefined`, never tested for falsiness, because `api.getEnginePreflight` legitimately resolves `null`.
- **`refreshError` reads `isError && !isFetching`.** The library keeps `status: "error"` while the next refetch is in flight, so the naive `isError` mapping would render `RefreshErrorLine` and `RefreshingLabel` together inside the same `aria-live` region; the hand-rolled loader cleared the error at the start of every refresh and this preserves that.
- **Three per-query overrides** of the client defaults, none of which touches `queryClient.ts`: `staleTime: 0` and `refetchOnMount: "always"` (an engine A → B → A switch or a remount must refetch, or the five unpolled tiles would show stale data with no cue), and `refetchInterval: 60_000` with `refetchIntervalInBackground: true` on `repoStatus` and `recurringStatus` only (the hand-rolled `setInterval` kept firing in a hidden tab, and the library pauses interval polling there unless told otherwise).
- **Invalidation** is the bridge described above: `useChangeRefetch("engines", refetch, engineKey !== null)` calls `useInvalidateEngineResource`, which is exact and non-cancelling. The query's own mount fetch and the bridge's mount invalidation therefore join into one request.
- **Intended request-count drops.** `recurring-status` is now one request per invalidation across `RepoStatusStrip` and `RecurringProcessesPanel` (they share the `["engine", "recurringStatus", engineKey]` entry; each fetched independently before, and a request-count baseline on the health page will read 1 where it read 2). `GET /api/engines/{owner}/{repo}` is one request shared by `PostureTile` and `AccentPicker` on `RepoEngineConfig`, where each fetched separately before. The `RecurringProcessesPanel` comment that documented the old independent-fetch contract is deleted with this change.

**Engine list.** `useEngines()` in `src/hooks/useEngines.ts` keeps its eight-member `UseEnginesResult` (`engines`, `hiddenEngines`, `hiddenCount`, `hiddenEngineKeys`, `allEngines`, `hasNonDefaultEngine`, `loaded`, `loadFailed`) with the same names and types; no consuming page or component reads it differently. The fetch lifecycle underneath is `useEnginesListQuery` and `useInvalidateEnginesList` in `queries.ts`; the hand-rolled `useState` triple, the mounted-ref stale guard and the in-hook `useChangeRefetch` are gone. The key is `["engines","list"]` and the fetcher is the existing `api.listEngines`. The four derived memos (visible list, hidden list, hidden keys, `hasNonDefaultEngine`) are unchanged.

- **One override, two identity axes, one mechanism.** `structuralSharing: false` is the only departure from the client defaults, and it serves two requirements that pull in opposite directions. *Axis A:* the derived visible-only list must keep its reference across a render that fetched nothing, or downstream memo/effect chains re-ignite in a loop; that holds because `allEngines` is the query's `data` (referentially stable between fetches) or a module-level empty-array constant before the first fetch (`data ?? []` inline would hand out a new array every pre-load render), and the memos hang off it. No `select` is used. *Axis B:* the list must get a **fresh** reference on every successful fetch, even for a byte-identical payload, because `features/home/hooks/useConnectStates.ts` uses that identity change as its only subscription to the `"engines"` stream. Several event kinds routed into that bucket (`secret_written`, `preflight_completed`, `dep_sweep_changed`, `repo_status_refreshed`, `recurring_status_refreshed`, `pool_lifecycle_changed`, see `_ENGINE_KINDS` in `alan/routes/events.py`) do not change the `listEngines()` payload at all, and `secret_written` is precisely the event whose purpose is to re-run the connect-state fan-out; default structural sharing returns the previous reference for deep-equal data and would silence every one of them. Nothing else can satisfy both axes, so they are one clause pair: a change that removes the override fails the axis-B tests, and a change that fixes axis B by handing out a new list per render fails the axis-A tests.
- **Status mapping.** `loaded` is `isFetched`, so a failed fetch still counts as settled and a consumer gating its blank-slate branch on it (Home) is never pinned in loading. `loadFailed` is `isError`, **or** no list has ever been fetched and at least one fetch has failed (`data === undefined && errorUpdateCount > 0`). The second clause exists because the library resets `status` to `pending` (clearing `isError`) when a fetch starts on a query that has no data, so a recovery fetch after a *first* failure would otherwise flip the flag to `false` mid-flight and render "confirmed zero engines" in place of "fetch failed" — the two states must never render the same. After a failure that followed a good list the library keeps `status: "error"` while the next fetch is in flight, which is what today's success-arm-only clearing did. Do **not** copy `useEngineResource`'s `isError && !isFetching`: it clears the flag mid-refetch.
- **No retry.** `retry: false` is the client default and is not overridden; stock retry would pin Home's blank-slate branch through the backoff. A single failure settles immediately.
- **Client defaults inherited, not the engine-resource overrides.** `staleTime` stays `Infinity` and `refetchOnMount` stays `false`. `staleTime: 0` / `refetchOnMount: "always"` exist in the engine-resource family for A → B → A key switching that a single static key does not have, and they would let any consumer mounting anywhere refetch the shared entry — which, with `structuralSharing: false`, hands every other consumer a new list identity.
- **One bus subscription, hoisted.** `useEnginesRefresh()` (exported from `useEngines.ts`) is `useChangeRefetch("engines", useInvalidateEnginesList())` and is called by exactly one component: `EnginesRefresh` in `App.tsx`, rendered inside `Shell`, which is inside `ServerEventsProvider` (a render outside it would read the context default, `connected: false` and no counters, and poll instead of following the bus). `useEngines()` alone registers no subscription. Thirteen per-consumer bridges plus `structuralSharing: false` would make every consumer mount a fresh-identity event: opening the command palette on a repo page (`CommandPaletteProvider` renders `CommandPalette`, which calls `useEngines()`, conditionally) would re-fire `useConnectStates`' N-engine secrets-and-readiness fan-out, and while the bus is disconnected the 15 s fallback poll of thirteen out-of-phase consumers would fire up to thirteen fan-outs per window instead of one. The engine-resource bridges are correct per consumer *there* because that family is keyed per engine; `useEngines` has one static key, so thirteen bridges would be thirteen copies of one subscription. The invalidation is exact and non-cancelling like the others, so the bridge's mount invalidation joins the observer's mount fetch.
- **Always-active observer.** `useInvalidateExact` refetches only active observers. `ShellShortcuts` and `Shell` in `App.tsx` both call `useEngines()` and are mounted for the app's whole life, so the engine-list observer is always active; an invalidation while no `useEngines` observer is mounted would silently do nothing.
- **Intended request-count drop.** Thirteen independent list requests on load (one per `useEngines` call site) collapse to one shared request per fetch, and to one refetch per tick. No end-to-end spec counted requests on the engine-list endpoint (they only stub the route; counting is confined to per-engine endpoints), so no spec changes.
- **Tests.** `useEngines.test.ts` drives two successive successful fetches with deep-equal but distinct payloads and asserts on the derived visible list (`not.toBe`, `toEqual`), and a re-render with no refetch (`toBe`); removing `structuralSharing: false` turns the first red. `App.test.tsx` asserts one engine-list request on load with every shell and page consumer mounted, no request and no new fan-out when the command palette mounts, and a fan-out re-run on a byte-identical `"engines"` tick. Scoped script: `npm run test:x28-engine-list`. `serverState.drift.test.ts` additionally pins `useEngines.ts` free of `useState`, `useEffect` and `mountedRef`.

**Control-token status.** `useControlTokenStatus()` in `src/hooks/useControlTokenStatus.ts` is a thin adapter over `useControlTokenStatusQuery` and `useSetControlTokenStatus` in `queries.ts`. Its result is `{ status: ControlTokenStatus | null, error: boolean, applyStatus }`; `ControlTokenSection` is the only consumer and reads exactly those three. The former `refetch` member is removed, not ported — nothing in production called it. The key is `["control-token", "status"]` and the fetcher is the existing `api.getControlTokenStatus`; `CONTROL_TOKEN_STATUS_POLL_MS` (30 s) is exported from `queries.ts`.

- **Five per-query overrides**, none of which touches `queryClient.ts`. The endpoint exists so an expired or revoked credential stays legible, and a cached "active" reading of a credential that has since died is a false-reassurance state — worse than an error, which at least renders as one. Each override therefore departs from a client default:
  - `staleTime: 0` (default `Infinity`) and `refetchOnMount: "always"` (default `false`): Settings is opened and closed repeatedly, and every open must fetch, exactly as the hand-rolled hook did on every mount.
  - `refetchInterval: 30_000` with `refetchIntervalInBackground: true`: the hand-rolled `setInterval` ignored focus, and the library pauses interval polling in an unfocused window unless told otherwise — exactly when a token expires unattended.
  - `gcTime: 0` (default five minutes): `serverStatusText` ignores the error flag whenever `status` is non-null, so a cache entry that outlived its observer would render a cached "active" line on a reopen whose fetch then fails. With no observer the entry is dropped, so a reopen starts from `null` and a failed fetch renders the unreachable-server message.
- **`applyStatus` is `setQueryData`.** A caller that has just mutated the token (extend, rotate, revoke) already holds the server's fresh `ControlTokenStatusResponse`; `useSetControlTokenStatus` writes it straight into the query cache, so the section shows it immediately, with no further status GET and without waiting for the next poll tick. It lives in `queries.ts` because `useQueryClient` may only be called there.
- **Invariant.** A failed refetch retains `data` and sets `isError`, so the last known status stays on screen while `error` is `true`; the next successful fetch, or an `applyStatus`, clears the flag.
- **The seed write never creates the entry.** `useSetControlTokenStatus` writes only while the query exists. `setQueryData` on a missing key rebuilds it with the client's default five-minute `gcTime`, not the read's `gcTime: 0`, so a mutation resolving after `ControlTokenSection` unmounted and its entry was collected would leave a cached reading that a later Settings open renders even when its forced fetch fails. Dropping the write once the entry is gone matches what the removed unmount guard did.
- **Behaviour delta** (by construction; nothing renders differently): `applyStatus` after a failed poll now clears `error`, because the cache write moves the query to `success`. The hand-rolled `applyStatus` left `error` set until the next poll succeeded.

**Document family.** Four keyed one-shot reads moved onto `useDocQuery(namespace, key, fetch)` and `useResetDoc(namespace, key)` in `queries.ts`: `useProjectDoc` (`"project"`, `api.getProjectDoc`), `useEngineConfigDoc` (`"engine-config"`, the composite config-plus-sources fetcher), `useProjectEngineKey` (`"project-engine"`, `api.getProject`, extracted from the body of `features/engine/pages/EngineConfigEditor.tsx` unchanged in shape) and `useInvocationDocs` (`"invocations"`, the workspace document fan-out). The shared loader `hooks/useKeyedResourceDoc.ts` is deleted; nothing else imported it. Each adapter keeps its exported result union and its `refetch`, so `Project.tsx`, `RepoEngineConfig.tsx`, `Workspace.tsx` and the four modules that import `DocsState` as a type are not touched.

- **Key.** `["doc", namespace, key]`, with `null` standing in for an undefined key (the read is disabled). Beside the engine family's `["engine", resource, engineKey]` this is the only other key shape in `queries.ts`. The namespace is what keeps two endpoints that share an id apart: `"project"` (`GET /api/projects/{id}/doc`) and `"project-engine"` (`GET /api/projects/{id}`) both take a project id and cache different payloads.
- **View.** `DocQueryView<T>` projects `data`, `isError` and `error` only — never `isFetching` or `isPlaceholderData`. With the placeholder opted out `isPlaceholderData` is permanently `false`, so projecting it would add an arm no test can reach. Every adapter reduces to one shape: `isError` → `error`, `data === undefined` → `loading`, otherwise `ready`. A disabled read is pending with idle fetch status and `undefined` data, so a route that has not resolved its id yet lands on `loading`, never `error`, with no extra branch.
- **Four per-read overrides**, none of which touches `queryClient.ts` or `queries.defaults.test.tsx`. Each read must land on its loading state and issue a fresh read on both mount and key change, exactly as the hand-rolled hooks did (they reset on every key change and refetched on every mount), and the client defaults would break both:
  - `placeholderData: NO_PLACEHOLDER` (default `keepPreviousData`): a key change would render the previous key's document under the new key — on `RepoEngineConfig`, one repository's configuration under another repository's URL, and on `EngineConfigEditor` a redirect to the previous project's destination. `NO_PLACEHOLDER` is the function form `() => undefined` because `exactOptionalPropertyTypes` makes an explicit `placeholderData: undefined` a type error; a function that returns `undefined` is what the client's plain-spread merge accepts. Contrast `refetchOnReconnect`, `throwOnError` and `networkMode`, which have explicit undefined fallbacks in the library, so an undefined override silently reverts to the default.
  - `gcTime: 0` (default five minutes) is the remount defence: without it a remount inside the retention window finds the finished entry and renders it as `ready` before its refetch lands, and an A → B → A key switch shows A's old document. With no observer the entry is dropped after one zero-delay timer, so a remount or a revisit starts from `loading`.
  - `staleTime: 0` (default `Infinity`) and `refetchOnMount: "always"` (default `false`): the fresh read itself. `staleTime` decides whether a key change fetches an entry that still exists, `refetchOnMount` whether a mount does. They only matter in the window before the gc timer fires, which is why `gcTime: 0` alone does not make them redundant in tests. The window is a single macrotask; a real user cannot land in it, and a landing there renders the cached document and immediately refetches rather than rendering `loading`.
- **Refresh resets, it does not invalidate.** `useResetDoc` calls `resetQueries({ queryKey, exact: true })`, not the `useInvalidateExact` helper the health and engine families use. These reads are not on the server-event bus, so nothing bridges a silent background refresh into the UI; the landing on `loading` is the user feedback that a re-read is under way. `invalidateQueries` would keep a `ready` or `empty` document rendered, and keep `isError` true during an error retry — silently changing `RepoEngineConfig`'s retry button. `resetQueries` returns the entry to its initial state, so a refresh from `ready`, `empty` and `error` alike lands on `loading`. Like the invalidators it returns a stable `() => void`, and it is a no-op for an unmounted key.
- **`useEngineConfigDoc` stays one query.** The 404 → `{ kind: "missing" }` branch (never registered as an engine, surfaced as `empty`, never `error`) and the `api.getEngineSources().catch(() => null)` degrade to an unknown `source` both live inside the one fetcher. Two queries would need the degrade and the single refresh affordance coordinated, which is a hand-rolled gate by another name.
- **The invocation set loads as one unit.** `useInvocationDocs` keys one query by `${taskId}|${invIds.join(",")}`, and its fetcher is the per-invocation `Promise.all` with each item's own catch, so a failed document lands in the `errors` map and never fails the set. Per-invocation keys would let unchanged members keep their observers and resolve instantly across an id-list change, which loses the reset-to-empty the consumers depend on. Per-document cache sharing is given up deliberately, and a gate that suppresses results until every read settles was rejected as a hand-rolled coordination primitive. The loading arm returns one module-level `DocsState` constant so `InvocationGraph` and `TaskInvocationSection` do not see a fresh `Map` each render.
- **Tests.** `hooks/docReadDefaults.test.tsx` runs one `describe.each` over the four reads with a named case per override; each of the four overrides was removed in turn and a distinct case went red. It asserts through the reads' own results and fetch counts, never through the library, and `test/docReadHarness.ts` supplies `flushGc` (one macrotask, so the zero-delay gc timer has fired) and `deferredFetch` (a gate that holds a response so the loading arm is observable). Scoped scripts: `npm run test:doc-read-hooks` and `npm run test:doc-read-pages`.
- **Deferred.** Two inline reads of the same shape stay hand-written on purpose — the one in `Project.tsx`'s body that duplicates the `useProjectDoc` call above it, and `useHandovers` in `InvocationGraph.tsx`, which uses the same joined-key idiom as the fan-out — as does the error-banner consolidation on the workspace page. Stale-then-refresh as a product behaviour would be its own change with its own before-and-after.

**Placement is enforced two ways.** `alan/web/.dependency-cruiser.cjs`'s `query-lib-confined` rule fails `lint:deps` when any module outside `src/api/{queryClient.ts,QueryProvider.tsx,queries.ts}` and `src/test/` imports `@tanstack/*`. `alan/web/eslint.config.js` forbids calls to the library's hooks (`no-restricted-syntax`, scoped to `src/**/*.{ts,tsx}` with `src/api/queries.ts` ignored). Dependency-cruiser resolves module edges, not symbols, so both are needed. ESLint flat config replaces a rule entry rather than merging it, so the same selector is repeated in the `src/**/*.test.{ts,tsx}` + `src/test/**` block that carries the wall-clock-timer selectors — the query block must precede that block, and `src/test/lintRules.test.ts` asserts the timer selectors survive. The half of the rule that confines query hooks to a feature directory depends on a directory a later item creates and is not enforced yet.

**Feature folders are closed to inbound imports.** `.dependency-cruiser.cjs`'s `feature-inbound` rule (severity `error`) fails `lint:deps` when a production module outside `src/features/` imports anything under it. Allowed importers are `src/App.tsx`, `src/main.tsx`, test files and `src/test/`, plus the from→to pairs in `FEATURE_INBOUND_EXCEPTIONS`, today exactly one: `components/ConnectUnboundNotice.tsx` → `features/connect/pages/connectStep4PostureLogic.ts` (its `UnboundReason` type). An exception names one edge, not one importer: a companion entry under the same rule name fails any other feature import from the excepted file. Setting `DEPCRUISE_NO_FEATURE_EXCEPTIONS` empties the list, which is a local check against the real tree; the standing proof that the rule fires is `src/test/featureRules.test.ts` (`npm run test:feature-rules`). `query-lib-confined` is unchanged; the feature-directory half of query placement is still not enforced.

**Feature folders are closed to each other.** `.dependency-cruiser.cjs`'s `feature-cross` rule (severity `error`) fails `lint:deps` when a module inside one feature folder imports from a different feature folder. A module's feature is the first folder under `src/features/` that contains it: same-feature imports are allowed, and an import that crosses into any other feature folder is forbidden. Test files inside a feature are covered — the rule draws no exception for them. There is no exception mechanism today; the chat ← workspace exception the architecture plan expected was never needed — both features have now moved (`src/features/chat/`, `src/features/workspace/`) and neither imports the other. `src/test/featureRules.test.ts` loads the committed `forbidden` list through dependency-cruiser's own config loader (`extractDepcruiseConfig`), cruises a small planted tree from its symlink-free realpath, and asserts that both `feature-cross` and the general `feature-inbound` rule report at `error` — deleting, downgrading or breaking either rule turns this test red. It evaluates only the rule list, never the configuration's `options`. Known gap: nothing proves the per-exception companion rules that confine each excepted importer (`FEATURE_INBOUND_EXCEPTIONS`) to its one named target; that gap closes as the exceptions list drains to zero while features move.

**Measurement guard.** `src/serverState.drift.test.ts` fixes how the item's counts are measured — production `.ts`/`.tsx` under `src/`, excluding `*.test.*` and `src/test/` — and asserts tightening-only upper bounds, each set to the value measured at the PR head and never raised: effect sites (`useEffect(` lines) ≤ 58; fetch-polling intervals (`setInterval(` sites minus the named non-poll holder `components/QueuePausedBanner.tsx`, the queue-pause countdown clock) ≤ 1, with the disconnected-SSE fallback in `api/ServerEventsProvider.tsx` the only polling interval left (the conversation rail's hand-rolled interval became a `refetchInterval`, and a separate test pins the holder's file name); stale-guard declarations (`let cancelled|ignore = false`) ≤ 3; and busy-state setter twins (distinct file/`set[A-Z]…` pairs called with both `(true)` and `(false)` in non-component `.ts` modules) ≤ 13. Scoped scripts: `npm run test:x28-drift` (the guard), `test:x28-workspace-detail`, `test:x28-drafts` and `test:x28-reads`.

**Refresh, polling and mutation semantics (PR-2g).** These are the invariants the remaining-reads migration keeps; the hooks are in `queries.ts`.

- **Workspace epoch.** `useWorkspaceDetailQuery` reads the workspace query's `dataUpdateCount` (through `getQueryState`) as an `epoch`, and the invocation list is keyed `["workspace-invocations", taskId, epoch]`. Every successful workspace read therefore starts a new list query, which reproduces the old page's behaviour exactly: the invocation list empties for a moment on each live refresh and the invocation documents (and so invocation-level status) refetch. The counter does not move on a failed read and does not depend on the clock, so two refreshes landing in the same millisecond still get distinct epochs. The workspace query sets `structuralSharing: false` (each refresh hands out a fresh `ws`, as `setWs(detail)` did), `notifyOnChangeProps: "all"` (so a refresh that resolves to the very same object still re-reads the epoch) and `gcTime: 0` with no placeholder, so a task switch shows the loading state rather than the previous task. The list is enabled only for a non-triage workspace.
- **Cancel-then-refetch refresh.** `useRefreshWorkspaceDetail` synchronously `cancelQueries` (with revert) on the `["workspace-invocations", taskId]` prefix and on the exact workspace key, then `refetchQueries` the workspace key. `cancelRefetch: true` alone is not enough: query-core cancels an in-flight fetch only when the query already holds data, so a refresh arriving during the first load would merge into it and surface that load's stale rejection. Cancelling the list prefix means a superseded list that resolves late is discarded and can never start document fetches. A failed refresh keeps the query's data but reports `isError`, which the page turns into the load alert exactly as before; a list error surfaces through the same alert.
- **`useRefetchDoc`.** Returns a stable `() => void` that invalidates its exact doc key with `cancelRefetch: true`: it merges into a first load that is still running (no double mount request) and replaces an in-flight fetch once data exists, keeping the newest-wins semantics of the hand-rolled generation counters. The unblocker-activity health-bus refetch and the rail's active-session refetch use it. `useSetDocData` writes a loaded entry in place with no network call and never creates an entry for a key that was not loaded.
- **Visibility-paused polling.** `useDocQuery` takes an optional `pollMs` that becomes `refetchInterval` with `refetchIntervalInBackground: false`, so the poll stops while `document.visibilityState` is `"hidden"` (the library's focus manager reads it) — the same pause the rail's old `document.hidden` guard gave. The conversation rail polls at `FALLBACK_POLL_MS`; tests stub `document.visibilityState`, never the focus manager.
- **Mutate-callback unmount rule.** `useActionMutation` runs its action through `useMutation` with `networkMode: "always"` and takes its callbacks at `run(...)` time (mutate-level), because the library skips mutate-level callbacks once the component has unmounted: a delete that finishes after the user has left neither navigates them anywhere nor reports an error. `useDeletableDraft` holds its busy state through success (`isPending || isSuccess`) until the caller removes the draft, and clears it on failure.
- **Unblocker activity.** `useUnblockerActivity` keys its read by engine (`default` for the fleet, `engine:<key>` for a repo). A failed refresh keeps the last good snapshot with `error: true`; an engine change drops to not-loaded and never shows another engine's snapshot.

**Chat-session family.** Build-chat and explore-chat's session reads (`useBuildChatSession`, `useExploreChatSession`, both layered on the shared `useChatSessionGeneric`) share one query family keyed `["chat-session", family, sessionId]` (`family` is `"build"` or `"explore"`) via `useChatSessionQuery`, `fetchChatSession` and `useInvalidateChatSession` in `queries.ts`. Before this family moved, opening a conversation issued two identical `GET /sessions/{id}` reads — one from the family hook's own repository-binding lookup (`useSessionBinding` / `useEngineKeyBinding`), one from the session loader inside `useChatSessionGeneric`; both now resolve through the same cache key and coalesce into one request via the library's own in-flight dedup.

- **Injected fetcher, not a hard-wired endpoint.** `useChatSessionQuery`/`fetchChatSession` take the caller's `get: (id) => Promise<...>` rather than calling `api.*` directly; `family` supplies only the cache key. This keeps `useChatSessionGeneric` testable through a stub `ChatSessionApi` and lets `useBuildChatSession`/`useExploreChatSession` each derive their own repository binding off the identical query the generic hook also reads, without sharing a code path — only a shared cache entry.
- **The cached snapshot excludes messages and the brief.** `useChatSessionQuery`'s `select` projects only `runSummary`, `collisionRunSummary`, `projectId`, `repoProvision` and `engineKey` (`ChatSessionSnapshot`) — never `messages`, `brief` or `in_flight_turn`. Both excluded fields are written locally by a path the server has not observed: messages are appended optimistically on send, and the brief is set by `summarize()`/`updateBrief()`. A cache re-read that clobbered either would undo that optimism the next time the query refetches; excluding them from the query's own projected type makes the omission structural rather than a convention a later change could quietly break. `fetchChatSession` still resolves the full wire response (through the same key, joining the observer's in-flight fetch) for the one-time session load, where messages/brief/`in_flight_turn` are consumed directly from the resolved promise into local state — never read back out of the query cache.
- **A binding reports unresolved only when it has never read successfully.** `useSessionBinding` (build) and `useEngineKeyBinding` (explore) compute `engineKey` as `isError && data === undefined ? null : data?.engineKey` — `null` only when the query has never once resolved; a failed *background* refresh after an earlier success keeps the last known binding, since the cached `data` from that success is retained. Sharing the cache key with `useChatSessionGeneric`'s own snapshot read means a server error on the post-turn refresh — today silently swallowed — cannot flip the binding to an error state and make the repository badge vanish or break "clear and start over" mid-conversation.
- **`placeholderData: NO_PLACEHOLDER` is mandatory, not the client's `keepPreviousData` default.** `useChatEngineSelfCorrect` redirects on any non-null `engineKey` mismatch against the URL's scoped repository; `keepPreviousData` would hand a previous session's `engineKey` to it across a session-id change, before the new session's own read has resolved, and trip a spurious redirect.
- **`clear()` invalidates nothing and resets no query.** `useChatComposerActions.ts` runs `clear().then(onCleared)`, batching the session-id change and the resulting query-key change (`["chat-session", family, newSessionId]`) into one render; a `resetQueries`/`invalidateQueries` call on the *old* key would refetch an entry for a session `clear()` just deleted, 404, and — since the binding treats a never-succeeded read as unresolved — flash the unresolved-repository notice for a session that no longer exists.
- **Polling moved into the query.** The `repo_provision === "pending"` 1500 ms poll that used to run as a hand-rolled `setInterval` effect inside `useChatSessionGeneric` is now `refetchInterval` on the same query (`q.state.data?.repo_provision === "pending" ? 1500 : false`, `refetchIntervalInBackground: true`, no error guard on the predicate — a failed background tick keeps the interval running rather than silently stopping it on a stale "pending" read, matching what the old poll effect did).

## Agent catalogue and the run launch view

The screen at `/repos/:owner/:repo/agents` (`features/engine/pages/RepoAgents.tsx`, a child route of `RepoShell` in `App.tsx`) renders the backend's per-repository agent catalogue (`GET /api/engines/{owner}/{repo}/agents`, see [agent_catalogue.md](agent_catalogue.md)); the engine configuration page links to it through `AgentCatalogueTile` (`.../agents/summary`) in the place the roles list and the prompt-overrides section used to occupy. The screen is read-only: nothing on it, in the tile or in the run view can edit a model, effort, prompt or setting, and the flags the backend raises are displayed, never corrected.

- **Data.** `useAgentCatalogue(engineKey)` and `useAgentCatalogueSummary(engineKey)` (`features/engine/hooks/useAgentCatalogue.ts`) are two more `useDocQuery` namespaces (`"agent-catalogue"`, `"agent-catalogue-summary"`), so the document family's overrides apply: no placeholder across a key change, `gcTime: 0`, a fresh read on every mount, and `useResetDoc` on retry lands on `loading`. The result is `loading | error (message, refetch) | ready (data, refetch)`. The page shows loading, an `ErrorBanner` with a Retry button, and — when the filters leave nothing — a no-match panel with a clear action that resets every URL key.
- **Search is pure and client-side** (`lib/agentSearch.ts`). One trimmed, case-insensitive, non-overlapping substring matcher serves the agent name, id, model, effort and the **full prompt text**; the per-prompt count shown on a row is the number of occurrences in that plain text, and `AgentPromptViewer` highlights ranges computed from the very same string (`promptPlainText`: text segments verbatim, each run-time placeholder as `{{LABEL}}`), so the count and the highlights can never disagree. The filters match the displayed model and effort (`CLI default` is a real option) and the agent kind (`team_role`, `chat`, `background_helper`, `operator_launched`). The result count (`Showing N of M agents`) is a `role="status"` `aria-live="polite"` region updated on every keystroke.
- **URL is the state.** `q`, `agent`, `model`, `effort` and `kind` are kept in the query string through `useSearchParams` with `replace`, so a bookmark or shared link restores the search, the filters and the expanded row; an empty value or an unknown `kind` is read as absent rather than filtering everything away. Only the search text also lives in local component state (seeded from `q` once): the field is the source of truth for what the reader typed and the URL follows it, so the input's value never waits on a router navigation committing. One agent is expanded at a time (`agent=<id>`, the id being the backend's `AgentKey.id`).
- **Rows** use the controlled `Disclosure` `row` preset (`open` from the `agent` key, `onOpenChange` writing it) with a `flex-wrap` label span — name, kind, `model · effort`, an "overridden" chip, a "N flagged" chip and, while a search is active, "N matches in prompt". No new preset was added. The body mounts only while the row is open, so a catalogue of sixty-odd long prompts costs nothing until one is expanded. The body shows when the agent runs, scope and tag chips, any resolver error, the flags, the appended system prompt, the first-user-message template and the launch setup.
- **`AgentPromptViewer`** (`components/`) renders a prompt as plain read-only text in one `<pre>` — never through markdown — with `<mark>` highlights, Previous/Next match buttons that wrap around, a polite "Match i of n" status, and a Copy button that copies the plain text (without the shared-block labels, which are `select-none`) and reports "Copied" or a failure. Run-time placeholders appear as `{{LABEL}}` chips; a legend below lists each placeholder's description and each shared block, and a shared block is also labelled inline (`[shared block: terseness_block]`). It never scrolls on its own: the current match is scrolled into view by a callback ref only after the reader has pressed Next or Previous. That is deliberate — `serverState.drift.test.ts` caps `useEffect(` sites at 58 and the viewer needs none. The same component shows the first-user-message template (no search) and, in the run view, the resolved prompt.
- **`LaunchSetupList`** (`components/`) is the one definition of a complete launch: thirteen fields in a fixed order — model, effort, turn limit, permission mode, stored / effective / denied tools, extra directories, session, working directory, timeouts, environment (names and categories only), and process priority and detachment. `entryLaunchValues(entry)` feeds it from a catalogue entry (model and effort with their source, an explicit "CLI default" with no source chip when alan passes none, adaptive-budget and conditional-directory notes); `recordLaunchValues(record)` feeds it from a run's recorded launch; `notRecordedLaunchValues()` fills every run field with "not recorded for this run". The run view omits only the stored-tools field, which a launch record does not carry.
- **Page-level notes** come straight from the response: `notes.appended_prompt` (every text is appended to Claude Code's own built-in system prompt, which is not reproduced) and `notes.inherited` (user-level settings, the repository guidance file Claude Code loads from the working directory, user-level permissions, hooks, MCP servers and plugins — **named only; their contents are neither read nor shown**). Catalogue-wide flags (for example an unread stored role) render above the list, and each row carries its own.
- **Run view.** `NodeDetailModal` reads the node config document, whose optional `launch` is the recorded launch. The Prompt tab shows `launch.prompt_segments` — the role prompt, the turn-budget line and every appended tail block — through `AgentPromptViewer`, then the first user message. The Config tab shows `LaunchSetupList` with the values the CLI actually received (the effort included), then a "recorded at step start" block holding the adaptive-ceiling row and the stored (pre-narrowing) allowed tools. A record with no `launch` — everything written before the launch was recorded — shows "not recorded for this run" for the resolved prompt and for every launch field, and its flat `system_prompt`, `model`, `max_turns`, `permission_mode` and `allowed_tools` appear only under explicit "recorded when the step started" and "(recorded)" / "(stored)" labels; no value is ever guessed from them.

## Chat-session state (chat session state onto a reducer)

`useChatSessionGeneric.ts` (shared by `useBuildChatSession`/`useExploreChatSession`, and so by both the Build and Explore chat pages) reads its turn state from `chatSessionReducer.ts`, a pure reducer with two discriminants instead of the four independent flags (`status`, `isAssistantThinking`, `error`, `archivedTaskId`) it used to expose:

- `ChatSession` — `loading | ready | load_failed | archived{archivedTaskId}` — which the page/panel layer reads through `archivedTaskIdOf(session)`.
- `ChatTurn` — `idle | running{notice} | failed{error}` — read through `isTurnRunning(turn)` (thinking indicator, Stop availability, the two pages' `useStickToBottom` inputs) and `chatErrorOf(turn)` (the one error-banner surface: `running`'s `notice` and `failed`'s `error` are the only two sources of banner text). A transport-level stream error (the SSE connection's own `onError`, not a `"error"` chat event) attaches as a `notice` on a still-`running` turn rather than ending it, matching the pre-reducer behaviour where a raw stream error set `error` without touching `isAssistantThinking`; the same handler fails an `idle` or already-`failed` turn outright, since there is no running turn left to attach a notice to. A load failure sets `session = load_failed` and `turn = failed{message}` together; sending on a `load_failed` session still works (the send clears the turn's error and starts a `running` turn) because `sendMessage` only reads `turn`, never `session`, to decide whether to send directly or queue.

**Single write path.** The hook holds exactly one `useRef` — a snapshot of the latest reducer state — behind one stable `apply(action)` callback that runs the pure reducer, assigns the ref, and publishes via `setState`. Reading `stateRef.current` synchronously (rather than through the `state` closed over by a stale render) is what lets two `sendMessage` calls issued in the same tick see each other: the first send's `apply` call updates the ref before the second call's `isTurnRunning` check runs, so the second is queued instead of both racing to send. The same synchronous read is why `sendMessage`'s promise-reject-on-409 contract survives the rewrite unchanged: `useProposePrefetch.ts`'s `runAfterLockRelease` retries a composer send only on a *rejected* promise, so `sendMessage` must still throw on a direct-send failure rather than resolve early.

**Flush and retry.** A message sent while a turn is `running` is queued (`queuedMessage`); the load effect's own closure — not a ref — flushes it once the turn ends (`assistant_done` or the SSE `"error"` event; a `turn_stopped` deliberately does not flush, restoring the draft instead). The user-facing transcript row for a queued message is appended exactly once, when the flush starts, never again on a retry: a 409 during a flush attempt schedules a backoff (turn goes back to `idle`, `queuedMessage` reappears so the queued-indicator returns) and the retry re-enters the `running` turn without re-appending the message. Retry timers, the flush's local attempt counter, and the cancellation/staleness checks (an id comparison against the current reducer state) live as plain local variables inside the load effect's closure, cleared on its cleanup — not in a ref — so `cancelQueued()` and unmount both stop a pending retry by construction rather than by a mutable side channel.

**Effect count.** The hook now has one `useEffect` (session load, subscribe, and flush bookkeeping) instead of two: the second effect that used to exist purely to keep a ref in sync with the latest `binding` (avoiding a stale closure without re-running the load-and-subscribe cycle on every unrelated `binding` identity change) is replaced by a `useEffectEvent`, called only from inside the load effect.

## Bulk actions (removed)

`alan/web/src/components/BulkActionBar.tsx` and `alan/web/src/bulkDrain.ts` are deleted
(remove-inbox-from-web-ui) — Inbox's bulk-acknowledge was their only real caller (the "single
bulk-action surface for the whole app" claim this section used to make was already stale before this
change: no workspace-list bulk archive/unarchive/stop/resume surface using them ever shipped). The
serial-drain rationale (never `Promise.all`/`allSettled`, since concurrent mutations against the same
workspace/incident queue race the backend's non-atomic disposition read-modify-write) dies with it —
nothing in this codebase performs a client-driven bulk mutation loop today.

`alan/web/src/workspaceBulkOps.ts` holds the workspace-list-specific policy: `isEligible(status, op)` is a pure client-side mirror of the server's per-operation eligibility (stop needs `active`, resume accepts `paused` or `awaiting_input`, archive accepts anything but `archived`, unarchive needs `archived`) — an optimisation over a server that stays authoritative, not a redefinition of what any operation means. `OPS_FOR_TAB` maps the active tab to `["archive", "stop", "resume"]` and the archived tab to `["unarchive"]`. `summarizeBulk(op, tally)` renders the plain-language batch report (`"stopped 6, skipped 4 (not running)"`, `"archived 8"`).

`alan/web/src/useWorkspaceBulk.ts` wires selection state to the drain: it intersects `selected` against the *currently visible* (project-filtered) rows before partitioning by `isEligible`, seeds the tally with the pre-filtered skips, and classifies a caught `ApiError` (see below) with `status` 404 or 409 as `"skipped"` — every other status (or non-`ApiError`) is a `"failed"`, since a `WorkspaceSummary` row doesn't carry the `has_running_job` / `has_resumable_failed_job` detail the single-workspace page uses, so a server-side rejection is only knowable from the response status. It calls the passed-in `reload()` in `.finally()` so the list reflects the batch's outcome deterministically rather than waiting on SSE delivery.

`alan/web/src/api.ts` exports `ApiError extends Error` (adds a `.status: number`, same `"${status}: ${detail}"` message format every other error already used) from the four workspace action wrappers (`archiveWorkspace`, `unarchiveWorkspace`, `stopWorkspace`, `resumeWorkspace`) plus `request()`/`deleteWorkspace` — this is what lets `useWorkspaceBulk` recover the HTTP status to classify skip-vs-fail.

## Chat page-flow scrolling, the collapsed activity line, and stick-to-bottom (calm-the-chat-reading-experience)

Build Chat and Explore Chat (`features/chat/pages/BuildChat.tsx`/`features/chat/pages/ExploreChat.tsx`,
via the shared `features/chat/components/ChatScaffold.tsx`/`features/chat/components/ChatPanel.tsx`) no
longer confine the transcript to a viewport-height box with its own inner
scrollbar above the `sm` breakpoint — see `docs/DESIGN_SYSTEM.md`'s "Two
chat scroll modes" entry for the `SCROLL_COLUMN_FLOW_CLASS`/
`SCROLL_BODY_FLOW_CLASS` constants that carry this.

`src/features/chat/hooks/useStickToBottom.ts` replaces `useAutoScroll` for the two page-flow
chat surfaces only. `useAutoScroll` always scrolled its anchor into view on
every dependency change — correct for a bounded internal scroll region,
where the anchor's own container is the only thing that can move — but
wrong once the transcript scrolls with the whole page, where an
unconditional auto-scroll would yank a reader who has scrolled up to read
an earlier reply back down to the bottom on every operation update.
`useStickToBottom(deps)` tracks whether the reader is currently within
`isNearBottom`'s threshold of `document.scrollingElement`'s bottom via a
`window` `scroll` listener — deliberately not a read taken inside the
dependency-triggered effect itself, since by the time that effect runs the
DOM has already grown to include the new content, which would make "was I
at the bottom" and "am I at the bottom after this content landed" the same
(always-false) question. The listener only fires on genuine user scrolling,
never merely from content appended below the fold, so the last position it
recorded is exactly the position that existed immediately before the update
that is now being decided — the ref it writes into is checked, not
re-measured, when a dependency-triggered effect runs. The hook returns
`{ anchorRef, pinned, jumpToLatest }`: `anchorRef` is the same
`chat-scroll-anchor` sentinel `useAutoScroll` used, `pinned` reflects the
last-recorded position, and `jumpToLatest` scrolls to the anchor and forces
`pinned` back to `true` — the one path a reader has to opt back into
following along live without scrolling by hand. `features/chat/components/ChatPanel.tsx`
renders a `Button variant="ghost"` labelled "Jump to latest"
(`data-testid="chat-jump-to-latest"`) whenever `!pinned`, positioned via
`shell/stickyOffsets.ts`'s `JUMP_TO_LATEST_CLASS` — `fixed` to the
viewport's bottom-centre, not placed between the transcript and the
repo-provisioning banner in document flow — so it stays visible at a
constant screen position regardless of how far the reader has scrolled up
the page. See `docs/DESIGN_SYSTEM.md`'s "Jump to latest" entry for the full
class composition and layering rationale.

`features/chat/components/ActivityLine.tsx` is the single primitive behind the collapsed
"Alan is working" line — see `docs/architecture/build_chat.md`'s "Per-message
operation record" section for where its `entries` come from on each side.
It renders at most one `aria-live="polite"` node (`data-testid="thinking"`,
text "Alan is thinking…") for the whole component, so a screen-reader user
is told a turn is running without having every individual operation label
announced as it changes — the current operation's label is a plain sibling
`<span>` outside the live region, updated silently. The collapsed row's
height is fixed regardless of entry count (zero, one, or fifty) because the
expand toggle button is always mounted at the app's own touch-target
minimum height and dominates the row's layout height in every state; only
the truncated last-entry label and the conditional thinking text vary
inside it. **Revised by calm-the-chat-reading-experience (explicit
reversal):** expanding used to render every entry inside an
absolutely-positioned, `max-h-40 overflow-y-auto` list overlaid on the
collapsed row, justified by a "nothing moves while you read" invariant. The
invariant itself is retained but narrowed to what it actually protects:
content must not move *unprompted* — a disclosure the reader has just
clicked open is not unprompted, it is the direct result of their own click.
The expansion is therefore now a normal-flow, full-width, wrapping,
unbounded list (no `absolute`, no `max-h`, no `overflow-y-auto`, no
`truncate` on its entries) that pushes the composer and any later messages
down exactly as any other growing content would — the same "no nested
scroll region" rule this roadmap item applies to the chat page as a whole
now applies to this disclosure too, and a conversation turn can record up
to a couple of hundred tool operations, so a fully expanded section can run
long; this is accepted, since it is opt-in and collapsed by default.
