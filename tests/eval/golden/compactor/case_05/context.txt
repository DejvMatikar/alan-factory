The decomposer evaluated the `add-workspace-export-and-import` build brief against the split-vs-keep rule in docs/ROADMAP.md's P1.3 appendix. The brief asks for two distinct capabilities: (1) a `GET /api/workspaces/{task_id}/export` endpoint that serializes a workspace's meta.json + handover YAMLs into a single archive, and (2) a `POST /api/workspaces/import` endpoint that accepts that archive and reconstructs a workspace under a fresh task_id.

Decision: split into two subtasks. Rationale: export and import touch almost entirely disjoint code paths (alan/routes/workspaces.py's read-only serialization helpers vs. alan/workspace.py's `create`-adjacent reconstruction logic), and export has zero data-integrity risk while import can corrupt `~/.alan/workspaces/` state if malformed — the two deserve independently reviewable PRs and different verification postures (import needs a fuzz-style malformed-archive test suite that export doesn't).

Forbidden actions for both subtasks: do not add a generic "workspace archive" abstraction shared between them beyond a plain `WorkspaceArchive` dataclass in alan/workspace.py; do not wire either endpoint into the frontend in this pass — `alan/web/` is explicitly out of scope until both backend endpoints are reviewed; do not touch `alan/routes/_deps.py`'s dependency wiring beyond adding the two new route registrations.

Open question (blocking): should the import endpoint require the archive's `schema_version` to exactly match the running server's handover schema version, or should it accept older versions and run the existing schema-migration helpers from alan/handover.py? Left unresolved — this changes the import subtask's scope materially (a strict-version check is a half-day task; wiring migration is a multi-day task) and needs an explicit decision before that subtask's implementation_plan iteration begins.

Next step: dispatch `export-workspace-endpoint` to implementation_plan immediately (unblocked); hold `import-workspace-endpoint` at architecture until the schema_version question above is answered, then dispatch it as a second, independent implementation_plan iteration.
